## 1. 使用方式

这份文档用于统一回答 4 个问题：

1. 某个模块的主对象是什么
2. 某个模块当前有没有 API 入口
3. 前端能力主要承接在哪个模块
4. 某个模块主要归属哪个专题设计包

默认阅读顺序：

1. 先看 [README.md](./README.md)
2. 再看本矩阵
3. 最后进入具体模块 `README.md`

## 4. API 与前端承接说明

### 4.1 API 入口主承接

- 当前后台与 mini 读取接口主要集中在 `logistics_web/controllers/`
- 证据图片类读取接口主要集中在 `logistics_trace_evidence/controllers/`
- 其余业务模块默认优先提供模型与服务能力，不直接扩散成多个控制器层

### 4.2 前端承接主模块

- 当前前端动作、组件、样式、模板和部件能力主要集中在 `logistics_web/static/src/`
- `logistics_dispatch`、`trace_core`、`trace_evidence`、`trace_exception` 主要承接业务对象与聚合数据源

## 5. 归属专题说明

- `前端设计`：重点覆盖 `logistics_dispatch`、`logistics_web`，并消费 `trace_*` 相关对象
- `企业隔离设计`：重点覆盖 `logistics_dispatch`、`logistics_trace_core`、`logistics_trace_evidence`、`logistics_trace_exception`
- `仓管设计`：当前更多关联 `logistics_base`，后续如仓储能力落地，可能扩展到新的执行/库存模块
- `高并发优化设计`：当前重点覆盖 `logistics_web` 的聚合读取和高频查询路径

## 6. 使用规则

- 需要判断“代码该落到哪个模块”时，先看“现行模块矩阵”。
- 需要判断“接口应放在哪层”时，优先收敛到 `logistics_web` 或 `logistics_trace_evidence` 的现有入口，不轻易散落到每个业务模块里。
- 需要追溯旧命名时，只进入桥接目录，不把桥接目录重新误当成现行模块。
