# 设计文件规范化治理正式规范

适用范围：

- `ai-code/docs/`
- `ai-code/专题设计/`
- 后续新增设计文件、评审文件、方案文件、验收文件与归档文件

---

## 1. Objective

建立一套可长期执行的设计文件治理基线，解决以下问题：

1. 背景、规范、方案、草稿、验收单、历史稿混放
2. 同一主题有多份文档，但没有明确主文档
3. 文件名不能反映时间、主题、类型和状态
4. 代码改了，主规范和专题方案没有同步
5. 历史资料仍被误当作现行依据

---

## 2. Boundary

本规范负责：

- 目录治理
- 文档分级
- 生效规则
- 命名规则
- 变更闭环

本规范暂不强制：

- 本轮一次性重命名全部历史文件
- 本轮把所有历史资料都物理迁入统一归档目录
- 本轮重写全部旧文档正文

本轮默认采取：

- 先建立正式治理骨架
- 再逐轮把存量文件纳入新规则

---

## 3. Behavior

### 3.1 目录分层

设计文件体系统一按以下 7 层理解：

1. `context`
2. `architecture`
3. `spec`
4. `topic_design`
5. `review`
6. `change_notes`
7. `archive`

### 3.2 各层职责

#### `context/`

放：

- 项目背景说明
- 当前业务主线
- Odoo 复用判断
- 项目理解口径

不放：

- 单模块详细设计正文
- 页面草图
- 临时执行清单

#### `architecture/`

放：

- 系统架构
- 模块边界
- addon 职责
- 依赖与桥接关系

不放：

- 单次联调记录
- 历史来源草图

#### `spec/`

放：

- 正式治理规范
- 命名规则
- 生效规则
- 文档状态模板
- 跨目录协同规则

不放：

- 背景介绍
- 一次性调研纪要

#### `topic_design/`

放：

- 专题设计总入口
- 专题包导航
- 专题体系与主体系的关系说明

说明：

- 当前专题正文的真实物理目录仍以 `ai-code/专题设计/` 为主
- `docs/topic_design/` 负责作为规范化入口层，而不是替代全部专题文件正文

#### `review/`

放：

- 检查清单
- 评审结论
- 文档治理核验规则

#### `change_notes/`

放：

- 每轮真实改动记录
- 本轮同步了哪些入口文档
- 为什么改

#### `archive/`

放：

- 历史归档规则
- 历史资料的归档入口说明
- 退场目录和历史材料的解释文件

### 3.3 文档分级

每份文档必须归入以下 5 类之一：

1. 背景说明
2. 正式规范
3. 专题方案
4. 临时草稿
5. 历史归档

推荐映射关系：

| 类型 | 默认目录 | 说明 |
| --- | --- | --- |
| 背景说明 | `context/` | 负责解释背景与当前口径 |
| 正式规范 | `spec/` / `architecture/` | 负责长期生效的正式规则或结构定义 |
| 专题方案 | `专题设计/` | 负责阶段化、专题化设计正文 |
| 临时草稿 | `context/`、专题包内待确认稿 | 必须显式保留 `draft` 或待确认标记 |
| 历史归档 | `archive/`、`99_待归档/`、`来源资料与历史草图/` | 只保留追溯价值 |

### 3.4 生效规则

每个主题只能保留一个当前主文档。

主文档必须满足：

1. 标题与主题清楚
2. 所属目录正确
3. 能说明当前状态
4. 能指向相关专题或桥接文档
5. 不让读者猜哪份算准

非主文档只能是以下角色之一：

1. 引用文档
2. 桥接文档
3. 草稿文档
4. 历史归档

如果一个主题存在多份文档：

- 只允许一份写成“当前正式入口”
- 其他文档必须在标题、文件名或正文中明确写出自身角色

### 3.5 命名规则

新文档默认命名格式：

```text
YYYY-MM-DD_主题_文档类型_状态.md
```

字段含义：

- `YYYY-MM-DD`：成文或首次落地日期
- `主题`：对象、专题或规则名称
- `文档类型`：如 `context`、`spec`、`plan`、`review`、`checklist`、`note`
- `状态`：如 `active`、`draft`、`bridge`、`archive`

示例：

- `2026-05-07_design_document_governance_spec_active.md`
- `2026-05-07_phase6_interface_checklist_draft.md`
- `2026-05-07_trace_object_mapping_bridge.md`

补充规则：

1. 稳定长期入口允许保留语义名，但正文必须声明其为正式入口
2. `draft / bridge / archive` 状态不允许省略
3. 历史文件本轮可不强制全量改名，但新增文件必须遵守

例外：

- `docs/change_notes/` 继续沿用现有 note 命名约定：
  `YYYY-MM-DD_topic_summary.md`
- 原因是该目录承担高频变更留痕职责，继续保持当前检索习惯优先于强制统一到更长格式

### 3.6 文档头部最小元数据

新增或重写的重要文档，建议在开头补齐：

```text
文档类型：
当前状态：
当前角色：
主文档：
上游文档：
下游文档：
```

最低要求：

- 至少写清“当前状态”
- 至少写清“是否为主文档”

### 3.7 变更闭环

凡是出现以下变化，必须同步检查文档：

- 改代码
- 改 API
- 改状态流转
- 改页面结构
- 改对象命名
- 改模块边界
- 改目录结构

至少同步以下内容：

1. 主规范
2. 相关专题文档
3. `change_notes`

推荐检查顺序：

1. `context/`
2. `architecture/`
3. `spec/`
4. `topic_design/`
5. `review/`
6. `change_notes/`

### 3.8 目录索引版 README 规则

阶段目录和子目录如果承担“目录入口 + 文件阅读顺序”职责，应补 `README.md`。

目录索引版 `README.md` 默认应包含：

1. 当前角色
2. 核心文件索引
3. 其余文件处理规则
4. 状态标识

分类规则：

- `现行`：当前仍作为实施、联调、评审依据
- `草稿`：待确认、草案、讨论稿
- `归档`：历史稿、来源材料、旧阶段产物

长度规则：

1. 小目录允许全量列出
2. 大目录不应把所有 `.md` 文件都堆入表格
3. 当目录内核心 `.md` 文件超过 10 个，或同类文件很多时，应改为“只列核心文件 + 其余文件处理规则”

模板入口：

- `docs/spec/directory_index_readme_template.md`

## 4. 当前实施约束

### 4.1 当前专题体系

当前专题正文仍主要位于：

- `ai-code/专题设计/前端设计/`
- `ai-code/专题设计/仓管设计/`
- `ai-code/专题设计/企业隔离设计/`
- `ai-code/专题设计/高并发优化设计/`
- `ai-code/专题设计/六期后端性能优化设计/`

因此本轮治理结论是：

- `docs/topic_design/` 作为统一入口层补齐
- `专题设计/` 继续作为正文承载层
- 后续再逐轮统一专题命名、状态和归档口径

### 4.2 当前归档策略

当前历史归档现实同时存在于：

- `专题设计/*/04_来源资料与历史草图/`
- `专题设计/*/99_待归档/`
- `ai-code/.safety_backups/`
- 历史桥接稿

因此本轮先统一归档规则，不强制一次性物理归并。

## 5. Verify

本规范落地后，至少应满足：

1. `docs/` 入口能看到 `spec / topic_design / archive`
2. 团队能区分“背景说明 / 正式规范 / 专题方案 / 临时草稿 / 历史归档”
3. 同主题默认只有一个主文档
4. 新增文档有统一命名规则
5. 改代码或规则时，能明确知道要同步 `主规范 + 相关专题 + change_notes`
