# Odoo Logistics Master Data Draft

> 状态说明：
> - 本文档当前继续保留 `draft` 命名。
> - 原因是客户、门店、人员、仓库等主数据方向仍处于待确认草图阶段，不适合升格为现行正式设计稿。
> - 默认不作为当前开发主入口；只有在主数据专题明确启动时再深入使用。

## 1. 文档定位

本文档现在明确降级为主数据方向草图，而不是一期已确认设计。

它的用途是：

- 记录客户、门店、工作人员、仓库未来可能在 Odoo 中承载的方向
- 给后续业务访谈和字段确认提供一个起点
- 避免我们忘记这些领域将来大概率需要 Odoo 扩展

它当前不是：

- 已确认的业务需求说明
- 可以直接据此完成正式开发的字段合同
- 当前项目的第一优先级模块设计来源

## 2. 为什么要调整口径

结合 D:\Desktop\ai-code-main\ai-code\系统设计\系统设计md文档\ 里的已有设计，当前真正成熟的系统设计集中在：

- 订单
- 批次
- 留痕
- 图片
- 登录认证与会话

相比之下，客户、门店、工作人员、仓库目前没有同等成熟度的功能设计，所以本文件必须被视为待确认草图。

## 3. 当前可保留的最小假设

### 3.1 客户

当前只保留一个非常弱的假设：

- 未来大概率需要一个客户主体来承接 client_id、业务归属和联系人信息

但以下问题尚未确认：

- 这个客户主体是否直接对应 Odoo 的 res.partner
- 它是纯主数据对象，还是需要参与订单权限、结算、统计
- 它和当前系统里的 tb_client 是一一对应还是需要转换

### 3.2 门店

当前只保留一个非常弱的假设：

- 未来可能需要在客户之下维护履约门店、收货点或项目点位

但以下问题尚未确认：

- 门店是否真的是长期主数据，而不是订单快照地址
- 门店是否必须和客户是父子关系
- 门店是否需要履约时间窗、签收要求、卸货要求等长期字段

### 3.3 工作人员

当前只保留一个非常弱的假设：

- 未来可能需要维护执行人员、调度、客服、管理员等对象

但以下问题尚未确认：

- 是否真的要用 hr.employee 做业务主体
- 还是只需要账号体系与操作人快照
- 司机、现场上传人员、后台管理员是否是同一套人员模型

### 3.4 仓库

当前只保留一个非常弱的假设：

- 未来可能需要引用仓库、集散点、作业点等地点对象

但以下问题尚未确认：

- 是否真的需要 stock.warehouse 级别的正式对象
- 当前业务中的仓库是库存中心，还是履约节点
- 是否会进入真实库存或 WMS 逻辑

## 4. 现阶段不应继续扩写的内容

在业务确认前，以下内容都不建议继续无限细化：

- 客户等级、生命周期、结算口径
- 门店 SLA、卸货规则、签收规则的正式枚举
- 人员角色、组织关系、调度规则
- 仓库状态、仓型、作业能力等扩展字段

这些内容可以保留方向，但不应继续写成仿佛已经被确认的正式设计。

## 5. 与 logistics_base 的关系

当前仓库里的 custom_addons/logistics_base 已经有了一个最小技术骨架，但它现在应被理解为：

- 技术预留
- 结构占位
- 未来主数据扩展的落点

而不是：

- 已经确认需求的正式一期业务模块

换句话说，logistics_base 当前可以存在，但不应该继续膨胀成一个假设过多的主数据大模块。

## 6. 后续需要业务确认的核心问题

建议后续围绕下面 4 组问题做专题确认：

1. 客户
   - tb_client 到 Odoo 中的目标对象是什么
   - 客户在 Odoo 中是权限对象、业务对象还是主数据标签

2. 门店
   - 门店是不是长期主数据
   - 门店和订单地址之间如何区分

3. 工作人员
   - 账号、员工、司机、上传人是否统一建模
   - 谁是订单责任人，谁只是操作人快照

4. 仓库
   - 当前业务是否真的需要 Odoo 库存模型
   - 还是只需要作业地点、发出地、集散点这样的轻量对象

## 7. 当前结论

主数据方向仍然值得保留，但此刻只能停留在草图层。

后续如果没有业务确认，最安全的做法是：

- 不再扩大 logistics_base 的字段范围
- 不把主数据模块作为当前第一开发主线
- 先完成订单、留痕、图片、异常这些已较明确领域的 Odoo 化设计
