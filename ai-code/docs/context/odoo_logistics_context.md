## 2. 当前系统主线

当前项目已经明确的业务组织方式是：

```text
波次记录 -> 批次 -> 运单号 -> 运单下订单列表 -> 留痕事件 -> 证据图片/备注
```

这条主线意味着：

- `波次记录` 是调度组织层对象
- `批次` 是执行组织层对象
- `运单号` 是现场留痕主对象
- `订单列表` 是运单下的履约明细
- `留痕事件` 是现场事实层
- `证据图片/备注` 是留痕事件下的证据层

最关键的口径是：

**留痕和证据围绕运单做闭环，不围绕单个订单做闭环。**

订单仍然重要，但订单在当前系统里的职责已经收口为：
- 提供业务明细
- 提供数量、重量、体积等汇总基础
- 支持从运单反查订单、从订单反查运单

它不再承担：
- 现场留痕主对象
- 图片证据直接主挂点
- 异常主挂点

## 3. 当前已稳定的设计判断

截至 2026-04-13，下面这些判断已经可以视为当前 `ai-code` 的有效设计基线。

### 3.1 对象层判断

- 运单是现场留痕主对象
- 批次是执行组织对象，不替代运单
- 波次是更高一层的调度组织对象
- 订单是运单下业务明细，不再是追溯主对象

### 3.2 分层判断

- `logistics_dispatch` 负责执行主线
- `logistics_trace_core` 负责留痕事实层
- `logistics_trace_exception` 负责问题与处理层
- `logistics_trace_evidence` 负责证据层
- `logistics_trace_dashboard` 负责聚合展示层

### 3.3 前端判断

后台前端当前不是传统 ERP 录单系统，而是：

**围绕执行主线和追溯主线展开的 Odoo Web 物流后台。**

它至少包含两条核心阅读链：

1. 执行主线  
`波次 -> 批次 -> 运单`

2. 追溯主线  
`运单 -> 留痕 -> 证据 -> 异常`

### 3.4 异常判断

- 异常不是事实层本身，而是问题对象
- 异常优先挂在 `运单 / 批次 / 留痕事件` 上
- 异常详情必须能反读到关键留痕与关键证据

## 4. 当前仓库现实与目标设计的关系

当前仓库里的 `custom_addons` 既包含已经开始落地的当前模块，也包含历史阶段保留的占位目录。

当前现实大致是：

```text
custom_addons/
  logistics_base/          # 已有基础扩展模块
  logistics_dispatch/      # 已开始承接真实执行主线代码
  logistics_order/         # 历史占位目录
  logistics_trace/         # 历史占位目录
  logistics_exception/     # 历史占位目录
```

所以要区分两件事：

1. 仓库现实  
当前文件夹里还保留旧命名、旧占位目录、旧草图文档

2. 设计现实  
当前有效设计已经转到 `dispatch / trace_core / evidence / exception / dashboard` 这组模块理解上

也就是说：

- `logistics_dispatch` 已经是当前真实实现起点之一
- `logistics_order / logistics_trace / logistics_exception` 现在主要承担历史过渡作用

## 5. 当前成熟度判断

### 5.1 已较成熟，可继续深化 Odoo 设计

| 领域 | 当前状态 | 说明 |
|---|---|---|
| 波次 / 批次 / 运单主线 | 较成熟 | 主对象层级、职责与页面主线已较明确 |
| 留痕事件 | 较成熟 | 已明确批次级与运单级留痕并存 |
| 证据链 | 较成熟 | 已明确证据挂在留痕事件下，且可由外部图片服务承接 |
| 异常层 | 中高 | 已明确异常不挂订单，需建立在运单/批次/留痕上下文之上 |
| 后台前端信息架构 | 较成熟 | 已形成系统总览、菜单结构、页面草图与交互规范 |
| 前端开发准备 | 中高 | 已形成接口总表、组件规范、开发任务拆分与联调清单 |

### 5.2 仍偏草图，不能视为已定需求

| 领域 | 当前状态 | 说明 |
|---|---|---|
| 客户 | 较弱 | 方向有了，但业务职责和字段边界未完全确认 |
| 门店 | 较弱 | 已知会复用 `res.partner` 思路，但功能范围仍需业务确认 |
| 工作人员 | 较弱 | 是否只作基础关联，还是承接流程责任，仍需进一步确认 |
| 仓库 | 较弱 | Odoo 原生仓储底座明确，但项目侧业务扩展尚未收紧 |
| logistics_base 深化范围 | 较弱 | 现在更像基础扩展层，不宜被当成一期主业务模块 |

### 5.3 当前不应再作为有效基线的旧理解

- `shipment_batch -> shipment_order -> trace_record -> trace_record_image`
- “订单是留痕主对象”
- “异常默认挂订单”
- “先把客户/门店/人员/仓库全部设计完整，再推进追溯主链”

这些都不再符合当前项目口径。

## 6. 当前 Odoo 设计工作的重点

如果只讨论设计层，不进入编译和开发运行，当前最合理的推进方式是：

### 6.1 优先继续深化的部分

- 执行主线对象设计  
波次、批次、运单、运单下订单明细

- 追溯主线对象设计  
留痕事件、证据对象、异常对象

- 后台前端设计  
菜单、页面结构、字段、动作、搜索筛选、聚合展示、技术分层

### 6.2 已可以开始并行推进的实现部分

- `logistics_dispatch` 的真实模块骨架与 P0 页面承载
- 运单列表页和运单详情页的 Odoo 视图落地
- 后续 `trace_core / exception / evidence` 的模块起步准备

### 6.3 暂时不要高估成熟度的部分

- 客户中心
- 门店中心
- 人员中心
- 仓库业务扩展
- 大而全的基础资料中心

这些不是不能做，而是目前还不应被当成“一期已收紧、只差编码”的模块。

## 8. 当前结论

当前项目已经不适合再按“订单留痕系统 Odoo 化”来理解。

更准确的理解应该是：

**这是一个基于 Odoo 的物流执行与追溯后台设计项目，并且已经开始从设计层进入真实模块落地阶段。**

它当前最稳定、最值得继续推进的部分，是：

- `波次 -> 批次 -> 运单` 执行主线
- `运单 -> 留痕 -> 证据 -> 异常` 追溯主线
- 围绕这两条主线展开的后台前端设计与模块边界设计
- `logistics_dispatch` 作为当前真实代码落点的起步模块

而客户、门店、人员、仓库这些主数据扩展，当前仍然更接近“后续补强方向”，而不是“已收口完成的一期核心模块”。
