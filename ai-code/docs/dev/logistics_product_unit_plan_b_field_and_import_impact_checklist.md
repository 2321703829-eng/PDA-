# `logistics_product_unit` 方案 B 字段清单 + 导入改造影响清单

## Objective

明确 `logistics_product_unit` 在方案 B 下的落地口径：

- 一条记录只表达一个销售单位
- 当前行只维护当前 `sale_unit_name` 对应单位自己的属性
- 不再在同一行里重复维护小/中/大单位的跨单位字段

同时明确这套设计对导入层、执行层、页面层的影响边界。

## Boundary

本清单只讨论：

- `logistics_product_unit` 字段保留/删除/兼容处理
- 商品单位导入模板和命中逻辑的改造影响

本清单不直接覆盖：

- 客户商品关系表详细字段
- 运单货物执行表改造
- 前端页面交互改造

## 基础口径

方案 B 的核心原则只有一句话：

**同一个商品的多个单位，用多条记录表达，而不是在一条记录里混放小/中/大三个单位的信息。**

推荐唯一约束保持为：

```text
unique(product_tmpl_id, spec_desc, sale_unit_name)
```

也就是：

- 同一个商品
- 同一个规格
- 同一个销售单位层级

只能有一条记录。

## 一、字段保留清单

这些字段建议保留，属于“当前单位这一行自己应该维护的信息”。

### 1. 主键与归属字段

- `product_tmpl_id`
- `sku_code`
- `spec_desc`
- `full_category_name`

### 2. 当前单位标识字段

- `unit_name`
- `sale_unit_name`
- `convert_to_base`

说明：

- `unit_name`：当前记录的单位名称
- `sale_unit_name`：当前记录所属销售单位层级，如小/中/大
- `convert_to_base`：当前单位换算到基础单位的系数

### 3. 当前单位经营字段

- `barcode`
- `standard_price`
- `purchase_price`
- `retail_price`
- `sale_tax_rate`

### 4. 当前单位尺寸与体积重量字段

- `length_cm`
- `width_cm`
- `height_cm`
- `weight`
- `volume`

说明：

- `weight`：当前单位自己的重量
- `volume`：当前单位自己的体积

### 5. 辅助属性字段

- `brand_owner_name`
- `default_vendor_name`
- `buyer_name`
- `min_order_qty`
- `can_press_stock`
- `unit_remark`

## 二、建议删除字段清单

这些字段不建议继续作为方案 B 的正式长期结构，因为它们描述的是“其他单位”的信息，会破坏“一行一个单位”的设计。

### 1. 小/中单位重量字段

- `small_unit_weight`
- `middle_unit_weight`

删除原因：

- 当前记录如果是大单位，却还存小/中单位重量，属于跨行冗余
- 同类数据应通过查询其他 `sale_unit_name` 对应记录获得

### 2. 小/中单位体积字段

- `small_unit_volume`
- `middle_unit_volume`

删除原因：

- 与 `weight` 同理，属于跨单位冗余

### 3. 大单位数量字段

- `large_unit_qty`

删除原因：

- 这个字段本质上是在当前记录里描述“与大单位的数量关系”
- 更合理的表达方式应来自 `convert_to_base` 或多单位记录间的换算关系

### 4. 大单位专属说明字段

- `volume_unit_large`
- `gross_weight_unit_large`

删除原因：

- 字段语义不稳定，且明显带有“大单位专属描述”色彩
- 如果未来真需要包装层表达，建议单独抽象，不要塞回当前单位行

## 三、可选兼容字段处理

如果你们当前已经有部分代码、模板、导入草稿在引用这些字段，不建议第一天物理删除。

更稳的处理是：

### 第一阶段

- 设计上标记为“废弃字段”
- 页面不再展示
- 导入不再写入
- 新代码不再依赖

### 第二阶段

- 确认没有实际读写后，再物理删除

## 四、方案 B 的表结构示意

### 示例：同一商品同一规格的三条记录

```text
商品 A / 500ml / 小单位 / 件
商品 A / 500ml / 中单位 / 盒
商品 A / 500ml / 大单位 / 箱
```

每条记录只维护：

- 自己这一个单位的价格
- 自己这一个单位的条码
- 自己这一个单位的重量
- 自己这一个单位的体积

而不是在“小单位”这一行里再写“大单位毛重”“中单位体积”。

## 五、导入改造影响清单

这是方案 B 最大的联动区域。

## 1. 导入模板结构要改

如果你们当前模板是“一行商品同时带出小/中/大单位信息”，方案 B 下需要调整为：

- 一行只对应一个 `sale_unit_name`
- 同一个商品如果有三个单位，就导三行

### 原有思路

```text
商品A | 小单位条码 | 中单位条码 | 大单位条码 | 小单位重量 | 中单位重量 | ...
```

### 方案 B 新思路

```text
商品A | sale_unit_name=小单位 | 当前条码 | 当前重量 | 当前体积 | ...
商品A | sale_unit_name=中单位 | 当前条码 | 当前重量 | 当前体积 | ...
商品A | sale_unit_name=大单位 | 当前条码 | 当前重量 | 当前体积 | ...
```

## 2. 导入命中规则要改

导入时的唯一命中键建议统一成：

- `product_tmpl_id`
- `spec_desc`
- `sale_unit_name`

如果导入前还没命中 `product_tmpl_id`，则前置命中流程应该先完成：

- 商品本体命中
- 再进入单位层命中

## 3. 导入校验规则要改

### 新增必填约束

- `sale_unit_name` 必填
- 当前行单位自己的重量/体积/价格按业务需要校验

### 删除旧校验

不再校验：

- 小中大三组字段必须成组出现
- 当前行必须同时提供其他单位的重量/体积

## 4. 导入错误提示要改

建议错误提示从“多单位并列校验”改成“当前单位单行校验”，例如：

- 未填写 `sale_unit_name`
- 同商品同规格同销售单位重复
- 未命中商品主档
- 当前单位换算系数非法

## 5. 导入回写逻辑要改

原来如果程序是一次把一整行拆进一条 `logistics_product_unit`，现在要改成：

- 一行导一条单位记录
- 同商品多单位要多行写入

## 六、页面联动影响清单

## 1. 商品单位维护页

页面应改成“一条记录一个单位”的理解。

页面上不再显示：

- 小单位重量
- 中单位重量
- 小单位体积
- 中单位体积
- 大单位数量

页面上只显示当前行单位自己的：

- 条码
- 价格
- 重量
- 体积
- 换算系数

## 2. 页面查询逻辑

如果后续页面需要同时展示该商品的小/中/大单位情况，不应再从同一行取值，而应：

- 先按商品 + 规格查出多条单位记录
- 再按 `sale_unit_name` 组织展示

## 七、执行层联动影响清单

## 1. 运单货物层

`goods_line` 应继续：

- 关联 `product_tmpl_id`
- 关联 `product_unit_id`
- 保留快照

不需要因为方案 B 改成跨单位存储。

## 2. 风险点

如果执行层代码之前默认：

- 从当前 `product_unit_id` 一行里拿到小/中/大所有单位属性

那这些逻辑都要改成：

- 查当前单位这一行
- 或者按同商品同规格查其他 `sale_unit_name`

## 八、工作量评估

按“先设计收口、再分阶段实现”估算：

### 数据库层

- 中等偏小
- 本质是删/废弃几列，不是大规模重构主表

### 导入层

- 中等偏大
- 是这次最大改造面

### 页面层

- 中等
- 主要是维护页和展示逻辑要转为多行理解

### 风险等级

- 开发阶段：中等可控
- 如果模板和导入逻辑已经大量联调：中等偏大

## 九、推荐执行顺序

### 第一步

先冻结设计稿：

- `logistics_product_unit` 正式采用方案 B

### 第二步

同步导入模板口径：

- 一行一个 `sale_unit_name`

### 第三步

调整商品单位维护页和查询逻辑：

- 不再依赖跨单位字段

### 第四步

最后再做旧字段下线：

- 先停用
- 再删除

## Final Recommendation

如果你们已经确定采用方案 B，那么最重要的不是“马上删字段”，而是：

1. 先把表结构口径定死为“一行一个单位”
2. 先把导入模板改成多行表达
3. 再逐步把页面和执行层从跨单位字段依赖里移出来

这样改，成本主要集中在导入层，但长期结构会干净很多。
