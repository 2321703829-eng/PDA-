# structural_governance_one_page_plan

## 1. 目标

在不打断当前开发的前提下，用一轮轻量治理把当前项目的版本、架构、文档和目录口径先收成可持续状态。

这轮计划只追求：

1. 建立版本锚点
2. 收口正式入口
3. 标清新旧命名角色
4. 形成后续可重复执行的流程

---

## 2. 边界

本轮纳入：

- Git tag 规范建立
- 文档/目录治理规范建立
- 核心入口文档同步
- 首轮治理清单和节奏

本轮不纳入：

- 大规模重命名文件夹
- 一次性清空所有历史文档
- 强制改造所有分支策略
- 对每个 addon 做深度架构重构

---

## 3. 当前判断

当前最主要的问题不是“没有设计”，而是：

1. 设计和实现已经走到新主线，但部分入口文档仍停留在旧目录现实
2. 新旧模块并存，但没有形成统一治理语义
3. 仓库还缺少项目级 tag 锚点
4. 文档治理已有片段规则，但没有形成主管可复述的结构性方案

---

## 4. 三阶段推进

### Stage 1: 建基线

目标：
- 先让团队知道“现在什么算当前有效版本、当前有效入口”

动作：
- 建立 `version_tag_governance`
- 建立 `document_directory_governance`
- 更新 `ARCHITECTURE / context / custom_addons_blueprint / doc_sync / upgrade_and_verify`
- 选定首个 `baseline/...` tag 候选点

产出：
- 一套正式治理口径
- 一组同步后的入口文档

### Stage 2: 做清单

目标：
- 把“要整理什么”列清楚，而不是一上来全仓库动刀

动作：
- 列出现行有效文档清单
- 列出桥接文档清单
- 列出历史归档文档清单
- 列出后续建议重命名或迁移的目录清单

产出：
- 一份可排期的治理 backlog

### Stage 3: 分批执行

目标：
- 把治理变成持续动作，而不是一次性突击

动作：
- 每轮只处理一类主题：
  - 模块命名
  - 页面入口
  - 历史桥接
  - 发布基线
- 每轮都补 change note
- 每轮需要时创建新 baseline 或 milestone tag

产出：
- 可持续迭代的治理节奏

---

## 5. 角色建议

### 主管

关注：
- 当前阶段基线是否明确
- 哪些是正式入口
- 哪些历史内容可以保留但不再干扰当前决策

### 架构/设计负责人

关注：
- 主对象、模块边界、页面主线是否一致
- 新文档是否进入正确目录
- 历史文档是否已标清角色

### 开发负责人

关注：
- 哪个 tag 是当前开发基线
- 哪些 addon 是当前真实实现模块
- 哪些目录不要继续深化

---

## 6. 两周内可执行的轻量方案

### 第 1 周

- 确认首个 `baseline` 候选提交
- 同步治理规范与入口文档
- 收口“当前有效 / 桥接 / 历史”三层口径

### 第 2 周

- 输出首轮目录/文件命名治理 backlog
- 选 1 到 2 个高收益点先做
- 给主管汇报第一轮治理结果和下一轮范围

---

## 7. 首轮验收标准

满足下面条件即可认为首轮治理完成：

1. 团队知道应该从哪几份文档开始读
2. 团队知道当前真实实现模块是哪几组
3. 团队知道旧目录为什么还在，但不应继续当主入口
4. 团队知道什么时候该打 tag
5. 后续每轮变更都有 change note 和文档同步意识

---

## 8. 风险

### 风险 1

只改文件名，不先收口业务主线和模块边界。

后果：
- 表面更整齐，实际更混乱。

### 风险 2

治理文档新开很多，但没有挂回现有入口。

后果：
- 又形成一套并行文档体系。

### 风险 3

过早大规模清理历史文档。

后果：
- 丢失桥接价值，影响回溯。

---

## 9. 当前建议

当前最稳妥的推进方式是：

1. 先确立 baseline 和治理入口
2. 再按清单分批整理
3. 每轮只做少量高收益收口

这样最符合你们现在“设计已较多实现，但结构仍需治理”的阶段特点。
