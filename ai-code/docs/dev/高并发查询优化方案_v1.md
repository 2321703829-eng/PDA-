# 高并发查询优化方案 v1

## 1. 目标

基于首轮高并发查询调查结果，给出一版可执行的优化路径。

本方案只聚焦当前已确认的主要风险：

- `/api/admin/logistics/dashboard/summary`
- `/api/admin/logistics/boss_trace/summary`
- 统计中心接口

并按 3 个层次拆解：

- 短期止血
- 中期重构
- 长期架构

## 2. 当前判断

当前风险不是“所有查询都危险”，而是结构上已经出现明显分层：

- 首页摘要：中风险
- 老板页摘要：低到中风险
- 统计中心：高风险，优先级最高

首轮结论已经说明：

1. 首页和老板页的问题更多是：
   - 多次 ORM 查询
   - 局部 Python 聚合
2. 统计中心的问题更本质：
   - 时间范围内全量 `search`
   - Python 侧 `filtered / grouped / bucket / ranking`
   - 数据量和并发一放大后，响应时间和 worker 压力都会线性变差

## 3. 优化总原则

### 原则一：先改数据访问模式，再谈加机器

当前最大风险点是查询模式本身。

在没有改掉：

- 全量取数
- Python 内存聚合
- 多次相似查询

之前，单纯加 worker 或加机器收益有限。

### 原则二：先止血，再重构，再架构升级

优化顺序建议固定为：

1. 先做低风险、低成本、见效快的止血项
2. 再做统计中心的查询模式重构
3. 最后再决定是否引入预聚合或统计快照层

### 原则三：优先保证统计口径不变

性能优化不能顺手改业务定义。

每次优化前都要锁定：

- 指标口径
- 时间范围定义
- 去重规则
- 状态归类规则
- 排行榜排序规则

## 4. 短期止血

目标：

- 不大改结构
- 优先降低明显浪费
- 先把首页、老板页、统计中心中最容易优化的点收掉

### 4.1 首页与老板页：把 `search + len` 改成数据库计数

适用对象：

- `dashboard/summary`
- `boss_trace/summary`

当前问题：

- 明明只需要数量，却先 `search(...)` 拉出记录，再 `len()`

优化方式：

- 直接改成 `search_count()`
- 或改成更少次的数据库聚合查询

收益：

- 减少不必要的记录集构建
- 降低 Python 侧对象开销

难度：`低`

风险：`低`

### 4.2 高风险批次数：把 Python 去重改成数据库去重

适用对象：

- `dashboard/summary`
- `boss_trace/summary`

当前问题：

- 先查异常记录
- 再 `mapped("batch_id.id")`
- 再 Python 去重

优化方式：

- 优先尝试 `read_group`
- 如果口径不够，改成定制聚合 SQL

收益：

- 降低记录拉取量
- 降低 Python 去重开销

难度：`低到中`

风险：`低`

### 4.3 确认索引命中并补齐薄弱索引

首批必查字段：

- `logistics_dispatch_waybill.delivery_date`
- `logistics_dispatch_waybill.state`
- `logistics_trace_exception.report_time`
- `logistics_trace_exception.state`
- `logistics_trace_exception.exception_type`
- `logistics_trace_exception.batch_id`
- `logistics_trace_exception.severity_level`

优化方式：

- 先 `EXPLAIN ANALYZE`
- 确认是否走索引
- 对组合过滤高频场景评估组合索引

收益：

- 对首页、老板页、统计页都会有基础收益

难度：`低`

风险：`低`

### 4.4 首页摘要查询批次收紧

当前问题：

- 一次首页加载会打多次摘要/统计查询

优化方式：

- 合并部分可同批返回的口径
- 减少前端首屏并行请求数

收益：

- 降低瞬时查询风暴
- 改善首页首屏稳定性

难度：`中`

风险：`低到中`

## 5. 中期重构

目标：

- 把统计中心从“能跑”改成“更适合并发”
- 重点改数据访问模式

### 5.1 统计中心 `overview` 改为聚合查询

当前问题：

- `overview` 先拉时间范围内所有 `waybill`
- 再拉所有 `exception`
- 再在 Python 里算：
  - 运单数
  - 签收率
  - 超时率
  - 异常数

优化方式：

- 能用 `read_group` 的先用 `read_group`
- 比率类指标可以拆成：
  - 分子聚合
  - 分母聚合
  - 最后再计算

收益：

- 明显减少对象装载量
- 更适合高并发

难度：`中`

风险：`中`

### 5.2 统计中心 `distributions` 改为数据库分组

当前问题：

- 分布类指标现在是整批数据取回后再 Python 分组

优化方式：

- `exception_type_distribution` 用数据库分组
- `region_waybill_distribution` 优先用数据库分组
- 对复杂区域映射，必要时补维表或预处理字段

收益：

- 分布类查询会先稳定下来
- 是中期最值得优先落地的一组改造

难度：`中`

风险：`中`

### 5.3 统计中心 `trends` 改为按 bucket 聚合

当前问题：

- 先全量拉记录
- 再按日/周/月切 bucket

优化方式：

- 用数据库端按时间粒度聚合
- 将 bucket 粒度下沉到 SQL 层
- Python 只做结果整形，不再做主计算

收益：

- 趋势查询的扩展性会明显变好

难度：`中到高`

风险：`中`

### 5.4 统计中心 `rankings` 分层重构

当前问题：

- 排行类往往最复杂
- 容易掺杂多层 Python 计算

优化方式：

- 先拆成：
  - 批次排行
  - 区域排行
  - 司机排行
- 能数据库聚合的优先数据库聚合
- 对逻辑过重的排行榜，评估是否直接进入长期方案

收益：

- 排行接口性能可控
- 便于后续做缓存或快照

难度：`中到高`

风险：`中`

### 5.5 抽公共统计访问层

当前问题：

- 每个统计方法自己拿 `waybills / exceptions`
- 重复逻辑多

优化方式：

- 建一层统计查询服务
- 统一封装：
  - 时间范围过滤
  - 状态过滤
  - 聚合查询
  - 指标口径

收益：

- 便于维护
- 便于做统一缓存和压测

难度：`中`

风险：`中`

## 6. 长期架构

目标：

- 让统计/看板真正具备更稳定的高并发承载能力
- 避免每次页面请求都实时重算

### 6.1 引入预聚合表 / 统计快照层

适用场景：

- 老板页
- 高频统计页
- 固定时间窗口指标
- 排名榜单

做法：

- 按天/批次/区域/司机等维度生成快照
- 页面优先读快照，不直接扫业务主链表

收益：

- 查询延迟最稳定
- 最适合中高并发读取

难度：`高`

风险：`中到高`

### 6.2 建立异步统计刷新机制

适用场景：

- 对实时性要求不必秒级一致的统计页面

做法：

- 通过 cron / job / queue 刷新统计结果
- 读写分离：
  - 写业务主链
  - 读统计结果层

收益：

- 把统计压力从页面请求链里拿出去

难度：`高`

风险：`中`

### 6.3 对高频首页摘要做缓存层

适用场景：

- 首页摘要
- 老板页摘要

做法：

- 设短 TTL 缓存
- 或按事件增量刷新缓存

收益：

- 在多人同时打开首页时收益明显

难度：`中到高`

风险：`中`

### 6.4 建立持续性能观测基线

做法：

- 长期开启 `pg_stat_statements`
- 固定慢 SQL 采样
- 建一套：
  - Top SQL
  - 接口 P95
  - 统计页耗时
  - worker 负载

收益：

- 后续不会每次都靠临时排查

难度：`中`

风险：`低`

## 7. 难度评估

### 低难度

- `search + len` 改 `search_count`
- Python 去重改数据库去重
- 补索引、校验索引命中

特点：

- 改动小
- 见效快
- 回归风险低

### 中难度

- 首页摘要合并查询
- `overview / distributions` 改数据库聚合
- 抽公共统计访问层

特点：

- 需要对齐业务口径
- 需要补验证

### 中到高难度

- `trends / rankings` 重构
- 复杂统计改 SQL 聚合

特点：

- 性能收益大
- 口径验证复杂

### 高难度

- 预聚合表
- 统计快照层
- 异步刷新链

特点：

- 不只是优化，是统计架构升级

## 8. 推荐实施顺序

### 第一阶段：1 个短迭代先止血

建议先做：

1. 首页/老板页 `search + len` 清理
2. 高风险批次数数据库去重
3. 统计中心核心索引核查与补齐

目标：

- 先降低明显浪费
- 为第二阶段重构打基础

### 第二阶段：1 到 2 个迭代重构统计中心

建议顺序：

1. `overview`
2. `distributions`
3. `trends`
4. `rankings`

目标：

- 把最危险的“全量取数 + Python 聚合”模式逐步替换掉

### 第三阶段：根据压测结果决定是否架构升级

如果第二阶段后仍不能满足并发目标，再进入：

1. 预聚合表
2. 统计快照
3. 缓存层

## 9. 当前建议

如果现在只允许做一轮优化，我建议优先级就定成：

1. 先优化统计中心
2. 再优化首页摘要
3. 最后收老板页摘要

原因很简单：

- 最容易先出问题的是统计中心
- 最容易先做出效果的是首页/老板页

所以策略应该是：

- **先盯最危险的点**
- **同时拿几个低成本项先止血**

## 10. 结论

这批风险总体上是：

- 能解决
- 但不是一轮小修就能把统计中心彻底做成高并发友好型

最稳的方案不是一步到位，而是：

- 短期止血
- 中期重构
- 长期架构升级

一句话总结：

**首页和老板页更容易先优化，统计中心更值得先优化；真正决定系统高并发查询上限的，会是统计中心这条链的重构质量。**
