# 高并发查询调查清单 v1

适用范围：
- 当前 `Odoo` 物流项目的查询承载调查
- 重点针对首页、看板、统计、结果页、主数据查询页
- 不直接用于证明“系统已经具备高并发能力”，而用于形成首轮调查结论

## 1. 目标

这份清单要回答 4 个问题：

1. 当前项目的高并发查询热点到底在哪些页面和接口
2. 当前实现里哪些地方更可能先成为瓶颈
3. 现阶段应当如何做首轮压测和观测
4. 哪些结果可以判定为 `通过 / 待优化 / 明显不通过`

## 2. 边界

本轮调查只关注：

- 后台查询承载
- 页面聚合查询
- 列表页分页查询
- 结果页任务明细查询
- 统计分析类查询

本轮不直接展开：

- 图片二进制服务本体压测
- 导入写入链大批量并发写入压测
- 外部对象存储带宽压测
- 浏览器端渲染 FPS 优化

## 3. 当前判断基线

当前代码已经足够支持“调查”，但还不能直接支持“下结论说可承载高并发”。

主要依据：

  - 参考：[logistics_dashboard_service.py](/D:/Desktop/Odoo/custom_addons/logistics_web/models/logistics_dashboard_service.py:15)
- 统计页存在时间范围内全量拉取后 Python 分桶统计
  - 参考：[logistics_stats_service.py](/D:/Desktop/Odoo/custom_addons/logistics_web/models/logistics_stats_service.py:13)
- 主链关键表已经补过部分索引
  - 参考：[post-migration.py](/D:/Desktop/Odoo/custom_addons/logistics_dispatch/migrations/19.0.1.1.0/post-migration.py:1)
- 结果页与任务页已经做了分页，不是无限列表查询
  - 参考：[waybill_standard_import_service_v2.py](/D:/Desktop/Odoo/custom_addons/logistics_web/services/waybill_standard_import_service_v2.py:745)

## 4. 调查对象优先级

### P0 必查

1. 首页
- 页面：物流首页
- 风险：一次进入触发多次并发统计请求
- 重点接口：
  - `/api/admin/logistics/dashboard/summary`
  - `logistics.dispatch.waybill.search_count`
  - `logistics.trace.exception.search_count`

2. 老板页 / 看板页
- 页面：异常看板、老板追溯页、统计中心入口
- 风险：聚合查询多，且有 Python 内存聚合
- 重点接口：
  - `/api/admin/logistics/boss_trace/summary`
  - `/api/admin/logistics/stats/*`

3. 统计中心
- 页面：趋势、分布、排行
- 风险：时间范围拉宽后全量搜索 + Python 分桶
- 重点代码：
  - [logistics_stats_service.py](/D:/Desktop/Odoo/custom_addons/logistics_web/models/logistics_stats_service.py:13)

### P1 次查

4. 导入结果页
- 页面：导入结果头、行结果、错误明细
- 风险：分页查询相对可控，但任务量大时仍可能有压力
- 重点接口：
  - `/api/admin/logistics/imports/tasks/{task_no}`
  - `/lines`
  - `/errors`

5. 导出结果页
- 页面：导出任务头、行结果、错误明细
- 风险：分页链是否稳定、导出任务数多时是否有慢查询
- 重点接口：
  - `/api/admin/logistics/exports/tasks/{task_no}`
  - 相关 lines/errors 接口

6. 主数据查询页
- 页面：客户、商品、司机、车辆
- 风险：搜索、筛选、分页是否命中索引

## 5. 调查前准备

### 环境

至少准备 3 套数据量口径：

1. 小样本库
- 验证功能可跑通

2. 接近真实联调库
- 用于首轮承载判断

3. 放大样本库
- 至少把主链数据放大到真实量级的 3 到 10 倍

### 数据量建议

首轮建议至少覆盖：

- `waybill`：10 万 / 30 万 / 100 万
- `customer_line`：随运单层级联动放大
- `order_line`
- `goods_line`
- `trace_exception`

### 观测工具

至少开启下面 4 类观测：

1. PostgreSQL 慢查询日志
2. `pg_stat_statements`
3. Odoo SQL 日志或调试日志
4. 系统层 CPU / 内存 / 连接数监控

## 6. 调查步骤

### Step 1：先做静态热点梳理

逐页列出：

- 页面入口
- 页面首次加载请求数
- 每个请求调用的模型方法
- 是否分页
- 是否会在 Python 侧做二次聚合

输出物：

- 页面 -> 接口 -> ORM/SQL 路径清单

### Step 2：抓真实 SQL

针对 P0 页面操作一次，记录：

- 最慢 SQL
- 调用次数最高 SQL
- 平均耗时最高 SQL
- 返回行数异常大的 SQL

输出物：

- Top 20 SQL 清单

### Step 3：单接口压测

不要一上来压整站，先压单接口。

优先顺序：

1. `/api/admin/logistics/dashboard/summary`
2. `/api/admin/logistics/boss_trace/summary`
3. `/api/admin/logistics/stats/...`
4. `/api/admin/logistics/imports/tasks/{task_no}/lines`
5. `/api/admin/logistics/exports/tasks/{task_no}/lines`

每个接口至少做：

- 10 并发
- 30 并发
- 50 并发
- 100 并发

记录：

- P50
- P95
- P99
- 错误率
- 超时率

### Step 4：组合场景压测

模拟真实后台使用节奏：

- 多人同时打开首页
- 同时查看看板
- 同时点导入结果页
- 同时跑导出结果页

目标不是极限压测，而是模拟“日常高峰时段”。

### Step 5：定位瓶颈归类

每个问题要归到 1 类，不要混说：

1. 索引缺失
2. ORM 查询次数过多
3. Python 内存聚合过重
4. 页面首屏请求数过多
5. 分页粒度不合理
6. 数据模型字段设计不利于过滤
7. 连接数/worker 数不足

## 7. 通过标准建议

### 首页 / 看板 / 统计页

- 10 并发：P95 小于 1 秒
- 30 并发：P95 小于 2 秒
- 50 并发：P95 小于 3 秒
- 错误率接近 0

### 分页结果页

- 30 并发：P95 小于 1.5 秒
- 100 行以内分页查询应保持稳定

### 明显不通过的信号

出现任一项就应判为“待优化”：

- 单页请求中出现 1 条以上 3 秒慢 SQL
- 单接口 30 并发已经明显超时
- PostgreSQL CPU 长时间打满
- Odoo worker 明显阻塞
- 统计页通过“全量 search + Python 分桶”导致响应时间随数据量线性劣化

## 8. 当前代码下的重点风险假设

本轮调查前可以先带着这几个假设去验证：

1. 首页多次 `search_count` 在数据量放大后会先成为热点
2. 统计页的 Python 侧聚合会比导入结果页更早出问题
3. `read_group` 和预聚合替换空间主要在统计中心，不在结果页
4. 导入导出任务页压力更多是“任务记录数量”问题，不是主链最大瓶颈

## 9. 首轮建议输出物

调查结束后至少要产出：

1. 热点页面与接口清单
2. Top SQL 清单
3. 慢查询截图或导出
4. 三档并发结果表
5. P0 优化建议
6. P1 延后建议

## 10. 首轮优化方向预告

如果调查结果和当前静态判断一致，后续优化大概率集中在：

1. 把首页和看板的部分查询改成聚合接口
2. 把统计页从“全量 search + Python 分桶”改成：
- `read_group`
- SQL 聚合
- 或预聚合表
3. 对高频筛选字段继续补索引
4. 收紧页面首屏请求数
5. 对统计类页面增加缓存或按时间粒度预计算

## 11. 本轮结论

当前工作区代码：

- **足以支撑高并发查询调查**
- **不足以直接证明系统已经具备高并发承载能力**

所以正确动作不是先争论“能不能扛”，而是按这份清单把热点查询链跑一遍，再基于真实 SQL 和真实并发结果定优先级。
