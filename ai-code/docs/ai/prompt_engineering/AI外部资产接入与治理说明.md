# AI外部资产接入与治理说明

## 目的

规范外部 `skills`、`rules`、`docs`、提示词和其他 AI 协作资产进入当前 `ai-code` 项目的方式，避免“外部材料很多，但一并进来后反而把项目带偏”。

这份文档关注的是：

- 外部 AI 资产怎么进入项目
- 进入前怎么筛选
- 进入后怎么治理
- 哪些能原样接入，哪些必须改写

## 适用范围

- `ai-code/_upstream/`
- `ai-code/.agents/skills/`
- `ai-code/docs/ai/`
- 与 AI 协作规则相关的筛选、适配、试点和淘汰动作

## 当前原则

### 1. 项目规则优先

当前项目中，优先级从高到低如下：

1. `AGENTS.md`
2. `docs/ai/`
3. `docs/context/`
4. `docs/architecture/ARCHITECTURE.md`
5. 本地 `.agents/skills/`
6. 已适配并正式接入的外部资产
7. `_upstream/` 中的隔离参考库

结论：

`_upstream/` 中的内容默认不是当前项目生效规则。

### 2. 隔离优先于并入

外部仓库先放入隔离目录，再筛选。

推荐目录：

- `ai-code/_upstream/<repo-name>/`

不建议的做法：

- 直接把外部 `skills/` 散复制到 `.agents/skills/`
- 直接把外部 `rules` 并入现有 `docs/ai`
- 在未筛选前把外部提示词当默认总控规则

### 3. 改写优先于原样复用

对当前 Odoo 物流项目，真正适合原样接入的外部资产通常很少。

大多数高价值内容都应该：

- 保留方法论
- 去掉私有平台术语
- 去掉不相关技术栈绑定
- 改成当前项目自己的业务语言和目录落点

## 生命周期

### Stage 1: 引入

把外部仓库放到 `_upstream/`，只作为参考库。

### Stage 2: 第一轮筛选

按三类归档：

- `可直接复用`
- `需改写`
- `不建议引入`

筛选结果应沉淀到：

- `docs/review/`
- `docs/change_notes/`

### Stage 3: 本地适配

只把真正有价值的内容改写进：

- `.agents/skills/`
- `docs/ai/`

改写时要遵守：

- 当前项目主线
- Odoo 原生能力优先比对
- Outcome / Behavior / Boundary
- 文档同步要求

### Stage 4: 试点

新接入的本地 skill 或规则，先小范围试点，不默认扩展成全局最高规则。

### Stage 5: 晋升或淘汰

试点后再决定：

- 晋升为正式本地规则
- 保持为专项 skill
- 回退为参考材料
- 淘汰

## 分类标准

### 可直接复用

同时满足以下条件时，才建议原样引入：

- 不依赖私有平台、私有 CLI、私有服务
- 不绑定错误技术栈
- 不改写当前项目边界
- 不和 `AGENTS.md`、`docs/ai` 冲突

### 需改写

满足以下任意一点，就应改写后再接入：

- 方法论有价值，但术语不匹配
- 流程有价值，但工具依赖不匹配
- 输出模板有价值，但目录落点不匹配
- 内容正确，但业务对象和当前项目不同

### 不建议引入

满足以下任意一点，就不建议进入主链：

- 强绑定其他技术栈
- 强绑定其他业务平台
- 与当前项目边界冲突
- 与现有系统级能力重复且收益低

## 接入检查清单

每次准备接入外部 AI 资产前，至少检查：

- 是否已经完成隔离存放
- 是否已经做第一轮筛选
- 是否明确归类
- 是否说明了为什么值得进入主链
- 是否明确落点是 `.agents/skills/` 还是 `docs/ai/`
- 是否补了 `docs/change_notes/`

## 变更与同步

当外部 AI 资产正式进入本地主链时，至少要同步：

- `docs/change_notes/`
- 必要时同步 `docs/review/`
- 必要时同步 `docs/ai/`

如果改动影响仓库级 AI 工作规则，再评估是否需要更新：

- `AGENTS.md`

## 当前落地方式

当前项目对外部 AI 资产采用：

- 上游仓库隔离保存
- 先筛选
- 再做项目化改写

而不是：

- 外部规则整仓并入
- 原样替换当前项目规则

## 结论

对当前 `ai-code` 而言，外部 AI 资产最合适的角色是：

- 上游参考库
- 方法论来源
- 局部能力补丁

而不是当前项目的默认最高规则来源。
