# AI验证与回归规则

## 目的

为当前 `ai-code` 项目里的 AI 协作提供一套更贴近 Odoo 物流项目现实的验证与回归规则。

这份规则不追求“所有改动一律 80% 覆盖率”或“所有任务强制 TDD”，而是强调：

- 升级可跑
- 关键链路可验
- 权限边界不回归
- 页面、接口、导入导出等关键行为可回读
- 无法验证时要明确说明，不要假装已经验证

## 适用范围

- `.agents/skills/` 驱动下的本地 AI 协作
- `custom_addons/` 下的 Odoo 物流相关 addon
- 与模块升级、接口、视图、权限、导入导出、前端联调相关的真实改动

## 当前基线

验证优先遵守以下本地材料：

1. `AGENTS.md`
2. `docs/dev/upgrade_and_verify.md`
3. `docs/context/`
4. `docs/architecture/ARCHITECTURE.md`
5. 相关设计文档与 `docs/change_notes/`

## 核心原则

### 1. 升级与可运行优先于抽象覆盖率目标

当前项目首先要保证：

- addon 可安装或升级
- 关键页面可打开
- 关键接口可调用
- 权限不明显越权
- 文档与变更记录同步

在这个前提下，再补更细的测试或回归验证。

### 2. 关键链路验证优先于平均用力

不要为了追求形式上的“全都测一点”，反而漏掉最关键的链路。

优先验证：

- `wave / batch / waybill` 执行主线
- `waybill / trace / evidence / exception` 追溯主线
- 导入、导出、结果页、下载链
- 权限、访问、上传、下载等高风险路径

### 3. 鼓励测试先行，但不把它变成僵硬门槛

对于纯逻辑、服务层、工具函数、格式转换、数据映射等改动，优先考虑先写测试或至少先写可验证样例。

但对于 Odoo 模型、XML 视图、权限、动作绑定、资产注册等改动，不应机械套用“先写测试再写代码”的口号，而应选择更适合的验证方式。

### 4. 无法验证时必须诚实披露

如果本轮没有跑升级、没有跑 smoke、没有跑页面、没有跑接口，就必须明确说出来。

不能把“静态阅读通过”表述成“已经验证通过”。

## 按改动类型的最小验证要求

### 改模型 / 字段 / 关系

至少验证：

- 模块可升级
- 字段存在且可读写
- 必填、默认值、关联关系没有明显异常
- 旧数据读取路径没有明显断裂

### 改视图 / 菜单 / 动作

至少验证：

- 对应菜单或动作可打开
- `list / form / search` 没有明显缺字段
- 按钮、跳转、client action 注册正常

### 改权限 / ACL / 记录规则

至少验证：

- 目标角色可访问
- 非目标角色不会明显越权
- 关键 create / read / write / download 路径符合预期

### 改 controller / API / 下载上传链

至少验证：

- 关键请求可走通
- 返回壳、字段、错误码与当前契约一致
- 无权限或异常时有合理报错
- 上传 / 下载 / 访问 key 相关路径没有明显越权

### 改导入 / 导出 / 任务链 / 结果页

至少验证：

- 主链路可从入口走到结果页或结果回读
- 任务号、状态、下载、错误明细链路一致
- 与既有模板、字段映射或任务契约不冲突

### 改前端资产 / OWL / 模板 / 注册表

至少验证：

- 资产已纳入 manifest
- 对应 action / template / registry 可正常命中
- 页面不因模板缺失或 tag 未注册而直接报错

### 只改文档 / skill / 规则

至少验证：

- 新文件存在
- 目录落点合理
- 与当前 `AGENTS.md`、`docs/ai/`、本地主线不冲突
- `docs/change_notes/` 已同步

## 推荐验证层级

### Level 1：静态验证

适用于文档、skill、轻量配置、明显不涉及运行态的改动。

常见方式：

- 结构检查
- 路径存在检查
- Python AST / XML 解析
- 引用与命名检查

### Level 2：升级 / 接口 / 页面 smoke

适用于大多数真实业务改动。

常见方式：

- 模块安装或升级
- 页面打开
- 接口调用
- 浏览器点击主链路
- 简单权限验证

### Level 3：场景化回归

适用于高风险改动或关键链路调整。

常见方式：

- 导入后结果回读
- 导出后下载与错误报告
- 多角色权限对照
- 旧数据读取回归
- 关键主线端到端 smoke

## AI输出要求

当 AI 完成一次真实改动时，验证部分至少应明确说明：

- 实际做了哪些验证
- 没做哪些验证
- 当前结论基于静态检查、smoke 还是更完整回归
- 是否需要补充人工验证

推荐表达方式：

- `已做：...`
- `未做：...`
- `风险：...`

## 不建议照搬的上游规则

对于当前项目，不建议直接照搬以下上游思路：

- 强制 80% 覆盖率作为所有任务统一门槛
- 所有任务一律先写测试再写实现
- 用单一测试形式覆盖所有类型改动

更合适的做法是：

- 按风险和改动类型选择验证方式
- 优先验证升级、权限、页面、接口、主链路
- 如无法验证，诚实披露并给出下一步建议
