# Mini API 安全设计说明

## 1. 文档目的

本文档用于定义 Odoo 19 物流小程序接口的安全收口方案，覆盖：

- 当前联调阶段的最小安全要求
- 不影响司机现有使用的渐进式切换策略
- 后续升级为更完整司机身份体系时的演进方向

本文档的设计对象包括但不限于：

- `GET /api/mini/logistics/waybills/<no>/stops`
- `POST /api/mini/logistics/traces`
- `POST /api/mini/logistics/evidences`
- `POST /api/mini/logistics/evidences/<id>/images`

---

## 2. 背景问题

当前小程序链路在快速联调阶段为了先打通业务，曾采用：

- `auth="public"`
- `csrf=False`
- controller 内部 `sudo()` 读写

这样做的优点是：

- 前后端联调阻力小
- 司机端可以快速验证查站点、建留痕、传图片、回显图片

但对应的问题也很明显：

- 没有应用级准入控制
- 没有用户级身份识别
- 任何能命中接口的人都可能直接读写业务数据

因此必须补安全方案，但又不能粗暴上锁，避免影响当前司机端使用。

---

## 3. 设计目标

### 3.1 Outcome

- 小程序接口不再长期保持“完全开放写入”
- 安全能力可以逐步启用，不影响当前司机端联调
- 启用后，只有携带正确凭证的小程序请求可以访问 mini 接口
- 方案能从“应用级 token”平滑演进到“司机级身份”而不推翻现有链路

### 3.2 Behavior

- 默认状态下，mini token 校验可关闭
- 当服务端开关打开后，mini 请求必须携带正确 token
- token 错误或缺失时，接口返回 `401`
- token 校验通过后，后端才允许继续做 `sudo()` 读写

### 3.3 Boundary

- 本文档先解决 mini 接口的**应用级安全准入**
- 不在本轮直接引入司机登录态、手机号登录、设备绑定等完整身份体系
- 不改变当前小程序业务接口契约
- 不要求司机手工输入 token

---

## 4. 当前推荐方案：开关式应用级 token 鉴权

## 4.1 核心思路

采用“**默认兼容、显式开启**”的方式：

- 服务端保留 token 校验能力
- 默认不开启，不影响司机当前使用
- 等小程序端和后端都准备好后，再打开开关正式启用

这是一种渐进式切换策略。

---

## 5. 服务端配置项

建议使用两个配置项：

### 5.1 启用开关

- `logistics_web.mini_api_token_enabled`

可取值：

- `true / 1 / yes / on`
- `false / 0 / no / off`

说明：

- 当为真时，mini 接口强制校验 token
- 当为假或未配置时，mini 接口按当前兼容模式继续放行

### 5.2 token 值

- `logistics_web.mini_api_token`

说明：

- 当启用开关为真时，服务端使用该 token 做请求校验
- 也可允许环境变量兜底：
  - `LOGISTICS_MINI_API_TOKEN`

---

## 6. 客户端传参方式

推荐优先使用 Header 传 token。

### 6.1 支持的 Header

- `X-Mini-Api-Token`
- `X-Mini-Token`
- `X-App-Token`

建议统一收口为：

- `X-Mini-Api-Token`

### 6.2 兼容的 body/query 字段

为了兼容不同调用方式，可暂时支持：

- `mini_api_token`
- `miniApiToken`
- `token`
- `app_token`
- `appToken`

### 6.3 推荐口径

最终建议只保留：

- Header：`X-Mini-Api-Token`

这样最清晰，也最利于排查。

---

## 7. 权限状态对业务的影响

### 7.1 当前关闭开关时

表现：

- 司机仍可像现在一样正常使用小程序
- 不需要司机手工做任何额外动作
- 上传留痕、创建证据、上传图片流程不受影响

### 7.2 打开开关但小程序未带 token 时

表现：

- mini 接口返回 `401`
- 司机上传会失败
- 司机会在前端看到操作失败提示

### 7.3 打开开关且小程序正确带 token 时

表现：

- 司机无感
- 仍按现有流程使用
- 但接口已从“完全开放”升级成“持 token 才可访问”

---

## 8. 推荐启用步骤

建议按下面顺序落地：

1. 先在后端上线支持 token 的代码，但开关保持关闭
2. 小程序前端统一在请求头中加 `X-Mini-Api-Token`
3. 在测试环境验证：
   - 带 token 成功
   - 不带 token 返回 `401`
4. 验证通过后，在联调/生产逐步打开：
   - `logistics_web.mini_api_token_enabled = true`

这样可以保证：

- 司机侧体验不被突然打断
- 前后端都能独立完成准备
- 启用动作可控、可回滚

---

## 9. 为什么不直接上司机级权限

因为当前阶段的主要目标是：

- 先堵住“完全开放写接口”这个大洞
- 但不要引入过高改造成本

司机级权限体系通常还需要补：

- 小程序登录态
- 司机身份模型映射
- 运单与司机权限绑定
- 设备绑定/手机号校验
- token 刷新与过期策略

这属于下一阶段的能力，不适合和当前联调收口混在一起做。

---

## 10. 后续演进方向

当前方案是：

- **应用级共享 token**

后续建议演进为：

1. 应用级 token
2. 司机级身份 token
3. 运单/批次范围授权

最终理想状态：

- 司机只能看到或操作自己有权限的批次、运单、站点
- 后端能明确知道是谁在上传、什么时候上传、操作了什么对象

---

## 11. 当前结论

### 11.1 短期结论

推荐采用：

- **开关式 mini token 校验**

优点：

- 不影响当前司机端使用
- 安全能力可以平滑启用
- 不需要立刻改造完整身份体系

### 11.2 中期结论

后续建议逐步升级到：

- mini 端司机身份体系
- 司机/运单范围授权

---

## 12. 一句话总结

当前最合理的安全方案不是马上强制所有司机重新登录或换协议，而是：

**先用“默认关闭、可显式启用”的 mini token 校验把开放接口收紧，再在后续阶段升级到真正的司机级权限体系。**
