# 证据页面按留痕事件类型筛选与展示拆分设计说明

## 1. 设计背景

当前证据页面已经支持展示“留痕事件”信息，但页面中的“留痕事件”字段实际上是一个拼接后的展示串，例如：

- `完成签收 - 2026-05-06 07:00:47`
- `完成装车 - 2026-04-30 09:23:49`

这种方式在早期适合快速展示，但已经不适合作为正式的筛选口径和正式的主展示口径。  
如果继续依赖这类拼接字段，会带来以下问题：

- 无法按“完成签收 / 完成装车 / 到达门店”等事件类型精确筛选
- 用户在列表页不容易一眼区分“事件类型”和“事件时间”
- 展示字段和业务筛选字段混在一起，后续统计、导出、搜索难以统一
- 历史数据兼容时容易长期依赖字符串识别，维护成本高

因此，本次设计不仅要把“留痕事件”的**筛选口径**与**展示口径**分开，还要把页面展示字段正式拆开。

---

## 2. 设计目标

本次设计目标如下：

1. 证据页面支持按“留痕事件类型”做正式筛选
2. 列表页展示拆分为“留痕事件类型”和“留痕时间”两列
3. 后端字段口径与留痕主对象保持一致
4. 为后续统计、导出、搜索统一打基础
5. 对历史数据保留可控兼容策略，不强依赖字符串长期解析

---

## 3. 核心设计原则

### 3.1 展示字段和筛选字段分离

证据页面中的“留痕事件”不再承担筛选职责。  
它不再作为列表页唯一主列，而是拆分成：

- 事件类型列
- 事件时间列

### 3.2 正式筛选必须依赖结构化字段

筛选必须基于事件类型结构化字段，而不是基于：

- 显示名称
- 拼接文案
- 时间字符串

### 3.3 数据来源统一追溯到 trace event

证据页面中与“留痕事件”相关的字段，应优先来源于关联的 `trace_event` 主对象，而不是由 `evidence` 自己长期重复拼接和固化。

---

## 4. 建议字段模型

证据页面围绕留痕事件，建议明确三层字段：

### 4.1 `trace_event_type`

正式业务字段。  
用于：

- 筛选
- 统计
- 统一业务口径
- 列表“留痕事件类型”列展示

建议值示例：

- `sign_completed`
- `loading_completed`
- `arrived`
- `left`
- `exception_reported`
- `other`

建议中文映射：

- 完成签收
- 完成装车
- 到达门店
- 离开门店
- 异常上报
- 其他

### 4.2 `trace_event_time`

正式时间字段。  
用于：

- 排序
- 时间筛选
- 列表“留痕时间”列展示
- 详情页辅助展示

### 4.3 `trace_event_display_name`

展示辅助字段。  
例如：

- `完成签收 - 2026-05-06 07:00:47`

该字段不再作为证据列表页主列，而调整为：

- 详情页辅助展示
- 导出兼容字段
- 历史迁移过渡字段

---

## 5. 页面设计建议

### 5.1 搜索区设计

证据页面搜索区建议新增独立筛选项：

- `留痕事件类型`

推荐控件形式：

- 下拉单选

后续如果业务需要更复杂组合查询，也可升级为：

- 多选标签

推荐默认选项：

- 全部
- 完成签收
- 完成装车
- 到达门店
- 离开门店
- 异常上报
- 其他

### 5.2 列表展示设计

证据列表页正式拆分为两列：

- `留痕事件类型`
- `留痕时间`

对应关系如下：

- `留痕事件类型` -> `trace_event_type`
- `留痕时间` -> `trace_event_time`

原来的“留痕事件”拼接展示串不再作为列表页主列。

### 5.3 页面体验收益

拆分后，用户可以直接获得：

1. 事件类型一眼可见
2. 时间信息单独可读
3. 搜索项与列表列保持一致
4. 后续支持按事件时间排序或分组更自然

### 5.4 本轮采用方案

本轮明确采用拆开版正式方案：

1. 搜索区新增 `留痕事件类型`
2. 列表列调整为：
   - `留痕事件类型`
   - `留痕时间`
3. 后端查询按 `trace_event_type` 正式过滤
4. 排序继续基于 `trace_event_time`

不再保留“列表继续显示事件 + 时间拼接串”的保守版方案作为本轮目标。

---

## 6. 后端口径设计

### 6.1 正式筛选口径

证据页面后端查询时，留痕事件相关筛选应基于：

- `trace_event_type`

而不是：

- `trace_event_display_name`
- `留痕事件字符串模糊匹配`

### 6.2 数据来源建议

证据页面的数据模型建议优先从：

- `evidence.trace_event_id`

关联到 trace event，再取：

- `event_type`
- `event_time`
- `display_name`

如果证据页面当前已有冗余摘要字段，也建议将其定义为：

- 查询辅助字段
- 展示辅助字段

而不是未来的长期主口径。

---

## 7. 历史数据兼容策略

当前历史数据中，很多记录可能只有：

- 留痕事件显示串

而未完全结构化成正式事件类型字段。

因此本轮建议采用如下兼容策略：

### 7.1 新数据

新生成的证据记录，应保证：

- `trace_event_type`
- `trace_event_time`
- `trace_event_display_name`

三层字段都可以明确获得。

### 7.2 旧数据

旧数据优先按以下顺序回填：

1. 优先从关联 `trace_event` 读取结构化字段
2. 若历史关系缺失，再从旧展示串做一次迁移识别
3. 识别结果应尽量落入结构化字段，不建议长期依赖字符串解析

### 7.3 旧展示串的角色调整

旧的 `trace_event_display_name` 建议调整角色为：

- 详情页展示辅助字段
- 导出兼容字段
- 历史数据迁移过渡字段

不再作为证据列表页主列。

### 7.4 不建议长期保留的做法

不建议将以下方式作为长期主方案：

- 按“留痕事件展示串”模糊搜索
- 通过字符串包含关系判断事件类型
- 在前端页面做事件类型识别

这些都只适合作为过渡兼容。

## 8. 推荐实施方案

### 8.1 第一阶段：本轮正式落地版本

建议优先实现：

1. 搜索区新增 `留痕事件类型`
2. 列表改为两列：
   - `留痕事件类型`
   - `留痕时间`
3. 后端查询改为按 `trace_event_type` 过滤
4. 列表排序继续按 `trace_event_time`

这是本轮推荐并采用的正式方案。

### 8.2 第二阶段：结构统一增强

后续可继续做：

1. 历史数据结构化回填
2. 证据导出 / 统计 / 仪表盘统一复用 `trace_event_type`
3. 详情页也统一展示结构化事件字段

## 9. 页面字段改动清单

本节用于直接指导证据页面前端与视图层改造。

### 9.1 列表页字段调整

当前建议将原有单列：

- `留痕事件`

调整为两列：

1. `留痕事件类型`
2. `留痕时间`

对应字段建议：

- `留痕事件类型` -> `trace_event_type`
- `留痕时间` -> `trace_event_time`

### 9.2 搜索区字段调整

搜索区新增正式筛选项：

1. `留痕事件类型`

推荐保留并继续配合使用的现有筛选项：

1. `上传时间`
2. `批次`
3. `运单`
4. `上传人`
5. `状态`
6. `异常相关`

### 9.3 详情页字段建议

详情页建议保留或补齐以下字段：

1. `留痕事件类型`
2. `留痕时间`
3. `留痕事件展示名`

对应关系建议：

- 结构化主字段：
  - `trace_event_type`
  - `trace_event_time`
- 辅助展示字段：
  - `trace_event_display_name`

### 9.4 列表排序建议

列表默认排序建议继续按：

- `trace_event_time desc`

这样可以保持证据记录按事件时间倒序查看。

### 9.5 分组建议

本轮不是必须项，但如果后续要增强筛选体验，建议可考虑新增分组项：

1. 按 `留痕事件类型` 分组
2. 按 `上传时间日期` 分组
3. 按 `批次` 分组

## 10. 后端查询改造清单

本节用于指导查询域、字段来源与兼容逻辑改造。

### 10.1 查询主字段

证据页面后端正式筛选字段应调整为：

- `trace_event_type`

不再以以下内容作为主查询字段：

- `trace_event_display_name`
- 事件 + 时间拼接串
- 纯字符串包含关系

### 10.2 查询域改造建议

当用户在证据页按“留痕事件类型”筛选时，后端查询域建议基于：

- `evidence.trace_event_id.event_type`

如果页面层已经做了 evidence 侧摘要字段冗余，也应保证冗余字段与主字段一致，但正式口径仍以关联的 `trace_event` 为准。

### 10.3 返回字段清单

证据页面列表接口 / search_read / 视图读数，建议确保可直接得到以下字段：

1. `trace_event_type`
2. `trace_event_time`
3. `trace_event_display_name`
4. `batch_no`
5. `waybill_no`
6. `uploaded_at`
7. `upload_user_name`
8. `image_count`
9. `image_items_json`
10. `state`
11. `is_exception_related`

### 10.4 数据来源改造建议

后端应统一以下数据来源：

- `trace_event_type` <- `trace_event.event_type`
- `trace_event_time` <- `trace_event.trace_time`
- `trace_event_display_name` <- 基于事件类型 + 时间生成的展示摘要，或沿用结构化摘要字段

### 10.5 历史数据兼容逻辑

对于历史记录，后端兼容策略建议如下：

1. 优先直接取关联 `trace_event` 的结构化字段
2. 若 `trace_event` 存在但字段缺失，则尝试历史摘要字段回填
3. 若仅剩旧展示串，则允许一次性迁移识别
4. 不建议长期在实时查询时依赖字符串拆解

### 10.6 搜索与导出统一口径

后续若证据页支持导出或统计，也建议统一复用：

- `trace_event_type`
- `trace_event_time`

避免出现：

- 页面筛选按一种口径
- 导出按另一种口径
- 统计再按第三种口径

## 11. Odoo 实现清单

本节将设计直接落到 Odoo 19 的实现维度，方便后续拆解开发任务。

### 11.1 Model 层实现清单

证据主模型建议补齐或明确以下字段：

1. `trace_event_type`
   - 类型：建议 `Selection` 或 `Char + 规范化映射`
   - 作用：
     - 列表展示
     - 搜索筛选
     - 导出与统计复用

2. `trace_event_time`
   - 类型：`Datetime`
   - 作用：
     - 列表展示
     - 排序
     - 时间分析

3. `trace_event_display_name`
   - 类型：`Char`
   - 作用：
     - 详情展示
     - 历史兼容摘要

4. 关联来源建议：
   - `trace_event_id`
   - 从 `trace_event_id.event_type`
   - 从 `trace_event_id.trace_time`
   - 从结构化字段或 compute 逻辑生成 `trace_event_display_name`

### 11.2 Model 字段策略建议

建议采用以下策略：

1. `trace_event_type`
   - 优先从 `trace_event_id.event_type` 同步或 compute
   - 页面和导出统一读该字段

2. `trace_event_time`
   - 优先从 `trace_event_id.trace_time` 同步或 compute

3. `trace_event_display_name`
   - 由 `trace_event_type + trace_event_time` 组合生成
   - 不作为主筛选字段

### 11.3 Search View 实现清单

证据页面的 search view 建议补齐：

1. 新增字段搜索：
   - `trace_event_type`

2. 新增筛选项：
   - 全部
   - 完成签收
   - 完成装车
   - 到达门店
   - 离开门店
   - 异常上报
   - 其他

3. 建议新增的分组项：
   - 按留痕事件类型分组
   - 按批次分组
   - 按上传日期分组

4. 建议保留的现有搜索项：
   - 上传时间
   - 批次
   - 运单
   - 上传人
   - 状态
   - 异常相关

### 11.4 Tree View 实现清单

证据列表 tree view 建议改造为：

1. 删除或弱化原单列：
   - `留痕事件`

2. 新增 / 调整为两列：
   - `留痕事件类型`
   - `留痕时间`

3. 推荐保留列顺序思路：
   - 上传时间
   - 证据
   - 批次
   - 留痕事件类型
   - 留痕时间
   - 运单
   - 上传人
   - Image Count
   - 证据缩略图
   - 异常相关
   - 状态

4. 默认排序建议：
   - `trace_event_time desc`
   - 次级可保留 `id desc`

### 11.5 Form View 实现清单

证据详情 form view 建议补齐并调整展示：

1. 结构化展示字段：
   - `留痕事件类型`
   - `留痕时间`

2. 兼容展示字段：
   - `留痕事件展示名`

3. 推荐布局：
   - 第一层展示结构化字段
   - 第二层展示摘要 / 兼容字段
   - 避免只展示一个混合串

### 11.6 Action / 默认视图行为建议

证据菜单 action 建议调整：

1. 默认排序：
   - 按 `trace_event_time desc`

2. 默认搜索上下文可考虑：
   - 打开时优先使用标准 search view
   - 不预设某个单一事件类型

3. 如后续业务需要，可在 action context 增加：
   - 默认按批次分组
   - 或默认按留痕事件类型分组

### 11.7 导出 / 报表复用清单

后续如证据页支持导出、统计或报表，建议统一复用：

1. `trace_event_type`
2. `trace_event_time`
3. `batch_no`
4. `waybill_no`
5. `uploaded_at`
6. `image_count`

避免报表仍然回退到：

- `trace_event_display_name`
- 拼接字符串

### 11.8 历史数据迁移实现建议

如果后续要做数据修正，建议拆成三步：

1. 先补字段
   - `trace_event_type`
   - `trace_event_time`
   - `trace_event_display_name`

2. 再做回填
   - 优先从 `trace_event_id` 回填
   - 再处理历史无结构化字段记录

3. 最后再改视图
   - 确保用户看到的新列都是可稳定读取的

## 12. 按模块拆分的开发任务清单

本节用于把本设计直接拆成可执行的模块级任务，便于排期、分工和实现落地。

### 12.1 `logistics_trace_evidence` 模块任务

这是本次改造的主承载模块。

建议任务如下：

1. 补齐或明确 evidence 侧结构化字段
   - `trace_event_type`
   - `trace_event_time`
   - `trace_event_display_name`

2. 明确字段来源
   - 从 `trace_event_id.event_type` 同步或 compute `trace_event_type`
   - 从 `trace_event_id.trace_time` 同步或 compute `trace_event_time`
   - 组合生成 `trace_event_display_name`

3. 补历史数据兼容逻辑
   - 有 `trace_event_id` 的优先直接回填
   - 缺失结构化字段的老记录做一次兼容迁移

4. 统一导出、统计、详情页读数来源
   - 后续与事件相关的取值统一复用结构化字段

5. 如当前模型里已有旧摘要字段
   - 保留兼容
   - 但明确其角色降级为辅助展示字段

### 12.2 `logistics_trace_evidence` 视图任务

建议在该模块内完成证据页面视图层改造。

1. Tree View
   - 原“留痕事件”列调整为：
     - `留痕事件类型`
     - `留痕时间`

2. Form View
   - 增加结构化字段展示：
     - `留痕事件类型`
     - `留痕时间`
   - 保留：
     - `留痕事件展示名`
     作为兼容辅助展示

3. Search View
   - 新增字段搜索：
     - `留痕事件类型`
   - 新增筛选项：
     - 完成签收
     - 完成装车
     - 到达门店
     - 离开门店
     - 异常上报
     - 其他
   - 可选新增 group by：
     - 按留痕事件类型
     - 按批次
     - 按上传日期

### 12.3 `logistics_web` 模块任务

如果证据页面当前是通过自定义前端 action 或 web 组件做增强展示，则该模块需要配合调整。

建议任务如下：

1. 若证据列表页有自定义前端字段映射
   - 将原单列“留痕事件”映射拆成：
     - `trace_event_type`
     - `trace_event_time`

2. 若前端页面有搜索面板增强
   - 加入“留痕事件类型”筛选项

3. 若结果页、导出页、统计页引用证据事件字段
   - 优先改读结构化字段
   - 不再直接读 `trace_event_display_name` 做业务判断

4. 若页面有自定义排序或快速筛选
   - 调整为按 `trace_event_time` 排序

### 12.4 `logistics_web` 导出 / 报表相关任务

如果证据相关导出或结果页口径需要和证据页面保持一致，建议同步处理：

1. 导出索引字段复用：
   - `trace_event_type`
   - `trace_event_time`

2. 若有结果页摘要或统计卡片
   - 后续事件维度统计统一使用结构化字段

3. 避免导出层继续依赖：
   - `trace_event_display_name`
   - 拼接展示串

### 12.5 数据迁移任务

建议单独拆为一项数据治理任务，避免混在页面修改里。

任务建议：

1. 补字段
2. 跑回填
3. 抽样校验
4. 再切视图

优先级顺序建议：

1. 先保证新数据结构化
2. 再治理旧数据
3. 最后统一页面展示

### 12.6 联调验证任务

实现完成后建议单独回归以下场景：

1. 证据页按“完成签收”筛选
2. 证据页按“完成装车”筛选
3. 同一事件类型下列表是否只显示对应记录
4. 列表中的“留痕时间”是否正确
5. 详情页中的事件类型、事件时间、展示名是否一致
6. 历史老记录是否还能正常显示

### 12.7 推荐开发拆分方式

如果要分给不同同事，建议这样拆：

1. `logistics_trace_evidence` 后端字段与回填
2. `logistics_trace_evidence` 视图改造
3. `logistics_web` 页面映射 / 搜索增强 / 导出兼容
4. 联调与历史数据核验

这样可以避免：

- 一个人同时改模型、数据、视图、页面
- 最后联调时才发现口径没统一

## 13. 预期收益

本设计完成后，证据页面可获得以下收益：

1. 用户能按事件类型快速定位证据
2. 用户能更直观看懂每条证据对应的事件时间
3. 证据页和留痕页口径统一
4. 后续统计“完成签收类证据 / 完成装车类证据 / 异常类证据”会更容易
5. 不再长期依赖展示字符串做业务筛选和主展示
6. 后续导出和查询能力更容易扩展

## 14. 本轮设计结论

证据页面中的“留痕事件”应拆分为：

- 正式筛选字段：`trace_event_type`
- 正式时间字段：`trace_event_time`
- 展示辅助字段：`trace_event_display_name`

本轮正式采用的页面方案为：

- 搜索区新增“留痕事件类型”筛选
- 列表拆分为：
  - `留痕事件类型`
  - `留痕时间`
- 后端按 `trace_event_type` 正式查询
- `trace_event_display_name` 降级为详情与兼容用途

这样既能提升证据页使用体验，也能为后续统计、导出和结构统一做好铺垫。
