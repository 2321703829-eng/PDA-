# logistics_base Addon 设计稿

## 1. 文档状态

本文档现阶段应视为技术预留设计稿，不再视为已确认的一期正式业务设计稿。

原因很明确：

- 当前项目里真正成熟的设计集中在订单、批次、留痕、图片、IAM 这些领域
- 客户、门店、工作人员、仓库还没有完成同等成熟度的功能确认
- 因此，logistics_base 不能再被默认当作当前最优先、最确定的业务模块

## 2. 当前定位

logistics_base 当前最合适的定位是：

- 一个轻量、非阻塞的官方模型扩展模块
- 一个未来主数据能力的承接点
- 一个技术骨架，而不是一个需求已经坐实的主数据中心

## 3. 当前应该控制的范围

### 3.1 可以保留的内容

- 对 res.partner 的轻量扩展入口
- 对 hr.employee 的轻量扩展入口
- 对 stock.warehouse 的轻量扩展入口
- 最少量的标识性字段、备注字段、引用字段

### 3.2 当前不应继续放大的内容

- 过细的客户等级体系
- 过细的门店履约规则体系
- 过细的人员岗位与调度体系
- 过细的仓库作业与状态体系
- 任何会让人误以为这些需求已经被业务确认的正式字段合同

## 4. 与当前真实项目的关系

目前真实项目的核心，不在于先把客户和门店主数据做完整，而在于：

- 保留既有订单、留痕、图片主链路
- 在 Odoo 中找到对这条主链路最合适的表达方式
- 避免主数据设计反过来阻塞真实成熟业务的迁移

因此，logistics_base 当前不应成为订单模块的前置阻塞点。

## 5. 当前骨架的意义

仓库里已经创建了 custom_addons/logistics_base 模块骨架，这件事仍然是成立的。

它的意义是：

- 建立自定义模块目录结构
- 验证官方模型扩展的落点
- 为未来主数据确认后留出接入点

它当前不意味着：

- 主数据方案已经确认
- 可以马上继续大规模补字段和页面
- 订单和留痕模块应该依赖它的完整版本才能开始设计

## 6. 当前建议做法

对 logistics_base，当前建议是收住，而不是继续加深。

建议动作：

- 保留现有最小模块骨架
- 不继续追加大批量业务字段
- 不继续把它当成主线模块扩写
- 等客户、门店、人员、仓库专题确认后，再补正式设计

## 7. 需要确认的问题

后续如果要真正推进 logistics_base，至少要先确认下面几件事：

1. 客户是否要直接映射到 res.partner
2. 门店是否是真实长期主数据，而非订单地址快照
3. 工作人员是否真的进入 hr.employee，还是只保留账号或操作人
4. 仓库是否需要真正接入 stock.warehouse 业务语义
5. tb_client 与 Odoo 客户主体之间的映射关系是什么

## 8. 当前结论

logistics_base 现在适合作为一个已经落地的技术骨架存在，但不适合作为下一阶段的主线工作重心。

下一阶段的主线，应该转向订单、留痕、图片、异常这些已经更接近真实需求的领域设计。
