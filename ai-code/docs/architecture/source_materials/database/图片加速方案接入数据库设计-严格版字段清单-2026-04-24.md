# 图片加速方案接入数据库设计-严格版字段清单

适用前提：
- 严格按桌面《四期数据库底表设计稿》执行。
- 严格遵守当前业务主链：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`。
- 图片、留痕、证据首轮按 `customer_line` 作为最小业务挂点。
- 当前仓库证据模块仅作为现状参考，不作为最终数据库设计边界。

## 一、总体结论

图片加速方案接入时，不建议继续把图片存储细节堆在 `logistics.trace.evidence` 主表上。  
严格按数据库设计和后续扩展要求，建议收成三层：

1. `logistics.trace.event`
2. `logistics.trace.evidence`
3. `logistics.trace.evidence.image`

其中：
- `trace_event` = 留痕事件主表
- `evidence` = 证据主表
- `evidence.image` = 图片资产子表

## 二、对象分层要求

### 1. logistics.trace.event

角色：
- 留痕事件主表
- 承接司机在某次配送节点上的业务动作

严格要求：
- 必须可关联 `waybill_id`
- 建议补齐 `customer_line_id`
- `customer_line_id` 才是后续图片、证据、异常的最小业务挂点

### 2. logistics.trace.evidence

角色：
- 证据主表
- 记录某次留痕下的一组证据集合

建议只保留主业务字段：
- `trace_event_id`
- `waybill_id`
- `customer_line_id`
- `batch_id`
- `name`
- `remark`
- `uploader_id`
- `uploaded_at`
- `state`
- `sequence`

不建议继续放在主表中的字段：
- `preview_url`
- `full_url`
- `storage_bucket`
- `storage_relative_path`
- `image_access_key`
- 云上/本地对象存储细节

这些字段应下沉到图片子表。

### 3. logistics.trace.evidence.image

角色：
- 图片资产主表
- 一条 `evidence` 下可对应多张图片
- 承接图片加速方案的全部状态与存储路由字段

## 三、图片资产子表字段清单

建议正式字段如下。

### 1. 关联字段

- `evidence_id`
  - 关联 `logistics.trace.evidence`
- `trace_event_id`
  - 冗余快照，便于查询
- `waybill_id`
  - 冗余快照，便于按运单聚合
- `customer_line_id`
  - 严格建议保留
  - 作为最小业务挂点
- `batch_id`
  - 冗余快照

### 2. 访问与识别字段

- `image_access_key`
  - 前后端统一访问 key
  - 建议唯一索引
- `sequence`
  - 图片顺序
- `source_filename`
  - 原始文件名
- `stored_file_name`
  - 最终存储文件名

### 3. 文件元数据字段

- `mime_type`
- `content_type`
- `file_ext`
- `file_size`
- `etag`
- `content_hash`
  - 如果后续做重复图识别，可保留

### 4. 云对象存储字段

- `cloud_provider`
  - 例如 `oss / cos / s3 / obs`
- `cloud_bucket`
- `cloud_object_key`
- `cloud_uploaded_at`
- `cloud_expire_at`

### 5. 本地 MinIO / 本地归档字段

- `local_provider`
  - 默认可为 `minio`
- `local_bucket`
- `local_object_key`
- `local_synced_at`

### 6. 状态机字段

- `storage_status`
  - 建议枚举值：
    - `cloud_only`
    - `syncing`
    - `both`
    - `local_only`
    - `sync_failed`
    - `deleted`

### 7. 同步与异常字段

- `sync_retry_count`
- `sync_started_at`
- `sync_finished_at`
- `last_sync_error`
- `last_sync_error_at`

### 8. 审计字段

- `create_uid`
- `create_date`
- `write_uid`
- `write_date`

## 四、严格约束建议

### 1. 唯一约束

- `image_access_key` 全局唯一

### 2. 索引建议

- `evidence_id`
- `trace_event_id`
- `waybill_id`
- `customer_line_id`
- `batch_id`
- `storage_status`
- `cloud_expire_at`
- `uploaded_at`

### 3. 非空建议

至少建议以下字段非空：
- `evidence_id`
- `image_access_key`
- `storage_status`
- `source_filename`
- `uploaded_at`

## 五、与现有仓库证据模块的映射关系

当前现状：
- `logistics.trace.evidence` 直接挂了图片访问与存储字段

严格版改造方向：
- `logistics.trace.evidence`
  - 保留证据业务信息
- `logistics.trace.evidence.image`
  - 承接图片存储与访问信息

现有字段迁移建议：

- `logistics.trace.evidence.image_access_key`
  -> `logistics.trace.evidence.image.image_access_key`
- `preview_url`
  -> 不再长期落库为主字段，建议运行时路由生成
- `full_url`
  -> 同上
- `storage_provider`
  -> 拆成 `cloud_provider` 或 `local_provider`
- `storage_bucket`
  -> 拆分到云/本地字段
- `storage_relative_path`
  -> 拆分到 `cloud_object_key` 或 `local_object_key`

## 六、接口层严格要求

接入图片加速方案后，前端仍然不直接感知云上还是本地。

建议接口职责如下：

### 1. init-upload

作用：
- 生成 `image_access_key`
- 生成云对象存储 presigned upload URL
- 预创建图片资产记录或预分配上传上下文

### 2. complete-upload

作用：
- 校验云对象是否存在
- 写入图片资产主记录
- 初始状态记为 `cloud_only` 或 `syncing`
- 投递异步归档任务

### 3. preview-url

作用：
- 只接收 `image_access_key`
- 后端根据：
  - `storage_status`
  - `cloud_expire_at`
  - 本地归档状态
  决定返回云上 URL 还是本地 MinIO URL

### 4. download

作用：
- 同样按 `image_access_key` 路由
- 不让前端依赖具体存储位置

## 七、与主链导入的边界

图片加速方案不得反向影响以下主链导入结构：
- `wave`
- `batch`
- `waybill`
- `customer_line`
- `order_line`
- `goods_line`

也就是说：
- 客户信息导入不因图片方案改字段
- 商品信息导入不因图片方案改字段
- 四 Sheet 正式模板不因图片方案改结构

图片方案只属于：
- 留痕
- 证据
- 图片资产
- 图片访问路由
- 归档异步任务

## 八、推荐实施顺序

1. 先新增 `logistics.trace.evidence.image` 设计
2. 再让 `trace_event / evidence` 补齐 `customer_line_id`
3. 再改上传链路为：
   - `init-upload`
   - 云上直传
   - `complete-upload`
4. 再补异步归档任务
5. 最后把现有预览/下载接口切到图片子表驱动

## 九、最终结论

严格按数据库设计和业务主逻辑，图片加速方案应落在：
- `trace_event`
- `evidence`
- `evidence.image`

其中真正承接云上短存、本地归档、状态机路由的核心对象，应是：

`logistics.trace.evidence.image`

一句话结论：
图片加速方案可以接，但必须作为“图片资产子表 + 状态机 + 统一路由”接入，不能继续停留在“证据主表单图字段堆叠”的阶段。
