# 前端代码目录规划

## 文档定位

本文档用于明确：

- 当前项目的前端代码应如何在仓库内归属
- 前端负责人应主要在哪些目录中工作
- 哪些前端代码适合集中放置
- 哪些前端代码仍应保留在业务模块内

本文档面向当前 GitHub 协作方式，重点解决“前端代码是否应单独放在一个目录中”这个问题。

---

## 1. 结论

当前项目**不建议**采用“完全独立前端工程”的方式。

也就是说，当前不建议在仓库根目录另起一套完全脱离 Odoo addon 体系的：

- `frontend/`
- `webapp/`
- `react-admin/`
- `vue-admin/`

之类的独立前端工程。

当前项目**建议**采用下面这套方式：

**业务基础视图留在业务模块，前端增强能力集中到一个前端承载 addon。**

推荐新增或明确一个前端承载模块，例如：

- `custom_addons/logistics_web`

这个模块用于承接你负责的前端增强代码。

---

## 2. 为什么不建议完全独立前端工程

当前系统不是纯前后端分离项目，而是：

- 基于 Odoo Web 后台
- 以 Odoo 模型、菜单、动作、权限体系为基础
- 以 Odoo RPC 为主路线
- 以少量 JSON controller 为补充路线

因此，如果再单独起一个完全独立的前端工程，会带来这些问题：

1. 会弱化 Odoo 原生菜单、动作、权限和上下文体系
2. 会让标准 `tree / form / search / act_window` 页面失去原生承载优势
3. 会引入第二套前端壳、第二套路由、第二套状态组织
4. 会让前后端联调复杂度明显上升
5. 会让你负责的“后台增强层”与实际业务模块边界更加模糊

所以，当前更适合：

- 在 Odoo addon 体系内继续开发
- 通过一个前端承载 addon 集中你的主要工作区域

---

## 3. 当前推荐的代码归属原则

## 3.1 业务基础能力归业务模块

以下内容应优先归属于对应业务模块：

- 模型定义
- 字段定义
- `ir.model.access.csv`
- 记录规则
- 标准 `tree / form / search` 视图
- 基础菜单与 `act_window`
- 标准 smart button 跳转

对应模块示例：

- `custom_addons/logistics_dispatch`
- `custom_addons/logistics_trace_core`
- `custom_addons/logistics_trace_exception`

## 3.2 前端增强能力归前端承载模块

以下内容更适合集中归属于前端承载模块：

- 时间线增强 widget
- 证据查看 widget
- 工作台聚合页
- 老板追溯摘要页
- 通用页面组件
- 前端模板
- 通用样式
- 轻量前端增强逻辑
- client action

推荐模块：

- `custom_addons/logistics_web`

## 4. 推荐目录结构

## 4.1 仓库级结构

```text
custom_addons/
├── logistics_base/
├── logistics_dispatch/
├── logistics_trace_core/
├── logistics_trace_exception/
└── logistics_web/
```

其中：

- `logistics_base`：主数据扩展层
- `logistics_dispatch`：波次/批次/运单执行主线
- `logistics_trace_core`：留痕事实层
- `logistics_trace_exception`：异常对象层
- `logistics_web`：前端增强层

## 4.2 `logistics_web` 建议目录

```text
custom_addons/logistics_web/
├── __init__.py
├── __manifest__.py
├── controllers/
├── data/
├── security/
├── static/
│   └── src/
│       ├── js/
│       │   ├── actions/
│       │   ├── components/
│       │   ├── services/
│       │   └── widgets/
│       ├── scss/
│       ├── xml/
│       └── img/
└── views/
    ├── logistics_web_menus.xml
    ├── logistics_web_actions.xml
    └── logistics_web_templates.xml
```

## 5. 各类前端代码放置建议

## 5.1 适合放在 `logistics_web` 的内容

### 页面增强与聚合页面

- 管理工作台
- 老板追溯摘要页
- 证据总览页
- 增强版时间线阅读页

### 通用组件

- `PageHeader`
- `PageFilterBar`
- `SummaryBand`
- `StatusTag`
- `SummaryCard`
- `TraceTimelineWidget`
- `EvidenceViewerWidget`

### 通用前端能力

- 页面级数据读取封装
- controller 调用封装
- UI 状态组件
- 通用样式变量

## 5.2 适合留在业务模块内的内容

### `logistics_dispatch`

- 批次 `tree / form / search`

- 留痕对象的基础列表与表单

### `logistics_trace_exception`

- 异常列表
- 异常详情基础表单
- 异常状态流转按钮
- 异常对象的基础 smart button

## 6. 目录边界判断规则

如果一个功能同时涉及业务模块和前端展示，优先按下面规则判断放哪里：

### 放业务模块，如果它主要是：

- 业务对象结构
- 字段与状态
- 标准后端视图
- 权限与记录规则
- 与单一模型强绑定的基础页面

### 放 `logistics_web`，如果它主要是：

- 跨模型聚合展示
- 增强阅读体验
- 自定义组件
- 统一前端样式
- 非标准原生页面
- client action

---

## 7. GitHub 协作建议

## 7.1 为什么前端代码要有相对独立归属

如果前端代码全部散落在每个业务模块中，会出现：

- PR 边界不清楚
- 与后端同学改同文件的概率上升
- review 不容易快速识别“这是前端改动”
- 联调阶段责任边界不清楚

相反，如果把前端增强代码主要集中到 `logistics_web`：

- 你的工作主目录更明确
- PR 更容易按前端功能拆分
- 与后端并行开发更稳
- 页面增强层和业务对象层边界更清楚

## 7.2 推荐协作方式

建议采用：

- 后端同学主改：
  - `logistics_dispatch`
  - `logistics_trace_core`
  - `logistics_trace_exception`
- 前端负责人主改：
  - `logistics_web`

你仍然可以在必要时少量修改业务模块中的基础视图，但主工作区建议集中在 `logistics_web`。

---

## 8. 当前最推荐的实际做法

在正式进入前端编码前，建议先补齐：

1. `custom_addons/logistics_web/` 模块骨架
2. `static/src/js/components/`
3. `static/src/js/widgets/`
4. `static/src/xml/`
5. `static/src/scss/`
6. `views/logistics_web_actions.xml`

第一批优先承接的内容建议是：

1. 管理工作台
2. 时间线增强 widget
3. 证据查看 widget
4. 老板追溯摘要页

---

## 9. 当前不建议的做法

当前不建议：

1. 在仓库根目录单独新建完全独立的前端工程
2. 把所有页面都抽离出 Odoo 原生视图体系
3. 把所有前端代码彻底塞进单一业务模块
4. 在尚未建立前端承载 addon 前，就把 widget 和样式散落到多个 addon 中

---

## 10. 结论

当前项目应采用：

**Odoo addon 体系内开发 + 业务基础视图留在业务模块 + 前端增强代码集中到 `logistics_web`。**

这套方式最适合当前的：

- Odoo Web 宿主模式
- GitHub 协作方式
- 前端负责人单独承担页面增强工作的团队结构
