# 物流批量导出结果展示口径设计

适用范围：
- `custom_addons/logistics_web`
- 导出任务结果页
- 导出任务详情页
- 导出任务行结果列表

优先基准：
- `docs/architecture/ARCHITECTURE.md`
- `docs/architecture/logistics_web_addon_design.md`
- `docs/change_notes/2026-04-30_evidence_chain_midterm_rollout.md`

---

## 1. 文档目标

本文档用于统一物流系统中“批量导出结果”的页面展示口径。

它要解决的不是导出实现细节，而是下面 4 个问题：

1. 技术侧 `Success / Failed / Skipped` 应该如何翻译成业务能理解的结果状态
2. 行级结果、任务级结果和摘要统计分别该怎么展示
3. 哪些情况属于系统异常，哪些情况属于数据缺失
4. 当任务已经处理到部分内容，但最终没有生成下载文件时，页面应该如何表达

---

## 2. Outcome

导出结果页最终需要满足：

1. 业务用户一眼能看懂“哪些已经导出、哪些没导出、为什么没导出”
2. 页面不再直接把 `Skipped` 暴露给业务用户
3. 页面能区分：
   - 系统处理失败
   - 数据本身不完整导致未导出
4. 当任务存在成功行但最终没有可下载文件时，页面能明确提示“未生成导出文件”

---

## 3. Behavior

## 3.1 技术状态到业务状态的映射

当前导出任务行存在的技术态主要包括：

- `Success`
- `Failed`
- `Skipped`

页面展示时应映射为业务态：

### A. 已导出

含义：
- 该任务行已成功写入导出包
- 用户最终可以从导出文件中拿到这一行对应的内容

技术映射：
- `Success`

建议展示文案：
- `已导出`

### B. 未导出-系统异常

含义：
- 这条内容理论上应该能导出
- 但由于系统处理、文件写入、权限、运行时异常等原因未成功导出

技术映射：
- `Failed`
- 以及其他可识别为系统故障的任务级错误

典型原因：
- 导出文件写入失败
- ZIP 生成失败
- 存储目录权限异常
- 运行时代码异常

建议展示文案：
- `未导出-系统异常`

### C. 未导出-数据缺失

含义：
- 不是系统处理坏了
- 而是这条记录本身就没有可导内容，或历史数据不完整

技术映射：
- `Skipped`
- 以及一部分能明确识别为“源数据缺失”的失败场景

典型原因：
- 证据没有图片
- 历史图片文件已丢失
- 记录只有 legacy key，但底图不存在

建议展示文案：
- `未导出-数据缺失`

---

## 3.2 行级结果展示

导出任务行列表不再直接展示：

- `Success`
- `Failed`
- `Skipped`

而是统一展示为：

- `已导出`
- `未导出-系统异常`
- `未导出-数据缺失`

同时每一行都应保留“处理说明”，但文案要偏业务理解，而不是只保留技术异常原文。

### 行级处理说明建议

| 场景 | 技术原文示例 | 建议业务文案 |
|---|---|---|
| 无图片 | `has no exportable images` | `该证据没有可导图片` |
| 历史图丢失 | `Legacy image file does not exist on local storage` | `历史图片文件缺失，未导出` |
| 写盘失败 | `Permission denied` / `EXPORT_FILE_WRITE_FAILED` | `导出文件生成失败，请联系管理员` |
| 压缩包失败 | ZIP 生成异常 | `导出包生成失败，请稍后重试` |

---

## 3.3 任务级结果展示

任务级状态不应只机械地沿用底层状态，而要以“用户最终是否拿到文件”为准。

建议任务级只展示 3 类业务状态：

### A. 导出成功

判定建议：
- 有可下载文件
- 所有应导内容均已导出
- 没有系统异常，也没有数据缺失未导出的任务行

### B. 部分导出成功

判定建议：
- 有可下载文件
- 至少有一部分内容已导出
- 但仍有部分内容未导出
- 未导出原因可能包括：
  - 数据缺失
  - 系统异常

### C. 导出失败

判定建议：
- 没有生成可下载文件
- 或全部内容均未导出
- 或任务在最终产出阶段失败

特别强调：

如果出现下面这种情况：

- 行级成功数大于 0
- 但 `output_file_name` / `output_storage_path` 为空
- 没有生成最终文件

则任务级仍然必须显示：

- `导出失败`

并额外提示：

- `本次导出未生成可下载文件`

---

## 3.4 结果摘要展示

结果摘要不建议直接写：

- 成功
- 失败
- 跳过

建议改成：

- `已导出`
- `未导出-系统异常`
- `未导出-数据缺失`

### 推荐摘要字段

1. `总任务行`
2. `已导出`
3. `未导出-系统异常`
4. `未导出-数据缺失`
5. `导出运单`
6. `导出证据`
7. `导出图片`

### 推荐说明

- `已导出`：真正进入导出包的内容
- `未导出-系统异常`：需要开发/运维排查的问题
- `未导出-数据缺失`：需要业务补数据或接受历史残缺的情况

---

## 3.5 文件区展示

文件区应以“是否有可下载文件”为最高优先级展示。

### 有文件时

展示：
- 文件名
- 文件大小
- 下载按钮

任务状态建议为：
- `导出成功`
- 或 `部分导出成功`

### 无文件时

展示：
- `--`
- 或 `未生成文件`

并明确提示：
- `本次导出未成功生成可用文件，建议先查看错误明细，再决定是否重试。`

如果行内已有部分成功，也应额外提示：
- `虽然部分内容处理成功，但最终导出文件生成失败。`

---

## 4. Boundary

本文档只定义：

- 导出结果页的展示口径
- 技术状态到业务状态的映射
- 摘要统计与文案口径

本文档不负责：

- 导出底层 ZIP 生成逻辑
- 导出存储路径实现
- 证据图片导出算法本身
- 历史脏数据清理策略

也就是说：

- “如何展示”属于本文档
- “如何修复写盘失败”属于实现和运维问题
- “如何清理 legacy 脏数据”属于数据治理问题

---

## 5. 当前导出任务的特殊口径

结合当前证据图片批量导出场景，页面要特别区分两类未导出：

### A. 系统异常型

例如：
- 导出文件根目录不可写
- ZIP 文件生成失败
- 权限不足

这类应显示为：
- `未导出-系统异常`

### B. 数据缺失型

例如：
- evidence 无图片
- legacy 图片 key 还在，但底图已丢失

这类应显示为：
- `未导出-数据缺失`

不要把这两类都混在一个泛化的 `Failed` 或 `Skipped` 里给业务看。

---

## 6. Verify

上线前至少验证下面几类场景：

1. 全部导出成功
- 有下载文件
- 所有行显示 `已导出`

2. 部分导出成功，部分无图
- 有下载文件
- 无图行显示 `未导出-数据缺失`

3. 部分导出成功，但最终 ZIP 写盘失败
- 无下载文件
- 任务级显示 `导出失败`
- 页面明确提示“未生成可下载文件”

4. 历史 legacy 图片文件丢失
- 行级显示 `未导出-数据缺失`
- 处理说明显示 `历史图片文件缺失，未导出`

5. 纯系统异常
- 行级或任务级显示 `未导出-系统异常`
- 页面能明确提示需要管理员处理

---

## 7. 推荐落地顺序

1. 先改结果页展示口径
2. 再改导出任务摘要统计文案
3. 再改行级处理说明文案映射
4. 最后按新口径清理底层状态与错误分类

这样可以先让业务侧“看懂结果”，再逐步收敛底层实现。
