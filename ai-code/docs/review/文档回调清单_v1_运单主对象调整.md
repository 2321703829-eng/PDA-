## 1. 本次回调的核心原因

新文档已经明确修正了一个关键前提：

**留痕闭环的直接主对象不是订单，而是运单号。**

这意味着此前如果有以下表述，就需要回调：
- 订单是留痕主对象
- 订单是证据主对象
- 后台主入口是订单追溯
- 留痕粒度默认是订单级 / 批次级

新的统一主线应理解为：

```text
波次记录 -> 批次 -> 运单号 -> 留痕事件 -> 图片证据
                    -> 运单下订单列表
```

因此，本次回调不是普通措辞修正，而是“对象层级和追溯主入口”的结构性回调。

---

## 2. 回调原则

本次回调建议统一遵循以下原则：

1. 不把“订单”删除，而是把它从主对象降为运单下明细对象。
2. 不把已有文档全部推倒，而是优先修正主对象、主链路、页面入口和模型挂载点。
3. 页面层优先把“订单追溯”改成“运单追溯”。
4. 模型层优先把“订单级留痕”改成“运单级留痕”。
5. 批次继续保留为执行组织对象，不替代门店交付事实对象。
6. 波次记录作为调度组织对象，当前可先进入架构层文档，不必一开始就改动全部页面文档。

这些文档直接定义了主对象、模型映射、后台主链路，建议作为第一批处理。

## 3.1 `docs/architecture/logistics_order_mapping.md`

### 当前问题
- 以“订单与批次”作为主映射对象
- 把 `logistics.order` 直接当作当前追溯主对象
- 订单快照和留痕主对象之间没有清楚分层

### 建议修改
- 文档主题调整为“运单与批次 Odoo 模型映射设计”
- 明确 `运单号` 才是留痕和证据的主对象
- 如果继续保留 `logistics.order` 名称，需要在文档中强制说明它当前承载的是“运单主对象快照”，而不是传统订单明细
- 更推荐补充命名调整建议：
  - `logistics.waybill`
  - `logistics.batch`
  - `logistics.wave`
- 把订单改成“运单下订单明细关系”

### 修改目标
- 让架构层先从“订单主对象”切换到“运单主对象”

## 3.2 `docs/architecture/logistics_trace_mapping.md`

### 当前问题
- 默认把留痕粒度理解成 `order / batch`
- 直接使用 `order_id / order_name` 作为留痕主归属

### 建议修改
- 把 `record_granularity` 改成：
  - `waybill`
  - `batch`
- 主归属字段改成：
  - `waybill_id`
  - `waybill_no`
- 保留订单作为从属关系或反查关系，不再作为留痕主挂载点
- 明确图片挂载点支持两类主体：
  - 批次级留痕事件
  - 运单级留痕事件

### 修改目标
- 让事实层和证据层的模型挂载点与新业务前提一致

## 10. 最终建议

这次不建议只做文字替换，而建议按下面方式回调：

1. 先统一主对象口径：
   - 运单是留痕主对象
   - 批次是执行组织对象
   - 订单是运单下明细对象
2. 再统一模型口径：
   - 留痕粒度是运单级 / 批次级
3. 再统一页面口径：
   - 后台主入口从订单追溯切到运单追溯
4. 最后统一统计与文案口径：
   - 优先展示运单数、异常运单数、运单留痕状态

如果按这个顺序处理，回调成本会明显低于“逐篇零散修补”。
