# 示例 03：需求评审

## Findings

### 1. 重要型

- 问题：如果只写“导出结果页”，容易漏掉“入口发起成功后必须直接带 `task_no` 跳转”的行为约束。
- 影响：会导致 API 做完但前端入口和结果链断层。
- 建议：在需求层明确把“发起成功后进入结果页”写成主流程的一部分。

### 2. 重要型

- 问题：如果只说“从运单导出”，很容易把入口类型和文件内部包结构混为一谈。
- 影响：后续实现可能把文件结构错误压缩成单层 waybill 视角，和四 Sheet 正式模板冲突。
- 建议：单独写明 `from_waybill` 是入口类型，`dispatch_main_four_sheet` 是文件内部正式结构。

### 3. 阻塞型

- 问题：如果不在需求里明确范围外内容，后续极易被顺手扩成 `from_batch / from_customer / 图片 ZIP`。
- 影响：范围膨胀，首轮难以收口。
- 建议：明确列出本轮不做的入口和不做的文件类型。

### 4. 优化型

- 问题：需求层可以进一步明确“结果页要复用导入阅读节奏，但不共用同一页面实现”。
- 影响：减少后续前端误读成“必须做导入导出完全共页”。
- 建议：在行为描述里补一条“阅读节奏复用，不要求页面物理实现复用”。

## Gate Decision

- 有条件继续

## Missing or Ambiguous Areas

- 入口类型与包结构的区分要写得更硬一点
- 结果页跳转链要明确
- 范围外能力要列得更完整

## Suggested Fixes

- 在结构化需求中单列 `Outcome / Behavior / Boundary`
- 在 `Rules / Data / States` 里明确 `entry_type` 与 `package_structure`
- 在 `Interfaces / Page Impact` 里显式写出结果页入口行为

## Short Summary

这份需求已经足够进入方案设计，但必须先把入口类型、包结构、结果页跳转链和范围外能力写清楚，否则后续很容易返工。
