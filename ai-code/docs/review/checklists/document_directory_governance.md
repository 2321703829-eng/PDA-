# document_directory_governance

## 1. 目的

为 `ai-code/` 当前文档体系建立统一的目录、文件名、状态标识和归档规则，重点解决下面问题：

1. 同一件事在多个目录重复出现
2. 文件名和文件夹名不能反映真实层级
3. 新旧模块命名并存，但没有明确标出谁是现行、谁是桥接、谁是历史
4. 新人看到文档后，不知道哪份该先看、哪份只能参考

这份规范的目标不是追求“文档看起来整齐”，而是：

**让文档体系服务当前业务主线和模块边界，而不是反过来制造理解成本。**

---

## 2. 当前项目的治理前提

当前项目的有效主线是：

```text
wave -> batch -> waybill -> trace -> evidence -> exception
```

因此文档命名和目录归类都应优先围绕这条主线，而不是围绕历史阶段的：

- `order` 作为留痕主对象
- `trace` 作为未拆分粗模块
- `exception` 独立脱离 `trace_core` 上下文

---

## 3. 文档状态分层

每份文档默认应能归入下面 4 类之一。

### 3.1 现行有效

含义：
- 当前可以直接作为设计、开发、联调、评审依据

典型位置：
- `docs/context/`
- `docs/architecture/`
- `docs/dev/`
- `docs/versioning/`
- 当前有效前端设计目录
  当前默认主入口按 `ai-code/专题设计/前端设计/一期前端相关设计/` 理解。
  如果是二期、三期、四期专题，再分别进入 `ai-code/专题设计/前端设计/二期前端优化设计/`、`ai-code/专题设计/前端设计/三期前端优化设计/`、`ai-code/专题设计/前端设计/四期前端优化设计/`。

要求：
- 文件名清晰
- 标题和模块边界一致
- 不再依赖读者自行猜测“这是不是旧稿”

### 3.2 桥接参考

含义：
- 用于解释旧命名、旧方案、旧评审记录如何映射到当前体系

典型内容：
- `logistics_order_mapping`
- `logistics_trace_mapping`
- 旧模块说明但已加“历史命名入口”声明的文档

要求：
- 必须明确写出“桥接”或“历史命名入口”角色
- 不能伪装成现行主入口

### 3.3 历史归档

含义：
- 保留追溯价值，但不再作为当前决策依据

典型位置：
- `docs/change_notes/`
- 历史评审清单
- 已完成阶段的来源草图

要求：
- 允许保留原文件
- 但不应继续放在现行阅读主链里作为第一入口

### 3.4 待确认草稿

含义：
- 方向可参考，但业务边界还没有收紧

典型内容：
- 仍带 `draft` 的上下文或方案文档

要求：
- 可以保留 `draft`
- 不要强行升级为正式入口

## 4. 目录分工规则

### 4.1 `docs/context/`

放什么：
- 项目级业务主线
- 可实现性判断
- 原生模块复用口径

不放什么：
- 具体 addon 的实现细节
- 页面级交互设计
- 单次任务计划

### 4.2 `docs/architecture/`

放什么：
- 系统级架构
- addon 边界
- 模块蓝图
- 依赖关系

不放什么：
- 临时调研纪要
- 纯执行步骤

### 4.3 `docs/dev/`

放什么：
- 升级、验证、执行流程
- 团队操作规范
- 当前阶段执行计划

不放什么：
- 长期架构定义
- 只用于回溯的历史判断

### 4.4 `docs/review/`

放什么：
- 文档同步规则
- 过期排查清单
- 评审、核验、归档判断

不放什么：
- 正式业务基线
- 单模块功能设计正文

### 4.5 `docs/change_notes/`

放什么：
- 每轮真实变更记录

要求：
- 说明改了什么
- 说明为什么改
- 说明同步了哪些入口文档

### 4.6 `docs/versioning/`

放什么：
- tag 命名规范
- baseline / milestone / release 说明
- 项目阶段版本说明

不放什么：
- 与版本无关的普通执行计划
- 只为一次任务临时存在的随手记录

---

## 5. 文件命名规则

### 5.1 默认命名形式

建议优先使用：

```text
<domain>_<topic>.md
<YYYY-MM-DD>_<topic>.md
```

适用说明：

- 稳定正式规范优先用语义名
- 单轮记录、阶段记录优先用日期名

### 5.2 稳定正式文档

适合语义名，例如：

- `version_tag_governance.md`
- `document_directory_governance.md`
- `upgrade_and_verify.md`

含义：
- 这些文档不是“一次性记录”
- 是持续复用入口

### 5.3 单轮记录或阶段记录

适合日期名，例如：

- `2026-04-27_version_tag_governance_baseline_added.md`

含义：
- 这是状态记录，不是长期主入口

### 5.4 历史或草稿标识

当文档不是现行正式稿时，应显式体现状态，例如：

- `*_draft.md`
- `*_mapping.md`
- `*_bridge.md`
- `*_archive.md`

不要把历史稿伪装成正式入口。

---

## 6. 文件夹命名规则

### 6.1 文件夹名应体现用途，不应体现个人习惯

优先使用：

- `context`
- `architecture`
- `dev`
- `versioning`
- `review`
- `change_notes`

避免：

- 模糊但看不出作用的文件夹名
- 临时阶段名称直接变成长期主目录

### 6.2 同一层不要混放两套口径

如果某个目录里既有现行稿又有历史稿，应至少满足其一：

1. 历史稿移动到更合适的归档目录
2. 历史稿标题和正文显式声明“仅作桥接/归档参考”

### 6.3 目录真实状态要和正文一致

如果仓库里已经真实存在：

- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- `logistics_web`

则架构文档、上下文文档和目录说明不能继续只写旧阶段目录快照。

---

## 7. 现行入口必须满足的最小标准

凡是要作为团队默认入口的文档，至少应满足：

1. 开头说明适用范围
2. 写清优先基准
3. 明确当前有效口径
4. 区分现行、桥接、历史、草稿
5. 能告诉读者下一步应该看什么

---

## 8. 变更触发规则

下面场景发生时，应同步检查文档/目录治理：

1. 新增或重命名 addon
2. 模块职责变化
3. 主对象变化
4. 页面入口和信息架构变化
5. 当前正式阅读链变化
6. 主管明确要求做结构治理

---

## 9. 执行顺序建议

进行文档治理时，建议按下面顺序收口：

1. 先确认当前有效主线
2. 再确认当前有效模块边界
3. 再区分现行入口、桥接文档、历史文档
4. 最后才做文件名和目录名整理

原因是：

**如果业务主线和模块边界还没先收口，直接改名字只会把混乱换一种写法。**

---

## 10. 当前项目建议的首轮治理目标

首轮不要追求一次性大整理，只要先做到下面 5 件事：

1. 当前正式入口文档不再描述过期目录现实
2. 新旧模块命名的角色区分清楚
3. 新文档统一放到已有 `context / architecture / dev / versioning / review / change_notes` 体系里
4. 每轮真实改动都补 `change_notes`
5. 打 tag 前先做文档同步检查

## 12. 当前结论

文档/目录治理的目标不是让所有文件名都变漂亮，而是让团队在任何一个阶段都能快速分清：

- 哪份是当前有效
- 哪份只是桥接
- 哪份已经历史化
- 新工作应该落在哪个结构里
