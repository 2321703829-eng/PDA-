## 3. 项目介绍

### 3.1 项目是什么

当前项目是建立在 Odoo 19.0 基础上的物流执行与追溯系统定制项目。

它不是传统意义上的“标准 ERP 录单系统微调”，而是围绕物流现场执行、过程留痕、证据沉淀、异常追溯和后台管理展开的一套业务化系统。

项目的目标，不是只把订单录进系统，而是把下面这些能力串成可管理、可追溯、可持续扩展的主链：

- 调度组织
- 现场执行
- 运单追踪
- 留痕事实记录
- 证据采集与阅读
- 异常发现与处理
- 后台工作台与聚合查看

### 3.2 项目试图解决什么问题

如果只依赖传统 ERP 单据流，物流现场常见的几个问题很难被稳定表达：

1. 现场执行过程缺少清晰主对象  
   订单、拣货、出库、配送、签收等信息分散，难形成统一追踪入口。

2. 留痕与证据缺少结构化承载  
   图片、备注、时间、地点、司机、车辆、批次关系容易散落在聊天、附件或临时表里。

3. 异常处理缺少上下文  
   出现异常时，业务方往往只能看到结果，反读不到关键留痕和关键证据。

4. 后台管理缺少面向现场的阅读链  
   传统 ERP 后台更偏静态主数据和业务单据，而不是面向物流现场执行与追溯的工作台。

这个项目的设计核心，就是在 Odoo 现有底座上，补出一条更适合物流执行与追溯的业务主线。

### 3.3 当前核心业务主线

截至本次基线版本，项目当前有效主线已经明确为：

```text
wave -> batch -> waybill -> waybill order lines -> trace -> evidence -> exception
```

其中：

- `wave` 是调度组织层对象，用来承接更高层的波次组织和调度分组
- `batch` 是执行组织层对象，用来承接一轮实际执行批次和现场组织
- `waybill` 是当前现场留痕主对象，是追溯阅读链的核心入口
- `waybill order lines` 是运单下的履约明细，用来描述该运单关联的订单明细和汇总关系
- `trace` 是现场事实层，用来记录某个关键节点发生了什么
- `evidence` 是事实下的证据层，用来承接图片、备注、签名和相关元数据
- `exception` 是问题与处理层，用来承接异常对象、状态流转和处理记录

本次基线确认的是：

**当前项目已经不再按“订单留痕系统 Odoo 化”来理解，而是按“运单主对象的物流执行与追溯系统”来理解。**

### 3.4 当前系统如何被阅读

对不熟悉项目的人，当前系统最重要的阅读方式有两条：

1. 执行主线  
`wave -> batch -> waybill`

2. 追溯主线  
`waybill -> trace -> evidence -> exception`

这两条主线共同决定了系统不是单纯的单据系统，而是“执行组织 + 事实留痕 + 证据追溯 + 异常处理”的组合系统。

### 3.5 当前项目与 Odoo 原生能力的关系

当前项目不是从零自建平台，而是建立在 Odoo 原生底座之上。

其中：

- `contacts / res.partner` 负责客户、门店、联系人等基础对象底座
- `hr / hr.employee` 负责人员基础对象底座
- `stock / stock.warehouse / stock.picking` 负责仓储与出入库底座
- `fleet / fleet.vehicle` 负责车辆基础对象底座
- `mail` 负责消息、活动、协作、附件等基础能力

但 Odoo 原生对象本身不足以直接表达当前这套物流执行与追溯主链，因此项目采用“原生底座 + 自定义 addon 主业务层”的方式推进。

## 4. 当前模块结构介绍

### 4.1 模块分层总览

当前项目的模块理解可以先分成 4 层：

1. Odoo 核心框架层  
   提供 ORM、视图、菜单、权限、模块安装升级等通用能力。

2. Odoo 官方业务底座层  
   提供客户、人员、仓储、车辆、消息附件等标准业务基础。

3. 项目自定义业务层  
   提供物流执行、留痕、证据、异常等项目专属业务对象。

4. 后台页面与交互承载层  
   提供物流后台工作台、页面入口、控制器和前后端交互实现。

### 4.2 当前真实自定义模块

截至本次基线，项目至少已经形成下面这组真实模块现实：

- `logistics_base`
- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- `logistics_web`

同时，下面这组目录仍保留历史过渡意义：

- `logistics_order`
- `logistics_trace`
- `logistics_exception`

这说明当前仓库已经从“旧命名主导阶段”进入“新主线模块现实已出现且可持续推进”的阶段。

### 4.3 各模块职责说明

#### `logistics_base`

这是基础扩展层。

它的主要职责是：

- 承接对 Odoo 官方模型的轻量扩展
- 放置共用字典、共用字段、基础 mixin 和通用约定
- 为后续业务模块提供统一基础能力

它不是一期的主业务对象模块，而是整个项目的公共底座。

#### `logistics_dispatch`

这是执行组织层，也是当前项目最核心的业务模块之一。

它的主要职责是：

- 承接波次、批次、运单等执行主对象
- 承接车辆、司机、仓侧上下文、装车位、路线顺序等执行上下文
- 承接运单与订单明细的归并关系
- 承接后台执行主线的基础页面和菜单入口

对陌生读者来说，可以把 `logistics_dispatch` 理解成：

**“负责回答当前要执行什么、按什么组织执行、运单与批次如何被管理”的模块。**

#### `logistics_trace_core`

这是留痕事实层。

它的主要职责是：

- 承接批次级和运单级留痕事件
- 表达关键现场节点发生的事实
- 承接留痕时间线、留痕查询和事件类型

它不直接承担证据细节和异常处理细节，而是负责把“发生了什么事实”表达清楚。

#### `logistics_trace_evidence`

这是证据层。

它的主要职责是：

- 承接图片、备注、签名、元数据等证据对象
- 承接访问 key、预览信息、挂接关系
- 让后台能够从留痕事实继续往下读到证据材料

它的存在意味着证据不再直接散落在附件里，而是作为留痕主链中的结构化对象存在。

#### `logistics_trace_exception`

这是异常层。

它的主要职责是：

- 承接异常对象本身
- 承接异常状态流转
- 承接处理记录、责任跟进、处理人和处理过程
- 保证异常详情能回读到相关运单、留痕和证据

它不是单纯“记录一个坏结果”，而是负责把异常放回上下文里管理。

#### `logistics_web`

这是当前物流后台页面与交互承载层之一。

它的主要职责是：

- 承接物流后台工作台、页面和动作入口
- 承接控制器、前后端接口对接和部分服务层逻辑
- 把执行主线与追溯主线落成可用的后台体验

对不熟悉项目的人来说，`logistics_web` 可以理解成：

**“把前面那些业务模块真正呈现在后台界面上的落地层”。**

### 4.4 当前未作为正式现实主线的模块

虽然仓库里仍能看到：

- `logistics_order`
- `logistics_trace`
- `logistics_exception`

但它们当前更多代表：

- 早期阶段的模块拆分思路
- 历史命名兼容入口
- 过渡性目录现实

它们不再代表当前最终业务边界，也不应继续作为后续设计和实现的主理解入口。

## 5. 模块之间关系图式说明

### 5.1 业务主线图

如果只用一句话概括当前系统，可以理解为：

```text
调度组织 -> 执行组织 -> 运单主对象 -> 现场事实 -> 证据材料 -> 异常处理
```

展开到当前项目主线后，可读成：

```text
wave
  -> batch
    -> waybill
      -> waybill order lines
      -> trace
        -> evidence
        -> exception
```

这条图的意思是：

- `wave` 负责更高层调度分组
- `batch` 负责一轮实际执行组织
- `waybill` 是核心业务阅读入口
- `waybill order lines` 负责承接明细
- `trace` 负责记录发生了什么
- `evidence` 负责记录有什么证据
- `exception` 负责记录哪里出了问题、怎么处理

### 5.2 模块承载关系图

如果按“哪个模块承接哪一层能力”来理解，可以读成：

```text
Odoo core / official addons
  -> logistics_base
    -> logistics_dispatch
      -> logistics_trace_core
        -> logistics_trace_evidence
        -> logistics_trace_exception
    -> logistics_web
```

更贴近职责的解释是：

```text
官方底座
  -> 基础扩展
    -> 执行主线
      -> 留痕事实
        -> 证据
        -> 异常
    -> 后台页面与交互承载
```

### 5.3 面向非技术读者的理解方式

对不熟悉代码的人，可以把当前几个核心模块理解成下面这组关系：

```text
logistics_base
  是基础规则层

logistics_dispatch
  是执行主线层

logistics_trace_core
  是现场事实层

logistics_trace_evidence
  是证据材料层

logistics_trace_exception
  是异常处理层

logistics_web
  是后台展示与交互落地层
```

如果换成更业务化的说法：

- `logistics_dispatch` 回答“这票货怎么组织执行”
- `logistics_trace_core` 回答“现场发生了什么”
- `logistics_trace_evidence` 回答“有什么材料可以证明”
- `logistics_trace_exception` 回答“出了什么问题、怎么处理”
- `logistics_web` 回答“这些内容在后台怎么被看见、怎么被操作”

### 5.4 当前系统的整体关系图

把业务对象、模块和后台入口放到一张简化图里，可以理解为：

```text
官方基础对象
  contacts / hr / stock / fleet / mail
        |
        v
  logistics_base
        |
        v
  logistics_dispatch
    |         |
    |         +--> logistics_web 后台执行入口
    |
    +--> waybill
           |
           +--> logistics_trace_core
                  |         |
                  |         +--> logistics_trace_exception
                  |
                  +--> logistics_trace_evidence
           |
           +--> logistics_web 追溯阅读入口
```

这张图最想表达的是：

- 项目不是一堆平行页面拼起来的
- 它是围绕 `waybill` 这个核心对象，把执行、留痕、证据、异常和后台入口串成一条链
