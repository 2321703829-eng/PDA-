## Objective

在不改变当前业务主链、模块边界和 Odoo 承载方式的前提下，为现有物流后台补一轮更适合中国用户的 UI 与中文体验优化方案。

这轮方案重点解决：

1. 当前界面仍然过于接近 Odoo 原生风格，缺少中国物流后台常见的重点分区和行动导向
2. 部分中文虽然已完成翻译，但表达仍偏直译、机翻或技术语气，不够贴近日常使用习惯
3. 运单详情页中仍存在中英混排、页签命名不统一、列表列头偏英文数据模型名的问题

---

## Boundary

本方案只覆盖：

- `custom_addons/logistics_web` 前端增强层
- 运单详情页中的留痕与证据增强区
- 工作台与管理层总览页
- 用户可见的中文标题、按钮、状态、提示语、空态与错误态

本方案不覆盖：

- 官方 Odoo 通用皮肤整体替换
- 执行主线和追溯主线的对象结构调整
- 接口、模型、权限、菜单体系的大改
- 小程序端或外部 React 后台的完整迁移

---

## Benchmark

本轮优化统一参考三类基准：

1. 项目现有业务主线基准  
   `wave -> batch -> waybill -> trace -> evidence -> exception`

2. 当前 Odoo 后台设计基准  
   保留 Odoo 原生后台的稳定结构、表单能力和模块承载方式，只增强阅读体验

3. 外部参考基准  
   参考 `D:\Desktop\ai-code-main` 中已经体现出的几个可借鉴方向：
   - 导航命名更业务化，不直接暴露技术词
   - 看板卡片更像行动入口，而不是纯展示数字
   - 中文文案更短、更直接、更像团队日常说法
   - 页面层级依靠留白、卡片、标题和摘要建立，而不是靠堆边框和堆术语

## Current Understanding

结合当前仓库代码、已有设计稿和你提供的截图，现阶段最明显的问题有 4 类。

### 1. 风格仍偏 Odoo 原生默认后台

- 卡片和区块更像“默认可用态”，不像已经收口过的物流管理后台
- 标题区说明偏弱，页面没有明确告诉用户“先看什么、再做什么”
- 风险和重点没有被稳定地提炼成简洁的分区和信号卡

### 2. 中文命名不够本土化

- 菜单和页面里仍有 `Frontend`、`Trace & Evidence` 这类偏技术或英文残留
- 某些状态词如果直接按英文状态翻译，会出现“打开”这类不符合中文业务习惯的表达
- 提示语中仍有“读取失败”“不可用”等偏系统语气，缺少业务动作导向

### 3. 运单详情页中英混排明显

从当前截图可以直接看到：

- 页签同时出现 `订单明细`、`备注`、`Trace & Evidence`
- 列头同时出现 `External Order No`、`Sale Order`、`Stock Picking`、`Goods Summary`、`Line Status`
- 中文用户会先感知到“这是技术系统”，而不是“这是物流运营后台”

### 4. 信息结构还可以更贴合中国团队的使用习惯

- 中国物流后台更强调“今日重点”“待处理”“待补证据”“直接进入处理”
- 说明文案更适合短句、动作词和结论先行
- 管理层页面更适合“风险摘要 + 重点对象”，而不是泛化的 dashboard 描述

---

## Outcome

如果本轮优化完成，用户应该感知到下面这些变化：

1. 页面还是简约的，但明显不再像未经处理的 Odoo 默认页
2. 菜单、页签、卡片、按钮和提示语都更像中国物流团队会直接使用的叫法
3. 工作台和管理层总览更像“业务入口页”，不是“技术数据页”
4. 运单详情里的留痕与证据区更像阅读面板，而不是附加在表单里的技术块

---

## Behavior

### 1. 视觉方向

- 保持简约，不做重装饰和高饱和界面
- 采用更稳定的灰蓝中性色做主底色，用风险色只强调重点对象
- 标题区使用更清楚的页面职责表达，例如“运营工作台”“管理层总览”
- 卡片强调“点击后做什么”，而不是只告诉用户一个数字
- 留痕和证据区强调阅读顺序：先看留痕，再看证据，再看异常

### 2. 中文文案方向

- 优先使用业务中文，不优先保留英文模型词
- 标题尽量短，副标题只说“看什么、做什么”
- 状态文案统一偏业务表达：
  - `open` 优先显示为 `待处理`
  - `processing` 显示为 `处理中`
  - `resolved` 显示为 `已解决`
- 动作文案统一偏行动词：
  - `查看证据`
  - `查看异常`
  - `查看关联留痕`
  - `打开原图`

### 3. 运单详情页命名方向

建议统一调整为：

- `Trace & Evidence` -> `留痕与证据`
- `Trace Timeline` -> `留痕时间线`
- `Evidence Viewer` -> `证据查看`
- `Fallback Data (Debug)` -> `原始关联数据（调试）`

订单明细表格列头建议统一调整为更自然的中文：

- `External Order No` -> `外部单号`
- `Sale Order` -> `销售订单`
- `Stock Picking` -> `出库单`
- `Goods Summary` -> `货物摘要`
- `Line Status` -> `明细状态`

## Visual Rules

### 1. 页面标题区

- 标题区必须同时承担“页面命名 + 处理引导”职责
- 副标题不要重复标题，要补充“下一步建议”
- 标题区可以轻量增强背景和边框，但不能喧宾夺主

### 2. 指标卡片

- 卡片文案必须偏动作入口
- 优先展示“待处理异常”“待补证据”“风险批次”这类可直接驱动操作的指标
- 高风险卡片数量不宜过多，防止整页始终处于红色告警感

### 3. 留痕时间线

- 时间点要醒目，但不要比结论文案更抢眼
- 留痕类型、证据数量、异常标签要清晰分层
- 默认支持“只看有图”“只看异常”这类阅读筛选

### 4. 证据查看区

- 主图区和元信息区要分层明确
- 图片切换、查看原图、查看关联留痕应保持固定位置
- 元信息只保留最有判断价值的字段，不要像技术调试面板

---

## Copy Rules

### 1. 统一命名

- 同一页面里不要混用“追踪 / 跟踪 / 追溯”
- 同一页面里不要同时出现“异常 / 争议 / 问题”三套平级叫法
- 技术词如果不影响业务，优先翻成业务中文

### 2. 空态文案

空态要说明“现在没有什么”：

- `当前还没有留痕记录`
- `当前还没有证据`
- `当前没有需要优先处理的对象`

### 3. 错误态文案

错误态要说明“出问题了”和“用户现在能做什么”：

- `运营工作台加载失败，请刷新页面或稍后再试。`
- `留痕时间线加载失败，请稍后重试。`
- `证据暂时无法读取，可先查看关联留痕。`

## Risks

### 1. 不能把“本土化”做成“堆砌装饰”

如果过度追求所谓中国风，很容易把页面做得更重、更乱。  
本项目应该保持简约，只提升层级和语气。

### 2. 不能让中文和状态语义脱节

有些英文状态可以技术上保留，但面对用户时必须换成业务表达，否则会出现“翻译正确但体验很怪”的问题。

### 3. 不要直接改成完全脱离 Odoo 的另一套后台

这轮是“增强”，不是“另起炉灶”。  
如果连基础结构都推翻，后续 Odoo 落地成本会明显升高。

## Development Plan

### Step 1. 先清理最显眼的中英混排

- 页签
- 工作台标题
- 管理层总览标题
- 留痕与证据 widget 标题
- 订单明细列头

### Step 2. 收口工作台和管理层总览的页面语气

- 把标题、副标题、卡片标题改成中文业务语气
- 把“技术描述”改成“行动提示”

### Step 3. 收口留痕与证据区的阅读体验

- 调整区块层级
- 强化“先留痕、后证据”的顺序
- 让按钮和标签更短、更稳、更适合中国用户

### Step 4. 最后统一做一轮视觉收口

- 卡片边距
- 标题层级
- 风险标签
- 空态和错误态

## 2026-04-15 补充收口

在 Step 1 已经基本完成后，这一轮继续补下面几类“看起来不大，但会明显影响体验”的问题：

1. 管理层总览继续统一命名

- 用户可见页面里不再混用“异常 / 争议 / 问题”这类平级词
- 管理层对象卡、风险卡和动作按钮统一使用“异常”体系
- 动作按钮统一偏业务动作词，例如“查看异常 / 查看运单 / 查看批次”

2. 运单“留痕与证据”页补足阅读引导

- 在页签内增加轻量引导条，明确“先看留痕顺序，再看证据图片，最后核对异常”
- 不改变原有对象结构，只增强用户阅读顺序和处理路径
- 原始关联数据区继续保留，但弱化为调试排查用途

3. 留痕时间线补充筛选反馈

- 当用户启用“只看有图 / 只看异常”时，界面要明确告诉用户“当前共多少条、筛选后剩多少条”
- 当筛选后无结果时，空态文案要提醒可以取消筛选继续查看，而不是只显示空白
- 时间线仍然保持简洁，不增加重型统计面板

4. 证据查看补充上下文摘要

- 当前正在看的证据，需要明确关联哪条留痕、是否与异常相关、当前是第几张
- 当只能预览、不能打开原图时，要给出轻量提示，减少“按钮灰掉但用户不知道原因”的感受
- 证据查看仍然以图片为主，不做成技术调试面板
