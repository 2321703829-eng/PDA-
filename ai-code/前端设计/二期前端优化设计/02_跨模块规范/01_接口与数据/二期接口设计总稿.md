# 二期接口设计总稿（领导阅读版）

适用范围：
- 用于向领导、项目负责人、后端负责人统一说明二期接口升级内容
- 当前只覆盖后台 `admin` 场景

当前状态：
- 本文档是二期接口资料的默认主入口
- 目标是把原先分散在多份文档里的结论合并到一份总稿中
- 同目录下其他文档继续保留，但默认视为工作底稿和参考材料

---

## 1. 文档定位

这份总稿只回答 5 个核心问题：

1. 二期相较一期，接口到底新增了什么
2. 哪些接口继续复用一期，哪些只是扩字段
3. 二期新增接口分别服务哪些页面和能力
4. 这些接口建议落在当前仓库哪个模块、哪些文件附近
5. 后端应该按什么顺序开工和联调

如果领导只看一份文档，默认看本文件即可。

## 2. 二期相较一期的升级结论

### 2.1 一句话结论

二期接口升级不是重写一期，而是在一期稳定基础上，重点补齐 4 组能力：

1. 首页聚合
2. 所有统计图表
3. 运单详情三层阅读结构
4. 标准导入模板主路径

### 2.2 二期总体判断

| 类别 | 结论 |
| --- | --- |
| 一期稳定列表、详情、异常、证据、留痕接口 | 继续复用 |
| 首页、统计图表、导入主流程 | 二期新增接口 |
| 运单详情头部摘要 | 在一期接口基础上扩字段升级 |
| 品牌化、菜单改名、中文化、显隐 | 不建议误判为“必须新开接口” |

### 2.3 二期新增接口域

| 接口域 | 二期动作 | 推荐路线 |
| --- | --- | --- |
| 首页 | 新增 | JSON controller |
| 所有统计图表 | 新增 | JSON controller |
| 运单详情三层阅读 | 新增子表接口，详情头部扩字段 | RPC 优先 |
| 标准导入模板主路径 | 新增 | JSON controller |

## 5. 路线、命名与统一返回口径

### 5.1 路线结论

| 场景 | 推荐路线 |
| --- | --- |
| 首页聚合 | JSON controller |
| 所有统计图表 | JSON controller |
| 标准导入模板主路径 | JSON controller |
| 运单详情头部与子表读取 | RPC 优先 |

### 5.2 路径前缀结论

二期新增后台接口统一按：

- `/api/admin/logistics/...`

当前总稿不展开 `mini` 与 `open` 场景。

### 5.3 命名结论

| 类型 | 命名规则 |
| --- | --- |
| 读取类 | `getXxx...` |
| 下载类 | `downloadXxx...` |
| 预校验类 | `precheckXxx...` |
| 正式提交类 | `confirmXxx...` |
| 结果读取类 | `getXxxResult...` |

### 5.4 统一返回结构

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

错误返回统一保持：

```json
{
  "code": "IMPORT_TEMPLATE_INVALID",
  "message": "模板格式不正确",
  "data": {
    "field": "template_version",
    "detail": "当前模板版本不在白名单内"
  }
}
```

## 6. 导入模板与错误反馈统一规则

### 6.1 二期导入结构

二期导入不再只看“一张平表”，而是按三层结构组织：

1. 运单层
2. 客户层
3. 货物层

### 6.2 模板字段分组

| 分组 | 典型字段 |
| --- | --- |
| 运单层 | `waybill_no`、`batch_no`、`wave_no`、`delivery_date`、`store_no`、`store_name` |
| 客户层 | `customer_no`、`customer_name`、`delivery_note`、`signoff_requirement` |
| 货物层 | `goods_code`、`goods_name`、`specification`、`quantity`、`package_count`、`uom_name`、`weight`、`volume`、`temperature_zone`、`package_type` |
| 系统辅助 | `template_version`、导入批次标识等 |

### 6.3 预校验必须覆盖的错误类型

| 错误层级 | 典型问题 |
| --- | --- |
| 模板级 | 文件类型错误、模板版本错误、表头缺失 |
| 字段级 | 必填缺失、格式非法、数值越界 |
| 主数据匹配 | 运单找不到、客户找不到、门店找不到 |
| 分层一致性 | 运单号不一致、客户与货物归属不一致、重复行冲突 |

### 6.4 结果页必须反馈的统计

| 指标 | 说明 |
| --- | --- |
| `created_waybill_count` | 成功创建或处理的运单数 |
| `created_customer_line_count` | 成功处理的客户明细数 |
| `created_goods_line_count` | 成功处理的货物明细数 |
| `failed_row_count` | 失败行数 |
| `errors[]` | 错误明细 |

## 8. 实现优先级与联调顺序

### 8.1 实现优先级

| 优先级 | 任务包 | 接口范围 | 原因 |
| --- | --- | --- | --- |
| P0 | 运单详情三层读取包 | `getWaybillDetailV2`、`getWaybillCustomerLinesByWaybill`、`getWaybillCustomerGoodsLinesByWaybill` | 二期数据结构升级基础 |
| P0 | 首页聚合接口包 | `getHomeOverviewSummary`、`getHomeRecentActivities`、`getHomeGuideByRole` | 首页为二期主入口 |
| P1 | 统计图表接口包 | `getStatsOverviewByDateRange`、`getStatsTrendByMetric`、`getStatsRankingByDimension` | 依赖聚合但不阻塞基础详情 |
| P1 | 模板下载与预校验包 | `downloadWaybillStandardTemplate`、`precheckWaybillStandardImport` | 导入链路前半段 |
| P2 | 正式导入与结果页包 | `confirmWaybillStandardImport`、`getWaybillImportResult` | 依赖预校验稳定后推进 |

### 8.2 推荐开工顺序

1. 先做运单详情三层读取
2. 再做首页聚合
3. 再做统计图表
4. 再做模板下载与预校验
5. 最后做正式导入与结果页

### 8.3 推荐联调顺序

| 联调阶段 | 联调对象 | 重点 |
| --- | --- | --- |
| L1 | 运单详情三层读取 | 数据结构是否匹配页签 |
| L2 | 首页聚合 | 卡片数据、趋势卡片、角色引导是否稳定 |
| L3 | 统计图表 | 时间范围、趋势点、排行结构 |
| L4 | 模板下载与预校验 | 模板版本、字段校验、错误反馈 |
| L5 | 正式导入与结果页 | token 生命周期、导入结果统计 |

## 10. 给领导的最终结论

二期接口升级的核心不是“接口数量变多”，而是“业务入口和数据结构升级了”。真正需要新增的接口集中在首页、统计图表、三层运单详情和标准导入四组，范围是收敛的、可控的，而且已经可以明确映射到现有 `custom_addons` 仓库结构中开工。

从管理视角看，这一轮已经具备 3 个条件：

1. 接口边界已经清楚，不会和一期混写
2. 仓库落位已经清楚，可以直接拆给后端实现
3. 排期、联调、检查口径已经清楚，可以进入执行阶段
