## Objective

在一期完成基础业务承载、二期完成首页、导入和统计入口优化后，三期继续围绕“管理对象升级、分析能力升级、界面系统化收口”推进前端优化工作。

本轮方案重点回应下面 3 类需求：

1. 把员工模块进一步分层，形成更清晰的后台工作人员管理与司机管理体系
2. 把统计模块从摘要型看板升级成更专业的物流分析中心
3. 把当前后台界面中已经影响可读性、层级感和专业感的问题纳入系统化美化范围，并作为后续持续补充的设计线索

在保持这 3 条主线不变的前提下，三期同时承接一小组与当前主线不冲突的二期收尾项：

- 导入结果页的进一步页面化与回看体验补齐
- 三期新增接口与二期存量接口的命名/口径统一
- 与当前前端主路径直接相关的少量技术债清理

## 审批关注点



1. 三期主线是否冻结为 `司机管理 / 统计图表 / 界面系统化美化`
2. 二期遗留是否只承接小范围收尾项，而不重新拉回导入中心扩建
3. 司机画像页与全局统计页的边界是否清楚
4. 界面系统化美化是否按“先方向收口、后持续补点”的方式推进
5. 实施顺序是否接受“先司机管理，再统计图表，后界面系统化美化与收尾项”

## Boundary

本方案覆盖：

- 司机管理专题
- 统计图表专题
- 三期界面系统化美化方向
- 与三期主线直接相关的二期可承接收尾项
- 三期涉及的页面结构、交互、接口升级方向和实施顺序

本方案不直接覆盖：

- 本轮代码实现

- 与三期目标无关的历史页面全面重做
- 非运单对象的导入中心化扩建
- 独立客户明细 / 货物明细标准模板
- 客户与货品固定需求 + 临时需求体系
- 企业分离方案中的套餐能力层与跨租户能力设计

## Benchmark

本轮方案统一参考下面几条基准：

1. 当前项目业务主线  
`wave -> batch -> waybill -> trace -> evidence -> exception`

2. 当前项目前端基准  
一期已完成：基础对象页、追溯页、异常页和跨模块基础规范  
二期已完成：首页、导入入口、统计入口和结构化阅读优化

3. Odoo 原生能力基准  
复用 Odoo 的模型、权限、菜单、动作、导入导出与 Web 承载能力，但三期继续在司机管理、统计图表和界面表达层进行项目化扩展

4. 当前三期业务目标基准  
让系统在管理能力、分析能力和产品感知上同时进一层，而不是只补单点功能

## Odoo Baseline Comparison

### 1. Odoo 已有能力

- Odoo 原生可承载后台菜单、列表页、详情页、搜索和基础 dashboard
- Odoo 原生 `hr`、`contacts`、`fleet` 等模块可继续作为三期对象建模参考基础
- Odoo 原生 Web 壳层可承载页面级布局和动作入口，但当前项目仍需继续做项目化视觉和信息层级优化

### 2. 当前项目仍然缺少的部分

- 缺少面向执行资源对象的司机画像式管理能力
- 缺少真正可下钻、可分析、可解释的物流统计图表中心
- 缺少一套逐步收口的界面系统化美化规则，导致个别页面顶部、列表和操作区仍保留默认后台痕迹
- 二期遗留中仍有少量适合并入三期的收尾项尚未正式纳入三期口径

### 3. 设计路径判断

- 司机管理：`extend Odoo + create custom capability`
- 全局统计图表页：`create custom capability`
- 三期界面系统化美化：`extend Odoo`

## Current Understanding

### 1. 当前系统在一期、二期完成后的现状

- 一期完成了物流主对象和核心链路的基础承载
- 二期完成了首页、导入体验和统计入口等较大范围的结构优化
- 三期目前已经逐步形成司机管理和统计图表两条主线的专题资料

### 2. 三期真正要解决的问题

- 系统需要从“有页面可用”继续走向“有对象可管理、有分析可判断、界面更像成熟产品”
- 当前用户对顶部栏、列表页、详情页和图表页的专业感要求已经高于二期阶段
- 界面美化不适合继续按零散修补推进，需要先形成方向，再按使用过程持续补充问题点

### 3. 本轮新增纠偏结论

结合当前现状，三期建议补充下面这些硬性纠偏：

1. 顶部栏优先解决可读性、主次层级和技术噪声问题，不再直接沿用默认壳层表达
2. 全局统计页和司机画像页的分工必须保持清楚，避免司机图表重复堆叠
3. 界面系统化美化先收口规则和问题方向，再在后续使用中逐步补充细节点
4. 二期遗留不应整包并入三期，只承接与当前三期主线直接相关的结果页页面化、接口口径统一和少量技术债清理

## Outcome

如果本轮方案后续按阶段执行，目标状态应是：

1. 司机管理成为独立清晰的执行资源管理专题
2. 统计模块成为具备趋势、排行、分布和下钻闭环的物流分析中心
3. 三期开始形成界面系统化美化规则，而不是继续只做零散调样式
4. 首页、统计页和对象页的整体产品感显著高于二期
5. 三期后续新增的界面问题能被持续归档并纳入同一条设计主线
6. 二期中可承接的收尾项不再悬空，而是并入三期统一规划和联调

## Interface Direction

### 1. 一期、二期继续复用的接口域

- 运单基础列表与详情读取
- 异常基础列表与详情读取
- 批次基础列表与详情读取
- 二期导入结果读取与错误报告下载能力

### 2. 三期明确新增或升级的接口域

- 司机管理接口域
- 全局统计图表接口域
- 导入结果页页面化所需的最小结果回看能力
- 后续如界面系统化美化涉及新的环境标识、顶栏配置或入口配置，再按需补充

### 3. 路线判断

- 标准对象列表、详情、子表读取：优先 `RPC`
- 聚合首页、统计、画像指标和趋势页：优先 `JSON controller`
- 当前后台接口前缀建议：`/api/admin/logistics/...`

## Phasing Plan

### Phase 0. 方案冻结

- 冻结三期范围
- 冻结司机管理、统计图表与界面系统化美化三条主线
- 冻结统计指标口径与页面边界

### Phase 1. 司机管理

- 完成司机管理专题、接口、交互、权限和验收清单
- 确认司机画像页与后台工作人员管理的边界

### Phase 2. 统计图表

- 完成统计图表专题、指标字典、交互、接口和验收清单
- 确认全局统计页与司机画像页的图表分工

### Phase 3. 界面系统化美化

- 在不打乱前两条线的前提下，逐步收口三期界面美化规则
- 先记录并处理已识别问题，再随着实际使用持续补充更多美化点

### Phase 3.5 二期可承接收尾

- 在不改变三期三条主线的前提下，补齐导入结果页页面化与结果回看体验
- 结合三期新增接口实现，同步收口二期存量接口与三期接口的命名/口径一致性
- 清理与当前前端主路径直接相关的少量技术债，例如 deprecated 路由写法与旧兼容资源残留

## Risks

### 1. 结构性风险

- 如果三期继续只做功能补充，不同步收口界面规则，页面体验会越来越碎

### 2. 联调风险

- 如果统计图表、司机画像和原业务列表的下钻口径不一致，后续联调会反复返工

### 3. 用户迁移风险

- 如果界面美化一次性改动过大，可能影响已有用户的使用惯性

### 4. 当前控制方式

- 先冻结专题边界，再进入实现
- 界面系统化美化先从高感知、低风险的位置开始
- 持续把新增问题点回写到三期文档，而不是只停留在临时讨论里
- 二期遗留只承接与三期主线直接相关的部分，避免把三期重新拉回导入中心扩建项目

## 已识别的首批界面美化问题

当前已确认并写入三期总纲的界面系统化美化问题包括：

1. 首页顶部左侧系统名称与当前页文字当前使用了偏蓝色字体，在蓝底背景上对比度不足，影响可读性
2. 首页顶部右侧按钮区当前同时混有通知、公司、用户与环境信息，信息噪声偏高，需要评估保留项并重组格式

说明：

- 这两项作为三期界面系统化美化的首批已识别问题先写入总纲
- 后续如在实际使用中发现新的美化问题点，继续按同一条设计线补充
