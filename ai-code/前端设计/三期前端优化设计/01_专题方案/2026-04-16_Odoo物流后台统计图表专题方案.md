## Objective

在二期已经完成首页、统计入口和部分统计能力补充的基础上，把当前偏摘要化的统计模块升级成一个更像“物流分析中心”的全局统计页。

这轮方案重点解决 4 个问题：

1. 当前统计模块仍偏简单看板，缺少能让用户一眼看懂趋势和风险的图表表达
2. 现有统计内容虽然有摘要，但缺少清晰分组，容易让用户觉得只是数字堆叠，不像专业后台
3. 司机相关图表如果全部放在全局统计页，会和司机画像详情页职责重复
4. 统计页如果没有稳定的下钻目标，就很容易沦为只展示、不行动的 BI 墙

## 审批关注点

建议主管重点确认下面 5 个结论：

1. 三期统计页是否正式定位为“物流分析中心”，而不是摘要型 dashboard
2. 统计页第一页是否按 `执行概览 / 风险概览 / 司机与资源 / 区域与质量` 4 组组织
3. 第一版是否正式冻结为 `10 张图`，其中 `P0 8 张 + P1 2 张`
4. 全局统计页是否只保留 `司机月均异常率排行图`，其余司机个人趋势图全部放到司机画像页
5. 图表是否必须具备下钻闭环，而不是只做展示

## Boundary

本方案覆盖：

- 全局统计图表页第一页结构
- 三期第一版保留图表清单
- `P0 / P1` 图表优先级
- 图表分组与页面层级
- 图表下钻到业务列表的方向
- 图表页与司机画像页的分工

本方案不覆盖：

- 司机画像页中的个人趋势图
- 统计图表的最终视觉稿
- 后端接口实现细节与聚合 SQL
- 多租户跨企业汇总统计
- 更复杂的经营报表和计费型报表体系

## Benchmark

本轮方案统一参考下面 4 条基准：

1. 当前项目业务主线基准  
   `wave -> batch -> waybill -> trace -> evidence -> exception`

2. 当前项目前端基准  
   一期已形成基础对象页、追溯页和异常页  
   二期已形成首页、统计入口、导入入口和阅读层优化

3. Odoo 原生能力基准  
   继续复用 Odoo 后台页面、菜单、动作和基础视图承载，但统计图表表达需要明确补强项目自定义能力

4. 当前三期业务目标基准  
   让统计模块不再只是“数字摘要区”，而是能支持运营管理、风险识别和价值感知的分析中心

## Odoo Baseline Comparison

### 1. Odoo 已有能力

- Odoo 原生可承载菜单、client action、列表页、搜索和基础 dashboard 页面
- Odoo 原生可承载图表型视图和统计展示，但不天然等同于项目需要的物流经营分析中心
- Odoo 原生权限、动作和上下文机制可继续复用

### 2. 当前项目仍然缺少的部分

- 缺少一页收口的全局物流统计中心
- 缺少围绕运单、批次、司机、地区、证据风险的稳定图表组合
- 缺少“从图表直接下钻到业务列表”的统一动作链
- 缺少全局统计页与司机画像页之间清晰的职责分工

### 3. 设计路径判断

- 全局统计图表页：`create custom capability`
- 图表数据聚合接口：`extend Odoo + custom capability`
- 图表下钻到原有业务列表：`extend Odoo`
- 司机个人趋势图：`create custom capability`，但承接在司机画像页而不是全局统计页

## Current Understanding

### 1. 当前系统在一期、二期完成后的现状

- 二期已经明确了 `所有统计图表` 应作为独立入口
- 当前系统里已有部分摘要和排行方向，但图表层仍不够强
- 用户已经明确希望三期统计页覆盖“运单物流相关的所有统计图”，而不是只做司机附属图表

### 2. 当前真正需要解决的问题

- 不是简单“加几张折线图”，而是要把统计页升级成一个可分析、可下钻、可解释的全局入口
- 统计页必须优先服务运营和管理，而不是泛化成装饰型大屏
- 图表页必须回答明确问题，例如：
  - 业务量怎么变
  - 风险集中在哪里
  - 哪些批次最危险
  - 哪些地区最需要关注

### 3. 当前已冻结的关键结论

1. 全局统计页第一页按“管理问题”而不是“图表类型”分组
2. 地区维度统一采用 `门店地区` 口径
3. 证据相关指标统一围绕 `缺证据运单` 收口
4. 全局统计页只保留 `司机月均异常率排行图`
5. 司机个人趋势图统一留在司机画像详情页，不再放进全局统计页
6. 三期统计页第一版按 `10 张图` 收口，其中 `P0` 先做 `8 张`，`P1` 再补 `2 张`

## Outcome

如果本轮方案后续按阶段执行，目标状态应是：

1. 全局统计页成为一个更像物流分析中心的独立入口
2. 统计页上半屏可快速看整体执行量和履约质量，下半屏可快速看风险、地区和司机维度问题
3. 图表和业务列表之间形成稳定的下钻闭环
4. 司机相关图表在全局页和画像页之间职责清楚，不发生重复堆叠
5. 统计模块在用户感知上明显比二期更专业、更成熟、更值得付费

## Information Architecture

### 1. 页面定位

三期全局统计页建议统一理解为：

- 面向运营管理者和管理层的物流分析中心
- 不是单纯 dashboard 摘要页
- 也不是单个对象画像页

### 2. 页面分组

全局统计页第一页统一按下面 4 组组织：

1. `执行概览`
2. `风险概览`
3. `司机与资源`
4. `区域与质量`

### 3. 页面分组说明

#### 3.1 执行概览

回答的问题：

- 业务量怎么变化
- 履约质量是否稳定

建议放：

- `运单量趋势折线图`
- `运单签收率 + 超时率双折线图`

#### 3.2 风险概览

回答的问题：

- 当前主要问题是不是在扩大
- 风险集中在哪些异常类型
- 哪些批次最危险

建议放：

- `异常总量趋势折线图`
- `异常类型分布图`
- `高风险批次排行图`

#### 3.3 司机与资源

回答的问题：

- 全局维度下，哪些司机更值得关注

建议放：

- `司机月均异常率排行图`

说明：

- 本区只做横向比较
- 不承接单司机纵向趋势图

#### 3.4 区域与质量

回答的问题：

- 各地区业务量是否均衡
- 哪些地区更容易出问题
- 履约质量和证据质量是否稳定

建议放：

- `地区运单量分布图`
- `地区异常率排行图`
- `地区签收率对比图`
- `缺证据率 + 缺证据运单数双指标趋势图`

## Driver Boundary

### 1. 全局统计页中的司机图

全局统计页只保留：

- `司机月均异常率排行图`

它承担的职责是：

- 从全局视角发现高风险司机
- 作为进入司机画像详情页的入口

### 2. 司机画像页中的司机图

司机画像详情页承接：

- `司机月度运单量趋势图`
- `司机异常率趋势图`
- `司机签收率 + 超时率双指标趋势图`

### 3. 分工原则

- 统计页负责横向比较
- 画像页负责单对象纵向解释

这样可以避免：

- 同一批司机图在两个页面重复出现
- 全局统计页被个人画像信息拖重

## Drilldown Rules

### 1. 总体原则

三期统计图表必须支持下钻，但下钻目标应尽量直接进入“可继续处理”的列表页或对象页。

### 2. 统一下钻规则

- 趋势图点时间点 -> 跳对应时间范围的业务列表
- 排行图点对象 -> 跳对象详情页或对象关联列表
- 分布图点分类 -> 跳该分类筛选后的列表

### 3. 典型下钻方向

- `运单量趋势图` -> 运单列表
- `签收率 / 超时率图` -> 对应运单列表
- `异常总量趋势图` -> 异常列表
- `异常类型分布图` -> 对应异常列表
- `高风险批次排行图` -> 批次详情或批次异常运单列表
- `司机月均异常率排行图` -> 司机画像详情页
- `地区运单量分布图` -> 地区运单列表
- `地区异常率排行图` -> 地区异常运单列表
- `地区签收率对比图` -> 地区签收 / 未签收运单列表
- `缺证据双指标趋势图` -> 缺证据运单列表

## Risks

### 1. 图表过多风险

如果第一版一上来把所有候选图都塞进去，统计页会重新变成“大而全但不好用”的图表墙。

### 2. 指标漂移风险

如果统计页图表口径和指标字典不一致，用户会很快失去对图表的信任。

### 3. 职责混乱风险

如果全局统计页继续堆单司机纵向趋势图，司机画像页价值会被削弱。

### 4. 下钻失效风险

如果图表只能看、不能继续下钻，统计页会沦为展示层，难以支撑实际运营动作。
