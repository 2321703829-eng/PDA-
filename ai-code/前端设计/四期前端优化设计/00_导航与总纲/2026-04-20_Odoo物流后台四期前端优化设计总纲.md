## 一页结论

四期当前的总判断可以直接收口成 10 条：

1. 四期不是继续补零散字段，而是一次性收口导入、对象、图片、阅读链四条主线。
2. 前端默认主入口是**单表快捷导入**，不再让业务用户优先面对三 Sheet。
3. 三 Sheet 继续保留，但只作为**四期过渡契约**和技术契约，前端可隐藏。
4. 系统内部稳定结构是：
   - `waybill -> customer_line -> order_line -> goods_line`
5. `customer_line` 正式定义为运单下的**门店交付节点**。
6. `order_line` 是首轮**主阅读层**，承接订单快照和订单对应货物的展示快照。
7. `goods_line` 是商品事实源与货物基础信息层，首轮保留但不作为主阅读层。
8. 图片链路与 XLSX 主数据链路分开，首轮只认 `customer_line` 作为业务最小挂点。
9. 图片物理结构首轮收口为：
   - `运单图片包 -> 门店图片包 -> 图片文件`
10. 四期首轮最重要的实施路径不是重构底座，而是：
    - 稳定键
    - 映射层
    - 结果页
    - 图片包进出链路

## 四期边界

### 四期覆盖

- 单表快捷导入主入口
- 三 Sheet 过渡契约与复用预校验
- `waybill / customer_line / order_line / goods_line` 四层对象职责重排
- 门店节点稳定键 `customer_line_no`
- 订单层回归正式结构
- 货物层事实源与展示快照分离
- 留痕和证据向门店层下沉
- 图片批量导入、预览、批量导出
- 页面阅读链与联调验收口径

### 四期不直接覆盖

- 完整重写 `wave / batch / waybill` 执行主线
- 完整对象存储底座重构
- 历史全量迁移和历史账务对齐
- 企业分离、套餐、多租户等更高层议题
- 非运单对象导入中心化扩展
- 订单层图片挂点

## 模块一：导入模块

## 1.1 模块目标

导入模块要解决的核心问题不是“多加几个字段”，而是：

- 让业务用户只需要维护一张单表
- 又不把系统内部结构扁平化
- 同时还能复用现有三 Sheet 导入主链的校验和结果能力

## 1.2 当前结论

- 单表是前端默认主入口。
- 三 Sheet 是四期过渡契约。
- 单表导入不单独设计第二套预校验。
- 单表先映射，再复用三 Sheet 预校验主链。
- `order_line` 不单独出物理 Sheet。
- `order_line` 中间对象在预校验前于内存中生成。

## 1.3 固定映射链

四期导入链固定收口为：

`single_import_row -> waybill -> customer_line -> order_line -> goods_line`

### 聚合规则

- 运单聚合：只按 `waybill_no`
- 门店节点聚合：
  - 优先 `customer_line_no`
  - 否则 `waybill_no + store_no`
  - 再否则 `waybill_no + customer_no`
- 订单聚合：
  - `单据号`
  - `订单号`
  - `销售订单号`
- 商品行：
  - 单表一行默认一条 `goods_line`

### 冲突规则

- 同运单共享字段冲突：直接失败
- 同门店节点共享字段冲突：直接失败
- 同一订单键下多商品：首轮直接失败

## 1.4 最小导入模板口径

首轮最小导入模板重点围绕：

- 运单锚点
- 门店节点锚点
- 订单锚点
- 商品原子字段
- 经纬度和停靠点顺序

首轮更重要的字段包括：

- `运单号/发车单号`
- `配送日期`
- `司机姓名`
- `仓库`
- `线路`
- `停靠点顺序`
- `门店名称`
- `联系人`
- `联系电话`
- `详细地址`
- `经度`
- `纬度`
- `单据号`
- `订单号`
- `销售订单号`
- `货号`
- `商品名称`
- `单据数量`

## 1.5 为什么四期不直接升级成四 Sheet

当前不直接升级四 Sheet 的原因是：

- 用户仍更适合维护一张并表
- 当前一订单多商品还不是稳定常态
- 三 Sheet 预校验链路还能复用
- `order_line` 还没有进入独立导入生命周期

### 后续升级阈值

只有当下面条件逐步成立，才值得正式从三 Sheet 升到四 Sheet：

- 一订单多商品成为常态
- 订单层字段显著扩张
- 用户开始按“订单头 + 商品行”维护
- 三 Sheet 错误定位明显变差
- `order_line` 进入独立生命周期

## 模块二：对象结构模块

## 2.1 模块目标

对象结构模块要解决的是：

- 哪一层才是真正的业务阅读层
- 哪一层是事实源
- 哪些字段该挂在哪一层

## 2.2 当前正式结构

系统内部正式结构收口为：

`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`

其中四期最关键的 4 层是：

- `waybill`
- `customer_line`
- `order_line`
- `goods_line`

## 2.3 各层职责

### `waybill`

角色：

- 执行总容器
- 运单共享字段承接层
- 汇总阅读与导航入口

### `customer_line`

角色：

- 门店交付节点
- 图片与门店现场事实首轮挂点
- 留痕与证据后续下沉的首轮锚点

### `order_line`

角色：

- 订单/单据层
- 首轮主阅读层
- 订单快照层
- 订单对应货物的主展示承接层

### `goods_line`

角色：

- 商品事实源
- 较稳定货物基础信息层
- 保留层/扩展层
- 为未来一订单多商品预留能力

## 2.4 当前关键业务判断

- `客户名称 = 门店名称`
- 一个门店节点下面可以有多个订单
- 一个订单下面通常只对应一个货物
- 因此当前最核心阅读链是：
  - `waybill -> customer_line -> order_line`
- 而事实源链保留为：
  - `order_line -> goods_line`

## 2.5 稳定键与主键判断

### `customer_line_no`

- 对系统内部：必选稳定键
- 对用户输入：首轮可不手填
- 生成优先级：
  - 用户传入的 `customer_line_no`
  - `waybill_no + store_no`
  - `waybill_no + customer_no`
  - 再否则失败

### 订单键优先级

- `单据号`
- `订单号`
- `销售订单号`

## 2.6 动态必填规则

对于这类字段：

- `spec`
- `barcode`
- `uom`
- `weight`
- `volume`
- `package_type`

四期首轮采用：

**主数据优先、快照兜底**

也就是：

- 命中完整货物基础信息时，订单快照里的重复字段允许为空
- 命不中，或命中但基础信息不完整时，这些字段必须显式提供

## 模块三：图片与证据模块

## 3.1 模块目标

图片模块要解决的不是“能不能传图片”，而是：

- 图片能不能按业务对象成组导入
- 能不能在门店节点稳定阅读
- 能不能按门店或运单打包导出

## 3.2 当前正式判断

- 图片链路独立于 XLSX 主数据链路
- 图片首轮只认 `customer_line`
- 图片物理结构为：
  - `运单图片包 -> 门店图片包 -> 图片文件`
- 业务最小挂点仍然是 `customer_line`

## 3.3 两层 manifest 结构

### 运单包 manifest

作用：

- 只描述这张运单包含哪些门店包
- 不直接承接图片明细

### 门店包 manifest

作用：

- 直接描述这个门店包里有哪些图片
- 以及每张图属于什么场景

### `scene_code`

首轮枚举固定为：

- `arrival`
- `sign`
- `exception`
- `other`

## 3.4 图片导入、展示、导出流程

### 导入

- 上传运单图片整合包
- 先解析运单包 manifest
- 再解析门店包 manifest
- 优先按 `customer_line_no` 命中
- 否则按 `waybill_no + store_no`
- 成功后挂到对应 `customer_line`

### 展示

- 运单页负责汇总
- 门店节点页负责真实阅读
- 首轮主阅读入口围绕 `customer_line`

### 导出

- 门店节点可导出门店包
- 运单可导出运单整合包
- 导出结构与导入结构保持对称

## 3.5 当前现状吸收判断

根据 2026-04-21 数据库与接口现状盘点，图片链路还要明确 4 个现状：

1. 当前上传链路已有基础，但更接近“单 evidence 单图片”。
2. 当前访问链路已有基础，但 `preview_url / full_url` 还未真正形成缩略图与原图双链路。
3. 当前后台和网站更多还是按单张图片地址阅读，不是业务化批量阅读。
4. 当前真正的业务化批量导出和 ZIP 打包能力基本缺失，四期必须补。

## 3.6 `manifest` 的边界

四期当前图片包里的 manifest 是**打包清单结构**，不是数据库里已经存在的正式业务对象。

根据现状盘点：

- 当前系统没有独立 `manifest` 业务主对象
- 如果未来要正式引入 `manifest_no / manifest_id`
- 需要单独建对象层，不能只在现有模型里零散塞字段

## 模块四：页面与阅读链模块

## 4.1 模块目标

页面模块要解决的是：

- 四期页面从哪里进入
- 最终读到哪一层
- 图片和导入结果如何与业务页衔接

## 4.2 四期页面主入口

首轮主要入口为：

- 导入中心
- 运单列表
- 运单详情

其中导入中心下新增两类入口：

- 单表快捷导入
- 图片批量导入

## 4.3 四期主阅读链

### 执行与业务阅读链

`waybill -> customer_line -> order_line`

### 事实源链

`order_line -> goods_line`

### 图片与证据阅读链

`waybill 汇总 -> customer_line -> 图片预览 / 留痕 / 证据`

## 4.4 关键页面角色

### 运单详情

- 执行总览页
- 门店节点和订单区的总入口
- 运单图片包导出入口

### 门店节点阅读区

- 四期首轮现场事实阅读中枢
- 地址、联系人、顺序、经纬度、图片、后续留痕在这里汇合

### 订单阅读区

- 四期首轮主阅读层
- 直接展示规格、条码、数量、体积、重量、备注等主信息

### 图片导入结果页

- 单次图片导入的回看页
- 结果按：
  - 运单包层
  - 门店包层
  - 单图层
 组织

## 模块五：后端与接口模块

## 5.1 模块目标

后端模块要解决的是：

- 哪些模型和表必须改
- 哪些接口必须先改
- 哪些接口可以后置

## 5.2 当前吸收后的后端结论

根据现状盘点和四期设计，当前 3 个判断已经比较明确：

1. `customer_line_id` 现有结构基本可承接。
2. `customer_line_no` 当前结构不够，必须补字段、唯一约束、索引和解析逻辑。
3. `manifest` 当前没有正式业务对象，未来若正式引入要单独建对象层。

## 5.3 首轮优先改造的后端链路

### 导入链路

当前必须优先改的一层仍然是：

- template
- precheck
- confirm
- result
- error-report

### 模型层

重点影响：

- `waybill`
- `customer_line`
- `order_line`
- `goods_line`
- `trace_event`
- `evidence`

### 结果与查询层

当前网站和后台部分详情页并不完全依赖独立 controller，而是直接通过 ORM/searchRead 取数。

因此如果要承接：

- `customer_line_no`
- `customer_line_id`
- 后续可能的 `manifest_no / manifest_id`

就必须同步考虑：

- 模型字段
- 视图字段
- 前端字段列表
- 检索 domain

## 5.4 当前可后置的接口

小程序相关现有接口首轮可以先不动。

只有当后续要按：

- `customer_line`
- 或未来 `manifest`

维度做读写时，再联动小程序接口。

## 模块六：实施与联调模块

## 6.1 实施阶段建议

### Phase 0 口径冻结

- 冻结单表主入口
- 冻结四层对象结构
- 冻结订单键优先级
- 冻结图片包结构

### Phase 1 导入与对象落位

- 完成单表映射层
- 接入三 Sheet 预校验复用
- 补 `customer_line_no`
- 补订单层承接

### Phase 2 图片链路补齐

- 运单包/门店包导入
- 图片结果页
- 门店图片预览
- 门店包/运单包导出

### Phase 3 页面与结果承接

- 运单页
- 门店节点阅读区
- 订单阅读区
- 导入结果页与图片结果页

### Phase 4 联调与验收

- 单表导入
- 图片导入
- 图片阅读
- 图片导出
- 三 Sheet 兼容回归

## 6.2 当前最大风险

当前最值得持续盯住的风险不是“字段不够”，而是这 5 类：

1. 只改模板，不改对象理解
2. 没有稳定 `customer_line_no`
3. 单表直接落库，不做聚合
4. 一订单多商品进入首轮主路径
5. 图片继续混进主 XLSX

## 6.3 当前联调重点

四期首轮联调要重点看 6 件事：

1. 单表导入链是否真正跑通
2. `waybill -> customer_line -> order_line` 阅读链是否真正跑通
3. 动态必填规则是否真的生效
4. 图片包导入与结果页是否跑通
5. 门店节点图片预览是否跑通
6. 运单包/门店包导出是否跑通
