# 数据库与接口现状盘点说明

日期：2026-04-21  
系统：Odoo 物流留痕系统  
主库：`odoo_logistics_prod`

## 一、盘点目标

本次盘点聚焦两个问题：

1. 当前数据库表、字段、索引、关联，是否足够承接 `customer_line_no` / `customer_line_id` / `manifest`
2. 当前系统现有的导入、查询、详情、导出接口，哪些需要调整

## 二、数据库现状结论

当前结论可以直接概括为：

- `customer_line_id`：现有结构基本可以承接
- `customer_line_no`：现有结构不够，需要补字段、约束、索引和解析逻辑
- `manifest`：现有结构基本不具备承接能力，需要新增业务主对象

## 三、现有核心表

当前主链路涉及的核心业务表包括：

- `logistics_dispatch_waybill`
- `logistics_dispatch_waybill_customer_line`
- `logistics_dispatch_waybill_customer_goods_line`
- `logistics_dispatch_waybill_stop`
- `logistics_trace_event`
- `logistics_trace_evidence`
- `logistics_import_batch`

当前数据库中这些表已经可以支撑：

- 运单主对象
- 客户行
- 客户货品行
- stop 明细
- 留痕事件
- 留痕证据
- 导入批次

## 四、关于 customer_line_id

### 1. 现状

系统当前已经存在 `customer_line_id` 这条链路：

- `logistics_dispatch_waybill_customer_goods_line.customer_line_id` 已存在
- 该字段关联到 `logistics_dispatch_waybill_customer_line.id`
- 当前数据库中已经建立了对应外键和索引

### 2. 结论

如果目标是“货品行稳定挂接到客户行主键”，当前数据库结构是够用的。

## 五、关于 customer_line_no

### 1. 现状

当前 `logistics_dispatch_waybill_customer_line` 模型里没有业务编号字段：

- 没有 `customer_line_no`
- 没有等价的业务唯一编号字段
- 没有基于业务编号的唯一约束

现阶段客户行更多是依赖：

- 系统内部 `id`
- `waybill_no + customer_no/customer_name`

### 2. 风险

当前货品行解析 `customer_line_id` 时，如果只按运单号和客户信息匹配，在“同一运单下同一客户对应多个门店行”的场景里，容易产生歧义。

### 3. 结论

如果后续要正式引入 `customer_line_no`，当前结构不够，需要至少补：

- `logistics_dispatch_waybill_customer_line.customer_line_no`
- 唯一约束，例如 `(waybill_id, customer_line_no)`
- 对应查询索引
- 导入解析和校验逻辑

## 六、关于 manifest

### 1. 现状

当前系统中没有独立的业务 `manifest` 对象：

- 没有 `logistics.dispatch.manifest` 之类的业务表
- 没有 `manifest_id`
- 没有 `manifest_no`
- 留痕、证据、运单、客户行、货品行中都没有 manifest 级字段

### 2. 结论

如果业务未来要承接 `manifest`，不是简单加一个字段就能完成，而是需要补一层新的业务主对象及其关联链路。

## 七、现有关联与索引是否足够

### 1. 目前够用的部分

当前这些关系已具备：

- `waybill -> customer_line -> customer_goods_line`
- `waybill -> stop`
- `waybill -> trace_event -> trace_evidence`

这些关系支撑现有系统主链路没有问题。

### 2. 当前不足的部分

当前还存在以下不足：

- `logistics_dispatch_waybill` 缺少更强的业务唯一口径约束
- `logistics_dispatch_waybill_customer_line` 缺少业务编号字段
- `logistics_dispatch_waybill_customer_line` 缺少面向业务查询的组合索引
- `logistics_trace_event` / `logistics_trace_evidence` 未下沉到 `customer_line` 级
- 整体没有 `manifest` 维度

### 3. 结论

当前数据库设计足够承接“运单主链 + 客户行主键挂接”，但不足以优雅承接“客户行业务编号”和“manifest 主对象”。

## 八、接口现状盘点

## 1. 导入接口

当前实际生效的导入链路为：

- `GET /api/admin/logistics/imports/waybill-standard/template`
- `GET /api/admin/logistics/imports/waybill-standard/template/download`
- `POST /api/admin/logistics/imports/waybill-standard/precheck`
- `POST /api/admin/logistics/imports/waybill-standard/confirm`
- `GET /api/admin/logistics/imports/waybill-standard/result`
- `GET /api/admin/logistics/imports/waybill-standard/error-report`

### 结论

如果要承接 `customer_line_no` / `manifest`，导入接口是必须改的一层。

至少要调整：

- 模板字段定义
- precheck 校验
- confirm 写入逻辑
- result 统计维度
- error-report 错误输出字段

## 2. 查询接口

当前小程序和留痕相关接口主要包括：

- `GET /api/mini/logistics/waybills/<no>/stops`
- `POST /api/mini/logistics/traces`
- `POST /api/mini/logistics/evidences`
- `POST /api/mini/logistics/evidences/<id>/images`
- `DELETE /api/mini/logistics/waybills/<no>/stops/<seq>/evidences`
- `GET /logistics_trace/evidence-images/<key>`

### 结论

如果只是后台导入层先支持 `customer_line_no` / `manifest`，这些小程序接口可以暂时不动。  
但如果以后希望小程序也能按客户行或 manifest 维度查/写，就必须同步改造。

## 3. 详情接口与页面数据读取

当前网站详情页并不完全依赖独立 HTTP 控制器，部分页面是通过 Odoo ORM `searchRead` 直接取模型数据。

### 结论

如果网站页面需要展示或检索：

- `customer_line_no`
- `customer_line_id`
- `manifest_no`
- `manifest_id`

则需要同步改：

- 模型字段
- 视图字段
- 前端字段列表
- 检索 domain

## 4. 导出接口

当前系统已有的“导出能力”主要是：

- 模板下载
- 导入错误报告下载

目前并没有单独的业务导出接口用于导出：

- customer line
- goods line
- manifest
- manifest 明细

### 结论

如果后续要做“按 `customer_line_no` 或 `manifest` 导出”，需要新增导出能力，而不是只改现有接口。

## 九、建议的最小改造方向

建议按以下顺序推进：

1. 先补 `customer_line_no`
2. 再补 `customer_line` 级唯一约束与索引
3. 同步修改导入模板、预检、确认逻辑
4. 再决定是否正式引入 `manifest`
5. 如果引入 `manifest`，单独建立业务主对象，而不是零散塞字段

## 十、最终结论

截至当前系统版本：

- `customer_line_id`：可以承接
- `customer_line_no`：不能完整承接，需补模型与导入链路
- `manifest`：不能承接，需新增对象层设计

接口层面：

- 必须优先改：导入链路
- 需要联动改：网站查询与详情页
- 条件再改：小程序接口
- 需要新增：业务导出接口

如果后续要进入实施阶段，建议先产出一份更细的改造清单，拆成：

- 必须新增的表/字段/索引
- 必须改造的接口
- 可以后置的接口
- 数据迁移与兼容方案

## 十一、图片链路现状盘点

### 1. 上传能力现状

当前图片上传链路已经存在，入口为：

- `POST /api/mini/logistics/evidences`
- `POST /api/mini/logistics/evidences/<id>/images`

当前实现能力包括：

- 先创建证据记录，再向该证据记录上传图片
- 支持的图片类型包括 `jpg`、`jpeg`、`png`、`webp`、`bmp`
- 上传后会在 `logistics.trace.evidence` 上写入：
  - `image_access_key`
  - `preview_url`
  - `full_url`
  - `source_filename`
  - `stored_file_name`
  - `file_ext`
  - `mime_type`
  - `file_size`
  - `storage_relative_path`
  - `uploaded_at`

### 2. 上传能力的主要缺口

当前上传链路的最大限制是：

- 一条 `logistics.trace.evidence` 记录只承接一组图片字段
- 也就是当前模型是“单证据单图片”结构，不是“单证据多图片”结构

这意味着：

- 如果一个留痕要挂多张图，目前通常只能新建多条 evidence
- 缺少真正的子表式图片对象
- 没有多图排序、主图标记、单张删除、单张补传等能力

另外还缺这些上传侧能力：

- 没有文件大小限制配置和超限提示
- 没有图片压缩、缩略图、转码
- 没有重复图片识别
- 没有批量上传能力
- 删除 evidence 时没有看到同步清理物理文件的逻辑

### 3. 访问能力现状

当前图片访问链路已经存在，入口为：

- `GET /logistics_trace/evidence-images/<image_access_key>`

当前访问能力包括：

- 可通过 `image_access_key` 读取物理文件
- 可返回正确的 `Content-Type` 和 `Content-Length`
- 小程序 stops 接口会把 `evidence_images` 数组一并返回
- 网站详情页会读取 `preview_url` / `full_url` 并尝试直接渲染图片

### 4. 访问能力的主要缺口

当前访问链路仍有这些明显不足：

- `preview_url` 和 `full_url` 实际上是同一个地址，没有真正区分缩略图和原图
- 没有独立缩略图生成机制
- 没有图片过期签名、临时授权、下载令牌这类更强控制
- 访问路由是 `auth="user"`，外部分享和匿名访问能力不足
- 没有按订单聚合图片展示的数据接口
- 当前后台原始模型页仍更多展示 URL/字段，不是专门的图库接口

### 5. 导出能力现状

当前图片相关“导出”能力非常弱。

现阶段已有的其实只是：

- 返回 `preview_url`
- 返回 `full_url`
- 后台可打开单张图片链接

### 6. 导出能力的主要缺口

目前缺少这些真正可用的图片导出能力：

- 没有按订单导出全部证据图片
- 没有按留痕事件导出图片
- 没有打包 ZIP 下载
- 没有导出图片清单 CSV/Excel
- 没有图片及元数据一并导出
- 没有批量下载按钮和后台导出任务

### 7. 图片链路最终结论

截至当前版本，图片链路的状态可以概括为：

- 上传：能用，但本质是单 evidence 单图片模型
- 访问：能看，但预览图和原图没有真正分层
- 导出：基本缺失，只能单张访问，不能业务化批量导出

如果后续要把图片链路做成更成熟的运营后台，建议优先补三件事：

1. 把图片从 evidence 主记录里拆成独立子表，形成真正多图结构
2. 补缩略图/原图双链路和按订单聚合展示
3. 补图片批量导出和压缩包下载能力
