1. 四期设计会打到哪些后端模型、表和索引
2. 单表导入在后端最小应该改哪一段链路

## Objective

在不推翻当前 Odoo 物流主线和现有三 Sheet 导入主链的前提下，评估四期设计对后端数据库、服务层、控制器和结果接口的真实影响面，为后续开发拆分与调研分工提供依据。

## Current Understanding

四期当前已经冻结的关键口径如下：

1. 前端主导入入口是单表快捷导入。
2. 三 Sheet 是四期过渡契约，用于复用原有预校验主链。
3. `order_line` 不单独出 Sheet，但要在预校验前于内存中生成。
4. 内部结构是：
   - `waybill`
   - `customer_line`
   - `order_line`
   - `goods_line`
5. `goods_line` 是事实源，`order_line` 是主阅读层和展示快照层。
6. 图片模块是独立链路，首轮业务最小挂点是 `customer_line`。
7. 留痕首轮开始下沉到 `customer_line`，但先做最小可用版。

同时结合 2026-04-21 数据库与接口现状盘点，可进一步收口 5 个现状结论：

1. `customer_line_id` 现有结构基本可承接，尤其 `goods_line.customer_line_id` 链路和索引基础已存在。
2. `customer_line_no` 当前结构不具备，需要补字段、唯一约束、索引和解析逻辑。
3. `manifest` 当前没有对应业务主对象，若未来正式引入，不能只在现有对象上零散加字段。
4. 当前后台详情页部分是通过 Odoo ORM `searchRead` 直接取模型数据，不完全依赖独立 HTTP controller。
5. 当前图片上传、访问、导出三侧能力不平衡：上传和单张访问已有基础，但批量导出与真正多图结构仍明显不足。

## 0. 现状盘点吸收结论

### 0.1 当前主表与主链基础

根据现状盘点，当前数据库中与四期直接相关的核心表包括：

- `logistics_dispatch_waybill`
- `logistics_dispatch_waybill_customer_line`
- `logistics_dispatch_waybill_customer_goods_line`
- `logistics_dispatch_waybill_stop`
- `logistics_trace_event`
- `logistics_trace_evidence`
- `logistics_import_batch`

这些表已经可以承接：

- 运单主对象
- 客户行/门店节点的基础承接
- 客户货品行
- stop 明细
- 留痕事件
- 留痕证据
- 导入批次

### 0.2 `customer_line_id` 现状

现状盘点确认：

- `logistics_dispatch_waybill_customer_goods_line.customer_line_id` 已存在
- 当前数据库中已有对应外键和索引

因此如果目标只是“货品行稳定挂接到客户行主键”，当前基础结构是够用的。

### 0.3 `customer_line_no` 现状

现状盘点确认：

- 当前 `logistics_dispatch_waybill_customer_line` 没有 `customer_line_no`
- 没有等价业务编号字段
- 没有基于业务编号的唯一约束

因此四期若正式引入 `customer_line_no`，至少要补：

- `customer_line_no` 字段
- `(waybill_id, customer_line_no)` 或等价唯一约束
- 查询索引
- 导入解析逻辑

### 0.4 `manifest` 现状

现状盘点确认：

- 当前没有独立 `manifest` 业务对象
- 没有 `manifest_id`
- 没有 `manifest_no`
- 运单、客户行、货品行、留痕、证据都没有 manifest 级字段

因此若未来要正式承接 `manifest`，需要补一层新的业务主对象，而不是零散塞字段。

## 1. 数据库模型影响面

## 1.1 `logistics.dispatch.waybill`

文件基线：

- `custom_addons/logistics_dispatch/models/logistics_dispatch_waybill.py`

主要影响：

- 继续承接运单共享字段
- 需要补更多导入来源字段和阅读字段
- 需要补门店节点、订单层、货物层的统计汇总字段

建议关注字段方向：

- `driver_name / driver_phone / vehicle_no / route / warehouse_code`
- 运单级备注
- 图片汇总数
- 门店节点数
- 订单数

## 1.2 `logistics.dispatch.waybill.customer.line`

文件基线：

- `custom_addons/logistics_dispatch/models/logistics_dispatch_waybill_customer_line_v2.py`

这是四期最重要的承接层。

主要影响：

- 从“客户明细行”升级为“门店交付节点”
- 增加 `customer_line_no`
- 增加 `stop_seq / longitude / latitude`
- 增加图片挂点与后续留痕挂点的承接能力

建议优先补的索引：

- `customer_line_no`
- `waybill_id`
- `store_no`
- `stop_seq`

## 1.3 `logistics.dispatch.waybill.order.line`

文件基线：

- `custom_addons/logistics_dispatch/models/logistics_dispatch_waybill_order_line.py`

这是四期首轮主阅读层对应的后端重点。

主要影响：

- 正式承接订单/单据层
- 增加订单键字段：
  - `source_doc_no`
  - `order_no`
  - `sale_order_no`
- 增加 `customer_line_id`
- 增加订单展示快照字段：
  - `special_requirement`
  - `order_remark`
  - `spec / barcode / uom / weight / volume / package_type` 展示快照

建议优先补的索引：

- `customer_line_id`
- `source_doc_no`
- `order_no`
- `sale_order_no`

## 1.4 `logistics.dispatch.waybill.customer.goods.line`

文件基线：

- `custom_addons/logistics_dispatch/models/logistics_dispatch_waybill_customer_goods_line_v2.py`

主要影响：

- 继续作为商品事实源
- 保留货物基础信息字段
- 与 `order_line` 建立稳定关联

建议关注：

- `goods_code`
- `goods_name`
- `spec`
- `barcode`
- `uom`
- `qty`
- `weight`
- `volume`
- `package_type`

建议优先补的索引：

- `goods_code`
- `customer_line_id`
- 稳定订单键关联字段

## 2. 留痕与图片模型影响面

## 2.1 `logistics.trace.event`

文件基线：

- `custom_addons/logistics_trace_core/models/logistics_trace_event.py`

四期最小改动方向：

- 增加 `customer_line_id`
- 保留 `waybill_id`
- 让门店现场留痕真正能挂到门店节点

建议优先补的索引：

- `waybill_id`
- `customer_line_id`
- `event_type`
- `event_time`

## 2.2 `logistics.trace.evidence`

文件基线：

- `custom_addons/logistics_trace_evidence/models/logistics_trace_evidence.py`

四期最小改动方向：

- `customer_line_id` 跟随 `trace_event.customer_line_id`
- 补图片元数据字段
- 补预览与原图访问字段

建议优先补的索引：

- `trace_event_id`
- `customer_line_id`
- `image_access_key`
- `scene_code`

补充吸收现状盘点结论：

- 当前 `logistics.trace.evidence` 更接近“单 evidence 单图片”结构，不是真正的多图子表结构
- 若四期首轮只做到运单包/门店包导入和业务化批量导出，可以先沿现有结构做最小承接
- 但若未来要支持：
  - 多图排序
  - 主图标记
  - 单张删除
  - 单张补传
  则更适合把图片从 evidence 主记录中进一步拆成独立子表

## 2.3 图片包元数据承接

四期应新增或明确一层图片导入元数据承接。

可选实现方向：

1. 继续扩展 `evidence` 模型承接图片元数据
2. 新增更轻量的图片导入批次/图片包记录模型

当前更推荐：

- 用图片导入批次记录承接包级结果
- 用 `evidence` 承接单图级挂点

这样结果页和业务对象阅读不会混淆。

同时结合现状盘点，四期应明确：

- 当前上传能力已有基础：
  - `POST /api/mini/logistics/evidences`
  - `POST /api/mini/logistics/evidences/<id>/images`
- 当前访问能力已有基础：
  - `GET /logistics_trace/evidence-images/<image_access_key>`
- 但当前导出能力基本仍停留在“单张访问链接”，缺少业务化 ZIP、清单导出和批量下载能力

## 3. 导入服务层影响面

## 3.1 当前基线

当前主要基线在：

- `custom_addons/logistics_web/services/waybill_standard_import_service_v2.py`

四期最关键的判断不是重写，而是：

- 在它前面增加一个“单表映射层”
- 把单表拆成内存中的：
  - `waybill_rows`
  - `customer_line_rows`
  - `order_line_rows`
  - `goods_line_rows`
- 再整理为三 Sheet 过渡契约格式复用原有预校验链

## 3.2 需要新增的服务层职责

建议新增一层服务职责：

- `single_sheet_mapping_service`

最小职责：

1. 读取单表
2. 生成内存态 `order_line`
3. 做聚合与冲突检测
4. 生成三 Sheet 过渡数据
5. 调用现有 `waybill_standard_import_service_v2`

## 3.3 为什么不直接改原预校验层

因为当前最稳的是：

- 单表先映射
- 预校验继续复用

否则会在单表和三 Sheet 上各长一套校验逻辑，后期成本更高。

## 4. 控制器与 API 影响面

## 4.1 当前基线

当前控制器基线主要在：

- `custom_addons/logistics_web/controllers/logistics_web_import_v2.py`
- `custom_addons/logistics_web/controllers/logistics_web_import_v3.py`

## 4.2 单表导入接口建议

建议在现有导入域下新增或扩展：

- 单表模板下载接口
- 单表预校验接口
- 单表正式导入接口

但要注意：

- 外部是单表接口
- 内部不要再开第二套独立结果模型

结合现状盘点，当前实际必须改动的导入接口层包括：

- `GET /api/admin/logistics/imports/waybill-standard/template`
- `GET /api/admin/logistics/imports/waybill-standard/template/download`
- `POST /api/admin/logistics/imports/waybill-standard/precheck`
- `POST /api/admin/logistics/imports/waybill-standard/confirm`
- `GET /api/admin/logistics/imports/waybill-standard/result`
- `GET /api/admin/logistics/imports/waybill-standard/error-report`

四期至少要在这些接口相关链路中补：

- `customer_line_no`
- 单表映射结果统计
- 订单层统计
- 更细的错误输出字段

## 4.3 图片接口建议

建议新增独立图片接口域：

- 上传运单图片整合包
- 获取图片导入结果
- 导出运单图片包
- 导出门店图片包
- 获取门店节点图片列表

建议路径方向继续保持：

- `/api/admin/logistics/...`

补充吸收现状盘点后的接口判断：

- 小程序现有 stops / trace / evidence 接口首轮可以暂时不动
- 但网站详情页和后台页面如果要展示或检索：
  - `customer_line_no`
  - `customer_line_id`
  - 未来 `manifest_no`
  - 未来 `manifest_id`
  则必须同步改：
  - 模型字段
  - 视图字段
  - 前端字段列表
  - 检索 domain

## 5. 查询与结果页接口影响面

## 5.1 单表导入结果页

当前结果页接口已存在运单导入基线。

四期最小扩展方向：

- 结果页统计补到：
  - `created_waybill_count`
  - `created_customer_line_count`
  - `created_order_line_count`
  - `created_goods_line_count`
- 错误反馈增加：
  - 运单聚合冲突
  - 门店节点冲突
  - 订单键缺失
  - 一订单多商品失败

## 5.2 图片结果页

需要新增图片导入结果接口。

建议结果结构至少分三层：

- 运单包层
- 门店包层
- 单图层

这样前端结果页才能稳定承接。

## 5.3 导出接口现状与新增方向

结合现状盘点，当前系统已有的“导出能力”主要仍是：

- 模板下载
- 导入错误报告下载
- 单张图片访问链接

因此四期若要支持下面这些业务导出，必须新增能力，而不是只扩现有接口：

- 按门店节点导出图片包
- 按运单导出图片整合包
- 后续按 `customer_line_no` 导出
- 后续若引入 `manifest`，按 `manifest` 导出

## 7. 适合并行调研的后端任务

下面这些任务适合并行分给同事做“现状盘点”，不直接碰最终拍板口径：

1. 现有模型字段盘点
2. 现有索引盘点
3. 现有导入控制器与 service 调用链盘点
4. 现有运单/门店/订单/货物详情接口返回字段盘点
5. 现有证据图片访问链路盘点

但下面这些仍建议统一拍板：

- 订单键优先级
- 三 Sheet 是否继续过渡
- `goods_line` 与 `order_line` 的事实源关系
- 图片首轮只认 `customer_line`

## 8. 当前调研结论

1. 四期后端改造不需要推翻当前 `waybill` 主线。
2. 真正的关键是：
   - `customer_line` 升级为门店节点
   - `order_line` 回归正式业务层
   - `goods_line` 保留为事实源
3. 单表导入最小可行后端路径是：
   - 新增映射层
   - 复用现有三 Sheet 预校验服务
4. 图片模块最小可行后端路径是：
   - 新增图片包结果承接
   - 单图仍落到证据/图片元数据层
   - 首轮可沿当前单图访问基础前进，但需要单独补业务化批量导出与结果结构
5. 首轮最值得优先做的不是大重构，而是：
   - 稳定键
   - 索引
   - 映射层
   - 结果接口
