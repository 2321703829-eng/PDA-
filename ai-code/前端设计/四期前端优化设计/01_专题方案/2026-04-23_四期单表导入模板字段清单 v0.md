# 2026-04-23 四期单表导入模板字段清单 v0

## 文档定位

- 本文只用于讨论和冻结“单表导入模板本身应该长什么样”。
- 本文不讨论预校验实现、导入报告实现、页面交互实现，只定义模板层最小基础。
- 本文以数据库基线 [四期数据库底表设计稿 v1（第二次修正版）](</d:/Desktop/Odoo/ai-code/前端设计/四期前端优化设计/02_跨模块规范/01_接口与数据/2026-04-21_四期数据库底表设计稿 v1（第二次修正版）.md:1>) 为准。

## Outcome

- 明确单表导入的推荐粒度。
- 明确哪些字段应该进入单表模板，哪些字段不应该进入模板。
- 明确每个模板字段归属到 `wave / batch / waybill / customer_line / order_line / goods_line` 哪一层。
- 为后续“模板结构评审”和“代码重构”提供统一底稿。

## Behavior

### 1. 单表粒度

- 单表导入固定采用：`一行 = 一条 goods_line`
- 同一张表内允许多行归并到同一个：
  - `wave`
  - `batch`
  - `waybill`
  - `customer_line`
  - `order_line`
- `goods_line` 作为最细事实层，不再拆第二张货物 Sheet。

### 2. 模板字段设计原则

- 模板字段不等于数据库字段逐列平铺。
- 模板优先承接“业务输入事实”，不承接数据库主键、related 字段、审计字段。
- 用户填写列头尽量使用业务语言；系统内部再映射到数据库字段。
- 能由系统稳定回填的字段，不要求业务重复填写。
- 布尔类配送要求、周维度配送周期允许在模板层铺开多列，在数据库层汇总为编码字段。

### 3. 本文中的字段状态定义

- `必填`：每行必须填写。
- `条件必填`：满足某条件时必须填写，或同组字段至少填一项。
- `选填`：允许为空。
- `不进模板`：由系统回填、系统生成，或不属于本模板首轮范围。

## Boundary

### 本轮纳入

- `dispatch_main` 主数据导入单表。
- `wave / batch / waybill / customer_line / order_line / goods_line` 六层输入字段。
- 配送可达性布尔组。
- 周维度配送周期布尔组。

### 本轮不纳入

- `import_source_file / import_task / import_task_line / import_error_line` 审计字段。
- 数据库 `id`、外键 `res_id`、related/store 字段。
- 图片包导入字段。
- 人工核验字段。
- 客户、门店、商品主档全量画像字段。

## 当前理解

- 当前代码里的单表模板只有约 `27` 个业务列，无法完整承接数据库基线中的 `order_line` 与大部分 `goods_line` 字段。
- 当前模板更像“运单 + 门店 + 简化货物”的压缩版，而不是正式的“单表主链导入模板”。
- 因此接下来应先冻结模板字段，再反推预校验、导入、结果页，而不是反过来做。

## 一、推荐模板总结构

建议把单表模板拆成 6 个逻辑区，但仍保留在一张 Sheet 中：

1. 导入控制与主链骨架
2. 运单执行信息
3. 门店节点信息
4. 门店配送要求扩展
5. 订单层信息
6. 货物层信息

## 三、明确不进入模板的字段

以下字段不建议出现在单表模板中：

### 3.1 系统主键与关系字段

- `wave_id`
- `batch_id`
- `waybill_id`
- `customer_line_id`
- `order_line_id`
- `partner_id`
- `product_tmpl_id`
- `product_unit_id`

原因：

- 这些字段是系统内部关系字段，不适合人工填写。
- 模板应提供的是业务键和业务快照，而不是数据库主键。

### 3.2 审计与导入日志字段

- `source_file_no`
- `task_no`
- `status`
- `success_count`
- `fail_count`
- `operator_id`
- `started_at`
- `finished_at`
- `error_code`
- `error_message`

原因：

- 这些字段属于导入过程产物，不属于导入源数据。

### 3.3 纯系统回填字段

- `warehouse_name_snapshot`
- `organization_name_snapshot`（若能由组织上下文稳定回填）
- `driver_employee_id`
- `vehicle_id`

原因：

- 模板应输入“识别信息”，系统再完成匹配、回填和落库。

## 四、v0 的必填策略建议

### 4.1 每行硬必填

- `warehouse_code`
- `delivery_date`
- `wave_no`
- `batch_no`
- `waybill_no`
- `customer_name`
- `product_name`
- `doc_qty`

### 4.2 条件必填

- `customer_line_no`
  - 若为空，则至少要有一组稳定识别门店节点的信息
  - v0 建议最少满足：`customer_name + address_full`
- 订单键组
  - `source_doc_no / order_no / sales_order_no`
  - 三者至少填一项
- `doc_unit_name`
  - 有 `doc_qty` 时建议一起填写
- `address_full`
  - 当 `province/city/district` 不能完整表达配送地址时必须填写

## 五、v0 需要继续确认的点

以下问题建议在下一轮业务评审中定死：

1. `wave_no` 是否要求业务手工提供，还是允许导入端按规则自动生成。
2. `customer_line_no` 是否必须由业务提供，还是允许导入时按 `waybill_no + sequence` 自动生成。
3. 司机、车辆字段首轮是否纳入主链导入，还是先完全降为后补字段。
4. 周维度配送周期是否跟本次主链导入一起走，还是拆到客户/门店画像导入。
5. 货物层金额字段是否全量纳入首轮模板，还是只保留数量、重量、体积，再把经营金额放二期。
6. `doc_qty`、`box_qty`、历史 `package_count` 三者最终保留哪套业务口径。

## 六、v0 结论

- 当前单表模板字段明显不足，不能继续作为正式模板基线。
- `v0` 推荐方向是：一行承接一条 `goods_line`，并显式补齐 `order_line`。
- 模板首轮应优先保证“主链事实完整”，而不是先追求实现细节或导入报告完整。
- 下一步最合适的是在此文基础上继续收一版：
  - `v1 必填字段版`
  - 只冻结首轮真正要上线的字段，不再讨论所有可选扩展列
