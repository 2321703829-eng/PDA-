## Objective

- 把正式模板从“结构方向”推进到“可制作模板文件”的级别。
- 避免后续实现时再反复争论每个 Sheet 的主键列和关联列。
- 为模板文件制作、预校验规则设计、正式导入实现提供一致基线。

## Benchmark

本次冻结统一以以下基线为准：

1. 数据库正式结构：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
2. 正式标准模板：四 Sheet
3. 快捷导入模板：单表
4. 历史兼容模板：旧三 Sheet
5. 正式模板优先服务稳定录入与稳定导入，不优先追求“单文件最少列数”

业务列头命名额外统一参考这两份现有 Excel：

1. [副本客户信息完整版0421.xlsx](</d:/Desktop/Odoo/ai-code/副本客户信息完整版0421.xlsx>)
2. [数据库底表，更新日期4.22.xlsx](</d:/Desktop/Odoo/ai-code/数据库底表，更新日期4.22.xlsx>)

列头冻结原则为：

- 业务现有 Excel 已有稳定列头时，优先沿用现有业务叫法。
- 数据库有字段、但业务 Excel 暂无稳定列头时，再使用系统化命名。
- 系统实现仍保留系统字段名，模板面对业务时优先展示业务列头。
- 正式模板数据字段只保留“现有业务表里有，且数据库底表里也有对应”的交集字段。
- 模板结构关系键例外保留：
  - `waybill_no`
  - `customer_line_no`
  - `order_line_no`

## OBB

### Outcome

- 正式模板固定为四个 Sheet：
  - `Waybill`
  - `CustomerLine`
  - `OrderLine`
  - `GoodsLine`
- 四个 Sheet 的主键列、关联列、必填列一次冻结。
- `OrderLine` 引入模板内关系键 `order_line_no`，用于降低 `GoodsLine` 的重复填报成本。

### Behavior

- `Waybill` 承接 `wave + batch + waybill` 共享字段。
- `CustomerLine` 承接门店节点快照，以及客户/门店画像层的可同步输入字段。
- `OrderLine` 承接订单/单据层，并通过 `order_line_no` 供 `GoodsLine` 关联。
- `GoodsLine` 承接最细货物事实层，不再重复整套上层字段。

### Boundary

- 本文冻结的是正式模板结构，不直接等于数据库字段清单。
- 本文允许使用“模板内关系键”，只要最终可稳定映射回数据库结构。
- 本文不涉及代码实现。

## 一、总结构冻结

### 1.1 Sheet 名称冻结

| Sheet 英文名 | Sheet 中文建议名 | 行粒度 |
| --- | --- | --- |
| `Waybill` | 运单 | 一行一条运单 |
| `CustomerLine` | 门店节点 | 一行一条门店节点 |
| `OrderLine` | 订单 | 一行一条订单/单据快照 |
| `GoodsLine` | 货物明细 | 一行一条货物明细 |

### 1.2 主键与关联列总表

| Sheet | 模板主键列 | 父级关联列 | 说明 |
| --- | --- | --- | --- |
| `Waybill` | `waybill_no` | 无 | 顶层业务键 |
| `CustomerLine` | `waybill_no + customer_line_no` | `waybill_no` | `customer_line_no` 只要求在同一运单内唯一 |
| `OrderLine` | `order_line_no` | `waybill_no + customer_line_no` | `order_line_no` 为模板内关系键，要求同一文件内唯一 |
| `GoodsLine` | 无独立业务主键要求 | `order_line_no` | 一条货物行直接归属一个订单行 |

| Sheet | 硬必填列 |
| --- | --- |
| `Waybill` | `warehouse_code`、`delivery_date`、`wave_no`、`batch_no`、`waybill_no` |
| `CustomerLine` | `waybill_no`、`customer_line_no`、`customer_name`、`address_full` |
| `OrderLine` | `order_line_no`、`waybill_no`、`customer_line_no`，以及订单键组二选一 |

- `source_doc_no`
- `sales_order_no`

## 二、关键设计决定

### 2.1 为什么 `OrderLine` 要引入 `order_line_no`

如果 `GoodsLine` 继续通过：

- `waybill_no`
- `customer_line_no`
- `source_doc_no / sales_order_no`

来关联 `OrderLine`，会有两个问题：

- `GoodsLine` 需要重复填写整套上层订单键
- 当订单键组存在多种来源口径时，模板和预校验都会变得更重

因此 v1 冻结为：

- `OrderLine` 必填 `order_line_no`
- `GoodsLine` 通过 `order_line_no` 关联 `OrderLine`

这里的 `order_line_no` 是：

- 模板内关系键
- 文件内唯一键
- 不是数据库正式字段

正式落库时仍需把：

- `source_doc_no`
- `sales_order_no`

等业务字段写入 `logistics.dispatch.waybill.order.line`

### 2.2 为什么 `CustomerLine` 不再允许缺少 `customer_line_no`

单表快捷模板阶段，可以讨论“如果没填，系统自动生成”。

但正式四 Sheet 模板中，`CustomerLine` 已经是独立对象层，因此 v1 冻结为：

- `customer_line_no` 必填

原因：

- 它本来就是正式业务稳定键之一
- 它承担 `OrderLine` 的父级关联职责
- 它还能支撑图片、核验、导出、对账等后续场景

### 2.3 为什么 `GoodsLine` 不再重复填 `waybill_no + customer_line_no`

正式模板设计优先追求：

- 结构稳定
- 填写负担可控
- 错误定位清晰

因此 `GoodsLine` 只要求：

- `order_line_no`

作为父级关联列，不再强制重复：

- `waybill_no`
- `customer_line_no`
- 订单键组

除非后续评审确认要保留这些冗余列做人工比对，否则 v1 不纳入硬必填。

## 四、四 Sheet 之间的导入顺序冻结

正式模板读取顺序固定为：

1. `Waybill`
2. `CustomerLine`
3. `OrderLine`
4. `GoodsLine`

对应导入依赖固定为：

1. 先创建或命中 `waybill`
2. 再创建 `customer_line`
3. 再创建 `order_line`
4. 最后创建 `goods_line`

## 五、跨 Sheet 校验冻结

### 5.1 `Waybill`

- `waybill_no` 文件内唯一
- 同一行的 `wave_no / batch_no / warehouse_code / delivery_date` 不得缺失

### 5.2 `CustomerLine`

- 每一行都必须命中存在的 `waybill_no`
- 同一 `waybill_no` 下，`customer_line_no` 不得重复

### 5.3 `OrderLine`

- 每一行都必须命中存在的 `waybill_no + customer_line_no`
- `order_line_no` 文件内唯一
- `source_doc_no / sales_order_no` 至少一项非空

### 5.4 `GoodsLine`

- 每一行都必须命中存在的 `order_line_no`
- 同一 `order_line_no` 下允许多条 `GoodsLine`
- `product_name`、`doc_qty` 不得为空

## 六、v1 结论

- 正式四 Sheet 模板已经从“结构方向”推进到“可制作模板文件”的冻结级别。
- 本轮最关键的冻结点是：
  - `CustomerLine.customer_line_no` 改为正式模板必填
  - `OrderLine.order_line_no` 作为模板内关系键正式引入
  - `GoodsLine` 通过 `order_line_no` 关联，不再重复整套上层字段
- 这一版冻结后，后续模板文件、预校验、正式导入都应以本文为准。
