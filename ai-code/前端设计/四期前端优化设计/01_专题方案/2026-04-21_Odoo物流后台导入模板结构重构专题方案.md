## Objective

四期导入模板结构重构要解决的不是“再多加一些字段”，而是下面 8 个结构性问题：

1. 当前三 Sheet 模板字段量已经不足以承接新增业务字段。
2. 当前 `客户明细` 仍偏“客户信息行”，尚未稳定成为运单下的门店交付节点。
3. 当前订单层没有作为正式主结构稳定承接。
4. 当前大量新增字段如果继续堆到 `运单` 头层，会破坏对象边界。
5. 当前用户侧导入仍要求理解三张表关系，填写门槛偏高。
6. 当前图片没有稳定的批量导入、预览、批量导出链路。
7. 当前最小导入模板还没有按“门店节点 + 订单 + 商品”的新结构收口。
8. 当前单表导入到预校验之间的映射链路还没有写死。

因此，本文档的目标收口为：

- 保留系统内部标准对象结构，不改回单表大模型。
- 对用户提供一张并表大模板的快捷导入入口。
- 通过映射脚本把大表拆回 `waybill / customer_line / order_line / goods_line`。
- 把 `客户明细` 提升为运单下的门店交付节点层。
- 把 `order_line` 与 `goods_line` 分层收回到正确位置。
- 把图片设计为独立附件包，不混入主数据 XLSX。
- 为后续门店级留痕和证据挂点提供稳定对象基础。
- 冻结“先映射到现有三表结构，再复用原有预校验”的实现口径。

## Benchmark

本文档统一参考下面 8 条基准：

1. 当前业务主线  
`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`

2. 当前追溯主线  
`waybill -> trace -> evidence -> exception`

3. 当前图片承接判断  
图片应独立于主数据 XLSX，按附件包方式导入和导出

4. 当前业务判断  
- `客户名称 = 门店名称`
- `单据对应订单层级`
- `一个门店可以对应多个订单`
- `一个订单通常只对应一个货物`

5. 当前对象判断  
- `waybill` 是总容器与执行主对象  
- `customer_line` 应升级为运单下的门店交付节点  
- `order_line` 应成为订单/单据层，也是首轮主阅读层  
- `goods_line` 是商品事实源，作为保留层/扩展层

6. 当前导入体验判断  
- 用户侧适合填写一张并表大模板  
- 系统内部仍保持标准对象结构  
- 映射脚本负责把大表拆解成标准结构

7. 当前预校验判断  
- `order_line` 不单独出 Sheet  
- 单表导入不单独设计一套预校验  
- 先映射成现有三表数据结构，再复用原有预校验模块  
- `order_line` 中间对象在预校验前生成

8. 当前司机执行模板判断  
- 行粒度更接近“运单下的门店停靠点”  
- 导出时可以带订单汇总和货物汇总  
- 导入时仍应保留订单层与商品层的原子字段

9. 当前入口判断  
- 单表是前端导入主入口  
- 三 Sheet 是四期过渡契约  
- 三 Sheet 可在前端隐藏，仅作为内部标准和预校验复用结构

## OBB

### Outcome

- 系统内部标准结构被明确为 `waybill -> customer_line -> order_line -> goods_line`。
- 用户可直接使用一张并表大模板进行快捷导入。
- 导入完成后，系统内部能稳定形成四层对象链。
- `customer_line` 成为后续门店级留痕、证据的自然挂点。
- 图片不混进主模板，而是通过独立附件包进入系统。
- 最小导入模板字段口径已经可直接用于后续实现拆解。

### Behavior

- 运单级共享字段进入 `waybill`
- 门店级共享字段进入 `customer_line`
- 订单/单据字段与订单快照字段进入 `order_line`
- 商品基础信息与商品原子字段进入 `goods_line`
- 单表快捷导入时，一行大表经映射后拆成四层标准结构
- 图片按独立包导入，并能预览与批量导出
- 对重复商品字段采用“主数据优先、快照兜底”的动态必填规则

### Boundary

- 本方案不把外部第四表原样保留为唯一正式模板。
- 本方案不改变 `wave / batch / waybill` 主执行对象结构。
- 本方案允许用户主入口为单表，但不允许内部对象因此扁平化。
- 本方案允许后续继续扩字段，但不再允许字段层级继续模糊。

## Current Understanding

### 1. 当前模板已经进入“结构不够用”阶段

现有标准模板：

- `运单`
- `客户明细`
- `货物明细`

在二期阶段足够承接基础导入，但已经难以稳定承接：

- 单据号、源单号、第三方单号
- 商品条码、品牌、类别、标签
- 数量、箱数、重量、体积多口径
- 金额、税额、成本、毛利等经营快照字段
- 联系人、电话、地址、业务员、渠道等门店交付字段

### 2. 当前对象边界需要重新定型

四期需要把当前结构正式收口成：

`waybill -> customer_line -> order_line -> goods_line`

这个升级的意义是：

- 导入后，门店节点稳定存在
- 门店节点自动挂在运单下面
- 订单稳定挂在门店节点下面
- 商品行稳定挂在订单下面
- 现场留痕和证据也可以继续挂在门店节点上

### 3. 当前图片链路不能继续混在主模板里

如果四期要支持图片批量导入、预览和批量导出，就不适合继续把图片字段硬塞进主 XLSX。

更合理的判断是：

- 主数据继续走标准三 Sheet 或单表快捷导入
- 图片走独立附件包
- 两条链路在导入结果阅读中汇合

### 4. 当前用户更适合单表输入，但系统仍必须分层存储

业务用户更容易维护一张并表，而不是三张关联表。  
但系统内部仍然必须保留：

`waybill -> customer_line -> order_line -> goods_line`

因此需要新增：

`单表快捷导入 -> 映射脚本 -> 标准对象结构`

进一步收口为：

- 单表是前端导入主入口
- 三 Sheet 是四期过渡契约
- 三 Sheet 可在前端隐藏
- 三 Sheet 主要服务于内部标准结构和预校验复用

### 5. 当前几项关键规则已经可以先冻结

- `customer_line_no` 对系统内部是必选稳定键，但首轮可以自动生成，不要求用户手填
- 运单聚合首轮只按 `waybill_no`
- 门店节点聚合首轮优先 `customer_line_no`，否则 `waybill_no + store_no`，再否则 `waybill_no + customer_no`
- 订单聚合首轮优先 `单据号`，否则 `订单号`，再否则 `销售订单号`
- 共享字段冲突一律报错，不自动覆盖
- 留痕首轮即下沉到 `customer_line`，但先做最小可用版
- 图片附件包首轮 manifest 只保留最小字段集
- 经纬度首轮硬必填
- 单表导入先映射到现有三表数据结构，再复用原有预校验模块
- `order_line` 中间对象在预校验前生成
- 首轮若同一订单键下出现多商品，直接报错
- 图片首轮只认门店节点 `customer_line`
- 规格、条码、单位、重量、体积等字段采用“主数据优先、快照兜底”的动态必填规则

## Core Design Decision

### 1. 继续保留内部标准对象结构，不回退成扁平大模型

系统内部标准结构继续保持：

1. `waybill`
2. `customer_line`
3. `order_line`
4. `goods_line`

原因：

- 这样才符合当前业务真实层级
- 便于分层校验
- 便于门店节点挂在运单下面
- 便于订单与商品正确分层
- 便于门店级挂点下沉
- 便于列表、详情、查询、导出的稳定承接

### 2. 对用户新增单表快捷导入入口

用户侧可新增一张并表大模板，包含：

- 运单级字段
- 门店级字段
- 订单/单据级字段
- 货物/商品级字段

它的目标是：

- 降低业务填写门槛
- 不要求用户理解多层对象关系
- 不改变系统内部对象结构

这里进一步冻结为：

- 单表作为前端导入主入口
- 三 Sheet 作为四期过渡契约保留
- 前端可隐藏三 Sheet，不要求业务直接接触

### 3. 单表导入通过映射脚本拆回内部标准结构

推荐流程：

`single_import_row -> mapping_script -> waybill_rows / customer_line_rows / order_line_rows / goods_line_rows`

实现上优先建议：

- 读取大表
- 按规则聚合
- 直接在内存中组装对象结构
- 先映射成现有三表数据结构
- 再复用标准导入链路的预校验和落库逻辑

这里进一步冻结为：

- `order_line` 不单独出 Sheet
- `order_line` 中间对象在预校验前生成
- 但用户模板和预校验入口仍维持现有三表物理结构

### 4. 把 `客户明细` 正式升级为运单下的门店交付节点层

`客户明细` 不再只是“客户信息补充表”，而是：

**门店交付节点表**

它承接：

- 门店识别
- 联系方式
- 地址
- 签收要求
- 后续留痕、证据挂点

### 5. 把 `order_line` 收回订单/单据层

因为当前业务已经确认：

- 单据对应订单层级
- 一个门店可以对应多个订单

因此下列字段应优先落在 `order_line`：

- 单据号
- 订单号
- 销售订单号
- 单据日期
- 单据来源
- 单据状态
- 审核状态
- 支付状态
- 结算状态
- 业务类型
- 主表备注
- 制单人
- 创建日期
- 审核人
- 审核日期

`order_line` 同时承接这单对应货物的展示快照，例如：

- 特殊要求
- 订单备注
- 展示用规格
- 展示用体积/重量

### 6. 把 `goods_line` 收回商品事实源层

更适合留在 `goods_line` 的是：

- 货号
- 商品名称
- 规格
- 条码
- 单位
- 数量
- 单价
- 金额
- 重量
- 体积
- 明细备注

这里进一步收口为：

- `goods_line` 存较稳定的货物基础信息
- `order_line` 存这次订单的快照层信息
- 两层允许存在展示字段重叠，但真相优先级是：
  - `goods_line` 为事实源
  - `order_line` 为展示快照

但在首轮 1:1 落地前提下，`goods_line` 的角色应收口为：

- 保留层/扩展层
- 不作为首轮主阅读层
- 为未来“一单多货”场景保留商品原子扩展能力

### 6.1 首轮由 `order_line` 承接货物主展示字段

虽然 `goods_line` 继续保留，但首轮页面、结果阅读和司机执行视角中，订单对应货物的核心展示信息直接由 `order_line` 承接，至少包括：

- `goods_code`
- `goods_name`
- `spec`
- `barcode`
- `uom`
- `qty`
- `weight`
- `volume`
- `goods_remark`
- `package_type`（如业务需要）

也就是说，首轮主阅读链收口为：

`waybill -> customer_line -> order_line`

而不是让用户先进入 `goods_line` 才能读到规格、备注、体积等信息。

### 6.2 动态必填规则

对于规格、条码、单位、重量、体积、包装类型这类既可能来自货物基础信息、也可能来自订单快照的字段，四期首轮采用：

**主数据优先、快照兜底**

具体判断是：

- 如果通过稳定 `goods_code` 能命中完整货物基础信息，这些订单快照字段允许为空
- 如果命不中，或者命中但基础信息不完整，这些字段在导入数据中必须显式提供

首轮优先适用这条规则的字段包括：

- `spec`
- `barcode`
- `uom`
- `weight`
- `volume`
- `package_type`

### 7. 引入稳定的门店节点编号

建议新增正式节点键：

- `customer_line_no`

它的作用是：

- 唯一标识一条运单下的门店交付节点
- 作为 `order_line` 和后续留痕挂点的对象基础
- 避免长期依赖 `waybill_no + customer_no + store_no` 的弱组合键

这里进一步冻结为：

- 对系统内部：`customer_line_no` 是必选主键
- 对用户输入：首轮可以非必填
- 导入时优先取用户提供值
- 未提供时按 `waybill_no + store_no` 自动生成
- 若无 `store_no`，退化到 `waybill_no + customer_no`
- 若仍无法生成，则直接报错

### 8. 图片链路独立于主模板

四期图片能力收口为：

- 支持批量导入
- 支持预览
- 支持批量导出

推荐形式：

- `ZIP + manifest`
- 其中运单包包含多个门店包

不推荐把图片混进主三 Sheet XLSX 或单表快捷导入模板。

首轮两层 manifest 结构冻结为：

- 运单包 manifest  
  只描述“这张运单包含哪些门店包”，不直接承接图片明细  
  建议字段：
  - `manifest_version`
  - `package_type=waybill_package`
  - `waybill_no`
  - `delivery_date`
  - `driver_name`
  - `route`
  - `store_package_count`
  - `store_packages[]`
    - `store_no`
    - `store_name`
    - `customer_line_no`
    - `stop_seq`
    - `package_path`
    - `image_count`
- 门店包 manifest  
  直接描述门店图片明细  
  建议字段：
  - `manifest_version`
  - `package_type=store_package`
  - `waybill_no`
  - `customer_line_no`
  - `store_no`
  - `store_name`
  - `stop_seq`
  - `contact_name`
  - `contact_phone`
  - `address`
  - `longitude`
  - `latitude`
  - `image_count`
  - `images[]`
    - `file_name`
    - `scene_code`
    - `image_seq`
    - `taken_at`（可选）
    - `remark`（可选）
    - `source_doc_no`（可选）

`scene_code` 首轮枚举冻结为：

- `arrival`
- `sign`
- `exception`
- `other`

图片挂点边界进一步冻结为：

- 图片首轮只认门店节点 `customer_line`
- 后续再评估是否延伸到订单层

## Template Structure Redesign

## 1. 标准导入层

### 1.0 三 Sheet 的四期定位

- 三 Sheet 是四期过渡契约
- 三 Sheet 主要用于内部标准结构和复用现有预校验
- 三 Sheet 可在前端隐藏，不作为业务主入口

### 1.1 `运单` Sheet

定位：只承接整张运单共享的执行公共头信息。

建议字段范围：

- `waybill_no`
- `batch_no`
- `wave_no`
- `delivery_date`
- `warehouse_code`
- `vehicle_no`
- `driver_name`
- `driver_phone`
- `route`
- `remark`

### 1.2 `客户明细` Sheet

定位：正式升级为运单下的门店交付节点表。

建议字段范围：

- `customer_line_no`
- `waybill_no`
- `store_no`
- `store_name`
- `contact_name`
- `contact_phone`
- `address`
- `delivery_remark`
- `signoff_requirement`
- `stop_seq`
- `longitude`
- `latitude`

### 1.3 `货物明细` Sheet

定位：当前存量模板保持使用，但四期设计上要明确它不再独占承接所有单据字段。

建议在四期过渡期内保留：

- `waybill_no`
- `store_no`
- `goods_code`
- `goods_name`
- `spec`
- `qty`
- `uom`
- `weight`
- `volume`
- `remark`

说明：

- 四期实现时应补订单层承接，不再把所有单据字段继续塞进 `货物明细`
- 如需兼容现有模板，可在映射脚本中先拆到 `order_line + goods_line`
- 首轮即使继续保留 `货物明细` Sheet，也不代表 `goods_line` 仍然是主阅读层

## 2. 用户侧单表快捷导入模板

### 2.1 定位

面向业务用户的一张并表大模板。

### 2.2 字段分组方向

- 运单级字段组
- 门店级字段组
- 订单/单据级字段组
- 商品级字段组

### 2.3 基本判断

- 单表一行默认代表一条 `goods_line`
- 同运单共享字段用于聚合 `waybill`
- 同门店共享字段用于聚合 `customer_line`
- 同订单共享字段用于聚合 `order_line`

### 2.4 核心边界

- 单表只是用户输入入口简化
- 单表不是内部标准结构
- 单表不替代分层对象模型

## 3. 图片附件包

### 3.1 定位

独立于主数据模板的证据图片批量进出载体。

### 3.2 建议组成

- 一个运单图片整合包
- 多个门店图片整合包
- 运单包 manifest
- 门店包 manifest
- 图片文件

### 3.3 两层 manifest 方向

#### 3.3.1 运单包 manifest

运单包 manifest 只负责描述：

- 这是哪张运单的图片总包
- 里面包含哪些门店子包

建议字段：

- `manifest_version`
- `package_type=waybill_package`
- `waybill_no`
- `delivery_date`
- `driver_name`
- `route`
- `store_package_count`
- `store_packages[]`
  - `store_no`
  - `store_name`
  - `customer_line_no`
  - `stop_seq`
  - `package_path`
  - `image_count`

#### 3.3.2 门店包 manifest

门店包 manifest 直接负责描述：

- 这个门店包属于哪张运单、哪个门店节点
- 这个门店包里有哪些图片
- 每张图属于哪个场景

建议字段：

- `manifest_version`
- `package_type=store_package`
- `waybill_no`
- `customer_line_no`
- `store_no`
- `store_name`
- `stop_seq`
- `contact_name`
- `contact_phone`
- `address`
- `longitude`
- `latitude`
- `image_count`
- `images[]`
  - `file_name`
  - `scene_code`
  - `image_seq`
  - `taken_at`（可选）
  - `remark`（可选）
  - `source_doc_no`（可选）

### 3.4 口径说明

- 图片包不替代主数据导入。
- 图片包只承接证据图片批量导入、预览和批量导出链路。
- 图片挂点优先围绕 `customer_line` 和后续 `trace_event`。
- 但在四期首轮，图片仍只认 `customer_line`
- 运单图片整合包的元素是多个门店图片整合包
- 业务最小挂点仍然是 `customer_line`，不是运单包本身
- 首轮 manifest 匹配优先级按：
  - `customer_line_no`
  - 否则 `waybill_no + store_no`
- 经纬度作为首轮硬必填字段，与门店证据上下文一并校验

### 3.5 图片导入流程

#### 3.5.1 用户上传单位

- 用户上传一个运单图片整合包。
- 一个运单包内包含多个门店图片整合包。
- 业务上不鼓励首轮直接上传散图。

#### 3.5.2 系统解析顺序

- 第一步：读取运单包 manifest
  - 确认 `waybill_no`
  - 确认包含哪些门店子包
- 第二步：逐个读取门店包 manifest
  - 确认 `customer_line_no / store_no / stop_seq / longitude / latitude`
  - 确认每张图片的 `file_name / scene_code / image_seq`
- 第三步：逐个门店包匹配业务节点
  - 优先 `customer_line_no`
  - 否则 `waybill_no + store_no`
- 第四步：图片文件入图片服务，图片元数据入业务关系

#### 3.5.3 导入结果反馈

导入结果需要支持三层反馈：

- 运单包层：这张运单包是否成功
- 门店包层：哪些门店包成功，哪些失败
- 单图层：哪些图片成功，哪些图片失败以及失败原因

### 3.6 图片展示流程

- 首轮主阅读入口围绕 `customer_line` 展开。
- 运单页负责汇总展示该运单下的门店图片情况。
- 门店节点页负责真实图片阅读与预览。
- 首轮页面读取的不是原始压缩包，而是解析后的图片元数据与访问地址。
- 门店页至少可读：
  - 场景分类
  - 图片顺序
  - 预览图
  - 原图访问
  - 拍摄时间与备注（如有）

### 3.7 图片导出流程

- 门店节点可导出单个门店图片包。
- 运单可导出一个运单图片整合包。
- 运单导出时系统应重新组装：
  - 运单包 manifest
  - 多个门店包 manifest
  - 对应图片文件
- 导出包结构与导入结构保持对称，便于业务归档、复核和二次流转。

## Mapping Rules Direction

## 1. 主映射链

正式映射链收口为：

`single_import_row -> waybill -> customer_line -> order_line -> goods_line`

## 2. 运单聚合规则

优先使用：

- `waybill_no`

四期首轮默认不鼓励靠多字段猜运单，且无 `waybill_no` 时不进入正式导入主路径。

## 3. 门店节点聚合规则

优先使用：

- `customer_line_no`

首轮规则进一步冻结为：

- 优先使用 `customer_line_no`
- 没有 `customer_line_no` 时，用 `waybill_no + store_no`
- 没有 `store_no` 时，用 `waybill_no + customer_no`
- 再往下不猜，直接报错

## 4. 订单聚合规则

优先使用：

- `单据号`

否则使用：

- `订单号`

再否则使用：

- `销售订单号`

再往下不猜，直接报错。

首轮若同一订单键下出现多商品：

- 直接报错
- 不自动合并
- 不自动拆单

## 5. 货物明细落行规则

- 大表每一行默认落一条 `goods_line`
- 单据字段先归到 `order_line`
- 商品字段、数量字段、重量体积字段随行落入 `goods_line`

## 6. 冲突规则

如果同一 `waybill_no` 下这些共享字段不一致，应报错而不是自动合并：

- 仓库
- 司机
- 线路
- 配送日期

如果同一 `customer_line_no` 下这些共享字段不一致，也应报错：

- 联系人
- 电话
- 地址
- 门店名称

如果同一订单聚合键下这些共享字段不一致，也应报错：

- 单据日期
- 单据来源
- 审核状态
- 支付状态
- 结算状态

首轮统一原则冻结为：

- 共享字段冲突一律报错
- 不做自动覆盖
- 不做“取最后一条”处理

## 7. 内存映射优先

推荐实现方向：

- 读取大表
- 聚合成四层内存结构
- 先映射成现有三表数据结构
- 再复用标准导入链路的核心校验和落库逻辑

不要求先在磁盘上生成中间 Sheet 文件。

## Association Rules

## 1. 标准结构关联链

正式关联链收口为：

`waybill -> customer_line -> order_line -> goods_line`

## 2. 关键关联规则

### 2.1 门店节点关联运单

- `customer_line.waybill_no` 必须命中 `waybill.waybill_no`

### 2.2 订单关联门店节点

- `order_line.customer_line_no` 必须命中 `customer_line.customer_line_no`

### 2.3 货物关联订单

- `goods_line` 必须先命中稳定订单键

### 2.4 节点唯一性

- 同一导入批次内，`customer_line_no` 必须唯一
- `customer_line_no` 应至少满足“运单内唯一”，也允许系统设计为全局唯一

### 2.5 导入后的首要关系验收

- 一张运单下面应能自动看到多个门店节点
- 每个门店节点下面应能看到多个订单
- 每个订单下面应能看到自己对应的货物

也就是导入后的首要验收结构是：

`waybill -> customer_line -> order_line -> goods_line`

## 四 Sheet 升级阈值

本专题方案当前仍以：

- 物理模板三 Sheet
- 内部对象四层
- 单表映射补 `order_line`

作为首轮方案。

后续只有在下面这些条件逐步成立时，才建议把物理模板正式升级成四 Sheet：

1. 一单多货成为常态。
2. 订单层字段显著增多，且不再适合继续通过映射层从单行重复值中推导。
3. 业务用户已经稳定按“订单头 + 多商品行”维护数据。
4. 三 Sheet 下订单层预校验、报错定位和返修体验明显变差。
5. `order_line` 进入独立生命周期，需要独立导入、独立更新或独立校验。

演进边界判断收口为：

**只有当订单层已经不能被“三 Sheet + 映射层”稳定承接时，才值得把物理模板升级成四 Sheet。**

## Risks

### 1. 不先冻结订单层的风险

如果继续把订单字段和商品字段混在同一层，后续查询、导出和留痕挂点都会越来越难收口。

### 2. 不新增稳定节点键的风险

如果继续只靠 `waybill_no + customer_no + store_no` 猜挂接，后续门店节点、留痕和证据都会越来越难稳定。

### 3. 只改模板不改对象理解的风险

如果模板变了，但 `customer_line` 和 `order_line` 仍未被正式定型，后续页面、查询和追溯仍会反复返工。

### 4. 单表无聚合规则直接落库的风险

如果并表直接导入而没有先做运单/门店节点/订单聚合，内部结构会被错误扁平化。

### 5. 图片继续混进主模板的风险

如果图片继续混在主 XLSX 或并表模板中，后续批量导入、预览和批量导出都会越来越重。
