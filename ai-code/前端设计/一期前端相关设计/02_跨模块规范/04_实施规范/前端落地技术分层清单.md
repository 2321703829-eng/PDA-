# 前端落地技术分层清单

适用范围：
- `ai-code/前端相关设计/` 目录下的后台页面与草图
- Odoo 19 后台中的列表、详情、时间线、证据、看板相关实现

关联文档：
- `后台页面改造清单.md`
- `后台接口_查询消费清单.md`
- `运单追溯列表页草图.md`
- `运单详情页草图.md`
- `缺失和优化总览.md`

---

## 1. 文档目标

这份文档用于把当前前端设计正式拆成 4 类实现层级，回答三个问题：

1. 哪些页面可以直接用 Odoo 原生视图完成
2. 哪些页面要先补聚合字段，才能稳定落地
3. 哪些页面必须接受自定义 widget 或轻量前端增强

这份文档不讨论视觉对不对，而只讨论：

**这套设计如何在 Odoo 中真实落地。**

---

## 2. 分层标准

### A 类：纯原生可做

标准：
- 主要由 `menuitem + act_window + search + tree + form` 组成
- 不依赖复杂前端交互
- 不需要自定义 JS widget

适合：
- 基础列表页
- 基础配置页
- 基础异常页

### B 类：原生视图 + 聚合字段

标准：
- 页面结构仍然可以用原生 `tree/form/search` 承接
- 但页面是否好用，高度依赖后端预聚合字段
- 不先补聚合字段，页面虽然能出，但会不好用或会卡

适合：
- 运单列表
- 批次列表
- 异常列表
- 部分详情摘要区

### C 类：原生视图 + 轻量自定义 widget

标准：
- 主体仍在 Odoo 原生页面里
- 但某个关键阅读区需要增强
- 不建议整页重写，只增强局部

适合：
- 留痕时间线区
- 证据查看区
- 右侧摘要卡
- 工作台卡片区

### D 类：需要专门定制或暂缓

标准：
- 如果坚持 1:1 还原草图，原生 Odoo 不够用
- 要么接受一期降级
- 要么专门做 controller + widget + 自定义页面

适合：
- 复杂证据总览
- 高交互工作台
- 高密度老板决策页
- 复杂图表 / graph / pivot 驱动的管理页

---

## 3. 当前总体判断

### 当前推荐策略

- `P0` 页面优先走 `B + C`
- `P1` 页面优先走 `B`
- `P2` 页面优先走 `D`

### 当前不推荐

- 一开始就按草图 100% 重做整页前端
- 在没有聚合字段方案前先硬做工作台
- 把时间线和证据区强行塞进纯 XML，导致阅读体验和性能都很差

## 5. 每类页面的具体落地建议

## 5.1 运单追溯列表页

建议层级：`B`

### 可直接用原生承接的部分
- `search view`
- `tree view`
- 快捷筛选
- 默认排序
- 行内跳转动作

### 必须先补的聚合字段
- `latest_trace_time`
- `latest_trace_type`
- `evidence_completeness`
- `exception_status`
- `latest_submit_user`

### 当前不建议一步做到的部分
- 行内复杂证据预览
- 行内时间线展开

### 一期推荐实现形态
- 先做双行信息列表
- 用 decoration / badge 表达异常和证据状态
- 保持“查找 + 第一轮判断”定位

## 5.2 运单详情页

建议层级：`B + C`

### 可直接用原生承接的部分
- 头部摘要
- 当前状态区
- 执行上下文区
- 处理记录区

### 需要聚合字段的部分
- 头部摘要
- 异常摘要
- 最近留痕摘要
- 最近证据摘要

### 建议做轻量增强的部分
- 留痕时间线区
- 证据查看区
- 右侧摘要卡

### 一期推荐实现形态
- 页面主体仍走 `form`
- 时间线和证据区先做可用版
- 不追求第一版就完全等于草图

## 5.3 留痕时间线区

建议层级：`C`

### 原生可做的简版
- one2many 列表
- 按时间倒序
- 展示类型、时间、提交人、图片数

### 原生不足点
- 卡片化阅读弱
- 异常高亮有限
- 和证据的双向联动体验弱

### 推荐实现方式
- 一期：原生列表 + 少量装饰
- 二期：自定义 timeline widget

## 5.4 证据查看区

建议层级：`C`

### 原生可做的简版
- one2many 图片列表
- 点击跳图片链接
- 查看关联留痕摘要

### 原生不足点
- 大图预览体验弱
- 左右切图体验弱
- 上下文阅读关系弱

### 推荐实现方式
- 一期：局部 evidence widget
- 不重写整页，只增强图片区

## 5.5 批次追溯列表页

建议层级：`B`

### 原生可做的部分
- 列表
- 搜索与筛选
- 下钻运单 / 异常

### 依赖的聚合字段
- `total_waybill_count`
- `exception_waybill_count`
- `signed_waybill_count`
- `latest_trace_time`
- `evidence_completeness`
- `risk_level`

### 一期推荐实现形态
- 做成“聚合判断页”
- 不把运单明细直接塞进首页

## 5.6 异常详情页

建议层级：`B + C`

### 原生可做的部分
- 异常摘要
- 处理状态区
- 处理记录

### 建议增强的部分
- 关联证据区
- 关键留痕区
- 关联对象快捷阅读

### 一期推荐实现形态
- 原生 form 承接主体
- 关键证据区做增强

## 5.7 管理工作台

建议层级：`C / D`

### 适合一期先做的部分
- 3 到 5 张卡片
- 优先处理对象列表
- 最近变化简表
- act_window 下钻

### 不建议一期强做的部分
- 重图表
- 复杂 dashboard 容器
- 强交互式统计面板

### 一期推荐实现形态
- “轻工作台”
- 重点是卡片下钻，不是 BI 展示

## 5.8 老板追溯查看页

建议层级：`C / D`

### 一期可做形态
- 摘要卡
- 争议对象短列表
- 简化证据摘要

### 不建议一期强做
- 复杂责任分析面板
- 复杂证据对比器

## 6. 按实现前置条件拆分

### 6.1 只要模型骨架就能开始的内容

- 页面信息架构
- 菜单和 action 设计
- search/tree/form 原型
- 基础字段落位

### 6.2 必须先定聚合字段的内容

- 运单列表
- 批次列表
- 异常列表
- 运单详情头部摘要
- 工作台卡片

### 6.3 必须先定自定义增强策略的内容

- 留痕时间线正式版
- 证据查看区正式版
- 管理工作台正式版
- 老板页正式版

---

## 7. 一期推荐降级方案

为了保证项目先动起来，当前建议接受以下降级：

1. 运单详情页先用原生 `form` + 简版时间线 + 简版证据区
2. 工作台先做“卡片 + 列表”，不做重 dashboard
3. 老板页先做简版摘要，不做复杂决策面板
4. 证据总览页先不进一期

---

## 8. 当前最推荐的实现顺序

1. 运单追溯列表页
2. 运单详情页头部摘要 + 上下文区
3. 留痕时间线简版
4. 证据查看区简版
5. 当前异常列表页
6. 异常详情页
7. 批次追溯列表页
8. 批次详情页
9. 管理工作台简版

---

## 9. 结论

当前这套设计不是“不能做”，而是：

**必须分层做。**

真正合理的落地方式不是：
- 一上来按草图 100% 还原

而是：
- 先用 Odoo 原生能力把主链跑通
- 再把关键阅读区做轻量增强
- 最后才补重交互页面

只要按这个分层推进，当前设计是完全有机会稳步落地的。
