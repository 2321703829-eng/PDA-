# 仓储管理前端接入设计草案

适用范围：
- `ai-code/前端相关设计/` 下 Odoo 物流后台的仓储管理接入设计
- Odoo 原生 `stock` 能力在物流留痕后台中的前端接入、反查入口与追溯链路挂接

优先基准：
- `Odoo物流后台前端总体设计总览.md`
- `前端模块结构与菜单总表.md`
- `系统页面关系总览.md`

关联文档：
- `运输与调度模块前端设计草案.md`
- `后台按波次批次运单追溯页面设计.md`

## 1. 文档定位

这份文档不负责重做仓储页面，也不把仓储模块改造成新的主阅读中心。

它主要回答 4 个问题：

1. 哪些仓储页面直接复用 Odoo 原生入口
2. 哪些仓储页面需要增加追溯入口和 Smart Button
3. 仓储页面应该暴露哪些“能看懂追溯关系”的摘要字段
4. 仓储页面如何跳到批次、运单、留痕、异常这些主链页面

当前阶段的重点是：
- 让仓储页成为“业务事实来源页”和“反查入口页”
- 让追溯主链继续留在 `批次 -> 运单 -> 留痕/证据/异常`
- 优先复用 Odoo 原生 `stock` 页面，不重复建设仓储 UI

---

## 2. 模块定位

`仓储管理` 在整套前端结构中的定位是：

- 它属于 `业务接入层`
- 它以复用 Odoo 原生仓储能力为主
- 它承担“仓侧作业入口”和“从仓侧反查追溯链”的职责
- 它不是最终责任判断页，也不是老板阅读页

因此，仓储管理回答的问题应当是：

- 货当前在哪个仓、哪个货位、哪个出入库单据里
- 当前仓储作业做到哪一步
- 这个仓储作业关联到哪个批次、哪些运单
- 需要进一步判断时，应该跳到哪个追溯主页面

它不负责单独回答：

- 最终责任归属
- 争议结论
- 全链路事实阅读
- 复杂异常处理闭环

这些仍由 `留痕与追溯`、`异常中心`、`老板追溯页` 承担。

---

## 3. 模块边界

| 范围 | 当前纳入 | 当前不纳入 |
|---|---|---|
| 页面策略 | 复用 Odoo 原生仓储页，补追溯入口 | 重做完整仓储前端 |
| 主对象 | 仓库、货位、出入库作业、库存记录 | 车辆、司机、路线等二期资源对象 |
| 追溯关系 | 反查批次、运单、留痕、异常 | 在仓储页直接完成责任裁定 |
| 页面职责 | 入口、摘要、跳转、反查 | 取代运单详情/异常详情成为主阅读页 |

补充约束：

- 当前仓储接入必须兼容一期范围，不把二期调度资源当成必备前提
- 即使后续存在 `波次` 组织层，仓储页也不应依赖 `波次` 才能工作
- 仓储页优先围绕 `批次` 和 `运单` 建立稳定反查关系

---

## 4. 接入原则

当前仓储管理前端接入统一按下面 6 条原则执行：

1. 原生页面优先  
   能直接复用 Odoo `stock` 页面时，不做平行自研页面。

2. 入口增强优先  
   需要补的是 Smart Button、摘要字段、默认筛选和跳转动作，而不是整页重画。

3. 反查优先于主查  
   仓储页更适合承接“我在仓库单据里看到了问题，接下来跳去追溯”的路径。

4. 摘要先于深读  
   仓储页只展示足够判断“要不要继续下钻”的信息，不承担完整事实阅读。

5. 批次优先于直接异常  
   仓储对象与追溯链的首要连接点优先是 `批次`，其次才是 `运单` 与 `异常摘要`。

6. Odoo 原生动作传参优先  
   跳转统一优先使用 `act_window + domain + context + search_default_*` 实现。

## 5. 菜单与入口结构

当前建议保留 `仓储管理` 一级模块，并在其下挂接 3 类二级入口：

```text
物流后台
└── 仓储管理
    ├── 出入库作业
    ├── 库存查询
    └── 仓储追溯入口
```

三类入口的定位如下：

| 二级入口 | 页面类型 | 当前定位 |
|---|---|---|
| 出入库作业 | 原生页面入口 | 进入收货、发货、内部调拨、相关批量作业页面 |
| 库存查询 | 原生页面入口 | 查看仓、货位、库存数量、库存状态与可用量 |
| 仓储追溯入口 | 关联入口 / Smart Button 聚合入口 | 从仓侧对象快速跳到批次、运单、留痕主链 |

说明：

- `出入库作业` 和 `库存查询` 仍然以 Odoo 原生页面为主
- `仓储追溯入口` 可以是独立菜单，也可以先以多个 Smart Button 和预置筛选视图实现
- 当前不建议为了这一级入口额外设计复杂新首页

## 6. 原生页面接入清单

当前建议优先接入下面这些 Odoo 原生仓储对象页面：

| 页面对象 | Odoo 基础模块 | 页面角色 | 当前接入说明 |
|---|---|---|---|
| `stock.picking` | `stock` | 仓储作业事实页 | 作为最重要的仓侧单据入口 |
| `stock.picking.batch` | `stock_picking_batch` | 仓储批量作业页 | 作为仓侧聚合作业入口 |
| `stock.quant` | `stock` | 库存结果页 | 用于回答库存当前分布与数量状态 |
| `stock.location` | `stock` | 货位资料与库存承载页 | 用于从货位反查相关批次/运单 |
| `stock.warehouse` | `stock` | 仓级资料与总览页 | 用于从仓维度汇总查看相关执行对象 |

接入优先级建议如下：

1. `stock.picking`
2. `stock.picking.batch`
3. `stock.quant`
4. `stock.location`
5. `stock.warehouse`

原因：

- `stock.picking` 最贴近“某次实际入库/出库/调拨到底发生了什么”
- `stock.picking.batch` 最适合承接仓侧的聚合作业反查
- `quant/location/warehouse` 更偏结果视角和资料视角，适合作为二级补充入口

## 7. 仓储页面中的追溯入口设计

## 7.1 `stock.picking` 页面

`stock.picking` 是当前仓储接入的第一优先页面。

建议补充的入口：

- `关联批次` Smart Button
- `关联运单` Smart Button
- `查看追溯` Smart Button
- `查看异常` Smart Button

建议暴露的摘要字段：

- 仓储单据类型
- 对应仓库
- 来源单据编号
- 关联批次数
- 关联运单数
- 高风险运单数
- 最新留痕时间
- 是否存在未闭环异常

推荐跳转关系：

- 从 `stock.picking` 跳 `批次详情` 或 `批次列表`
- 从 `stock.picking` 跳 `运单追溯列表`
- 从 `stock.picking` 跳 `当前异常列表`
- 从 `stock.picking` 跳 `留痕与追溯` 主链页

当前判断：

- `stock.picking` 不是追溯主详情页
- 但它必须成为最自然的仓侧反查入口

## 7.2 `stock.picking.batch` 页面

这个页面更适合作为仓储侧的聚合作业入口。

建议补充的入口：

- `关联批次` Smart Button
- `关联运单` Smart Button
- `查看仓储追溯` Smart Button

建议暴露的摘要字段：

- 批量作业编号
- 作业状态
- 仓库
- 包含单据数
- 关联批次数
- 关联运单数
- 异常摘要
- 最近更新时间

推荐跳转关系：

- `stock.picking.batch -> 批次列表 / 批次详情`
- `stock.picking.batch -> 运单追溯列表`
- `stock.picking.batch -> 当前异常列表`

说明：

- 这里的“批量作业”是仓储执行聚合视角
- 它可以和物流批次形成映射，但前端不应把两者直接混成同一个页面概念

## 7.3 `stock.quant` 页面

`stock.quant` 主要回答库存结果问题，不适合承载太多操作。

建议补充的入口：

- `相关批次` 快捷入口
- `相关运单` 快捷入口

建议暴露的摘要字段：

- 仓库
- 货位
- 商品
- 可用量
- 在手量
- 最近关联批次
- 最近关联运单
- 最近留痕时间

推荐跳转关系：

- `stock.quant -> 批次列表`
- `stock.quant -> 运单追溯列表`

说明：

- 这里更适合做“结果反查”
- 不建议在库存列表页堆积过多异常处理动作

## 7.4 `stock.location` 页面

货位页建议承担“仓内位置反查入口”的职责。

建议补充的入口：

- `相关批次`
- `相关运单`
- `查看追溯摘要`

建议暴露的摘要字段：

- 货位类型
- 所属仓库
- 当前批次数
- 当前运单数
- 异常运单数
- 最近留痕时间

推荐跳转关系：

- `stock.location -> 批次列表`
- `stock.location -> 运单追溯列表`

## 7.5 `stock.warehouse` 页面

仓库页更偏总览入口，建议只做摘要接入。

建议补充的入口：

- `当前批次`
- `当前运单`
- `当前异常`

建议暴露的摘要字段：

- 仓库编码
- 当前批次数
- 当前运单数
- 当前异常数
- 今日出入库作业数
- 最近留痕时间

推荐跳转关系：

- `stock.warehouse -> 批次列表`
- `stock.warehouse -> 运单追溯列表`
- `stock.warehouse -> 当前异常列表`

## 8. 仓储页面建议暴露的追溯关联字段

为了让仓储页具备“可读的追溯入口价值”，当前建议统一补充一组轻量摘要字段。

| 字段类别 | 推荐字段 | 主要用途 |
|---|---|---|
| 关联对象类 | 关联批次、关联运单、关联客户、关联门店 | 让仓储单据能快速知道业务归属 |
| 留痕摘要类 | 最新留痕时间、最新留痕类型、最新留痕人员 | 判断是否有足够事实可看 |
| 异常摘要类 | 是否有异常、未闭环异常数、高风险标记 | 判断是否需要继续下钻 |
| 仓侧位置类 | 仓库、货位、作业类型、单据状态 | 维持仓储页自身可读性 |
| 追溯入口类 | 追溯详情入口、批次入口、运单入口 | 降低跨模块跳转成本 |

字段补充原则：

- 先补摘要字段，不先补复杂聚合大屏
- 优先补“能决定下一步去哪看”的字段
- 尽量避免在仓储页直接展示过深的证据明细

## 9. 跳转与上下文传递设计

仓储页跳转到追溯主链时，统一建议保留下面几类上下文：

- 来源对象类型  
  例如：来自 `stock.picking`、`stock.picking.batch`、`stock.location`

- 来源对象 ID  
  用于详情页返回、面包屑和日志记录

- 关联仓库 / 货位上下文  
  便于在追溯列表页自动带出筛选条件

- 默认目标对象范围  
  例如默认展示当前仓储单据关联的 `批次` 或 `运单`

推荐动作方式：

| 场景 | 推荐方式 |
|---|---|
| 跳批次列表 | `act_window + domain` |
| 跳运单列表 | `act_window + domain + search_default_*` |
| 跳异常列表 | `act_window + context` |
| 跳追溯详情 | `act_window` 直接开目标 form |

上下文建议包含：

- `default_source_model`
- `default_source_id`
- `search_default_warehouse_id`
- `search_default_location_id`
- `search_default_has_open_exception`

说明：

- 优先沿用 Odoo 标准动作机制
- 不建议为了这一层接入单独发明复杂前端路由体系

## 10. 仓储管理与追溯主链的关系

当前统一按下面这条原则理解：

```text
仓储管理 = 业务事实入口与反查入口
留痕与追溯 = 事实主阅读链
异常中心 = 问题处理链
老板追溯页 = 决策摘要链
```

因此，推荐关系是：

- 仓储页先展示“仓侧事实和摘要”
- 需要判断时跳到 `批次详情`
- 需要看单笔事实时跳到 `运单详情`
- 需要处理问题时跳到 `异常详情`

而不推荐：

- 在仓储页直接拼接完整时间线
- 在仓储页直接承载证据查看主界面
- 在仓储页直接承担老板阅读视角

## 11. 实现层建议

当前实现策略建议尽量轻：

1. 复用 Odoo 原生 `tree/form/search` 页面
2. 在原生页面上增加少量关联字段
3. 用 Smart Button 提供追溯链入口
4. 用动作上下文传递默认筛选条件
5. 把复杂聚合留给追溯页和工作台页

如果需要实现优先级排序，建议按下面顺序推进：

1. `stock.picking` 入口增强
2. `stock.picking.batch` 入口增强
3. `stock.quant` 结果反查
4. `stock.location` / `stock.warehouse` 摘要增强

---

## 12. 当前阶段结论

当前阶段对 `仓储管理` 的前端判断可以收口为：

1. 仓储页以复用 Odoo 原生能力为主，不重做主页面
2. 仓储页最重要的任务是提供稳定的追溯反查入口
3. `stock.picking` 是最优先增强对象
4. 仓储页只做摘要，不替代 `批次详情`、`运单详情`、`异常详情`
5. 一期范围内应优先围绕 `批次`、`运单`、`留痕`、`异常` 建立关系，不依赖二期调度资源
