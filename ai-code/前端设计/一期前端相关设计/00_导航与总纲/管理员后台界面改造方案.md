## 1. 文档定位

本方案是管理员后台界面的现行正式稿。

它用于统一回答下面这些问题：

1. 管理员后台的核心价值是什么
2. 管理员到底先看什么、再看什么、最后做什么
3. 运单、批次、留痕、证据、异常如何串成稳定的后台阅读链
4. 哪些页面属于一期必须打通的主闭环，哪些放到后续阶段
5. 这套方案如何落到 Odoo 的菜单、动作、列表、表单、搜索与轻量增强上

本方案不是视觉稿，不替代页面草图，也不替代字段和接口清单。

它的作用是：

- 作为管理员后台的总方案正文
- 作为页面清单、字段清单、动作清单、接口清单的上游说明
- 作为前后端评审时的范围与边界基线

## 3. 目标与边界

### 3.1 Outcome

管理员进入后台后，应能稳定完成这条主链：

`找到对象 -> 看当前状态 -> 看留痕过程 -> 看图片证据 -> 判断异常 -> 记录处理动作`

### 3.2 Behavior

管理员后台必须优先支持：

1. 按运单、批次、异常快速找到对象
2. 在列表页完成第一轮判断
3. 在详情页完成摘要、过程、证据、异常的连贯阅读
4. 从异常对象快速回跳到运单、批次、留痕与证据
5. 在问题对象上完成有限且可追踪的处理动作

### 3.3 Boundary

本方案明确不承担：

- 泛协同消息中心
- CRM 式客户经营界面
- 复杂审批流壳子
- 与留痕主闭环无关的大而全后台改版

本方案也不把下面对象当成证据主对象：

- 批次
- 车次
- 普通附件
- chatter 消息流

## 4. 设计前提

当前管理员后台必须统一接受以下判断：

1. 这套系统的本质是物流过程留痕取证系统，不是通用 ERP 皮肤改造项目。
2. 后台第一价值是“查、看、追溯、判断、处理”，不是录入和审批。
3. 后台阅读主线已经固定为：
   - 执行主线：`波次 -> 批次 -> 运单`
   - 追溯主线：`运单 -> 留痕 -> 证据 -> 异常`
4. 运单详情页是后台阅读中枢，不是批次页，也不是异常页。
5. 证据必须挂在留痕事实下面被阅读，不能退化成普通附件入口。
6. 管理员页和老板页共享同一套事实来源，但不是同一套阅读密度和动作密度。

## 5. 管理员后台的核心任务

管理员后台主要服务下面 5 类任务：

1. 查询对象
   - 找运单
   - 找批次
   - 找异常
2. 看当前状态
   - 当前到了哪一步
   - 当前有没有异常
   - 最近留痕是什么
3. 看历史过程
   - 何时发生
   - 谁提交了留痕
   - 过程是否断档
4. 看证据链
   - 有几张图
   - 图属于哪次留痕
   - 证据是否足够支持判断
5. 做处理动作
   - 标记处理中
   - 添加处理备注
   - 跳关联对象继续追查

因此，管理员后台不是“运营录入后台”，而是“追溯与处理后台”。

## 6. 页面结构模型

管理员后台的关键页面统一按下面三层组织：

### 6.1 当前状态层

用于回答：
- 现在怎么样

典型信息：
- 运单当前状态
- 批次当前状态
- 当前是否异常
- 最新留痕摘要
- 最新证据摘要

主要服务：
- 列表页
- 工作台卡片
- 详情页头部摘要区

### 6.2 留痕事实层

用于回答：
- 过程中发生过什么

典型信息：
- 留痕时间
- 留痕类型
- 提交人
- 留痕备注
- 所属节点
- 是否异常留痕

主要服务：
- 时间线
- 历史追溯区
- 异常关联区

### 6.3 图片证据层

用于回答：
- 有哪些可直接查看的证据

典型信息：
- 图片列表
- 顺序
- 对应留痕
- 上传人或拍摄时间
- 图片备注
- 证据完整度

主要服务：
- 证据查看区
- 证据弹层或抽屉
- 异常详情中的关键证据区

## 7. 模块边界与依赖

### 7.1 依赖的自定义模块

管理员后台主要依赖：

- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- `logistics_trace_dashboard`

其中分工为：

- `logistics_dispatch` 提供执行上下文
- `logistics_trace_core` 提供留痕事实
- `logistics_trace_evidence` 提供证据材料
- `logistics_trace_exception` 提供问题对象与处理状态
- `logistics_trace_dashboard` 提供工作台与聚合摘要

### 7.2 依赖的 Odoo 原生能力

管理员后台优先复用：

- `menu`
- `act_window`
- `search view`
- `tree/list`
- `form`
- `kanban`
- `smart button`
- `stat button`
- `notebook`
- chatter 作为辅助协作区

默认原则：

1. 先用 Odoo 原生壳承接主体页面
2. 聚合摘要靠字段或轻量接口补足
3. 时间线区和证据区允许做轻量 widget 增强
4. 不把一期直接做成重前端系统

## 8. 信息架构与菜单口径

当前系统级菜单口径按 8 个一级模块组织，但管理员后台的一期冻结范围优先聚焦下面 3 个：

```text
物流后台
├─ 工作台
│  └─ 管理工作台
├─ 留痕与追溯
│  ├─ 运单追溯
│  ├─ 批次追溯
│  ├─ 当前异常
│  └─ 历史异常
└─ 运输与调度
   ├─ 波次管理
   ├─ 批次管理
   └─ 运单管理
```

补充约定：

- `待处理争议` 优先做异常列表预设视图，不强制独立菜单
- `证据查看` 优先挂在运单详情与异常详情中，不单独顶层化
- `设置与规则`、`统计与看板`、`业务单据`、`仓储管理` 当前保留设计位，不抢 P0 主闭环优先级

## 9. 页面体系与优先级

### 9.1 P0

P0 目标是先打通管理员后台最小证据闭环。

必须先做：

1. 管理工作台
2. 运单追溯列表页
3. 运单详情页
4. 留痕时间线区
5. 证据查看区
6. 当前异常列表页
7. 异常详情页基础处理区

### 9.2 P1

P1 目标是补齐运营追溯能力和聚合判断能力。

建议补做：

1. 批次追溯列表页
2. 批次详情页
3. 历史异常列表页
4. 待处理争议视图
5. 波次追溯页

### 9.3 P2

P2 再考虑增强层能力。

后续再做：

1. 车次追溯页
2. 证据总览页
3. 高级统计与导出
4. 更细颗粒度分析看板

## 10. 核心阅读路径

### 10.1 管理主路径

```text
管理工作台
  -> 当前异常列表 / 运单追溯列表 / 批次追溯列表
  -> 运单详情 / 异常详情 / 批次详情
  -> 留痕时间线区 / 证据查看区
  -> 处理动作与备注
```

### 10.2 运单阅读路径

```text
运单追溯列表
  -> 运单详情
  -> 留痕时间线
  -> 证据查看
  -> 异常详情
```

### 10.3 问题处理路径

```text
当前异常列表
  -> 异常详情
  -> 关联运单 / 批次 / 关键留痕 / 关键证据
  -> 标记处理中 / 添加处理备注 / 标记已核实
```

设计原则：

- 工作台负责“先看什么”
- 运单详情负责“到底发生了什么”
- 异常详情负责“问题怎么处理”

## 11. 页面分区原则

### 11.1 列表页

列表页必须优先支持：

- 主搜索框
- 快捷筛选
- 稳定排序
- 行内主动作
- 第一列可点击进入详情

列表页不应承担：

- 大量编辑动作
- 冗长字段堆叠
- 难以解释的统计

### 11.2 详情页

详情页统一按下面顺序组织：

1. 头部摘要区
2. 当前状态区
3. 执行上下文区
4. 留痕时间线区
5. 证据查看区
6. 异常摘要区
7. 处理记录区

详情页不能退化成：

- 单纯字段堆叠页
- 单纯附件浏览页
- 单纯消息流页面

### 11.3 工作台

工作台是首页与分流入口，不是事实终点页。

它应重点承接：

- 概览卡
- 优先处理对象
- 风险分布
- 最近变化
- 快捷下钻

## 12. 搜索、筛选与动作口径

### 12.1 默认搜索项

管理员后台优先支持：

- 运单号
- 批次号
- 异常编号
- 外部单号
- 人员

### 12.2 常用筛选项

高频筛选应优先服务判断，而不只是检索：

- 有异常
- 证据不足
- 今日有更新
- 待处理
- 高严重度

### 12.3 页面主动作

统一优先保留下面这组动作：

- 查看详情
- 查看留痕
- 查看证据
- 查看异常
- 跳关联对象
- 标记处理中
- 添加处理备注
- 标记已核实

动作原则：

1. 先阅读，再处理
2. 主动作尽量控制在 1 到 3 个
3. 跳转动作优先于大量原地编辑
4. 状态动作必须可追踪、可控权限

## 13. 权限与角色口径

管理员后台当前至少区分下面几类角色：

- 系统管理员
- 物流运营管理员
- 异常处理人员
- 追溯查看人员
- 老板或管理层查看人员

当前推荐口径：

1. 没权限优先表现为入口不显示或动作不显示，不优先表现为报错
2. 摘要可见不等于详情可编辑
3. 同一页面可以分区控制权限
4. 状态流转动作必须附着角色与当前状态判断

## 14. 后端依赖、聚合字段与 SQL 结论

### 14.1 依赖的核心能力

管理员后台最依赖的不是复杂前端框架，而是：

- 可信的主对象模型
- 稳定的聚合字段
- 可解释的摘要口径
- 可承受的查询性能

### 14.2 一期推荐结论

当前推荐：

1. 主体列表与详情先以 Odoo 原生 RPC 和标准视图承接
2. 对于列表页判断和详情页摘要，优先补聚合字段
3. 时间线区和证据区允许走轻量增强接口
4. 一期先不额外引入复杂 SQL 视图或重型物化层
5. 如果搜索和聚合性能不足，再补索引与受控聚合方案

### 14.3 必须先稳定的聚合方向

一期必须优先稳定：

- 运单当前状态摘要
- 最新留痕摘要
- 证据完整度
- 当前异常数
- 批次聚合风险摘要
- 工作台概览指标

### 14.4 索引与查询性能关注点

优先关注：

- 运单号
- 外部单号
- 批次号
- 异常编号
- 提交人
- 时间范围与状态组合筛选

## 15. Odoo 落地方式

当前最推荐的落地方式是：

1. 列表页：`search + tree/list + act_window`
2. 详情页：`form + notebook + stat button + smart button`
3. 工作台：聚合首页或 `client action` 轻量承接
4. 时间线区：详情页增强区或轻量 widget
5. 证据区：详情页增强区或轻量 widget

明确不建议的一期做法：

- 整体脱离 Odoo 再造前端壳
- 所有页面都重做为重定制 SPA
- 在主链未稳定前先做复杂图表大屏

---

## 16. 当前不做范围

当前明确不纳入管理员后台主范围：

- Discuss 风格消息中心
- 聊天、频道、私聊页面
- 日历、会议、办公协同页面
- 泛联系人中心
- CRM 式客户经营视图
- 复杂审批外壳
- 与留痕主闭环无关的重统计系统

---

## 17. 与老板页的区别

管理员后台与老板页共享事实来源，但区别明确：

1. 管理员页重“过程阅读 + 对象处理”
2. 老板页重“结论摘要 + 风险判断”
3. 管理员页信息密度更高
4. 老板页动作更少，优先看结论和关键证据

因此：

- 管理员后台不是老板页的详细版
- 老板页也不是管理员工作台的压缩版

---

## 18. 当前结论

管理员后台的现行正式口径可以收敛成一句话：

**围绕运单主对象，把工作台、运单详情、时间线、证据区、异常处理串成一个可阅读、可判断、可处理的后台追溯闭环。**

一期先打通主闭环，二期再补齐更广的聚合视角和增强能力。
