## 1. 文档定位

这份文档是当前整套 Odoo 物流后台前端设计的总纲。

它要解决的不是某一页怎么画，而是先把下面这些问题统一下来：

1. 这个后台系统到底是干什么的
2. 后台里最重要的对象和主链是什么
3. 各一级模块在前端里的职责怎么分
4. 哪些模块是自研核心，哪些是复用 Odoo
5. 后续各模块设计草案应该挂在哪个结构下面

因此，这份文档的作用是：

- 给产品、前端、后端、评审者一个共同理解入口
- 给后续各模块草案提供统一的系统级结构
- 让整个前端设计不再只停留在零散页面层面

---

## 2. 系统定位

本系统基于 Odoo Web 后台构建，是一套以物流留痕与追溯为核心能力、以运输执行与后台判责为主要使用场景的物流管理后台。

它的核心价值不是“把 ERP 页面换个皮”，而是把下面这条业务闭环做顺：

- 调度形成执行主线
- 批次承接车辆与司机任务
- 运单承接门店级交付对象
- 留痕记录现场事实
- 证据沉淀图片与备注
- 异常承接问题处理
- 后台支持查询、阅读、判断、追溯、反查

换句话说，这个后台不是传统录单型系统，而是一个：

**以运单追溯和执行管理为核心的 Odoo 物流后台。**

---

## 3. 当前最重要的对象主线

根据当前基准文档，系统的核心对象主线已经明确为：

```text
波次记录 -> 批次 -> 运单号 -> 运单下订单列表 -> 留痕事件 -> 证据图片/备注
```

这里要特别强调 4 个判断：

1. `运单号` 才是现场留痕与证据归档的主对象
2. `订单` 是运单下的履约明细对象，不是留痕主对象
3. `批次` 是执行组织对象，不替代门店交付事实
4. `波次记录` 是调度组织视角，不直接承担现场留痕主职责

这条主线直接决定了前端设计的阅读顺序：

- 管理视角先看波次和批次
- 追溯视角重点看运单
- 事实阅读重点看留痕和证据
- 问题处理重点看异常

## 4. 使用角色

当前后台前端设计主要服务这几类角色：

### 4.1 管理员 / 运营

主要任务：
- 查询对象
- 筛选问题
- 查看过程
- 核对证据
- 跟进异常

### 4.2 物流负责人

主要任务：
- 看波次和批次整体执行情况
- 判断某批次是否存在集中问题
- 从批次下钻到运单与异常

### 4.3 老板 / 管理层

主要任务：
- 快速锁定争议对象
- 快速看关键过程和关键证据
- 快速做责任与现状判断

### 4.4 资料与配置维护人员

主要任务：
- 维护规则、编号、类型、权限
- 维护部分基础资料
- 保证系统口径与入口配置正确

---

## 5. 前端设计总目标

这一轮后台前端设计，不是单纯让页面更美观，而是要同时达到 5 个目标：

1. 让后台主链清晰
2. 让管理员和老板能快速找到目标对象
3. 让留痕、证据、异常之间的关系一眼就能读懂
4. 让 Odoo 原生模块和自定义追溯链路自然接上
5. 让后续视图设计、接口设计和模块设计都能依附同一套结构推进

---

## 6. 一级模块总览

当前后台前端按下面 8 个一级模块组织：

1. `工作台`
2. `留痕与追溯`
3. `运输与调度`
4. `仓储管理`
5. `业务单据`
6. `商品与基础资料`
7. `统计与看板`
8. `设置与规则`

这 8 个模块不是并列同权的。它们在系统里的角色不同。

---

## 7. 模块分层

为了让后续设计有重点，建议把这 8 个模块分成 4 层来理解。

## 7.1 核心阅读层

包含：
- 工作台
- 留痕与追溯
- 当前异常
- 老板追溯查看

这一层负责：
- 让人快速找到目标对象
- 让人快速读懂过程和证据
- 让问题处理有明确入口

它是整个后台最核心的“看”和“判”层。

## 7.2 执行组织层

包含：
- 运输与调度
- 波次管理
- 批次管理
- 运单管理
- 车辆管理
- 司机管理

这一层负责：
- 定义后台的执行主线
- 提供追溯页面所依赖的稳定上下文
- 把管理页和追溯页区分开

它是整个后台的“组织”和“承接”层。

## 7.3 业务接入层

包含：
- 仓储管理
- 业务单据
- 商品与基础资料

这一层负责：
- 复用 Odoo 原生能力
- 为运单、批次、留痕、异常提供上下游入口
- 通过 Smart Button、关联字段、上下文跳转接入追溯主链

它是整个后台的“连接”和“反查”层。

## 7.4 管理与配置层

包含：
- 统计与看板
- 设置与规则

这一层负责：
- 给管理者提供聚合视图
- 给系统提供规则与参数配置入口
- 让追溯结果与规则体系形成闭环

它是整个后台的“分析”和“控制”层。

---

## 8. 各一级模块定位

## 8.1 工作台

定位：
- 整个后台的首页与分流入口

主要任务：
- 展示全局概况
- 提示待处理问题
- 提供高频入口

它不是完整分析平台，而是：

**先告诉管理员“今天先看什么”。**

## 8.2 留痕与追溯

定位：
- 整个后台最核心的业务阅读模块

主要任务：
- 围绕运单做完整追溯
- 围绕批次做聚合查看
- 围绕异常做问题处理
- 围绕老板视角做决策式阅读

它是后台最核心的：

**追溯与判责中心。**

## 8.3 运输与调度

定位：
- 后台执行主线的管理模块

主要任务：
- 管波次、批次、运单、车辆、司机
- 提供执行组织上下文
- 与追溯链形成一前一后两条主线

它不是纯资料模块，而是：

**执行主对象管理中心。**

## 8.4 仓储管理

定位：
- 复用 Odoo 原生库存与出入库能力

主要任务：
- 为批次与运单提供仓侧数据来源
- 提供入库、出库、库存查询等入口
- 在必要处接入追溯反查

它的重点不是重做，而是：

**复用 + 补入口。**

## 8.5 业务单据

定位：
- 复用 Odoo 原生销售、采购、出入库单据能力

主要任务：
- 保持原生单据链完整
- 提供跳转到运单、批次、追溯页面的入口
- 支持从单据反查执行与追溯对象

## 8.6 商品与基础资料

定位：
- 提供整个系统的基础数据入口

主要任务：
- 管商品
- 管客户/门店
- 管仓库与货位

这一层不承担追溯主阅读职责，但应支持必要的追溯关联展示。

## 8.7 统计与看板

定位：
- 为管理层和运营层提供聚合视角

主要任务：
- 展示留痕相关统计
- 展示异常相关统计
- 输出排行榜、趋势、聚合结果

这一层建立在主链稳定之后，不抢核心页面优先级。

## 8.8 设置与规则

定位：
- 配置留痕、异常、编号、权限等系统规则

主要任务：
- 固化规则
- 配置类型
- 管理编号
- 对齐角色与菜单权限

## 9. 页面分层

当前后台页面建议统一理解为 3 层：

## 9.1 入口层

典型页面：
- 管理工作台
- 运单追溯列表
- 批次追溯列表
- 当前异常列表
- 老板追溯查看页
- 波次管理列表
- 批次管理列表
- 运单管理列表

这一层重点解决：
- 去哪找对象
- 先看什么
- 先筛什么

## 9.2 核心对象层

典型页面：
- 运单详情
- 批次详情
- 异常详情
- 波次详情
- 运单管理详情

这一层重点解决：
- 这个对象当前是什么状态
- 它关联哪些上下文
- 我下一步要往哪里下钻

## 9.3 过程与证据层

典型页面：
- 留痕时间线页
- 证据查看页

这一层重点解决：
- 现场到底发生了什么
- 证据是否足够
- 是否能支撑当前判断

---

## 10. 两条核心前端主链

## 10.1 执行管理主链

```text
波次管理 -> 批次管理 -> 运单管理 -> 车辆/司机/仓侧上下文
```

这条链主要服务：
- 物流负责人
- 调度管理者
- 需要从组织视角看执行情况的人

## 10.2 追溯阅读主链

```text
工作台 / 运单追溯 / 批次追溯 / 当前异常
  -> 运单详情 / 批次详情 / 异常详情
  -> 留痕时间线
  -> 证据查看
```

这条链主要服务：
- 管理员
- 运营
- 客服
- 老板

这也是当前后台前端体验设计最优先的一条链。

## 11. 页面布局统一原则

## 11.1 列表页

列表页统一以“查找与筛选”为主。

推荐结构：
- 面包屑与标题
- 主搜索栏
- 快捷筛选
- 可展开高级筛选
- 数据表格
- 分页与结果状态

重点不是堆字段，而是让用户先筛出值得看的对象。

## 11.2 详情页

详情页统一以“阅读与判断”为主。

推荐结构：
- 顶部标题、状态、主操作
- 左侧主阅读区
- 右侧摘要与快捷跳转区

重点不是做成复杂表单，而是让阅读路径自然。

## 11.3 时间线与证据页

这两类页是事实阅读层。

推荐原则：
- 时间线强调事件顺序和节点上下文
- 证据页强调图片与所属留痕的对应关系
- 不单独设置“无上下文证据中心”

---

## 12. 与 Odoo 原生模块的关系

当前总体策略不是重做一套全新后台，而是：

**在 Odoo 原生后台壳子里，把复用模块和自定义追溯链路组织成一套更适合当前业务的前端结构。**

建议分成三类：

### A 类：核心自研前端模块

包括：
- 留痕与追溯
- 异常中心
- 老板追溯查看
- 部分工作台卡片与阅读页

### B 类：管理型自研模块

包括：
- 波次管理
- 批次管理
- 运单管理
- 车辆管理
- 司机管理

### C 类：复用型模块

包括：
- 仓储管理
- 业务单据
- 商品与基础资料
- 权限与角色管理

这类模块设计重点不是整页重做，而是：
- 定义入口
- 定义关联字段
- 定义 Smart Button
- 定义跳转上下文

---

## 13. 当前设计边界

为了避免范围继续发散，这一轮前端总体设计明确不做下面这些事：

1. 不设计司机端小程序 / H5 具体页面
2. 不在这一轮里展开后台代码实现
3. 不把统计看板提前做成完整 BI 平台
4. 不把证据查看做成脱离运单/留痕上下文的附件中心
5. 不把订单重新拉回留痕主对象

## 15. 总结

当前这套 Odoo 物流后台前端，不应再被理解成“几个追溯页面的集合”，而应理解成：

- 一套以 `波次 -> 批次 -> 运单` 为执行主线
- 以 `运单 -> 留痕 -> 证据 -> 异常` 为阅读主线
- 以 Odoo 原生模块为底座
- 以追溯、判断、反查、接入为目标

的系统级后台前端设计。

后续所有模块级设计草案，都应以这份文档为总入口和总边界。
