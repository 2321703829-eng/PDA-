# enterprise-isolation-p0-p1

## 通用协作约束

1. 完成编码工作后，默认需要向用户提供详细的人工复核操作流程，除非用户已明确说明“不需要核实”或“不需要复核”。
2. 开启设计文档编写工作前，默认需要先与用户讨论编写思路；未得到用户确认前，不开始正式编写，除非用户已明确说明“不需要讨论”或直接要求开始编写。
3. 每次完成文档编写或编码后，默认需要回扫当前所处阶段对应的设计文档，并对其中已过期、已冲突或已不再符合当前实现/方案的内容进行同步修正，除非用户已明确说明“不需要更改”。
4. 若无法明确当前工作属于哪一期或哪个阶段，在进行上述设计文档回扫和修改前，默认需要先询问用户确认；只有在用户已明确说明无需询问或无需更改时，才可以跳过。

## 目的

为“企业分离功能”相关任务提供一个收口到 `P0 / P1` 的本地入口，避免新对话一上来就把主题误扩成：

- 平台控制面
- 套餐系统
- 跨租户汇总
- 商用运营能力

本 skill 只服务：

- 多数据库底盘验证
- 现有物流模块租户化落地
- 企业隔离与 `multi-company` 的边界澄清
- 租户内基础角色组与能力骨架的前置判断

## 使用场景

- 用户要求继续“企业分离功能”的设计或实现准备
- 用户要求验证数据库级企业隔离是否可行
- 用户要求规划 `P0` 多数据库底盘验证
- 用户要求规划 `P1` 现有物流模块租户化落地
- 用户要求判断某项需求属于 `P0/P1` 还是 `P2/P3`
- 用户要求在不破坏当前物流主线的前提下推进企业隔离

## 不适用场景

下面这些不由本 skill 直接承接，应先单独确认范围：

- 平台后台
- 租户任务中心
- 自动开租户
- 租户生命周期平台化运维
- 跨租户统计看板
- 套餐计费、续费、宽限期、降级自动化
- 灰度升级、版本治理、商用运营增强

这些主题默认属于：

- `P2` 平台控制基础版
- `P3` 商用运营增强版

如果用户没有明确要求，不要主动把任务拉入 `P2/P3`。

## 固定边界口径

企业分离主题默认遵守下面 5 条：

1. 不同企业之间隔离，默认靠数据库级隔离
2. 同一企业内部如有多个法人，才考虑 `multi-company`
3. 物流业务对象继续沿用当前项目主线
4. 不允许为企业分离重起一套 `tms_*` 主对象体系
5. 企业分离不能打散当前 `wave / batch / waybill / trace / evidence / exception` 主线

## P0 目标与不做项

### P0 目标

- 一套 Odoo 服务承载多个数据库
- 每个企业一个独立数据库
- 子域名到数据库的基本映射
- 关闭数据库枚举能力
- 关闭数据库管理页
- 手工建库、手工装模块、手工备份恢复

### P0 不做项

- 自助开租户
- 平台后台
- 跨租户统计看板
- 套餐、到期、续费
- 自动灰度升级

### P0 默认检查项

1. `dbfilter` 是否能稳定命中目标数据库
2. 反向代理是否正确透传 `Host`
3. 是否已关闭数据库列表和数据库管理入口
4. 租户库是否能独立登录和运行
5. 备份与恢复后是否仍能独立访问

## P1 目标与不做项

### P1 目标

- 每个租户数据库安装同一套现有物流模块
- 物流对象统一使用当前项目主线
- 租户内业务人员可按标准物流流程操作
- 租户内角色、菜单、权限按当前项目方案落地
- 同一企业内部如有多法人，再按需启用 `multi-company`

### P1 必须坚持的对象口径

- 执行主线：`wave -> batch -> waybill -> waybill order lines`
- 追溯主线：`waybill -> trace -> evidence -> exception`

### P1 不做项

- 平台库
- 平台控制面
- 自动开租户
- 套餐与模块自动同步
- 跨租户指标汇总
- 商用运营能力

### P1 默认检查项

1. `logistics_base` 是否可在租户库稳定安装
2. `logistics_dispatch` 是否可在租户库稳定安装
3. 业务对象是否仍按当前主线运行
4. 证据是否仍围绕 `trace_event`
5. 异常是否仍优先挂在运单 / 批次 / 留痕事件
6. 租户内角色组、菜单和页面权限是否成立

## 默认工作方式

1. 先确认当前任务属于 `P0` 还是 `P1`
2. 先区分“企业隔离”和 `multi-company`
3. 先检查是否会破坏现有物流主线
4. 只在 `P0/P1` 范围内拆任务
5. 如需求开始涉及平台控制面或套餐系统，主动提示已越到 `P2/P3`
6. 实施或文档更新后同步记录 `docs/change_notes/`

## 何时先补文档再编码

遇到下面任一情况，默认先补文档：

- 需要从 `P1` 继续走向 `P2`
- 需要定义平台侧表、租户主档、任务状态机
- 需要定义套餐能力层、能力快照或到期策略
- 需要定义跨租户汇总口径
- 需要把页面权限层和套餐能力层一起说清

## 实现边界提醒

1. 企业分离不是 `multi-company`
2. 页面隐藏只能作为体验层，不是最终安全边界
3. 不要把平台侧表和租户侧表混成一层
4. 套餐与模块的映射应配置化，不要写死在页面逻辑里
5. 关键动作仍应在模型层再次校验能力和权限

## 何时提示用户暂缓实现

如果当前同时满足下面任一情况，应明确告诉用户先不要直接开做：

- 企业分离目录还没有进入接口、权限、实施、验收细稿
- 任务已经明显落到 `P2/P3`
- 当前物流主线实现本身还未稳定
- 团队还没有验证多数据库底盘

## 最低验证清单

完成 `P0/P1` 范围内工作后，至少回扫下面几件事：

1. 是否仍坚持数据库级企业隔离
2. 是否没有把 `multi-company` 用成企业隔离替代方案
3. 是否没有重起另一套业务主对象体系
4. 是否没有提前引入平台控制面和商用能力
5. 是否已更新相关设计文档和 `docs/change_notes/`
