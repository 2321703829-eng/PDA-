# odoo-security-baseline

## Purpose

为 Odoo 物流项目提供一套够用、可落地的安全基线，重点覆盖：

- controller / API
- 上传与图片证据
- 权限、记录规则、`sudo`
- SQL 与外部输入
- 配置、密钥、访问凭证

这个 skill 不追求抽象的“安全口号”，而是帮助在真实开发里尽早挡住高风险错误。

## Use When

- 新增或修改 controller / API
- 文件上传、图片预览、对象存储访问
- 权限组、访问控制、记录规则
- 使用 `sudo()`、原生 SQL、外部 HTTP 调用
- 登录、令牌、访问 key、签名 URL
- 用户明确要求做安全 review

## Core Standard

默认遵守 6 条底线：

1. 所有外部输入都不可信。
2. 服务端权限判断不能交给前端。
3. `sudo()` 只能最小化使用，并说明原因。
4. 不在代码、文档、日志里泄露密钥和敏感值。
5. 上传、下载、预览都要校验访问范围。
6. 真实风险优先于“写起来方便”。

## Workflow

### 1. Identify the risk surface

先判断本次改动涉及哪些风险面：

- 用户输入
- 文件上传
- 图片访问
- 记录权限
- 企业隔离
- SQL 查询
- 第三方服务调用
- 配置 / 密钥 / access key

### 2. Apply baseline checks

#### Input and request validation

- 不信任前端传入的 `user_id`、`company_id`、`employee_id`、状态值、对象 ID。
- 对 query、body、文件名、类型、大小做白名单或边界校验。
- 不要把“前端已校验”当成服务端不校验的理由。

#### Permission and `sudo`

- 默认先用正常权限路径实现。
- 使用 `sudo()` 前先回答：
  - 为什么必须提权
  - 提权范围能否缩小
  - 提权后是否仍做业务范围校验
- 涉及企业隔离、客户隔离、仓库隔离时，重点检查记录规则是否被绕过。

#### SQL and data access

- 能用 ORM 就优先用 ORM。
- 必须写 SQL 时：
  - 参数化，不拼接用户输入
  - 明确 where 条件和权限边界
  - 不因为性能理由直接跳过访问控制思考

#### Upload and image evidence

- 校验文件类型、大小、扩展名和实际用途。
- 不把上传文件名直接当存储路径。
- 对图片访问 key、下载 URL、预览接口，检查是否存在越权读取风险。
- 结合当前项目基线：
  - 生产规模证据图片优先元数据加对象存储方向
  - 不把长期大体量图片二进制继续堆到默认附件方案里

#### Secrets and config

- 不硬编码 AK/SK、token、密码、签名 key。
- 不把真实密钥写进：
  - 代码
  - 文档
  - 示例请求
  - 日志
- 调试日志里避免输出完整 access key、手机号、证件号、签名串。

#### Error exposure

- 对外接口错误信息避免暴露：
  - 绝对路径
  - SQL 细节
  - 栈追踪
  - 内部对象存储 bucket/key
- 用户可见报错应偏业务化，技术细节留服务端日志。

### 3. Verify the security path

至少确认：

- 普通用户不能读写不该访问的记录
- 上传非法文件会被拒绝
- 图片或附件访问链接不会越权
- 提权路径仍受业务边界控制
- 日志里没有明显泄露敏感值

## Checklist

- 是否信任了前端传来的身份或权限字段
- 是否有不必要的 `sudo()`
- 是否拼接了 SQL / 路径 / shell 风格字符串
- 是否缺少上传类型或大小校验
- 是否暴露了对象存储访问细节
- 是否把真实凭证写入代码或文档
- 是否需要同步企业隔离相关文档或 skill

## Output Expectation

使用这个 skill 时，至少要给出：

- 本次改动的主要风险面
- 实际风险点和优先级
- 最小修复建议
- 最小验证步骤
