# structured-requirement-review

## Purpose

对当前项目里的需求文档、结构化 PRD、设计草案或任务规格做质量评审，优先找出那些会让后续方案、实现、联调或验收跑偏的问题。

这个 skill 不是做“是否值得做”的产品决策评判，而是检查需求本身是否已经清楚、完整、可实现、可验证，是否足够支撑后续 `Understand -> Spec -> Plan -> Implement -> Verify -> Document`。

## Use When

- 用户要求“评审需求”“review PRD”“检查规格质量”
- 已经写出需求文档，但还没进入技术方案或编码
- 一个需求会影响模型、状态、接口、页面、导入导出或业务流程
- 团队想判断当前规格是否够稳定，能不能继续往下走
- 需要在实现前尽量减少返工和反复补定义

## Trigger Phrases

出现下面这类话时，优先考虑用这个 skill：

- “review 一下这份需求 / PRD”
- “这份规格现在能不能开始开发”
- “帮我看还缺什么定义”
- “检查一下验收和边界是不是够清楚”
- “先做需求质量评审，不要直接写方案”

## Not For

下面这些情况，优先不要用这个 skill：

- 重点是检查 spec、代码、change note 是否一致
- 重点是写技术方案而不是审需求
- 只是做模块概览或 onboarding 文档

## Core Standard

默认遵守 6 条评审基线：

1. 先按需求质量评审，再谈实现细节。
2. 先报缺陷和风险，再给概括总结。
3. 只报有文档证据的问题，不报空泛猜测。
4. 评审重点是清晰度、完整度、边界和可验证性。
5. 不把 Odoo 实现细节提前塞进本应保持业务层的需求里。
6. 评审结论要能回答“现在能不能继续做方案或开发”。

## Review Dimensions

默认重点检查 8 个维度：

- 完整性：主流程、异常流程、角色、条件、限制是否缺项
- 无歧义性：术语、规则、时间条件、数量条件是否可能被多种理解
- 一致性：文档内部定义是否自洽，是否和现有项目基线冲突
- 可验证性：验收条件是否可测、可演示、可判定通过或失败
- 可行性：在当前 Odoo 与项目边界下是否存在明显实现阻塞
- 必要性：内容是否真的服务当前目标，还是把后续阶段内容提前混入
- 技术无关性：需求层是否过度指定实现细节
- 可追踪性：目标、规则、验收与对象之间是否能对应起来

## Workflow

### 1. Lock the review target

先明确本轮评审对象：

- 是需求摘要、结构化需求、PRD，还是设计草案
- 目标功能或模块是什么
- 当前处于方案前、开发前，还是变更后的复审

### 2. Read with the project baseline

评审时至少对照：

- `AGENTS.md`
- `docs/context/`
- `docs/architecture/ARCHITECTURE.md`
- 相关设计说明

如果规格与当前主线 `wave -> batch -> waybill -> trace -> evidence -> exception` 明显偏离，要单独指出。

### 3. Inspect requirement quality

按 8 个维度逐项检查，重点追问：

- 有没有漏掉关键角色、前置条件、异常分支
- 有没有模糊词，比如“尽快”“适当”“必要时”
- 有没有把主对象和从属对象说混
- 有没有验收标准写成无法判定的口号
- 有没有把实现方案误写成需求本身

### 4. Classify the findings

把问题分成三类：

- 阻塞型：不修就不适合继续进方案或开发
- 重要型：会明显增加误解、返工或联调成本
- 优化型：不影响主流程，但值得收口

### 5. Make a gate decision

最后至少给出一个门禁判断：

- 可继续：当前规格可以继续进下一步
- 有条件继续：先修关键问题再继续
- 不建议继续：规格仍不稳定，应先补需求

## Suggested Output Template

默认按下面顺序输出：

1. Findings
2. Gate Decision
3. Missing or Ambiguous Areas
4. Suggested Fixes
5. Short Summary

每条 finding 至少尽量包含：

- 严重级别
- 文档位置
- 问题是什么
- 为什么会阻塞或增加返工
- 建议怎么改写

## Checklist

- 是否说明了评审对象和当前阶段
- 是否按完整性、歧义、一致性、可验证性几个核心维度检查
- 是否指出了和项目基线冲突的地方
- 是否区分了阻塞型、重要型、优化型问题
- 是否明确给出继续 / 有条件继续 / 不建议继续
- 是否让结论足够支撑下一步方案或开发

## Output Expectation

使用这个 skill 时，最终结果至少要让团队快速知道：

- 这份需求现在是否足够稳定
- 哪些问题最容易造成后续返工
- 最小修正动作是什么
- 修完后是否可以继续往方案或实现推进
