## 1. 文档定位

本方案是老板追溯界面的现行正式稿。

它用于统一回答下面这些问题：

1. 老板页与管理员后台的本质区别是什么
2. 老板应该先看哪些摘要、再看哪些证据、最后在哪个页面做决策判断
3. 风险摘要、争议对象、关键证据、决策记录如何组织成稳定的老板阅读链
4. 哪些老板视角页面属于一期必须具备的最小可用能力
5. 这套方案如何落到 Odoo 的看板、卡片、摘要页和必要的下钻入口上

本方案不是管理员后台的简化版，也不替代看板草案、字段清单和接口清单。

它的作用是：

- 作为老板视角的总方案正文
- 作为老板总览、争议对象、证据摘要、决策记录的上游说明
- 作为管理层评审与前后端对齐时的范围基线

## 3. 目标与边界

### 3.1 Outcome

老板进入界面后，应能稳定完成这条主链：

`看风险总览 -> 找到争议对象 -> 看关键证据摘要 -> 做责任判断 -> 留下决策记录`

### 3.2 Behavior

老板页必须优先支持：

1. 在总览层快速看到今天整体风险结构
2. 快速定位最值得关注的争议对象
3. 直接查看关键证据摘要，而不是被迫先读完整时间线
4. 必要时下钻运单、异常或批次详情继续核实
5. 在结论足够时记录判断和跟进意见

### 3.3 Boundary

本方案明确不承担：

- 日常运营处理
- 大量状态流转
- 完整时间线主阅读
- 资源管理、规则配置、执行组织管理
- 大而全 BI 平台

本方案也不把下面内容作为老板页的主阅读入口：

- 待办事项长列表
- 技术字段明细
- 大量编辑表单
- 全量原始证据列表

## 4. 设计前提

老板追溯界面必须统一接受以下判断：

1. 老板的核心价值是“判断、决策、追责”，不是“运营、处理、协调”。
2. 老板进入后台，不应先看到待处理清单，而应先看到风险摘要和争议焦点。
3. 老板的判断链必须是：
   - 先看结论摘要
   - 再看争议对象
   - 再看关键证据链
   - 最后才决定是否需要下钻原始过程
4. 老板页和管理员页共享同一套事实来源，但不是同一套阅读密度和动作密度。
5. 老板页必须明显比管理员页更“结论优先”和“证据摘要化”。

---

## 5. 与管理员后台的关键差异

| 维度 | 管理员后台 | 老板追溯界面 |
|---|---|---|
| 核心价值 | 追溯、处理、协调 | 判断、决策、追责 |
| 第一眼内容 | 待处理事项、最新留痕 | 风险摘要、争议对象、关键证据 |
| 证据呈现 | 完整时间线 + 原始证据 | 关键证据摘要 + 焦点对比 |
| 默认动作 | 标记处理中、添加备注、状态变更 | 记录判断、标记已核实、指派跟进 |
| 信息密度 | 中高 | 低到中 |
| 默认下钻 | 先进入详情看过程 | 先看结论，不够再下钻详情 |

结论：

- 老板页不是管理员工作台的压缩版
- 管理员页也不是老板页的明细页
- 两者共享事实来源，但服务完全不同的阅读阶段

## 6. 页面结构模型

老板页的核心页面统一按下面四层组织：

### 6.1 风险摘要层

用于回答：
- 当前整体风险怎么样

典型信息：
- 今日争议数
- 证据不足对象数
- 高风险批次数
- 闭环率
- 风险趋势

主要服务：
- 老板总览页
- 摘要卡区

### 6.2 争议对象层

用于回答：
- 最值得关注的对象是哪些

典型信息：
- 对象编号
- 争议焦点
- 风险等级
- 责任线索摘要
- 最近更新时间

主要服务：
- 争议对象列表
- 高风险对象排行

### 6.3 关键证据层

用于回答：
- 关键证据是否足够支撑判断

典型信息：
- 关键节点图
- 双方证据摘要
- 证据完整度
- 关键留痕摘要

主要服务：
- 争议详情页
- 关键证据摘要区

### 6.4 决策记录层

用于回答：
- 老板做了什么判断

典型信息：
- 当前判断结论
- 决策备注
- 决策时间
- 跟进要求

主要服务：
- 决策记录区
- 已核实对象视图

## 7. 模块边界与依赖

### 7.1 依赖的自定义模块

老板页主要依赖：

- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- `logistics_trace_dashboard`

其中分工为：

- `logistics_dispatch` 提供批次、运单等执行上下文
- `logistics_trace_core` 提供关键事实来源
- `logistics_trace_evidence` 提供关键证据来源
- `logistics_trace_exception` 提供争议对象与问题状态
- `logistics_trace_dashboard` 提供聚合摘要、看板与排行入口

### 7.2 依赖的 Odoo 原生能力

老板页优先复用：

- `menu`
- `act_window`
- `kanban`
- `tree/list`
- `form`
- `search view`
- 轻量图表容器
- 轻量摘要卡与下钻入口

默认原则：

1. 老板页优先用看板和摘要卡承接聚合信息
2. 老板页只在必要时下钻到标准详情页
3. 先聚合摘要，再进入事实阅读
4. 不把老板页做成完整运营控制台

## 8. 信息架构与菜单口径

当前系统级菜单按统一口径组织，但老板视角建议单独保留一组稳定入口：

```text
老板追溯
├─ 总览看板
├─ 争议对象
├─ 关键证据摘要
└─ 决策记录
```

补充约定：

- 一期优先落稳 `总览看板` 和 `争议对象`
- `关键证据摘要` 和 `决策记录` 可先以页内区块或下级页面承接
- 老板视角不直接承接全量菜单体系，而是承接高价值决策入口

## 9. 页面体系与优先级

### 9.1 P0

P0 目标是先形成最小可用的争议决策入口。

必须先做：

1. 老板总览页
2. 争议对象列表页
3. 总览卡区的稳定下钻
4. 关键证据摘要区的基础形态

### 9.2 P1

P1 目标是补齐老板视角的完整判断能力。

建议补做：

1. 争议详情页
2. 决策记录区
3. 关键证据摘要页或独立页
4. 高风险批次与证据不足对象的专题入口

### 9.3 P2

P2 再考虑增强型趋势与复盘能力。

后续再做：

1. 风险趋势看板
2. 历史决策追溯页
3. 更细粒度对象排行
4. 更完整的闭环效率分析

## 10. 核心阅读路径

### 10.1 决策主路径

```text
老板总览
  -> 争议对象列表
  -> 争议详情
  -> 关键证据摘要
  -> 决策记录
```

### 10.2 必要下钻路径

```text
争议详情
  -> 运单详情
  -> 异常详情
  -> 批次详情
```

设计原则：

- 老板总览负责“先看哪类风险”
- 争议详情负责“是否已经足够判断”
- 管理员详情负责“如果不够，需要回到哪里看原始过程”

---

## 11. 页面分区原则

### 11.1 老板总览页

老板总览页应优先承接：

1. 顶部筛选区
2. 结论卡区
3. 重点争议对象列表
4. 关键证据链摘要区
5. 风险分布摘要区
6. 最近变化区

它的目标不是展示很多图，而是让老板在 10 秒内知道今天最该看什么。

### 11.2 争议对象列表页

列表页应优先支持：

- 按风险等级默认排序
- 简明的争议摘要
- 双方证据摘要或完整度
- 一键进入争议详情

它不应承担：

- 复杂批量操作
- 过深的高级筛选
- 技术字段阅读

### 11.3 争议详情页

争议详情页统一按下面顺序组织：

1. 争议摘要区
2. 关键证据对比区
3. 责任判断区
4. 决策记录区
5. 必要的管理员页下钻入口

它必须先帮助老板形成结论，而不是先堆满原始过程。

## 12. 看板与老板页的关系

老板页不是独立漂浮的一套页面，它需要吸收统计与看板模块中最适合老板的聚合能力。

当前最适合接入老板页的看板内容包括：

- 物流留痕看板中的证据完整度与高风险对象排行
- 异常分析看板中的异常结构、高风险对象、闭环效率

当前推荐关系：

1. 老板总览页吸收看板中的高价值摘要卡与排行
2. 争议对象页负责把聚合结果转化成可判断对象
3. 真正的趋势分析和更宽视角统计仍保留在统计与看板模块

换句话说：

- 老板页优先是“决策入口”
- 看板页优先是“聚合观察入口”

## 13. 搜索、筛选与动作口径

### 13.1 默认筛选项

老板页优先保留下面这组筛选：

- 时间范围
- 风险等级
- 对象类型
- 区域
- 证据完整度

默认不建议暴露过多技术筛选项。

### 13.2 默认关注对象

老板页优先看：

- 当前争议对象
- 高风险批次
- 证据不足对象
- 最近风险升级对象

### 13.3 页面主动作

统一优先保留下面这组动作：

- 查看争议详情
- 查看关键证据
- 查看管理员详情
- 记录判断
- 标记已核实
- 指派跟进

动作原则：

1. 主动作尽量控制在 1 到 3 个
2. 决策动作优先于状态流转动作
3. 只在信息足够时才允许做判断记录

## 14. 权限与角色口径

老板页主要服务：

- 老板
- 管理层
- 高权限复核人员

当前推荐口径：

1. 老板页默认比管理员页更少动作、更少可编辑区
2. 没权限的角色不应看到老板页主入口
3. 老板页可以查看摘要，但不默认拥有日常运营处理权限
4. 决策记录动作必须有明确角色控制

## 15. 后端依赖、聚合字段与 SQL 结论

### 15.1 依赖的核心能力

老板页最依赖的不是完整事实列表，而是：

- 稳定的聚合指标
- 可信的对象摘要
- 可解释的关键证据摘要
- 清晰的下钻路径

### 15.2 一期推荐结论

当前推荐：

1. 老板总览优先依赖聚合字段和摘要接口
2. 争议对象列表优先依赖高价值预聚合字段
3. 关键证据摘要允许使用受控增强接口
4. 一期先不额外引入复杂 SQL 物化层
5. 如果排行和筛选性能不足，再补索引和受控聚合方案

### 15.3 必须先稳定的聚合方向

一期必须优先稳定：

- 待处理争议数
- 证据不足对象数
- 高风险批次数
- 异常闭环率
- 争议对象风险摘要
- 关键证据完整度摘要

### 15.4 索引与查询性能关注点

优先关注：

- 异常编号
- 运单号
- 批次号
- 风险等级
- 状态与时间范围组合

## 16. Odoo 落地方式

当前最推荐的落地方式是：

1. 老板总览页：看板页或聚合首页承接
2. 争议对象列表页：精简列表页或摘要列表页承接
3. 争议详情页：详情页 + 证据摘要区 + 决策记录区
4. 管理员页下钻：复用现有 Odoo 详情页和动作跳转

明确不建议的一期做法：

- 直接做成复杂 BI 门户
- 在老板页承接完整运营处理动作
- 把老板页和管理员页做成一套无区别页面

---

## 17. 当前不做范围

当前明确不纳入老板页主范围：

- 日常运营处理入口
- 大量状态机流转
- 完整时间线主阅读
- 深度技术排错信息
- 大而全统计平台

---

## 18. 当前结论

老板追溯界面的现行正式口径可以收敛成一句话：

**围绕争议对象和关键证据，把老板总览、争议对象、关键证据摘要、决策记录串成一个以结论优先的决策闭环。**

一期先把风险摘要和争议入口做稳，二期再补齐更完整的证据摘要、趋势分析与历史决策追溯。
