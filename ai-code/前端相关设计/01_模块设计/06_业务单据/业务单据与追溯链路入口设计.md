# 业务单据与追溯链路入口设计

适用范围：
- `ai-code/前端相关设计/` 下业务单据到物流追溯主链的入口与跳转设计
- 销售订单、采购订单、出入库单据与 `批次 / 运单 / 留痕 / 异常` 之间的入口规则统一

优先基准：
- `业务单据前端接入设计草案.md`
- `仓储管理前端接入设计草案.md`
- `系统页面关系总览.md`

关联文档：
- `前端模块结构与菜单总表.md`
- `后台按波次批次运单追溯页面设计.md`
- `留痕与追溯模块前端设计草案.md`
- `异常中心前端设计草案.md`

---

## 1. 文档定位

这份文档不再讨论“业务单据模块是什么”，而是专门解决入口规则的统一问题。

它主要回答下面这些问题：

1. 从哪类业务单据，优先跳到哪个目标对象
2. Smart Button 和关联入口应该如何分层
3. 动作命名如何统一
4. 跳转时需要传哪些上下文
5. 目标页打开后默认应该看到什么
6. 用户从追溯页回看来源单据时，应该如何保留路径感

这份文档的作用是：

- 给后续 `Smart Button设计清单.md` 提供母规则
- 给 Odoo 动作、按钮、上下文命名提供统一口径
- 避免同类入口在不同页面各写各的

---

## 2. 总体原则

当前业务单据到追溯主链的入口设计统一按下面 7 条原则执行：

1. 来源单据不等于主对象  
   `sale.order`、`purchase.order`、`stock.picking` 都只是入口，不是追溯主对象。

2. 入口优先跳执行对象  
   业务单据优先跳到 `批次` 或 `运单`，而不是直接把用户扔进证据明细。

3. 列表优先于详情  
   当来源单据可能对应多个对象时，优先跳列表页并带默认筛选。

4. 唯一对象直达详情  
   当明确只关联单一 `批次` 或单一 `运单` 时，可以直接打开详情页。

5. 异常入口独立保留  
   即使首选跳转是 `批次/运单`，也要保留 `查看异常` 这种问题导向入口。

6. 上下文必须可回溯  
   所有入口都应保留来源单据模型和来源单据 ID。

7. 同类入口名称统一  
   不允许同一语义在不同页面出现多种按钮名字。

---

## 3. 入口分层

当前建议把业务单据到追溯链的入口分成 3 层：

| 入口层级 | 典型形式 | 作用 |
|---|---|---|
| L1 主入口 | Smart Button | 从单据详情页直接跳关键对象 |
| L2 辅入口 | 关联字段、摘要链接 | 从摘要区快速下钻 |
| L3 批量入口 | 菜单页、列表页动作、预设筛选 | 从单据列表批量反查执行链 |

推荐理解为：

- Smart Button 解决“我现在就要看相关对象”
- 摘要链接解决“我先看一眼，再决定要不要进去”
- 列表动作解决“我要批量找一类相关对象”

---

## 4. 单据到目标页的入口矩阵

## 4.1 `sale.order`

| 入口名称 | 首选目标 | 打开方式 | 适用场景 |
|---|---|---|---|
| `关联运单` | 运单追溯列表 / 运单详情 | 多对象开列表，单对象开详情 | 客户交付与履约主入口 |
| `关联批次` | 批次列表 / 批次详情 | 多对象开列表，单对象开详情 | 需要从聚合执行视角查看 |
| `查看追溯` | 运单追溯列表 | 开列表并带销售来源筛选 | 想先看整体履约状态 |
| `查看异常` | 当前异常列表 | 开列表并带销售来源筛选 | 想先看问题对象 |

当前口径：

- `sale.order` 的首选入口是 `关联运单`
- `查看追溯` 是面向阅读链的总入口
- `查看异常` 不替代 `关联运单`，但必须常驻

## 4.2 `purchase.order`

| 入口名称 | 首选目标 | 打开方式 | 适用场景 |
|---|---|---|---|
| `关联批次` | 批次列表 / 批次详情 | 多对象开列表，单对象开详情 | 入仓、收货、聚合判断主入口 |
| `关联运单` | 运单追溯列表 | 通常开列表 | 需要查看后续逐单执行情况 |
| `查看入仓追溯` | 批次列表 | 带采购来源筛选 | 先从批次看整体收货与入仓 |
| `查看异常` | 当前异常列表 | 带采购来源筛选 | 想先找异常收货对象 |

当前口径：

- `purchase.order` 的首选入口是 `关联批次`
- 采购来源更适合先落到聚合对象，再下钻运单

## 4.3 `stock.picking`

| 入口名称 | 首选目标 | 打开方式 | 适用场景 |
|---|---|---|---|
| `关联批次` | 批次列表 / 批次详情 | 多对象开列表，单对象开详情 | 作业与聚合执行对象强绑定 |
| `关联运单` | 运单追溯列表 / 运单详情 | 多对象开列表，单对象开详情 | 需要看逐单执行事实 |
| `查看追溯` | 运单追溯列表 | 带仓侧来源筛选 | 先进入阅读链 |
| `查看异常` | 当前异常列表 | 带仓侧来源筛选 | 先进入问题链 |

当前口径：

- `stock.picking` 可以并列保留 `关联批次` 和 `关联运单`
- 两者都属于主入口，不应只留其一

## 4.4 `account.move`

| 入口名称 | 首选目标 | 打开方式 | 适用场景 |
|---|---|---|---|
| `相关业务单据` | 销售/采购单据 | 开来源单据页 | 从财务回看业务来源 |
| `相关运单` | 运单追溯列表 | 列表页 | 轻量回溯使用 |
| `相关异常` | 当前异常列表 | 列表页 | 问题回溯使用 |

当前口径：

- 财务单据不作为物流链主入口
- 只保留轻量回溯能力

---

## 5. 统一入口名称规则

当前建议把业务单据层常用入口名称冻结为下面这组：

| 统一名称 | 含义 | 备注 |
|---|---|---|
| `关联运单` | 跳到当前来源单据关联的运单对象 | 主入口 |
| `关联批次` | 跳到当前来源单据关联的批次对象 | 主入口 |
| `查看追溯` | 跳到追溯主链列表视角 | 总入口 |
| `查看异常` | 跳到异常列表视角 | 问题入口 |
| `相关出入库单据` | 跳到相关 `stock.picking` | 业务到仓储入口 |
| `相关业务单据` | 从财务或辅助对象跳回来源单据 | 回溯入口 |

不推荐使用：

- `查看物流`
- `执行情况`
- `订单追踪`
- `履约详情`
- `链路详情`

原因：

- 这些名字语义容易漂移
- 会让“追溯”“执行”“异常”三条线边界变糊

---

## 6. 动作命名规则

动作命名建议继续沿用系统级规则：

```text
action_logistics_{module}_{object}_{page}
```

业务单据链路建议补齐下面这组动作：

| 目标动作 | 推荐动作名 |
|---|---|
| 销售来源跳运单列表 | `action_logistics_business_sale_waybill_list` |
| 销售来源跳批次列表 | `action_logistics_business_sale_batch_list` |
| 销售来源跳异常列表 | `action_logistics_business_sale_exception_list` |
| 采购来源跳批次列表 | `action_logistics_business_purchase_batch_list` |
| 采购来源跳运单列表 | `action_logistics_business_purchase_waybill_list` |
| 采购来源跳异常列表 | `action_logistics_business_purchase_exception_list` |
| 出入库来源跳批次列表 | `action_logistics_business_picking_batch_list` |
| 出入库来源跳运单列表 | `action_logistics_business_picking_waybill_list` |
| 出入库来源跳异常列表 | `action_logistics_business_picking_exception_list` |

命名原则：

- 动作名体现“来源语义”，不是只体现“目标语义”
- 同一目标页允许有多个来源动作，因为默认筛选不同
- 不要把所有来源都复用成一个没有上下文含义的通用动作名

---

## 7. 上下文传递规范

所有业务单据入口在跳转时，统一建议至少传下面这些上下文键：

| 上下文键 | 含义 | 使用场景 |
|---|---|---|
| `default_source_model` | 来源模型 | 所有入口必带 |
| `default_source_id` | 来源记录 ID | 所有入口必带 |
| `default_source_ref` | 来源单据编号 | 面包屑、标题提示 |
| `search_default_customer_id` | 客户默认筛选 | 销售来源入口 |
| `search_default_store_id` | 门店默认筛选 | 销售来源入口 |
| `search_default_supplier_id` | 供应商默认筛选 | 采购来源入口 |
| `search_default_picking_id` | 出入库单据默认筛选 | 仓储或库存来源入口 |
| `search_default_has_open_exception` | 未闭环异常筛选 | 异常入口 |

补充规则：

- `default_*` 主要用于 form 预填和页面来源标识
- `search_default_*` 主要用于列表默认筛选
- 如果目标页不是列表页，不要滥传无效的 `search_default_*`

---

## 8. 目标页打开规则

为了保证入口体验一致，当前建议统一按下面规则打开目标页：

| 关联对象数量 | 推荐打开方式 |
|---|---|
| 0 个 | 不跳转，提示“暂无关联对象” |
| 1 个 | 直接打开详情页 |
| 多个 | 打开列表页并带默认筛选 |

提示文案建议统一：

- `暂无关联运单`
- `暂无关联批次`
- `暂无关联异常`

不推荐：

- 没有关联对象时仍强行打开空列表
- 有多个对象时直接跳第一个详情页

---

## 9. 回跳与路径保留

业务单据入口跳入追溯页后，当前建议保留路径感，而不是只做一次性跳转。

推荐保留方式：

- 详情页标题区显示来源提示
- 面包屑中保留来源单据名称或编号
- 目标页支持 `返回来源单据`
- 详情页记录“来源于哪类单据进入”

示例：

```text
销售订单 SO20260413001
  -> 关联运单
  -> 运单详情 WB20260413008
  -> 标题区显示：来源销售订单 SO20260413001
```

这件事的价值是：

- 降低跨模块跳转后的迷失感
- 让管理人员知道当前阅读是从哪个业务上下文进入的

---

## 10. 业务单据与异常入口关系

当前建议把异常入口作为单独稳定入口保留，而不是隐藏在追溯详情之后。

推荐关系：

- `sale.order` 保留 `查看异常`
- `purchase.order` 保留 `查看异常`
- `stock.picking` 保留 `查看异常`

原因：

- 有些用户是问题导向，不是事实导向
- 他们并不想先看运单详情，再找异常
- 直接进入异常列表可以缩短处理路径

但同时要保持边界：

- `查看异常` 只是入口，不是来源单据页本身承担异常处理

---

## 11. 业务单据与仓储入口关系

当前建议把业务单据入口和仓储入口写成互补关系：

| 起点 | 更适合先去哪里 |
|---|---|
| 想看来源和履约归属 | 业务单据 |
| 想看仓侧作业事实 | 仓储页 |
| 想看执行聚合情况 | 批次页 |
| 想看逐单事实 | 运单页 |
| 想看问题处理 | 异常页 |

因此入口设计上要避免两种错误：

- 把业务单据页做成仓储页替身
- 把仓储页做成来源单据页替身

---

## 12. 统一入口实现建议

如果从实现角度拆分，当前建议按下面方式落地：

1. 用 Smart Button 承担主入口
2. 用摘要字段中的可点击数字承担辅入口
3. 用 `act_window` 承担列表和详情跳转
4. 用 `context/domain/search_default_*` 承担来源约束
5. 用详情页标题区或摘要区承接来源提示

实现优先顺序建议如下：

1. `sale.order` 的 `关联运单 / 查看异常`
2. `purchase.order` 的 `关联批次 / 查看异常`
3. `stock.picking` 的 `关联批次 / 关联运单 / 查看异常`
4. 再补辅助入口和返回来源单据入口

---

## 13. 当前阶段结论

当前这份入口设计的核心结论是：

1. 业务单据到追溯主链必须按统一入口矩阵设计，不能页面各写各的
2. `sale.order` 首选跳 `运单`，`purchase.order` 首选跳 `批次`
3. 当关联对象不唯一时，统一先开列表页并带默认筛选
4. 所有入口都应保留来源模型和来源记录上下文
5. `查看异常` 必须作为独立稳定入口保留
