# 2026-04-28 《方案 A 调整到方案 B 的影响清单与迁移步骤》

## 1. 文档定位

- 本文用于回答：如果当前先按“方案 A：子域名映射数据库”落地，后续再调整到“方案 B：单域名 + 路径前缀映射数据库”，改造范围有多大、应如何迁移。
- 本文不讨论“统一登录后按 session / cookie 动态切库”的平台化方案。
- 本文服务于当前 `P0 / P1` 的工程判断，帮助团队提前识别迁移成本与风险。

## 2. 前提定义

### 2.0 当前执行口径

当前专题已经明确：

- **本轮先采用方案 A 落地**
- **方案 B 不作为当前同步实施项**
- **本文的作用，是为后续从 A 调整到 B 提前做影响识别和迁移准备**

### 2.1 方案 A

```text
https://<tenant_code>.tianshu.cn/login_in
```

- 通过 `Host`
- 配合 `dbfilter`
- 直接命中 `tenant_<tenant_code>`

### 2.2 方案 B

```text
https://tianshu.cn/<tenant_code>/login_in
```

- 通过路径前缀识别 `<tenant_code>`
- 由网关 / 反向代理做映射
- 转发时注入 `X-Odoo-Database`
- 再把路径重写成 Odoo 实际处理路径

## 3. 总体判断

## 3.1 难度等级

当前判断：

**方案 A 调整到方案 B 属于中等难度、可控迁移。**

补充说明：

- 这里说的是“后续迁移成本”判断
- 不代表当前要并行实施 A 和 B
- 当前仍以 A 为正式落地方案，B 作为后续扩展方向

### 3.2 为什么说可控

因为 A 和 B 共享三条关键基础：

- 仍然是一租户一数据库
- 仍然保留 `tenant_code`
- 仍然要求“请求进入 Odoo 前就选好库”

因此，这次迁移主要改的是：

- 访问入口
- 反向代理 / 网关
- 外部 URL 组织方式

而不是去推翻：

- 租户库业务模型
- `trace / evidence / exception` 设计
- `waybill` 主阅读链
- 企业内权限模型

## 4. 影响清单

## 4.1 会明显受影响的部分

### 4.1.1 反向代理 / 网关配置

这是最核心的改动点。

从原来的：

- 按 `Host` 命中数据库

改成：

- 按 path 第一段识别 `<tenant_code>`
- 映射数据库
- 注入 `X-Odoo-Database`
- 重写 URL path

需要重做或补充：

- `<tenant_code>` 提取规则
- 非法租户码拦截规则
- path rewrite 规则
- header 注入规则
- 日志与排障字段

### 4.1.2 登录入口与首页入口

原来的对外入口是：

```text
https://acme.tianshu.cn/...
```

迁移后会变成：

```text
https://tianshu.cn/acme/...
```

因此需要检查：

- 登录地址
- 首页地址
- 退出后回跳地址
- 未登录重定向地址

### 4.1.3 外部跳转与绝对地址

凡是系统里自己拼出来的完整链接，都要检查。

例如：

- 登录后跳转
- 导入导出下载链接
- 图片访问链接
- 对外回调 URL
- 消息通知里的链接

### 4.1.4 静态资源与业务路径兼容性

因为方案 B 会引入路径前缀，所以要验证：

- `/web`
- `/web/login`
- `/web/assets/...`
- `/api/...`
- 图片下载路径
- 导出下载路径

是否都能在路径重写后正常工作。

### 4.1.5 运维与验收文档

原来围绕子域名的内容都要同步调整：

- `P0` 环境参数登记
- 网关部署说明
- 验收步骤
- 排障说明

## 4.2 有一定影响但不算重的部分

### 4.2.1 测试与联调用例

需要把原来“访问某个子域名”的用例改成：

- 访问统一主域名下的某个租户路径

### 4.2.2 浏览器会话与多标签页验证

方案 B 比方案 A 更需要确认：

- 同浏览器下多租户路径是否互不串库
- 重定向是否仍保留租户路径前缀

### 4.2.3 监控与日志字段

建议新增或强化：

- `tenant_code`
- 原始访问 path
- 注入后的目标数据库名

方便定位“路径识别错租户”的问题。

## 4.3 基本不需要大改的部分

以下内容通常不需要因为 A -> B 而重写：

- `tenant_code` 规则
- `tenant_<tenant_code>` 数据库命名规则
- 一租户一数据库原则
- `trace / evidence / exception` 主链设计
- `waybill` 主阅读入口
- 图片补链主逻辑
- 租户内权限设计
- `logistics_dispatch / logistics_trace_*` 业务模型

一句话说：

**进库后的业务基本不变，变的是“怎么进库”。**

## 5. 主要风险点

## 5.1 路径重写不完整

最常见风险是：

- 登录页正常
- 但后续某些链接跳回了不带租户前缀的路径

结果就是：

- 请求丢失租户上下文
- 或直接落到错误入口

## 5.2 某些代码写死了 Host 形式

如果已有代码、模板、通知、脚本写死了：

```text
https://<tenant_code>.tianshu.cn/...
```

就需要统一回扫。

## 5.3 同域多路径的 cookie / redirect 行为未充分验证

虽然方案 B 不是“登录后再切库”，但由于对外统一成单域名，仍然要特别验证：

- 登录态是否稳定
- 多租户路径并发访问是否会互相影响

## 5.4 网关层成为新关键点

方案 A 的关键点主要在：

- DNS
- `Host`
- `dbfilter`

方案 B 会把关键性更多转移到：

- 网关 path 识别
- header 注入
- rewrite 正确性

所以迁移后排障能力会更依赖网关配置质量。

## 6. 推荐迁移步骤

## 6.1 第一步：先守住不变项

迁移前先明确以下内容不改：

- `tenant_code`
- 数据库名：`tenant_<tenant_code>`
- 一租户一数据库
- 租户内业务模块与数据结构

这样后续迁移只动入口层。

## 6.2 第二步：先补方案 B 网关设计稿

在改任何配置前，先补一份方案 B 的落地规范，至少写清：

- path 前缀格式
- `<tenant_code>` 校验规则
- path rewrite 规则
- `X-Odoo-Database` 注入规则
- 非法路径返回策略

## 6.3 第三步：搭一个单租户试点

先不要全量切。

建议先选一个租户做：

- `https://tianshu.cn/acme/...`

验证：

- 登录
- `/web`
- `/api`
- 图片访问
- 导入导出

## 6.4 第四步：回扫“写死子域名”的点

按以下范围回扫：

- 前端跳转
- 控制器返回 URL
- 下载地址
- 图片地址
- 消息通知
- 脚本与运维文档

## 6.5 第五步：补专项验收

迁移到方案 B 后，专项验收至少增加：

- 路径前缀能否稳定命中数据库
- 不同租户路径是否会串库
- 不带租户前缀的访问如何处理
- 非法租户码是否被拦截
- 多标签页是否稳定

## 6.6 第六步：再决定是否全量切换

只有单租户试点稳定后，再决定：

- 全量切到方案 B
- 或保留 A/B 并行过渡期

## 7. 推荐过渡策略

当前更建议的迁移方式不是“一刀切”，而是：

### 方案一：A/B 并行短过渡

- 老租户先保留子域名入口
- 新入口同时开放路径前缀
- 逐步把使用习惯迁到路径前缀

### 方案二：先试点再整批切换

- 先选 1 个租户验证
- 再选 3~5 个租户验证
- 最后批量切换

如果团队资源有限，推荐方案二。

补充执行建议：

- 当前阶段不建议提前把 B 混入本轮 `P0 / P1` 实施
- 更推荐先把 A 跑真、跑稳、跑出真实验收记录
- 等子域名规模和运维压力接近评估阈值后，再单独启动 B 的专项迁移

## 8. 当前结论

### 8.1 能不能从 A 调到 B

能，而且是可控的。

### 8.0 当前是否现在就切到 B

当前不切。

当前执行结论是：

- 先按 A 落地
- 后续再开展 B

### 8.2 会不会很痛

不会像“统一登录后再按 session 切库”那样伤筋动骨，但也不是零成本。

### 8.3 最大工作量在哪里

最大工作量不在业务模块，而在：

- 网关
- 路径重写
- 外部 URL 回扫
- 验收与排障治理

## 9. 一句话收口

**方案 A 调整到方案 B，本质上是“入口层迁移”，不是“业务层重构”；只要提前守住 `tenant_code / 数据库命名 / 请求前选库` 这三条不变项，后续迁移是可控的。**
