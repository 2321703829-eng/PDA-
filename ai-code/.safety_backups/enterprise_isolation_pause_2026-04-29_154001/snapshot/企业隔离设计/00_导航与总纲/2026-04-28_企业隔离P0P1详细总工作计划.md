# 2026-04-28 企业隔离 `P0 / P1` 详细总工作计划

## 1. 文档定位

- 本文用于把当前企业隔离专题下已经稳定的边界、设计、落位稿、验收稿和配套执行稿，统一压成一份可直接推进的 `P0 / P1` 详细总工作计划。
- 本文服务的是当前单人推进、逐步编码、逐步联调的工作方式。
- 本文是“设计与实施版总计划”，不是精确到人天与多人排期承诺的项目计划。

本文主要回答：

- `P0 / P1` 到底要做哪些工作
- 这些工作应该按什么顺序推进
- 每一阶段依赖什么、产出什么
- 每一阶段完成后，用什么材料确认可以进入下一步

## 2. 当前计划基线

### 2.1 当前只做什么

当前总计划只覆盖：

- `P0`：多数据库底盘验证
- `P1`：现有物流模块租户化落地

### 2.2 当前明确不做什么

当前不纳入本计划主体：

- 平台库与平台侧租户主档表
- 套餐、授权、计费、到期、降级
- 平台任务中心、平台审计中心
- 跨租户汇总、运营看板、指标仓
- 自动开租户、自动绑域名、自动编排

这些内容如后续进入 `P2 / P3`，再单独起平台化工作计划承接。

### 2.3 当前统一业务口径

当前 `P1` 继续兼容以下业务基线：

- 执行与数据主链：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
- 页面主阅读入口：`waybill`
- 页面主阅读链：`waybill -> order_line`
- 图片阅读链：`waybill -> 图片预览 / 留痕 / 证据`
- 正式追溯链：`waybill -> trace_event -> evidence -> exception`
- `customer_line` 当前在“一运单一门店”强约束下，收口为兼容 / 扩展结构层，不再作为 `P1` 主阅读入口

## 3. 工作目标

### 3.1 `P0` 目标

验证数据库级企业隔离底盘在当前 Odoo 环境下稳定成立，至少保证：

- 域名到数据库一对一命中成立
- `dbfilter` 路由稳定
- 数据库列表与数据库管理入口正确收口
- 单租户库可独立安装基础物流模块
- 单租户库可独立备份与恢复

### 3.2 `P1` 目标

让每个租户数据库都能运行同一套现有物流系统，并在当前强约束下保证：

- `waybill` 稳定承担主阅读入口
- `trace / evidence / exception` 三层可安装、可读取、可联动
- 图片命中、补链、异常闭环不打坏当前主对象口径
- 租户内权限、页面职责、联调顺序和验收边界清晰

## 5. 总体推进顺序

当前建议固定按下面顺序推进：

1. `P0` 路由与底盘验证
2. `P0` 真实环境登记与验收记录沉淀
3. `P1` 模块安装与主链回扫
4. `trace_core`
5. `evidence`
6. `exception`
7. 页面职责与权限收口
8. 三层联动回归
9. `P1` 首轮验收与回归记录沉淀

## 6. `P0` 工作包

### 6.1 `P0-A` 命名与路由准备

工作内容：

- 确认 `tenant_code`
- 确认数据库命名
- 确认主访问域名
- 确认域名与数据库一对一映射
- 确认 `dbfilter` 规则
- 如主管不接受多子域名，补做“路径前缀 -> 网关选库 -> X-Odoo-Database”方案评估与定稿

主要输入：

- `P0` 命名 / 域名 / `dbfilter` 规范
- `P0` 环境参数样例稿
- `P0` 路由选库方案对比与推荐说明

主要输出：

- 真实环境参数登记单
- 域名、数据库、`tenant_code` 映射登记

完成标准：

- 域名、数据库、`tenant_code` 可人工逆推

### 6.2 `P0-B` 访问链路验证

工作内容：

- 反向代理配置
- `Host` 透传
- 租户域名访问测试
- 未登记域名 / 非法域名行为确认

主要输出：

- 访问验证记录

完成标准：

- 域名稳定命中正确数据库
- 不出现串库

### 6.3 `P0-C` 选库入口收口

工作内容：

- 数据库列表关闭确认
- 数据库管理入口收口确认
- 普通用户不依赖手工选库

主要输出：

- 入口收口确认记录

完成标准：

- 正式链路下不可误选库

### 6.4 `P0-D` 单库安装与恢复验证

工作内容：

- 手工建库或确认目标库
- 安装 `logistics_base`
- 安装 `logistics_dispatch`
- 单库备份验证
- 单库恢复验证

主要输出：

- 单库安装记录
- 备份恢复记录

完成标准：

- 租户库可独立安装、登录、恢复

### 6.5 `P0-E` 首轮验收记录沉淀

工作内容：

- 回写通过项
- 回写待修项
- 回写阻塞项
- 明确是否允许进入 `P1`

主要输出：

- `P0` 首轮真实验收记录

完成标准：

- 明确给出“是否进入 `P1`”结论

## 7. `P1` 工作包

### 7.1 `P1-A` 主链与模块基础回扫

工作内容：

- 安装 `logistics_trace_core`
- 安装 `logistics_trace_evidence`
- 安装 `logistics_trace_exception`
- 回扫 `waybill / customer_line / order_line / goods_line`
- 确认主阅读入口仍为 `waybill`

主要输出：

- 模块安装记录
- 主链回扫记录

完成标准：

- 三个模块可在租户库独立安装和读取

### 7.2 `P1-B` `trace_core`

工作内容：

- 校对 `trace_event` 主挂点
- 补 `waybill` 留痕摘要字段
- 补 `waybill` 留痕查询与查看入口
- 校对 `batch / waybill / trace_event` 回跳链
- 收口留痕角色边界

主要输入：

- `trace` 细稿
- `waybill` 摘要区落位稿
- 权限落位表
- 模块级改动清单

主要输出：

- 留痕实现变更
- 留痕联调记录

完成标准：

- `waybill` 留痕摘要与入口稳定
- `trace_event` 正式对象归属不被带偏

### 7.3 `P1-C` `evidence`

工作内容：

- 补图片命中规则
- 补 `image_package` 导入与结果链
- 补 `image_package -> trace_event` 正式补链
- 补证据预览 / 导出 / 审计权限边界
- 收口 `waybill` 证据摘要区与入口

主要输入：

- `evidence` 细稿
- 图片命中与补链字段落位稿
- 字段与动作命名统一表
- 权限落位表

主要输出：

- 图片包与证据链实现变更
- 证据联调记录

完成标准：

- 图片可命中、可补链、可在 `waybill` 主阅读入口稳定回读

### 7.4 `P1-D` `exception`

工作内容：

- 校对异常状态流转
- 补异常详情反读留痕与证据
- 收口 `waybill` 异常摘要区
- 收口异常提报 / 跟进 / 关闭 / 只读边界

主要输入：

- `exception` 细稿
- `exception` 模型级约束稿
- 权限落位表

主要输出：

- 异常实现变更
- 异常联调记录

完成标准：

- 异常能在 `waybill` 主阅读入口下形成最小闭环

### 7.5 `P1-E` 页面职责收口

工作内容：

- 依据页面职责分工表回扫页面
- 确认 `batch / waybill / customer_line / order_line / trace_event / evidence / exception` 职责不串位
- 确认 `customer_line` 仍为结构层，不再误抬成主阅读入口

主要输出：

- 页面职责回扫记录

完成标准：

- 主阅读入口、详情页、回跳链全部与现行设计一致

### 7.6 `P1-F` 权限收口

工作内容：

- 依据权限复用对照表和权限分组建议稿收口
- 保留现有可复用组
- 收口 `base.group_user` 过宽写权限
- 补当前 `P1` 需要的轻量角色与能力组
- 补页面层 / 接口层 / 模型层三层校验一致性

主要输出：

- 权限调整记录
- access / rule / 页面显隐收口记录

完成标准：

- 当前租户内角色边界清楚，且不过度扩张到 `P2 / P3`

### 7.7 `P1-G` 三层联动回归

工作内容：

- 联调 `trace -> evidence -> exception`
- 验证 `waybill -> 留痕 / 图片预览 / 证据 / 异常`
- 验证权限、页面职责、对象归属没有互相打架

主要输入：

- 联调用例包
- 回归检查表

主要输出：

- 三层联动回归记录

完成标准：

- 三层链路完整成立

### 7.8 `P1-H` 首轮验收记录沉淀

工作内容：

- 回写通过项
- 回写待修项
- 回写阻塞项
- 给出是否允许进入下一轮业务联调或试运行的结论

主要输出：

- `P1` 首轮真实验收记录
- 每轮提交后的回归检查记录

完成标准：

- 形成清晰的阶段结论

## 8. 关键依赖

### 8.1 `P0 -> P1`

若以下条件未成立，不建议进入 `P1`：

- 域名命中数据库不稳定
- 数据库列表 / 数据库管理入口未收口
- 单库安装链路没跑通
- 备份恢复链路没跑通

### 8.2 `trace -> evidence -> exception`

若以下条件未成立，不建议继续后续模块：

- `trace_event` 归属未稳，不进入 `evidence`
- 图片命中与补链未稳，不进入 `exception`
- 权限边界未稳，不进入最终三层联动回归

## 10. 建议推进节奏

### 10.1 第一轮

- 先把 `P0` 跑真
- 先沉淀真实环境登记和 `P0` 验收记录

### 10.2 第二轮

- 先稳 `trace`
- 再稳 `evidence`
- 再稳 `exception`

### 10.3 第三轮

- 收页面职责
- 收权限边界
- 做三层联动回归

### 10.4 第四轮

- 回写 `P1` 首轮真实验收记录
- 形成是否继续扩展的结论

## 11. 当前最大风险点

- `P0` 如果没有真实环境登记和真实验收记录，后面的 `P1` 会建在未验证底盘上。
- `image_package` 如果补链没落稳，证据链和异常链都会反复返工。
- 权限如果一开始做得过细，开发与联调工作量会快速膨胀。
- 页面职责如果不回扫，旧口径会继续混入当前实现。

## 12. 当前建议

当前最推荐的推进方式不是把全部工作一次铺满，而是：

1. 先拿一个真实租户跑通 `P0`
2. 再拿这个租户跑第一轮 `P1`
3. 每轮提交后用回归检查表短回扫
4. 把真实环境参数、验收记录和待修项持续回写下来

## 13. 一句话结论

当前企业隔离专题已经足够支撑一份完整的 `P0 / P1` 总工作计划；接下来真正关键的，不是再补大方向，而是按这份计划把 `P0` 跑真、把 `P1` 跑顺、把回归与验收记录沉淀下来。

## 14. 当前阶段口径更新

### 14.1 `image_package` 口径更新

- `image_package` 从“待加强主缺口”调整为“当前已满足 `P1`，后续可选增强项”。
- 当前已实现并完成首轮人工回归的范围包括：
  - 图片包导入
  - 运单命中
  - 正式补链到 `trace_event -> evidence`
  - 失败记录
  - 基本重试
  - 导入中心接入

因此，当前计划不再把 `image_package` 的增强型能力作为下一轮主推进项。

### 14.2 当前下一步重点

按当前阶段收口，下一步工作重点调整为：

1. 企业隔离 `P0` 正式部署
2. 企业隔离 `P0` 正式验收
3. `P1` 与正式 `P0` 入口联动后的最终收口

### 14.3 当前不再优先推进的增强项

- 图片包人工复核台账增强
