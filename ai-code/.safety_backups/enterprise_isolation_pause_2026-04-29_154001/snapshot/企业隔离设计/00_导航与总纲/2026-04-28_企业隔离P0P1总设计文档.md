# 2026-04-28 企业隔离 `P0 / P1` 总设计文档

## 1. 文档定位

- 本文是当前企业隔离专题的现行总设计文档。
- 本文用于把已经分散在总纲、`P0` 规范、`P1` 细稿、权限稿、执行稿、联调稿中的有效结论统一收口。
- 本文不替代细稿、实施清单、验收清单和工作计划，而是作为它们的统一入口与统一口径说明。

## 2. 当前范围

### 2.1 当前只做什么

当前只覆盖两期：

- `P0`：多数据库企业隔离底盘验证
- `P1`：现有物流模块租户化落地

### 2.2 当前明确不做什么

当前不纳入本期主体：

- 平台库与平台侧租户主档
- 套餐、授权、计费、到期、降级
- 平台任务中心、平台审计中心
- 跨租户汇总、运营看板、指标仓
- 自动开租户、自动绑域名、自动编排

这些内容后续如进入 `P2 / P3`，再单独起平台化设计承接。

## 3. 当前统一基线

### 3.1 企业隔离原则

- 企业之间：数据库级强隔离
- 同一企业内部多法人协同：才考虑 `multi-company`
- 不另起一套新的 `tms_*` 业务体系
- 物流核心能力继续由当前自定义模块承接

### 3.2 当前业务主链

- 执行与数据主链：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
- 正式追溯主链：`waybill -> trace_event -> evidence -> exception`
- 当前正式追溯主对象：`waybill`

### 3.3 当前阅读链

- 页面主阅读入口：`waybill`
- 页面主阅读链：`waybill -> order_line`
- 图片主阅读链：`waybill -> 图片预览 / 留痕 / 证据`

补充说明：

- `customer_line` 继续保留在数据结构中
- 在“一运单一门店”强约束下，`customer_line` 当前收口为结构 / 快照 / 命中辅助层
- `customer_line` 不再承担当前 `P1` 主阅读入口职责
- `trace_event` 仍是正式留痕事件锚点

### 3.4 当前模块边界

当前现行模块方向：

- `logistics_base`
- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`

## 4. `P0` 总设计

### 4.1 `P0` 目标

`P0` 只回答一个问题：

**数据库级企业隔离在当前 Odoo 环境下能不能稳定成立。**

### 4.2 `P0` 的 OBB

`Outcome`

- 至少 1 个示例租户库可通过独立访问链稳定进入
- 同一套 Odoo 服务可承接多租户数据库且不串库
- 运维可手工完成建库、装模块、初始化、备份和恢复

`Behavior`

- 外部访问通过域名命中数据库
- 数据库列表与数据库管理入口在正式链路下默认关闭
- 备份恢复把数据库与相关文件存储视为成对对象处理

`Boundary`

- 不要求平台化租户编排
- 不要求自动建库、自动装模块、自动绑域名
- 不要求平台任务、套餐、授权和平台审计

### 4.3 `P0` 路由口径

当前正式口径：

- **当前先采用方案 A**
- 方案 A：`子域名 -> dbfilter -> 数据库`
- **方案 B 后续再开展**
- 方案 B：`单域名 + 路径前缀 -> 网关映射 -> X-Odoo-Database`

当前不采用统一登录后再靠 session / cookie 动态切库的方案。

### 4.4 `P0` 命名与映射口径

- `tenant_code`：稳定技术编码，不等于企业显示名
- 数据库命名：`tenant_<tenant_code>`
- 访问域名：`<tenant_code>.<base_domain>`
- 当前推荐 `dbfilter` 方向：与租户子域直接对应

当前还需要持续回填真实环境参数：

- `tenant_code`
- 数据库名
- 域名
- `dbfilter`
- 环境说明
- 备份恢复记录

## 5. `P1` 总设计

### 5.1 `P1` 目标

让每个租户数据库都能运行同一套现有物流系统，并形成：

- 可安装
- 可读取
- 可联动
- 可回归
- 可验收

的最小闭环。

### 5.2 `P1` 的 OBB

`Outcome`

- 租户库内主链、留痕、证据、异常可独立运行
- `waybill` 稳定承担当前 `P1` 主阅读入口职责
- 三层联动、页面职责和租户内权限边界清晰

`Behavior`

- `waybill` 承担留痕摘要、证据摘要、异常摘要和主回跳入口
- 图片导入先做结构命中，再补链到正式 `trace_event`
- 异常继续围绕 `waybill / batch / trace_event` 流转
- 页面层、接口层、模型层共同承接权限校验

`Boundary`

- 不把 `customer_line` 重新抬成主阅读入口
- 不改变 `trace_event` 和 `evidence` 的正式主挂点
- 不把异常扩成完整工单平台
- 不扩展到平台级跨租户权限和套餐能力

### 5.3 `trace / evidence / exception` 口径

`trace`

- `trace_event` 继续围绕 `batch_id / waybill_id`
- `waybill` 承担留痕摘要与入口
- `batch / waybill / trace_event` 三层形成稳定联动

`evidence`

- 图片主阅读继续围绕 `waybill`
- 证据正式挂点继续围绕 `trace_event`
- `image_package` 与 `dispatch_main` 审计链保持分离

`exception`

- 异常继续优先围绕 `waybill / batch / trace_event`
- `waybill` 承担异常摘要
- 异常详情页反读留痕、证据和处理日志

### 5.4 当前 `image_package` 口径

当前 `image_package` 已不再作为 `P1` 主缺口，而是视为：

- 已满足当前 `P1` 最小可用
- 后续如业务需要再做增强

当前已满足的范围包括：

- 图片包导入
- 命中运单
- 补链到正式 `trace_event -> evidence`
- 失败记录
- 基本重试
- 导入中心接入

因此，现阶段不再要求继续补更重的图片包运营能力才算 `P1` 成立。

### 5.5 当前权限口径

当前租户内权限不再追求过细矩阵，而是按 `P1` 最小可用方案收口：

- 租户管理员
- 调度 / 客服
- 图片导入 / 现场工作人员
- 只读查看
- 图片审计

承载层继续复用：

- `res.groups`
- `ir.model.access`
- `ir.rule`
- 菜单 / 按钮 / action 显隐
- 模型层最终兜底校验

## 6. 当前真正剩余的重点

结合当前已完成实现与人工回归，当前真正剩余的重点为：

1. `P0` 正式部署与正式验收
2. `P0` 正式入口、正式权限、正式备份恢复记录沉淀
3. `P1` 与正式 `P0` 入口联动后的最终收口确认

以下内容不再列为当前主推进项，而保留为后续可选增强：

- 图片包人工复核台账增强
- 图片包批量人工改挂
- 图片包复杂批量重试策略
- 图片包更完整任务看板

## 8. 一句话结论

当前企业隔离专题已经不再把“完整平台化多租户方案”当作本期主体，而是先把数据库级隔离、现有物流主链、`waybill` 主阅读入口、`trace / evidence / exception` 三层承接、权限边界、联调与验收收成一套可直接指导编码和落地的 `P0 / P1` 现行方案；当前阶段主线已经正式转向 `P0` 的正式部署与正式验收。
