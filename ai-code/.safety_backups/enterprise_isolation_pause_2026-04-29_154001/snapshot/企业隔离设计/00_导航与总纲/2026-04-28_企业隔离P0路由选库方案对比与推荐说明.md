# 2026-04-28 企业隔离 `P0` 路由选库方案对比与推荐说明

## 1. 文档定位

- 本文用于补充 `P0` 阶段“请求到底如何命中正确租户库”的路由选库说明。
- 本文**不替代**现有的 [2026-04-27_企业隔离P0租户库命名_域名映射与dbfilter规范.md](../02_跨模块规范/01_接口与数据/2026-04-27_企业隔离P0租户库命名_域名映射与dbfilter规范.md)。
- 现有 `dbfilter` 规范继续保留，作为“**子域名映射数据库**”方案的标准规范。
- 本文当前只回答两件事：
  - 如果不想维护大量子域名，是否可以改成“路径前缀选库”
  - 当前 `P0` 最推荐落哪一档方案

## 2. OBB

### 2.1 Outcome

- 团队对 `P0` 的路由选库方案形成统一口径。
- 明确区分：
  - 当前还能继续采用方案 A
  - 如果子域名带来持续运维压力，可以切到方案 B
- 在不打散当前多数据库隔离原则的前提下，给出当前推荐路径。

### 2.2 Behavior

- 所有业务请求在进入租户库业务逻辑前，就应当已经确定目标数据库。
- 不允许把“选库”做成模糊推断，也不允许依赖人工手工选库来兜底正式链路。
- 允许对外访问入口从“子域名”扩展到“路径前缀”，但仍要求请求进入 Odoo 前完成选库。

### 2.3 Boundary

- 本文不设计平台库表。
- 本文不设计统一用户中心。
- 本文当前只讨论方案 A 与方案 B。

## 3. Odoo 原生基线

在当前 Odoo 机制下，请求初始化时就会尝试确定数据库。当前源码里的核心顺序是：

1. 已存在的 `session.db`
2. `X-Odoo-Database` header
3. `Host + dbfilter`

也就是说，Odoo 天然更偏向：

- 先选库
- 再进入数据库内 ORM 请求

这也是为什么我们原先的 `P0` 规范默认采用“子域名 -> `dbfilter` -> 数据库”的口径。

## 4. 当前待比较的两档方案

## 4.1 方案 A：子域名映射数据库

### 访问形态

```text
https://<tenant_code>.tianshu.cn/login_in
```

### 典型映射

```text
acme.tianshu.cn -> tenant_acme
north-hub.tianshu.cn -> tenant_north-hub
```

### 当前实现方式

- 反向代理透传 `Host`
- Odoo 通过 `dbfilter` 按 `Host` 命中数据库

### 优点

- 最贴近 Odoo 原生多库机制
- `dbfilter` 可直接落地
- 排障最直观
- 请求进入业务前就已经确定数据库
- 不需要改 Odoo 选库入口逻辑

### 缺点

- 子域名数量会随租户数增长
- 域名管理、证书、DNS 运维会变重
- 对外入口看起来更分散

### 适用判断

- 如果运维侧能接受子域名规模，这是最稳方案
- 如果主管主要反对的是“域名太多”，那它的运维压力确实要认真评估

### 方案 A 的子域名规模与运维压力判断

子域名到多少会开始产生运维压力，没有一个绝对数字。

关键不在 Odoo 本身，而在运维侧是否已经具备：

- 泛域名能力
- 泛证书能力
- 统一反向代理模板
- 标准化租户登记
- 标准化开通 / 回收流程

如果按当前常见工程经验做粗粒度判断，可以这样理解：

- `1 ~ 20` 个子域名：
  - 通常压力较小
  - 手工维护 DNS、代理、证书和登记表，往往还能接受

- `20 ~ 50` 个子域名：
  - 开始出现明显运维感知
  - 如果仍然依赖人工逐个配置、逐个核对，出错概率会开始上升

- `50 ~ 100` 个子域名：
  - 如果没有自动化，通常会变成持续压力
  - 新租户开通、证书、排障、变更和回收都会开始明显拖慢节奏

- `100+` 个子域名：
  - 基本不建议继续靠纯手工维护
  - 这时问题已不再只是“域名多”，而是进入平台化运维能力问题

需要特别说明的是：

如果所有租户都能统一落在：

- `*.tianshu.cn`
- 同一套泛证书
- 同一套标准化代理配置
- 同一张租户登记表

那么子域名数量带来的压力会明显下降。

也就是说，真正让运维压力快速上升的，往往不是“子域名数量”本身，而是下面这些因素叠加在一起：

- 每个租户都要单独配 DNS
- 每个租户都要单独配证书
- 每个租户都要单独配代理
- 没有统一租户登记
- 没有标准化开通 / 回收流程

当前可以给出的务实判断是：

- 如果没有较成熟的自动化能力，子域名规模接近 `30 ~ 50` 时，就应认真评估方案 B
- 如果已经具备较成熟的泛域名和模板化运维，方案 A 的可承载规模还可以继续往上走

## 4.2 方案 B：单域名 + 路径前缀映射数据库

### 访问形态

```text
https://tianshu.cn/<tenant_code>/login_in
```

例如：

```text
https://tianshu.cn/acme/login_in
https://tianshu.cn/north-hub/login_in
```

### 典型实现思路

- 用户访问带租户前缀的统一主域名
- 反向代理 / 网关识别第一段 path：`<tenant_code>`
- 网关查映射：
  - `acme -> tenant_acme`
- 转发到 Odoo 时注入：

```text
X-Odoo-Database: tenant_acme
```

- 同时把路径重写成 Odoo 真正处理的登录或业务路径

### 优点

- 对外只维护一个主域名
- 不需要给每个租户维护独立子域名
- 仍然保持“请求进入 Odoo 前就完成选库”
- 比纯 `dbfilter` 方案更容易回应“子域名过多”的运维诉求

### 缺点

- 不能直接靠 `dbfilter` 单独完成，需要网关配合
- 路径重写、header 注入、静态资源和跳转路径都要认真验证
- 对反向代理配置质量要求更高

### 适用判断

- 如果团队希望“少子域名、仍保留多数据库隔离”，这是当前最值得评估的替代方案

## 5. 两档方案对比

| 维度 | 方案 A：子域名 | 方案 B：路径前缀 |
| --- | --- | --- |
| 对外域名数量 | 多 | 少 |
| 是否顺着 Odoo 原生入口 | 是 | 基本是 |
| 是否要求请求前完成选库 | 是 | 是 |
| 是否依赖网关能力 | 中 | 高 |
| `P0 / P1` 改造复杂度 | 低 | 中 |
| 排障与验收难度 | 低 | 中 |
| 当前推荐度 | 高 | 高 |

## 6. 当前推荐口径

### 6.0 当前执行决定

当前专题先按以下口径执行：

- **当前先采用方案 A：子域名映射数据库**
- **方案 B：单域名 + 路径前缀映射数据库，作为后续扩展与调整方向**

也就是说，当前 `P0 / P1` 的正式落地仍以方案 A 为准，方案 B 暂不进入本轮实施链路，只作为后续当子域名规模与运维压力上升时的替代路径预研。

## 6.1 当前首选推荐

如果运维侧可以接受子域名规模，当前仍然推荐：

**方案 A：子域名映射数据库**

原因是：

- 最顺着 Odoo 原生
- 设计和验收最简单
- 风险最低

## 6.2 当前替代推荐

如果主管明确反对“子域名太多”，当前最推荐的替代是：

**方案 B：单域名 + 路径前缀映射数据库**

它的定位是：

- 对外域名收敛
- 内部仍保持“请求前选库”
- 不额外引入平台化统一登录问题

## 7. 对现有 `dbfilter` 规范的影响

- 原有 [2026-04-27_企业隔离P0租户库命名_域名映射与dbfilter规范.md](../02_跨模块规范/01_接口与数据/2026-04-27_企业隔离P0租户库命名_域名映射与dbfilter规范.md) **继续有效**。
- 该文档现在应理解为：
  - 它完整定义了**方案 A：子域名映射数据库**的标准规范。
- 如果后续正式改走方案 B，应新增一份：
  - “路径前缀 -> 网关映射 -> `X-Odoo-Database`”的落地规范
  - 而不是直接推翻原有 `dbfilter` 文档

## 8. 当前建议决策方式

建议团队先做下面这个决策：

1. 是否还能接受“每租户一个子域名”
2. 如果不能，是否接受“统一主域名 + 路径前缀 + 网关选库”

当前这一步的实际结论已经收口为：

- 当前接受方案 A，先按方案 A 落地
- 方案 B 保留为后续专项推进方向，而不是当前同步实施项

## 9. 一句话收口

当前 `P0 / P1` 的关键不是“域名形式看起来更统一”，而是“请求进入 Odoo 前就把数据库稳定选对”；因此在当前阶段，**先按方案 A 落地，方案 B 作为后续运维压力上升后的扩展方向。**
