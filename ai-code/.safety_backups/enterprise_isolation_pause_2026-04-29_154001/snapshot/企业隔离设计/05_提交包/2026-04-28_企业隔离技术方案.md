# 企业隔离技术方案

## 评审历史

- `2026-04-28` `V1.0` 初稿，依据 `专题设计/企业隔离设计/` 现有总纲、细稿、实施规范、验收资料整理形成。

## 需求理解

### 一、背景信息

- 专题名称：企业隔离设计
- 当前阶段：`P0` 多数据库底盘验证 + `P1` 现有物流模块租户化落地
- 设计输入：
  - `00_导航与总纲/2026-04-28_企业隔离P0P1总设计文档.md`
  - `00_导航与总纲/2026-04-28_企业隔离P0路由选库方案对比与推荐说明.md`
  - `02_跨模块规范/01_接口与数据/2026-04-27_企业隔离P0租户库命名_域名映射与dbfilter规范.md`
  - `02_跨模块规范/04_实施规范/2026-04-27_企业隔离P0P1租户初始化安装与首轮验收SOP.md`
  - `02_跨模块规范/01_接口与数据/2026-04-27_企业隔离P1_waybill主阅读下的trace细稿.md`
  - `02_跨模块规范/03_权限与状态/2026-04-27_企业隔离P1_三层联动与租户内角色矩阵细稿.md`
  - `02_跨模块规范/04_实施规范/2026-04-28_企业隔离P1模块级改动清单.md`
  - `02_验收与联调/2026-04-28_企业隔离P1回归检查表.md`
- 项目业务基线：
  - 执行与数据主链：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
  - 正式追溯主链：`waybill -> trace_event -> evidence -> exception`
  - 当前正式追溯主对象：`waybill`
- 本方案目标不是把单库权限继续做细，而是把不同企业之间的边界收口为数据库级强隔离，并让现有物流模块在每个租户库内独立运行。

### 二、需求要点

- 企业之间默认采用数据库级强隔离，同一企业内部多法人协同才考虑 `multi-company`。
- `P0` 只解决“同一套 Odoo 服务如何稳定命中正确租户库”以及“单租户建库、装模块、备份恢复是否成立”。
- `P1` 只解决“现有物流模块在租户库内如何按当前业务口径运行”，不扩展平台主档、套餐、授权、计费、跨租户运营看板。
- 当前 `P1` 的页面主阅读入口必须收口到 `waybill`，不再把 `customer_line` 作为主阅读入口。
- 正式对象锚点不改写：`trace_event` 继续承接正式留痕，`evidence` 继续围绕 `trace_event`，`exception` 继续优先围绕 `waybill / batch / trace_event`。
- 权限边界继续采用 Odoo 原生承接层：`res.groups + ir.model.access + ir.rule + 菜单/按钮显隐 + 模型层最终兜底`。
- 图片导入与补链需要与主链审计分离：`dispatch_main` 与 `image_package` 两类任务区分。

## 实现方案

### 2.1 接口定义

> 本期以 Odoo 后台主链联动和租户访问链路为重点，不新增平台级跨租户开放 API。若后续扩展外部接口，仍需遵守项目现有 REST 前缀规范：`/api/admin/logistics/...`、`/api/mini/logistics/...`、`/api/open/logistics/...`。

###### 租户访问入口

- 方案 A，首选：
- 访问形态：`https://<tenant_code>.<base_domain>/...`
- 选库方式：`Host + dbfilter`
- 推荐 `dbfilter`：`^tenant_%d$`
- 方案 B，替代：
- 访问形态：`https://<base_domain>/<tenant_code>/...`
- 选库方式：网关解析路径前缀后注入 `X-Odoo-Database`
- 适用条件：运维侧无法接受子域名规模持续增长

###### Odoo 选库顺序约束

- 当前 Odoo 请求初始化阶段，目标库判定顺序固定为：
- 已存在的 `session.db`
- `X-Odoo-Database` header
- `Host + dbfilter`
- 本期约束：
- 所有请求在进入租户业务逻辑前必须确定目标数据库
- 不允许依赖人工手工选库兜底正式链路
- 不建议采用“统一登录后按 session / cookie 动态切库”

###### 租户内业务入口

- 本期不新增跨租户平台控制入口。
- 租户库内主入口继续由现有 Odoo 后台菜单承接：
- `waybill` 主阅读页
  - `trace_event` 详情页
  - `evidence` 详情 / 预览页
  - `exception` 详情页
- 所有后台动作默认共享同一套租户范围，不做跨库读取和跨库写入。

### 2.2 业务流程图

#### 模块结构（模块关系 / 交互）

- 底座层：
- `logistics_base`
- 主链层：
  - `logistics_dispatch`
- 三层事实链：
  - `logistics_trace_core`
  - `logistics_trace_evidence`
  - `logistics_trace_exception`
- 隔离原则：
- 企业之间靠数据库边界隔离
- 租户内继续复用 Odoo 原生权限体系与现有模块骨架

#### 逻辑流程（关键业务流程）

##### `P0` 请求命中租户库流程

1. 用户通过正式域名或路径前缀访问租户入口。
2. 反向代理透传 `Host`，或按路径前缀注入 `X-Odoo-Database`。
3. Odoo 在请求初始化阶段确定目标数据库。
4. 数据库列表与数据库管理入口在正式链路下保持关闭。
5. 请求进入目标租户库后，再执行 ORM、权限与业务逻辑。

##### 租户初始化安装流程

1. 确认 `tenant_code`、数据库名、访问域名与登记清单。
2. 创建或确认空租户库。
3. 配置反向代理、`Host` 透传与 `dbfilter`。
4. 按顺序安装模块：
   - `logistics_base`
   - `logistics_dispatch`
   - `logistics_trace_core`
   - `logistics_trace_evidence`
   - `logistics_trace_exception`
5. 初始化管理员、语言、时区与必要基础参数。
6. 执行 `P0` 底盘验收，验证域名命库、模块安装、备份恢复。
7. 再执行 `P1` 主链与三层模块回扫。

##### `P1` 主阅读与三层联动流程

1. 用户从 `waybill` 进入主阅读页。
2. `waybill` 页展示三块摘要：
- 留痕摘要
   - 证据摘要
   - 异常摘要
3. 留痕入口进入 `trace_event` 列表或详情，作为正式事实层。
4. 证据入口进入图片预览、证据详情，并通过 `trace_event` 回读上下文。
5. 异常入口进入异常详情，并回读 `waybill / trace_event / evidence / process_log`。

##### 图片命中与补链流程

1. 图片包导入任务进入 `image_package` 审计链。
2. 系统先按结构层做命中：
- `waybill_no + customer_line_no`
   - `waybill_no + store_no`
   - `waybill_no`
3. 命中结果进入 `match_status / link_status` 流程。
4. 已确认结果补链到正式 `trace_event`，生成正式证据对象。
5. 失败项记录失败原因、重试次数与人工复核标记。

##### 异常处理流程

1. 异常围绕 `waybill / batch / trace_event` 发起或回读。
2. 状态机按最小闭环流转：
- `draft / open -> processing -> resolved -> closed`
   - `cancelled` 作为兼容终态保留
3. 模型层统一校验状态迁移、关闭说明、对象一致性与日志生成。

### 2.3 配置变动表

- 租户标识配置
  - `tenant_code`
  - 数据库名：`tenant_<tenant_code>`
  - 主访问域名：`<tenant_code>.<base_domain>`
- Odoo 运行配置
  - `dbfilter=^tenant_%d$`（方案 A）
  - `list_db=False`
  - `proxy_mode=True`
  - `addons_path` 需包含官方模块与 `custom_addons`
- 运维登记清单
  - `tenant_code`
  - 企业显示名
  - 数据库名
  - 主访问域名
  - 环境
  - 当前状态
  - 备注
- 权限与任务类型配置
  - 角色至少区分：租户管理员、调度/客服、图片导入/现场工作人员、只读查看人员
  - 导入任务区分：`dispatch_main`、`image_package`

### 2.4 数据模型

#### 2.4.1 DB 表结构 / 模型对象

本期不新增平台库，也不建设平台侧租户主档表。首轮实现采用：

- 租户库：
  - 每个企业一个独立 Odoo PostgreSQL 数据库
- 运维登记层：
  - 用受控清单记录 `tenant_code / db_name / domain / env / status`

租户库内本期重点对象如下：

- 主链对象
  - `wave`
  - `batch`
  - `waybill`
  - `customer_line`
  - `order_line`
  - `goods_line`
- 留痕对象
  - `logistics.trace.event`
  - 核心归属字段：`batch_id`、`waybill_id`
  - 摘要字段：`trace_count`、`latest_trace_time`、`latest_trace_type`、`latest_trace_summary`、`has_exception_related_trace`
- 证据对象
  - `logistics.trace.evidence`
  - 命中字段：`match_status`、`match_method`、`match_waybill_no`、`match_customer_line_no`、`match_store_no`
  - 补链字段：`link_status`、`linked_trace_event_id`、`linked_waybill_id`、`link_fail_reason`、`link_retry_count`、`manual_review_flag`
  - 摘要字段：`evidence_count`、`latest_evidence_time`、`pending_link_image_count`
- 异常对象
  - `logistics.trace.exception`
  - 核心关联：`waybill_id`、`batch_id`、`trace_event_id`
  - 摘要字段：`open_exception_count`、`latest_exception_time`、`latest_exception_type`、`highest_exception_status`、`has_processing_exception`
  - 过程日志：`logistics_trace_exception_process_log`

#### 2.4.2 Redis

- 本期企业隔离方案不把 Redis 作为成立前提。
- 若后续为图片命中、摘要缓存或回归加速引入缓存，仍需遵守：
  - 缓存键必须显式带租户上下文
  - 不允许跨租户复用命中结果
  - 模型层真值优先于缓存

#### 2.4.3 ES

- 本期不以 ES 作为前置依赖。
- 搜索与筛选先基于 Odoo 现有 ORM、索引和后台视图能力承接。
- 若后续扩展跨页全文检索，应保证索引分租户隔离，并与数据库边界一致。

### 2.5 兼容性处理

> 【建议】以下是本方案需要重点考虑的兼容性场景：数据库路由方式兼容、现有物流模块边界兼容、租户库内主阅读口径兼容、权限模型兼容、历史数据与历史目录命名兼容。
> 【结论】本期企业隔离方案以增量兼容为主，不推翻现有物流模块体系，不引入跨企业单库兼容方案，不把 `customer_line` 再抬回主阅读入口。

- 路由兼容：
- 首选继续采用“子域名 -> `dbfilter` -> 数据库”方案，与当前 Odoo 多数据库能力最顺。
- 如运维侧后续无法接受子域名规模，再兼容切换到“单域名 + 路径前缀 + `X-Odoo-Database`”方案，但要求选库动作仍在进入 Odoo 前完成。
- 模块边界兼容：
- 继续沿 `logistics_base / logistics_dispatch / logistics_trace_core / logistics_trace_evidence / logistics_trace_exception` 承接。
- 不为本期企业隔离另起一套新的 `tms_*` 业务对象体系。
- 业务口径兼容：
- 保留 `customer_line` 在数据链中的结构层角色。
- 不恢复 `customer_line` 主阅读入口职责，`waybill` 继续作为当前 `P1` 主阅读入口。
- Odoo 能力边界兼容：
- 企业隔离靠数据库，不靠单库多公司模拟。
- 同一企业内部多法人协同才考虑 `multi-company`。
- 历史实现兼容：
- 允许保留历史目录、历史草图和桥接命名。
- 新设计、新开发、新验收统一以 `waybill -> trace_event -> evidence -> exception` 为正式基线。
- 数据与接口兼容：
- 本期不新增平台级跨租户 API，不改变当前租户内正式对象锚点。
- 图片命中、补链、异常流转均在当前租户库内闭环，不做跨库回读。

### 2.6 灰度放量设计

> 【建议】本专题影响访问链路、主阅读链和三层联动，必须灰度推进。
> 【边界】灰度放量设计只描述放量策略、准入准出和回滚触发条件；测试标准、自测清单和回归项应放在 `自测方案` 与 `影响面&测试关注点` 中。

- 灰度阶段：
- 阶段一：单示例租户验证 `P0`。
- 阶段二：单示例租户验证 `P1`。
- 阶段三：小批量复制到多个租户库。
- 阶段四：按正式租户批次推广。
- 灰度准入条件：
- 进入 `P1` 之前，租户必须先通过 `P0` 底盘验收。
- 进入小批量复制之前，单示例租户必须完成 `waybill` 主阅读、三层联动和角色边界回归。
- 灰度准出条件：
- 当前批次租户的域名命库稳定、不串库。
- 当前批次租户的高风险动作入口未出现越权。
- 当前批次租户的图片补链、异常流转未出现系统性失败堆积。
- 回滚触发条件：
- 出现错误域名命中其他租户库。
- 出现跨租户数据可见、跨租户导出或跨租户写入。
- 出现图片补链批量误挂、异常状态机批量卡死等系统性问题。
- 放量策略说明：
- 默认先推广方案 A；若子域名运维压力持续升高，再单独评估方案 B 的切换窗口。
- 灰度过程中要避免新旧配置同时指向不同数据库，避免不同租户误命中同一库。

## 可靠性评估

> 一般来说，服务端和核心链路变更都要做可靠性评估。这里重点关注访问链路是否稳定、租户命库是否失败即止、三层联动是否可回读、补链失败是否可恢复、异常状态机是否可追溯。

- 访问链路可靠性：
- 方案 A 可靠性最高，最顺着 Odoo 原生多数据库能力。
- 方案 B 可以成立，但更依赖网关路径重写和 `X-Odoo-Database` 注入正确性。
- 失败处理：
- 域名或路径前缀无法确定目标库时，应直接失败，不允许模糊命中其他租户库。
- 图片补链失败时保留失败原因、重试次数和人工复核标记，不直接写成正式证据。
- 数据一致性：
- `P0` 只有在“域名命库稳定 + 不串库 + 备份恢复可验证”三项同时成立后才允许推进 `P1`。
- `trace -> evidence -> exception` 的依赖顺序必须稳定，不允许异常或证据绕开正式 `trace_event` 锚点。
- 降级与回退：
- `waybill` 摘要区异常时，至少不能影响租户命库和核心对象读取。
- 高风险动作如导出、补链重试、异常关闭必须可以单独拦截，不应拖垮主阅读链。
- 日志与排障：
- 必须能从访问域名、租户库、`waybill_id`、`trace_event_id`、导入任务号、异常单号定位问题。
- 结论：
- 当前方案在单租户验证、小批量复制、分批推广的前提下可靠性可控，主要风险集中在路由配置质量和三层联动回归不充分。

## 安全性评估

> 安全性评估重点关注四类问题：企业边界是否会串库、租户内是否会越权、敏感对象是否会被错误导出、日志和调试信息是否会泄露不该暴露的租户信息。

- 企业间边界：
- 数据库级隔离是主边界，不接受只靠权限组模拟跨企业隔离。
- 路由规则必须是一对一、可逆推、可人工校验，不允许宽松匹配。
- 租户内鉴权：
- `res.groups + ir.model.access + ir.rule` 承接静态授权。
- 菜单、按钮、action 负责入口显隐，模型层负责最终写入兜底。
- 当接口入参里出现 `waybill_id`、`trace_event_id`、`evidence_id`、`exception_id` 时，必须校验对象是否归属于当前租户库和当前角色可见范围。
- 敏感数据与日志：
- 不在普通日志中打印完整图片访问 key、完整对象存储地址、跨租户数据库名映射表。
- 补链失败原因、异常处理日志、导出审计需要保留业务可追踪信息，但避免泄露无关租户信息。
- 高风险动作控制：
- 证据导出、补链重试、异常关闭、过程日志修改均不得只靠页面隐藏控制。
- 图片导入/现场工作人员默认不具备导出证据、关闭异常、重试补链等高风险权限。
- ORM 与模型约束：
- 业务 CRUD 默认走 ORM，不允许用越权 SQL 或绕过模型约束的方式跨租户写数据。
- 结论：
- 当前安全风险主要不在单条业务逻辑，而在路由选库、越权导出和模型层兜底是否落实，属于可以通过配置收口和模型约束明确规避的风险。

## 容量预估

> 容量预估不要求在本期做到非常精准，但要对租户数量、访问链路、数据库数量、图片导入任务量和补链重试量有基本判断，并给出超预期时的限制手段。

- 当前主要容量压力点：
- 租户数据库数量增长。
- 子域名、反向代理、`dbfilter` 或网关映射规则数量增长。
- 图片包导入、补链任务、异常处理记录增长。
- 当前阶段容量判断：
- `P0 / P1` 不建设平台级任务中心和指标仓，主压力仍在访问链路、租户数据库和图片任务队列。
- 单租户验证阶段压力较小，重点不是资源打满，而是配置正确性与回归稳定性。
- 小批量租户阶段需要重点观察导入任务和补链失败堆积情况。
- 超预期限制手段：
- 若无自动化能力，子域名规模接近 `30 ~ 50` 时，应开始认真评估方案 B。
- 若图片任务堆积明显，应优先限制并发导入批次、错峰执行补链重试，而不是放任失败任务堆积。
- 若异常处理日志和证据审计读取变慢，应优先补索引和摘要字段，而不是扩大跨页联查。
- 结论：
- 本期容量风险总体可控，前提是租户推广分批推进、图片任务限速执行、路由配置保持模板化管理。

## 自测方案

> 研发需提供自测用例集和自证结果。本期自测不能只验证对象能打开，还要验证租户路由、权限拦截、三层联动和失败补链的完整链路。

- `P0` 自测：
- 域名命中正确租户库。
- 不出现数据库选择页。
- 基础模块可独立安装。
- 数据库与文件存储成对备份恢复。
- 错误域名或错误租户前缀不会误命中其他租户库。
- `P1` 自测：
- `waybill` 留痕摘要正常。
- `waybill` 证据摘要正常。
- `waybill` 异常摘要正常。
- `trace_event`、`evidence`、`exception` 均可在当前租户库内独立读取和联动。
- 图片命中失败、补链失败、非法状态迁移、越权导出均能被正确拦截或记录。

## 影响面&测试关注点

> 一般可以从受影响模块、受影响链路、受影响角色、受影响租户和受影响数据几个维度来给出影响面评估。本期尤其要关注访问链路、主阅读入口和三层联动是否同时变化。

##### 主链页面

- `waybill` 主阅读页摘要区。
- `customer_line` 结构层角色是否被误抬高。
- `order_line` 与 `goods_line` 反读链是否仍正常。

##### 权限与联动

- 只读查看员是否仍有越权入口。
- 图片导入人员是否被误赋予导出或关闭异常能力。
- 异常关闭是否要求 `close_summary`。
- 非法状态迁移是否被模型层拦截。

##### 多数据库隔离

- 当前租户域名是否仍可能命中错误数据库。
- 是否还有手工选库依赖残留。
- 是否出现跨租户数据可见或跨租户导出。

## 发布计划

> 发布计划需要同时覆盖发布顺序、配置清单、验证动作和回滚路径。本期既涉及 Odoo 多数据库路由，又涉及模块级联动，发布与回滚必须一起写清楚。

1. 先完成 `P0` 单租户底盘验证。
2. 再完成 `P1` 单租户主链与三层联动验证。
3. 再推广到小批量租户库做统一安装与统一回归。
4. 最后再进入正式租户推广。

- 发布前检查：
- 租户登记清单、域名映射、数据库名、`dbfilter` 或网关映射规则全部核对完成。
- 模块安装顺序、基础参数、角色分组、回归表准备完成。
- 回滚计划：
- 路由配置回滚优先于业务模块开放。
- 若 `P1` 联动回归失败，可停留在通过 `P0` 的租户底盘状态，不强行开放三层入口。
- 若图片补链或异常流转异常，先关闭高风险动作入口，再回退到稳定读链。

## 监控方案

> 方案上线后，研发需要重点关注“路由是否正确、链路是否可读、补链是否堆积、异常是否卡住、越权入口是否误开放”这几类指标，必要时补充告警。

- 环境侧监控：
- 域名访问是否命中正确租户库。
- 数据库列表与数据库管理入口是否被意外放开。
- 路由配置变更后是否出现错误域名命中。
- 业务侧监控：
- 图片导入失败率。
- 补链失败数量和重试堆积数量。
- 异常状态卡住数量。
- `waybill` 摘要区读取异常数量。
- 验收侧监控：
- 每轮提交后至少按 `P1` 回归检查表回扫一次 `waybill` 摘要、权限、联动入口、异常状态机。
- 小批量推广阶段至少保留一轮人工抽检结果。

## 预估开发时间

- `P0`：方案与环境收口 `1 ~ 2` 天，单租户底盘验证与验收 `1 ~ 2` 天。
- `P1`：`trace_core` `2 ~ 3` 天，`evidence` `2 ~ 4` 天，`exception` `2 ~ 3` 天，联动回归与权限收口 `1 ~ 2` 天。
- 整体节奏以 `P0` 先过、`P1` 再进、三层顺序固定为前提，若中途发现路由方案需切到方案 B，则排期需额外增加网关联调与回归时间。

## 数据修复【可选】

> 如果本期推广前已经存在历史图片包、历史异常单或历史挂点不一致数据，需要先判断是否必须修，再判断修复范围、耗时、回滚方式和是否可重入。

- 历史图片包未补链时，需要补做命中结果回扫、失败原因登记、人工复核后重试补链。
- 历史异常单挂点不符合当前口径时，需要回扫是否误挂到 `customer_line / order_line`，以及是否缺失 `waybill / batch / trace_event` 一致性关系。
- 数据修复原则：
- 能不批量修的先不批量修。
- 能先隔离问题入口的，先隔离入口再修数据。
- 修复脚本或修复动作必须可回滚、可重入、可留痕。

## 成本和收益

> 【建议】本节用于给出方案推进的直接成本、长期收益，以及为什么本期值得做、不做会有什么隐性代价。

- 成本：
- 多数据库带来更高的域名、代理、备份和运维管理成本。
- 三层联动与权限收口需要模块级增量改造。
- 收益：
- 企业之间边界清晰，降低串库风险。
- 每个租户库可以独立安装、回归、验收与恢复。
- 现有物流系统可在不推翻业务口径的前提下逐步租户化。
- 为后续 `P2 / P3` 平台化能力预留稳定底盘。
