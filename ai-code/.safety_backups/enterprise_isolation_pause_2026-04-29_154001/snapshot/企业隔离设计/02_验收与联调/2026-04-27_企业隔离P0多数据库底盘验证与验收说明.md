# 2026-04-27 企业隔离 `P0` 多数据库底盘验证与验收说明

## 1. 文档定位

- 本文用于企业隔离专题 `P0` 的底盘验证、人工验收和联调执行。
- 本文只覆盖数据库级企业隔离成立前必须验证的底盘链路。
- 本文不扩展到：
  - 平台控制面
  - 自动开租户
  - 套餐、授权、计费
  - 跨租户汇总

## 2. `P0` 的目标

`P0` 只回答一个问题：

**数据库级企业隔离在当前 Odoo 环境中能不能稳定成立。**

这里的“成立”至少包括：

- 不同企业可以通过不同域名稳定命中各自数据库
- 用户不会误入数据库列表或数据库管理入口
- 单个租户数据库可以独立安装当前物流基础模块
- 单个租户数据库可以独立备份、恢复和回读
- 恢复时数据库与文件存储能按一组对象理解

## 3. OBB

### 3.1 Outcome

- 至少 1 个示例租户库可通过独立域名正常访问。
- 同一套 Odoo 服务可承接多个租户库，不发生串库访问。
- 运维可手工完成单个租户库的建库、装模块、初始化、备份和恢复。

### 3.2 Behavior

- 域名如何命中数据库：按 `租户库命名、域名映射与 dbfilter 规范` 执行。
- 数据库列表和数据库管理页如何处理：正式访问链路下默认关闭。
- 备份恢复如何处理：数据库与文件存储按成对对象处理，不接受只恢复其一的做法。

### 3.3 Boundary

- 不要求平台化租户编排。
- 不要求自动建库、自动装模块、自动绑域名。
- 不要求平台任务状态机、平台审计日志、平台汇总能力。

## 4. 验收前提

- [ ] 已有可用的 Odoo 环境。
- [ ] 已有可用的反向代理或网关配置位置。
- [ ] 已确认目标环境允许多数据库运行。
- [ ] 已准备至少 1 个示例租户编码。
- [ ] 已准备与租户编码对应的独立域名或测试子域名。
- [ ] 已明确数据库命名规则、域名规则和 `dbfilter` 规则。

## 5. 验收范围

本轮 `P0` 只验以下六类内容：

1. 租户库命名与域名映射
2. `dbfilter` 路由
3. 数据库列表与数据库管理入口关闭
4. 单库模块安装与访问
5. 单库备份与恢复
6. 常见误配置与失败场景

## 6. 验收步骤

### 6.1 租户库命名与域名映射

- [ ] 为测试租户准备符合规范的 `tenant_code`。
- [ ] 为测试租户准备符合规范的数据库名。
- [ ] 为测试租户准备符合规范的访问域名。
- [ ] 确认数据库名与域名之间是一对一映射，而不是模糊映射。
- [ ] 确认不会通过中文名、显示名或备注名参与路由匹配。

### 6.2 `dbfilter` 路由

- [ ] Odoo 已配置符合当前规范的 `dbfilter`。
- [ ] 反向代理或网关已正确透传 `Host`。
- [ ] 访问示例租户域名时，请求可稳定命中对应数据库。
- [ ] 修改浏览器地址中的租户子域名后，不会误命中另一个租户数据库。
- [ ] 非法域名、未登记域名或无对应库域名，不会错误落入其他租户库。

### 6.3 数据库列表与数据库管理入口

- [ ] 正式访问链路下数据库列表不可见。
- [ ] 正式访问链路下数据库管理页不可作为普通用户入口使用。
- [ ] 用户登录时不会看到“手工选库”的正常使用路径。
- [ ] 误访问数据库管理入口时，系统表现符合预期安全边界。

### 6.4 单库模块安装与访问

- [ ] 可在目标租户库手工安装 `logistics_base`。
- [ ] 可在目标租户库手工安装 `logistics_dispatch`。
- [ ] 安装后可通过租户域名登录并访问基础物流页面。
- [ ] 租户库内读取仅针对当前数据库，不出现其他租户数据。

### 6.5 单库备份与恢复

- [ ] 可对目标租户库执行独立备份。
- [ ] 可识别该租户库对应的文件存储路径或对象存储边界。
- [ ] 恢复时数据库和文件存储按一组对象恢复。
- [ ] 恢复后可通过租户域名重新访问并登录。
- [ ] 恢复后基础模块与已安装物流模块状态正确。

### 6.6 常见误配置与失败场景

- [ ] 域名存在但数据库不存在时，系统不会误落其他库。
- [ ] 数据库存在但域名未登记时，系统不会开放正常业务入口。
- [ ] `Host` 未透传时，可被识别为配置异常而不是串库。
- [ ] 恢复数据库但未恢复文件存储时，可识别为不通过。
- [ ] 恢复文件存储但未恢复数据库时，可识别为不通过。

## 7. 通过 / 不通过判定

### 7.1 通过

满足以下条件可判定 `P0` 通过：

- 域名到数据库映射稳定成立
- 单库访问与登录稳定成立
- 数据库列表与数据库管理入口被正确约束
- 单库安装、备份、恢复链路成立
- 全程未出现跨租户串库

### 7.2 部分通过

满足主链但仍有以下问题，可判定部分通过：

- 访问链路成立，但数据库管理入口策略不稳定
- 安装链路成立，但备份恢复链路仍需补强
- 单租户验证成立，但多租户切换验证不足

### 7.3 不通过

出现以下任一情况，应直接判定不通过：

- 域名命中错误数据库
- 可通过正式链路访问数据库列表并误选库
- 恢复后只能恢复数据库、不能恢复文件存储
- 不同租户之间出现任何串读、串写或对象标识泄露

## 8. 验收输出要求

每次 `P0` 验收后至少记录：

- 验收日期
- 环境名称
- 租户编码
- 域名
- 数据库名
- `dbfilter` 规则版本
- 通过项
- 待修项
- 阻塞项
- 是否允许进入 `P1`

## 9. 与 `P1` 的衔接条件

只有当下面条件全部满足时，才建议进入 `P1`：

- 域名到数据库的一对一命中稳定成立
- 数据库列表与数据库管理入口已正确收口
- 租户库可独立安装当前物流基础模块
- 单租户备份恢复链路已跑通

## 10. 当前明确不做

- 不补平台侧租户主档表
- 不补平台侧任务状态机
- 不补套餐、授权、到期、降级设计
- 不补跨租户汇总与指标仓

## 11. 一句话收口

`P0` 的意义不是“把多租户平台做出来”，而是先把“不同企业不同数据库”的访问、安装、备份和恢复底盘验证扎实，只有这层稳定了，后续 `P1` 才有继续落的价值。
