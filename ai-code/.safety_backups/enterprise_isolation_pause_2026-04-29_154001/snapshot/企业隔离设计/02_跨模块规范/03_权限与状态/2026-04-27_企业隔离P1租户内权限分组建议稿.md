# 2026-04-27 企业隔离 `P1` 租户内权限分组建议稿

## 1. 文档定位

- 本文承接《现有 Odoo 权限体系与企业隔离 `P1` 角色矩阵复用对照表》。
- 本文不再只回答“哪些可以复用”，而是直接给出企业隔离 `P1` 下建议保留、建议新增、建议拆分的权限分组方案。
- 本文目标是为后续 `groups / access / rule / 页面显隐 / 模型校验` 的实现提供一份可直接落地的分组草稿。

## 2. 适用边界

本文只覆盖：

- 单个租户库内部权限分组
- 当前 `P1` 范围内的：
  - `dispatch`
  - `trace`
  - `evidence`
  - `exception`
  - `image_package`

本文不覆盖：

- 平台级跨租户管理员
- 套餐到期 / 降级权限
- 公司级组织树 / 区域树 / 门店树的完整数据域设计

## 3. 设计原则

- 企业之间继续靠数据库隔离，不靠权限组模拟企业隔离。
- 租户内权限优先继续使用 Odoo 原生承载层：
  - `res.groups`
  - `ir.model.access`
  - `ir.rule`
  - 菜单 / 按钮 / action 显隐
  - 模型层最终兜底校验
- 不建议让一个“超级 manager 组”兜住全部能力。
- 建议采用：
  - 基础角色组
  - 专项能力组
  - 页面显隐和模型校验分层配合

## 4. 总体分组思路

当前建议把租户内权限分组分成两层：

### 4.1 基础角色组

用于表达“你是谁”：

- 租户管理员
- 调度 / 客服
- 图片导入 / 现场工作人员
- 只读查看

### 4.2 专项能力组

用于表达“你还能做什么”：

- 主链管理
- 留痕管理
- 图片导入
- 图片补链 / 审计
- 异常处理
- 导出执行
- 导出管理
- 主数据维护

## 5. 建议保留并继续复用的组

下面这些组建议继续保留，不必推翻：

| 现有组 | 当前作用 | 在 `P1` 中建议定位 |
| --- | --- | --- |
| `group_logistics_dispatch_manager` | 执行主链管理 | 主链管理能力组 |
| `group_logistics_import_manager` | 标准导入管理 | 导入管理基础组，后续再细分图片导入能力 |
| `group_logistics_export_user` | 导出执行 | 导出执行能力组 |
| `group_logistics_export_manager` | 导出管理 | 导出管理能力组 |
| `group_logistics_trace_event_manager` | 留痕管理 | 留痕管理能力组 |
| `group_logistics_trace_manager` | 证据 / 异常管理 | 作为过渡期能力组，后续建议拆细 |
| `group_logistics_profile_manager` | 主数据维护 | 主数据维护能力组 |

## 6. 建议新增或拆细的组

### 6.1 建议新增

| 建议组名 | 作用 |
| --- | --- |
| `group_logistics_tenant_admin` | 租户内总管理角色映射组 |
| `group_logistics_dispatch_operator` | 调度 / 客服日常执行组 |
| `group_logistics_image_field_operator` | 图片导入 / 现场工作人员组，承接图片包上传、留痕提交与基础只读 |
| `group_logistics_image_auditor` | 图片命中结果、补链失败、重试补链处理组 |
| `group_logistics_exception_handler` | 异常跟进与关闭处理组 |
| `group_logistics_readonly_viewer` | 只读查看组 |

### 6.2 建议拆细

当前最适合拆细的是：

- `group_logistics_trace_manager`

建议从“一个大 manager 组”过渡为：

- 留痕管理能力
- 证据管理能力
- 异常处理能力
- 图片补链 / 审计能力

## 8. 角色与能力组建议映射

### 8.1 租户管理员

建议组合：

- `group_logistics_tenant_admin`
- `group_logistics_dispatch_manager`
- `group_logistics_trace_event_manager`
- `group_logistics_export_manager`
- `group_logistics_profile_manager`

可选附加：

- `group_logistics_image_auditor`
- `group_logistics_exception_handler`

中文理解：

- 这个角色是当前租户库内的最高业务管理角色。
- 可以看当前租户内主链、留痕、证据、异常、导入导出结果。
- 可以管理主链对象、管理留痕、处理异常、发起和管理导出。
- 如附加图片审计能力，还可以看全部图片任务、处理补链失败和重试补链。
- 这个角色不是平台级管理员，只在当前租户库内生效。

### 8.2 调度 / 客服

建议组合：

- `group_logistics_dispatch_operator`

按需附加：

- `group_logistics_exception_handler`
- `group_logistics_export_user`

中文理解：

- 这个角色负责日常业务操作，主要围绕 `waybill` 主阅读入口工作。
- 可以查看主链、留痕、证据、异常的业务阅读内容。
- 可以发起异常、补充备注、推进日常业务处理。
- 默认不作为最高管理角色，不直接拥有全部导出和全部关闭异常的能力。
- 如果额外附加异常处理或导出能力，才放开对应高风险动作。

### 8.3 图片导入 / 现场工作人员

建议组合：

- `group_logistics_image_field_operator`

按需附加：

- `group_logistics_image_auditor`

默认不附加：

- 异常关闭
- 证据导出
- 图片补链重试

中文理解：

- 这个角色是当前 `P1` 下最轻量的现场执行角色。
- 主要做两件事：上传图片包、提交留痕。
- 同时可以看和自己工作直接相关的基础页面信息，以及本人导入结果。
- 默认不能处理异常，不能导出证据，也不能重试图片补链。
- 如果后面确实需要参与图片审计，再额外挂图片审计能力，不在首轮默认放开。

### 8.4 只读查看

建议组合：

- `group_logistics_readonly_viewer`

默认不附加：

- 导出
- 处理
- 上传

中文理解：

- 这个角色只负责看，不负责写。
- 可以查看授权范围内的运单摘要、留痕、证据、异常详情。
- 默认不能上传图片、不能提交留痕、不能处理异常、不能导出证据。
- 适合老板看板、辅助查看、跨岗位协同查看这类场景。

## 10. 页面层、接口层、模型层的分工建议

### 10.1 页面层

页面层建议根据组控制：

- 菜单是否出现
- 按钮是否可见
- 导出入口是否显示
- 补链入口是否显示
- 关闭异常按钮是否显示

### 10.2 接口层

接口层建议根据组控制：

- 是否允许进入导出接口
- 是否允许进入图片上传接口
- 是否允许进入补链重试接口
- 是否允许进入异常关闭接口

### 10.3 模型层

模型层必须兜底：

- 即使按钮误显，也不能越权写入
- 即使接口被手工调用，也不能非法关闭异常
- 即使 access 放开，也要结合角色和状态做最终判断

## 11. 当前最需要收口的点

### 11.1 过宽的 `base.group_user`

当前不建议继续让 `base.group_user` 默认承接：

- 留痕创建
- 证据创建
- 异常创建

建议改为：

- 通过更明确的业务组承接

### 11.2 `group_logistics_trace_manager` 过大

当前它混合了：

- 证据全量查看
- 异常全量查看
- 处理类管理语义

建议在 `P1` 下逐步拆细，不再长期作为一个大兜底组使用。

### 11.3 `image_package` 需要独立权限口径

当前导入权限主要还是标准主链导入思路。

企业隔离 `P1` 下应把图片包导入、命中结果查看、补链失败查看、重试补链单独做成权限口径。

### 11.4 现场工作人员不再承担仓侧留痕职责

按当前收口，`P1` 不再单独保留“仓库 / 装车”基础角色组。

现场工作人员统一并入“图片导入 / 现场工作人员”组，但该组只保留：

- 图片包上传
- 留痕提交
- 本人导入结果查看
- 与当前工作相关的基础只读

不再默认承接：

- 异常处理
- 证据导出
- 图片补链重试

## 12. 建议实施顺序

1. 先保留现有组，不做破坏性改名。
2. 先新增租户内基础角色组。
3. 再把现有 manager 组解释为能力组。
4. 再收口 `base.group_user` 的过宽写权限。
5. 最后补 `image_package` 与异常关闭的专项能力组。

## 13. 一句话结论

企业隔离 `P1` 下最稳的权限分组方案，不是重做权限系统，而是以 Odoo 原生机制为底座，保留现有模块里的权限骨架，再补一层“租户内基础角色组 + 专项能力组”的清晰映射。
