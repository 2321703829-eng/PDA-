# 2026-04-27 现有 Odoo 权限体系与企业隔离 `P1` 角色矩阵复用对照表

## 1. 文档定位

- 本文用于回答企业隔离 `P1` 下一个关键问题：
  - 企业内部权限划分是否可以复用 Odoo 原生权限体系
  - 是否可以复用我们现有模块中已经做过的权限划分
  - 哪些可以直接复用，哪些只能部分复用，哪些需要补强
- 本文不是平台级权限系统设计。
- 本文只覆盖当前企业隔离 `P1` 的租户库内权限复用与收口。

## 2. 先说结论

当前企业隔离 `P1` 不应该新造一套脱离 Odoo 的权限系统。

正确做法是：

- 企业之间：继续靠数据库级隔离
- 企业内部：继续优先复用 Odoo 原生权限体系
- 模块侧：尽量复用我们现有自定义模块里已经落过的组、access、rule 和页面显隐模式
- 差距处：按企业隔离 `P1` 的角色矩阵做收口与补强

一句话说：

**企业隔离不会推翻现有权限系统，而是把现有权限系统从“单库权限”收口为“租户库内权限”。**

## 3. 复用范围

本文同时覆盖三类复用对象：

1. Odoo 原生权限承载层
2. 现有自定义模块已经落下的权限骨架
3. 企业隔离 `P1` 目标角色矩阵

## 4. Odoo 原生权限承载层

当前企业隔离 `P1` 下，最适合继续复用的 Odoo 原生能力包括：

- `res.groups`
  - 承接角色组、能力组
- `ir.model.access`
  - 承接模型级 `read / write / create / unlink`
- `ir.rule`
  - 承接记录级可见范围与数据域限制
- 菜单 / action / 按钮显隐
  - 承接页面体验层入口控制
- 模型层业务校验
  - 承接最终兜底，不允许仅靠页面显隐替代真实安全边界

## 5. 现有模块权限骨架盘点

### 5.1 `logistics_dispatch`

当前已存在的核心组包括：

- `group_logistics_dispatch_manager`
  - 文件：`custom_addons/logistics_dispatch/security/logistics_dispatch_security.xml`
- `group_logistics_import_manager`
- `group_logistics_export_user`
- `group_logistics_export_manager`

当前已存在的模式包括：

- 主链对象的 `user / manager` 两层 access
- 导入任务的“本人可看 / manager 看全部”
- 导出任务的“执行用户可看自身 / manager 看全部”

### 5.2 `logistics_trace_core`

当前已存在：

- `group_logistics_trace_event_manager`
  - 文件：`custom_addons/logistics_trace_core/security/logistics_trace_core_security.xml`

当前 access 特点：

- `base.group_user` 可读、可创建 `trace_event`
- manager 可读、可写、可创建

### 5.3 `logistics_trace_evidence`

当前已存在：

- `group_logistics_trace_manager`
  - 文件：`custom_addons/logistics_trace_evidence/security/logistics_trace_evidence_security.xml`

当前规则模式：

- 上传人看自己的证据
- manager 看全部证据
- 图片明细对象也延续“本人 / manager”模式

### 5.4 `logistics_trace_exception`

当前未单独再起 manager 组，而是直接复用：

- `logistics_trace_evidence.group_logistics_trace_manager`

当前规则模式：

- 上报人看自己的异常
- manager 看全部异常
- 处理日志也沿用相同模式

### 5.5 `logistics_base`

当前已存在：

- `group_logistics_profile_manager`
  - 文件：`custom_addons/logistics_base/security/logistics_base_security.xml`

适合继续承接：

- 基础资料配置
- 画像类主数据管理

## 6. 企业隔离 `P1` 目标角色矩阵

当前企业隔离 `P1` 设计已经收口的租户内角色包括：

- 租户管理员
- 调度 / 客服
- 图片导入 / 现场工作人员
- 只读查看人员

当前企业隔离 `P1` 还要求至少区分四类能力：

- 查看
- 上传
- 处理
- 导出

## 7. 复用对照总表

| 现有承载层 / 现有组 | 当前已有能力 | 在企业隔离 `P1` 中可复用为 | 复用方式 | 是否需要补强 |
| --- | --- | --- | --- | --- |
| `res.groups` | 角色分组基础能力 | 所有租户内角色与能力组 | 直接复用机制 | 否 |
| `ir.model.access` | 模型级 CRUD 控制 | `trace / evidence / exception / dispatch` 的基础读写边界 | 直接复用机制 | 否 |
| `ir.rule` | 记录级数据域控制 | 本人可看、manager 看全部、后续租户内范围限制 | 直接复用机制 | 否 |
| 菜单 / action / 按钮显隐 | 页面入口控制 | 页面层体验控制 | 直接复用机制 | 是，不能单独算安全边界 |
| `group_logistics_dispatch_manager` | 执行主链对象管理 | 调度主管、租户管理员的主链管理能力 | 可直接复用为能力基础组 | 是，需要与角色矩阵重新命名或映射 |
| `group_logistics_import_manager` | 标准导入任务全量查看 | 图片导入 / 导入审计能力基础组 | 可部分复用 | 是，需要区分 `dispatch_main` 与 `image_package` |
| `group_logistics_export_user` | 可发起导出并看本人结果 | 普通导出执行能力 | 可直接复用为导出执行基础组 | 是，需要叠加证据导出场景 |
| `group_logistics_export_manager` | 可看全部导出任务 | 导出管理能力 | 可直接复用为导出管理基础组 | 是，需要区分普通导出与证据导出 |
| `group_logistics_trace_event_manager` | 全部留痕事件管理 | 留痕管理能力 | 可直接复用为留痕能力组 | 是，需要从“manager”语义过渡到租户内角色矩阵 |
| `group_logistics_trace_manager` | 证据与异常全量管理 | 证据管理、异常管理、补链管理能力 | 可直接复用为能力基础组 | 是，需要拆成更细能力 |
| `group_logistics_profile_manager` | 基础资料管理 | 主数据维护能力 | 可直接复用 | 否 |
| `base.group_user` 上的主链只读 access | 普通登录用户可读主链对象 | 只读查看基础能力 | 可直接复用 | 是，需要限制不要过宽扩到高风险对象写入 |
| `base.group_user` 上的 `trace/evidence/exception create` | 普通登录用户可创建留痕、证据、异常 | 作为历史骨架可参考 | 不建议原样照搬 | 是，需按角色拆细 |

## 8. 哪些可以直接复用

下面这些可以直接复用，不需要推翻重做：

### 8.1 机制层

- `groups + access + rule + 页面显隐 + 模型校验` 这套组合

### 8.2 现有“本人 / manager”规则模式

例如：

- 导入任务：本人可看自己的、manager 可看全部
- 导出任务：执行人看自己的、manager 看全部
- 证据：上传人看自己的、manager 看全部
- 异常：上报人看自己的、manager 看全部

这套模式非常适合继续作为企业隔离 `P1` 的基础模板。

### 8.3 主链对象 manager 组

- `group_logistics_dispatch_manager`
- `group_logistics_trace_event_manager`
- `group_logistics_trace_manager`
- `group_logistics_profile_manager`

这些都可以继续保留，只是需要重新挂到新的角色矩阵解释下。

## 9. 哪些不能原样照搬

### 9.1 `base.group_user` 过宽写权限

当前若继续让所有普通登录用户默认拥有：

- 创建留痕
- 创建证据
- 创建异常

在企业隔离 `P1` 下通常会偏宽。

更合理的做法是：

- 留痕提交交给仓库 / 调度类角色
- 图片导入交给图片导入 / 审计类角色
- 异常提报交给调度 / 客服或授权业务角色

按当前进一步收口后，可再简化为：

- 留痕提交主要交给调度 / 客服或专门授权角色
- 图片导入交给图片导入 / 现场工作人员
- 现场工作人员可承担留痕提交

### 9.2 “manager” 语义直接等于“租户管理员”

现有很多组名里都叫 `manager`，但它们的管理范围其实不完全相同。

在企业隔离 `P1` 下不能简单理解为：

- 所有 manager 组 = 同一个租户管理员

更稳的做法是：

- 保留 manager 组作为能力组
- 再由租户内角色去组合这些能力组

### 9.3 证据与异常共用同一 manager 组的现状

当前 `exception` 直接复用 `logistics_trace_evidence.group_logistics_trace_manager`。

这说明：

- 当前能跑
- 但语义不够细

后续在企业隔离 `P1` 下更适合拆分成：

- 证据管理能力
- 异常处理能力
- 图片补链能力

## 10. 企业隔离 `P1` 推荐复用策略

### 10.1 先保留基础角色

建议继续以这 5 类角色做业务理解：

- 租户管理员
- 调度 / 客服
- 图片导入 / 现场工作人员
- 只读查看人员

### 10.2 再通过能力组挂实现

角色不一定直接等于一个组，更适合由多个能力组组合而成：

- 主链管理能力
- 留痕管理能力
- 图片导入能力
- 图片审计 / 补链能力
- 导出执行能力
- 导出管理能力
- 异常处理能力
- 主数据维护能力

### 10.3 推荐映射关系

| `P1` 角色 | 推荐复用的现有能力骨架 | 还需补的能力 |
| --- | --- | --- |
| 租户管理员 | `group_logistics_dispatch_manager`、`group_logistics_trace_event_manager`、`group_logistics_trace_manager`、`group_logistics_export_manager`、`group_logistics_profile_manager` | 租户级统一解释、角色快照、按钮与模型三层一致校验 |
| 调度 / 客服 | `group_logistics_dispatch_manager` 的部分能力、异常现有对象权限 | 异常关闭是否开放、证据导出是否开放、跨页面处理动作限制 |
| 图片导入 / 现场工作人员 | `group_logistics_import_manager` 的部分能力、主链只读能力、部分 `trace_event` 提交能力 | `image_package` 上传、本人成果查看、基础只读、留痕提交，不默认开放补链重试与异常处理 |
| 只读查看人员 | 主链只读 access、本人相关只读规则模板 | 导出默认关闭、处理默认关闭、敏感详情按需再控 |

## 11. 当前最需要补强的点

### 11.1 从“本人 / manager”升级到“角色 + 能力”

当前规则模式是一个很好的起点，但还不够支撑：

- 查看
- 上传
- 处理
- 导出

四类动作的细分。

### 11.2 把权限解释从“模块局部组”升级到“租户内统一矩阵”

当前每个模块各有自己的 manager 语义。

企业隔离 `P1` 下应统一改成：

- 业务角色怎么理解
- 这些角色组合了哪些能力组
- 哪些动作一定要模型层兜底

### 11.3 对 `image_package` 单独补权限

当前导入权限更多围绕标准主链导入。

企业隔离 `P1` 下必须单独补：

- 图片包上传
- 命中结果查看
- 补链失败查看
- 人工补链 / 重试

## 12. 当前建议

当前最稳的推进方式不是重做全部权限，而是：

1. 保留 Odoo 原生权限承载层
2. 保留现有自定义模块权限骨架
3. 用企业隔离 `P1` 角色矩阵重新解释这些组
4. 对过宽的 `base.group_user` 写权限做收口
5. 对 `image_package`、异常关闭、证据导出补专项能力组

## 13. 一句话结论

现有 Odoo 原生权限体系和我们已有模块权限划分都可以被企业隔离 `P1` 大量复用；真正要做的不是另起一套权限系统，而是把现有“模块局部权限”统一收口成“租户库内角色矩阵 + 能力组”的解释和实现。
