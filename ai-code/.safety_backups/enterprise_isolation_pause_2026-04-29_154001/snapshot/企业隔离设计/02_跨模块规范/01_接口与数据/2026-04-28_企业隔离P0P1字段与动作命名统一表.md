# 2026-04-28 企业隔离 `P0 / P1` 字段与动作命名统一表

## 1. 文档定位

- 本文用于统一当前企业隔离 `P0 / P1` 里几个最容易漂移的命名点。
- 本文不替代字段落位稿和权限落位表，而是提供统一命名口径。
- 本文首轮重点覆盖：
  - `image_package`
  - 补链状态
  - 异常处理动作
  - 权限组命名

## 2. 命名总原则

- 优先使用简短、稳定、团队可直接读懂的英文单词。
- 页面中文文案与模型 / 字段 / 枚举英文值分开管理，不把中文直接落入技术字段值。
- 首轮 `P1` 不为命名洁癖重构大范围历史字段，只收口新增项和高风险项。
- 同一概念只保留一个主名称，避免“同义词并存”。

## 3. 对象与任务命名

### 3.1 `image_package`

| 项目 | 建议命名 | 说明 | 不建议 |
| --- | --- | --- | --- |
| 任务分类值 | `image_package` | 用于标识图片包类任务 | `image_pkg`、`photo_package`、`picture_package` |
| 中文显示 | 图片包 | 给业务侧阅读 | 图片批、图片任务包、照片包混用 |
| 对应对照值 | `dispatch_main` | 主数据导入链任务 | `main_dispatch` |

### 3.2 导入审计链

建议继续统一为：

- `import_source_file`
- `import_task`
- `import_task_line`
- `import_error_line`

不建议同时混用：

- `import_batch`
- `import_row`
- `import_result_line`

除非它们明确是现有模型名且不做本轮重构。

## 4. 图片命中与补链状态命名

### 4.1 `match_status`

| 状态值 | 中文理解 | 使用场景 |
| --- | --- | --- |
| `unmatched` | 未命中 | 尚未命中任何候选对象 |
| `matched` | 已命中 | 已命中候选对象 |
| `ambiguous` | 命中歧义 | 命中多个候选，需要人工判断 |
| `invalid` | 无效数据 | 数据缺失或格式错误 |

说明：

- `match_status` 解决的是“识别到候选没有”。
- 不用它表达“正式证据是否挂上”。

### 4.2 `match_method`

| 状态值 | 中文理解 |
| --- | --- |
| `waybill_customer_line` | 运单号 + 门店结构行命中 |
| `waybill_store` | 运单号 + 门店编码命中 |
| `waybill_only` | 仅运单号命中 |
| `manual` | 人工确认命中 |

### 4.3 `link_status`

| 状态值 | 中文理解 | 使用场景 |
| --- | --- | --- |
| `pending` | 待补链 | 已识别候选但未正式挂证据 |
| `linked` | 已补链 | 已正式挂到 `trace_event / evidence` |
| `failed` | 补链失败 | 自动或人工补链失败 |
| `skipped` | 跳过 | 人工确认本轮不处理 |

说明：

- `link_status` 解决的是“正式证据有没有挂上”。
- 不建议把 `matched / unmatched` 再复用到补链状态。

### 4.4 辅助字段命名

建议统一：

- `match_waybill_no`
- `match_customer_line_no`
- `match_store_no`
- `candidate_waybill_id`
- `candidate_customer_line_id`
- `candidate_trace_event_id`
- `link_fail_reason`
- `link_retry_count`
- `manual_review_flag`

不建议同时出现：

- `candidate_waybill`
- `match_waybill`
- `waybill_candidate_id`

这类语序混乱的并行版本。

## 5. 异常状态与处理动作命名

### 5.1 异常状态

建议继续统一为：

- `draft`
- `open`
- `processing`
- `resolved`
- `closed`
- `cancelled`

说明：

- 当前 `P1` 页面主流口径优先围绕 `open -> processing -> resolved -> closed`
- `cancelled` 保留为兼容最终态

### 5.2 异常处理动作

| 动作场景 | 建议方法名 | 中文理解 |
| --- | --- | --- |
| 进入处理中 | `action_mark_processing` | 标记为处理中 |
| 标记已解决 | `action_mark_resolved` | 标记为已解决 |
| 标记已关闭 | `action_mark_closed` | 标记为已关闭 |

如后续需要补：

| 动作场景 | 建议方法名 | 中文理解 |
| --- | --- | --- |
| 取消异常 | `action_mark_cancelled` | 标记为已取消 |
| 回跳运单 | `action_open_waybill` | 打开相关运单 |
| 回跳留痕 | `action_open_trace_event` | 打开相关留痕 |
| 回跳批次 | `action_open_batch` | 打开相关批次 |
| 查看证据 | `action_open_evidence` | 打开相关证据 |

### 5.3 处理日志动作类型

建议继续统一为：

- `create`
- `state_change`
- `note`

不建议再平行引入：

- `comment`
- `update`
- `status_update`

除非后续确实扩展日志体系。

## 6. 权限组命名

## 6.1 命名原则

- 基础角色组用 `group_logistics_<role>` 风格。
- 专项能力组用 `group_logistics_<ability>` 风格。
- 不在组名里混入页面名、按钮名或临时业务说法。

### 6.2 基础角色组建议

| 中文角色 | 建议组名 |
| --- | --- |
| 租户管理员 | `group_logistics_tenant_admin` |
| 调度 / 客服 | `group_logistics_operator` |
| 图片导入 / 现场工作人员 | `group_logistics_field_image_operator` |
| 只读查看员 | `group_logistics_readonly` |

### 6.3 专项能力组建议

| 中文能力 | 建议组名 |
| --- | --- |
| 证据导出 | `group_logistics_evidence_export` |
| 图片补链 / 审计 | `group_logistics_image_audit` |
| 异常高级处理 | `group_logistics_exception_advanced` |
| 主数据维护 | `group_logistics_profile_manager` |

### 6.4 现有组复用时的命名说明

现有组如：

- `group_logistics_dispatch_manager`
- `group_logistics_import_manager`
- `group_logistics_export_user`
- `group_logistics_export_manager`
- `group_logistics_trace_event_manager`
- `group_logistics_trace_manager`

首轮可以继续保留，但在新设计稿、排期表和评审口径里，建议统一用“中文角色 / 中文能力”先说清楚，再映射到现有组名。

## 7. 页面与摘要入口命名

建议统一使用：

- 留痕摘要区
- 证据摘要区
- 异常摘要区
- 查看全部留痕
- 查看全部证据
- 查看全部异常
- 图片预览入口

不建议同时混用：

- 留痕面板 / 留痕块 / 留痕卡片
- 证据区 / 图片区 / 结果区

除非特指不同组件。

## 8. 推荐落地方式

1. 先按本文统一新加字段与新加动作名
2. 再把排期表、联调用例和模块改动清单里的说法同步到这一套
3. 对已有历史字段，如不改代码，也至少在文档里注明它对应的现行口径

## 9. 一句话收口

这份统一表的作用，不是把命名做成完美词典，而是把 `P0 / P1` 当前最容易漂移的字段、状态、动作和权限组，收成一套团队能持续复用的统一说法。
