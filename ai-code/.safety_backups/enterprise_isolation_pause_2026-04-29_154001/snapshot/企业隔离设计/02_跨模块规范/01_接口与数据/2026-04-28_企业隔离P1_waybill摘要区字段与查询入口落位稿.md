# 2026-04-28 企业隔离 `P1` `waybill` 摘要区字段与查询入口落位稿

## 1. 文档定位

- 本文用于把 `waybill` 主阅读页下的摘要区设计进一步压成字段与查询入口落位稿。
- 本文默认只覆盖 `P1` 首轮最小闭环，不扩展到完整运营看板。
- 本文重点回答：
  - `waybill` 页哪些摘要字段必须有
  - 这些字段建议落模型还是落查询
  - 查询入口按什么对象维度收口

## 3. 设计原则

- `waybill` 是当前 `P1` 主阅读入口
- 摘要字段服务于阅读与跳转，不替代正式对象
- 能稳定聚合的字段优先做摘要字段
- 详情型数据优先通过查询入口反开，不在 `waybill` 页硬堆全量字段

## 4. 摘要区分层

当前 `waybill` 摘要区建议拆成四块：

- 留痕摘要区
- 证据摘要区
- 异常摘要区
- 业务明细区

本文只细化前三块和它们的查询入口。

## 6. 查询入口落位建议

### 6.1 留痕入口

建议最小入口：

- 查看全部留痕
- 查看最新留痕详情

建议查询维度：

- 按 `waybill_id`
- 必要时带 `batch_id` 做上层回跳

### 6.2 证据入口

建议最小入口：

- 查看全部证据
- 查看最近图片
- 导出证据
- 查看补链失败结果

建议查询维度：

- 按 `waybill_id`
- 详情页再反开 `trace_event_id`

### 6.3 异常入口

建议最小入口：

- 查看全部异常
- 打开最新异常详情

建议查询维度：

- 按 `waybill_id`
- 详情页再反开 `trace_event_id / evidence`

## 7. 字段 vs 查询的取舍原则

### 7.1 建议直接落 `waybill` 聚合字段的内容

- 总数
- 最近时间
- 最近类型
- 最近对象主键

原因：

- 页面读取频率高
- 摘要区展示稳定
- 适合做 smart button 和角标

### 7.2 建议走查询入口即时取数的内容

- 全量时间线
- 全量图片列表
- 全量异常处理日志
- 补链失败明细

原因：

- 数据量更大
- 变化更频繁
- 不适合全部堆在 `waybill` 主对象字段上

## 8. 最小查询入口清单

建议首轮至少有以下统一查询入口：

| 入口 | 建议对象维度 | 主要用途 |
| --- | --- | --- |
| `waybill trace summary` | `waybill_id` | 摘要区留痕汇总 |
| `waybill trace list` | `waybill_id` | 查看全部留痕 |
| `waybill evidence summary` | `waybill_id` | 摘要区证据汇总 |
| `waybill evidence list` | `waybill_id` | 查看全部证据 |
| `waybill exception summary` | `waybill_id` | 摘要区异常汇总 |
| `waybill exception list` | `waybill_id` | 查看全部异常 |

## 9. 与权限的配合要求

- 摘要区能看到，不等于能点进所有详情
- 导出入口必须单独走导出权限校验
- 补链失败入口只对图片审计类角色开放
- 异常关闭动作不应放进摘要区直接处理

## 10. 首轮实现优先级

### 第 0 优先级

- `trace_count`
- `latest_trace_time`
- `evidence_count`
- `latest_image_access_key`
- `open_exception_count`
- `latest_exception_time`

### 第 1 优先级

- `latest_trace_event_type`
- `latest_exception_type`
- `highest_exception_status`
- `link_failed_image_count`

### 第 2 优先级

- 更细场景码聚合
- 更细标签与告警提示

## 11. 一句话收口

`waybill` 摘要区设计的关键不是把所有明细塞进主对象，而是只沉淀最稳定、最常读的聚合字段，再把全量阅读统一交给按 `waybill_id` 收口的查询入口。
