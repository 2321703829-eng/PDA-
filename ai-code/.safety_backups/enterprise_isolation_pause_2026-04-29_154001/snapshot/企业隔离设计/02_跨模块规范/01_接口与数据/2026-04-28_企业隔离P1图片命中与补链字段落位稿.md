# 2026-04-28 企业隔离 `P1` 图片命中与补链字段落位稿

## 1. 文档定位

- 本文用于把 `evidence` 细稿中的图片命中与补链规则进一步压成字段落位稿。
- 本文不重新讨论大方向，只回答实现层最关心的问题：
  - 字段落在哪
  - 字段分成哪几层
  - 哪些字段是命中辅助，哪些字段是正式补链状态

## 2. 前置基线

本文以前置文档为准：

- `2026-04-27_企业隔离P1_evidence图片命中补链导出与审计细稿.md`
- `2026-04-27_企业隔离P1_waybill主阅读下的trace细稿.md`
- `../04_实施规范/2026-04-27_企业隔离P1_开发任务拆分单_v2.md`

## 3. 设计原则

- 正式证据对象继续围绕 `trace_event_id`
- `customer_line` 只做命中辅助层，不做正式主挂点
- 命中状态与补链状态分开，不混成一个字段
- 自动命中失败要有明确失败状态，不能直接写坏正式证据链

## 4. 字段分层

### 4.1 导入任务层

建议落在 `image_package` 或图片导入任务对象上：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `task_type` | selection | 固定区分 `image_package` |
| `source_file_id` | many2one | 对应导入源文件 |
| `import_status` | selection | 导入任务整体状态 |
| `matched_count` | integer | 命中成功数 |
| `unmatched_count` | integer | 命中失败数 |
| `linked_count` | integer | 正式补链成功数 |
| `link_failed_count` | integer | 正式补链失败数 |

### 4.2 单图片元数据层

建议落在图片元数据或导入明细对象上：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `image_access_key` | char | 图片存储访问键 |
| `source_filename` | char | 原文件名 |
| `scene_code` | selection/char | 场景码 |
| `capture_time` | datetime | 图片采集时间 |
| `waybill_no` | char | 命中主键之一 |
| `customer_line_no` | char | 命中辅助键之一 |
| `store_no` | char | 命中辅助键之一 |
| `matched_waybill_id` | many2one | 命中到的运单 |
| `matched_customer_line_id` | many2one | 命中到的结构层节点 |
| `match_status` | selection | 命中状态 |
| `match_remark` | text | 命中解释说明 |

### 4.3 正式证据补链层

建议落在正式证据对象或专门补链状态对象上：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `trace_event_id` | many2one | 正式主挂点 |
| `link_status` | selection | 补链状态 |
| `link_mode` | selection | 自动 / 人工 |
| `link_fail_reason` | text | 失败原因 |
| `linked_at` | datetime | 补链完成时间 |
| `linked_by` | many2one | 补链执行人 |
| `retry_count` | integer | 重试次数 |

## 5. 推荐状态枚举

### 5.1 `match_status`

建议最小集合：

- `pending`
- `matched`
- `ambiguous`
- `unmatched`

说明：

- `pending`：还未执行命中
- `matched`：结构层命中成功
- `ambiguous`：候选不唯一，需人工处理
- `unmatched`：未命中

### 5.2 `link_status`

建议最小集合：

- `pending`
- `linked`
- `failed`
- `manual_review`

说明：

- `pending`：尚未进入正式补链
- `linked`：已挂到正式 `trace_event`
- `failed`：补链失败
- `manual_review`：需要人工处理后再补链

## 6. 命中优先级落位

建议把命中规则明确落为：

1. `waybill_no + customer_line_no`
2. `waybill_no + store_no`
3. `waybill_no` 仅做候选，不直接自动补链

实现要求：

- 命中成功先回写 `matched_waybill_id`
- 如命中到结构层，再回写 `matched_customer_line_id`
- 即使命中到了 `customer_line`，也不能跳过 `trace_event_id`

## 7. 补链候选上下文落位

建议至少保留这些候选字段：

| 字段 | 作用 |
| --- | --- |
| `matched_waybill_id` | 正式主对象上下文 |
| `scene_code` | 场景候选 |
| `capture_time` | 时间窗判断 |
| `candidate_trace_event_ids` 或等价结果 | 候选事件集合 |
| `selected_trace_event_id` | 最终选中的正式事件 |

说明：

- 候选集合可以是临时计算结果，也可以是可审计字段
- 首轮如果不单独落候选集合表，至少要有失败说明和人工选择入口

## 8. 与 `waybill` 摘要区的接口关系

字段设计最终要服务于：

- `waybill` 证据摘要区
- `waybill` 图片预览入口
- 导入结果页
- 补链失败审计页

因此至少要保证：

- 能按 `waybill` 快速聚合证据数
- 能按 `waybill` 快速读最近图片
- 能按 `waybill` 快速读补链失败数

## 9. 首轮开发优先级

### 第 0 优先级

- `matched_waybill_id`
- `matched_customer_line_id`
- `match_status`
- `trace_event_id`
- `link_status`
- `link_fail_reason`

### 第 1 优先级

- `scene_code`
- `capture_time`
- `retry_count`
- `link_mode`
- `linked_at`
- `linked_by`

### 第 2 优先级

- 更细的候选集合审计字段
- 更完整的人工补链痕迹字段

## 10. 一句话收口

图片命中与补链的字段设计要始终坚持两段式思路：先把图片稳定命中到 `waybill` 和可选结构层，再把正式证据稳定挂回 `trace_event`。
