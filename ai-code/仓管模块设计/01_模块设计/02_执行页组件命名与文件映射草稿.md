## 1. 文档定位

本文件用于从：

- `四类主单统一页面结构规范草稿 v0.1`
- `执行页统一交互规范草稿 v0.1`

两份规范中，再往前端实现层推进半步，专门沉淀“执行页组件命名与文件映射”的统一规则。

当前重点不是给出全部真实代码实现，而是先固定：

- 执行页入口对象如何命名
- OWL 组件和模板如何命名
- 文件与目录如何组织
- 四类执行页如何共享公共容器与差异化子组件

## 2. 范围与边界

### 2.1 当前纳入范围

- 收货执行页
- 上架执行页
- 拣货执行页
- 复核执行页
- 执行页公共容器
- 页内提示条 / toast / confirm dialog 的统一承载层
- `logistics_wms_web` 中相关文件与目录组织

### 2.2 当前不纳入范围

- 普通列表页 / 详情页 XML 全量拆分细节
- 全量 manifest 资产清单最终版本
- 具体 OWL hooks 与 service 实现细节
- PDA 专用前端最终目录结构
- 测试文件命名与测试目录设计

## 3. 统一命名目标

当前更推荐执行页相关命名同时满足这 4 个目标：

1. 看名字就知道这是执行页对象，不会和普通详情页对象混淆
2. 看名字就知道对应哪一种动作语义：`receive / putaway / pick / check`
3. 看名字就知道它属于：
   - 入口对象
   - 页面容器
   - 局部组件
   - 模板
   - 文件
4. 能与已确定的 `logistics_wms_*` 前缀体系保持一致

一句话收口：

`执行页命名应同时表达“业务动作 + 页面层级 + 技术对象类型”。`

## 4. 命名对象范围

当前建议这份规范主要约束以下对象：

- `client action` XML ID
- `client action tag`
- OWL 页面容器组件名
- OWL 子组件名
- QWeb / OWL 模板 `t-name`
- JS / XML / SCSS 文件名
- 公共目录与四类动作子目录名

当前不建议把以下对象也一并锁死在本版：

- service 名称全集
- 所有 store / state 管理对象名称
- 所有 API DTO 名称

这些后续可以在实现阶段再继续细化。

## 5. 执行页入口对象命名规则

### 5.1 client action XML ID

当前更推荐统一采用：

- `client_action_logistics_wms_receive_execution`
- `client_action_logistics_wms_putaway_execution`
- `client_action_logistics_wms_pick_execution`
- `client_action_logistics_wms_check_execution`

统一规则是：

- 前缀固定：`client_action_logistics_wms_`
- 中间固定：动作语义
- 后缀固定：`_execution`

### 5.2 client action tag

当前更推荐统一采用：

- `logistics_wms.receive_execution`
- `logistics_wms.putaway_execution`
- `logistics_wms.pick_execution`
- `logistics_wms.check_execution`

统一规则是：

- 前缀固定：`logistics_wms.`
- 中间固定：动作语义
- 后缀固定：`_execution`

### 5.3 一句话入口对象口径

`XML ID 使用 client_action_logistics_wms_*_execution，前端注册 tag 使用 logistics_wms.*_execution。`

## 6. OWL 组件与模板命名规则

### 6.1 页面容器组件名

当前更推荐四类页面容器组件统一采用 PascalCase：

- `ReceiveExecutionPage`
- `PutawayExecutionPage`
- `PickExecutionPage`
- `CheckExecutionPage`

公共容器组件建议：

- `ExecutionPageLayout`
- `ExecutionPendingTable`
- `ExecutionActionPanel`
- `ExecutionBottomTabs`
- `ExecutionHintBar`

### 6.2 模板 `t-name`

当前更推荐统一采用：

- `logistics_wms.ReceiveExecutionPage`
- `logistics_wms.PutawayExecutionPage`
- `logistics_wms.PickExecutionPage`
- `logistics_wms.CheckExecutionPage`

公共模板建议：

- `logistics_wms.ExecutionPageLayout`
- `logistics_wms.ExecutionPendingTable`
- `logistics_wms.ExecutionActionPanel`
- `logistics_wms.ExecutionBottomTabs`
- `logistics_wms.ExecutionHintBar`

### 6.3 子组件命名原则

当前更推荐：

- 页面级组件：`动作语义 + ExecutionPage`
- 公共容器：`Execution + 区块语义`
- 业务特有子块：`动作语义 + 区块语义`

例如：

- `ReceiveQuantityBlock`
- `PutawayTargetLocationBlock`
- `PickBatchBlock`
- `CheckResultBlock`

一句话收口：

`页面容器按动作命名，公共区块按 Execution 前缀命名，业务特有块按动作 + 区块命名。`

## 9. 资产与注册层的当前口径

### 9.1 当前推荐的注册边界

当前更推荐：

- client action 统一在 `logistics_wms_web` 注册
- 普通列表 / 详情仍优先走业务模块 XML 视图
- 执行页强交互统一沉到前端容器层

### 9.2 当前推荐的 asset 口径

当前更推荐：

- 执行页 JS / XML / SCSS 统一进入 `logistics_wms_web` 的 backend asset
- 不把四类执行页分散塞进多个业务模块的 asset bundle

这样更利于：

- 统一升级
- 统一 rebuild
- 统一排查模板 / registry / asset 问题

### 9.3 当前不建议的一期做法

当前不建议：

- 每个业务模块各自注册一套执行页容器
- 公共组件复制到四个动作目录里各自维护
- client action tag、组件名、文件名各走各的命名风格

### 9.4 当前推荐的一句话落地口径

`执行页入口、注册、公共组件和 asset 统一收在 logistics_wms_web；业务模块继续承接模型与普通视图。`

## 10. 执行页 service / hook 命名规则

当前更推荐把执行页前端中的 `service` 与 `hook` 命名，继续收敛到和：

- client action
- 页面组件
- 模板
- 文件命名

同一条语义线上，避免出现“入口叫一套、组件叫一套、service 又叫另一套”的情况。

### 10.1 当前推荐的 service 命名目标

当前建议 service 命名同时满足：

1. 一眼能看出它服务于执行页，而不是普通详情页
2. 一眼能看出它是公共执行 service，还是某一动作专用 service
3. 能和 `logistics_wms_web` 下的公共组件命名保持一致

一句话收口：

`service 命名应优先表达“执行页语义 + 服务职责”，而不是只表达技术动作。`

### 10.2 当前推荐的公共 service 命名草稿

当前更推荐公共 service 统一采用：

- `executionFeedbackService`
- `executionNavigationService`
- `executionDraftInputService`
- `executionScanService`

这些名称分别适合承接：

- 页内提示条 / toast / confirm dialog 的统一反馈调用
- 执行页内返回、切换、跳下一条等导航动作
- 未保存输入、清空输入、脏表单判断
- PDA / 扫码输入接入

这里建议继续保持：

- 公共执行能力统一以 `execution` 为前缀
- 不要在公共层掺入太强的 `receive / putaway / pick / check` 语义

### 10.3 当前推荐的动作专用 service 命名草稿

如果后续四类执行页确实需要动作专用 service，当前更推荐：

- `receiveExecutionService`
- `putawayExecutionService`
- `pickExecutionService`
- `checkExecutionService`

这些名称更适合承接：

- 动作专属字段预处理
- 动作专属提交流程封装
- 动作专属校验规则组合

这里的统一原则是：

- 公共能力走 `executionXxxService`
- 动作专属能力走 `动作语义 + ExecutionService`

### 10.4 当前推荐的 hook 命名草稿

当前更推荐 hook 统一采用：

- `useExecutionPendingSelection`
- `useExecutionActionState`
- `useExecutionFeedback`
- `useExecutionUnsavedGuard`
- `useExecutionScanner`

如果后续需要动作专用 hook，可按下面方式组织：

- `useReceiveExecutionFields`
- `usePutawayExecutionFields`
- `usePickExecutionFields`
- `useCheckExecutionFields`

当前统一原则是：

- 公共 hook：`useExecutionXxx`
- 动作专用 hook：`use动作语义ExecutionXxx`

### 10.5 当前推荐的一句话 service / hook 口径

`公共层统一用 execution 前缀，动作专用层统一用 动作语义 + Execution 前缀；service 表职责，hook 表状态与交互封装。`

## 11. manifest asset 片段示例

当前更推荐在 `logistics_wms_web` 的 `__manifest__.py` 中，把执行页相关前端资源统一收进同一个 backend asset 片段，而不是分散到多个业务模块里各自维护。

### 11.1 当前推荐的组织原则

当前建议遵守以下原则：

1. 执行页公共资源先于动作页资源加载
2. JS / XML / SCSS 按“公共 -> 动作”顺序组织
3. 四类执行页统一进入同一个 backend bundle
4. 不把执行页资源拆散塞进 `logistics_wms_inbound`、`logistics_wms_outbound` 等业务模块的前端 bundle

一句话收口：

`执行页 asset 统一收在 logistics_wms_web，并按公共层优先、动作层后置的顺序组织。`

### 11.3 当前推荐的加载顺序理解

当前更推荐按下面的顺序理解：

**1. 公共容器先加载**

例如：

- `execution_page_layout`
- `execution_pending_table`
- `execution_action_panel`
- `execution_bottom_tabs`
- `execution_hint_bar`

这些组件是四类执行页共用的底层承载。

**2. 动作页后加载**

例如：

- `receive_execution_page`
- `putaway_execution_page`
- `pick_execution_page`
- `check_execution_page`

这些组件依赖公共容器，因此应放在公共容器后面。

### 11.4 当前不建议的一期做法

当前不建议：

- 在业务模块 manifest 中重复声明执行页 asset
- 用很多通配符一次性把整个目录全打进 bundle
- 在未明确顺序的情况下让动作页资源排在公共组件前面
- JS、XML、SCSS 完全无序混排

### 11.5 当前推荐的一句话 asset 片段口径

`manifest asset 片段应优先显式列出执行页公共资源，再列出四类动作页资源，统一进入 logistics_wms_web 的 backend asset。`

## 12. 与 odoo-frontend-asset-guard 相关的校验清单

当前更推荐在执行页真正联调或准备落地前，先按一份轻量但统一的校验清单过一遍，重点检查：

- asset 是否正确进 bundle
- client action 是否正确注册
- 模板是否正确加载
- JS / XML / SCSS 是否按既定顺序组织
- 普通页面与执行页的入口是否走对层级

这里虽然当前没有直接读取到本地 `odoo-frontend-asset-guard` 的 `SKILL.md` 文件，但按项目现有专题规范，已经可以先固定一版足够实用的校验清单。

### 12.1 asset 层校验

当前更推荐优先检查：

1. 执行页公共资源是否进入 `web.assets_backend`
2. 四类动作页资源是否进入同一 backend bundle
3. 公共资源是否排在动作页资源之前
4. 是否误把执行页资源分散到业务模块的前端 bundle

建议检查点：

- `__manifest__.py` 中 `assets` 配置
- 公共资源路径是否与目录规划一致
- 动作页资源路径是否与目录规划一致

### 12.2 client action / registry 校验

当前更推荐优先检查：

1. `client_action_logistics_wms_*_execution` 是否已定义
2. `logistics_wms.*_execution` tag 是否已注册
3. 详情页按钮或待处理入口是否跳转到正确的执行页入口
4. 是否出现“菜单、action、client action 命名不一致”的情况

建议检查点：

- XML ID 命名是否与规范一致
- 前端注册键是否与 XML 入口一致
- 按钮或入口动作是否指向正确对象

### 12.3 模板与组件校验

当前更推荐优先检查：

1. 页面容器组件名与模板 `t-name` 是否对应
2. 公共组件命名是否统一使用 `Execution` 前缀
3. 动作页组件命名是否统一使用 `动作语义 + ExecutionPage`
4. 是否出现模板文件名、组件名、模板名三者互不一致的情况

建议检查点：

- 组件类名
- 模板 `t-name`
- 文件名
- import 路径

### 12.4 文件与目录校验

当前更推荐优先检查：

1. 公共容器是否放在 `execution/common/`
2. 动作页是否放在各自语义目录下
3. JS / XML / SCSS 是否成组存在
4. 是否出现同一组件在多个动作目录中复制维护

建议检查点：

- `execution/common/`
- `execution/receive/`
- `execution/putaway/`
- `execution/pick/`
- `execution/check/`

### 12.5 页面入口层校验

当前更推荐优先检查：

1. 普通菜单是否仍进入 `act_window`
2. 执行入口是否主要来自详情页按钮与待处理列表动作
3. client action 是否没有直接挂成主菜单入口
4. 是否保持了：
   - `列表 -> 详情 -> 执行页`

这条主路径

### 12.6 当前不建议忽略的高风险点

当前特别不建议忽略以下问题：

- 只配了 JS 没配 XML 模板
- tag 已注册但 XML ID 未对上
- 资源顺序错误导致动作页早于公共组件加载
- 执行页资源散落多个模块，后续升级或重建时难排查
- 普通详情页和执行页重复维护同一套按钮 / 字段区块

### 12.7 当前推荐的一句话校验口径

`执行页前端联调前，至少应按 asset、registry、template、文件目录、入口路径五层做一次统一检查。`

## 13. 更细的公共组件拆分清单

当前更推荐把执行页公共组件继续拆成“页面壳层、列表层、录入层、反馈层、信息层”五组。  
这样既能让四类执行页共用更多组件，又不会把动作专属字段和逻辑过早塞进公共层。

### 13.1 页面壳层公共组件

当前更推荐优先沉淀这些页面壳层组件：

- `ExecutionPageLayout`
- `ExecutionTopContextBar`
- `ExecutionTopActions`
- `ExecutionMainSplitLayout`

它们分别适合承接：

- 整页布局骨架
- 顶部上下文区
- 顶部页面级按钮区
- 中部主从双栏容器

这里建议保持：

- 壳层只负责布局与插槽
- 不承接具体动作语义

### 13.2 左侧待处理区公共组件

当前更推荐优先沉淀这些列表层组件：

- `ExecutionPendingTable`
- `ExecutionPendingToolbar`
- `ExecutionPendingRowState`
- `ExecutionPendingEmptyState`

它们分别适合承接：

- 左侧标准表格
- 搜索 / 筛选 / 刷新工具条
- 行状态标签或状态小块
- 左侧空结果占位

这里建议保持：

- 统一基础列、统一排序、统一高亮逻辑沉到公共层
- 条码、批次、来源位、目标位这类差异列仍留给动作页配置

### 13.3 右侧执行区公共组件

当前更推荐优先沉淀这些录入层组件：

- `ExecutionActionPanel`
- `ExecutionCurrentItemSummary`
- `ExecutionPrimaryFields`
- `ExecutionPrimaryActions`
- `ExecutionSecondaryFields`

它们分别适合承接：

- 右侧主面板壳层
- 当前项摘要
- 本次处理关键字段区
- `确认本次 / 确认并下一条 / 完成本次记录 / 取消`
- 条件出现的次级字段区

这里建议保持：

- 公共层只统一录入区层次与按钮摆放
- 具体字段仍由收货 / 上架 / 拣货 / 复核各自注入

### 13.4 底部信息层公共组件

当前更推荐优先沉淀这些信息层组件：

- `ExecutionBottomTabs`
- `ExecutionProgressTab`
- `ExecutionLogTab`
- `ExecutionRelatedObjectsTab`
- `ExecutionEvidenceTab`

它们分别适合承接：

- 底部 tab 容器
- 进度摘要页签
- 执行日志页签
- 关联执行对象页签
- 证据 / 附件页签

这里建议保持：

- tab 容器与四个标准页签组件可先共用
- 页签内部字段的业务差异通过 props 或配置下沉

### 13.5 反馈层公共组件

当前更推荐优先沉淀这些反馈层组件：

- `ExecutionHintBar`
- `ExecutionToastBridge`
- `ExecutionConfirmDialog`
- `ExecutionUnsavedGuard`

它们分别适合承接：

- 页内提示条
- 成功 toast 调用桥
- 普通确认 / 危险确认弹窗
- 未保存输入离开拦截

这里建议保持：

- 成功 / 警告 / 错误语义统一
- 弹窗按钮顺序和文案模板统一
- 不在动作页各自重复造一套反馈逻辑

### 13.6 当前不建议的一期拆法

当前不建议：

- 一开始把公共组件拆得过碎
- 为四类执行页分别复制一套几乎相同的表格和面板
- 把动作专属字段写死在公共组件里
- 让公共组件直接依赖某一个业务模型的专属字段名

更稳的做法是：

- 先把布局、表格、反馈、tab 这类稳定层抽公共
- 动作差异通过配置、插槽、子组件注入

### 13.7 当前推荐的一句话公共组件口径

`公共组件先抽稳定结构层，不抽过深业务语义层；统一的是壳、表、tab、反馈，差异留给四类动作页自己承接。`
