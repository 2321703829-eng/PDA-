## 1. 文档定位

本文件用于从总讨论稿中抽出“出库单状态机”相关内容，形成独立专题草稿。

当前重点不是覆盖全部出库业务细节，而是先固定：

- 一期主状态机
- 普通取消边界
- 异常补充状态边界
- 拣货 / 复核失败时主状态停留口径
- 发货前与发货后异常的处理边界

## 2. 范围与边界

### 2.1 当前纳入范围

- 出库单一期主状态机
- 拣货、复核、待发货主流程状态
- 普通取消边界
- 异常补充状态设计方向
- 拣货失败 / 复核失败的主状态停留口径
- `waiting_ship` 与 `done` 的主线边界
- 待异常处理视图与详情页异常信息区

### 2.2 当前不纳入范围

- 全量出库单字段字典
- 拣货页 / 复核页执行交互细节
- 面单、承运商、包裹与装箱的深度规则
- 已发货后的逆向流程详细方案
- 完整异常中心或售后中心设计

## 3. 一期主状态机

当前一期更推荐出库单主状态机保持以下 8 个状态：

- `draft`
- `waiting_pick`
- `picking`
- `picked`
- `checking`
- `waiting_ship`
- `done`
- `cancel`

对应业务理解为：

- `draft`：草稿
- `waiting_pick`：待拣货
- `picking`：拣货中
- `picked`：已拣货待复核
- `checking`：复核中
- `waiting_ship`：待发货
- `done`：已发货完成
- `cancel`：已取消

当前不建议一期在 `picked` 与 `waiting_ship` 之间继续增加：

- `checked`

## 4. 主状态定义

### 4.1 `draft`

含义：

- 出库单已创建，但尚未进入正式出库执行

进入条件：

- 新建出库单
- 或导入后先落草稿

退出条件：

- 用户确认生效或提交，进入 `waiting_pick`
- 用户主动取消，进入 `cancel`

### 4.2 `waiting_pick`

含义：

- 出库单已生效，但尚未开始真实拣货动作

进入条件：

- `draft` 提交成功

退出条件：

- 开始拣货，进入 `picking`
- 未开始拣货前允许取消，进入 `cancel`

### 4.3 `picking`

含义：

- 已开始拣货，但尚未完成全部应拣内容

进入条件：

- 第一次正式开始拣货
- 或第一笔有效拣货动作产生

退出条件：

- 全部应拣内容完成，进入 `picked`
- 拣货过程中继续保持 `picking`

### 4.4 `picked`

含义：

- 拣货闭环完成，但尚未开始或尚未完成复核

进入条件：

- 全部应拣内容完成

退出条件：

- 开始复核，进入 `checking`

### 4.5 `checking`

含义：

- 已进入复核过程，但尚未完成复核闭环

进入条件：

- 第一次正式开始复核
- 或第一笔有效复核动作产生

退出条件：

- 复核完成，进入 `waiting_ship`
- 复核过程中继续保持 `checking`

### 4.6 `waiting_ship`

含义：

- 拣货与复核已完成，等待发货确认

进入条件：

- `checking` 完成

退出条件：

- 发货确认完成，进入 `done`

### 4.7 `done`

含义：

- 出库单已完成发货

进入条件：

- 发货确认完成

退出条件：

- 无正常退出，视为终态

### 4.8 `cancel`

含义：

- 在允许取消的阶段被取消

进入条件：

- `draft / waiting_pick` 阶段的普通取消

退出条件：

- 无正常退出，视为终态

## 5. 当前推荐的主状态推进原则

当前更推荐按以下原则推进行库单主状态：

1. 状态推进尽量由真实业务动作触发
2. 不建议仅靠人工手改状态推动主流程
3. 拣货完成前不进入 `picked`
4. 复核完成前不进入 `waiting_ship`
5. 发货确认完成前不进入 `done`

一句话收口：

`开始拣货，才进入 picking；全部拣完，才进入 picked；开始复核，才进入 checking；复核完成，才进入 waiting_ship；发货确认完成，才进入 done。`

## 6. 普通取消边界

当前一期更推荐的普通取消边界为：

### 6.1 允许普通取消

- `draft`
- `waiting_pick`

### 6.2 谨慎允许 / 原则上不建议普通取消

- `picking`
- `picked`
- `checking`

### 6.3 不建议直接取消

- `waiting_ship`
- `done`
- `cancel`

一句话收口：

`一期普通取消只开放到 draft / waiting_pick。`

## 7. 异常补充状态设计口径

当前更推荐出库单与入库单保持一致，采用：

- 主状态表达主流程位置
- 异常补充状态表达当前主线之外的问题

一期当前更推荐先预留轻量异常补充枚举：

- `terminated`
- `exception`
- `pending_action`

但业务启用层面，一期先只实际启用：

- `terminated`

当前更推荐：

- 不把异常直接塞进主状态字段
- 页面上主状态占主位
- 异常补充状态做次标签

## 8. 拣货 / 复核失败的处理口径

当前更推荐按“失败发生在哪个阶段，主状态就停在哪个阶段”来处理。

### 8.1 拣货失败

当前更推荐：

- 主状态停在 `picking`
- 异常补充状态挂外围

不建议：

- 失败后退回 `waiting_pick`

### 8.2 复核失败

当前更推荐：

- 主状态停在 `checking`
- 异常补充状态挂外围

不建议：

- 失败后退回 `picked`

一句话收口：

`拣货 / 复核失败时，主状态停在 picking / checking，异常挂外围。`

## 9. waiting_ship 与 done 的边界

### 9.1 `checked` 是否单独纳入主状态机

当前更推荐：

- 不单独新增 `checked`

主要因为：

- `checking` 已足够表达“进入复核”
- `waiting_ship` 已足够表达“复核完成后待发货”

### 9.2 `waiting_ship` 是否允许普通回退到 `checking`

当前更推荐：

- 原则上不走普通回退
- 如发货前发现问题，应通过异常处理或人工处理重新进入复核

当前不建议一期提供普通：

- “回退到 checking”按钮

### 9.3 `done` 后的边界

当前更推荐：

- `done` 仍是终态
- 一期不做从已发货回退的主流程按钮
- 后续如出现问题，走逆向 / 异常 / 履约或物流侧处理

### 9.4 发货前异常与发货后异常的边界

当前更推荐明确分成两类：

#### 发货前异常

- 仍属于仓管主线范围
- 可继续沿“主状态 + 异常补充状态”处理

#### 发货后异常

- 不再只是仓内执行异常
- 更接近物流 / 履约 / 逆向处理
- 不建议继续只靠出库单主状态机承接全部语义

## 10. 异常处理视图与异常信息区口径

当前更推荐：

- 一期应有轻量“待异常处理”视图
- 出库单详情页应单独有“异常处理信息区”

异常信息区一期最小展示建议为：

- 异常补充状态
- 原因
- 备注
- 处理人
- 时间

当前更推荐：

- 异常处理视图按仓库、货主、主状态、异常补充状态筛选
- 详情页头部仍先显示主状态，再补异常标签

## 11. 出库单按钮与状态联动矩阵

本节用于把前述出库单状态机进一步映射到详情页常见按钮与动作入口，形成一期更可执行的按钮基线。

### 11.1 当前纳入矩阵的按钮范围

当前先聚焦一批高频、关键按钮：

- `提交 / 生效`
- `取消`
- `开始拣货`
- `开始复核`
- `开始发货`
- `查看拣货记录`
- `查看复核记录`
- `查看发货确认记录`
- `终止（terminated）`
- `查看异常处理信息`

这里的原则是：

- 普通详情页先只收页面级 / 记录级按钮
- 执行页内的“确认本次”“完成本次记录”不在本节展开

### 11.2 按钮与状态联动的当前总原则

当前更推荐按以下原则统一理解：

1. `draft` 承接建单后确认与取消
2. `waiting_pick / picking` 承接拣货入口
3. `picked / checking` 承接复核入口
4. `waiting_ship` 承接发货确认入口
5. `done` 以查看与追溯为主，不再提供主流程推进按钮
6. `cancel` 以查看为主，不再提供普通主流程动作
7. `terminated` 作为危险动作下沉，不与主流程按钮抢主位

### 11.3 当前推荐的按钮矩阵

| 按钮 / 动作 | draft | waiting_pick | picking | picked | checking | waiting_ship | done | cancel |
|---|---|---|---|---|---|---|---|---|
| 提交 / 生效 | 是 | 否 | 否 | 否 | 否 | 否 | 否 | 否 |
| 取消 | 是 | 是 | 否 | 否 | 否 | 否 | 否 | 否 |
| 开始拣货 | 否 | 是 | 是 | 否 | 否 | 否 | 否 | 否 |
| 开始复核 | 否 | 否 | 否 | 是 | 是 | 否 | 否 | 否 |
| 开始发货 | 否 | 否 | 否 | 否 | 否 | 是 | 否 | 否 |
| 查看拣货记录 | 否 | 否 | 是 | 是 | 是 | 是 | 是 | 否 |
| 查看复核记录 | 否 | 否 | 否 | 否 | 是 | 是 | 是 | 否 |
| 查看发货确认记录 | 否 | 否 | 否 | 否 | 否 | 否 | 是 | 否 |
| 终止（terminated） | 否 | 否 | 是 | 否 | 是 | 否 | 否 | 否 |
| 查看异常处理信息 | 否 | 否 | 条件显示 | 否 | 条件显示 | 条件显示 | 条件显示 | 否 |

上表中的“是 / 否 / 条件显示”当前建议这样理解：

- `是`：一期默认可显示，仍需满足角色权限
- `否`：一期默认不显示
- `条件显示`：仅当存在异常补充状态或异常信息时显示

### 11.4 关键按钮的当前解释口径

#### A. `提交 / 生效`

当前更推荐：

- 只在 `draft` 显示
- 触发后主状态进入 `waiting_pick`

#### B. `取消`

当前更推荐：

- 只在 `draft / waiting_pick` 显示
- 一旦开始真实拣货，就不再作为普通按钮出现

#### C. `开始拣货`

当前更推荐：

- 在 `waiting_pick` 显示为主
- 在 `picking` 可继续显示为“继续拣货”语义
- 触发后进入或继续停留在 `picking`

#### D. `开始复核`

当前更推荐：

- 在 `picked` 显示为主
- 在 `checking` 可继续显示为“继续复核”语义
- 不在 `picking` 提前开放

#### E. `开始发货`

当前更推荐：

- 只在 `waiting_ship` 显示
- 不在 `checking` 提前开放
- 发货确认完成后主状态进入 `done`

#### F. `终止（terminated）`

当前更推荐：

- 只在 `picking / checking` 阶段开放
- 且仅对主管 / 异常处理权限角色可见
- 触发后主状态停在当前阶段
- 异常补充状态置为 `terminated`

### 11.5 按钮分层建议

当前更推荐在详情页上按以下层次放置：

#### 顶部主按钮区

优先承接：

- `提交 / 生效`
- `取消`
- `开始拣货`
- `开始复核`
- `开始发货`

#### 次级入口 / smart button 区

优先承接：

- `查看拣货记录`
- `查看复核记录`
- `查看发货确认记录`
- `查看异常处理信息`

#### 危险动作或更多菜单

优先承接：

- `终止（terminated）`

也就是说，`terminated` 当前不建议与普通主流程按钮并列抢主位。

### 11.6 当前不建议的一期做法

当前不建议一期采用以下做法：

- 在 `picking / checking` 继续保留普通 `取消`
- 在 `picked` 前提前开放“开始复核”
- 在 `checking` 前提前开放“开始发货”
- 在 `done` 上继续保留主流程推进按钮
- 把 `terminated` 直接放成和 `开始拣货 / 开始复核` 同层级的普通主按钮
- 让“查看异常处理信息”长期占位但没有异常内容

### 11.7 当前阶段关于按钮与状态联动的统一收口

截至当前阶段，更推荐统一收敛为：

1. `draft` 负责提交与取消
2. `waiting_pick / picking` 负责拣货入口
3. `picked / checking` 负责复核入口
4. `waiting_ship` 负责发货入口
5. `done / cancel` 以查看与追溯为主
6. `terminated` 只在 `picking / checking` 阶段开放，且作为危险动作下沉

## 12. 出库单状态与执行记录的联动矩阵

本节用于把出库单主状态与三类关键执行记录进一步挂钩：

- `pick record`
- `check record`
- `ship confirm record`

当前目标不是穷尽所有细节，而是先固定“一期主状态大致对应什么执行记录状态和行为”。

### 12.1 当前联动的统一原则

当前更推荐按以下原则理解：

1. 主状态表达主单所处业务阶段
2. 执行记录表达该阶段内已发生或正在发生的动作
3. 主状态不直接替代执行记录
4. 执行记录也不反向替代主状态
5. 页面展示时，主单状态与执行记录进度应互相印证

### 12.2 当前推荐的联动矩阵

| 主状态 | 拣货记录（pick record） | 复核记录（check record） | 发货确认记录（ship confirm） | 当前理解 |
|---|---|---|---|---|
| `draft` | 无 | 无 | 无 | 尚未进入执行 |
| `waiting_pick` | 无 | 无 | 无 | 已生效，待开始拣货 |
| `picking` | 可存在 `draft / in_progress / done` | 无 | 无 | 已开始拣货，允许分批、多次拣货 |
| `picked` | 已存在且应全部达到 `done` | 无或仅预备 | 无 | 拣货闭环完成，尚未进入正式复核 |
| `checking` | 已完成 | 可存在 `draft / in_progress / done` | 无 | 已开始复核，允许分批、多次复核 |
| `waiting_ship` | 已完成 | 已完成 | 无 | 拣货与复核闭环完成，待发货确认 |
| `done` | 已完成 | 已完成 | 已完成 | 发货确认完成，出库闭环完成 |
| `cancel` | 无 | 无 | 无 | 未进入真实执行即取消 |

### 12.3 当前推荐的状态判断口径

#### A. 从 `waiting_pick` 到 `picking`

当前更推荐以“第一笔有效拣货动作或正式开始拣货”为判断点。

也就是说：

- 不是看页面有没有打开
- 而是看是否真实进入拣货执行

#### B. 从 `picking` 到 `picked`

当前更推荐以“应拣内容全部完成”为判断点。

也就是说：

- `pick record` 可以有多条
- 但主单进入 `picked` 时，拣货闭环应已完成

#### C. 从 `picked` 到 `checking`

当前更推荐以“第一笔有效复核动作或正式开始复核”为判断点。

#### D. 从 `checking` 到 `waiting_ship`

当前更推荐以“复核闭环完成”为判断点。

#### E. 从 `waiting_ship` 到 `done`

当前更推荐以“发货确认完成”为判断点。

### 12.4 终止场景下的联动口径

若发生 `terminated`，当前更推荐：

- 主状态停在对应当前阶段：
  - 拣货阶段停在 `picking`
  - 复核阶段停在 `checking`
- 已发生的 `pick record / check record` 保留事实
- 不通过删除执行记录来“伪造回退”
- `ship confirm` 不继续正常推进

### 12.5 当前不建议的一期做法

当前不建议一期采用以下方式：

- 用 `pick record` 或 `check record` 的最后一条状态直接代替主单主状态
- 主单一进入 `picked` 就自动视为开始复核
- 主单一进入 `waiting_ship` 就自动视为已发货
- 通过删除执行记录来回退主状态

### 12.6 当前阶段关于状态与执行记录联动的统一收口

截至当前阶段，更推荐统一收敛为：

1. `waiting_pick` 之前无正式执行记录
2. `picking` 主要由拣货记录承接
3. `picked` 表示拣货闭环完成、复核尚未正式开始
4. `checking` 主要由复核记录承接
5. `waiting_ship` 表示拣货与复核均完成，待发货确认
6. `done` 表示拣货记录、复核记录与发货确认记录均已完成

## 13. 出库单详情页 / 列表页状态展示口径

本节用于把出库单主状态与异常补充状态进一步收成页面语言，避免后续同一状态在列表页和详情页各说各话。

### 13.1 当前推荐的展示总原则

当前更推荐按以下原则统一展示：

1. 列表页优先追求短、稳、易扫读
2. 详情页允许比列表页多一层解释
3. 主状态始终占主位
4. 异常补充状态始终做次标签
5. 不把主状态和异常补充状态混写成一个新的数据库状态名

### 13.2 列表页展示口径

当前更推荐列表页按以下方式展示：

| 主状态 | 列表页主展示 | 次标签（如有） |
|---|---|---|
| `draft` | 草稿 | 无 |
| `waiting_pick` | 待拣货 | 无 |
| `picking` | 拣货中 | `已终止`（如 terminated） |
| `picked` | 已拣货待复核 | 无 |
| `checking` | 复核中 | `已终止`（如 terminated） |
| `waiting_ship` | 待发货 | `异常` / `待处理`（后续如启用） |
| `done` | 已发货完成 | 可不加 |
| `cancel` | 已取消 | 可不加 |

这里的关键统一点是：

- 列表页主列只显示主状态短语义
- 补充情况通过次标签补充
- 不把 `picking + terminated` 或 `checking + terminated` 合并成新的主状态文案

### 13.3 详情页头部展示口径

当前更推荐详情页头部按以下方式展示：

- 主状态：显示主状态中文语义
- 异常补充状态：显示为次标签
- 辅助说明：必要时补一句更完整的解释文案

例如在 `checking + terminated` 场景下：

- 主状态：`复核中`
- 次标签：`已终止`
- 说明文案：`当前单据已进入复核，但后续处理已终止。`

### 13.4 列表筛选与状态归类口径

当前更推荐：

1. 主状态筛选继续按主状态归类
2. 异常补充状态单独作为补充筛选条件
3. `picking + terminated` 在主状态筛选中仍归入 `picking`
4. `checking + terminated` 在主状态筛选中仍归入 `checking`
5. 同时支持“仅看已终止”等异常补充状态筛选

也就是说：

- 主状态筛选不被异常补充状态打乱
- 异常筛选另开一条口径

### 13.5 执行记录区与状态展示的当前建议

当前更推荐：

- 在主状态为 `picking` 时，执行记录区重点展示拣货记录
- 在主状态为 `picked` 时，执行记录区强调拣货已完成、复核待开始
- 在主状态为 `checking` 时，执行记录区重点展示复核记录
- 在主状态为 `waiting_ship` 时，执行记录区强调拣货与复核已完成、待发货确认
- 在 `done` 时，拣货记录、复核记录与发货确认记录都应可完整回看

### 13.6 异常信息区的当前展示口径

当存在异常补充状态时，当前更推荐异常信息区最小展示：

- 异常补充状态
- 终止原因 / 异常原因
- 备注
- 处理人
- 时间

若不存在异常补充状态，则：

- 可整体弱化
- 或不在详情页正文中占主视觉位置

### 13.7 当前不建议的一期做法

当前不建议一期采用以下方式：

- 列表页把主状态和异常补充状态拼成过长文案
- 详情页只显示异常标签，不显示主状态
- 因存在 `terminated` 就把主状态从 `picking / checking` 挪走
- 列表页和详情页对同一状态使用不同中文语义

### 13.8 当前阶段关于页面状态展示的统一收口

截至当前阶段，更推荐统一收敛为：

1. 列表页主状态短展示，异常做次标签
2. 详情页头部保留主状态主位，异常做次标签并允许补说明
3. 主状态筛选与异常补充状态筛选分开
4. `picking / checking + terminated` 仍按原主状态归类，只在页面上补 `已终止`

## 14. 出库单与拣货页、复核页、发货页的跳转规则

本节用于把出库单主状态进一步映射到：

- 详情页如何进入拣货页
- 详情页如何进入复核页
- 详情页如何进入发货页
- 执行页如何回到主单
- 哪些状态不应开放错误跳转

当前目标是先固定一期主路径，避免后续拣货页、复核页、发货页入口分散。

### 14.1 当前推荐的跳转总原则

当前更推荐按以下原则统一理解：

1. 主路径始终是：`列表 -> 详情 -> 执行页`
2. 拣货页、复核页、发货页都应从出库单详情页发起为主
3. 待处理列表可作为辅助入口，但不替代详情页主入口
4. 执行页完成后应优先回到对应出库单详情上下文
5. 不开放与当前主状态明显不匹配的执行入口

### 14.2 出库单详情页到拣货页的当前规则

当前更推荐：

- `waiting_pick`
  - 可显示并进入“开始拣货”
- `picking`
  - 可显示并进入“继续拣货”
- 其他状态
  - 不作为正常拣货入口开放

也就是说：

| 主状态 | 拣货页入口建议 |
|---|---|
| `draft` | 不开放 |
| `waiting_pick` | 开放“开始拣货” |
| `picking` | 开放“继续拣货” |
| `picked` | 不开放 |
| `checking` | 不开放 |
| `waiting_ship` | 不开放 |
| `done` | 不开放 |
| `cancel` | 不开放 |

### 14.3 出库单详情页到复核页的当前规则

当前更推荐：

- `picked`
  - 可显示并进入“开始复核”
- `checking`
  - 可显示并进入“继续复核”
- 其他状态
  - 不作为正常复核入口开放

也就是说：

| 主状态 | 复核页入口建议 |
|---|---|
| `draft` | 不开放 |
| `waiting_pick` | 不开放 |
| `picking` | 不开放 |
| `picked` | 开放“开始复核” |
| `checking` | 开放“继续复核” |
| `waiting_ship` | 不开放 |
| `done` | 不开放 |
| `cancel` | 不开放 |

### 14.4 出库单详情页到发货页的当前规则

当前更推荐：

- `waiting_ship`
  - 可显示并进入“开始发货”
- 其他状态
  - 不作为正常发货入口开放

也就是说：

| 主状态 | 发货页入口建议 |
|---|---|
| `draft` | 不开放 |
| `waiting_pick` | 不开放 |
| `picking` | 不开放 |
| `picked` | 不开放 |
| `checking` | 不开放 |
| `waiting_ship` | 开放“开始发货” |
| `done` | 不开放 |
| `cancel` | 不开放 |

### 14.5 待处理列表到执行页的当前规则

当前更推荐待处理列表作为辅助入口：

- `待拣货`
  - 进入拣货执行页
- `待复核`
  - 进入复核执行页

这里仍建议保持两条统一口径：

1. 待处理列表本质是辅助入口，不替代主单详情
2. 从待处理列表进入执行页时，执行页头部应仍清楚保留主单上下文

### 14.6 执行页返回主单的当前规则

当前更推荐：

- 拣货页
  - 返回到原出库单详情页
- 复核页
  - 返回到原出库单详情页
- 发货页
  - 返回到原出库单详情页

返回后应尽量保持：

- 同一主单上下文
- 可继续查看执行记录
- 可继续发起下一步动作

也就是说，当前不建议执行页返回一个泛列表作为默认主出口。

### 14.7 执行页完成后的当前建议路径

当前更推荐：

#### A. 拣货页完成后

- 若仍有待拣内容：
  - 停留在拣货页继续处理
  - 或返回详情页继续观察
- 若全部拣货完成：
  - 返回详情页时主状态应体现为 `picked`
  - 详情页可进一步出现“开始复核”入口

#### B. 复核页完成后

- 若仍有待复核内容：
  - 停留在复核页继续处理
  - 或返回详情页继续观察
- 若全部复核完成：
  - 返回详情页时主状态应体现为 `waiting_ship`
  - 详情页可进一步出现“开始发货”入口

#### C. 发货页完成后

- 发货确认完成：
  - 返回详情页时主状态应体现为 `done`

### 14.8 终止场景下的跳转口径

若出库单在 `picking / checking` 阶段发生 `terminated`，当前更推荐：

- 对应执行页不再作为正常继续推进入口
- 详情页仍可查看拣货 / 复核记录
- 详情页显示异常处理信息区
- 后续转异常处理，不继续开放正常主流程入口

也就是说：

- 主状态仍停在原阶段
- 但页面入口行为应按“已终止”收紧

### 14.9 当前不建议的一期做法

当前不建议一期采用以下方式：

- 在 `picking` 状态同时开放“开始复核”
- 在 `checking` 状态同时开放“开始发货”
- 从普通列表页直接作为主入口跳到拣货页 / 复核页 / 发货页
- 执行页默认返回总列表而丢失主单上下文
- `terminated` 之后仍保留正常“继续拣货 / 继续复核”入口

### 14.10 当前阶段关于出库跳转规则的统一收口

截至当前阶段，更推荐统一收敛为：

1. 拣货入口只属于 `waiting_pick / picking`
2. 复核入口只属于 `picked / checking`
3. 发货入口只属于 `waiting_ship`
4. 详情页是主执行入口，待处理列表是辅助入口
5. 执行页默认返回主单详情，而不是总列表
6. `terminated` 后收紧正常执行入口，转异常处理口径

## 15. 出库单字段字典与状态字段落表方式

本节用于把前述状态机与异常补充状态进一步映射到一期更可执行的数据字段口径。

当前目标不是一次性做完整字段字典，而是先固定：

- 出库单主状态字段
- 异常补充状态字段
- 一期终止相关最小字段
- 页面展示和筛选最依赖的核心字段

### 15.1 当前推荐的字段分层

当前更推荐把出库单相关字段先分成以下 4 层：

1. 主单身份字段
2. 主流程状态字段
3. 异常补充状态字段
4. 统计 / 展示辅助字段

### 15.2 一期最小核心字段字典

当前更推荐出库单模型至少先保留以下核心字段：

| 字段名 | 建议类型 | 当前用途 |
|---|---|---|
| `name` | `Char` | 出库单号 |
| `owner_id` | `Many2one` | 货主 |
| `warehouse_id` | `Many2one` | 仓库 |
| `state` | `Selection` | 主状态 |
| `exception_state` | `Selection` | 异常补充状态 |
| `terminated_reason` | `Selection` | 终止原因 |
| `terminated_remark` | `Text` | 终止备注 |
| `terminated_by` | `Many2one` | 终止操作人 |
| `terminated_at` | `Datetime` | 终止时间 |
| `responsible_id` | `Many2one` | 负责人/责任人 |
| `create_date` | `Datetime` | 创建时间 |
| `write_date` | `Datetime` | 最后修改时间 |

如果后续要补业务维度字段，可在此基础上继续扩：

- `outbound_type`
- `customer_ref`
- `source_ref`
- `remark`

但这些不影响当前状态机主线，不作为本节重点。

### 15.3 `state` 字段的当前落表建议

当前更推荐：

- 字段名：`state`
- 类型：`Selection`
- 作为出库单主状态字段

一期枚举值当前更推荐固定为：

- `draft`
- `waiting_pick`
- `picking`
- `picked`
- `checking`
- `waiting_ship`
- `done`
- `cancel`

当前更推荐：

- `state` 只承接主流程状态
- 不把 `terminated` 这类异常终止值塞进 `state`

### 15.4 `exception_state` 字段的当前落表建议

当前更推荐：

- 字段名：`exception_state`
- 类型：`Selection`
- 用途：承接主状态之外的异常补充状态

一期先预留枚举：

- `terminated`
- `exception`
- `pending_action`

但一期真实业务启用层面，当前更推荐只实际使用：

- `terminated`

### 15.5 `terminated_*` 字段的当前落表建议

当前更推荐以下字段直接落在出库单主模型上：

- `terminated_reason`
- `terminated_remark`
- `terminated_by`
- `terminated_at`

原因是：

1. 一期暂不做完整异常中心
2. 当前只需要最小异常闭环
3. 这些字段与出库单详情页异常信息区直接对应

当前不建议一期为了这组字段额外起一张重型异常子表。

### 15.6 `terminated_reason` 的当前落表建议

当前更推荐：

- 字段名：`terminated_reason`
- 类型：`Selection`

一期建议枚举为：

- `customer_cancel`
- `goods_issue`
- `warehouse_issue`
- `other`

同时保留：

- `terminated_remark`

作为自由补充说明。

### 15.7 当前推荐的页面字段映射关系

当前更推荐页面层按以下关系取值：

| 页面位置 | 推荐字段来源 |
|---|---|
| 列表页主状态列 | `state` |
| 列表页异常次标签 | `exception_state` |
| 详情页头部主状态 | `state` |
| 详情页头部异常标签 | `exception_state` |
| 异常信息区原因 | `terminated_reason` |
| 异常信息区备注 | `terminated_remark` |
| 异常信息区处理人 | `terminated_by` |
| 异常信息区时间 | `terminated_at` |

### 15.8 当前推荐的筛选字段口径

一期更推荐列表与搜索至少支持以下状态相关筛选：

- `state`
- `exception_state`
- `terminated_reason`

其中：

- `state` 负责主流程归类
- `exception_state` 负责异常补充状态归类
- `terminated_reason` 负责异常原因进一步下钻

### 15.9 当前不建议的一期落表方式

当前不建议一期采用以下方式：

- 把 `terminated` 直接塞进 `state`
- 同时再做一套并行的“页面状态字段”
- 为一期最小异常闭环单独拆重型异常主表
- 用计算文案字段替代真正的 `state / exception_state`
- 把拣货 / 复核执行记录状态直接存回主单，替代主状态字段

### 15.10 当前阶段关于字段字典与落表方式的统一收口

截至当前阶段，更推荐统一收敛为：

1. `state` 只承接主流程状态
2. `exception_state` 只承接异常补充状态
3. `terminated_*` 先作为出库单主模型上的最小异常字段组直接落表
4. 页面主状态、异常标签、异常信息区都直接从这组字段取值
5. 一期不额外构建并行页面状态字段或重型异常子表

## 16. 出库单与 stock 原生对象的字段级关联

本节用于把前述出库单主状态机进一步挂到 Odoo 原生 stock 对象上，形成一期更清楚的字段级关联基线。

当前目标不是一次性给出所有技术字段，而是先固定：

- 主单与 `stock.picking` 的关联
- 出库单明细与 `stock.move` 的关联
- 拣货 / 复核 / 发货确认记录与 `stock.move.line` 或 `stock.picking` 的关联
- 主状态推进时更依赖哪些 stock 层事实

### 16.1 当前推荐的总体关联原则

当前更推荐继续沿以下原则推进：

1. 出库单负责业务主线与业务语义
2. `stock.picking / stock.move / stock.move.line` 负责执行事实
3. 主状态判断尽量依赖真实执行事实，而不是手工改状态
4. 不额外构建并行库存事实表

一句话收口：

`出库单负责“为什么发、发到哪一步”，stock 负责“货实际上怎么拣、怎么复核、怎么出”。`

### 16.2 出库单主单与 `stock.picking` 的当前关联建议

当前更推荐：

- 发货执行：
  - `stock.picking.wms_outbound_id -> logistics.wms.outbound`

对应在出库单主模型上反查：

- `delivery_picking_ids`

当前建议的理解是：

- 一张出库单允许对应多张 delivery picking
- 不做死的一对一
- 一期发货确认仍应建立在真实 delivery picking 之上

### 16.3 出库单明细与 `stock.move` 的当前关联建议

当前更推荐：

- `stock.move.wms_outbound_line_id -> logistics.wms.outbound.line`

对应在出库单明细上反查：

- `stock_move_ids`

这条关联主要用于承接：

- 哪条出库明细产生了哪些商品级移动计划
- 拣货、复核与后续发货如何回到出库单明细

### 16.4 拣货记录与 `stock.move.line` 的当前关联建议

当前更推荐：

- `stock.move.line.wms_pick_record_id -> logistics.wms.pick.record`

对应在拣货记录上反查：

- `stock_move_line_ids`

当前建议的理解是：

- `pick record` 表达一次拣货业务动作
- `move.line` 表达该动作下实际从哪些货位、批次拣了多少

### 16.5 复核记录与 `stock.move.line / stock.picking` 的当前关联建议

当前更推荐：

- `stock.move.line.wms_check_record_id -> logistics.wms.check.record`
- `logistics.wms.check.record.picking_id -> stock.picking`

对应在复核记录上反查：

- `stock_move_line_ids`

当前建议的理解是：

- `check record` 表达一次复核业务动作
- `move.line` 表达该动作下核了哪些明细
- `picking_id` 负责把整票执行上下文挂住

### 16.6 发货确认记录与 `stock.picking` 的当前关联建议

当前更推荐：

- `logistics.wms.ship.confirm.picking_id -> stock.picking`

如需反查，可由 `stock.picking` 补：

- `ship_confirm_ids`

当前建议的理解是：

- 发货确认记录最贴近“这一票 delivery picking 已完成发货确认”

### 16.7 主状态与 stock 事实的当前对应口径

当前更推荐按以下方式理解主状态与 stock 层事实的关系：

| 主状态 | 更依赖的 stock 事实 |
|---|---|
| `draft` | 尚无正式 stock 执行事实 |
| `waiting_pick` | 尚无正式拣货执行事实 |
| `picking` | 已存在 pick move line / pick 执行事实 |
| `picked` | 拣货相关 move line 已形成完整闭环 |
| `checking` | 已存在 check move line / check 执行事实 |
| `waiting_ship` | 拣货与复核相关执行事实均已完成，等待发货确认 |
| `done` | delivery picking 与发货确认事实均完成 |
| `cancel` | 未形成正式执行事实或已在允许阶段取消 |

### 16.8 `terminated` 场景与 stock 事实的当前口径

若发生 `terminated`，当前更推荐：

- 主状态停在对应当前阶段：
  - `picking`
  - 或 `checking`
- 已发生的 pick / check 相关 stock 事实继续保留
- 不通过删除 stock 执行事实来“伪造回退”
- `ship confirm` 不继续正常推进

也就是说：

- `terminated` 是对主线推进的收紧
- 不是对既有 stock 事实的抹除

### 16.9 当前推荐的字段级最小清单

当前更推荐一期至少先把以下字段级关联稳定下来：

#### 出库单主单侧

- `state`
- `exception_state`
- `delivery_picking_ids`

#### 出库单明细侧

- `stock_move_ids`

#### stock.picking 侧

- `wms_outbound_id`

#### stock.move 侧

- `wms_outbound_line_id`

#### stock.move.line 侧

- `wms_pick_record_id`
- `wms_check_record_id`

#### 发货确认侧

- `picking_id`

### 16.10 当前不建议的一期做法

当前不建议一期采用以下方式：

- 出库单自己再造一套并行库存主表
- 用主单状态直接替代 picking / move / move line 的完成事实
- 用删除 stock 记录的方式回退主状态
- 让 `picked` 在没有形成完整拣货事实时提前成立
- 让 `waiting_ship` 在没有形成完整复核事实时提前成立

### 16.11 当前阶段关于出库单与 stock 字段级关联的统一收口

截至当前阶段，更推荐统一收敛为：

1. 主单与 `stock.picking` 通过 delivery picking 建立稳定关联
2. 出库单明细与 `stock.move` 建立稳定行级关联
3. 拣货记录、复核记录与 `stock.move.line` 建立执行层关联
4. 发货确认记录与 `stock.picking` 建立确认层关联
5. 主状态推进尽量以 stock 执行事实为基础判断
6. `terminated` 不抹除已发生的 stock 事实，只改变主线推进口径

## 17. 出库单 search / filter / group by 的最终口径

本节用于把前述状态机、异常补充状态、页面展示与字段落表方式，进一步收成一期出库单搜索与列表分析的统一口径。

当前目标不是一次性定义所有高级搜索，而是先固定：

- search view 的最小搜索字段
- filter 的最小状态 / 异常 / 时间口径
- group by 的最小分析维度
- 主状态与异常补充状态在搜索上的分层方式

### 17.1 当前推荐的总体原则

当前更推荐按以下原则统一理解：

1. `search` 负责快速定位单据
2. `filter` 负责固定业务场景筛选
3. `group by` 负责常用管理分析维度
4. 主状态与异常补充状态在搜索口径上继续分层
5. 一期先做高频、低歧义的搜索项，不把 search view 做得过重

### 17.2 当前推荐的 search 字段口径

一期当前更推荐 search view 至少支持以下关键字搜索对象：

- 出库单号 `name`
- 货主名称 / 编码
- 客户单号 / 外部参考号（如后续启用）
- 仓库名称

如果一期业务字段已落地，也可补：

- `customer_ref`
- `source_ref`

但当前更推荐最小搜索仍以：

- `name`
- `owner_id`
- `warehouse_id`

为主。

### 17.3 当前推荐的 filter 口径

一期当前更推荐至少保留以下固定筛选：

#### A. 主状态类 filter

- 草稿
- 待拣货
- 拣货中
- 已拣货待复核
- 复核中
- 待发货
- 已发货完成
- 已取消

这些 filter 统一对应：

- `state`

#### B. 异常补充状态类 filter

- 仅看异常
- 仅看已终止

这些 filter 统一对应：

- `exception_state`

当前更推荐：

- 主状态 filter 与异常补充状态 filter 分开定义
- 不把“拣货中已终止”或“复核中已终止”做成新的主状态 filter

#### C. 时间类 filter

一期当前更推荐至少保留：

- 今日创建
- 近 7 天
- 近 30 天

时间口径当前优先建议基于：

- `create_date`

如后续业务更强调终止时间，再按需补：

- `terminated_at`

### 17.4 当前推荐的异常原因 filter 口径

若一期已启用 `terminated_reason`，当前更推荐再补一组轻量异常原因筛选：

- 客户取消
- 货物异常
- 仓内原因
- 其他

这些 filter 统一对应：

- `terminated_reason`

当前更推荐仅在：

- 已启用 `terminated`
- 且异常处理视图或详情分析场景

中强化使用，不必在所有普通视图默认铺满。

### 17.5 当前推荐的 group by 口径

一期当前更推荐至少保留以下 group by：

- 按主状态
- 按异常补充状态
- 按货主
- 按仓库
- 按创建日期（月 / 日）

如果后续业务字段启用，也可逐步补：

- 按出库类型
- 按负责人

但当前不建议一期就堆太多 group by 维度。

### 17.6 当前推荐的主状态与异常口径分层

当前更推荐继续按以下方式统一：

| 口径层 | 对应字段 | 当前用途 |
|---|---|---|
| 主流程筛选 | `state` | 主流程阶段归类 |
| 异常补充筛选 | `exception_state` | 异常补充状态归类 |
| 异常原因筛选 | `terminated_reason` | 终止原因下钻 |

也就是说：

- 搜索时先找主流程阶段
- 再看异常补充状态
- 最后才按异常原因细分

### 17.7 当前推荐的视图使用方式

当前更推荐：

#### 普通出库单列表页

优先保留：

- 主状态 filter
- 货主 / 仓库
- 时间
- 关键字搜索

#### 待异常处理视图

优先强化：

- `exception_state`
- `terminated_reason`
- 货主
- 仓库
- 时间

也就是说，异常视图应比普通列表更强调异常补充状态口径。

### 17.8 当前不建议的一期做法

当前不建议一期采用以下方式：

- 把 `state` 和 `exception_state` 混成一套搜索字段
- 在普通列表里默认铺满所有异常原因 filter
- 一上来就提供太多 group by 维度
- 为每个状态都再做一套重复的“快捷搜索别名”
- 让 `picking / checking + terminated` 变成新的主流程 group by 项

### 17.9 当前阶段关于 search / filter / group by 的统一收口

截至当前阶段，更推荐统一收敛为：

1. `search` 以单号、货主、仓库为主
2. `filter` 以主状态、异常补充状态、时间为主
3. `group by` 以主状态、异常补充状态、货主、仓库、日期为主
4. `state / exception_state / terminated_reason` 三层口径继续分开
5. 异常视图比普通列表页更强调异常补充筛选与异常原因筛选
