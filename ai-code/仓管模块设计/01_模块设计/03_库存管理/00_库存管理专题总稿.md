## 1. 文档定位

本文件不是库存页面明细稿，也不是数据库字段总表。

它的作用是：

- 给库存管理专题提供统一总入口
- 固定库存专题的业务边界和系统边界
- 把后续库存口径、库存反查、库存页面、库存联调的拆分方向先收住

当前更推荐把库存管理理解为：

`仓管模块中的结果层与反查层。`

它不直接替代：

- 入库、出库、盘点、移位这些业务主单专题
- Odoo 原生库存事实层
- 物流侧批次、运单、留痕、异常的主阅读链

它更适合回答的问题是：

- 现在库存在哪里
- 现在有多少
- 哪些库存可用、冻结、占用或待确认
- 当前库存结果和哪些业务主单、哪些物流对象有关
- 当发现库存问题时，下一步应跳到哪个对象继续看

## 2. Outcome / Behavior / Boundary

### 2.1 Outcome

本专题完成后，至少应明确：

- 库存管理在仓管模块中的职责
- 一期库存管理需要回答的核心问题
- 库存管理与其他仓管专题、物流专题的连接关系
- 库存管理与 Odoo 原生 stock 事实层的复用边界
- 库存页、库存反查页与追溯主链页之间的阅读路径

### 2.2 Behavior

本专题重点描述：

- 库存查询与库存反查的阅读路径
- 库存对象、库存状态、库存口径的统一理解方式
- 库存页如何跳转到相关业务主单和物流追溯主链
- 库存结果如何由入库、出库、盘点、移位四条主线共同影响

### 2.3 Boundary

本专题当前不直接展开：

- 全量字段总表
- 完整前端视觉稿
- 真实模块代码实现细节
- 复杂补货策略和库存优化算法
- 多租户库存隔离深度方案

## 3. 当前问题与专题目标

### 3.1 当前问题

当前库存管理方向的主要问题有 3 个：

1. 入库、出库、盘点、移位专题都已经开始形成状态机基线，但库存视角仍散落在各自正文里，缺少统一收口
2. 仓储管理前端接入稿已经明确了 `stock.quant / stock.location / stock.warehouse` 是仓侧结果页与反查入口，但库存专题还没有单独把这条阅读链沉淀下来
3. 数据库稿已经明确“复用原生库存事实层，不另造并行库存内核”，但库存专题还没有把这条原则翻译成业务语言和页面语言

### 3.2 专题目标

当前更推荐通过本专题先收住下面 5 件事：

1. 明确库存管理在仓管体系中的职责，不再把库存理解成“附在别的主单后面看的结果”
2. 明确库存管理和业务主单管理的边界，避免页面与对象职责混乱
3. 明确库存管理与物流侧批次、运单、留痕、异常的连接关系
4. 明确库存页应该以“结果查询 + 反查入口”为主，而不是重做一套新的执行主页面
5. 给后续库存口径稿、库存反查稿、库存页面稿提供母稿

一句话收口：

`库存管理专题要做的，不是再造库存内核，而是把“库存结果怎么读、怎么查、怎么反查”先固定下来。`

## 4. 模块定位与职责边界

### 4.1 模块定位

当前更推荐把库存管理放在仓管模块中的“结果层 + 反查层”理解。

它的主要职责不是发起作业，而是：

- 展示库存现状
- 展示库存在哪个仓、哪个货位、哪个批次
- 展示库存结果和哪些主单、哪些物流对象有关
- 提供从库存结果反查到主单和追溯主链的稳定入口

### 4.2 与业务主单管理的边界

当前建议保持以下边界：

- 入库、出库、盘点、移位负责业务动作主线
- 库存管理负责动作结果的查询、聚合和反查

也就是说：

- 入库页回答“货怎么进来”
- 出库页回答“货怎么出去”
- 盘点页回答“账实怎么校正”
- 移位页回答“货怎么在库内移动”
- 库存页回答“现在库存结果是什么”

### 4.3 与统计报表的边界

当前建议：

- 库存管理优先回答单对象、单结果、单条链路问题
- 统计与报表负责跨周期、跨维度、跨对象的聚合分析

也就是说：

- 库存管理更偏查询型页面
- 统计报表更偏管理型页面

### 4.4 与物流追溯主链的边界

当前建议继续遵守物流侧总原则：

```text
库存管理 = 结果查询与反查入口
留痕与追溯 = 事实主阅读链
异常中心 = 问题处理链
老板追溯页 = 决策摘要链
```

库存页可以跳到：

- 批次
- 运单
- 留痕
- 异常

但库存页本身不承担：

- 责任裁定
- 完整时间线阅读
- 证据主阅读
- 复杂异常闭环处理

## 5. 与 Odoo 原生 stock 的复用边界

### 5.1 当前直接复用的原生对象

根据数据库稿当前已固定的边界，库存专题应直接建立在以下 Odoo 原生对象之上：

- `stock.quant`
- `stock.location`
- `stock.warehouse`
- `stock.lot`
- `stock.move`
- `stock.move.line`

对应理解为：

- `stock.quant`：库存事实层
- `stock.location`：货位与位置层
- `stock.warehouse`：仓级组织层
- `stock.lot`：批次层
- `stock.move / stock.move.line`：库存变动事实与执行明细层

### 5.2 当前需要扩展但不应重造的对象

当前更推荐扩展而不是重造的对象包括：

- `stock.location`
  - 承接货位扩展字段、仓库归属、检索辅助字段
- `stock.move`
  - 承接与业务主单明细的外键映射
- `stock.move.line`
  - 承接与执行记录、执行事实的外键映射

### 5.3 当前不建议另建并行库存事实层的原因

当前更推荐继续沿数据库稿的结论推进：

1. 不另起并行库存主表
2. 不另起并行库存流水主表
3. 不另起并行货位事实层

原因是：

- 这样会出现两份库存真相
- 会拉长仓管和物流、主单和库存之间的对账链路
- 会让异常排查和联调成本明显升高

一句话收口：

`库存管理专题复用 Odoo stock 作为事实层，在其上补业务语义和阅读入口，而不是另建一套库存内核。`

## 6. 一期纳入范围

当前一期更推荐纳入以下范围：

### 6.1 库存结果查询

- 当前库存现状
- 当前库存分布
- 当前库存所在仓库 / 货位 / 批次
- 当前库存与商品、货主的关系

### 6.2 最小核心口径

- 在手量
- 可用量
- 冻结量
- 占用量

这里的目标不是一次性把所有库存术语拉满，而是先固定一组足以支撑页面、接口和报表统一表达的最小口径。

### 6.3 库存结果的主链连接

- 库存到入库单
- 库存到出库单
- 库存到盘点单
- 库存到移位单
- 库存到批次
- 库存到运单

### 6.4 页面入口与查询能力

- 以 `stock.quant` 为主的库存结果页
- 以 `stock.location` 为主的货位结果页
- 以 `stock.warehouse` 为主的仓级结果页
- 搜索、筛选、分组和反查入口

### 6.5 权限与联调基础能力

- 基于货主、仓库的库存可见范围
- 基于角色的页面进入和动作可见
- 库存页与主单页、追溯页之间的反查验证点

## 7. 当前不纳入范围

当前一期不建议纳入：

- 大屏级库存分析中心
- 高级补货策略
- 波次补货、动态补货算法
- 多租户库存隔离深度方案
- 成本、价值、结算口径
- 独立的库存异常引擎

一句话收口：

`一期库存专题先解决“结果怎么查、链路怎么接”，不解决“库存怎么优化到极致”。`

## 8. 核心对象与关系总览

### 8.1 核心对象清单

当前库存专题至少应围绕以下对象展开：

- 仓库 `stock.warehouse`
- 货位 `stock.location`
- 商品 `product.template / product.product`
- 批次 `stock.lot`
- 库存事实 `stock.quant`
- 变动事实 `stock.move / stock.move.line`
- 业务主单
  - 入库单
  - 出库单
  - 盘点单
  - 移位单

### 8.2 当前推荐的最小关系图

```text
仓库 -> 货位 -> stock.quant
商品 -> stock.quant
批次 -> stock.quant

入库单 / 出库单 / 移位单明细 -> stock.move
收货 / 上架 / 拣货 / 复核执行记录 -> stock.move.line
盘点明细 -> stock.quant

库存结果页 -> 相关主单 / 相关批次 / 相关运单
```

### 8.3 当前推荐的对象分层

当前更推荐按下面 3 层理解库存专题对象：

1. 原生事实层
   - `stock.quant`
   - `stock.move`
   - `stock.move.line`

2. 原生组织与位置层
   - `stock.warehouse`
   - `stock.location`
   - `stock.lot`

3. 业务阅读与反查层
   - 库存页
   - 货位页
   - 仓级页
   - 相关业务主单页
   - 物流追溯页

## 9. 与入库 / 出库 / 盘点 / 移位的关系

### 9.1 与入库的关系

入库主线负责让货进入仓内并落到相应位置。

库存专题负责回答：

- 入库后库存结果有没有形成
- 入库后库存落到了哪个仓、哪个货位、哪个批次
- 当前库存结果能否反查到对应入库单

### 9.2 与出库的关系

出库主线负责消耗仓内库存并形成发货结果。

库存专题负责回答：

- 出库前后库存结果如何变化
- 哪些库存已经被占用、冻结或减少
- 当前库存结果能否反查到对应出库单

### 9.3 与盘点的关系

盘点主线负责校正账实差异。

库存专题负责回答：

- 当前库存结果是否经历过盘点确认
- 当前库存结果能否反查到相关盘点单
- 当前库存结果中的差异调整是否已经吸收

这里库存专题与盘点专题的边界是：

- 盘点专题负责“怎么盘、怎么确认差异”
- 库存专题负责“盘完之后库存结果怎么看”

### 9.4 与移位的关系

移位主线负责改变库存位置而不是改变库存所有权或履约语义。

库存专题负责回答：

- 当前库存在哪个位置
- 某批库存最近是否发生过移位
- 当前库存结果能否反查到相关移位单

### 9.5 当前推荐的一句话关系口径

`入库、出库、盘点、移位共同影响库存结果；库存专题不替代它们的执行主线，而是负责把它们作用后的结果稳定展示出来。`

## 10. 与批次 / 运单 / 留痕 / 异常的关系

### 10.1 当前推荐的连接顺序

库存专题与物流侧对象的连接顺序，当前更推荐为：

`库存 -> 批次 -> 运单 -> 留痕 / 异常`

原因是：

- 批次更接近库存侧的结果对象
- 运单更接近物流侧的履约与留痕主对象
- 留痕和异常更适合作为继续下钻后的阅读层

### 10.2 库存到批次

当前建议把批次作为库存反查的第一优先物流对象。

库存页应该至少支持：

- 看到当前库存关联的批次
- 从库存页跳到批次列表或批次详情

### 10.3 库存到运单

当前建议把运单作为库存反查的第二优先物流对象。

库存页不必直接承载完整运单阅读，但应能：

- 展示最近关联运单
- 跳到运单追溯列表或运单详情

### 10.4 库存到留痕与异常

当前建议：

- 库存页只暴露轻量留痕摘要和轻量异常摘要
- 完整留痕、证据、异常阅读继续留在追溯主链页中

建议库存页只保留：

- 最新留痕时间
- 是否有未闭环异常
- 高风险标记或异常数摘要

### 10.5 当前推荐的一句话连接口径

`库存专题不直接承载物流主阅读链，而是通过批次、运单、留痕摘要、异常摘要把用户稳定送到主链。`

## 11. 页面入口与阅读路径

### 11.1 页面分层

当前更推荐把库存专题页面理解成 3 层：

1. 结果列表层
   - 库存列表
   - 货位列表
   - 仓级列表

2. 结果详情层
   - 库存明细
   - 货位明细
   - 仓级明细

3. 反查入口层
   - 相关主单
   - 相关批次
   - 相关运单
   - 相关留痕 / 异常摘要入口

### 11.2 当前推荐的主阅读路径

当前更推荐主路径为：

`库存列表 -> 库存明细 / 货位明细 -> 相关主单 / 相关批次 / 相关运单 -> 追溯主链`

### 11.3 当前推荐的页面职责

- 库存列表页
  - 负责查找、筛选、定位库存结果
- 库存明细页
  - 负责查看单条库存结果的上下文与反查入口
- 相关对象入口
  - 负责把用户送到业务主单与物流追溯主链

### 11.4 当前推荐的前端落地方向

当前建议继续与仓储管理前端接入稿保持一致：

- 优先复用 Odoo 原生 `stock.quant / stock.location / stock.warehouse` 页面
- 通过摘要字段、Smart Button、默认筛选和动作上下文补入口
- 不为库存专题额外重画一套新的执行型前端

## 12. 数据、状态与权限关注点

### 12.1 数据关注点

库存专题当前最需要关注的数据有：

- 数量口径
  - 在手量
  - 可用量
  - 冻结量
  - 占用量
- 位置口径
  - 仓库
  - 货位
- 关联口径
  - 批次
  - 主单
  - 运单

### 12.2 状态关注点

库存专题当前不建议另设复杂独立状态机。

更推荐把库存页状态理解成：

- 结果状态
  - 可用 / 冻结 / 占用 / 待确认
- 来源状态
  - 由入库、出库、盘点、移位主单提供其原有状态

也就是说：

- 库存专题可以有轻量结果标签
- 但不应该把库存页做成新的业务状态机中心

### 12.3 权限关注点

库存专题当前最关键的权限边界是：

- 按货主限制可见范围
- 按仓库限制可见范围
- 区分只读查询与执行角色

当前建议：

- 库存结果页优先以查看权限为主
- 高风险动作仍留在业务主单页或执行页中

### 12.4 一句话收口

`库存专题关注的是“结果能否被正确看到、正确筛到、正确反查到”，而不是在库存页上承接复杂动作。`
