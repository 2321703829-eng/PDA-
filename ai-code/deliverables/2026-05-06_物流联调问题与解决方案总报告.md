# 2026-05-06 物流联调问题与解决方案总报告

## 1. 文档目的

本文档用于汇总本轮物流联调过程中发现的主要问题、已经完成的修复、当前状态判断，以及后续建议。

本次覆盖的范围包括：

- 小程序运单 / 批次 / 站点查询
- 小程序留痕创建、证据创建、图片上传、图片预览
- 证据图片批量导出
- 导出结果页口径
- 证据列表缩略图
- 导入中心、异常页、顶部菜单中文兼容与入口清理
- 联调公网入口 `7084` 的代理链路问题

---

## 2. 本轮问题总览

本轮已经定位并处理的核心问题包括：

1. 小程序缺少 `GET /api/mini/logistics/waybills/<no>/stops` 主接口，导致按运单号 / 批次号查不到站点。
2. 小程序上传留痕时缺少 `POST /api/mini/logistics/traces`，导致“上传留痕并打卡”直接失败。
3. 小程序后续证据创建与图片上传接口缺失，导致上传链无法继续。
4. 图片预览路由不兼容 `/<lang>/...`，导致回显和预览 404。
5. 联调服 `logistics_trace_evidence` 结构不完整，`logistics.trace.evidence.image` 缺失，形成新旧结构混用。
6. 证据图片导出曾经出现“成功但没有可下载文件”，以及历史脏数据拖低成功率。
7. 证据图片导出结果页的技术状态不符合业务理解。
8. 导入中心与工作台等前端页面存在乱码中文和历史残留入口。
9. 公网入口 `http://8.166.131.218:7084` 偶发 `502`，与 Odoo 本体健康状态不一致。
10. 证据页面当前“留痕事件”展示为“事件 + 时间”拼接串，不适合作为正式筛选与正式主展示口径。

## 3. 小程序站点查询链路

### 3.1 问题

小程序主契约要求：

- `GET /api/mini/logistics/waybills/<no>/stops`

其中 `<no>` 同时支持：

- 运单号：`YD...`
- 批次号：`PC... / LC...`

联调初期，这条路由在 Odoo 19 后端不存在，导致请求被重定向到 `/<lang>/api/...` 后继续 `404`。

### 3.2 解决方案

已补齐并部署：

- `GET /api/mini/logistics/waybills/<no>/stops`
- `GET /<lang>/api/mini/logistics/waybills/<no>/stops`

查询规则：

- 先按运单号查 `logistics.dispatch.waybill.name`
- 查不到再按批次号查 `logistics.dispatch.batch.name`
- 运单模式返回该运单下的站点列表
- 批次模式返回该批次下所有运单的站点列表合并结果

### 3.3 当前状态

已验证可用的真实测试号：

- `YD2026042900027`
- `YD2026042900031`
- `PC202604290005`

结论：小程序按运单号和按批次号查站点均已打通。

同时将联调服证据链做成“短期兼容可运行 + 中期结构已补齐”的状态：

- 有 `logistics.trace.evidence.image` 时走正式图片子表结构
- 历史旧结构数据先兼容读取，不阻塞当前小程序上传

### 4.3 当前状态

当前已验证：

- traces 创建：`200`
- evidences 创建：`200`
- images 上传：`200`

结论：小程序“上传留痕并打卡”主链已经可用。

## 8. 证据图片批量导出

### 8.1 初始问题

批量导出曾存在两类问题：

1. 历史 legacy 图片文件缺失，导致导出成功率低。
2. 即使行内有成功，最终也可能没有导出文件可下载。

### 8.2 根因

第一类是历史脏数据问题：

- 旧 evidence 还带有 `image_access_key / preview_url`
- 但底层历史文件已经不存在

第二类是导出文件写盘问题：

- 导出 ZIP 最终写入目录不可写
- 造成“处理成功但没有导出文件”

### 8.3 已完成的重构与修复

已将导出主单位从“证据对象”重构为“图片”：

- 以当前列表筛选结果作为范围
- 直接抓取所有可导图片
- ZIP 中附带 `index.csv`

同时已修复：

- 导出包写盘路径
- `manifest.json` 的 `entry_type`
- 结果页返回入口

### 8.4 当前状态

当前本轮已完成并验证：

- ZIP 可以真实生成
- ZIP 中包含 `index.csv`
- 图片导出结果不再被空 evidence 主导

但历史脏数据仍会影响“未导出图片数”，只是现在已能被正确归类，而不是伪装成完全成功。

## 12. 公网入口 7084 的 502 问题

### 11.1 现象

联调过程中发现公网入口存在不一致：

- `http://8.166.131.218:7084/web/login?db=odoo_logistics_webtest_v19` 偶发 `502`
- `http://8.166.131.218:7084/web?db=odoo_logistics_webtest_v19` 有时可以返回 `200`
- 但容器内 Odoo 本体和本机隧道访问均正常

### 11.2 已确认事实

已确认：

- Odoo 容器内 `8069` 正常
- 主机本地映射 `19069` 正常
- 登录页和业务页在内网 / 本地隧道链路可访问
- `7084` 并不是 Odoo 容器内直接暴露的端口，而是经由公网 FRP 转发

已定位到当前外层转发链：

- `frpc.service`
- `/opt/frp/frpc.toml`
- `remotePort = 7084`
- `localPort = 19069`

同时，在 FRP 日志里已经看到过：

- 本地 `127.0.0.1:19069` 短暂 `connection refused`

这说明 `7084` 的 `502` 至少有一部分发生在：

- Odoo / 容器重启期间
- 或 FRP 公网入口到本地转发链短暂失联期间

### 11.3 当前判断

目前更接近的结论是：

- **7084 的不稳定主要在 FRP / 公网代理入口层**
- **不是 Odoo 页面模板、菜单、模型本体继续报错导致**

也就是说：

- Odoo 本体健康：基本已确认
- 公网入口稳定性：仍有待继续治理

### 11.4 当前建议

后续针对 `7084` 建议单独处理为“公网代理 / 入口稳定性问题”，而不要和 Odoo 本体问题混在一起。

优先建议：

1. 单独观察 FRP 日志与 `502` 时间点
2. 检查公网入口是否有额外反向代理或健康检查配置
3. 在联调阶段优先推荐使用：
   - VPN 内网 `19069`
   - 或 SSH 隧道 `127.0.0.1:19069`

## 15. 新增隐患与后续治理建议

在主链已经跑通的前提下，又继续做了一轮偏审计式检查，额外确认了几类不会立刻把系统打断、但很容易在后续联调或上线后反复出现的隐患。

### 15.1 `/api/mini/logistics/evidences` 仍然不是幂等接口

当前 `/api/mini/logistics/traces` 已经改成只创建 `trace_event`，不再自动创建 `evidence`，这是正确的。

但 `/api/mini/logistics/evidences` 目前仍是“每调用一次就直接新建一条 evidence”：

- 前端重复点击
- 网络抖动后的自动重试
- 网关层重放请求

都可能继续制造重复 evidence。

**风险判断：**
- 主链可用，但重复证据问题仍有机会以“另一种方式”回来

**建议方向：**
- 给 `/evidences` 增加幂等控制
- 优先考虑：
  - `trace_event_id + request_id`
  - 或 `trace_event_id + 时间窗口`
- 目标是“同一轮上传动作只落一条 evidence”

### 15.2 `/api/mini/logistics/evidences/<id>/images` 缺少去重机制

当前图片上传接口会把收到的每个文件直接写入图片子表，没有显式做重复图片检测。

如果前端因为超时或弱网场景重试：
- 同一张图可能被重复上传
- 同一 evidence 下可能出现重复 image 记录

**风险判断：**
- 当前功能可用
- 但后续容易出现“多张相同图”“缩略图数量异常”“导出包重复图”

**建议方向：**
- 后续引入图片内容哈希或其他幂等标识
- 至少保证同一 evidence 下的完全相同文件不会重复入库

### 15.3 mini 接口安全已补最小层，但仍依赖开关策略

当前 mini 接口安全状态已经从“完全裸奔”提升到“支持 token 校验”，但仍然是：

- `auth="public"`
- `csrf=False`
- 内部 `sudo()`
- 是否启用 token，取决于配置开关：
  - `logistics_web.mini_api_token_enabled`

这意味着：
- 如果配置没有打开
- 接口仍可能处于“不校验 token”的兼容状态

**风险判断：**
- 当前是为了不影响司机继续使用而保留的灰度策略
- 但中后期必须避免长期依赖“默认关闭安全”

**建议方向：**
- 联调完成后进入灰度启用阶段
- 最终目标是：
  - 默认开启 token 校验
  - 并配合小程序自动带 token

### 15.4 批次 stops 查询里的“当前站点”判定仍偏粗

当前批次查询接口中，`CURRENT` 的判定更接近：

- “列表里第一个未完成的 waybill”

而不是严格意义上的：

- “司机当前正在处理的真实站点”

这在当前阶段不会阻断功能，因为小程序主链主要依赖的是：
- 批次号可查
- stops 可返回

但如果后续司机端更依赖精确的“当前站点高亮”或“下一站切换逻辑”，这个口径可能不够。

**风险判断：**
- 当前可接受
- 但属于未来容易出现产品认知偏差的点

**建议方向：**
- 后续若要精确高亮当前站点，应引入更明确的业务判定依据
- 不建议长期仅凭顺序和状态推断

### 15.5 证据缩略图与展示层仍保留 legacy 回退

当前 `image_count` 与 `image_items_json` 的正式来源已经是：

- `logistics.trace.evidence.image`

但为了兼容历史数据，仍保留了：

- `image_access_key`
- `preview_url`
- `full_url`

这让列表页、回显和导出在少量历史数据上仍会混合读取“旧结构”。

**风险判断：**
- 当前是合理的兼容策略
- 但如果长期不收口，历史脏数据会持续混进正式展示链路

**建议方向：**
- 作为后续中期治理的尾项处理
- 最终把 legacy 回退从主展示链中逐步降级，只保留为历史残留兜底

### 15.6 当前新增隐患的建议优先级

如果后续要继续排治理优先级，建议顺序如下：

1. `/api/mini/logistics/evidences` 幂等
2. `/api/mini/logistics/evidences/<id>/images` 去重/幂等

5. legacy 展示回退逐步降级

### 15.7 小结

当前主链已经可用，但新增排查表明，后续最容易反复出现的不是“接口彻底坏掉”，而是：

- 安全开关长期不启用
- 当前站点判定口径过粗
- 历史 legacy 兼容拖得过久

这些都属于“现在不一定炸，但越往后越应该主动收掉”的问题。
