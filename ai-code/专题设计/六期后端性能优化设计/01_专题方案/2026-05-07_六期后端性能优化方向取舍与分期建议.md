# 六期后端性能优化方向取舍与分期建议

## 1. 文档目的

本文用于沉淀六期后端性能优化的第一轮讨论结论，回答两个核心问题：

1. 前期提出的 8 个优化方向，是否都值得纳入本期
2. 每个方向在本期应做到哪一步，哪些只做设计，哪些要做到落地

本文是六期专题讨论纪要，也是后续复盘与继续拆解的起点。

## 2. 当前判断

结论不是 8 个方向都在本期“全面展开”。

更合理的做法是：

1. 选出直接影响当前后台使用体验和接口承载能力的方向，作为本期主线
2. 选出会影响后续规模化但暂时不必大规模实施的方向，做到方案收口和小范围试点
3. 选出更偏中长期架构演进的方向，本期先做边界设计，不急着重投入

基于当前 Odoo 物流项目阶段，本期建议分为三层。

## 3. 本期优先级分层

### 3.1 P0：本期必须真正落地的方向

这几项不是只写文档，而是应形成排查、优化、验证闭环。

1. 查询链路性能治理
2. 计算字段与联动逻辑排雷
3. 列表页与聚合接口专门优化
4. 数据库层索引与慢 SQL 治理

### 3.2 P1：本期要做到设计收口并选择性试点的方向

这几项值得做，但本期不一定要全面铺开。

5. 写入链路瘦身
6. 批量任务与异步任务治理
7. 聚合快照与摘要缓存

### 3.3 P2：本期先定边界、不急于全面实施的方向

这项很重要，但更适合按架构约束先收口。

8. 证据体系冷热分层

## 4. 8 个方向逐项判断

### 4.1 查询链路性能

是否值得本期做：

- 值得，而且应作为本期第一主线

原因：

- 当前后台最容易被用户直接感知的性能问题，大概率集中在运单列表、批次列表、运单详情、批次详情、异常详情、追溯详情等读取链路
- 这类问题通常收益快，且能直接暴露 ORM 查询、关联字段、聚合口径上的真实瓶颈

本期做到哪一步：

1. 明确首轮治理范围：
   - 运单列表页
   - 运单详情页
   - 批次列表页
   - 批次详情页
   - 至少 1 个追溯或异常核心接口
2. 对每个对象建立首轮基线：
   - 响应耗时
   - SQL 次数
   - 主要慢查询
3. 完成首轮优化：
   - 循环查库收口
   - Python 聚合改为数据库聚合
   - 不必要字段延迟读取
4. 留下优化后复测记录

本期目标口径：

- 不是“全系统查询都优化完”
- 而是“核心后台阅读链路有一轮可量化的提速成果”

### 4.2 写入链路瘦身

是否值得本期做：

- 值得，但不建议一开始全面铺开

原因：

- 现场留痕、证据写入、异常触发是后续并发放大点
- 但如果本期连查询瓶颈都还没摸清，过早投入整条写入链路重构，容易分散主线

本期做到哪一步：

1. 锁定 2 到 3 条高价值写入链路：
   - 留痕事件创建
   - 证据元数据写入
   - 异常自动生成或状态更新
2. 识别以下问题：
   - 单次业务动作触发多次 `create/write`
   - 事务中混入非必要联动
   - 同步链路过长
3. 对最重的一条链路做首轮瘦身
4. 沉淀“同步必做 / 可异步处理”分类原则

本期目标口径：

- 做到“识别重链路 + 选 1 条落地优化”
- 不要求本期完成统一异步重构

### 4.3 计算字段与联动逻辑排雷

是否值得本期做：

- 值得，而且应作为本期 P0

原因：

- Odoo 项目后期性能问题很大一部分来自 `compute`、`depends`、`related`、`constraint`、`message` 联动放大
- 这类问题不排，后续无论查还是写都会持续变慢

本期做到哪一步：

1. 盘点核心模型中的高风险字段和联动：
   - `waybill`
   - `batch`
   - `trace`
   - `evidence`
   - `exception`
2. 标出高风险项：
   - 依赖过宽的 `store=True`
   - 列表页引用昂贵统计字段
   - 一次写入触发大量重算
3. 形成首轮整改清单
4. 先处理影响核心链路的前几项

本期目标口径：

- 建立“性能雷区地图”
- 先清掉最影响当前链路的雷，不追求一次性清空全部历史包袱

### 4.4 列表页与聚合接口专门优化

是否值得本期做：

- 值得，而且应该与查询链路一起推进

原因：

- 列表页和看板聚合接口通常不是单条 SQL 慢，而是字段太重、汇总过多、默认加载过深
- 这类问题非常影响后台体验

本期做到哪一步：

1. 选出首轮重点对象：
   - 运单列表
   - 批次列表
   - 异常列表或证据列表
   - 1 个统计/看板接口
2. 区分：
   - 列表轻载字段
   - 详情重载字段
3. 收口返回结构：
   - 列表页不默认回全部统计
   - 大字段和长备注不首屏回传
4. 对至少 1 个聚合接口完成改造验证

本期目标口径：

- 建立“轻列表、重详情”的统一后端返回思路

### 4.5 证据体系冷热分层

是否值得本期做：

- 值得，但本期以边界设计为主

原因：

- 证据图片是后续最容易规模化放大存储和读取压力的部分
- 但如果本期没有明显的图片链路瓶颈数据，直接全面推进冷热拆分容易过早投入

本期做到哪一步：

1. 明确边界口径：
   - Odoo 内保留什么元数据
   - 图片服务承接什么能力
2. 明确页面读取原则：
   - 首屏读摘要
   - 缩略图与原图分离
   - 列表与详情分层
3. 如果已有明显问题，可选 1 个场景做试点

本期目标口径：

- 先把边界设计说清楚
- 不要求本期把证据体系全面重构

### 4.6 聚合快照与摘要缓存

是否值得本期做：

- 值得，但本期不建议上来就做完整缓存体系

原因：

- 当前更需要的是“减少重复计算”，不是先引入复杂缓存基础设施
- Odoo 场景下，摘要字段、快照表、聚合表通常比直接上 Redis 更稳

本期做到哪一步：

1. 找出反复被读取的聚合事实：
   - 运单最新留痕
   - 运单证据数
   - 运单异常数
   - 批次维度汇总指标
2. 选出 1 到 2 个最值钱的摘要对象
3. 先做快照候选设计
4. 如果收益明确，可试点 1 个摘要字段或摘要表

本期目标口径：

- 做到“先找准适合快照的对象”
- 不要求本期形成完整缓存平台

### 4.7 数据库层优化

是否值得本期做：

- 值得，而且应作为本期基础支撑项

原因：

- 查询治理最终一定会落到索引、执行计划和大表访问路径
- 如果不做数据库层核查，很多 ORM 层优化无法真正落地

本期做到哪一步：

1. 对热点列表页、详情页、聚合接口补充 SQL 采样
2. 对核心慢查询做 `EXPLAIN` 或执行计划分析
3. 形成首轮索引核查表
4. 落下必要的单列或复合索引建议

本期目标口径：

- 支撑 P0 查询治理
- 以“热点链路索引治理”为主，不扩展成全面数据库重构

### 4.8 批量任务与异步任务治理

是否值得本期做：

- 值得，但本期以“任务分类 + 选择性拆出”更合适

原因：

- 很多后续性能问题不是单条 SQL，而是把本该后台做的事情塞进用户请求
- 但如果当前没有先明确哪些任务真该异步，很容易为了异步而异步

本期做到哪一步：

1. 梳理现有或预期任务类型：
   - 导入
   - 汇总更新
   - 异常重算
   - 对外同步
2. 明确分类：
   - 必须同步
   - 可延后同步
   - 必须后台异步
3. 选 1 个最合适对象做拆分试点

本期目标口径：

- 做到“异步边界清楚 + 至少 1 个试点”
- 不要求本期搭建完整任务平台

## 5. 本期建议的实际收口

如果六期目标是“值得做且能做出成果”，建议本期收口为下面 4 条主线 + 4 条配套线。

### 5.1 4 条主线

1. 运单、批次、追溯核心页面查询治理
2. 计算字段与联动逻辑排雷
3. 列表页与聚合接口轻载化
4. 热点 SQL 与索引核查

### 5.2 4 条配套线

1. 写入链路选点瘦身
2. 异步任务分类与试点
3. 聚合快照候选设计
4. 证据冷热分层边界收口

## 6. 本期不建议的做法

本期不建议一开始就这样推进：

1. 八个方向同时全面落地
2. 还没有基线数据就大规模重构
3. 一上来先做完整缓存平台
4. 一上来先做完整异步任务平台
5. 在证据冷热分层上做过重架构投入，但没有对应的热点数据支持

## 7. 推荐阶段目标

### 阶段 A：先摸清问题

建议先完成：

1. 热点页面与热点接口清单
2. 首轮耗时、SQL 次数、慢查询记录
3. 计算字段与联动高风险盘点

### 阶段 B：做首轮止血

建议完成：

1. 查询链路首轮优化
2. 列表轻载化和聚合收口
3. 必要索引优化
4. 1 条写入链路瘦身

### 阶段 C：做结构性试点

建议完成：

1. 1 个快照试点
2. 1 个异步任务试点
3. 证据冷热分层边界定稿

## 8. 当前讨论结论

当前第一轮判断如下：

1. 8 个方向都值得进入六期视野
2. 但不适合本期全部做成重投入落地项
3. 本期应把重心放在“查询、聚合、计算字段、索引”这 4 个最直接见效的方向
4. 写入链路、异步任务、快照、证据冷热分层本期更适合做到“收口 + 试点”

## 9. 下一步建议

下一步建议继续讨论并落文档的内容：

1. 把这 8 个方向正式转成六期 `P0 / P1 / P2` 清单
2. 为每个方向定义“完成标准”
3. 再进一步拆成“本期必须交付的具体项”
