# 六期后端性能优化各方向 Outcome 与落地工作

## 1. 文档目的

本文基于六期已经确定的 `P0 / P1 / P2` 优先级，继续往下回答两个更贴近实施的问题：

1. 每个方向真正落地后，系统应当变成什么样
2. 为了达到这个状态，本期需要完成哪些工作

本文不再展开更细的边界设计细节，而是先建立“方向 -> Outcome -> 工作项”的统一口径，方便后续拆任务和复盘。

## 2. 使用原则

- `Outcome` 用来定义“这个方向做完后，系统状态发生了什么变化”
- `落地工作` 用来定义“本期至少要做哪些动作，才算朝这个 Outcome 真正推进了”
- 本文以优先级顺序展开，先看 `P0`，再看 `P1`，最后看 `P2`

## 3. P0 方向

### 3.1 查询链路性能治理

#### Outcome

落地后，核心后台阅读链路不再依赖隐式的多次 ORM 查询和临时拼接聚合来支撑页面展示。

系统应达到的状态：

1. 运单、批次、追溯、异常等核心页面的读取耗时进入可接受区间
2. 页面或接口的 SQL 次数明显收口，不再出现大面积循环查库
3. 查询问题可被定位和复测，而不是靠体感判断快慢
4. 后端已经形成一轮明确的热点页面和热点接口治理清单

#### 落地工作

本期至少需要完成：

1. 选定首轮治理范围
   - 运单列表页
   - 运单详情页
   - 批次列表页
   - 批次详情页
   - 至少 1 个追溯或异常核心接口
2. 建立基线
   - 记录每个对象的响应耗时
   - 记录 SQL 次数
   - 标出主要慢查询
3. 完成首轮查询治理
   - 收口循环查库
   - 把不该在 Python 做的聚合下推数据库
   - 移除首屏非必要字段读取
4. 留下优化后复测记录
5. 输出未完成问题留单，作为后续继续治理入口

### 3.2 计算字段与联动逻辑排雷

#### Outcome

落地后，系统不会再因为少数字段、约束或自动联动逻辑，把读写链路持续拖慢。

系统应达到的状态：

1. 高风险 `compute / depends / related / constraint / message/activity` 已被识别
2. 核心模型的主要性能雷区有清单、有分级、有整改动作
3. 最影响页面和接口的联动放大点已经被削弱
4. 后续新增字段和联动逻辑有基本的性能审视意识

#### 落地工作

本期至少需要完成：

1. 盘点核心模型高风险项
   - `waybill`
   - `batch`
   - `trace`
   - `evidence`
   - `exception`
2. 对每个风险项记录
   - 字段或逻辑名称
   - 触发条件
   - 风险原因
   - 影响范围
3. 形成高、中、低三级整改清单
4. 优先整改最影响核心链路的高风险项
5. 对整改结果做影响复核
   - 重算次数是否下降
   - SQL 次数是否下降
   - 页面或接口是否变快

### 3.3 列表页与聚合接口专门优化

#### Outcome

落地后，后台列表和统计接口的设计不再是“为了方便一次性把所有数据都带出来”，而是明确区分轻列表和重详情。

系统应达到的状态：

1. 常用列表页默认返回的数据明显变轻
2. 看板和统计接口不再无节制地拼装重聚合
3. 页面展示数据开始按场景分层，而不是一套大而全返回结构
4. 后端对“列表字段、详情字段、聚合字段”的职责边界更清楚

#### 落地工作

本期至少需要完成：

1. 选出首轮重点对象
   - 运单列表
   - 批次列表
   - 异常列表或证据列表
   - 至少 1 个统计或看板接口
2. 明确字段分层
   - 哪些字段属于列表轻载字段
   - 哪些字段属于详情重载字段
   - 哪些字段属于聚合摘要字段
3. 对至少 2 个列表对象做返回收口
4. 对至少 1 个聚合接口完成改造与复测
5. 形成统一规则说明
   - 列表页不默认返回哪些重字段
   - 聚合值优先如何提供
   - 长备注、大文本、图片摘要如何延迟读取

### 3.4 数据库层索引与慢 SQL 治理

#### Outcome

落地后，本期性能优化不再停留在 ORM 层表面，而是有数据库层证据支撑。

系统应达到的状态：

1. 热点页面和接口对应的慢 SQL 已被识别
2. 主要查询路径的索引情况已经有首轮核查
3. 至少一轮必要索引优化已落地或已明确落地条件
4. 后续再出现慢查询时，团队知道该如何分析，而不是只能猜测

#### 落地工作

本期至少需要完成：

1. 对 P0 重点页面和接口做 SQL 采样
2. 对热点慢 SQL 做执行计划分析
3. 形成首轮索引核查表
   - SQL 归属页面或接口
   - 查询过滤条件
   - 排序条件
   - 当前索引情况
   - 建议动作
4. 落下必要索引建议，并至少完成一轮落地或验证
5. 把数据库层结论回挂到查询治理和列表治理结果上

## 4. P1 方向

### 4.1 写入链路瘦身

#### Outcome

落地后，现场高频写入链路不再被过长事务和过多同步联动拖住，主事务会更轻、更可控。

系统应达到的状态：

1. 留痕、证据、异常相关写入链路中，最重的几个点已经被识别
2. 至少 1 条重写入链路被做过首轮瘦身
3. 团队对“哪些动作必须同步完成，哪些可以延后处理”有明确共识
4. 后续异步化和任务拆分有了真实起点

#### 落地工作

本期至少需要完成：

1. 梳理 2 到 3 条高价值写入链路
   - 留痕事件创建
   - 证据元数据写入
   - 异常生成或状态更新
2. 分析每条链路
   - 事务边界
   - 主要 ORM 操作次数
   - 可疑放大点
3. 明确“同步必做 / 可延后 / 可异步”分类
4. 选 1 条最重链路做首轮瘦身
5. 留下优化前后对比记录

### 4.2 批量任务与异步任务治理

#### Outcome

落地后，系统不会继续把所有非必要工作都压在用户请求内完成，主请求和后台任务会开始分工。

系统应达到的状态：

1. 团队已经明确哪些任务必须同步，哪些适合后台处理
2. 至少 1 类任务完成了试点拆分
3. 主请求时长与后台处理边界开始被真正管理
4. 后续任务平台建设有清晰的业务依据，而不是技术先行

#### 落地工作

本期至少需要完成：

1. 梳理任务对象
   - 导入
   - 汇总更新
   - 异常重算
   - 对外同步
2. 定义任务分类原则
   - 必须同步
   - 可延后同步
   - 必须后台异步
3. 选 1 个最合适对象做试点
4. 记录试点前后的主请求变化和后台承接内容
5. 留下风险与注意事项

### 4.3 聚合快照与摘要缓存

#### Outcome

落地后，系统中最常被重复读取的聚合事实，不再每次都从底层明细表临时计算出来。

系统应达到的状态：

1. 至少识别出一批值得做快照的高价值聚合对象
2. 至少 1 个快照或摘要试点落下
3. 团队开始用“摘要字段 / 快照表 / 聚合表”的方式思考高频聚合问题
4. 后续看板、详情页、统计页的聚合压力有明确缓解路径

#### 落地工作

本期至少需要完成：

1. 找出候选对象
   - 运单最新留痕
   - 运单证据数
   - 运单异常数
   - 批次汇总指标
2. 对每个候选说明
   - 为什么值得做
   - 更新时机是什么
   - 一致性风险是什么
3. 选出 1 到 2 个最值钱对象
4. 完成至少 1 个摘要字段、摘要表或快照试点
5. 对试点收益和维护成本做判断记录

## 5. P2 方向

### 5.1 证据体系冷热分层

#### Outcome

落地后，证据体系的性能优化方向不会跑偏，团队对 Odoo 侧和图片服务侧的职责已经有统一理解。

系统应达到的状态：

1. 证据元数据与图片本体的边界被统一
2. 列表、详情、缩略图、原图的读取口径被统一
3. 后续如果图片量继续放大，系统有明确的扩展方向
4. 团队不会在没有必要的情况下过早做重型证据架构改造

#### 落地工作

本期至少需要完成：

1. 明确保留在 Odoo 内的证据元数据范围
2. 明确图片服务承接的能力范围
3. 明确页面读取规则
   - 列表读什么
   - 详情读什么
   - 缩略图和原图如何分层
4. 记录主要风险点
   - 一致性
   - 鉴权访问
   - 预览和导出性能
5. 如已有明确瓶颈，再决定是否做试点

## 6. 当前建议的阅读方式

如果从实施角度使用本文，建议按下面顺序理解：

1. 先看 `P0` 的 Outcome，确认本期必须交付的系统变化
2. 再看 `P0` 的落地工作，整理出本期必须做的动作
3. 再把 `P1` 视为“必须收口并试点的配套方向”
4. `P2` 当前先作为边界保底，不作为本期主战场

## 7. 当前结论

当前六期后端性能优化，不建议把 8 个方向当成 8 个平行模块去推进。

更准确的理解应该是：

1. `P0` 是本期主战场，目标是让核心页面和接口真正变快
2. `P1` 是结构性配套线，目标是为后续规模化优化打基础
3. `P2` 是方向保底线，目标是避免后续证据体系优化走偏

## 8. 下一步建议

下一步最合适的动作是继续往下拆：

1. 先把 `P0` 四项拆成“本期必须交付的具体项”
2. 再把这些具体项整理成六期任务表
3. `P1` 则同步确定各自的试点对象
