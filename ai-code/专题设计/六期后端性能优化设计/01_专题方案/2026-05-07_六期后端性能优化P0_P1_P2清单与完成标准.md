# 六期后端性能优化 P0 P1 P2 清单与完成标准

## 1. 文档目的

本文用于把六期后端性能优化的 8 个方向正式收口为 `P0 / P1 / P2` 清单，并为每个方向定义本期“完成标准”。

后续任务拆分、排期、复盘、验收，都应优先参考本文口径。

## 2. 分层原则

### P0

- 本期必须做出可验证结果
- 需要形成“排查 -> 优化 -> 复测 -> 记录”闭环
- 应直接改善当前后台使用体验或接口承载能力

### P1

- 本期必须收口方案并至少做小范围试点
- 不要求全面铺开，但不能只停留在口头讨论
- 应为下期进一步优化打下真实实现基础

### P2

- 本期先收口边界和设计原则
- 暂不要求大规模实施
- 只有在已有明确瓶颈数据时，才允许提前升格投入

## 3. 正式清单总览

### P0 清单

1. 查询链路性能治理
2. 计算字段与联动逻辑排雷
3. 列表页与聚合接口专门优化
4. 数据库层索引与慢 SQL 治理

### P1 清单

5. 写入链路瘦身
6. 批量任务与异步任务治理
7. 聚合快照与摘要缓存

### P2 清单

8. 证据体系冷热分层

## 4. 逐项完成标准

### 4.1 P0-1 查询链路性能治理

方向定义：

- 面向运单、批次、追溯、异常等核心后台阅读链路，识别并治理查询次数过多、聚合位置错误、字段读取过重、循环查库等问题

本期目标：

- 让核心后台阅读链路完成首轮可量化提速

完成标准：

1. 有正式治理范围清单，至少覆盖：
   - 运单列表页
   - 运单详情页
   - 批次列表页
   - 批次详情页
   - 至少 1 个追溯或异常核心接口
2. 每个对象都有首轮性能基线记录：
   - 响应耗时
   - SQL 次数
   - 主要慢查询
3. 至少完成 3 类典型问题优化中的 2 类：
   - 循环查库收口
   - Python 聚合下推数据库
   - 不必要字段延迟读取或移出首屏
4. 优化后有复测记录，并能明确说明“哪条链路变快了、快了多少”
5. 有未完成问题留单，避免只做一次性临时处理

不算完成的情况：

- 只有主观感受，没有基线和复测数据
- 只改了零散 SQL，没有覆盖核心页面或接口

### 4.2 P0-2 计算字段与联动逻辑排雷

方向定义：

- 面向 `compute`、`depends`、`related`、`constraint`、`message/activity` 等自动联动链路，识别性能放大点并完成首轮整改

本期目标：

- 建立性能雷区地图，并先清掉最影响核心链路的雷

完成标准：

1. 对核心模型完成高风险盘点，至少覆盖：
   - `waybill`
   - `batch`
   - `trace`
   - `evidence`
   - `exception`
2. 对每个高风险项至少记录以下信息：
   - 字段或逻辑名称
   - 触发条件
   - 风险原因
   - 受影响页面或接口
3. 形成正式整改清单，并按高、中、低风险分级
4. 至少完成 3 个高风险项的首轮整改，或完成 1 个链路级重灾区整改
5. 能说明整改后的影响：
   - 重算次数下降
   - SQL 次数下降
   - 写入或读取耗时下降

不算完成的情况：

- 只是列了字段名单，没有风险说明和整改动作
- 排查结果没有落到核心链路优化

### 4.3 P0-3 列表页与聚合接口专门优化

方向定义：

- 专门治理后台列表页和统计/看板接口中“字段太重、聚合过多、默认加载过深”的问题，建立轻列表、重详情的统一后端口径

本期目标：

- 让后台常用列表与聚合接口显著变轻

完成标准：

1. 选出首轮重点对象，至少覆盖：
   - 运单列表
   - 批次列表
   - 异常列表或证据列表
   - 至少 1 个统计或看板聚合接口
2. 每个重点对象都明确区分：
   - 列表轻载字段
   - 详情重载字段
3. 至少完成 2 个列表对象的返回收口
4. 至少完成 1 个聚合接口的改造与复测
5. 形成统一规则说明：
   - 列表页默认不回哪些重字段
   - 聚合值优先如何计算
   - 长备注、大文本、图片摘要如何延迟读取

不算完成的情况：

- 只优化单个接口，但没有建立列表/详情分层口径
- 列表仍默认回传大量重字段

### 4.4 P0-4 数据库层索引与慢 SQL 治理

方向定义：

- 通过 SQL 采样、执行计划分析、索引核查等手段，为热点链路性能优化提供数据库层支撑

本期目标：

- 支撑本期 P0 查询与聚合治理真正落地

完成标准：

1. 对 P0 重点页面和接口完成 SQL 采样
2. 至少对 5 条热点慢 SQL 做执行计划分析
3. 形成首轮索引核查表，至少包含：
   - SQL 归属页面/接口
   - 过滤条件
   - 排序条件
   - 当前索引情况
   - 建议动作
4. 至少落地 1 轮必要索引优化，或明确记录暂不落地原因
5. 优化结果与 P0-1/P0-3 的复测结果能互相对应

不算完成的情况：

- 只有模糊的“该加索引”结论
- 没有热点 SQL 与实际页面/接口的关联关系

### 4.5 P1-1 写入链路瘦身

方向定义：

- 治理留痕创建、证据元数据写入、异常触发等高价值写入链路中过长事务、重复 `create/write`、不必要同步联动等问题

本期目标：

- 识别关键重写入链路，并完成至少 1 条链路的首轮瘦身

完成标准：

1. 梳理出 2 到 3 条高价值写入链路
2. 每条链路至少识别：
   - 事务边界
   - 主要 ORM 操作次数
   - 可疑放大点
3. 明确“同步必做 / 可延后 / 可异步”的初步分类
4. 至少完成 1 条最重链路的首轮优化
5. 有优化前后对比记录：
   - 写入耗时
   - SQL 次数
   - 联动数量变化

不算完成的情况：

- 只讨论应该异步，没有先识别当前写入链路结构

### 4.6 P1-2 批量任务与异步任务治理

方向定义：

- 明确哪些任务应同步处理，哪些应延后处理，哪些应拆为后台异步任务，避免把非必要工作堆在用户请求里

本期目标：

- 明确异步边界，并完成至少 1 个任务试点

完成标准：

1. 形成现有或预期任务清单，至少覆盖：
   - 导入
   - 汇总更新
   - 异常重算
   - 对外同步
2. 对每类任务明确归类：
   - 必须同步
   - 可延后同步
   - 必须后台异步
3. 给出异步判定原则，而不是只列任务名称
4. 至少完成 1 个任务试点的方案或实现
5. 试点结果能说明：
   - 主请求缩短了什么
   - 后台任务承接了什么
   - 是否带来新的可控风险

不算完成的情况：

- 只有抽象原则，没有对应任务对象
- 只提出“后续做异步”，没有任何试点

### 4.7 P1-3 聚合快照与摘要缓存

方向定义：

- 为高频重复读取的聚合事实设计摘要字段、快照表或聚合表，减少重复计算和重复联表查询

本期目标：

- 找准适合做快照的对象，并完成至少 1 个试点

完成标准：

1. 明确首轮候选对象，至少从以下事实中选取：
   - 运单最新留痕
   - 运单证据数
   - 运单异常数
   - 批次汇总指标
2. 对每个候选对象说明：
   - 为什么值得做快照
   - 更新时机是什么
   - 一致性风险是什么
3. 至少选出 1 到 2 个高价值候选
4. 至少完成 1 个摘要字段、摘要表或快照方案试点
5. 试点要有收益判断：
   - 节省了什么查询或计算
   - 增加了什么维护成本

不算完成的情况：

- 只有“以后做缓存”的方向，没有对象、更新机制和试点

### 4.8 P2-1 证据体系冷热分层

方向定义：

- 进一步收紧 Odoo 侧元数据与外部图片服务之间的边界，明确首屏摘要、缩略图、原图、列表与详情之间的读取分层

本期目标：

- 把边界说清楚，为后续规模化优化预留正确架构方向

完成标准：

1. 明确 Odoo 内保留的证据元数据范围
2. 明确图片服务承接的能力范围
3. 明确页面读取原则：
   - 列表读什么
   - 详情读什么
   - 缩略图与原图如何区分
4. 明确至少 3 个潜在风险点：
   - 数据一致性
   - 鉴权访问
   - 预览性能或导出性能
5. 如果已有明确瓶颈数据，可额外完成 1 个试点；如果没有，不强制要求本期实现

不算完成的情况：

- 只说“图片不要放 Odoo”这类原则，没有边界、读取口径和风险设计

## 5. 本期验收视角

从六期整体看，本期完成标准应按三层来验收。

### P0 整体验收

必须满足：

1. 有基线
2. 有优化动作
3. 有复测结果
4. 有未完成问题留单

### P1 整体验收

必须满足：

1. 有明确分类或候选清单
2. 有试点对象
3. 有试点结论

### P2 整体验收

必须满足：

1. 有明确边界
2. 有读取或交互原则
3. 有风险清单

## 6. 当前正式结论

六期后端性能优化正式采用如下分层：

1. `P0`：
   - 查询链路性能治理
   - 计算字段与联动逻辑排雷
   - 列表页与聚合接口专门优化
   - 数据库层索引与慢 SQL 治理
2. `P1`：
   - 写入链路瘦身
   - 批量任务与异步任务治理
   - 聚合快照与摘要缓存
3. `P2`：
   - 证据体系冷热分层
