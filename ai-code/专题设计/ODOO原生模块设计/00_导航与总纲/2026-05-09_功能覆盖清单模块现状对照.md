- 对照 `ai-code/专题设计/ODOO原生模块设计/功能覆盖清单.md` 第一部分“`Odoo 原生已有（开箱即用）`”中的 1-29 项
- 用于核查这些模块和能力在当前仓库与当前系统中的真实状态

检查日期：

- 2026-05-09

检查基准：

- 仓库代码目录：`D:\Desktop\Odoo\addons`、`D:\Desktop\Odoo\custom_addons`
- 当前本地 Odoo 配置：`D:\Desktop\Odoo\odoo_local.conf`
- 当前主核查数据库：`odoo_logistics_webtest_v19`
- 辅助对比数据库：`odoo_logistics_dev`、`odoo_logistics_phase4_v1`

说明口径：

- `源码存在`：对应模块目录仍在当前仓库中
- `已安装`：模块已在 `odoo_logistics_webtest_v19` 数据库中安装
- `已隐藏`：模块或菜单记录存在，但根菜单被设为不可见，或实际入口被关闭
- `未安装`：源码在仓库中，但当前主库未启用

---

## 一、总体结论

当前截图中的 29 项能力可以分成 4 类：

1. 仍在系统中且当前可直接作为底座使用  
   `stock`、`account`、`contacts`、`hr`、`fleet`、`barcodes`、`logistics_dispatch`、`logistics_trace_*`

2. 仍在系统中，但菜单被隐藏  
   `sale` 主菜单当前被隐藏；`sale` 与 `sale_stock` 模块本身仍在系统中

3. 源码仍在仓库里，但当前主库未安装  
   `stock_picking_batch`、`purchase`、`purchase_stock`、`website_sale`、`website_sale_stock`、`sale_margin`、`sale_stock_margin`、`product_margin`、`delivery`、`stock_landed_costs`

4. 文档项本身对应的是同一模块下的子能力，不一定是单独模块  
   如多仓库、库位、补货、上架策略、盘点、批次追踪等，主要都属于 `stock` 内能力

## 三、特别说明

### 3.1 当前最容易误判的几项

#### `sale`

- 不是被删除
- 不是未安装
- 是主库中模块已安装，但 `sale.sale_menu_root` 当前为 `active = false`
- 这属于“被隐藏”，不是“系统没有”
- 同时当前 `logistics_dispatch` 仍然依赖 `sale`
- 这说明 `sale` 在当前系统中属于“底层仍在使用、前台入口被关闭”的状态

#### `stock_picking_batch`

- 源码目录存在
- 文档中将它当作“开箱即用”能力来源是合理的
- 但当前主库并未安装，所以现在不能直接认为已经在系统里可用

#### `purchase` / `purchase_stock`

- 源码目录存在
- 当前主库未安装
- 因此“采购下单、采购入库联动”目前是仓库具备、系统未启用，不是已经在线

#### `website_sale` / `website_sale_stock`

- 源码目录存在
- 当前主库未安装
- 所以截图里“电商前端、前端实时库存显示”更适合作为可选接入方向，不能算当前系统现状

### 3.2 当前已确认被隐藏的模块

就当前主核查库 `odoo_logistics_webtest_v19` 而言，这次最明确查到的“已安装但被隐藏”的原生模块是：

- `sale`

具体判断依据：

- `sale` 在主库中的模块状态为 `installed`
- `sale.sale_menu_root` 菜单记录仍然存在
- 但该菜单当前为 `active = false`

因此，`sale` 当前不是缺失，而是被关闭了原生前台入口。

需要特别注意：

- 被隐藏不等于没在用
- 当前 `logistics_dispatch` 仍依赖 `sale`
- 运单订单行模型中已存在：
  - `sale_order_id`
  - `stock_picking_id`

这说明当前系统底层仍在借助 `sale.order` 和 `stock.picking` 做关联，只是不希望用户直接按 Odoo 原生销售主线来操作。

### 3.3 `stock` 下面哪些入口已确认可见

在 `odoo_logistics_webtest_v19` 中，下面这些库存入口已确认存在且 `active = true`：

- `Inventory`
- `Transfers`
- `Locations`
- `Warehouses`
- `Replenishment`

这说明你关心的：

- 仓库
- 库位
- 补货
- 仓内调拨/出入库

这些核心能力当前都还在系统中，不属于被你隐藏掉的部分。

### 3.4 其他库的隐藏情况

辅助核查时还发现：

- `odoo_logistics_dev`：`Sales` 和 `Contacts` 都被隐藏
- `odoo_logistics_phase4_v1`：`Sales` 被隐藏，`Contacts` 可见
- `odoo_logistics_webtest_v19`：`Sales` 被隐藏，`Contacts` 可见

这说明“是否可见”并不是仓库统一状态，而是不同数据库各自有差异。

### 3.5 未启用原生模块里，哪些能力已被自定义模块部分承接

不是所有“主库未安装”的原生模块都等于“当前没人做”。结合现有自定义模块与设计稿，可以再分成三类：

#### A. 已有明显自定义承接迹象的

##### `stock_picking_batch`

- 原生模块当前主库未安装
- 但自定义 `logistics_dispatch` 已经在做：
  - `wave`
  - `batch`
  - `waybill`
- 这意味着“批次组织 / wave 式执行主线”这部分，已经由自定义模块在承接
- 需要注意的是：这不等于已经实现了原生 `stock.picking.batch` 的全部仓内批次拣货细节，而是业务主线层面存在明显重叠

##### `delivery`

- 原生 `delivery` 当前主库未安装
- 但 `logistics_dispatch` 中已经存在配送日期、路线摘要、线路顺序、排线草稿等字段与对象
- 这说明当前系统已经在自定义承接“配送执行与调度”能力
- 但这不等于已经实现原生 `delivery` 那套按重量/价格/目的地自动算运费的能力

#### B. 已做关联准备，但还不算自定义完整承接的

##### `purchase` / `purchase_stock`

- 设计稿中已把 `purchase` 作为后续关联与反查对象之一
- 但当前自定义模块里没有看到已经形成一套完整采购主流程去替代原生采购
- 因此更准确的状态是：有设计预留，暂无成熟替代

##### `website_sale` / `website_sale_stock`

- 当前 `logistics_web` 是物流后台增强层
- 不是电商商城前台
- 目前没有看到自定义商城前台去替代 `website_sale`

#### C. 当前基本没有看到自定义替代落地的

- `sale_margin`
- `sale_stock_margin`
- `product_margin`
- `stock_landed_costs`

这些模块对应的毛利核算、商品毛利报表、落地成本分摊能力，当前没有看到成熟的自定义替代实现。

## 四、可直接拿来做后续调研的结论

如果后续要基于当前系统继续调研“怎么把 Odoo 原生能力串起来”，建议把这 29 项先拆成下面三组：

### A. 当前已经在线、可以立即研究接法的

- `stock`
- `sale`
- `sale_stock`
- `account`
- `contacts`
- `hr`
- `fleet`
- `barcodes`
- `logistics_dispatch`
- `logistics_trace_*`

其中要特别注意：`sale` 虽然已安装，但当前先要处理“菜单隐藏”问题。

### B. 仓库里有源码，但要先安装再谈接法的

- `stock_picking_batch`
- `purchase`
- `purchase_stock`
- `website_sale`
- `website_sale_stock`
- `sale_margin`
- `sale_stock_margin`
- `product_margin`
- `delivery`
- `stock_landed_costs`

其中还要再区分：

- `stock_picking_batch`、部分配送执行能力：已被当前自定义执行主线部分承接
- `purchase`、`website_sale`：已有设计预留，但未见成熟自定义替代
- `sale_margin`、`sale_stock_margin`、`product_margin`、`stock_landed_costs`：当前基本仍是空缺待启用状态

### C. 不需要当成独立模块去找的

- 多仓库
- 库位
- 盘点
- 补货
- 上架策略
- 批次/序列号追踪

这些主要都是 `stock` 的配置能力、菜单能力或业务能力，不应误解为“还缺单独模块”。

---

## 五、本次对照结论摘要

这张清单里的模块并不是大面积“没了”，而是三种情况混在一起：

1. 真正在当前系统里在线可用的，以 `stock / account / contacts / hr / fleet / logistics_*` 为主
2. 模块还在，但你确实有隐藏过的，当前最明确的是 `sale`
3. 文档里列为“开箱即用”的一部分能力，在仓库层面成立，但在当前主库里其实尚未安装，例如 `purchase`、`website_sale`、`stock_picking_batch`

因此，后续做“原生能力怎么接到物流系统里”的调研时，应该先按：

- 已安装可用
- 已安装但隐藏
- 源码存在未启用

这三层来排优先级，而不要把它们都当成同一种“已经在系统里”。
