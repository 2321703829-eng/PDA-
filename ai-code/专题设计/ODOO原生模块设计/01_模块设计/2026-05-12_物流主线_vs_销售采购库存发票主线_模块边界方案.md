## 1. Objective

明确当前 Odoo 19 城市供应链项目在本期建设中 4 件事：

1. 本期重点建设哪些业务域，长期既有物流能力如何接入
2. 哪些能力应优先放入 ERP / WMS / TMS / BI / 系统底座
3. 哪些能力应通过启用和扩展 Odoo 官方模块接入
4. 哪些物流边界虽然不是本期重点建设面，但仍然不能被破坏

---

## 2. Outcome / Behavior / Boundary

### 2.1 Outcome

本方案落地后，系统应同时满足：

1. 本期优先完成销售、采购、库存/拣货、财务、结账、报表等 ERP 闭环
2. 仓储与配送能力按 WMS / TMS 边界逐步归位，而不是继续杂糅在一个大工具里
3. 既有物流对象和追溯对象继续保留，不被销售单、发票单、库存单吞掉
4. 官方单据与既有物流对象稳定联动，但不替代物流主对象
5. 菜单与工作台对用户表现为一个系统，而不是多套割裂后台

### 2.2 Behavior

- 销售、采购、库存、财务、结账、报表是本期优先建设面
- WMS / TMS 是本期重要建设面，负责仓内动作和配送执行归位
- 既有物流执行与追溯对象继续保留，作为边界约束和联动上下文
- 联动通过关系字段、适配服务、smart button、状态映射、汇总信号完成
- 页面主入口按本期模块化菜单进入，逐步形成 ERP / WMS / TMS / BI 分层入口
- 销售、采购、库存、财务页与既有物流页互相提供反查与协同入口

### 2.3 Boundary

本方案负责：

- 主线分层
- 模块边界
- 官方 vs 自定义归属
- 侵入级别判断
- 菜单与工作台原则
- 联动边界和验证口径

本方案不负责：

- 逐字段字典
- DTO / API 细项
- 当前轮迁移脚本
- 具体 OWL 页面视觉设计

## 3. Odoo Benchmark

### 3.1 长期正式物流主线

当前项目正式主线不是销采存财单据链，而是：

```text
物流执行主线：
wave -> batch -> waybill -> customer_line -> order_line -> goods_line

物流追溯主线：
waybill / customer_line context -> trace_event -> evidence -> exception
```

这里要特别锁定 3 个长期边界口径：

1. `waybill` 是现场执行与正式留痕主对象
2. `customer_line` 是运单下的门店执行节点和页面阅读节点
3. `trace_event` 才是正式事实锚点，`customer_line` 不是它的替代物

### 3.2 官方模块已经提供什么

- `sale` / `sale_stock`
  - 报价、销售订单、履约来源、销售与出库联动
- `purchase` / `purchase_stock`
  - 采购订单、收货来源、采购退货来源
- `stock`
  - 仓库、库位、批次、调拨、盘点、拣货、`stock.move`、`stock.quant`
- `account`
  - 发票、红字、应收应付、收付款、对账
- `contacts`
  - 客户、门店、供应商主数据底座
- `fleet`
  - 车辆主数据底座
- `hr`
  - 员工主数据底座
- `mail`
  - 协同、消息、活动、轻量附件

### 3.3 官方模块不自然提供什么

官方模块不能自然表达下面这些对象和职责：

- `wave`
- `batch`
- `waybill`
- `customer_line`
- `order_line` / `goods_line` 的物流执行语义
- 运单为主对象的现场执行闭环
- `trace_event -> evidence -> exception` 的正式追溯链
- 物流工作台、运单工作台、门店节点阅读链

### 3.4 本期 Benchmark 结论

- 对 ERP 主链能力：优先 `extend Odoo`
- 对 WMS / TMS / BI / 系统底座：按模块边界拆分建设，能复用则复用，缺口再自建
- 对既有物流执行主线与追溯主线：本期以保留边界和稳定联动为主，不把它们错误并入官方单据
- 对客户、门店、员工、车辆、仓库等基础对象：`reuse directly` 或轻扩展

## 4. Design Decision

### 4.1 主线分层结论

系统中应承认 5 条长期业务主线，但本期建设优先级不能按“物流一号主线”来理解：

### A. 物流执行主线

```text
wave -> batch -> waybill -> customer_line -> order_line -> goods_line
```

角色：
- 长期系统中的物流执行主线
- 当前更多作为既有执行域和边界约束存在，不是本期最大新增建设面

归属：
- `logistics_dispatch`

路径：
- `create custom capability`

对官方侵入级别：
- `low ~ medium`

说明：
- 需要稳定关联 `sale`、`stock`、`fleet`、`contacts`
- 但不能把 `sale.order`、`stock.picking` 拉升成这条主线的主对象

### B. 物流追溯主线

```text
waybill / customer_line context -> trace_event -> evidence -> exception
```

角色：
- 长期系统中的物流追溯主线
- 当前更多作为既有追溯域和边界约束存在

归属：
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- 后续聚合展示可进入 `logistics_trace_dashboard`

路径：
- `create custom capability`

对官方侵入级别：
- `low ~ medium`

说明：
- `customer_line` 提供上下文和阅读入口
- `trace_event` 才是正式事实对象

### C. 销售主线

```text
customer -> quotation / sale.order -> delivery source -> invoice -> payment
```

角色：
- 本期核心建设主线之一
- 提供订单来源、价格语义、金额语义、应收结算基础

归属：
- 官方 `sale`
- 官方 `sale_stock`
- 官方 `account`

路径：
- `extend Odoo`

对官方侵入级别：
- `low ~ medium`

说明：
- 它不仅是业务来源域，也是本期建设重点

### D. 采购主线

```text
vendor -> purchase.order -> receipt source -> vendor bill -> payment
```

角色：
- 本期核心建设主线之一
- 提供补货来源、收货来源、应付结算基础

归属：
- 官方 `purchase`
- 官方 `purchase_stock`
- 官方 `account`

路径：
- `extend Odoo`

对官方侵入级别：
- `low ~ medium`

### E. 库存 / 发票主线

库存主线：
- 入库 / 出库 / 调拨 / 盘点 / quant / 库位 / 批次

发票主线：
- `account.move` 发票 / 红字 / 收付款 / 对账

角色：
- 本期核心建设主线之一
- 提供库存事实底座、仓储作业边界和财务结果底座
- 不承担物流执行主对象职责

归属：
- 官方 `stock`
- 官方 `account`

路径：
- `extend Odoo`

对官方侵入级别：
- `low ~ medium`

### 4.2 系统级原则

这 5 条主线在本期应按下面理解：

1. 本期建设中心是 ERP 闭环与 WMS / TMS / BI 分域归位
2. 物流既有主线继续存在，但当前主要承担边界约束和联动对象作用
3. 官方业务域可以积极启用、扩展、开放入口，以减少本期工作量
4. 但不能反向吞掉 `waybill / customer_line / trace_event` 这一套既有物流对象语义

## 5. Official vs Custom Boundary

### 5.1 官方模块复用边界表

| 领域 | 官方基线 | 选择路径 | 侵入级别 | 最终归属 |
|---|---|---|---|---|
| 客户 / 供应商 | `res.partner` | `reuse directly` + light extension | low | 官方主数据底座 |
| 门店 | `res.partner` | `extend Odoo` | low | 官方主数据底座，物流侧引用 |
| 员工 | `hr.employee` | `reuse directly` + light extension | low | 官方主数据底座 |
| 车辆 | `fleet.vehicle` | `reuse directly` + light extension | low | 官方主数据底座 |
| 仓库 / 库位 / 批次 | `stock` | `extend Odoo` | low | 官方仓储底座 |
| 销售订单 / 报价 | `sale` | `extend Odoo` | low ~ medium | 官方销售底座 |
| 采购订单 / 收货 | `purchase` | `extend Odoo` | low ~ medium | 官方采购底座 |
| 发票 / 对账 / 收付款 | `account` | `extend Odoo` | low ~ medium | 官方财务底座 |
| wave / batch / waybill | 无自然等价对象 | `create custom capability` | custom | `logistics_dispatch` |
| customer_line / order_line / goods_line | 无自然等价对象 | `create custom capability` | custom | `logistics_dispatch` |
| trace_event | 无自然等价对象 | `create custom capability` | custom | `logistics_trace_core` |
| evidence | 官方附件仅能作补充 | `create custom capability` | custom | `logistics_trace_evidence` |
| exception | 官方 activity 不足以替代 | `create custom capability` | custom | `logistics_trace_exception` |
| 物流聚合工作台 | 官方无等价对象 | `create custom capability` | custom | `logistics_web` / 后续 dashboard |

### 5.2 核心边界规则

必须守住下面这些规则：

1. `sale.order` 不是物流执行主对象
2. `stock.picking` 不是 `waybill`
3. `account.move` 不是现场完成凭证
4. `customer_line` 是门店执行与阅读节点，不替代 `trace_event`
5. 正式证据围绕 `trace_event`，图片业务阅读优先围绕 `customer_line`
6. 异常挂点优先在 `waybill / batch / trace_event`，不是默认挂订单
7. 库存结果与发票结果服务物流主线，但不吞掉物流主线
8. 菜单入口可以统一，模型主责不能混同

## 6. Module Ownership

### 6.1 `logistics_base`

职责：
- 共用字典
- 通用 mixin
- 官方对象上的共用扩展字段
- 统一编号、审计、组织、基础约定

不要承接：
- `wave / batch / waybill / trace / evidence / exception` 主体业务

### 6.2 `logistics_dispatch`

职责：
- `wave`
- `batch`
- `waybill`
- `customer_line`
- `order_line`
- `goods_line`
- 执行工作台
- 装车、司机、车辆、库位、线路等执行上下文

对外关系：
- 关联 `sale.order`
- 关联 `stock.picking`
- 关联 `stock.picking.batch`
- 关联 `res.partner`
- 关联 `fleet.vehicle`
- 关联 `hr.employee`

### 6.3 `logistics_trace_core`

职责：
- `trace_event`
- 运单级 / 批次级留痕
- 事实时间线

对外关系：
- 主挂 `waybill`
- 可挂 `batch`
- 可带 `customer_line` 上下文

### 6.4 `logistics_trace_evidence`

职责：
- `evidence`
- 图片元数据
- 证据阅读口径
- 外部对象存储 key

对外关系：
- 主挂 `trace_event`
- 可带 `waybill` / `customer_line` 辅读字段

### 6.5 `logistics_trace_exception`

职责：
- `exception`
- 异常分类、状态、处理记录
- 整改动作、关闭动作

对外关系：
- 可挂 `waybill`
- 可挂 `batch`
- 可挂 `trace_event`
- 必须能反读关键 `evidence`

### 6.6 既有物流前端承载

职责：
- 承接既有物流页、运单页、门店节点页、追溯聚合页
- 提供与 ERP / WMS / TMS 页面的反查入口整合

说明：
- 本期会逐步形成模块化入口
- 但不能因为入口统一，就把长期对象边界重新混在一起

## 7. Contract Surface

### 7.1 官方主线与物流主线的联动原则

#### 销售主线 -> 物流主线

建议关系：

- `sale.order` 是业务订单来源对象
- 物流系统可按销售单、销售单行生成或挂接 `order_line`
- 真正现场执行锚点仍然是 `waybill / customer_line`

建议联动：

- 从销售单或出库来源动作触发生成物流对象
- 物流详情页可反查销售订单
- 销售侧可通过 smart button 查看关联运单 / 批次

不要做：

- 让销售订单状态直接替代运单状态
- 让销售订单承载现场图片、正式留痕、异常主挂点

#### 采购主线 -> 物流 / 库存主线

建议关系：

- `purchase.order` 负责补货来源
- `stock.receipt` 负责收货结果
- 物流自定义模块只在需要时读取收货结果、库位结果和批次结果

不要做：

- 把采购单扩成物流执行单

#### 库存主线 -> 物流主线

建议关系：

- `stock.quant` / `stock.move` / `stock.picking` 负责库存事实底座
- 物流系统负责业务语义聚合与执行工作台

建议联动：

- 运单拣货、装车、发运结果可映射到出库动作
- 库位、批次、库存可用量从 `stock` 读取

不要做：

- 把 `stock.picking` 直接理解为 `waybill`

#### 发票主线 -> 物流主线

建议关系：

- 发票是结算凭证
- 物流完成不自动等于发票完成
- 发票可根据销售或履约结果创建，但不承担现场履约真相

建议联动：

- 物流可向销售/财务提供“已完成 / 部分完成 / 异常关闭”这类可结算信号
- 财务按业务规则决定是否开票、部分开票、红冲

不要做：

- 用发票状态驱动现场执行主状态

### 7.2 推荐的关系字段方向

建议至少预留下面几类关系：

- `logistics.dispatch.waybill`
  - `sale_order_ids`
  - `stock_picking_ids`
  - `vehicle_id`
  - `driver_employee_id`

- `logistics.dispatch.waybill.customer.line`
  - `partner_id`
  - `sale_order_line_ids`
  - `stock_move_ids`

- `logistics.trace.event`
  - `waybill_id`
  - `batch_id`
  - `customer_line_id`

- `logistics.trace.evidence`
  - `trace_event_id`
  - `waybill_id` as helper field
  - `customer_line_id` as helper reading field

- `logistics.trace.exception`
  - `waybill_id`
  - `batch_id`
  - `trace_event_id`
  - `evidence_ids`

### 7.3 推荐的动作与页面入口

统一菜单应按“ERP / WMS / TMS / BI 主入口 + 既有物流联动入口”理解：

- 本期主入口：
  - 订单经营 ERP
  - 仓库作业 WMS
  - 配送调度 TMS
  - 数据看板 BI
  - 系统底座 / 系统设置

- 既有物流联动入口：
  - 运单相关页
  - 门店节点页
  - 留痕 / 证据 / 异常页

页面动作建议：

- 销售单页：
  - `查看关联运单`
  - `查看关联批次`

- 运单页：
  - `查看来源销售单`
  - `查看关联出库单`
  - `查看留痕`
  - `查看证据`
  - `查看异常`

- `customer_line` 页：
  - 图片预览
  - 门店节点留痕摘要
  - 订单行明细
  - 货物行明细

- 发票页：
  - 仅提供物流关联反查，不做现场执行入口

## 9. Verify

最小验证清单：

1. 销售、采购、库存/拣货、财务、结账、报表这条本期闭环是否清晰
2. WMS / TMS 的边界是否清晰，没有继续把仓内动作和配送动作混在 ERP 里
3. 销售单是否能稳定反查到关联运单
4. 既有 `trace_event -> evidence -> exception` 是否能在不依赖销售单的情况下闭环
5. `customer_line` 是否只承担节点与阅读层，不替代正式事实锚点
6. 发票是否仅承担结算结果，不干扰现场执行状态
7. 库位、库存、批次是否仍以官方 `stock` 或 WMS 边界语义为准
8. 多公司、多权限下，ERP / WMS / TMS / BI 与既有物流对象的读取边界是否清晰
9. 菜单是否做到统一入口，但未混淆对象归属

## 10. Risks / Open Questions

### 10.1 主要风险

- 把 `sale.order` 或 `stock.picking` 过度拉伸成物流主对象
- 状态映射过多，导致双向回写失控
- 发票、库存、物流完成三套状态互相覆盖
- `customer_line` 既承担阅读层又承担正式事实锚点，造成模型污染
- 过度侵入官方模块，提升升级难度
- 菜单统一后，团队误以为模型职责也可以混同
- 以“本期做 ERP”为理由，把长期 WMS / TMS / 物流边界错误塞回单一模块

### 10.2 当前开放问题

1. `waybill` 与 `stock.picking` 是一对一、一对多还是多对多
2. `customer_line` 的生成时机是按销售单、按出库单还是按外部导入
3. 物流完成信号如何传给销售与发票，但不反向劫持物流状态
4. 哪些库存动作必须实时写回 `stock`，哪些允许异步聚合
5. 门店是否只复用 `res.partner`，还是需要额外门店层字段与行为约束
