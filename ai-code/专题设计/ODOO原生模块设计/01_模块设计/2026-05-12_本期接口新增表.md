## 1. Objective

在正式开发跨模块联动前，先把本期需要新增或明确的接口整理出来，回答 5 个问题：

1. 哪些模块之间必须对接
2. 每条接口由谁触发
3. 传递什么主对象和关键字段
4. 谁是状态源头
5. 失败后如何补偿

---

## 2. 使用原则

- 接口先服务本期 P0 / P1 闭环，不扩成长期全集
- 每条接口必须明确“源头模块”和“目标模块”
- 每条接口必须明确“状态源头是谁”
- 允许先文件导入或批量同步，但口径要先锁住
- BI 接口默认只读，不反向改业务数据

## 4. 分方向接口说明

### 4.1 ERP -> WMS

本期至少需要两类下发：

- 销售出库计划下发
- 采购到货计划下发

必须传：

- 单据编号
- 门店/供应商
- SKU
- 数量
- 仓库
- 时效要求
- 批次要求（如适用）

不能让 WMS 自己补脑决定：

- 业务来源单据是谁
- 计划数量是多少
- 门店是谁

### 4.2 WMS -> ERP

本期至少需要三类回传：

- 收货结果回传
- 出库结果回传
- 盘点/调整结果回传

必须传：

- 来源单据编号
- 实际数量
- 差异数量
- 批次/效期
- 库存变动结果

状态源头：

- 实物动作状态以 WMS 为准
- 账面库存更新以 ERP 为准

### 4.3 WMS -> TMS

本期核心接口是：

- 装车交接完成后，通知 TMS 可以进入派车 / 发车链

必须传：

- 交接单号
- 线路编号
- 待配送门店集合
- 重量 / 方数 / 件数
- 装车状态

状态源头：

- 装车交接状态以 WMS 为准
- 派车与配送执行状态以 TMS 为准

### 4.4 TMS -> ERP

本期核心接口是：

- 签收结果回传
- 配送异常回传
- 运费明细回传

必须传：

- 签收状态
- 门店
- 回单引用
- 异常类型
- 赔付金额
- 运费明细

状态源头：

- 签收与配送异常状态以 TMS 为准
- 对账、扣赔、结算状态以 ERP 为准

### 4.5 各业务域 -> BI

BI 不做业务动作，只吃汇总或快照。

推荐本期先做：

- ERP 经营结果快照
- WMS 作业结果快照
- TMS 配送结果快照

不建议本期先做：

- 实时强一致复杂事件总线
- 复杂多层宽表

### 4.6 ERP/WMS/TMS -> 既有物流域

这部分本期不是主链接口，但必须预留：

- ERP 回传销售/结算结果摘要
- WMS 回传出库/装车结果摘要
- TMS 回传签收/异常结果摘要

用途：

- 保持既有物流页还能做统一反查
- 不让既有 `waybill / customer_line / trace_event` 失联

## 5. 本期接口实现建议

### 5.1 P0 / P1 建议优先形式

优先顺序建议：

1. 同库同系统内服务调用
2. 批处理同步表 / 待回写队列
3. 定时任务同步
4. 最后再考虑更重的异步事件流

### 5.2 每条接口建议的最小元数据

建议每条接口或同步任务至少记录：

- `interface_code`
- `source_module`
- `target_module`
- `source_doc_type`
- `source_doc_ref`
- `trigger_time`
- `payload_version`
- `sync_status`
- `retry_count`
- `last_error_message`

---

## 6. 本期明确不建议先做的接口

本期先不要一上来就做这些：

- B2B 全量对 ERP/WMS/TMS 的实时同步
- BI 反向控制业务模块
- 既有物流域反向驱动 ERP 主状态
- 多模块双向自动回写所有状态

原因：

- 会迅速把状态源头做乱
- 超出本期闭环最小必要范围

---

## 7. Verify

这份接口清单是否可用，可以用下面 7 条检查：

1. 本期 P0 / P1 主链是否都有对应接口支撑
2. 每条接口是否都定义了状态源头
3. 是否避免了 ERP、WMS、TMS 多边同时写同一业务状态
4. 是否保留了既有物流域的联动接口，但没有让其反客为主
5. 是否给出了失败补偿思路
6. BI 是否保持只读，不反向改业务
7. 是否能直接作为后续服务层、同步队列或任务调度设计输入
