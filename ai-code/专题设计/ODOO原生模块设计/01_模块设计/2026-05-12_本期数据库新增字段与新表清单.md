## 1. Objective

在正式开发前，先把本期数据库结构层需要新增的内容收口成清单，回答 4 个问题：

1. 哪些原生模型需要补字段
2. 哪些新表必须新增
3. 哪些表属于 ERP / WMS / TMS / BI / 系统底座
4. 哪些既有物流对象只补联动字段，不在本期重做主结构

---

## 2. 使用原则

- 先做结构清单，不直接等于最终迁移脚本
- 优先新增最小够用字段，不一次性把未来全部字段都塞进去
- 一张表只服务一个主责域
- 联动优先通过外键、关系表、状态摘要字段实现
- 既有物流域本期只补联动字段，不轻易改主语义

## 5. 本期明确不建议新增的大表

本期先不要上来就建下面这些重型结构：

- 完整 B2B 商城订单域全套表
- 完整总账、会计凭证衍生分析表
- 完整 BI 宽表与多层中间层
- 重型补货算法表
- 全量重建既有 `logistics_*` 主表

原因：

- 这些都不是本期 P0 / P1 核心阻塞项
- 过早建大表容易把长期蓝图错误压进本期范围

---

## 6. 本期结构设计顺序

建议按下面顺序继续下钻：

1. 先锁原生模型新增字段
2. 再锁 P0 / P1 必须新增的新表
3. 再锁表之间的主外键关系
4. 最后才进入实际迁移脚本和 ORM 模型设计

---

## 7. Verify

这份结构清单是否可用，可以用下面 7 条检查：

1. 是否每个本期主责域都有对应结构落点
2. 是否优先补的是 P0 / P1 最小够用字段和表
3. 是否没有把 WMS / TMS / 既有物流域结构错误塞进 ERP
4. 是否没有把 ERP 经营主档错误塞进 WMS / TMS
5. 是否既保留了长期物流域边界，又避免了本期重做
6. 是否能自然映射到开发工作清单中的各项任务
7. 是否可以直接作为下一步 ORM 模型设计和迁移脚本的输入
