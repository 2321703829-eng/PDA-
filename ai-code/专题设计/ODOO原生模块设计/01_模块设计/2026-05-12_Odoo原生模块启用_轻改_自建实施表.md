## 1. Objective

给当前 Odoo 19 城市供应链项目一张可直接指导本期实施顺序的表，回答 3 个问题：

1. 哪些 Odoo 原生模块应该立刻启用
2. 启用后哪些字段、视图、动作需要轻改
3. 哪些能力进入 ERP / WMS / TMS / BI / 系统底座，哪些能力继续留在既有物流域

---

## 2. 使用原则

- 优先启用能直接减少基础工作量的原生模块
- 优先做 `low` 侵入改造，谨慎进入 `medium`
- 本期优先服务 ERP / WMS / TMS / BI 的功能闭环
- 不用官方对象替代 `wave / batch / waybill / customer_line / trace_event`
- 页面入口按本期模块化建设组织，不继续把所有功能堆在一个物流工具里

---

| P0 | `stock` | 是 | 仓库、库位、批次、库存结果、出入库底座现成，是本期库存/仓储基础 | 增加仓储作业入口、补 ERP/WMS 反查字段、搜索筛选、看板入口 | 长期 `waybill` 执行语义、`customer_line`、既有物流工作台 | `extend Odoo` | low |

| P0 | `account` | 是 | 发票、应收应付、收付款底座现成，是本期财务与结账基础 | 发票页增加物流反查字段和入口、结算信号字段、筛选 | 现场完成状态、现场证据、异常处理闭环 | `extend Odoo` | low ~ medium |

| P1 | `stock_picking_batch` | 参考启用 | 提供 batch / wave 组织方式参考，减少从零理解批量作业成本 | 可补 smart button 或只做参考关系，不建议直接顶替项目批次对象 | 项目自己的 `wave`、`batch` 语义与页面 | `extend Odoo` 或参考复用 | low ~ medium |

## 4. 分模块实施建议

## 4.1 立刻启用且收益最高

### `contacts`

为什么先启用：

- 客户、门店、供应商都需要主数据底座
- 自己重造主数据最不划算

建议轻改：

- 字段
  - 门店类型
  - 门店编码
  - 物流可服务标记
  - 默认配送规则辅助字段
- 视图
  - 门店筛选页签
  - 客户 / 门店 / 供应商区分入口
- 动作
  - `查看关联运单`
  - `查看关联 customer_line`

不要做：

- 不要把 `res.partner` 当成物流执行对象

### `stock`

为什么先启用：

- 仓库、库位、批次、库存数量、出入库事实都是现成底座
- 本期库存、WMS 边界、拣货前后状态都离不开它

建议轻改：

- 字段
  - picking / move 上补关联物流对象字段
  - quant 查询页补物流辅助维度
- 视图
  - picking 列表补物流摘要列
  - quant 列表补库位、批次、可用量强化展示
- 动作
  - `查看关联运单`
  - `查看关联批次`

不要做：

- 不要把 `stock.picking` 直接改名理解为 `waybill`

### `sale` + `sale_stock`

为什么先启用：

- 销售订单、价格、客户订单来源、销售与出库联动都成熟
- 本期销售主链优先级高，原生复用收益最大

建议轻改：

- 字段
  - 关联 `waybill` / `batch` 摘要字段
  - 物流进度摘要字段
- 视图
  - 销售单增加物流信息页签或 smart button 区块
  - 列表页增加“是否已挂运单”筛选
- 动作
  - `生成 / 查看物流对象`
  - `查看关联运单`

不要做：

- 不要让销售单状态直接取代运单状态

### `account`

为什么先启用：

- 发票、收付款、应收应付、红冲都成熟，不值得重造
- 本期财务管理、对账、结账都需要它做底座

建议轻改：

- 字段
  - 结算来源辅助字段
  - 物流完成信号辅助字段
- 视图
  - 发票页增加物流反查入口
  - 对账页增加物流来源筛选
- 动作
  - `查看来源销售单`
  - `查看关联运单`

不要做：

- 不要把发票完成当成现场履约完成

---

## 4.2 应启用，但排在第二梯队

### `purchase` + `purchase_stock`

为什么进入第一批：

- 本期采购主链本身就是核心范围
- 采购、到货、收货结果和库存账必须尽早收口

建议轻改：

- 字段
  - 入库结果摘要
  - 供应商履约辅助信息
- 视图
  - 采购单页增加收货结果、库存影响摘要
- 动作
  - `查看收货单`
  - `查看库存影响`

不要做：

- 不要把采购单扩成物流执行单

### `fleet`

建议轻改：

- 字段
  - 是否参与物流调度
  - 载重、体积、温层、车牌别名
- 视图
  - 增加物流调度筛选

### `hr`

建议轻改：

- 字段
  - 是否司机
  - 是否调度员
  - 是否异常处理责任人
- 视图
  - 员工页增加物流角色筛选

### `stock_picking_batch`

建议理解：

- 它适合作为波次/批量作业参考
- 可以启用来看原生组织方式
- 但不建议直接当项目最终 `wave / batch`

## 4.3 必须自建，不能靠原生覆盖

### 既有 `logistics_dispatch`

当前处理原则：

- 不是本期最大新增建设面
- 继续保留为既有执行域
- 重点是保持边界稳定，并与 ERP / WMS / TMS 建立正确联动

至少承接：

- `wave`
- `batch`
- `waybill`
- `customer_line`
- `order_line`
- `goods_line`
- 物流执行工作台

### 既有 `logistics_trace_core`

当前处理原则：

- 继续保留为既有追溯事实层
- 本期不把它错误并入销售、库存或发票对象

至少承接：

- `trace_event`
- 运单级 / 批次级留痕
- 留痕时间线

### 既有 `logistics_trace_evidence`

当前处理原则：

- 继续保留为既有证据层
- 本期重点是做好与签收、异常、对账结果的联动边界

至少承接：

- 证据对象
- 图片元数据
- 外部对象存储 key
- 证据列表 / 详情 / 预览链

### 既有 `logistics_trace_exception`

当前处理原则：

- 继续保留为既有异常层
- 本期重点是分清仓库异常、配送异常、财务扣赔之间的数据归口

至少承接：

- 异常对象
- 状态流转
- 处理记录
- 关联证据

### 既有 `logistics_web`

当前处理原则：

- 继续保留既有物流页和聚合页
- 本期更多做菜单梳理和反查入口打通，而不是把所有用户都强行收口到物流工作台

至少承接：

- 运单列表
- 运单详情
- `customer_line` 阅读页
- 留痕 / 证据 / 异常聚合入口

## 5. 推荐实施顺序

| 阶段 | 建议动作 | 目标 |
|---|---|---|
| P0-1 | 启用 `contacts`、`mail`、`sale`、`purchase`、`stock`、`account` | 先把主数据、销采存财底座就位 |
| P0-2 | 结合本期范围梳理 ERP / WMS / TMS / BI 菜单与归属 | 先把功能归位，不继续杂糅 |
| P0-3 | 给 `sale`、`purchase`、`stock`、`account` 增加 smart button、关系字段、摘要列 | 打通反查与联动，但不改坏官方语义 |
| P1-1 | 启用并接入 `fleet`、`hr`，整理 TMS 相关基础档案 | 补齐车辆、司机、调度基础关系 |
| P1-2 | 保持 `logistics_*` 既有域稳定，补联动入口 | 保证长期物流边界不被错误吞并 |
| P1-3 | 评估 `stock_picking_batch`、WMS/TMS 目录与对象拆分方式 | 为后续模块化演进留结构 |

## 6. 一眼判断表

| 如果问题是… | 本期优先放哪里 |
|---|---|
| 客户、门店、供应商资料怎么管 | `contacts` / `res.partner` |
| 仓库、库位、批次、库存数量怎么管 | `stock` |
| 销售订单、销售出库来源怎么管 | `sale` / `sale_stock` |
| 发票、应收应付、收付款怎么管 | `account` |
| 车辆、司机基础资料怎么管 | `fleet` / `hr` |
| 运单、门店节点、运单明细怎么管 | 继续放既有 `logistics_dispatch` |
| 现场留痕、图片证据、异常闭环怎么管 | 继续放既有 `logistics_trace_*` |
| 用户日常工作的主入口怎么做 | 本期按 ERP / WMS / TMS / BI 模块化入口组织 |

## 7. Verify

这张表是否适用，可以用下面 6 条快速验证：

1. 是否已经把“直接启用能省工作量”的原生模块放进前两阶段
2. 是否本期优先服务了销采存财与 WMS / TMS 的功能闭环
3. 是否没有试图用 `sale.order` 或 `stock.picking` 替代 `waybill`
4. 是否把 `trace_event / evidence / exception` 留在既有自定义模块里
5. 是否对发票只做结算联动，没有让它接管现场执行状态
6. 是否优先做了 smart button、关系字段、摘要列和菜单归位，而不是先深改官方状态机
