# B2B 订货商城模块设计方案

文档类型：
- 模块设计

当前状态：
- active

适用阶段：
- 后续阶段正式设计
- 可作为 `kebi` 外部客户订货入口的前置方案

## 1. Objective

设计一套面向客户 / 门店 / 经销商的 `B2B` 订货商城方案，明确它与 `ERP / WMS / TMS / BI / 既有物流域` 的边界、模块复用路径、最小可行对象、页面入口和分阶段落地策略。

## 2. Boundary

本方案只定义 `B2B` 的模块设计与接入方式，不直接包含：

- 仓库拣货、复核、装车、盘点
- 排线、派车、司机任务、签收回单
- 完整财务记账和司机结算
- 重型营销中心、优惠券中心、积分中心
- 独立支付清结算平台

本方案默认：

- `B2B` 是客户前端交易入口
- `ERP` 是商品、客户、价格、销售单、库存账和结算主责域
- `WMS / TMS` 负责履约执行
- `BI` 负责只读分析
- 本期不新建完整独立 `B2B` 订单主表体系，订单先落到 `sale.order`
- 本期不接微信 / 支付宝等在线支付，先走账期、线下转账或货到结算

## 3. Benchmark

### 3.1 Odoo 原生可复用能力

- `website`
  - 提供网站、路由、页面和主题基础
- `portal`
  - 提供客户账号、订单查询、自助查看入口基础
- `website_sale`
  - 提供商品展示、购物车、结算、下单基础
- `website_sale_stock`
  - 提供前端库存可售显示基础
- `sale`
  - 提供正式销售订单和订单行主对象
- `contacts`
  - 提供客户、联系人、门店关联底座

### 3.2 当前仍缺的业务能力

- 客户可见商品范围控制
- 客户专属价 / 门店价 / 区域价读取
- 门店选择、送达时间、订货备注等订货口径
- `B2B` 订单来源标记和提交校验
- 客户订单查询页与 `WMS / TMS` 摘要联动
- 售后入口与异常流转
- `kebi` 正式站之外的客户前端接入策略

### 3.3 选型结论

采用：

- 原生复用：`website + portal + website_sale + sale`
- 本地化等级：`medium intrusion`
- 自定义补充：新增 `b2b_*` 客户入口能力，不把 `website_sale` 直接当成最终业务层

不采用：

- 直接裸开放原生商城给客户使用
- 先建一整套脱离 `sale.order` 的独立订单域
- 把 `B2B` 前台职责塞回 `ERP` 后台工作台

## 4. Current Understanding

现有设计已经明确：

- `B2B` 在中长期蓝图中存在明确位置
- 本期主建设面是 `ERP / WMS / TMS / BI`
- `B2B` 本期不是必须立即完工的主战场
- 但后续一旦启动，必须建立在当前主数据、价格、库存口径、销售承接链已经稳定的前提上

当前最合理的建设口径不是“重做一个商城系统”，而是：

- 先用 Odoo 原生商城能力承接客户入口
- 用自定义能力补齐客户价、门店、送达要求、订单追踪和售后口径
- 订单继续进入 `sale.order`
- 履约继续走 `WMS / TMS`

## 5. OBB

### 5.1 Outcome

客户能够在 `B2B` 前端：

- 登录
- 看商品
- 看自己的价格
- 选择门店
- 下单
- 查订单
- 看履约摘要

后台能够：

- 以 `sale.order` 承接 `B2B` 订单
- 识别订单来源为 `b2b`
- 将后续履约和结算继续交给 `ERP / WMS / TMS`

### 5.2 Behavior

最小业务链：

1. 客户登录 `B2B`
2. 读取客户可见商品与价格
3. 加入购物车并选择收货门店
4. 提交订单
5. 生成 `sale.order` 与 `sale.order.line`
6. `sale.order.source_channel = b2b`
7. 销售单审核后进入既有 `ERP -> WMS -> TMS` 链
8. `B2B` 订单页展示销售状态、仓配摘要、签收结果摘要
9. 付款状态由 `ERP / account` 侧维护，`B2B` 只展示付款方式和收款摘要

### 5.3 Boundary

`B2B` 不拥有：

- 实物库存主责
- 仓配作业状态机主责
- 财务应收应付主责
- 运单 / 交接单 / 派车单主责

`B2B` 只拥有：

- 客户访问入口
- 商品与价格展示入口
- 购物车和下单入口
- 客户视角订单查询与售后发起入口

## 6. 模块定位

### 6.1 一句话定位

`B2B` 是客户订货前台，不是经营中台，也不是仓配执行系统。

### 6.2 模块职责

- 客户登录与身份识别
- 商品目录展示
- 客户价展示
- 购物车
- 下单
- 订单查询
- 物流状态摘要展示
- 售后 / 异常发起

### 6.3 不承担的职责

- 价格规则维护
- 采购和供应商管理
- 库位与批次管理
- 拣货 / 复核 / 装车
- 排线 / 派车 / 签收执行
- 对账 / 结账 / 总账

## 7. 页面与入口设计

### 7.1 前端页面

- `B2B 首页`
  - 今日主推商品
  - 快捷分类
  - 订单入口
- `商品列表页`
  - 分类、品牌、规格、搜索
  - 可售库存提示
  - 当前客户价格
- `商品详情页`
  - SKU、箱规、单位、起订量、图片
  - 可送门店 / 配送限制提示
- `购物车页`
  - 数量调整
  - 门店选择
  - 送达要求
- `订单提交页`
  - 订单备注
  - 收货门店
  - 预估金额
- `我的订单页`
  - 待审核
  - 待出库
  - 配送中
  - 已签收
  - 异常
- `订单详情页`
  - 商品明细
  - 金额明细
  - `WMS / TMS` 摘要
  - 留痕 / 回单摘要
- `售后申请页`
  - 缺货
  - 短少
  - 破损
  - 拒收

### 7.2 正式站入口

推荐形态：

- 客户前端独立域名或独立路径
  - 如 `/shop` 或独立 `b2b.xxx.cn`
- 不建议直接挂进当前 `kebi` 企业后台首页
- `kebi` 后台只保留：
  - B2B 配置入口
  - 订单审核入口
  - 商品与价格同步入口

### 7.3 付款展示与下单后处理

当前阶段 `B2B` 不做在线支付页，不做支付回调，不做商城内退款。

页面只需要展示：

- 付款方式
- 是否需先款后货
- 是否已收款
- 对账 / 账期提示

推荐支持的付款方式：

- `credit`
  - 账期结算
- `bank_transfer`
  - 线下转账
- `cash_on_delivery`
  - 货到结算
- `monthly_statement`
  - 月结

## 8. 数据与对象设计

### 8.1 继续复用的主对象

- `res.partner`
  - 客户
  - 门店
  - 联系人
- `product.template` / `product.product`
  - 商品和 SKU
- `sale.order`
  - 正式订单主对象
- `sale.order.line`
  - 正式订单行

### 8.2 建议新增的最小自定义对象

- `b2b.catalog.scope`
  - 记录客户 / 门店可见商品范围
- `b2b.cart.draft`
  - 客户购物车草稿
- `b2b.cart.draft.line`
  - 购物车草稿明细
- `b2b.after_sale.ticket`
  - 客户售后申请

当前阶段不建议新建：

- 独立 `b2b.order` / `b2b.order.line` 正式订单域
- 独立 `b2b.payment` 支付域
- 独立营销活动全套域模型

### 8.3 关键字段建议

在现有设计基础上补充：

- `sale.order.source_channel = b2b`
- `sale.order.store_partner_id`
- `sale.order.delivery_time_required`
- `sale.order.b2b_submit_user_id`
- `sale.order.b2b_submit_note`
- `sale.order.b2b_payment_method`
- `sale.order.b2b_payment_status_note`
- `res.partner.is_b2b_customer`
- `res.partner.is_b2b_store`
- `res.partner.b2b_payment_method_default`
- `res.partner.b2b_is_credit_customer`
- `res.partner.b2b_credit_limit`
- `product.template.is_b2b_visible`
- `product.template.b2b_sort_no`
- `product.template.b2b_min_qty`

## 9. 状态与流转

### 9.1 B2B 自身轻量状态

- `cart_draft`
- `submitted`
- `cancelled`

### 9.2 正式订单状态主责

正式状态仍以 `sale.order` 和后续 `WMS / TMS` 摘要为准：

- `draft`
- `to_review`
- `confirmed`
- `wms_processing`
- `tms_processing`
- `signed`
- `delivery_exception`
- `closed`

`B2B` 前台只消费摘要，不另建一套平行状态机。

### 9.3 付款状态口径

当前阶段付款状态不在 `B2B` 前台单独建正式状态机，建议只展示轻量摘要：

- `unpaid`
- `pending_confirm`
- `partially_paid`
- `paid`

正式收款和核销仍以 `account.move / account.payment` 为准。

## 10. 下单与付款链路

### 10.1 下单链路

1. 客户登录 `B2B`
2. 加载客户可见商品、客户价、默认门店和默认付款方式
3. 客户加入购物车
4. 选择收货门店、送达要求、备注
5. 提交订单
6. 系统生成 `sale.order` 与 `sale.order.line`
7. 写入 `source_channel = b2b`
8. 进入 `ERP` 审核与后续履约链

### 10.2 付款链路

当前阶段不做线上支付，采用“下单成功、付款后置”的模式：

- 账期客户
  - 下单成功
  - 发货 / 签收后进入应收与对账
  - 财务登记收款
- 线下转账客户
  - 下单成功
  - 客户线下转账
  - 财务确认到账后放行或继续处理
- 货到 / 月结客户
  - 下单成功
  - 按客户结算方式进入后续收款流程

### 10.3 B2B 前台付款职责

`B2B` 前台只负责：

- 展示付款方式
- 展示付款说明
- 展示收款摘要
- 必要时提供上传付款凭证入口

`B2B` 前台不负责：

- 调起支付网关
- 支付回调处理
- 自动对账
- 退款闭环

## 11. 接口与同步

### 11.1 输入

- ERP 提供：
  - 商品主档
  - 商品图片
  - 客户价
  - 门店关系
  - 基础可售标记
- WMS / TMS 提供：
  - 履约摘要
  - 签收 / 异常摘要

### 11.2 输出

- `B2B -> ERP`
  - 订单提交
  - 售后申请
- `ERP / WMS / TMS -> B2B`
  - 订单状态摘要
  - 出库 / 配送 / 签收摘要
  - 异常处理结果

## 12. 与现有系统的关系

### 12.1 与 ERP

- ERP 维护商品、客户、价格、销售单、应收口径
- `B2B` 只读取并发起订单

### 12.2 与 WMS

- WMS 不接受来自 `B2B` 的直接作业指令
- WMS 只接受 ERP 正式销售单 / 出库计划

### 12.3 与 TMS

- TMS 不直接接 `B2B` 订单
- `B2B` 只展示配送摘要和签收结果

### 12.4 与既有物流域

- `B2B` 不反向改写 `waybill`
- 如需客户查询物流，可读取基于销售单 / 运单映射的摘要

## 13. 分阶段实施建议

### 13.1 Phase 1：订货 MVP

- 客户登录
- 商品展示
- 客户价展示
- 购物车
- 提交订单
- 生成 `sale.order`
- 付款方式展示

### 13.2 Phase 2：订单查询与履约摘要

- 我的订单
- 订单详情
- 出库 / 配送 / 签收摘要
- 收款摘要

### 13.3 Phase 3：售后入口

- 缺货 / 短少 / 破损 / 拒收申请
- 与异常处理链联动

### 13.4 Phase 4：营销增强

- 轻量促销
- 满减 / 套餐 / 活动页

## 14. 前置条件

启动 `B2B` 前，至少应满足：

- 商品主档稳定
- 客户 / 门店主档稳定
- 客户价口径稳定
- 可售库存口径稳定
- 销售订单承接稳定
- 客户结算方式和基础收款规则稳定
- `WMS / TMS` 基础履约链已可用
- `kebi` 后台接入和权限体系稳定

## 15. 风险

- 价格未收口就上商城，会直接放大价格错误
- 可售库存口径不稳，会造成前台下单与仓内执行冲突
- 如果过早自建独立 `b2b.order` 正式订单域，会和现阶段 `sale.order` 承接策略打架
- 如果过早接支付网关，会显著增加对账、退款和风控复杂度
- 如果直接复用原生商城默认主题，正式站体验会和现有系统风格脱节

## 16. 结论

`B2B` 可以做，而且后续必须做，但最稳的方案不是“立即重做一整套独立商城”，而是：

- 以 `website + portal + website_sale + sale` 为底座
- 通过中等侵入本地化补齐客户价、门店、订货和履约摘要
- 当前阶段不接在线支付，先走账期、线下转账和货到 / 月结
- 订单继续由 `sale.order` 承接
- 履约继续走 `ERP -> WMS -> TMS`

这能确保：

- 前端交易入口真正建立起来
- 又不会把当前已经跑通的经营和仓配链重新打散
