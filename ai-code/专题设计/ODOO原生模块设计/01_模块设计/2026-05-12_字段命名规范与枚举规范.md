## 1. Objective

在正式进入模型实现前，先把本期字段命名和枚举命名统一起来，避免后续出现：

- 同义字段多种写法
- 枚举值长短不一
- ERP/WMS/TMS/既有物流域命名混乱
- 接口和数据库字段口径不一致

---

## 2. 总原则

- 字段名统一使用英文小写蛇形命名
- 外键统一使用 `_id`
- 多值关系统一使用 `_ids`
- 布尔字段优先使用 `is_` / `has_` / `can_`
- 数量字段优先明确单位和语义
- 枚举值尽量短、稳定、可读
- 中文含义可以长，字段英文必须短而清楚

---

## 3. 字段命名规范

### 3.1 通用后缀规范

| 类型 | 规范 | 示例 |
|---|---|---|
| 主键 | `id` | `id` |
| 外键 | `_id` | `partner_id` |
| 多值关系 | `_ids` | `sale_order_ids` |
| 编码 | `_code` | `warehouse_code` |
| 名称 | `_name` | `route_name` |
| 状态 | `_status` | `wms_task_status` |
| 类型 | `_type` | `partner_role_type` |
| 日期 | `_date` | `arrival_plan_date` |
| 时间点 | `_at` | `last_failed_login_at` |
| 数量 | `_qty` | `reserved_qty` |
| 金额 | `_amount` | `freight_amount` |
| 比率/百分比 | `_rate` | `discount_rate` |
| 备注 | `_note` / `_remark` | `delivery_note` |
| 引用单号 | `_ref` | `business_source_ref` |
| 排序 | `_seq` / `_order` | `stop_seq` |

### 3.2 布尔字段规范

优先前缀：

- `is_`
- `has_`
- `can_`
- `allow_`

示例：

- `is_enabled`
- `is_driver`
- `has_batch_control`
- `can_split_delivery`
- `allow_negative_stock`

不要写：

- `enable_flag`
- `driver_yes_no`
- `status_bool`

### 3.3 数量字段规范

必须尽量写清语义：

- `ordered_qty`
- `planned_qty`
- `received_qty`
- `picked_qty`
- `checked_qty`
- `signed_qty`
- `returned_qty`
- `available_qty`
- `reserved_qty`

不要只写：

- `qty1`
- `num`
- `count_qty`

### 3.4 金额字段规范

优先使用：

- `order_amount`
- `payment_amount`
- `freight_amount`
- `deduction_amount`
- `compensation_amount`
- `profit_amount`

如果有税额语义，明确写出：

- `tax_amount`
- `amount_untaxed`
- `amount_total`

## 4. 枚举规范

### 4.1 枚举值总体要求

- 值尽量短
- 尽量单词化
- 不在枚举值里带中文
- 不混用过去式和现在式风格
- 一个状态链内部尽量统一风格

### 4.2 推荐状态值风格

推荐风格：

- 草稿：`draft`
- 待确认：`to_confirm`
- 已确认：`confirmed`
- 处理中：`processing`
- 已完成：`done` 或业务化明确值
- 已关闭：`closed`
- 已取消：`cancelled`
- 异常：`exception`

不要混写：

- `done`
- `finished`
- `complete`
- `completed`

同一个状态链只选一种主风格。

### 4.3 领域前缀规范

如果字段本身已经说明域，不强制加前缀。  
如果同一对象里会出现多个域状态，建议加域前缀。

示例：

- `erp_business_status`
- `wms_task_status`
- `tms_delivery_status`

## 6. 关系表命名规范

多对多关系表建议统一：

- `rel_<left>_<right>`

示例：

- `rel_waybill_sale_order`
- `rel_waybill_stock_picking`
- `rel_handover_dispatch_order`

关系表字段建议：

- `<left>_id`
- `<right>_id`
- `link_type`（如需要）
- `created_at`

---

## 7. 快照表命名规范

BI 与汇总快照建议统一：

- `bi_*_snapshot`

示例：

- `bi_daily_kpi_snapshot`
- `bi_exception_snapshot`
- `bi_cost_profit_snapshot`

快照字段建议至少有：

- `snapshot_date`
- `snapshot_time`
- `source_module`
- `metric_code`
- `metric_value`

---

## 8. 接口字段命名补充

接口载荷字段建议尽量与数据库主字段一致。

例如：

- `source_doc_ref`
- `source_module`
- `target_module`
- `trigger_time`
- `sync_status`
- `retry_count`
- `last_error_message`

不要在接口里再改成另一套风格，比如：

- `sourceDocRef`
- `source-doc-ref`
- `src_ref`

如果后端框架或前端协议确实要用其他风格，应有统一转换层，不要让表结构和接口结构各自发散。

---

## 9. 本期应避免的命名问题

不要出现下面这些：

- 同一个“门店编码”在不同表里写成 `store_code` / `shop_code` / `customer_store_code`
- 同一个“配送状态”同时写成 `delivery_status` / `dispatch_status` / `send_status`
- 同一个“是否启用”同时写成 `is_enabled` / `enabled_flag` / `active_bool`
- 同一个“金额”混写成 `money` / `amount` / `price_total`
- 状态值混写成 `done` / `completed` / `finished`

---

## 10. Verify

这份命名规范是否可用，可以用下面 6 条检查：

1. 是否足以覆盖本期数据库新增字段与新表
2. 是否足以覆盖本期接口新增表
3. 是否让 ERP/WMS/TMS/既有物流域字段风格统一
4. 是否让状态字段和状态映射表口径一致
5. 是否避免了未来模型和接口双套命名
6. 是否可以直接指导 ORM 字段命名和 SQL 表设计
