## 1. Objective

把本期工作总纲进一步拆成可执行开发清单，明确：

1. 本期按什么顺序开发
2. 每块功能由哪个模块主责
3. 每块功能依赖什么前置条件
4. 每块功能以什么口径验收
5. 每块功能是复用原生、轻改原生，还是新增自定义

---

## 2. 使用规则

- 本清单以本期总纲为准，不扩成长期完整蓝图
- 每项任务都必须有唯一主责模块
- 每项任务都必须明确依赖和验收口径
- 能复用原生模块的，不先自建
- 涉及 WMS / TMS / 既有物流域联动的任务，不得绕过边界文档单独拍脑袋实现

---

## 3. 本期任务分层

本期任务按下面 4 层理解：

### 3.1 P0 基础层

先做没有它就没法稳定推进的内容：

- 系统底座最小可用
- 主数据最小可用
- ERP 基础经营闭环骨架

### 3.2 P1 主链层

先把核心业务链跑顺：

- 销售主链
- 采购主链
- 库存账
- 收付款 / 对账 / 结账

### 3.3 P1 仓配层

把仓内动作和配送动作从杂糅状态中拆出来：

- WMS 核心动作
- TMS 核心动作

### 3.4 P2 看板与联动优化层

在主链跑顺后再补：

- BI 最小看板
- 跨模块体验优化
- 既有物流域反查与协同完善

## 6. 本期最关键的前置依赖

下面这些依赖必须提前锁住，否则后面开发会反复返工：

### 6.1 主数据编码规则

必须先锁：

- 商品编码
- 客户编码
- 供应商编码
- 门店编码
- 司机编码
- 车辆编码
- 仓库 / 库位编码

### 6.2 状态口径

必须先锁：

- 销售订单状态
- 采购订单状态
- 出库任务状态
- 分拣 / 复核 / 装车状态
- 排线 / 派车 / 在途 / 签收 / 异常状态
- 收款 / 付款 / 对账 / 结账状态

### 6.3 模块主责边界

必须先锁：

- ERP 管账
- WMS 管实物
- TMS 管配送执行
- BI 管看板
- 既有物流域保留长期边界

---

## 7. 本期不建议直接开工的内容

在没有补数据库和接口清单前，不建议直接开始下面这些开发：

- 大规模新增字段
- 大规模建新表
- 跨模块状态自动回写
- 多模块接口直接对接
- BI 指标口径固化

原因：

- 这几类一旦先做，很容易把边界重新做乱

---

## 8. Verify

这份清单是否可执行，可以用下面 8 条检查：

1. 每项任务是否都有唯一主责模块
2. 每项任务是否都标明了复用 / 轻改 / 自建路径
3. 每项任务是否都写了前置依赖
4. 每项任务是否都能落到清晰产出物
5. 本期总纲中的 8 个功能块是否都有映射
6. 是否优先保障了 ERP 经营闭环，再推进 WMS / TMS 归位
7. 是否保留了既有物流域边界，而没有强行吞并
8. 是否能自然衔接到数据库清单和接口清单
