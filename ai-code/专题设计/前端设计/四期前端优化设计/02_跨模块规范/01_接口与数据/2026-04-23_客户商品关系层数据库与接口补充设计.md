## 当前补充结论

1. 商品建模采用分层口径：
   - `product.template`：全局商品主档
   - `logistics_product_unit`：规格 / SKU / 销售单位层
   - `logistics_customer_product_profile`：客户商品关系层
   - `goods_line`：运单货物执行层
2. `logistics_product_unit` 采用方案 B：
   - 一条记录只表达一个销售单位
   - 当前行只维护当前 `sale_unit_name` 自己的价格、条码、尺寸、重量、体积
   - 不再补回 `small_* / middle_* / large_*` 跨单位字段
3. `logistics_customer_product_profile` 不属于“商品画像表”，而是“客户商品关系表”。
4. 多个客户共享同一商品本体与同一 SKU，不再为每个客户重复录入商品长期属性。
5. 客户侧差异化规则通过关系层承接，而不是写回商品主档或执行层。

补充说明：

- 上述结论为后续目标态，不代表本期立即开发。

## 一、数据库新增对象

### 1. 新增表：`logistics_customer_product_profile`

建议模型：

- `_name = 'logistics.customer.product.profile'`
- `_table = 'logistics_customer_product_profile'`

### 2. 字段清单

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `partner_id` | Many2one | 是 | 关联客户 |
| `product_tmpl_id` | Many2one | 是 | 关联商品本体 |
| `product_unit_id` | Many2one | 是 | 关联销售单位 |
| `customer_product_code` | Char(64) | 否 | 客户侧商品编码 |
| `customer_product_name_alias` | Char(128) | 否 | 客户侧商品别名 |
| `default_signoff_requirement` | Text | 否 | 默认签收要求 |
| `default_package_requirement_text` | Text | 否 | 默认包装要求 |
| `default_temperature_zone` | Char(32) | 否 | 默认温层要求 |
| `allow_substitute_unit` | Boolean | 否 | 是否允许替代单位 |
| `min_delivery_qty` | Float | 否 | 最小配送数量 |
| `is_frequently_ordered` | Boolean | 否 | 是否常用商品 |
| `is_disabled` | Boolean | 否 | 是否停用 |
| `sort_order` | Integer | 否 | 展示顺序 |
| `relation_remark` | Text | 否 | 关系备注 |
| `company_id` | Many2one | 否 | 公司维度 |
| `active` | Boolean | 否 | 软停用 |

### 3. 唯一约束

推荐唯一约束：

```text
unique(partner_id, product_tmpl_id, product_unit_id)
```

原因：

- 当前首轮直接按“客户 + 商品 + 销售单位”落粒度最稳定
- 能明确表达客户默认订货单位
- 避免“客户只挂商品本体，但默认单位仍然不清楚”的歧义

### 4. 完整性要求

- 要求 `product_unit_id.product_tmpl_id = product_tmpl_id`
- 停用关系用 `is_disabled / active`，不直接删历史关系

### 5. 建议索引

- `idx_lcpp_partner_id(partner_id)`
- `idx_lcpp_product_tmpl_id(product_tmpl_id)`
- `idx_lcpp_product_unit_id(product_unit_id)`
- `idx_lcpp_partner_active_freq(partner_id, active, is_frequently_ordered)`
- 视搜索场景再补 `idx_lcpp_partner_customer_product_code(partner_id, customer_product_code)`

## 二、与 `logistics_product_unit` 的边界

`logistics_product_unit` 继续只负责：

- SKU / 规格
- 销售单位
- 换算关系
- 条码
- 价格
- 尺寸
- 重量
- 体积

不再负责：

- 某客户的默认订货单位偏好
- 某客户的签收要求
- 某客户的包装要求
- 某客户的温层要求
- 某客户的专属商品编码

## 三、与 `goods_line` 的边界

`goods_line` 继续只负责：

- 这次运单实际送了什么
- 送了多少
- 当时命中的商品 / 销售单位
- 为历史稳定保留必要快照

不再负责：

- 商品长期主数据维护
- 客户商品关系主数据维护

## 四、接口与导入补充

### 1. 新增 DTO 对象

推荐新增客户商品关系 DTO：

```json
{
  "partner_id": 2001,
  "product_tmpl_id": 1001,
  "product_unit_id": 3001,
  "customer_product_code": "KH-A-0001",
  "customer_product_name_alias": "矿泉水标准箱",
  "default_signoff_requirement": "需门店负责人签收",
  "default_package_requirement_text": "整箱配送，不拆零",
  "default_temperature_zone": "常温",
  "allow_substitute_unit": false,
  "min_delivery_qty": 1.0,
  "is_frequently_ordered": true,
  "is_disabled": false,
  "sort_order": 10,
  "relation_remark": ""
}
```

### 2. 导入补充口径

导入层建议同步拆分为：

- 商品本体导入
- 商品销售单位导入
- 客户商品关系导入

不要再尝试用一张表同时承载：

- 商品长期属性
- 多销售单位
- 客户侧默认规则
