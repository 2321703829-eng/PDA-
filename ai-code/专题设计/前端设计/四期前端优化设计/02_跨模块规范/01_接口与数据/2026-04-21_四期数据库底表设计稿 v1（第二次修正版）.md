## 文档定位

- 本文用于收口四期数据库底表设计。
- 当前版本已恢复多门店运单结构。

## 当前结论

1. 当前主结构恢复为 `wave -> batch -> waybill -> customer_line -> order_line -> goods_line`。
2. `customer_line` 重新作为门店节点主对象。
3. `customer_line_no` 重新作为稳定业务键之一。
4. `配送时间窗` 是文本字段，放在门店配送画像层。
5. `停靠点顺序` 不是门店稳定属性，首轮放在 `customer_line` 的运单内顺序快照字段中。
6. 司机事实归属层仍是 `batch`。
7. 商品层不设计 `shelf_life`，改设计 `delivery_requirement_text`。
8. 配送可达性/入场要求在导入表中允许多个布尔列铺开，但数据库中汇总为单字段编码串，不平铺大量布尔列。
9. 司机和车辆首轮只保留 `主档 + 画像扩展层`；当前调度状态层与历史业务记录层延期到后续版本设计。
10. `batch` 仍是执行主线中的司机/车辆当前执行事实来源，不新增独立的司机/车辆当前调度事实表。
11. 司机/车辆历史业务关联首轮不单独建表；后续若需要排线追溯或司机/车辆历史画像，再单独设计历史层。
12. `logistics_product_unit` 一条记录只表达一个销售单位，价格与条码改为单值字段，通过 `sale_unit_name` 识别小/中/大单位层级。
13. 门店配送地址同时保留 `address_full`、`longitude`、`latitude`，并新增 `address_region_json` 承接省/市/区/详细地址结构。
14. 客户经营属性和门店配送规则拆分为 `logistics_customer_profile` 与 `logistics_store_profile` 两层，不再混放。
15. 商品主数据后续规划按“商品本体层 + 规格/SKU层 + 客户商品关系层 + 执行层”分层，本期先不继续扩改数据库代码。
16. `logistics_customer_product_profile` 作为后续规划关系表保留在设计中，本期不正式建表。

### 关系说明

- `res.partner` 存门店稳定主档，`logistics_customer_profile` 存客户经营画像，`logistics_store_profile` 存门店配送画像，`customer_line` 存运单下门店快照。
- `product.template` 存商品稳定主档，`goods_line` 存订单下商品事实与经营数据快照。
- `logistics_product_unit` 是商品规格/SKU层，一条记录只表达一个销售单位，负责承接单位、换算、价格、尺寸、条码等规格级属性。
- `logistics_driver_profile` / `logistics_vehicle_profile` 承接司机和车辆的长期稳定主数据与画像字段。
- 司机与车辆当前执行事实仍只归属到 `batch`，`waybill` 不再形成第二套司机/车辆当前事实来源。
- 司机与车辆首轮不设计固定 1:1 绑定关系，也不提前落库调度状态层和历史关联层。
- 图片、留痕、证据首轮按 `customer_line` 作为最小业务挂点，运单层只做汇总和打包。

### 3. 字段类型、长度、默认值统一口径

| 字段类别 | Odoo 类型 | 数据库建议 | 长度/精度 | 默认值口径 |
| --- | --- | --- | --- | --- |
| 主业务编号/外部编码 | `fields.Char` | `varchar` | 64 | 无默认值 |
| 名称类 | `fields.Char` | `varchar` | 128，长名称可到 256 | 无默认值 |
| 证照号/卡号/条码 | `fields.Char` | `varchar` | 64 | 无默认值 |
| 手机/电话/微信号 | `fields.Char` | `varchar` | 32 | 无默认值 |
| 枚举状态 | `fields.Selection` | `varchar` | 32 | 统一枚举默认值 |
| 布尔标记 | `fields.Boolean` | `boolean` | 无 | 默认 `False`，特殊状态表按文档另定 |

| 时间戳 | `fields.Datetime` | `timestamp` | 无 | 无默认值 |

| 金额 | `fields.Monetary` | `numeric` | `16,2` | 默认 `0` |
| 数量 | `fields.Float` | `numeric` | `16,4` | 默认 `0` |
| 重量/体积 | `fields.Float` | `numeric` | `16,6` | 默认 `0` |
| 费率/比例 | `fields.Float` | `numeric` | `8,4` | 默认 `0` |
| 经纬度 | `fields.Float` | `numeric` | `10,7` | 默认空 |
| 结构化地址 JSON | `fields.Json` | `jsonb` | 无 | 默认空对象或空 |
| 备注/说明/地址 | `fields.Text` | `text` | 不限 | 默认空字符串仅用于确需摘要字段 |
| Many2one | `fields.Many2one` | `bigint` | 无 | 默认空 |

补充规则：

- `receive_start_time`、`receive_end_time` 首轮按 `varchar(16)` 存 `HH:MM`，避免不同来源时间格式在首轮导入阶段放大兼容风险。
- `amount`、`settled_amount`、`unsettled_amount`、`tax_amount`、`amount_ex_tax`、`cost_amount`、`gross_profit`、`parking_fee_per_hour` 统一按金额精度 `16,2`。
- `base_qty`、`doc_qty`、`small_qty`、`box_qty`、`gift_qty`、`exchange_qty`、`approved_load_ton` 统一按数量精度 `16,4`。
- `unit_weight`、`total_weight`、`default_weight`、`weight`、`unit_volume`、`total_volume`、`default_volume`、`volume`、`approved_volume_m3` 统一按重量/体积精度 `16,6`。

### 6. 编号与 sequence 规则

- 使用独立业务编号的表：
  - `logistics.dispatch.wave.wave_no`
  - `logistics.dispatch.batch.batch_no`
  - `logistics.dispatch.waybill.waybill_no`
  - `import_source_file.source_file_no`
  - `import_task.task_no`
- 不使用独立业务编号、只使用 `id` + 业务组合键的表：
  - 所有扩展表
  - `customer_line / order_line / goods_line`
  - `import_task_line / import_error_line`
  - `master_data_change_log`
- 历史表规则：
  - 首轮不单独生成 `history_no`
  - 以 `id` + 组合唯一键作为追溯依据
- 日志表规则：
  - `import_source_file` 和 `import_task` 使用独立 sequence
  - `import_task_line.line_no` 只在同一 `task_id` 内递增，不走全局 sequence

## 六、设计原则

1. 优先复用 Odoo 原生对象：
   - 门店主档优先复用 `res.partner`
   - 商品主档优先复用 `product.template`
   - 司机主档优先复用 `hr.employee`
   - 车辆主档优先复用 `fleet.vehicle`
2. 稳定主数据和业务快照分开。
3. 一个字段尽量只有一个主要事实归属层。
4. 首轮先满足导入、查询、展示和执行，不提前为少量边缘场景做重结构。

## 六点五、配送可达性字段设计

### 设计结论

- 导入模板层可以继续保留多个布尔字段铺开，便于业务填写。
- 数据库存储层不平铺大量 `0/1` 字段，统一汇总到一个编码字段中。
- 主数据层和快照层都保留该字段：
  - `logistics_store_profile.delivery_access_flags`
  - `logistics.dispatch.waybill.customer.line.delivery_access_flags_snapshot`
- `上楼层数` 与 `地库限高` 不纳入 `delivery_access_flags`，单独结构化存储。

### 建议命名

| 系统字段（左） | 含义（右） |
| --- | --- |
| `delivery_access_flags` | 门店长期配送可达性要求编码串 |
| `delivery_access_flags_snapshot` | 本次运单下门店节点的配送可达性要求编码串快照 |

### 导入模板建议字段

以下字段保留在导入表中按布尔值铺开：

- `小巷子`
- `连停`
- `手推车`
- `托盘置换`
- `保温箱置换`
- `是否送货上门`
- `是否无电梯`

后续如果业务新增同类字段，也按同样模式扩展导入层，不直接扩展数据库字段列数。

以下字段不再放入布尔编码串，建议单独结构化：

- `上楼层数`
- `地库限高`

### 汇总规则

导入模块读取上述布尔字段后，统一汇总写入单字段编码串。

建议首轮编码：

| 导入字段（左） | 汇总编码（右） |
| --- | --- |
| `小巷子` | `alley` |
| `连停` | `continuous_stop` |

| `是否送货上门` | `door_delivery` |

存储格式建议：

- 使用 `|` 分隔
- 示例：`alley|handcart|door_delivery`
- 空值表示无特殊配送可达性要求

### 说明

- 该设计兼顾了业务填写体验和数据库结构可控性。
- `上楼层数` 采用数值字段承接，不再通过布尔字段间接表达。

- 若后续需要做精细规则引擎或复杂统计，再考虑升级为字典表或关系表。

## 十、当前仍需注意的边界

1. `配送时间窗` 已按文本字段设计，但其格式规则后续仍需单独补约束说明。
2. `停靠点顺序` 当前按 `customer_line` 的运单内顺序设计；若后续批次重排与多次重派变复杂，再评估是否升级为独立的批次-门店关系层。
3. `driver_employee_id` 在 `waybill` 侧仅保留 related/store 型字段，不应再形成第二套司机事实来源。
4. 商品配送需求当前先按主商品层承接，若后续规格级差异明显，再启用规格层覆盖字段。
5. 配送可达性/入场要求当前采用“导入多列布尔、数据库单字段汇总”的策略，首轮不在数据库中平铺大量布尔列。
6. 周维度配送周期当前采用“导入 7 列布尔、数据库单字段汇总”的策略，首轮只作为门店画像和排线参考，不作为强业务约束。
7. 司机夜班意愿属于司机画像层稳定字段，首轮以 `logistics_driver_profile.allow_night_shift` 为准，不在批次和运单层重复快照。
8. 司机/车辆当前待命仓、当前是否可调度等字段首轮暂不落库；若后续排线筛选需要，再补调度状态层。
9. 司机/车辆历史业务记录层首轮暂不建表；若后续需要阅读司机/车辆历史关联，再从 `batch / waybill / order_line` 主链需求反推设计。
10. `客户状态`、`是否允许货到付款`、`内部往来单位` 等字段属于客户经营画像层，不应混入门店配送画像层，也不应在 `customer_line` 首轮重复快照。
11. `开始收货时间`、`停车位置`、`卸货入口` 等到店规则属于门店配送画像层长期字段；首轮除非业务明确支持按单覆盖，否则不在运单层形成第二套事实来源。
12. 门店结构化地址建议统一写入 `address_region_json`，键名统一用 `province` / `city` / `district` / `detail`，避免后续接口多套命名。

## 十二点五、查询模型清单

### 1. 页面查询模型

- 运单列表页
  - 主查 `waybill`
  - 常用筛选：`waybill_no`、`batch_id`、`delivery_date`、`driver_employee_id`、`warehouse_name_snapshot`
- 运单详情页
  - 主查 `waybill`
  - 联查 `customer_line`
  - 汇总展示 `order_line`、图片、留痕、证据
- 门店节点阅读区
  - 主查 `customer_line`
  - 联查 `waybill`、`order_line`
  - 读取 `delivery_access_flags_snapshot`、经纬度、顺序、签收要求
- 订单阅读区
  - 主查 `order_line`
  - 联查 `goods_line`
  - 展示订单快照 + 商品展示快照
- 商品明细阅读
  - 主查 `goods_line`
  - 联查 `product.template`、`logistics_product_unit`

### 2. 接口查询模型

- 列表接口优先返回快照字段，不要求前端再联主数据拼装
- 详情接口允许同时返回：
  - 主对象
  - 直接下级对象
  - 必要汇总字段
- 导出接口优先走快照字段和冗余展示字段，避免导出时深度联表

### 3. 报表查询模型

- 司机工作量
  - 建议主维度：`batch`、`waybill`、`customer_line`
- 司机画像查询
  - 主查 `logistics_driver_profile`
  - 联查 `hr.employee`
  - 常用筛选：`allow_night_shift`、`driver_license_level`、`major_accident_record_flag`
- 车辆画像查询
  - 主查 `logistics_vehicle_profile`
  - 联查 `fleet.vehicle`
  - 常用筛选：`approved_load_ton`、`approved_volume_m3`、`operation_type`
- 当前司机/车辆执行阅读
  - 主查 `batch`
  - 联查 `hr.employee`、`fleet.vehicle`
  - 当前执行事实不从独立调度状态表读取
- 门店配送频次
  - 建议主维度：`customer_line.partner_id` + `delivery_date`
- 商品销量
  - 建议主维度：`external_product_code_snapshot`
  - 同时保留按 `base_unit_name` 统一口径的能力
- 订单金额分析
  - 建议主维度：`order_line`
  - 金额事实取自 `goods_line`

### 4. 查询设计结论

- 页面和接口的主阅读链优先走快照层：
  - `waybill -> customer_line -> order_line -> goods_line`
- 主数据层主要用于命中、补全、字典和画像，不作为首轮页面主联表中心。

## 十三、状态枚举设计

### 1. 支付状态 `payment_status`

### 3. 结算状态 `settlement_status`

- `unsettled` ← 未结算
- `partial_settled` ← 部分结算
- `settled` ← 已结算

### 4. 单据状态 `doc_status`

- `draft` ← 草稿
- `confirmed` ← 已确认
- `cancelled` ← 已取消

### 5. 物流状态 `logistics_status`

- `pending_outbound` ← 待出库

## 十四、写入边界设计

### 1. 主数据优先命中

导入时先尝试命中：

- `res.partner`
- `logistics_customer_profile`
- `logistics_store_profile`
- `product.template`
- `logistics_product_unit`
- `hr.employee`
- `fleet.vehicle`

命中成功后：
- 可复用主数据主键
- 同时写入本次业务快照层

### 2. 快照层不反向覆盖主数据

以下对象属于业务快照层：

- `waybill`
- `customer_line`
- `order_line`
- `goods_line`

原则：
- 导入写入快照层后，不自动反向覆盖主数据
- 主数据修订应通过专门主数据维护流程完成

### 3. 主数据为空时的兜底规则

- 若门店主数据未命中：
  - 允许先落 `customer_line` 快照
- 若商品主数据未命中：
  - 允许先落 `goods_line` 快照
- 但必须保留外部编码和原始名称，便于后续补命中

### 4. 字段来源单一原则

- 司机主事实来源：`batch.driver_employee_id`
- 车辆主事实来源：`batch.vehicle_id`
- 客户等级、客户状态、货到付款规则、内部往来单位、发票类型、注册信息、客户序号：`logistics_customer_profile`
- 司机排线夜班意愿：`logistics_driver_profile.allow_night_shift`
- 门店收货时间、停车规则、卸货规则：`logistics_store_profile`
- 门店长期配送可达性：`logistics_store_profile.delivery_access_flags`
- 本次门店配送可达性快照：`customer_line.delivery_access_flags_snapshot`
- 门店默认配送周期：`logistics_store_profile.delivery_week_flags`
- 门店默认上楼层数：`logistics_store_profile.upstairs_floor_count`
- 门店默认地库限高说明：`logistics_store_profile.basement_height_limit_text`
- 门店配送时间窗展示摘要：`logistics_store_profile.delivery_window_text`
  - 若已维护 `receive_start_time` / `receive_end_time` / `receive_time_slots_text`，则 `delivery_window_text` 只作展示摘要，不再作为第二事实来源
- 默认送货联系电话：`res.partner.contact_phone`
- 默认配送地址：`res.partner.address_full`
- 默认配送坐标与结构化地址：`logistics_store_profile.longitude` / `latitude` / `address_region_json`
- 本次门店地址快照：`customer_line.address_full_snapshot` / `longitude_snapshot` / `latitude_snapshot` / `address_region_json_snapshot`
- 注册电话：`logistics_customer_profile.registered_phone`
- 注册地址：`logistics_customer_profile.registered_address`
- 商品稳定配送要求：`product.template.delivery_requirement_text`

## 十五点五、敏感字段与权限边界

### 1. 敏感字段分级

- 一级敏感
  - `contact_phone`
  - `registered_phone`
  - `driver_phone`
  - `id_card_no`
  - `bank_card_no`
- 二级敏感
  - `address_full`
  - `registered_address`
  - `current_address`
  - `driver_license_no`
  - 经纬度
- 三级敏感
  - 金额、成本、毛利类字段

### 2. 默认权限建议

- 运营/调度
  - 可看运单、门店节点、订单、图片
  - 默认不看完整成本和毛利
- 财务
  - 可看金额、结算、支付、成本、毛利
- 司机端/轻终端
  - 只看本次配送必要字段
  - 不下发成本、毛利、敏感审计信息
- 管理员
  - 可看全部字段

### 3. 导出权限建议

- 联系电话、地址、金额、成本、毛利相关字段应支持按角色控制是否导出
- 图片导出应保留操作审计记录

### 4. 设计结论

- 敏感字段不仅要在接口层控制，也要在数据库设计稿中提前标注分类
- 后续若出接口专题稿，应继承本文权限分级，不再重新定义冲突口径

### 2. `CHECK` 约束建议清单

- 数量/统计类
  - `free_parking_minutes >= 0`
  - `upstairs_floor_count >= 0`
  - `upstairs_floor_count_snapshot >= 0`
  - `total_count >= 0 and success_count >= 0 and fail_count >= 0`
  - `success_count + fail_count <= total_count`
- 金额/重量/体积类
  - `parking_fee_per_hour >= 0`
  - 货物金额、税额、成本、重量、体积字段首轮统一要求 `>= 0`
- 布尔/状态类
  - `customer_status in ('normal','disabled','frozen')`
  - `import_task.status in ('pending','running','success','partial_failed','failed','cancelled')`
  - `import_task_line.status in ('pending','success','failed','skipped')`

说明：

- `Selection` 字段首选 Odoo 层兜底校验，数据库层 `CHECK` 作为二次保险
- `receive_start_time <= receive_end_time` 因首轮按 `varchar(16)` 存储，建议先在 Odoo `@api.constrains` 层校验

### 4. 不建议直接做普通索引的字段

- `address_full` / `registered_address` / `current_address`
- `delivery_window_text` / `receive_time_slots_text` / `no_receive_time_slots_text`
- `parking_location_text` / `parking_mode_text` / `unload_entrance_text` / `unload_location_text`
- `order_remark` / `line_remark`
- `raw_value` / `mapped_value` / `error_message`

这些字段若后续需要检索，优先走全文检索、专门检索表或条件缩小后查询，不建议首轮直接建普通 B-Tree 索引。
