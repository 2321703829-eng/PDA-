# 2026-04-24 四期司机侧导出模块设计方案

## Objective

- 设计一套面向司机阅读的导出能力，用于排线后帮助司机快速理解线路、停靠顺序、客户需求和卸货注意事项。
- 在保持与现有物流导出模块风格一致的前提下，避免把“标准数据导出”误当成“司机阅读包”。
- 尽可能复用现有导入/标准导出模块的任务链、结果页、任务编号和下载机制，但输出内容以“阅读效率”优先，不以“可再导入”优先。

## Boundary

- 本文讨论的是司机侧阅读导出，不替代标准数据导出。
- 本文首轮只覆盖排线后阅读和打印诉求，不扩展为司机移动端在线作业系统。
- 本文首轮不做图片二进制打包导出，不并入图片包导出链。
- 本文不直接进入编码实现，先冻结对象、输出内容、任务链和页面入口。

## OBB

### Outcome

- 系统支持在排线完成后，为司机生成一份可直接阅读的线路导出包。
- 司机侧导出包能回答 4 个核心问题：
  - 今天跑哪条线路
  - 先送谁后送谁
  - 每个客户有什么特殊收货要求
  - 每个停靠点大概要送什么、送多少
- 导出任务继续围绕 `task_no` 运转，并复用导出结果页和下载机制。

### Behavior

- 调度或运营人员可从批次执行入口发起司机侧导出。
- 系统异步生成司机阅读包，并在结果页展示任务摘要、成功/失败情况和下载入口。
- 下载结果优先是可打印、可转发、司机能直接看懂的阅读文件，而不是结构化宽表。

### Boundary

- 首轮不把司机侧导出设计成“可再导入模板”。
- 首轮不要求从司机管理页直接发起，因为当前首轮范围并未以司机调度状态表作为稳定主入口。
- 首轮不承诺“司机个人维度全局导出”，而是先围绕批次执行链落地。
- 波次和运单入口后续再补，不作为首轮正式承诺。

## Benchmark

### Odoo 原生可复用能力

- Odoo 原生 `ir.actions.report` / QWeb PDF 适合承接可打印阅读包。
- Odoo 原生列表导出适合字段导出，不适合承接司机阅读导出。

### 当前项目已有可复用基线

- 标准导出任务链和结果页设计已经成型。
- 四 Sheet 正式导出已经明确定位为“标准数据导出”。
- 批次、运单、客户/门店画像字段已经能从当前模型读取到较完整的线路和收货要求信息。

### 路径选择

- 不复用标准导出文件结构作为司机阅读文件。
- 复用“任务链、结果页、下载入口”，但单独定义司机阅读文件结构。
- 输出方式优先考虑 `PDF`，而不是继续扩展 `xlsx`。

## Current Understanding

你已经明确指出：司机侧真正需要的不是“数据齐不齐”，而是“看得快不快、读得懂不懂”。因此司机侧导出必须和标准导出分层：

1. 标准导出  
面向运营、客服、数据修订、回传再导入。  
特点是结构完整、层级严格、表头规范。

2. 司机侧导出  
面向排线后执行阅读。  
特点是信息压缩、顺序明确、提醒突出、适合打印和转发。

所以这套司机侧导出，不能再沿用四 Sheet 思路做文件主体，否则仍然是“数据包”，不是“阅读包”。

## 1. 正式定位

### 1.1 模块定位

司机侧导出是独立于标准导出的第二条导出线：

- 标准导出：`standard_export`
- 司机侧导出：`driver_route_export`

两者关系：

- 任务机制尽量一致
- 页面节奏尽量一致
- 文件内容和目标用户不同

### 1.2 目标用户

首轮目标用户不是司机本人在线操作，而是：

- 调度员
- 运营人员
- 现场管理人员

他们生成导出包后，可通过打印、微信转发、文件分发等方式交给司机阅读。

### 1.3 核心阅读对象

司机侧导出包首轮围绕这条阅读主线展开：

```text
线路/批次 -> 运单 -> 停靠客户 -> 客户需求 -> 货物摘要
```

注意：

- 这里不是正式数据层级定义
- 这是司机的阅读顺序定义

## 2. 导出入口设计

### 2.1 首轮正式入口

首轮正式入口只保留：

- `from_batch`

原因：

1. 批次是排线后的执行组织层，最适合生成“当天线路阅读包”。
2. 批次入口最接近调度实际发包动作，司机阅读包也最适合按批次分发。
3. 先把批次入口做稳，再补波次和运单入口，范围更可控。

### 2.2 为什么首轮不做波次、运单和司机入口

- `from_wave`
  当前不作为首轮入口，因为波次更偏调度组织层，司机实际拿到的阅读包更接近批次执行包。
- `from_waybill`
  后续可补，用于局部补打或单运单重导出，但不作为首轮前置能力。
- `from_driver`
  当前首轮范围里，司机/车辆调度状态表与历史表并不是已落稳的正式执行入口，因此不建议首轮直接承诺。

## 3. 输出文件设计

### 3.1 正式输出格式

首轮正式输出格式建议为：

- `PDF`

原因：

1. 司机阅读包优先服务“看”和“打印”，不是“编辑”。
2. PDF 更适合手机查看、打印、转发。
3. 能更稳定地控制版式层级、重点提示和分页。

### 3.2 PDF 内容结构

首轮建议采用“一个批次一份 PDF”的设计，内部按固定阅读顺序编排：

1. 封面摘要页  
显示配送日期、批次号、线路名称、仓库、司机、客户数、总件数、总重量、总备注。

2. 停靠顺序总览页  
按停靠顺序列出所有客户，帮助司机先建立整条线路的顺序感。

3. 客户需求卡页  
每个客户一块卡片，集中展示收货时间、停车、上楼、限高、卸货位置等需求。

4. 货物摘要页  
按客户或停靠点汇总总件数、总重量、总体积和重点货品摘要。

版式上我建议：

- A4 纵向，适合打印
- 手机转发时也能顺序阅读
- 每个客户需求卡尽量保持一屏或一页内完成
- 重点提醒字段用标签化样式，而不是长段文字

### 3.3 PDF 页面草图

为了让后续实现时不再停留在“有 4 个区块”的抽象层，首轮建议直接按下面的页面草图落版：

#### 第 1 页：封面摘要页

页面目标：

- 让司机一眼知道“今天这趟车是谁、跑哪条线、总共有几站、货量大概多少”

页面结构：

- 顶部标题区
  - 标题：`司机线路包`
  - 副标题：`配送日期 + 批次号`
- 中部摘要卡区
  - 第一行：线路名称、仓库、组织
  - 第二行：司机姓名、司机电话
  - 第三行：运单数、客户数、总件数、总重量、总体积
- 底部提醒区
  - 发车提醒
  - 线路总备注

#### 第 2 页：停靠顺序总览页

页面目标：

- 让司机先建立整条线路的顺序感，不进入细节前先看完整路径

页面结构：

- 顶部页头
  - 批次号
  - 线路名称
  - 页名：`停靠顺序总览`
- 主体为顺序表
  - 每行一站
  - 按送货顺序升序展示
- 每行右侧保留重点标记位
  - 有无时间窗
  - 有无停车/卸货重点要求
  - 有无上楼/限高要求

#### 第 3 页及后续：客户需求卡页

页面目标：

- 到每一个客户时，司机能快速看到“这站要注意什么”

页面结构：

- 每页建议放 `1-2` 张客户卡
- 每张客户卡分 4 个小区：
  - 基础信息区
  - 时间窗区
  - 停车/卸货区
  - 备注/提醒区

分页规则：

- 单个客户卡尽量不跨页
- 如果备注过长，备注单独续到下一页的“补充备注区”

#### 最后一页：货物摘要页

页面目标：

- 让司机对每站的大致货量和重点货物有数

页面结构：

- 顶部页头
  - 批次号
  - 页名：`货物摘要`
- 主体为按客户分组的摘要块
  - 客户头部
  - 数量重量体积汇总
  - 重点货品摘要
  - 装卸提醒

### 3.5 重点样式建议

司机阅读包不应只是把字段排出来，还要有明确的视觉优先级。首轮建议：

- `线路名称 / 批次号 / 送货顺序` 用大字号粗体
- `开始收货时间 / 截止收货时间 / 不收货时间段` 用时间标签样式
- `上楼层数 / 地库限高 / 停车位置 / 卸货入口` 用风险提醒标签样式
- `手推车 / 托盘置换 / 保温箱置换` 用是/否图标或高亮短标签
- `客户/门店备注` 限制为短段文本，不在正文出现大段说明墙

### 3.6 分页与截断规则

首轮建议明确下面几条规则：

1. 封面摘要页固定 1 页，不与后续页混排。
2. 停靠顺序总览页允许跨页，但表头必须在新页重复。
3. 客户需求卡尽量整卡不拆页。
4. 备注字段超过限定长度时：
   - 正文保留前半段
   - 超出部分进入“补充备注区”
5. 货物摘要页不强求展示全量货品明细，只保留摘要。

### 3.8 低保真示意图使用规则

为了避免后续实现时“结构回改”，首轮建议把这些示意图作为固定约束：

1. 封面摘要页必须独立成页。
2. 停靠顺序页必须是表格式，不改成卡片流。
3. 客户需求页必须以卡片为主，不改成纯表格。
4. 货物摘要页必须按客户或停靠点分组，不改成全局货物长表。
5. 补充备注页只在有超长备注时出现，没有备注则不生成。

### 3.3 是否附带 Excel

首轮不强制附带 Excel。

如果后续业务需要，可在任务完成后提供：

- 主下载：司机阅读 PDF
- 补充下载：标准数据 Excel

但这不是首轮前置要求。

建议：

## 4. 司机侧导出包结构

首轮建议固定为 4 个阅读区块，按阅读顺序排版。

### 4.1 区块一：线路总览

回答“今天这一趟到底是什么”。

建议包含：

- 配送日期
- 批次号
- 线路名称
- 仓库
- 组织
- 司机姓名
- 司机电话
- 运单数
- 客户数
- 总件数
- 总重量
- 总体积
- 发车提醒
- 总备注

### 4.2 区块二：停靠顺序清单

回答“先送谁后送谁”。

建议按停靠顺序列出：

- 送货顺序 / 停靠顺序
- 运单号
- 客户名称
- 门店名称
- 联系人
- 联系电话
- 完整地址
- 收货时间窗

- 当前停靠备注

### 4.3 区块三：客户需求卡

回答“到这个客户这里要特别注意什么”。

每个客户一张需求卡，建议包含：

- 客户名称
- 门店名称
- 联系人
- 联系电话
- 地址
- 开始收货时间
- 截止收货时间

- 不收货时间段
- 是否允许货到付款
- 上楼层数
- 地库限高
- 停车位置
- 停车方式
- 免费停车时长
- 停车费
- 卸货入口
- 卸货位置
- 是否需手推车
- 是否托盘置换
- 是否保温箱置换
- 其他配送备注

### 4.4 区块四：货物摘要

回答“每站大概要送什么、送多少”。

这里不建议把完整订单明细原样平铺给司机，而是以停靠客户为粒度做摘要：

- 客户名称
- 运单号
- 商品总行数
- 总件数
- 总重量
- 总体积
- 重点商品摘要
- 装卸提醒

说明：

- 首轮的“重点商品摘要”不要求全量列出所有货物行
- 可优先按前 N 个关键货品、数量汇总或异常标记输出
- 若业务后续坚持“司机必须看完整货物行”，再加附页

## 5.4 首轮字段来源说明

为了避免后续实现时“PDF 字段要了，但不知道从哪里取”，首轮字段来源建议明确如下：

- 批次号：`logistics.dispatch.batch.name`
- 线路名称：优先 `logistics.dispatch.batch.route_name_snapshot`，必要时补读 `waybill.route_name_snapshot`
- 运单号：`logistics.dispatch.waybill.name`
- 客户名称 / 门店名称 / 联系人 / 联系电话 / 地址：
  优先 `logistics.dispatch.waybill.customer.line` 的快照字段，缺失时回读 `res.partner`
- 送货顺序 / 停靠顺序：`logistics.dispatch.waybill.customer.line.stop_seq_in_waybill`
- 开始收货时间 / 截止收货时间 / 收货时间段 / 不收货时间段：
  `res.partner.receive_start_time / receive_end_time / receive_time_slots_text / no_receive_time_slots_text`
- 上楼层数 / 地库限高：
  优先 `customer_line` 快照，缺失时回读 `res.partner`
- 停车位置 / 停车方式 / 卸货入口 / 卸货位置：
  `res.partner.parking_location_text / parking_mode_text / unload_entrance_text / unload_location_text`
- 手推车 / 托盘置换 / 保温箱置换：
  首轮按导入口径从配送可达性字段或映射结果读取
- 客户/门店备注：
  优先 `customer_line.delivery_note`，必要时补读客户服务备注
- 总件数 / 总重量 / 总体积：
  优先按 `customer_line` 汇总字段读取

## 5.5 字段缺失与降级展示规则

司机阅读包不是内部调试页，因此字段缺失时不能直接把原始空值裸露给司机，也不能因为个别字段缺失就让整份 PDF 失去阅读价值。首轮建议采用“能展示就展示，不能展示就明确降级”的处理原则。

### A. 主信息字段

- `批次号`
  - 若缺失：该批次阅读包不生成，任务行记为 `failed`
  - 原因：这是整份 PDF 的最小主键，不能缺
- `线路名称`
  - 若缺失：降级显示为 `未配置线路名称`
  - 同时在封面摘要页追加提示：`请调度补齐线路名称`
- `运单号`
  - 若客户卡所在记录无法关联运单号：该客户块不进入正文，任务错误明细记录为数据缺失

### B. 客户识别字段

- `客户名称`
  - 优先读客户快照
  - 若缺失：降级读门店名称
  - 若仍缺失：显示 `未命名客户`
- `门店名称`
  - 若缺失：与客户名称相同则可不重复显示
  - 若客户名称也缺失：显示 `未命名门店`
- `联系人`
  - 若缺失：显示 `未留联系人`
- `联系电话`
  - 若缺失：显示 `未留联系电话`
  - 不阻塞 PDF 生成
- `地址`
  - 若缺失：该客户块继续生成，但显示 `地址缺失`
  - 同时在停靠顺序页和客户需求卡都打 `地址缺失` 标签
  - 若同批次地址缺失客户超过设定阈值，可把整批次任务记为 `partial_failed`

### C. 顺序与时间字段

- `送货顺序 / 停靠顺序`
  - 优先读 `stop_seq_in_waybill`
  - 若缺失或为 `0`：按批次内读取顺序临时补排，并加 `顺序待确认` 标签
- `开始收货时间`
  - 若缺失：显示 `未设开始时间`
- `截止收货时间`
  - 若缺失：显示 `未设截止时间`
- `收货时间段`
  - 若缺失：若存在开始/截止时间，则拼出 `开始时间 - 截止时间`
  - 若仍无法生成：显示 `未设收货时间段`
- `不收货时间段`
  - 若缺失：显示 `无`

### D. 配送要求字段

- `上楼层数`
  - 若缺失：显示 `未知`
- `地库限高`
  - 若缺失：显示 `未知`
- `停车位置`
  - 若缺失：显示 `未说明`
- `停车方式`
  - 若缺失：显示 `未说明`
- `卸货入口`
  - 若缺失：显示 `未说明`
- `卸货位置`
  - 若缺失：显示 `未说明`
- `手推车`
  - 若无法反解：显示 `未知`
- `托盘置换`
  - 若无法反解：显示 `未知`
- `保温箱置换`
  - 若无法反解：显示 `未知`
- `客户/门店备注`
  - 若缺失：不显示空白大块，直接省略备注正文

### E. 汇总字段

- `总件数`
  - 若缺失：显示 `待补汇总`
- `总重量`
  - 若缺失：显示 `待补汇总`
- `总体积`
  - 若缺失：显示 `待补汇总`

说明：

- 汇总字段缺失不应阻塞整份 PDF
- 但在封面摘要页和货物摘要页需要明确区分“真实为 0”和“未汇总成功”

### F. 任务级降级规则

- 单个客户字段缺失
  - 默认不阻塞整批次 PDF 生成
  - 通过标签和错误明细提醒
- 多个客户出现关键字段缺失
  - 任务状态可降级为 `partial_failed`
- 批次级主信息缺失
  - 如批次号无法识别，则整任务失败

### G. 文案规范

首轮建议统一使用下面这套降级文案，避免不同页出现不同写法：

- `未配置线路名称`
- `未命名客户`
- `未命名门店`
- `未留联系人`
- `未留联系电话`
- `地址缺失`
- `顺序待确认`
- `未设开始时间`
- `未设截止时间`
- `未设收货时间段`
- `无`
- `未知`
- `未说明`
- `待补汇总`

## 5.6 重点标签生成规则

司机阅读包里不应该把所有字段原样堆给司机，而应该把最重要的执行风险压缩成短标签。首轮建议把标签分成“时间类”“通行类”“卸货类”“异常提示类”四组。

### A. 时间类标签

- `限时`
  - 命中条件：
    - 存在 `开始收货时间` 或 `截止收货时间`
    - 或存在 `收货时间段`
  - 展示位置：
    - 停靠顺序页
    - 客户需求卡页
- `禁收时段`
  - 命中条件：
    - `不收货时间段` 非空
  - 展示位置：
    - 停靠顺序页
    - 客户需求卡页

### B. 通行类标签

- `上楼`
  - 命中条件：
    - `上楼层数 > 0`
- `限高`
  - 命中条件：
    - `地库限高` 非空
- `停车关注`
  - 命中条件：
    - `停车位置` 非空
    - 或 `停车方式` 非空
- `需手推车`
  - 命中条件：
    - `手推车 = 是`
- `托盘置换`
  - 命中条件：
    - `托盘置换 = 是`
- `保温箱置换`
  - 命中条件：
    - `保温箱置换 = 是`

### C. 卸货类标签

- `指定卸货口`
  - 命中条件：
    - `卸货入口` 非空
- `指定卸货位`
  - 命中条件：
    - `卸货位置` 非空
- `货到付款`
  - 命中条件：
    - `是否允许货到付款 = 是`

### D. 异常提示类标签

- `地址缺失`
  - 命中条件：
    - `地址` 为空
- `电话缺失`
  - 命中条件：
    - `联系电话` 为空
- `顺序待确认`
  - 命中条件：
    - `送货顺序 / 停靠顺序` 缺失后被系统临时补排
- `汇总待补`
  - 命中条件：
    - `总件数 / 总重量 / 总体积` 任一为 `待补汇总`

### E. 标签生成优先级

为了避免标签过多导致司机反而看不懂，首轮建议每个客户在停靠顺序页最多显示 `3` 个重点标签，优先级如下：

1. `地址缺失 / 电话缺失 / 顺序待确认`
2. `限时 / 禁收时段`
3. `上楼 / 限高`
4. `指定卸货口 / 指定卸货位`
5. `需手推车 / 托盘置换 / 保温箱置换`
6. `停车关注 / 货到付款 / 汇总待补`

说明：

- 停靠顺序页只展示最重要的少量标签，目的是快速扫读。
- 客户需求卡页可以展示完整标签组，不受 `3` 个限制。

### F. 标签文案规范

首轮建议统一使用以下短标签，不要在 PDF 正文里混用长短不同的说法：

- `限时`
- `禁收时段`
- `上楼`
- `限高`
- `停车关注`
- `需手推车`
- `托盘置换`
- `保温箱置换`
- `指定卸货口`
- `指定卸货位`
- `货到付款`
- `地址缺失`
- `电话缺失`
- `顺序待确认`
- `汇总待补`

### G. 标签展示规则

- 停靠顺序页：
  - 只显示高优先级短标签
  - 标签按优先级从左到右排列
- 客户需求卡页：
  - 在卡片头部显示完整标签条
  - 详细字段仍保留在正文
- 货物摘要页：
  - 只保留与装卸直接相关的标签，如 `上楼`、`限高`、`需手推车`

## 5.7 同批次内客户排序规则

司机阅读包的核心不是“数据全”，而是“顺序不能乱”。因此同批次内客户展示顺序首轮必须固定，不能由导出时的随机读取顺序决定。

### A. 首选排序键

首轮统一以：

- `logistics.dispatch.waybill.customer.line.stop_seq_in_waybill`

作为同批次内客户排序的第一优先级。

这条规则适用于：

- 停靠顺序总览页
- 客户需求卡页
- 货物摘要页

也就是说，这三部分都必须使用同一套客户顺序，不能各页各排。

### B. 排序规则

首轮建议固定为以下排序链：

1. `stop_seq_in_waybill` 升序
2. `waybill.route_seq` 升序
3. `waybill_no` 升序
4. `customer_line_no` 升序
5. `id` 升序

说明：

- 第一优先级永远是 `stop_seq_in_waybill`
- 只有在顺序相同、缺失或冲突时，才进入后续兜底排序

### C. 缺失值处理

- 若 `stop_seq_in_waybill` 为空或为 `0`
  - 该客户仍参与导出
  - 但视为“顺序待确认”
  - 排序时放在已明确顺序客户之后
- 若多个客户的 `stop_seq_in_waybill` 相同
  - 不阻塞 PDF 生成
  - 按兜底排序链继续排
  - 同时给这些客户打 `顺序待确认` 标签

### D. 展示口径

- 停靠顺序总览页
  - 展示的是最终排序后的连续序号
- 客户需求卡页
  - 卡片头部展示同一套连续序号
- 货物摘要页
  - 分组顺序必须与前两页一致

说明：

- 页面展示的顺序号可以是重新编号后的 `01 / 02 / 03`
- 但底层排序依据仍然优先来自 `stop_seq_in_waybill`

### E. 任务级提示

若同一批次内出现以下情况，任务可降级为 `partial_failed` 或至少给出明显提醒：

- 超过阈值数量的客户 `stop_seq_in_waybill` 缺失
- 多个客户顺序号重复
- 同批次内顺序号出现明显异常断层且无法确认

### F. 一句话结论

首轮司机阅读包的客户排序规则统一为：

- 优先按 `stop_seq_in_waybill` 排
- 缺失或冲突时再按运单与客户键兜底

## 5.8 批次内多运单展示规则

司机阅读包面向的是执行阅读，而不是数据库分层阅读。因此当一个批次内包含多个运单时，首轮不建议按“运单一块、运单一块”拆开给司机看，而应统一按停靠点顺序给司机展示。

### A. 核心原则

首轮固定采用：

- 批次内多运单统一合并阅读
- 统一按停靠点顺序字段排列
- 运单号作为辅助识别字段保留，但不作为主阅读分组

一句话就是：

- 司机先看“下一站是谁”，不是先看“下一张运单是什么”

### B. 页面展示规则

- 停靠顺序总览页
  - 直接把同批次下所有运单的客户停靠点混排到同一张顺序表里
  - 排序统一按 `stop_seq_in_waybill` 及兜底规则执行
  - `运单号` 仅作为表中一列保留
- 客户需求卡页
  - 按停靠顺序依次展开客户卡
  - 不先按运单切分页再排客户
  - 客户卡头部保留 `运单号`
- 货物摘要页
  - 也按同一套停靠顺序依次展示
  - 不按运单分块做两个独立摘要区

### C. 为什么不按运单分组优先展示

首轮不建议按运单优先分组，原因如下：

1. 司机执行时关心的是停靠顺序，不是系统里属于哪张运单。
2. 同批次内多运单时，按运单分组容易打断连续送货顺序。
3. 如果一位司机一次执行的其实是同一条线路上的多个运单，按停靠点统一混排更符合现场阅读习惯。

### D. 运单号的保留方式

虽然不按运单分组阅读，但 `运单号` 仍然必须保留，建议：

- 在停靠顺序总览页作为固定一列展示
- 在客户需求卡页头部展示
- 在货物摘要页客户块头部展示

这样司机在需要回对单据时，仍然能快速定位到对应运单。

### E. 异常场景处理

若同批次内多运单的停靠点顺序出现以下情况，仍按“司机优先阅读”原则处理：

- 多运单客户顺序交错
  - 允许统一混排
- 某运单全部顺序缺失
  - 该运单客户放到已明确顺序客户之后
  - 同时整段打 `顺序待确认` 标签
- 某运单只有部分客户有顺序
  - 先展示有明确顺序的停靠点
  - 缺失顺序的停靠点按兜底规则排到后面

### F. 一句话结论

首轮司机阅读包在批次内多运单场景下统一采用：

- 跨运单合并展示
- 按停靠点顺序字段给司机看
- 运单号只作为辅助识别字段保留

## 6. 任务链设计

### 6.1 任务链

尽量复用标准导出思路，建议为：

```text
export_source_scope -> export_task -> export_task_line -> export_error_line -> export_file
```

与标准导出的区别：

- 标准导出重点是结构化文件生成
- 司机侧导出重点是阅读文件排版生成

### 6.2 任务类型建议

建议增加：

- `task_category = driver_route_export`

首轮入口类型固定为：

- `entry_type = from_batch`

### 6.3 行结果粒度

首轮建议：

- 从批次发起：按批次为任务行粒度

原因：

- 司机阅读包首轮就是按批次执行包分发
- 没必要把每个客户卡拆成独立任务行

## 7. 页面与交互设计

### 7.1 入口位置

建议沿用现有物流模块的按钮节奏：

- 批次列表页：`导出司机线路包`
- 批次详情页：`导出司机线路包`

首轮不在运单页、司机管理页直接放正式入口。

### 7.2 结果页结构

结果页继续复用当前导入/导出任务页节奏：

- 顶部：任务摘要
- 中部：行结果
- 下部：错误明细
- 右上：下载文件

但摘要文案要偏司机阅读包口径，例如：

- 本次导出覆盖 `3` 个批次
- 生成 `3` 份司机线路 PDF
- `1` 个批次因客户地址缺失未生成

### 7.3 页面风格基线

司机侧导出虽然是新能力，但页面不应做成全新视觉语言。

建议继续复用当前物流模块的：

- 顶部上下文区
- 中部主工作区
- 下部结果反馈区
- 右上主按钮位

保持它仍然像物流系统里的一个标准动作页，而不是单独的外部打印工具。

## 9. 与标准导出的关系

### 9.1 直接复用

- `task_no`
- 结果页结构
- 行结果与错误明细接口
- 分页与状态反馈方式
- 下载入口机制

### 9.2 明确分离

- 标准导出输出 `xlsx`
- 司机侧导出输出 `pdf`
- 标准导出面向结构化数据
- 司机侧导出面向执行阅读

### 9.3 一句话边界

标准导出回答“数据怎么带走”，司机侧导出回答“司机怎么读懂”。

## 10. 首轮实施顺序建议

1. 先冻结司机阅读包正文字段范围。
2. 先从 `from_batch` 做起。
3. 先生成单个 PDF，不先做 ZIP。
4. 先跑一轮真实批次样本，验证司机是否真的能看懂。
5. 再决定是否补充完整货物附页、波次/运单入口、司机入口和移动端分享优化。

## Risks

- 如果首轮继续追求“字段越多越好”，司机阅读包会重新退化成数据包。
- 如果首轮就承诺从司机管理页聚合全局任务，容易与当前首轮范围的模型边界打架。
- 如果正文里塞入完整订单/货物逐行明细，阅读效率会快速下降。

## Core Conclusion

1. 司机侧导出必须独立于标准导出，不应继续沿用四 Sheet 作为主文件结构。
2. 司机侧导出首轮应定位为“排线后阅读包”，而不是“再导入数据包”。
3. 首轮最稳的方案是：只从批次入口发起，生成可打印 PDF，正文围绕“线路总览 + 停靠顺序 + 客户需求 + 货物摘要”组织。
