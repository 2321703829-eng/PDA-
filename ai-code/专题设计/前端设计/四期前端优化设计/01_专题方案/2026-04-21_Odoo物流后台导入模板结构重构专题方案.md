## Objective

四期导入模板结构重构要解决的不是“再多加一些字段”，而是下面 8 个结构性问题：

1. 旧模板口径无法稳定承接新的门店节点、订单和货物分层。
2. 旧文档把 `waybill_group_no`、`customer_line_no`、文本关联键混在一起，和数据库实际唯一约束不一致。
3. 旧文档把 `customer_line_no` 说成全局主键，但数据库正式口径是 `(waybill_id, customer_line_no)`。
4. 旧文档把 `goods_line` 收成首轮强制 1:1，和数据库 `order_line 1 -> n goods_line` 不一致。
5. 旧文档只谈模板，不谈 `import_task`、`import_error_line` 这类导入审计骨架。
6. 图片导入与主数据导入需要明确拆分为两个对象类型。
7. 页面主阅读链和数据库事实链需要各自稳定，不能互相替代。
8. 用户输入入口可以简化，但正式落库结构不能被扁平化。

因此，本文档的目标收口为：

- 保留系统内部标准对象结构，不改回单表大模型
- 对用户提供单表快捷导入入口
- 保留旧标准模板作为兼容输入模式，而不是四期总契约
- 通过映射脚本把输入结构拆回 `waybill / customer_line / order_line / goods_line`
- 把图片导入设计为独立的 `image_package` 任务链
- 把导入结果纳入统一任务审计与错误行反馈

## Benchmark

本文档统一参考下面 8 条基准：

1. 当前业务主线  
`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`

2. 当前数据库主键与唯一键口径  
- 所有表正式主键统一是 Odoo `id`  
- 业务唯一键用于幂等、导入和外部对接，不替代数据库主键

3. 运单口径  
- `waybill_no` 是正式运单业务唯一键  
- `waybill_group_no` 是导入控制字段

4. 门店节点口径  
- `customer_line_no` 是门店节点稳定业务键  
- 正式唯一性按 `(waybill_id, customer_line_no)` 收口

5. 订单与货物口径  
- `order_line` 是订单/单据快照层  
- `goods_line` 是订单下的货物事实明细层  
- 一张订单允许挂多条货物

6. 图片承接口径  
- 图片应独立于主数据 XLSX  
- 图片导入任务对象类型为 `image_package`

7. 主数据导入口径  
- 主数据主链导入对象类型为 `dispatch_main`

8. 导入审计口径  
- 源文件、任务、行结果、错误行都需要统一记录

## OBB

### Outcome

- 系统内部标准结构明确为 `waybill -> customer_line -> order_line -> goods_line`
- 单表快捷导入可以稳定落成四层对象链
- `waybill_group_no`、`customer_line_no`、订单键和 FK 关系的职责边界明确
- 图片导入和主数据导入拆成两条任务链
- 导入过程能通过任务表和错误行完整审计

### Behavior

- 运单级共享字段进入 `waybill`
- 门店级共享字段进入 `customer_line`
- 订单/单据字段进入 `order_line`
- 商品原子字段进入 `goods_line`
- 单表只是输入入口简化，不改变正式落库结构
- 图片按独立附件包导入，不混入主数据模板

### Boundary

- 本方案不把 `waybill_group_no` 当正式运单键
- 本方案不把 `customer_line_no` 当数据库主键
- 本方案不强行把 `goods_line` 收成 1:1
- 本方案不把页面主阅读链直接当数据库事实链使用

## Current Understanding

### 1. 当前模板问题不只是字段不够，而是对象边界失真

四期真正要解决的是：

- 运单字段不能继续吞并门店字段
- 门店字段不能继续和订单字段混层
- 订单字段不能继续和货物字段混层
- 图片导入不能继续挂在主数据 XLSX 上
- 导入结果不能继续只有页面提示，没有任务审计

### 2. 当前最需要对齐的是数据库唯一性与正式关系

以数据库设计为准，当前必须明确：

- `waybill` 的正式唯一键是 `waybill_no`
- `customer_line` 的正式唯一键是 `(waybill_id, customer_line_no)`
- `order_line` 正式归属 `customer_line_id`
- `goods_line` 正式归属 `order_line_id`

也就是说：

- 文本业务键要服务导入与查重
- FK 才是正式落库关系

### 3. 兼容输入模式可以保留，但不再代表总设计

现有标准模板可以继续存在，作为兼容输入模式和部分历史联调用途。

但四期总设计不能再表述为：

- “三 Sheet 是四期后台总契约”
- “order_line 不需要正式对象层”
- “goods_line 首轮可以强制按 1:1 简化”

### 4. 图片链和主数据链要真正拆开

当前应明确分成两条链：

- `dispatch_main`：主数据导入
- `image_package`：图片包导入

两条链在结果阅读中汇合，但不再共享同一上传结构。

## Core Design Decision

### 1. 内部标准对象结构继续保持四层

系统内部标准结构继续保持：

1. `waybill`
2. `customer_line`
3. `order_line`
4. `goods_line`

原因：

- 这样才能与数据库 FK 和唯一约束一致
- 便于导入审计与错误定位
- 便于页面层做分级阅读
- 便于后续导出、查询和结果页稳定承接

### 2. 对用户保留单表快捷导入入口

用户侧可继续使用一张并表大模板，字段按四组组织：

- 运单级字段组
- 门店节点字段组
- 订单字段组
- 货物字段组

但必须明确：

- 单表不是正式对象结构
- 单表只是导入适配层

### 3. 兼容输入模式继续保留，但不再写成总契约

现有标准模板可作为兼容输入模式保留。

更准确的表述应是：

- 它是历史兼容输入模式之一
- 不是四期对象边界的最终来源
- 正式对象边界仍由数据库设计决定

### 4. `waybill_group_no` 只保留导入控制职责

数据库已经明确：

- `waybill_no` 非空且唯一
- `waybill_group_no` 只是导入控制字段

因此四期导入设计统一收口为：

- 正式落库必须命中有效 `waybill_no`
- `waybill_group_no` 只用于导入预分组、提示和辅助处理
- 不再把 `waybill_group_no` 写成正式运单键替代方案

### 5. `customer_line_no` 是业务稳定键，不是数据库主键

数据库已经明确：

- `customer_line` 的主键是 `id`
- 唯一约束是 `(waybill_id, customer_line_no)`

因此四期导入设计统一收口为：

- `customer_line_no` 必须稳定保留
- 它服务于导入映射、图片命中、对外阅读和查重
- 它的唯一性范围是“同一运单内”
- 不再把它写成全局主键

### 6. `order_line -> goods_line` 按 1:n 设计

数据库没有给 `goods_line` 加一单一货唯一约束。

因此四期设计统一收口为：

- `goods_line` 是订单下的事实明细层
- 同一订单下允许多条 `goods_line`
- 首轮页面主阅读层仍可优先展示 `order_line`
- 但页面展示的货物信息必须可回溯到 `goods_line`

### 7. 导入任务与错误行成为正式设计的一部分

四期导入设计不再只描述“模板怎么填”，还必须正式纳入：

- `import_source_file`
- `import_task`
- `import_task_line`
- `import_error_line`

以及：

- `dispatch_main`
- `image_package`

这两类任务对象类型。

## Template Structure Redesign

## 1. 兼容输入模式

现有标准模板可以继续保留，但其定位改为：

- 兼容输入模式
- 历史联调与部分业务继续使用的输入形式
- 后端映射与导入链的输入来源之一

它不再承担：

- 决定正式对象边界
- 决定数据库关系
- 决定正式唯一键口径

## 2. 用户侧单表快捷导入模板

### 2.1 定位

面向业务用户的一张并表大模板。

### 2.2 字段分组方向

- 运单级字段组
- 门店节点字段组
- 订单字段组
- 货物字段组

### 2.3 核心边界

- 单表只是用户输入入口简化
- 单表不替代分层对象模型
- 单表必须映射成正式四层对象后才能落库

## 3. 图片附件包

### 3.1 定位

独立于主数据模板的图片导入载体。

### 3.2 当前收口

- 对象类型：`image_package`
- 物理结构：
  - `waybill package`
  - `store package`
  - `image files`

### 3.3 清单字段方向

- 必填：
  - `file_name`
  - `waybill_no`
  - `store_no`
  - `scene_code`
  - `image_seq`
- 可选：
  - `customer_line_no`
  - `taken_at`
  - `remark`
  - `source_doc_no`

## Mapping Rules Direction

## 1. 主映射链

正式映射链收口为：

`source_file -> import_task(dispatch_main) -> waybill -> customer_line -> order_line -> goods_line`

## 2. 运单聚合规则

- 正式落库必须有 `waybill_no`
- `waybill_group_no` 只作导入控制字段
- 同一 `waybill_no` 下共享字段冲突一律报错

## 3. 门店节点聚合规则

- 优先使用导入值 `customer_line_no`
- 若未提供，则在已命中 `waybill_no` 前提下由系统生成
- 生成后的结果必须满足运单内唯一
- 再往下不再写成“全局唯一”或“替代数据库主键”

## 4. 订单聚合规则

导入侧优先使用：

- `source_doc_no`
- `order_no`
- `sales_order_no`

说明：

- 这是一组导入侧聚合与兜底校验规则
- 正式落库关联仍通过 `customer_line_id` 和 `order_line_id`

## 5. 货物落行规则

- 大表每一行默认生成一条 `goods_line`
- 同一订单允许挂多条 `goods_line`
- 冲突规则只针对订单快照共享字段
- 不再因为“同一订单键下多商品”直接报错

---

## Association Rules

## 1. 正式关系骨架

正式关系统一按数据库 FK 理解：

- `customer_line.waybill_id -> waybill.id`
- `order_line.customer_line_id -> customer_line.id`
- `goods_line.order_line_id -> order_line.id`

## 2. 业务键职责

- `waybill_no`：正式运单业务键
- `customer_line_no`：运单内稳定门店节点键
- `source_doc_no / order_no / sales_order_no`：订单导入聚合键

## 3. 页面阅读与数据库事实的关系

- 页面主阅读链可收口到 `waybill -> customer_line -> order_line`
- 货物详情、数量、重量、体积等事实仍以 `goods_line` 为准

---

## Import Audit Direction

## 1. 源文件

- 每次上传先生成 `import_source_file`

## 2. 导入任务

- 主数据导入任务使用 `dispatch_main`
- 图片包导入任务使用 `image_package`

## 3. 行结果

- 每一行处理结果进入 `import_task_line`
- 每一个字段级失败进入 `import_error_line`

## 4. 任务状态

统一使用：

- `pending`
- `running`
- `success`
- `partial_failed`
- `failed`
- `cancelled`

---

## Validation Direction

## 1. 结构级

- 单表模式下并表模板必须匹配正式字段清单
- 兼容输入模式必须能被映射回四层对象
- 图片包清单字段必须匹配正式附件包格式

## 2. 关联级

- `waybill_no` 必须先命中或生成正式运单对象
- `customer_line_no` 最终必须满足运单内唯一
- `order_line` 必须命中稳定订单键
- `goods_line` 不允许脱离 `order_line`
- 图片清单不允许脱离 `waybill_no / store_no` 直接导入

## 3. 一致性级

- 运单级共享字段一致性
- 门店节点级共享字段一致性
- 订单级共享字段一致性
- 单表映射后的聚合一致性
- 数量、金额、重量、体积字段格式合法

## 4. 审计级

- 任务统计必须可对账
- 错误行必须记录字段名、原始值、映射值、错误码、错误说明

---

## Query And Page Carryover Direction

1. 运单页继续承担总览与聚合
2. 门店节点页继续承担门店快照、图片入口和订单归属入口
3. 订单页继续作为订单/单据层阅读入口
4. 货物事实虽不一定作为一级页面入口，但必须作为正式事实层保留
5. 本批不把 `trace / evidence` 的新增数据库字段当成已冻结内容

## Risks

### 1. 继续把 `waybill_group_no` 当正式运单键的风险

会直接和 `waybill_no` 的数据库唯一约束冲突。

### 2. 继续把 `customer_line_no` 当全局主键的风险

会直接和 `(waybill_id, customer_line_no)` 的数据库口径冲突。

### 3. 继续把 `goods_line` 收成 1:1 的风险

会让导入、结果页、页面阅读和数据库结构持续错位。

### 4. 只改模板不补导入审计的风险

后续错误定位、联调对账和结果页都会失去正式依据。

### 5. 提前把 `trace / evidence` 扩展当成本批数据库定稿的风险

会把下一阶段对象层设计误混进当前导入结构收口。
