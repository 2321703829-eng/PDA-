# 2026-04-24 四期批量导出模块设计方案

## Objective

- 设计四期标准批量导出能力，使其尽可能复用现有导入模块的任务链、结果页、错误反馈和任务编号设计。
- 支持按不同业务点发起批量导出，首轮至少覆盖批次、运单、客户三个核心入口。
- 让导出结果按正式导入模板的四级结构 `运单包 -> 客户 -> 订单 -> 货物` 组织，形成“可导出、可修订、可再导入”的闭环基础。

## Boundary

- 本文先定义标准数据导出，不展开图片二进制打包导出。
- 本文不直接进入编码实现，先冻结结构、入口、任务链与结果返回口径。
- 本文首轮不做“全系统通用导出中心”，而是先在物流主链范围内落成稳定方案。

## OBB

### Outcome

- 系统支持按 `batch / waybill / customer` 三类业务点发起批量导出任务。
- 导出任务统一围绕 `task_no` 运转，具备任务头、行结果、错误明细、下载结果的完整闭环。
- 标准数据导出文件内部统一复用四 Sheet 正式模板结构，减少额外维护一套独立导出模板的成本。

### Behavior

- 用户可在列表页、详情页或后续的导出中心入口发起导出。
- 导出任务创建后进入异步任务链，前端结果页与导入模块保持相同阅读节奏。
- 成功导出后可下载结构化 Excel；失败或部分失败时可查看错误明细与失败对象。

### Boundary

- 首轮不做图片文件打包 ZIP，不与图片模块导出合并为同一任务类型。
- 首轮不做复杂权限穿透下载，不做超大批量离线分片合并能力。
- 首轮不把导入与导出任务物理合并成一张通用任务表，但页面交互和任务结构尽量复用导入模块。

## Benchmark

### Odoo 原生可复用能力

- Odoo 原生列表导出能做表格导出，但更偏临时字段导出，不适合承接物流主链的多层结构包导出。
- Odoo 原生不提供“批次包 / 运单包 / 客户包”的正式任务链、结果页和失败明细反馈。

### 当前项目已有可复用基线

- 导入任务正式链：`import_source_file -> import_task -> import_task_line -> import_error_line`
- 结果阅读链：`task_no -> result -> lines -> errors -> error-report`
- 四 Sheet 正式模板：`Waybill / CustomerLine / OrderLine / GoodsLine`

### 路径选择

- 不直接复用 Odoo 原生临时列表导出作为正式方案。
- 采用“导出模型独立、交互与任务结构复用导入模块”的方式落地。

## Current Understanding

当前导入模块已经跑通四 Sheet 正式模板和 `task_no` 结果链，因此导出模块最合适的设计，不是重新做一套导出风格，而是尽量沿用以下 4 个能力：

1. 任务号驱动  
导出同样使用 `task_no` 作为正式任务主键。

2. 任务头 + 行结果 + 错误明细  
导入结果页已经验证过这套结构可读，导出继续复用同样的节奏。

3. 结构化 Excel 作为正式交付物  
导入标准模板已经固定为四 Sheet，导出文件尽量保持同结构，形成回写兼容。

4. 入口类型与包结构分离  
导出侧需要明确区分“从哪里发起导出”和“导出文件内部按什么层级组织”，不能把两者混成同一套对象名。

## 1. 正式设计结论

### 1.1 导出入口类型

首轮正式支持 3 类导出入口：

- `from_batch`
- `from_waybill`
- `from_customer`

说明：

- `from_batch` 代表从批次视角发起导出，导出该批次范围内的完整执行主链。
- `from_waybill` 代表从运单视角发起导出，导出该运单范围内的完整执行主链。
- `from_customer` 代表从客户/门店视角发起导出，导出当前筛选范围内相关主链数据。

### 1.2 导出包正式层级

无论从哪个入口发起，正式导出包内部都按导入模板四级结构组织：

- `waybill_package`
- `customer_line`
- `order_line`
- `goods_line`

对应文件层继续固定为四 Sheet：

- `Waybill`
- `CustomerLine`
- `OrderLine`
- `GoodsLine`

核心原则：

- 尽量与正式导入模板结构保持一致。
- 导出文件优先服务“业务回看 + 修订后二次导入”。
- 不额外发明一套只适合导出的专用宽表。

### 1.3 为什么批次不是正式包层级

`batch` 可以是导出入口，但不应成为导出文件内部正式层级，原因如下：

1. 当前正式导入模板本身没有 `Batch` Sheet。
2. 批次字段已经能在 `Waybill` Sheet 中承接上下文。
3. 如果把 `batch` 也做成正式导出层级，导出和导入结构就会分叉。

后续若批次视角阅读确实不足，再评估是否增加只读 `BatchSummary` Sheet，但它也应是摘要视图，而不是正式导入层级。

## 2. 任务链设计

### 2.1 正式任务链

建议首轮正式链路为：

```text
export_source_scope -> export_task -> export_task_line -> export_error_line
```

语义说明：

- `export_source_scope`：记录本次导出筛选条件、入口来源、对象范围快照
- `export_task`：任务头
- `export_task_line`：导出入口对象行结果
- `export_error_line`：字段级或对象级失败信息

### 2.2 为什么不直接复用 import_task

不建议把导出直接塞进 `import_task`，原因是：

1. 导入与导出的业务动作方向不同。
2. 导入需要原始文件落盘，导出需要结果文件生成与下载。
3. 两者虽然结构类似，但生命周期、状态机和结果文件字段并不相同。

因此建议：

- 数据模型分开
- `task_no`、结果页、接口风格、状态机设计尽量统一

## 3. 状态设计

### 3.1 任务状态

建议沿用导入模块阅读习惯，导出任务状态固定为：

- `pending`
- `running`
- `success`
- `partial_failed`
- `failed`
- `expired`
- `cancelled`

### 3.2 行结果状态

`export_task_line.status` 建议支持：

- `pending`
- `success`
- `failed`
- `skipped`

说明：

- `skipped` 适用于对象被筛选但最终因无下游数据或不满足导出条件而跳过。

## 4. 对象范围与导出粒度

### 4.1 从批次发起导出

#### 入口

- 批次列表页：勾选多条批次后批量导出
- 批次详情页：导出当前批次

#### 导出范围

- 所选批次
- 批次下关联运单
- 运单下 `customer_line / order_line / goods_line`

#### 导出文件内部层级

- `Waybill` Sheet 继续承接 `wave / batch / waybill` 上下文
- `CustomerLine / OrderLine / GoodsLine` 继续按正式模板展开

#### 行结果粒度

- 首轮建议以“批次”为任务行粒度
- `export_task_line.business_key = batch_no`

### 4.2 从运单发起导出

#### 入口

- 运单列表页：勾选多条运单后批量导出
- 运单详情页：导出当前运单

#### 导出范围

- 所选运单
- 运单下 `customer_line / order_line / goods_line`

#### 导出文件内部层级

- 不因入口变成运单而改成“只有运单一层”
- 仍然按 `Waybill / CustomerLine / OrderLine / GoodsLine` 四 Sheet 导出

#### 行结果粒度

- 首轮建议以“运单”为任务行粒度
- `export_task_line.business_key = waybill_no`

### 4.3 从客户发起导出

#### 入口

- 客户列表页：勾选多客户批量导出
- 客户详情页：导出当前客户相关数据
- 门店节点列表页：后续可作为补充入口

#### 导出范围

这里建议明确采用“客户导出 = 客户视角下的执行数据导出”，而不是一次把所有主数据全打走。

首轮范围建议为：

- 当前选中的客户
- 当前查询范围内与其相关的 `customer_line`
- 这些 `customer_line` 关联到的 `waybill / order_line / goods_line`

#### 行结果粒度

- 首轮建议以“客户”为任务行粒度
- `export_task_line.business_key = external_customer_code 或 customer_id`

说明：

- 若从执行数据场景进入，导出对象的真实承接主对象仍是 `customer_line`。
- 页面文案可写成“客户导出”或“客户/门店导出”，但内部逻辑要明确围绕当前业务范围取数。

## 5. 文件结构设计

### 5.1 默认导出文件

默认文件命名建议：

```text
TSL-EXPORT-{OBJECT_TYPE}-{YYYYMMDD-HHMMSS}.xlsx
```

示例：

- `TSL-EXPORT-FROM-BATCH-20260424-103000.xlsx`
- `TSL-EXPORT-FROM-WAYBILL-20260424-103000.xlsx`
- `TSL-EXPORT-FROM-CUSTOMER-20260424-103000.xlsx`

### 5.2 Sheet 结构复用原则

四个 Sheet 均复用正式导入模板表头：

- `Waybill`
- `CustomerLine`
- `OrderLine`
- `GoodsLine`

补充规则：

1. 导出时列顺序与导入模板保持一致。
2. 导出时只填实际已存在数据，不额外伪造空层级。
3. 若某个对象范围下无某层数据，该 Sheet 保留表头但可无数据行。

### 5.3 是否附带说明页

首轮建议不附带额外说明页，理由是：

- 保持导出文件可直接作为修订回写底板。
- 减少“导出文件能看但不能回写”的结构分叉。

后续若业务确实需要，可另做“阅读版导出包”。

## 6. 页面与交互设计

### 6.1 入口设计

尽量复用导入模块“中心入口 + 列表页入口 + 详情页入口”的思路：

1. 列表页批量按钮  
用于批次、运单、客户三个列表页。

2. 详情页单对象导出  
用于当前对象的单包导出。

3. 后续导出中心  
首轮可先不单独建设，等任务量上来后再统一沉淀历史任务入口。

### 6.2 结果页设计

结果页继续复用导入结果页结构：

- 顶部：任务摘要
- 中部：行结果列表
- 下部：错误明细
- 右上：下载导出文件

新增强调点：

- 导入结果页关注“写入成功了什么”
- 导出结果页关注“导出了什么、哪些对象失败、下载文件在哪里”

### 6.3 行结果字段建议

`export_task_line` 在结果页最少展示：

- `line_no`
- `business_key`
- `target_object_type`
- `status`
- `message`
- `export_count_summary`

### 6.4 错误明细字段建议

`export_error_line` 建议统一返回：

- `line_no`
- `business_key`
- `field_name`
- `error_code`
- `error_message`

## 7. 接口方案

### 7.1 路由前缀

保持 RESTful 风格，与导入平行：

- `/api/admin/logistics/exports/...`

### 7.2 任务接口建议

建议首轮提供：

- `POST /api/admin/logistics/exports/batch`
- `POST /api/admin/logistics/exports/waybill`
- `POST /api/admin/logistics/exports/customer`
- `GET /api/admin/logistics/exports/tasks/{task_no}`
- `GET /api/admin/logistics/exports/tasks/{task_no}/lines`
- `GET /api/admin/logistics/exports/tasks/{task_no}/errors`
- `GET /api/admin/logistics/exports/tasks/{task_no}/download`

### 7.3 请求体建议

以批次导出为例：

```json
{
  "entry_type": "from_batch",
  "selected_ids": [101, 102, 103],
  "export_mode": "standard_xlsx",
  "from_page": "batch_list",
  "scope_snapshot": {
    "domain": [["status", "=", "ready"]],
    "filters": {
      "warehouse_code": "WH"
    }
  }
}
```

### 7.4 结果页摘要建议

`GET /tasks/{task_no}` 建议返回：

```json
{
  "task_no": "EXT260424-00001",
  "entry_type": "from_batch",
  "package_structure": "dispatch_main_four_sheet",
  "status": "partial_failed",
  "total_count": 20,
  "success_count": 18,
  "fail_count": 2,
  "download_file": {
    "name": "TSL-EXPORT-BATCH-20260424-103000.xlsx",
    "ready": true,
    "download_url": "/api/admin/logistics/exports/tasks/EXT260424-00001/download"
  }
}
```

## 8. 与导入模块的复用边界

### 8.1 直接复用

- `task_no` 任务识别方式
- 结果页阅读结构
- 行结果与错误明细接口风格
- 分页、筛选、错误报告阅读节奏
- 四 Sheet Excel 结构

### 8.2 不直接复用

- 原始文件上传链
- `import_source_file`
- 预校验确认流程
- 导入专用状态字段和错误码

### 8.3 复用原则

一句话总结：

导出模块应当“长得像导入模块”，但不是“假装成导入模块”。

## 9. 首轮实施顺序建议

1. 先冻结 `from_batch / from_waybill / from_customer` 三类入口的导出范围。
2. 先实现标准 `xlsx` 导出，不先做 ZIP。
3. 先接通任务链、结果页、下载接口。
4. 先让导出结果文件与四 Sheet 模板兼容。
5. 跑通批次、运单、客户三条真实 smoke 后，再决定是否加导出中心和阅读增强能力。

## Risks

- 若客户导出不先收清“客户主档导出”与“客户执行数据导出”的边界，后续很容易口径漂移。
- 若首轮就加入图片 ZIP、阅读专用宽表、统计汇总页，范围会明显膨胀。
- 若导出文件结构与导入模板分叉，后续维护成本会快速上升。

## Core Conclusion

1. 批量导出首轮应当复用导入模块的任务链思路，而不是复用 Odoo 原生临时列表导出。
2. `批次 / 运单 / 客户` 是导出入口类型，不是导出文件内部正式层级。
3. 标准导出文件应统一复用 `运单包 -> 客户 -> 订单 -> 货物` 四级和对应四 Sheet 结构。
## 9. 统一入口补充

为减少“运单标准导出只有列表页勾选按钮可见”的问题，当前统一入口口径补充如下：

- 导入中心页面内增加 `运单标准导出` 说明区块
- 该区块不在中心页内直接做运单对象勾选
- 而是作为统一入口，明确引导用户：
  - 先进入运单列表
  - 勾选需要导出的运单
  - 再点击列表页顶部 `导出`

这样保留了：

- 当前最稳定的运单列表勾选导出链
- 中心页层面的可发现入口
