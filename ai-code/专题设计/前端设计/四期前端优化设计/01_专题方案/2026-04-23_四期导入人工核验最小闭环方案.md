# 2026-04-23 四期导入人工核验最小闭环方案

## 文档定位

- 本文用于补齐四期导入模块在“结果回看”之后的人工核验正式方案。
- 本文是规划方案，不代表当前代码已全部落地。
- 本文以当前数据库基线、正式任务链 `import_source_file -> import_task -> import_task_line -> import_error_line`、以及已落地的结果页为前提。

## OBB

### Outcome

- 导入任务在正式完成后，支持进入人工核验最小闭环。
- 人工核验以 `import_task_line` 为最小对象，不另起第二套业务行模型。
- 最小闭环固定支持 6 个核验要素：
  - `待核验`
  - `核验通过`
  - `核验驳回`
  - `核验备注`
  - `核验人`
  - `核验时间`

### Behavior

- 人工核验不替代导入结果，只是叠加在导入结果之上的“人工判断层”。
- 导入状态与人工核验状态并行存在：
  - 导入状态回答“系统执行结果是什么”
  - 核验状态回答“人工是否接受当前结果”
- 核验入口继续围绕 `task_no` 运转，从结果页和后续阅读链进入。
- 字段错误明细继续作为证据层，不单独承接人工核验状态。

### Boundary

- 本轮只定义最小闭环，不扩展为完整审批流。
- 本轮不引入多级审核、会签、指派、催办、通知、SLA、审核历史流水表。
- 本轮不自动回滚导入结果，也不自动重跑导入。
- 本轮先覆盖标准主数据导入 `dispatch_main`，图片包导入后续再接。

## 1. 基线对比

### 1.1 Odoo 原生可复用能力

- `mail` / chatter 可承接备注、附件、活动提醒。
- `base_import` 可承接导入入口和基础导入能力。
- 官方模块常见的 `audit_status` 更偏业务单据审核，不适合直接拿来承接导入任务行核验。

### 1.2 当前项目仍缺的能力

- 结果页能看见失败和错误，但还没有“人工已看过并给出结论”的正式状态。
- 没有行级核验备注、核验人、核验时间。
- 没有按“待核验 / 已通过 / 已驳回”过滤导入任务行。
- “按任务继续核验”目前更像跳转口径，还不是正式核验工作流。

### 1.3 路径选择

- 不直接复用 Odoo 原生审批对象。
- 采用“扩展现有导入任务正式模型”的方式落地。
- 核验主承载仍放在自定义链路：
  - 数据层归属 `logistics_dispatch`
  - 接口与页面归属 `logistics_web`

## 2. 当前理解

当前导入链已经稳定到这条正式结构：

```text
source_file -> import_task -> import_task_line -> import_error_line
```

其中：

- `import_task` 是任务头
- `import_task_line` 是最小行级结果
- `import_error_line` 是字段级错误证据

因此人工核验不应重新发明“核验行”对象，而应直接挂在 `import_task_line` 上：

```text
import_task_line
  -> import status
  -> manual review status
  -> review remark / user / time
```

这能保证：

- 系统导入结果与人工判断在同一条行上闭环
- 结果页、运单阅读链、错误明细链都能围绕同一任务号和同一行号回读
- 后续若要补核验历史表，也能从当前最小闭环平滑升级

## 3. 核验对象与状态模型

### 3.1 核验对象

- 核验主对象：`import_task_line`
- 证据只读对象：`import_error_line`

原因：

- `import_task_line` 已经具备 `line_no / source_row_no / import status / business_key / target_object / message`
- `import_error_line` 是字段级证据，不适合单独承担“通过 / 驳回”

### 3.2 核验状态

新增独立状态字段，不复用导入状态字段。

建议字段名：

- `review_status`

建议枚举：

- `pending` ← 待核验
- `passed` ← 核验通过
- `rejected` ← 核验驳回

语义说明：

- `pending`：当前行还没有完成人工判断
- `passed`：人工已确认当前导入结果或当前数据状态可接受
- `rejected`：人工确认当前导入结果或当前数据状态不可接受，需要后续修正、重导或补数据

注意：

- `passed` 不是“导入成功”的同义词
- `rejected` 不是“系统执行失败”的同义词
- 核验状态永远是人工判断层，不能覆盖系统导入状态

## 4. 最小数据字段方案

### 4.1 落字段位置

首轮直接落在 `import_task_line`。

### 4.2 新增字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `review_status` | `Selection` | 是 | 人工核验状态，默认 `pending` |
| `review_remark` | `Text` | 否 | 核验备注 |
| `review_user_id` | `Many2one(res.users)` | 否 | 最后一次核验人 |
| `reviewed_at` | `Datetime` | 否 | 最后一次核验时间 |

### 4.3 默认规则

- 任务进入最终状态后，所有 `import_task_line.review_status` 默认为 `pending`
- 初始不写 `review_user_id / reviewed_at`
- 初始 `review_remark` 为空

### 4.4 本轮不新增的字段

- 不新增独立 `review_log` 历史表
- 不新增 `first_reviewed_at / last_reviewed_at`
- 不新增 `review_owner_id`
- 不新增任务级持久化核验汇总字段

说明：

- 首轮任务级核验汇总通过 `import_task_line` 聚合返回
- 等最小闭环跑稳后，再决定是否把聚合计数下沉到 `import_task`

## 5. 交互规则

### 5.1 入口

人工核验统一从这两个入口进入：

1. 导入结果页的“按任务继续核验”
2. 运单列表 / 运单详情中带 `task_no` 的后续核验入口

### 5.2 页面承载

首轮不新开一整套“审核中心”，优先扩展现有结果页：

- 顶部继续看任务摘要
- 中间继续看行结果与字段错误
- 行结果区升级为“可筛选、可批量、可标记”的核验主区

### 5.3 核验动作

首轮固定支持 3 个动作：

1. 标记 `核验通过`
2. 标记 `核验驳回`
3. 重置为 `待核验`

### 5.4 备注规则

- `核验通过`：备注可选
- `核验驳回`：备注必填
- `待核验`：如果从已核验状态重置回待核验，则清空当前结论字段：
  - `review_remark`
  - `review_user_id`
  - `reviewed_at`

说明：

- 首轮没有核验历史流水，所以“重置待核验”意味着清掉当前结论
- 若后续要保留历史，则再补独立日志表

### 5.5 核验归属

- 每次提交核验动作时，当前登录用户写入 `review_user_id`
- 当前服务端时间写入 `reviewed_at`
- 同一行允许重复修改，始终以最后一次人工结论为准

## 6. 结果页最小升级方案

### 6.1 新增阅读问题

结果页在现有 5 个问题之外，再补 3 个问题：

1. 哪些行还没被人工看过
2. 哪些行已经被人工接受
3. 哪些行被人工驳回并需要后续处理

### 6.2 行结果区新增字段

在现有行结果字段基础上补：

- `review_status`
- `review_status_label`
- `review_remark`
- `review_user.name`
- `reviewed_at`

### 6.3 行结果区新增筛选

首轮建议支持双层筛选：

- 系统导入状态筛选：`pending / success / failed / skipped`
- 人工核验状态筛选：`pending / passed / rejected`

默认策略：

- 若任务存在失败行，默认进入结果页时优先显示：
  - 导入状态 = `failed`
  - 核验状态 = `pending`
- 若任务无失败行，默认显示：
  - 导入状态 = `all`
  - 核验状态 = `pending`

### 6.4 批量动作

首轮结果页支持：

- 勾选单行
- 勾选当前页多行
- 对当前选中行批量标记通过 / 驳回 / 重置待核验

本轮不支持：

- 跨页全选
- 大规模异步批处理任务

## 7. 接口正式方案

## 7.1 任务结果接口补充

`GET /api/admin/logistics/imports/tasks/{task_no}`

新增返回块：

```json
{
  "review_summary": {
    "pending_count": 25,
    "passed_count": 5,
    "rejected_count": 3,
    "is_complete": false
  }
}
```

说明：

- `is_complete = pending_count == 0`
- 首轮由服务层聚合计算，不强制落任务头字段

## 7.2 行结果查询接口补充

`GET /api/admin/logistics/imports/tasks/{task_no}/lines`

新增查询参数：

| 参数 | 说明 |
| --- | --- |
| `review_status` | 按人工核验状态筛选，支持 `pending / passed / rejected` |

新增返回字段：

| 字段 | 说明 |
| --- | --- |
| `review_status` | 人工核验状态 |
| `review_status_label` | 人工核验状态中文名 |
| `review_remark` | 核验备注 |
| `review_user` | `{ id, name }` |
| `reviewed_at` | 核验时间 |

## 7.3 人工核验提交接口

建议新增：

`POST /api/admin/logistics/imports/tasks/{task_no}/line-reviews`

请求体样例：

```json
{
  "line_ids": [101, 102, 103],
  "review_status": "rejected",
  "review_remark": "门店编号与原始单据不一致，需要修正后重导。"
}
```

返回样例：

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "task_no": "IMT260423-00001",
    "updated_count": 3,
    "review_summary": {
      "pending_count": 22,
      "passed_count": 5,
      "rejected_count": 6,
      "is_complete": false
    }
  },
  "request_id": "req_import_line_review_001"
}
```

### 7.4 提交校验规则

- 任务必须存在
- 任务状态必须已经结束，允许：
  - `success`
  - `partial_failed`
  - `failed`
- `line_ids` 必须全部属于同一个 `task_no`
- `review_status = rejected` 时，`review_remark` 必填
- `review_status = pending` 时，清空当前核验结论字段

## 8. 业务规则冻结

### 8.1 导入结果与人工核验并行

- 人工核验不能改写 `import_task.status`
- 人工核验不能改写 `import_task_line.status`
- 人工核验只改变人工判断字段

### 8.2 驳回不等于自动回滚

- `核验驳回` 只代表人工不接受当前结果
- 系统不自动删数据
- 系统不自动回滚已写入对象
- 系统不自动重跑导入

后续动作由人决定：

- 回源修正
- 重新导入
- 到业务对象页手工修补

### 8.3 字段错误仍是证据层

- `import_error_line` 继续只读展示
- 字段错误不能单独被标“通过/驳回”
- 一条行的人工核验结论，统一落到 `import_task_line`

## 9. 最小开发拆分

### 9.1 数据层

- 给 `import_task_line` 加 4 个字段：
  - `review_status`
  - `review_remark`
  - `review_user_id`
  - `reviewed_at`

### 9.2 服务层

- 给任务头返回补 `review_summary`
- 给行结果接口补 `review_status` 过滤和核验字段
- 新增批量核验写接口

### 9.3 页面层

- 结果页补人工核验摘要卡或状态条
- 行结果区补勾选、核验状态列、核验备注列
- 补批量通过 / 驳回 / 重置待核验动作

### 9.4 验收层

至少覆盖下面 6 条：

1. 任务完成后，所有行默认进入 `待核验`
2. 批量标记通过成功
3. 驳回时备注必填
4. 重置待核验后，核验人和核验时间被清空
5. 可按 `review_status` 正确筛选
6. `review_summary` 与行级真实状态一致

## 10. 本轮不纳入

- 多人并发抢占核验
- 审核历史流水
- 核验消息通知
- 指派责任人
- 图片包导入人工核验
- Mini/Open 端核验
- 自动生成整改任务

## 11. 结论

这版最小闭环的关键不是把导入模块做成完整审批系统，而是先把“看结果”升级成“给结论”：

- 结果仍然由正式任务链承接
- 人工核验仍然围绕 `task_no + import_task_line` 运转
- 状态、备注、核验人、核验时间都挂在当前正式行模型上

这样能让导入模块先具备正式的人工作业闭环，同时给后续升级保留清晰路径：

- 若后续需要完整审核流，再在当前行级闭环上补历史表、指派和通知
- 若只需要业务可用的最小核验，这一版就已经足够进入设计评审和开发拆分
