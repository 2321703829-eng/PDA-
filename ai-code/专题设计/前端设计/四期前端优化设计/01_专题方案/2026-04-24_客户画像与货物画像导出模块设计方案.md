# 2026-04-24 客户画像与货物画像导出模块设计方案

## 文档定位

- 本文用于把“客户画像导出”和“货物画像导出”从临时复用 Odoo 原生导出，推进到与 `from_waybill` 同风格的正式任务结果链方案。
- 本文是专题方案层，先明确对象边界、入口、文件结构、接口方向和演进顺序，不直接覆盖已经冻结的 `dispatch_main` 导出正式稿。
- 如本文确认无误，下一步再补“正式落库与接口冻结补丁稿”，把新对象类型、入口类型、通用统计字段和路由口径正式并入导出基线。

## Objective

- 让客户画像导出和货物画像导出不再依赖 Odoo 原生字段导出，而是复用当前已跑通的 `task_no -> result -> lines -> errors -> download` 正式结果链。
- 让用户可以从客户页和货物页直接发起导出，而不是被迫回到通用列表页找原生导出入口。
- 保持客户画像与货物画像的对象边界清晰，避免把“客户主档”“客户商品关系”“运单货物快照”继续混成一份不稳定的导出。

## Boundary

- 本文只讨论后台管理端导出，不覆盖司机侧阅读导出、图片 ZIP 导出和移动端导出。
- 本文只讨论“客户画像导出”和“货物画像导出”，不改 `from_waybill` 已上线链路。
- 本文默认导出文件仍以 `xlsx` 为首轮输出，不在同一轮展开 PDF、ZIP 或导出中心历史页。
- 本文不要求立即实现 `logistics.customer.product.profile`，但会把它作为客户侧和货物侧导出增强的二阶段依赖明确写出。

## Benchmark

### 1. 已有正式导出基线

- `from_waybill` 已经具备正式任务链、结果页、下载链路和浏览器 smoke 验证。
- 现有正式路由前缀已经稳定在 `/api/admin/logistics/exports/...`。
- 现有结果页和任务模型已经证明“业务化导出”优于 Odoo 原生字段导出。

### 2. 客户对象现状

- 用户侧统一客户画像已经收口到 `res.partner`，不再要求用户在“客户画像”和“门店画像”之间自己做对象判断。
- `logistics.customer.profile` 和 `logistics.store.profile` 当前更适合作为兼容包装层，不适合作为后续正式导出的主源对象。

### 3. 货物对象现状

- 当前没有一个已经正式落地的独立 `goods_profile` 表。
- 货物长期主数据当前更适合由三层承接：
  - `product.template`
  - `logistics.product.unit`
  - 后续规划的 `logistics.customer.product.profile`
- `goods_line` 属于运单执行快照层，不应继续承担“货物画像主档导出”的职责。

### 4. Odoo 原生能力基线

- Odoo 原生导出适合临时字段导出和模板保存。
- Odoo 原生导出不具备我们当前需要的业务任务号、结果页、错误明细、错误报告和下载审计链。
- 因此客户画像和货物画像不应继续长期依赖 Odoo 原生导出兜底。

## Current Understanding

### 1. 为什么客户画像导出不能继续靠原生导出

- 原生导出入口主要存在于列表页，详情表单页不形成稳定的业务导出入口。
- 当前客户画像页面本身还存在文案和可用性问题，继续要求用户“自己切列表页再原生导出”，体验不可接受。
- 客户画像导出需要和运单导出一样，成为一个显式业务动作，而不是隐藏在原生列表工具里的临时操作。

### 2. 为什么货物画像导出不能直接复用 `GoodsLine`

- `GoodsLine` 是执行事实和快照，不是长期货物画像。
- 如果把 `GoodsLine` 继续当作货物画像导出的主对象，会把“本次送了什么”和“系统长期维护什么商品”再次混在一起。
- 货物画像真正稳定的来源应是全局商品主档和规格层；客户差异化规则应由客户商品关系层承接。

### 3. 为什么不能简单新增一张 `goods_profile` 表

- 现有三层方案已经明确：大多数货物长期属性应收口到 `product.template + logistics.product.unit + customer relation`。
- 在这套结构都还没充分利用之前，新增一张 `goods_profile` 表只会制造第四套重复主数据。
- 因此用户侧可以叫“货物画像导出”，但实现层不建议新增一张名为 `goods_profile` 的正式底表。

## Outcome / Behavior / Boundary

### A. 客户画像导出

#### Outcome

- 用户可以从“物流客户画像”列表页和详情页直接发起正式导出。
- 导出进入统一结果页，有 `task_no`、行结果、错误明细和文件下载。
- 导出的文件表达“统一客户画像”，而不是再拆成“客户”和“门店”两套用户入口。

#### Behavior

- 用户入口来源于 `res.partner` 的统一客户画像动作。
- 服务层主对象按 `res.partner` 处理，要求 `is_logistics_partner = True`。
- 文件首轮聚焦客户画像主档本身，二阶段再补客户商品关系增强。

#### Boundary

- 首轮不再以 `logistics.customer.profile` 或 `logistics.store.profile` 作为正式导出主源。
- 首轮不要求依赖尚未落地的客户商品关系表才能上线。

### B. 货物画像导出

#### Outcome

- 用户可以从商品主档页直接发起正式导出。
- 导出进入统一结果页，有 `task_no`、行结果、错误明细和文件下载。
- 导出的文件表达“货物长期主数据 + 规格层”，而不是导出运单执行快照。

#### Behavior

- 服务层主对象按 `product.template` 处理。
- 首轮文件至少包含商品主档和商品规格两个正式层级。
- 二阶段在客户商品关系模型落地后，再补“该商品被哪些客户如何使用”的增强表达。

#### Boundary

- 首轮不以 `goods_line` 为货物画像主源。
- 首轮不新建 `goods_profile` 正式表。

## 核心结论

1. 客户画像导出要做成正式业务导出，但主对象必须是 `res.partner`，不是旧包装表。
2. 货物画像导出也要做成正式业务导出，但主对象必须是 `product.template`，不是 `goods_line`。
3. 货物画像的用户表达可以继续叫“货物画像”，实现层不要额外造 `goods_profile` 表。
4. 两条导出线应复用当前 `export_source_scope / export_task / export_task_line / export_error_line` 审计链，而不是再起一套并行底座。
5. 当前任务头统计字段是 `dispatch_main` 专用口径，后续必须补“通用 metrics JSON”扩展，才能承接客户画像和货物画像导出。

## 1. 对象收口方案

### 1.1 客户画像导出对象

用户侧名称：

- 客户画像导出

实现层推荐：

- `object_type = customer_profile`
- `entry_type = from_customer`
- `source_model = res.partner`

正式主对象：

- `res.partner`

兼容层说明：

- 如果入口来自现有 `logistics.customer.profile` 或 `logistics.store.profile` 菜单，服务层应先统一换算成 `partner_id`。
- 结果页、任务行、错误明细统一显示“客户画像”，不再暴露旧双对象概念。

### 1.2 货物画像导出对象

用户侧名称：

- 货物画像导出

实现层推荐：

- `object_type = product_profile`
- `entry_type = from_product`
- `source_model = product.template`

正式主对象：

- `product.template`

关联层：

- `logistics.product.unit`
- 后续 `logistics.customer.product.profile`

边界说明：

- 货物画像导出不是执行层 `goods_line` 导出。
- `goods_line` 仍由 `from_waybill` 导出承担，不挪到货物画像导出里做主表达。

## 2. 文件结构方案

## 2.1 客户画像导出文件

### 首轮建议结构

`package_structure = customer_profile_bundle_v1`

Sheet：

- `CustomerProfile`

行粒度：

- 一行一个 `res.partner`

字段方向：

- 基础身份与编码
- 联系方式与地址
- 经营画像字段
- 配送画像字段
- 签收、卸货、停车、时间窗等服务约束

这样做的原因：

- 当前用户侧已经统一到一个客户对象。
- 首轮先把最稳定、最可交付的客户画像主档导出做出来。
- 不让客户导出被尚未落地的客户商品关系表卡住。

### 二阶段增强结构

`package_structure = customer_profile_bundle_v2`

Sheet：

- `CustomerProfile`
- `CustomerProductRelation`

说明：

- 当 `logistics.customer.product.profile` 正式落地后，再在客户画像导出里补客户常用商品关系。
- 这个增强不应该阻塞客户画像导出首轮上线。

## 2.2 货物画像导出文件

### 首轮建议结构

`package_structure = product_profile_bundle_v1`

Sheet：

- `ProductProfile`
- `ProductUnit`

行粒度：

- `ProductProfile`：一行一个 `product.template`
- `ProductUnit`：一行一个 `logistics.product.unit`

字段方向：

- `ProductProfile`
  - 内外部商品编码
  - 商品名称
  - 品牌
  - 类别
  - 标签
  - 默认条码
  - 基础单位
  - 默认重量
  - 默认体积
  - 通用配送要求
- `ProductUnit`
  - SKU
  - 规格
  - 销售单位
  - 条码
  - 换算系数
  - 价格
  - 尺寸
  - 重量
  - 体积
  - 最小起订量
  - 备注

### 二阶段增强结构

`package_structure = product_profile_bundle_v2`

Sheet：

- `ProductProfile`
- `ProductUnit`
- `CustomerProductRelation`

说明：

- 当客户商品关系层落地后，货物画像导出可以进一步回答“这个商品被哪些客户如何使用”。
- 这张关系 sheet 是货物画像增强，不是首轮强依赖。

## 3. 任务链复用方案

两条导出线都继续复用当前正式任务链：

```text
export_source_scope -> export_task -> export_task_line -> export_error_line
```

### 3.1 可直接复用的部分

- 任务号生成
- 结果页读取节奏
- 错误明细和错误报告下载
- 文件下载接口
- 操作者与任务权限校验

### 3.2 必须补的扩展点

当前 `export_task` 和 `export_task_line` 的统计字段是 `dispatch_main` 专用：

- `exported_waybill_count`
- `exported_customer_line_count`
- `exported_order_line_count`
- `exported_goods_line_count`

这套字段无法自然承接客户画像和货物画像导出，因此建议：

- 保留现有专用字段，保证 `from_waybill` 不被破坏
- 在 `export_task` 新增 `package_metrics_json`
- 在 `export_task_line` 新增 `line_metrics_json`

推荐结构示意：

```json
{
  "customer_count": 12,
  "product_count": 0,
  "product_unit_count": 0,
  "customer_product_relation_count": 0
}
```

和：

```json
{
  "product_count": 1,
  "product_unit_count": 4
}
```

结果页策略：

- `dispatch_main` 继续优先读现有专用字段
- `customer_profile` 和 `product_profile` 改读 `metrics_json`
- 后续新对象类型不再继续堆叠专用统计列

## 4. 路由与 DTO 方案

### 4.1 客户画像导出

创建路由建议：

- `POST /api/admin/logistics/exports/customer-profile`

请求体建议：

```json
{
  "object_type": "customer_profile",
  "entry_type": "from_customer",
  "export_mode": "standard_xlsx",
  "package_structure": "customer_profile_bundle_v1",
  "selected_ids": [101, 102],
  "source_model": "res.partner",
  "source_page": "customer_profile_list",
  "scope_snapshot": {
    "domain": [["is_logistics_partner", "=", true]]
  }
}
```

### 4.2 货物画像导出

创建路由建议：

- `POST /api/admin/logistics/exports/product-profile`

请求体建议：

```json
{
  "object_type": "product_profile",
  "entry_type": "from_product",
  "export_mode": "standard_xlsx",
  "package_structure": "product_profile_bundle_v1",
  "selected_ids": [301, 302],
  "source_model": "product.template",
  "source_page": "product_template_list",
  "scope_snapshot": {
    "domain": []
  }
}
```

### 4.3 结果回读与下载

继续复用当前共享路由：

- `GET /api/admin/logistics/exports/tasks/<task_no>`
- `GET /api/admin/logistics/exports/tasks/<task_no>/lines`
- `GET /api/admin/logistics/exports/tasks/<task_no>/errors`
- `GET /api/admin/logistics/exports/tasks/<task_no>/error-report`
- `GET /api/admin/logistics/exports/tasks/<task_no>/download`

这样做的原则：

- 新对象类型增加创建入口
- 老的任务读取路由不再分裂
- 结果页只按 `object_type` 和 `package_structure` 切换文案与统计卡片

## 5. 页面入口方案

### 5.1 客户画像导出入口

首轮入口建议：

- `物流客户画像` 列表页：批量导出
- `物流客户画像` 详情页：导出当前客户画像

不建议首轮入口：

- 旧 `logistics.customer.profile`
- 旧 `logistics.store.profile`

理由：

- 用户侧已经统一为单对象入口。
- 继续在旧包装页加正式按钮，会把收口后的对象认知再次打散。

### 5.2 货物画像导出入口

首轮入口建议：

- 商品主档列表页：批量导出
- 商品主档详情页：导出当前货物画像

可选二阶段入口：

- 商品规格列表页导出当前筛选规格

不建议首轮直接从规格页发起正式导出，原因是：

- 用户更容易理解“导出商品画像”，而不是“导出某个 SKU 行”
- 首轮以 `product.template` 为导出主对象更稳定

## 6. 权限口径方案

建议按动作授权，而不是继续依赖“页面在原生列表里能否看到导出菜单”。

### 6.1 客户画像导出权限

- 可读 `res.partner` 且具备客户画像导出动作权限的用户，可以发起 `customer_profile` 导出
- 结果文件默认仅操作者本人和管理员可下载

### 6.2 货物画像导出权限

- 可读 `product.template` 且具备货物画像导出动作权限的用户，可以发起 `product_profile` 导出
- 结果文件默认仅操作者本人和管理员可下载

### 6.3 原则

- 导出权限与导出结果阅读权限分开定义
- 不继续让用户通过 Odoo 原生 `group_allow_export` 间接控制业务化导出

## 7. 首轮实施顺序建议

### 阶段 1：客户画像导出首轮

目标：

- 先打通 `customer_profile + from_customer + CustomerProfile sheet`

原因：

- 用户痛点最直接
- 当前客户侧已经有统一对象 `res.partner`
- 不依赖尚未落地的客户商品关系表

### 阶段 2：货物画像导出首轮

目标：

- 打通 `product_profile + from_product + ProductProfile / ProductUnit`

原因：

- 底层商品主档和规格层已经存在
- 可以在不新建 `goods_profile` 表的情况下快速形成稳定导出

### 阶段 3：客户商品关系增强

目标：

- 新增 `logistics.customer.product.profile`
- 客户画像和货物画像两条导出线同时补 `CustomerProductRelation`

原因：

- 这是两条导出线的共同增强层
- 放到统一阶段做，能避免客户导出和货物导出各自发明一套“常用商品关系”

## 8. 风险与注意点

### 8.1 当前客户画像页面还有文案/乱码问题

- 这属于页面质量问题，不影响方案方向
- 但正式落地客户画像导出前，建议把页面基础可用性一起收口

### 8.2 任务头统计字段不具备扩展性

- 如果不补 `metrics_json`，客户画像和货物画像导出会在结果页统计层卡住
- 这是后续正式落库补丁稿必须优先处理的结构问题

### 8.3 货物画像的对象认知容易再次跑偏

- 用户表达可以保留“货物画像”
- 但开发实现不能重新滑回 `goods_line = 货物画像`

### 8.4 客户商品关系层目前还未落地

- 它是增强项，不应阻塞客户画像和货物画像首轮导出上线
- 但方案里必须提前为它留口，不然后续又会回到临时拼字段
