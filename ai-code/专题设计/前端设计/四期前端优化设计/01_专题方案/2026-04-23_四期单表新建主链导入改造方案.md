# 2026-04-23 四期单表新建主链导入改造方案

## 文档定位

- 本文用于收口四期标准主数据导入从“旧三 Sheet 补录模式”升级到“单表新建主链模式”的正式方案。
- 当前方案以数据库底表设计稿、现有 `logistics_dispatch` 数据模型、以及当前 `logistics_web` 导入任务链实现为共同基线。
- 本文优先解决两个核心问题：
  - 导入模板仍为三 Sheet，而业务需要单表导入；
  - 预校验错误地要求批次、波次、运单等业务对象预先存在，而业务需要通过导入直接创建新的主链对象。

## Outcome

- 标准主数据导入默认入口切换为单表导入。
- 标准主数据导入默认模式切换为“新建主链导入”，允许通过导入创建新的 `wave -> batch -> waybill -> customer_line -> goods_line`。
- 预校验从“系统已有数据存在性校验”改为“文件结构、业务一致性、可建档性校验”。
- 正式导入以 `task_no` 为唯一正式任务键，按创建计划执行 `wave / batch / waybill` 的查找或创建，并沉淀行结果与错误明细。
- 旧三 Sheet 补录模式保留为兼容入口，但不再是默认模板与默认流程。

## Behavior

### 1. 导入模式

- 标准导入首轮固定提供两种模式：
  - `create_dispatch_main`：新建主链导入，默认模式；
  - `legacy_patch`：旧三 Sheet 补录兼容模式。
- 导入中心默认下载与上传 `create_dispatch_main` 对应的单表模板。
- 旧三 Sheet 模板仍可保留下载入口，但降级为历史兼容，不再作为默认推荐。

### 2. 单表输入结构

- 单表只是输入入口，不改变系统内部正式结构。
- 单表导入后统一映射到：
  - `source_file -> import_task(dispatch_main) -> wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
- 单表每一行至少对应一条 `goods_line` 事实行。
- 同一 `waybill_no + customer_line_no + order_line_key` 下允许多条 `goods_line`。

### 3. 单表字段分层

#### 3.1 wave / batch / waybill 层

- `warehouse_code`
- `delivery_date`
- `wave_no`
- `batch_no`
- `waybill_no`
- `vehicle_no`
- `driver_name`
- `driver_phone`
- `remark`

#### 3.2 customer_line 层

- `customer_line_no`
- `customer_no`
- `customer_name`
- `store_no`
- `store_name`
- `delivery_remark`
- `signoff_requirement`
- `customer_ref`

#### 3.3 order_line 层

- 首轮不要求模板显式出单独订单区块。
- 兼容沿用当前实现的轻量订单聚合规则：
  - 默认以 `waybill_no + customer_line_no + source_doc_no/order_no/sales_order_no` 生成内存级 `order_line`
  - 若三类订单键均缺失，则允许降级使用 `waybill_no + customer_line_no + goods_row_no` 生成匿名订单快照
- 匿名订单仅用于首轮承接单表导入，不对外暴露为推荐业务建模方式。

#### 3.4 goods_line 层

- `goods_code`
- `goods_name`
- `spec`
- `qty`
- `package_count`
- `uom_name`
- `weight`
- `volume`
- `temperature_zone`
- `package_type`

### 4. 预校验规则重构

#### 4.1 预校验目标

- 预校验不再判断“系统里是否已经存在这条批次/波次/运单，若不存在则报错”。
- 预校验改为判断：
  - 模板结构是否合法；
  - 必填字段是否齐全；
  - 同文件内主键是否重复；
  - 跨行归并字段是否一致；
  - 目标对象是否具备创建条件；
  - 是否与系统中的既有正式对象发生不可接受冲突。

#### 4.2 系统级主数据与业务对象的边界

- 首轮仍要求系统中必须存在的主数据：
  - `warehouse`
- 首轮不要求预先存在，允许在正式导入中创建的业务对象：
  - `wave`
  - `batch`
  - `waybill`
- 首轮不作为强阻塞条件的对象：
  - `customer`
  - `store`
- `customer/store` 在导入时先以快照方式落到 `customer_line`，不强制要求已存在正式主数据档案。

#### 4.3 预校验失败的典型场景

- `warehouse_code` 不存在；
- `delivery_date / batch_no / waybill_no / goods_name / qty` 缺失；
- 同文件内同一 `waybill_no` 对应多个互相冲突的 `warehouse_code`、`delivery_date`；
- 同文件内同一 `batch_no` 对应多个互相冲突的 `wave_no` 或 `warehouse_code`；
- 同文件内同一 `waybill_no + customer_line_no` 对应多个冲突的门店快照字段；
- 同文件内同一 `waybill_no` 重复且不满足多行货物归并规则；
- `qty / weight / volume / package_count` 非法。

#### 4.4 与系统既有数据的冲突策略

- 首轮默认导入策略为 `create_only`。
- 当系统里已存在同号 `waybill_no` 时：
  - 预校验直接报冲突；
  - 不进入自动合并或覆盖。
- 当系统里已存在同号 `batch_no` 或 `wave_no` 时：
  - 若关键归属字段一致，则允许复用现有对象；
  - 若关键归属字段冲突，则预校验报错。
- 首轮不引入自动覆盖、自动补丁、自动合并的写入行为。

### 5. 正式导入执行顺序

1. 从 `import_source_file.storage_path` 重读原始单表文件。
2. 解析单表并归并出内存级创建计划：
   - `wave plan`
   - `batch plan`
   - `waybill plan`
   - `customer_line plan`
   - `order_line plan`
   - `goods_line plan`
3. 按仓库解析与校验结果执行 `find-or-create wave`。
4. 按 `batch_no` 与 `warehouse` 执行 `find-or-create batch`。
5. 按 `waybill_no` 执行 `create waybill`。
6. 按 `waybill_id + customer_line_no` 执行 `customer_line` 创建。
7. 按订单归并规则生成内存 `order_line`，并落地关联的 `goods_line`。
8. 将每个源行的执行结果写入 `import_task_line`。
9. 将字段级失败写入 `import_error_line`。

### 6. 结果页与人工复核承载

- 结果页需要明确显示：
  - 本次新建 `wave` 数；
  - 本次新建 `batch` 数；
  - 本次新建 `waybill` 数；
  - 复用已有 `wave/batch` 数；
  - 因既有 `waybill` 冲突而失败的行数。
- 预校验结果页与正式导入结果页均应支持人工复核“将创建哪些对象”，而不仅仅是“哪些字段报错”。
- 首轮不扩展新的人工审批状态，仍沿用既有 `import_task / import_task_line` 结果视图承接人工复核。

## Boundary

### 本轮纳入

- 单表模板替代默认三 Sheet 模板；
- `create_dispatch_main` 新建主链导入模式；
- 预校验从存在性校验改为可建档校验；
- 正式导入支持创建新的 `wave / batch / waybill`；
- `customer/store` 以快照方式承接，不再作为导入硬阻塞；
- 结果页补充新建/复用统计。

### 本轮不纳入

- 自动创建正式 `customer` / `store` 主数据；
- 已存在 `waybill` 的自动合并、覆盖、补丁模式；
- 图片包导入并入本次单表主链方案；
- 复杂的订单主对象正式落库重构；
- 多模板并行长期治理与历史模板迁移清理。

## Benchmark

### Odoo 原生可复用部分

- Odoo 原生适合承接：
  - 仓库主数据 `stock.warehouse`
  - 序列号生成
  - 附件与导入任务界面容器能力

### 当前项目需要自定义扩展部分

- `wave / batch / waybill` 是物流自定义主链对象；
- 单表导入映射、行归并、快照策略、冲突策略都属于项目自定义业务能力；
- 因此本次路径应为“扩展现有自定义导入能力”，而不是尝试回退到 Odoo 原生导入器。

## Current Understanding

- 当前实现仍为三 Sheet 模板，且解析与模板下载均写死在 `waybill_standard_import_service_v2.py`。
- 当前预校验要求 `batch/wave/customer/store` 先存在，只允许创建新的 `waybill`，不符合“通过导入新建主链”的业务目标。
- 当前任务链、结果页、错误明细链已经统一到 `task_no`，为本次重构提供了较好的落点。

## Development Plan

1. 新增单表模板版本，并将默认模板指向单表。
2. 将解析逻辑从三 Sheet 改为单表解析与内存聚合。
3. 重写预校验规则，移除“批次/波次不存在即失败”的旧逻辑。
4. 补充 `find-or-create wave / batch` 与 `create-only waybill` 的正式导入逻辑。
5. 补充预校验与结果页的创建计划摘要。
6. 保留旧三 Sheet 兼容入口，但从默认路径中降级。

## Risks

- 单表改造会同时影响模板下载、上传解析、预校验、正式导入、结果摘要，范围较大。
- `customer/store` 改为快照承接后，需要确认业务方是否接受“先导入执行单，再补正式主数据”的模式。
- 若历史前端仍强依赖三 Sheet 元数据返回，需要同步兼容处理。

## Next Suggestion

- 先按本文完成标准导入服务重构与兼容层保留。
- 待新建主链模式稳定后，再评估是否需要增加 `waybill merge` 或 `customer/store auto-create` 二期能力。
