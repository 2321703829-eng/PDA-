# 2026-04-20 四期前端优化设计总纲

## 文档定位

- 本文档是四期前端设计总入口。
- 自 2026-04-23 起，四期前端导入与对象设计统一以 `../02_跨模块规范/01_接口与数据/2026-04-21_四期数据库底表设计稿 v1（第二次修正版）.md` 为当前有效数据库基线。
- 本文档负责把页面、导入、对象、接口阅读口径同步到数据库设计，不再保留与底表稿冲突的旧判断。

## 一页结论

1. 四期当前有效主结构是 `wave -> batch -> waybill -> customer_line -> order_line -> goods_line`。
2. `waybill_no` 是正式运单业务唯一键；`waybill_group_no` 只作为导入控制字段，不替代正式运单键。
3. `customer_line_no` 是门店节点稳定业务键，但数据库唯一性口径是 `(waybill_id, customer_line_no)`，不是全局主键。
4. `order_line` 与 `customer_line` 的正式关联落在 `customer_line_id`，不是长期靠文本键串联。
5. `goods_line` 是 `order_line` 下的事实明细层，数据库允许 `1 order_line -> n goods_line`，四期不再保留“首轮强制 1:1”的判断。
6. 图片导入作为独立对象类型推进，当前数据库口径对应 `image_package`，与主数据导入 `dispatch_main` 分开。
7. 导入链需要统一纳入 `import_source_file / import_task / import_task_line / import_error_line` 审计模型。
8. 页面主阅读链仍可收口为 `waybill -> customer_line -> order_line`，但底层数据事实必须保留 `goods_line`。
9. 司机事实仍归 `batch`，`waybill.driver_employee_id` 只保留 related/store 型查询字段。
10. 四期设计重点已经从“是否分层”切到“字段如何落层、导入如何入库、结果如何审计”。

## 边界

### 四期覆盖

- 单表快捷导入
- 标准导入模板的兼容输入模式
- `waybill / customer_line / order_line / goods_line` 四层对象设计
- 图片导入、预览、导出
- 运单详情页、门店节点阅读区、订单阅读区
- 导入结果审计、错误反馈和接口影响面同步

### 四期不直接覆盖

- 完整重写 `wave / batch / waybill` 执行主线
- 历史全量迁移与账务口径回补
- 完整对象存储底座重构
- `trace / evidence / exception` 全量数据库定稿
- 企业分离、多租户等更高层架构话题

## 模块一：导入模块

### 当前结论

- 单表仍是业务用户的主入口。
- 现有标准导入模板可以作为兼容输入模式继续保留，但不再作为四期总契约主语。
- 单表必须先映射成内部四层对象，再进入统一校验、落库和任务审计。

### 当前导入主链

`source_file -> import_task(dispatch_main) -> waybill -> customer_line -> order_line -> goods_line`

### 当前聚合与写入口径

- 运单正式落库必须有 `waybill_no`
- `waybill_group_no` 只用于导入预分组、查重提示或辅助映射
- 门店节点优先使用导入值 `customer_line_no`
- 若未提供 `customer_line_no`，系统在已命中 `waybill_no` 前提下生成运单内唯一节点编号
- 订单键导入侧优先级为：
  - `source_doc_no`
  - `order_no`
  - `sales_order_no`
- 若 `source_doc_no` 为空，导入侧必须按 `order_no / sales_order_no` 做兜底校验，和数据库约束保持一致

### 当前导入审计口径

- 源文件进入 `import_source_file`
- 主数据导入任务对象类型使用 `dispatch_main`
- 图片包导入任务对象类型使用 `image_package`
- 任务状态统一使用：
  - `pending`
  - `running`
  - `success`
  - `partial_failed`
  - `failed`
  - `cancelled`

## 模块二：对象结构模块

### 当前主结构

`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`

### 各层职责

#### `waybill`

- 运单总容器
- 承接执行主链公共头字段
- 对门店节点、订单和图片结果做汇总阅读

#### `customer_line`

- 运单下的门店交付节点
- 承接门店快照、联系人、地址、经纬度、停靠顺序、签收要求
- 是图片包命中与门店阅读的核心对象

#### `order_line`

- 门店节点下的订单/单据快照层
- 承接订单键、单据属性、状态、业务员、部门、渠道、备注等字段
- 页面上承担订单级主阅读职责

#### `goods_line`

- 订单下的货物事实明细层
- 承接商品识别、规格、单位、数量、金额、重量、体积、行备注等字段
- 数据库允许一张订单下挂多条货物，不再按 1:1 假设设计

## 模块三：图片模块

### 当前结论

- 图片最小业务挂点仍是 `customer_line`
- 图片导入与主数据导入拆开推进
- 物理结构继续采用：
  - `waybill package`
  - `store package`
  - `image files`

### 当前图片主链

`import_task(image_package) -> waybill package -> store package -> customer_line -> images`

### 当前命中口径

- 优先使用 `customer_line_no`
- 否则使用 `waybill_no + store_no`
- 不按门店名称或地址猜测业务对象

## 模块四：页面与阅读链模块

### 当前主阅读链

`waybill -> customer_line -> order_line`

### 当前关键页面

- 运单详情页：总览容器和聚合页
- 门店节点阅读区：门店快照、图片入口、订单归属入口
- 订单阅读区：订单快照与货物明细主展示区

### 页面与数据库的一致性要求

- 页面主阅读层可不直接暴露 `goods_line` 作为一级入口
- 但订单阅读区展示的货物规格、数量、体积等信息必须可回溯到 `goods_line`
- 门店节点页展示的编号口径应与 `(waybill_id, customer_line_no)` 唯一规则兼容

## 模块五：后端与接口模块

### 当前结论

- 数据库是本轮对象边界的最终依据
- `customer_line_no` 是业务稳定键，但不是数据库主键
- `customer_line_id`、`order_line_id`、`goods_line.order_line_id` 这些 FK 才是正式关系骨架
- 接口设计需要同步导入任务、结果审计和错误行能力

### 当前需要同步的接口面

- 单表导入接口
- 运单详情接口
- 门店节点详情接口
- 图片导入/导出接口
- 导入任务查询与结果反馈接口

## 模块六：实施与联调模块

### 当前结论

- 四期已经进入“以数据库结构反推导入与页面”的实施阶段
- 本轮联调不再接受与底表稿相冲突的局部设计口径

### 当前实施顺序建议

1. 先锁数据库底表、唯一键、FK 和导入任务模型
2. 再锁单表映射规则与图片命中规则
3. 再锁接口请求体、响应体和错误反馈结构
4. 最后推进页面阅读链、结果页和验收

### 当前联调重点

- 单表能否稳定落成 `waybill -> customer_line -> order_line -> goods_line`
- `customer_line_no` 是否始终满足运单内唯一
- 同一订单下多货物是否能稳定入到 `goods_line`
- 图片包是否稳定命中 `customer_line`
- 导入结果是否能通过任务表和错误行对账

## 当前数据结构说明

### 主数据层

- 门店主数据：`res.partner`
- 门店配送画像：`logistics_store_profile`
- 商品主数据：`product.template`
- 商品销售单位：`logistics_product_unit`
- 司机画像：`hr.employee + logistics_driver_profile`
- 车辆画像：`fleet.vehicle + logistics_vehicle_profile`

### 业务层

- `wave`
- `batch`
- `waybill`
- `customer_line`
- `order_line`
- `goods_line`

### 导入审计层

- `import_source_file`
- `import_task`
- `import_task_line`
- `import_error_line`

### 核心关系

- `wave 1 -> n batch`
- `batch 1 -> n waybill`
- `waybill 1 -> n customer_line`
- `customer_line 1 -> n order_line`
- `order_line 1 -> n goods_line`

## 当前重要设计结论

1. `waybill_no` 是正式运单键，`waybill_group_no` 是导入控制字段。
2. `customer_line_no` 需要稳定保留，但数据库唯一性范围是运单内。
3. 页面主阅读链和数据库事实层不再强行做成同一层级。
4. 图片导入必须进入独立任务类型，不再混入主数据导入。
5. 司机事实仍归属于 `batch`，不再在 `waybill` 或 `customer_line` 形成第二套事实源。
6. 一单多货由数据库结构直接支持，前端和导入方案都要与此一致。

## 当前仍需继续收口的点

1. `customer_line_no` 是否在前端模板和阅读页中默认展示
2. 单表里司机电话、车辆号是否进入首轮字段池
3. 图片包首轮标准清单是否固定为 `manifest.xlsx`、`manifest.csv`，还是两者并存
4. 兼容输入模式下，现有标准导入模板入口是否继续对业务用户开放

## 风险提示

1. 如果继续把 `waybill_group_no` 当正式运单键使用，后续数据库、接口和导入审计会持续错位。
2. 如果继续把 `customer_line_no` 误写成全局主键，会和 `(waybill_id, customer_line_no)` 的数据库约束冲突。
3. 如果继续保留“1 order_line -> 1 goods_line”的设计假设，前端结果页和导入规则会和底表结构脱节。
4. 如果页面主阅读链直接替代数据库事实链，后续查询、导出和错误定位会越来越难做。

## Next Suggestion

四期后续所有设计和开发，统一按下面这句话推进：

**以数据库底表设计为准，导入正式落库按 `waybill -> customer_line -> order_line -> goods_line` 组织，`waybill_group_no` 只作导入控制，`customer_line_no` 只作运单内稳定业务键。**
