# 2026-04-30 三张导出表回导差距清单

适用范围：
- `专题设计/前端设计/五期前端优化设计/`
- 用于判断当前三张 `0429` 导出表是否已经具备“导出后可直接回导导入中心”的真实闭环能力

文档状态：
- `draft`
- 面向当前仓库实现状态
- 以 `logistics_web/services/phase5_0429_export_service.py` 与 `logistics_web/services/phase5_workbook_import_service.py` 为准

---

## 1. 结论先行

当前系统已经具备：

- 三张 `0429` 导出表可由五期导出接口正式导出
- 三张表对应的单表文件可进入五期导入中心做预校验与正式导入
- 部分关键字段已经形成“导出字段 -> 导入字段 -> 落库字段”的承接链路

当前系统还不具备：

- 三张导出表“无损回导”
- 回导后再导出仍与原导出文件逐列一致
- 所有导出字段都存在一一对应的持久化字段与导入写库逻辑

因此当前状态应定义为：

- **结构兼容**
- **部分字段可回导**
- **尚未形成真正的导出即回导闭环**

---

## 2. 分类口径

本清单将每一列分为四类：

- `已可回导`
  - 导出字段已有明确导入表头
  - 导入后已有稳定落库字段或可复用字段
  - 再导出时原则上可回出同口径内容

- `可导入但会丢信息`
  - 导入中心能识别该列所在文件
  - 但该列当前不会完整写入对应字段，或只部分写入
  - 再导出时可能为空、变成聚合值、或改走其他来源

- `当前完全未落库`
  - 当前导入逻辑没有承接该列
  - 数据上传后不会保存到稳定字段

- `需要补模型/补导入逻辑`
  - 若要实现真正闭环，需要新增字段、补导入逻辑，或同时补两者

### 3.1 已可回导

| 导出列 | 当前导入承接 | 当前落库位置 | 说明 |
|---|---|---|---|
| 批次号 | 用于查找/补挂运单批次 | `logistics.dispatch.waybill.batch_id` | 可作为主链定位信息参与回导 |
| 运单号 | 用于查找/创建运单 | `logistics.dispatch.waybill.name` | 主识别键之一 |

| 导出列 | 当前情况 | 丢失方式 |

| 排线序号 | 当前未写入稳定字段 |
| 司机姓名 | 当前未写入稳定字段 |
| 车牌号 | 当前未写入稳定字段 |

### 3.4 需要补模型/补导入逻辑

| 导出列 | 建议动作 |
|---|---|
| 收货地址 | 若要求订单详情回导后再导出一致，需明确是否落到 `order_line` 快照字段，或强制从 `customer_line` 读取并在导入时同步更新 |

| 司机姓名 | 建议补导入逻辑，明确写入 `waybill`、`batch`、司机档案关联或排线停靠点快照 |
| 车牌号 | 建议补导入逻辑，明确写入 `waybill`、`batch`、车辆档案关联或排线停靠点快照 |

## 7. 是否值得做成真正闭环

如果目标只是：

- 导出后允许人工修订少数字段
- 再把修订结果回导进系统
- 重点承接订单、门店、货物的展示快照

那么当前版本已经接近可用，只需要优先补：

1. 排线序号
2. 司机姓名
3. 车牌号
4. 门店不收货时间段

如果目标是：

- 三张导出表都能作为“标准回写模板”
- 回导后再导出与原模板逐列对齐
- 支持对账、复盘、二次编辑、再回写

那么还需要额外补强：

1. 排线字段稳定落库方案
2. 司机与车辆字段归属方案
3. 门店聚合字段的反写策略
4. 多 Sheet 同次导入能力
5. 导入后再导出的逐列回归测试

---

## 8. 当前建议

建议把闭环目标分成两档：

### A 档：轻闭环

目标：
- 允许三张表“能导、能改、能回”
- 接受少量字段丢失
- 优先服务业务操作

建议补：
- 排线序号
- 司机姓名
- 车牌号
- 不收货时间段

### B 档：强闭环

目标：
- 三张表成为正式往返模板
- 导出与回导完全按同口径运行

除 A 档外，还要补：
- 聚合字段反写规则
- 双 Sheet 回导能力
- 完整字段级回归用例

当前更适合先走 **A 档轻闭环**，因为改动范围更小，也更符合“五期先跑通、先补第一版必要字段”的原始策略。
