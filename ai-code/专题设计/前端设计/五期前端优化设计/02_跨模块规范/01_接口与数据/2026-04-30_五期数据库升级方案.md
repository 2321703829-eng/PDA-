# 2026-04-30 五期数据库升级方案

适用范围：
- `专题设计/前端设计/五期前端优化设计/` 当前五期导入导出改造的数据库升级说明
- 面向五期第一版字段补齐、导出字段承接、导入落库映射与升级执行

文档状态：
- `draft`
- 当前版本以第一版必须新增字段为主
- 不覆盖后续大规模主数据治理、历史全量修数或性能专项重构

---

## 1. 升级目标

本次五期数据库升级目标是：

1. 支撑 `0429` 三张导出表在系统内稳定取数与导出
2. 支撑五张导入表的第一版正式落库
3. 只补第一版真正必需的新字段，不做大而全扩表
4. 保持现有执行主链 `wave -> batch -> waybill -> customer_line -> order_line -> goods_line` 稳定不被打乱
5. 为后续后端导入接口、前端展示字段和联调验收提供统一数据库基线

本次升级不追求：

- 一次性补齐 `0427` 客户和商品样表的全部历史扩展字段
- 重做所有聚合逻辑的持久化结构
- 一次性完成历史数据全量回填
- 引入复杂中间表、任务中心或平台级迁移框架

## 3. 表与字段变更清单

本次变更以“第一版必须新增字段”优先，能复用现有字段的尽量复用，能聚合得到的字段不新增冗余落库。

### 3.1 `logistics.dispatch.waybill.order.line`

建议新增字段：

| 字段名 | 类型建议 | 说明 | 主要用途 |
|---|---|---|---|
| `whole_package_count` | `Integer` | 整件数 | `0429` 订单详情、门店详情导出 |
| `loose_package_count` | `Integer` | 散件数 | `0429` 订单详情、门店详情导出 |
| `gathering_location` | `Char(128)` | 集货位 | `0429` 订单详情、门店详情导出 |
| `salesperson_phone` | `Char(32)` | 业务员联系方式 | 三联单导出 |

说明：

- 以上字段均属于导出直接依赖字段
- 放在 `order_line` 上比放在 `waybill` 或 `customer_line` 上语义更稳
- `whole_package_count / loose_package_count` 为订单级聚合值，不建议直接挂在门店级模型上

### 3.2 `logistics.dispatch.waybill.customer.goods.line`

建议新增字段：

| 字段名 | 类型建议 | 说明 | 主要用途 |
|---|---|---|---|
| `delivery_qty_text` | `Char(64)` | 发货数量展示文本 | 三联单导出 |

说明：

- 该字段用于承接“发货数量”的最终展示口径
- 当前不强行把它等同于 `quantity / doc_qty / small_qty` 中任一字段
- 后续若口径冻结，可再决定是否改成计算字段或保留为快照文本

### 3.3 本次确认复用、不新增的字段

以下字段当前设计中已存在或已有近似承接，优先复用：

| 字段 | 当前承接位置 |
|---|---|
| `order_remark` | `logistics.dispatch.waybill.order.line` |
| `small_unit_name` | `logistics.dispatch.waybill.customer.goods.line` |
| `small_unit_price` | `logistics.dispatch.waybill.customer.goods.line` |
| `amount` | `logistics.dispatch.waybill.customer.goods.line` |
| `specification` | `logistics.dispatch.waybill.customer.goods.line` |
| `contact_name_snapshot` | `logistics.dispatch.waybill.customer.line` |
| `contact_phone_snapshot` | `logistics.dispatch.waybill.customer.line` |
| `address_full_snapshot` | `logistics.dispatch.waybill.customer.line` |
| `longitude_snapshot / latitude_snapshot` | `logistics.dispatch.waybill.customer.line` |

### 3.4 本次明确不新增冗余落库的字段

以下字段当前优先通过查询聚合或现有链路回读，不做门店级固定冗余字段：

- `总重量_kg`
- `总体积_m3`
- `整件数`
- `散件数`

说明：

- 门店详情导出时仍需要这些字段
- 但当前设计优先通过 `order_line` 聚合或 `customer_line` 现有汇总字段得到
- 暂不在 `customer_line` 额外新增一组冗余数字字段

## 4. 历史数据迁移/回填策略

### 4.1 总体原则

本次升级采取“结构先行、增量可用、历史谨慎回填”的策略：

1. 先完成字段新增与模块升级
2. 先保证新导入、新生成、新导出链路可用
3. 历史数据不做默认全量回填
4. 对确实影响业务使用的关键字段，再按专项脚本回补

### 4.2 各字段迁移建议

`whole_package_count / loose_package_count`

- 历史数据默认不回填
- 新导入数据优先从正式导入模板或脚本中写入
- 若老数据需要补导出，可后续基于订单明细或货物明细出专项聚合脚本

`gathering_location`

- 历史数据默认不回填
- 若已有脚本底表或外部排线结果中存在该值，优先由正式导入链补写
- 若历史导出必须使用，可接受为空，待业务补数据后重导

`salesperson_phone`

- 默认不批量硬回填
- 若 `res.partner`、员工档案或外部台账存在稳定来源，再单独做映射回填
- 在来源未稳定前允许为空

`delivery_qty_text`

- 历史数据默认不回填
- 新导入链按模板原始值写入
- 对老数据如需导出，可先按既有数量字段临时拼接作为兼容回退口径

### 4.3 回填触发条件

只有满足下列情况，才建议启动历史回填：

- 关键客户导出必须覆盖历史单据
- 字段来源已收口且稳定
- 有明确回填脚本、验证口径与回滚方案

## 5. 索引与约束策略

### 5.1 新增字段索引建议

第一版建议：

- `whole_package_count`：不建索引
- `loose_package_count`：不建索引
- `gathering_location`：如仅展示导出，不建索引；若后续列表筛选高频，再补普通索引
- `salesperson_phone`：不建索引
- `delivery_qty_text`：不建索引

原因：

- 当前这些字段主要用于导出与详情展示
- 暂未进入高频搜索主路径
- 先避免无效索引增加写入与维护成本

### 5.2 约束策略

当前不建议为五期新增字段增加复杂唯一约束。

建议仅保持：

- 非负数值字段约束继续由模型层或已有约束承接
- `whole_package_count / loose_package_count` 默认值建议为 `0`
- `gathering_location / salesperson_phone / delivery_qty_text` 允许为空

### 5.3 后续可扩展策略

如后续出现以下需求，再考虑补索引：

- 频繁按 `gathering_location` 检索
- 频繁按业务员联系方式反查订单
- `delivery_qty_text` 进入高频搜索或对账比对

## 6. Odoo 模块升级步骤

### 6.1 升级前准备

1. 确认当前目标库为五期联调或测试环境
2. 备份数据库
3. 备份 `filestore`
4. 记录当前模块版本与 git 提交状态

### 6.2 升级顺序

建议升级顺序：

1. `logistics_base`
2. `logistics_dispatch`
3. `logistics_web`

说明：

- 若本次只涉及 `logistics_dispatch` 与 `logistics_web`，`logistics_base` 可仅做依赖确认，不强制变更
- 先升模型层，再升接口层，最后联调前端

### 6.3 执行方式

推荐方式：

```powershell
odoo-bin -d <db_name> -u logistics_dispatch,logistics_web --stop-after-init
```

如本次涉及 `logistics_base`：

```powershell
odoo-bin -d <db_name> -u logistics_base,logistics_dispatch,logistics_web --stop-after-init
```

### 6.4 升级后动作

1. 重启 Odoo 服务
2. 打开后台模型页面验证字段是否已生成
3. 执行导出接口冒烟测试
4. 执行导入模板预校验测试
5. 再接前端联调

## 7. 回滚方案

### 7.1 回滚原则

本次升级优先采用“数据库备份回滚 + 代码回退”组合方案。

原因：

- 新增字段类升级可逆性虽高
- 但一旦正式导入写入了新字段数据，仅删字段并不能恢复业务状态

### 7.2 回滚场景

建议在以下场景触发回滚：

- 模块升级失败导致 Odoo 无法启动
- 导出服务大面积报错
- 正式导入把主链对象写坏
- 新增字段导致核心页面无法打开

### 7.3 回滚步骤

1. 停止 Odoo 服务
2. 回退本次代码提交
3. 恢复升级前数据库备份
4. 恢复对应 `filestore`
5. 重启 Odoo 服务
6. 验证旧版本主链、导入中心、导出入口恢复正常

### 7.4 不建议的回滚方式

不建议直接在线手工：

- 删除字段
- 改表结构
- 部分改回一半字段一半代码

原因：

- 容易造成 ORM 定义与真实表结构不一致
- 后续会增加二次故障排查成本

## 9. 当前结论

五期数据库升级当前应按“最小必要字段补齐”推进，而不是一次性大改数据结构。

当前最稳的推进方式是：

1. 先补第一版必需字段
2. 先保证三张 `0429` 导出表跑通
3. 再保证五张导入表第一版落库
4. 历史数据只做谨慎、可回退的专项回填
5. 在导入导出主链稳定后，再讨论更大范围的主数据深化与结构优化
