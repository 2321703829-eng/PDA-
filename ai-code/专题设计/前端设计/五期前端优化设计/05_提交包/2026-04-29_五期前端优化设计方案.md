# 五期前端优化设计方案

## 评审历史

- `2026-04-29` `V1.0` 初稿，依据 `0429会议纪要.docx`、`2026-04-29_五期三联单与导出需求草案.md`、五期样例模板与当前仓库实现状态整理形成。

## 需求理解

### 一、背景信息

- 专题名称：`五期前端优化设计`
- 当前阶段：`P1` 三张 `0429` 导出表先跑通，`P2` 五张导入表与前端字段补齐逐步接入
- 设计输入：
  - `专题设计/前端设计/五期前端优化设计/0429会议纪要.docx`
  - `专题设计/前端设计/五期前端优化设计/00_导航与总纲/2026-04-29_五期三联单与导出需求草案.md`
  - `专题设计/前端设计/五期前端优化设计/03_模板与样例/排线-订单详情_名创+遇见0429.xlsx`
  - `专题设计/前端设计/五期前端优化设计/03_模板与样例/排线-门店详情_名创+遇见0429.xlsx`
  - `专题设计/前端设计/五期前端优化设计/03_模板与样例/排线-门店货物信息三联单名创+遇见0429.xlsx`
  - `专题设计/前端设计/五期前端优化设计/03_模板与样例/客户信息完整版-齐速达修改0427.xlsx`
  - `专题设计/前端设计/五期前端优化设计/03_模板与样例/商品列表-齐速达修改0427.xlsx`
- 项目业务基线：
  - 执行与数据主链：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
  - 当前页面主阅读链：`waybill -> customer_line -> order_line`
  - 当前正式追溯主链：`waybill -> trace_event -> evidence -> exception`
- 本方案目标不是重做一套新后台，也不是一次性完成全量主数据治理，而是围绕五期最紧急的导入、导出、三联单与展示诉求，收口一条可运行、可验证、可继续补强的链路。

### 二、需求要点

- 五期当前主目标先聚焦 `0429` 三张导出表，确保系统能稳定导出排线订单详情、排线门店详情、排线门店货物信息三联单。
- `0427` 客户与商品两张表当前主要承担字段补齐和导入口径输入，不是本期最终客户交付导出物。
- 当前策略明确为：
  - 先定 `3` 张导出表字段映射
  - 再定 `5` 张导入表落库映射
  - 只补第一版必须新增字段
  - 先做后端导出接口
  - 再做后端导入接口
  - 最后接前端展示字段
- 门店详情中的 `整件数 / 散件数 / 总重量 / 总体积` 当前优先按订单或货物行聚合查询，不额外冗余新增门店级固定字段。
- `包装规格` 属于打印和阅读字段，按轻量文本承接，不承担系统计算逻辑。
- `业务员联系方式`、`订单备注`、`集货位`、`创建时间` 属于五期必须明确来源或预留入口的关键字段。
- 复杂、变化快、偏一次性的数据整理仍优先由脚本承接；后台系统负责稳定关系、标准接口、导出入口和可追溯落库。

## 实现方案

### 2.1 接口定义

本期接口仍遵守项目既有前缀规范：

- 后台：`/api/admin/logistics/...`

五期优先接口分两组。

第一组，导出接口：

- `GET /api/admin/logistics/exports/phase5-0429/order_detail/direct-download`
- `GET /api/admin/logistics/exports/phase5-0429/store_detail/direct-download`
- `GET /api/admin/logistics/exports/phase5-0429/store_goods_triplet/direct-download`

接口特点：

- 以 `delivery_date` 为主筛选条件，`batch_no` 为可选细化条件
- 返回目标模板文件，不要求前端二次拼装字段
- 字段值由服务端按固定优先级组装，不把底层表结构直接暴露给前端

第二组，导入接口：

- 主数据或主链正式导入仍复用现有导入中心模式：
  - 模板查询
  - 模板下载
  - 预校验
  - 正式确认导入
  - 任务结果
  - 行结果
  - 错误报告
- 五期导入对象建议收口为：
  - `customer_profile`
  - `product_profile`
  - `dispatch_main`
  - `route_planning`
  - 预留 `triplet_support` 或同类五期补充对象作为后续扩展位

本期不新增跨系统开放接口，不在五期内建设独立脚本服务平台。脚本与系统仍按“文件输入 / 文件输出 / 中间表回流”模式协同。

### 2.2 业务流程图

模块结构：

- 主数据与基础字段层：
  - `logistics_base`
- 执行主链层：
  - `logistics_dispatch`
- 前端接口与导出导入承接层：
  - `logistics_web`
- 追溯层：
  - `logistics_trace_core`
  - `logistics_trace_evidence`
  - `logistics_trace_exception`

五期核心业务流程：

1. 外部原始数据先经过脚本清洗、关联、排序与底表整理。
2. 系统按模板接收正式导入文件，先完成预校验，再写入主数据和主链对象。
3. 运单、门店节点、订单行、货物行在系统内形成稳定关联。
4. 五期导出服务按固定口径聚合三张 `0429` 目标表。
5. 前端在导入中心、导出入口或结果页承接操作与反馈。
6. 若最终客户版模板仍需格式微调，则由脚本做最后一层轻量包装。

三联单导出阅读流程：

1. 从 `delivery_date` 或 `batch_no` 进入导出范围。
2. 先命中 `waybill` 与 `route_planning.stop.line`。
3. 再分别关联 `customer_line`、`order_line`、`goods_line`。
4. 由导出服务按表级口径输出：
   - 订单视角表
   - 门店视角表
   - 商品行三联单视角表

### 2.3 配置变动表

- 导出配置：
  - 新增五期 `0429` 三张表的导出键与文件名映射
  - 统一导出权限组控制
- 导入配置：
  - 五期新增模板沿用“模板元信息 + 模板下载 + 任务化导入”模式
  - 模板版本号必须显式维护，避免同名文件下口径漂移
- 页面配置：
  - 导入中心继续作为正式上传入口
  - 导出入口应明确放在运单、批次或导出中心，不允许临时散落在多个页面

### 2.4 数据模型

#### 2.4.1 五期目标导出表字段映射

`排线-订单详情_0429`

- `批次号`：`waybill.batch_id.name`，若存在排线停靠草稿则优先 `stop_line.batch_no`
- `排线序号`：优先 `stop_line.stop_seq`，其次 `customer_line.stop_seq_in_waybill`，最后 `waybill.route_seq`
- `运单号`：`waybill.name`
- `销售订单号`：优先 `order_line.sales_order_no`，其次 `order_line.order_no`，最后 `order_line.source_doc_no`
- `客户名称`：优先 `customer_line.customer_name_snapshot`，再回落 `partner.name`
- `订单备注`：`order_line.order_remark`
- `收货地址`：优先 `customer_line.address_full_snapshot`，其次 `stop_line.address_detail`
- `整件数`：`order_line.whole_package_count`
- `散件数`：`order_line.loose_package_count`
- `总重量_kg`：`order_line.weight_summary`
- `总体积_m3`：`order_line.volume_summary`
- `集货位`：`order_line.gathering_location`
- `司机姓名`：优先 `stop_line.driver_name`，其次 `batch.driver_name_snapshot`，最后 `waybill.driver_employee_id.name`
- `车牌号`：优先 `stop_line.vehicle_no`，其次 `waybill.vehicle_id.license_plate`，最后 `batch.vehicle_id.license_plate`

`排线-门店详情_0429`

- `批次号 / 排线序号 / 运单号`：同上
- `客户名称`：`customer_line` 口径
- `收货地址`：`customer_line.address_full_snapshot`
- `联系人`：`customer_line.contact_name_snapshot`
- `联系电话`：优先 `customer_line.contact_phone_snapshot`，其次 `stop_line.contact_phone`
- `集货位`：门店下关联订单行的 `gathering_location` 去重拼接
- `不收货时间段`：优先 `store_profile.no_receive_time_slots_text`，其次 `partner.no_receive_time_slots_text`
- `门店备注`：当前按 `waybill.remark` 或 `waybill.delivery_remark_snapshot` 理解
- `整件数 / 散件数`：门店下关联订单行聚合
- `总重量_kg / 总体积_m3`：优先 `customer_line.total_weight / total_volume`
- `经度 / 纬度`：优先 `customer_line.longitude_snapshot / latitude_snapshot`，其次 `stop_line`
- `司机姓名 / 车牌号`：同上

`排线-门店货物信息三联单_0429`

- `批次号 / 排线序号 / 运单号`：同上
- `销售订单号`：订单口径
- `客户名称`：门店口径
- `行号`：`goods_line.sequence`
- `商品名称`：优先 `goods_line.goods_name`，其次 `goods_line.product_name_snapshot`
- `商品编号`：优先 `goods_line.goods_code`，其次 `goods_line.external_product_code_snapshot`
- `商品条码`：`goods_line.barcode_snapshot`
- `包装规格`：优先 `goods_line.specification`，其次 `goods_line.spec_snapshot`
- `发货数量`：`goods_line.delivery_qty_text`
- `小单位销售单位`：`goods_line.small_unit_name`
- `小单位销售单价`：`goods_line.small_unit_price`
- `金额`：`goods_line.amount`
- `收货地址 / 联系人 / 联系电话`：门店节点口径
- `业务员`：`order_line.salesperson_name_snapshot`
- `业务员联系方式`：`order_line.salesperson_phone`

#### 2.4.2 五期目标导入表落库映射

当前建议按五张导入表理解五期落库：

- `Waybill`
  - 主要落到 `logistics.dispatch.waybill`
  - 负责运单号、配送日期、波次、批次、仓库、司机、备注等主链字段
- `CustomerLine`
  - 主要落到 `logistics.dispatch.waybill.customer.line`
  - 负责门店节点、联系人、地址、经纬度、时窗、配送限制类快照字段
- `OrderLine`
  - 主要落到 `logistics.dispatch.waybill.order.line`
  - 负责订单号、单据来源、业务员、状态、订单备注及订单级聚合字段
- `GoodsLine`
  - 主要落到 `logistics.dispatch.waybill.customer.goods.line`
  - 负责商品快照、数量、单位、价格、金额、包装规格及商品行备注
- `RoutePlanning`
  - 主要落到 `logistics.route.planning.batch` 与 `logistics.route.planning.stop.line`
  - 负责批次排线序号、停靠顺序、地址、经纬度、司机车牌等草稿态排线数据

#### 2.4.3 第一版必须新增字段

第一版只补五期直接依赖字段，不做大而全扩展。

建议优先新增或确认存在的字段如下：

- `logistics.dispatch.waybill.order.line`
  - `whole_package_count`
  - `loose_package_count`
  - `gathering_location`
  - `salesperson_phone`
- `logistics.dispatch.waybill.customer.goods.line`
  - `delivery_qty_text`
- 必要时补齐或确认复用：
  - `order_remark`
  - `small_unit_name`
  - `small_unit_price`
  - `amount`
  - `specification`
  - `contact_name_snapshot`
  - `contact_phone_snapshot`
  - `no_receive_time_slots_text`

字段补齐原则：

- 能复用现有快照字段的不新增平行字段
- 能按查询聚合得到的不做门店级冗余落库
- 纯展示文本允许轻量落库
- 需要未来继续参与计算或联动的字段要放在语义正确的模型上

### 2.5 兼容性处理

本期兼容性主要关注四类问题：历史模板兼容、旧字段口径兼容、脚本协同兼容、现有导入中心兼容。

- 模板兼容：
  - 保留现有标准四 Sheet 导入链
  - 五期在此基础上补三联单相关字段与后续五表映射，不推翻旧模板入口
- 字段兼容：
  - `门店备注` 当前按 `运单备注` 理解
  - `客户名称 / 门店名称 / partner_name` 保持兼容快照读取，不强推一次性命名清洗
- 脚本兼容：
  - 脚本继续负责高变化逻辑与最后一层格式化
  - 后台不抢脚本该做的清洗、排序、对账生成职责
- 页面兼容：
  - 旧页面可以暂时保留
  - 新字段优先先接数据和接口，再决定是否在列表、详情或导出结果页展示

### 2.6 灰度放量设计

- 第一阶段：
  - 只开放三张 `0429` 导出接口
  - 使用样例数据回归字段顺序与口径
- 第二阶段：
  - 开放五张导入表的预校验与正式导入
  - 仅内部使用，不直接对外宣传全量能力
- 第三阶段：
  - 接前端导入导出入口
  - 逐步把新增字段展示到运单、门店节点、订单行、货物行页面

灰度准入条件：

- 三张导出表与样例字段顺序完全一致
- 第一版新增字段来源明确
- 导入失败可定位到具体行与字段

回滚触发条件：

- 导出字段口径错位，导致客户版模板不可用
- 导入把主链对象写错层级或错对象
- 前端展示导致旧页面读取异常或高频报错

### 2.7 代码 MR

五期改动建议围绕以下模块增量展开：

- `logistics_dispatch`
  - 运单、门店节点、订单行、货物行字段补齐
  - Odoo 详情页和列表页新增必要展示字段
- `logistics_web`
  - 五期 `0429` 导出服务
  - 五张导入表服务与控制器
  - 导入结果页、导出入口和错误反馈
- `logistics_base`
  - 客户、门店、商品主数据字段复用或轻量补充

## 可靠性评估

- 三张导出表的可靠性关键不在 Excel 生成本身，而在字段来源优先级是否稳定。
- 五张导入表的可靠性关键在于：
  - 主键是否明确
  - 写入顺序是否固定
  - 失败是否可回溯到具体行
- 第一版尽量避免跨模型双写和大规模回填，降低导入后修复成本。

## 安全性评估

- 导入导出仍走后台用户权限控制，不开放匿名入口。
- 导出接口必须受导出权限组控制。
- 导入确认动作必须保留任务审计和错误报告。
- 不在普通页面上直接暴露无约束的批量覆盖入口。

## 容量预估

- 三张导出表当前主要压力在聚合查询和 Excel 生成，属于可控范围。
- 五张导入表当前主要压力在预校验和批量写库，建议按任务化处理，不走前端长事务直写。
- 若后续文件量明显变大，再评估异步队列和更细粒度缓存。

## 自测方案

- 导出自测：
  - 对照三张 `0429` 样表逐列核对
  - 验证空值回退逻辑
  - 验证 `delivery_date + batch_no` 过滤逻辑
- 导入自测：
  - 模板下载是否正确
  - 预校验是否能指出字段缺失、格式错误、关联失败
  - 正式导入后是否能在对应模型查到新记录
- 页面自测：
  - 新增字段在目标详情页是否可见
  - 导入结果页统计是否正确

## 影响面与测试关注点

- `waybill` 详情页
- `customer_line` 详情页
- `order_line` 模型与兼容页
- `goods_line` 模型与导出读取
- 导入中心
- 导出入口
- 样表字段顺序、命名、单位与空值格式

## 发布计划

1. 先冻结三张导出表字段映射。
2. 再冻结五张导入表落库映射。
3. 先上线后端导出接口。
4. 再上线后端导入接口。
5. 最后接前端展示字段和入口按钮。

## 监控方案

- 重点监控导出失败率
- 重点监控导入预校验失败率和正式导入失败率
- 重点监控错误报告是否可下载
- 重点监控新增字段读取是否导致详情页报错

## 预估开发时间

- 字段映射收口：`0.5 ~ 1` 天
- 第一版字段补齐：`0.5 ~ 1` 天
- 后端导出接口：`1 ~ 2` 天
- 后端导入接口：`2 ~ 4` 天
- 前端入口与展示：`1 ~ 2` 天
- 联调与回归：`1 ~ 2` 天

## 数据修复【可选】

- 若历史订单行缺少 `整件数 / 散件数 / 集货位 / 业务员联系方式`，优先补导入与新数据链路，不强制先批量回填老数据。
- 若历史商品行缺少 `包装规格 / 发货数量展示文本`，优先保证新导出可用，再决定是否回补。
- 修复动作必须可重入、可留痕、可回退。

## 成本和收益

- 成本：
  - 需要补一批字段和导入导出服务
  - 需要维护脚本与后台双链路边界
- 收益：
  - 三张 `0429` 目标表能正式系统化导出
  - 五张导入表可逐步沉淀成标准入口
  - 三联单、排线、门店、商品、订单的字段关系被正式收口
  - 后续无论继续走脚本协同，还是把稳定能力沉回后台，都有一份统一基线可依
