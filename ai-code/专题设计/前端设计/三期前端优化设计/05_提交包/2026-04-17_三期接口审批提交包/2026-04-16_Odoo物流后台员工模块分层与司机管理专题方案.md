## Objective

在不推翻当前一期、二期业务主线的前提下，把现有“员工”相关能力从通用后台对象，升级成更贴合物流执行管理的对象体系。

这轮方案重点解决 4 个问题：

1. 当前系统里“后台工作人员”和“司机”在管理视角上不是同一种对象，但前端上还缺少清晰分层
2. 司机目前更像隐含在运单、批次执行链路中的关联人，缺少独立管理入口和独立画像页
3. 管理者无法快速判断某个司机近期跑得怎么样、风险高不高、最近关联了哪些运单和异常
4. 司机相关图表如果全部堆进全局统计页，会让统计中心和对象画像页的职责混乱

## 审批关注点



1. 后台工作人员管理与司机管理是否正式拆成两条对象线
2. 司机是否作为独立执行资源对象管理，而不再只是运单 / 批次上的隐含关联人
3. 司机详情页是否采用“画像式详情页”而不是普通员工详情页
4. 司机个人趋势图是否全部放入司机画像页，而不是继续堆进全局统计页
5. 本轮是否接受“暂不拆自有司机 / 外协司机，只保留是否自己有车字段”

## Boundary

本方案覆盖：

- 员工模块前端入口分层
- 后台工作人员管理与司机管理的对象边界
- 司机列表页
- 司机画像详情页
- 司机与车辆、运单、批次、异常、证据的前端关系表达
- 司机相关指标卡与个人趋势图

本方案不覆盖：

- 员工薪酬、考勤、排班等 HR 深水区能力
- 车队管理的完整独立专题
- 自有司机 / 外协司机的正式类型拆分
- 三期统计中心的全部图表方案
- 后端接口、SQL、权限实现细节

## Benchmark

本轮方案统一参考下面 4 条基准：

1. 当前项目业务主线基准  
   `wave -> batch -> waybill -> trace -> evidence -> exception`

2. 当前项目前端基准  
   一期已完成执行对象、追踪对象和异常对象的基础结构  
   二期已完成首页、统计入口、导入体验和部分阅读结构优化

3. Odoo 原生能力基准  
   Odoo 已提供 `hr.employee`、`contacts`、`fleet.vehicle` 等主数据基础，但未直接提供面向物流执行的“司机画像页”和“司机经营视角”

4. 当前三期业务目标基准  
   三期不是再做一轮通用员工台账，而是把司机作为物流执行资源对象单独经营和管理

## Odoo Baseline Comparison

### 1. Odoo 已有能力

- `hr.employee` 可以承载员工基础档案
- `contacts` 可以承载联系人基础资料
- `fleet.vehicle` 可以承载车辆基础资料
- Odoo 原生列表、表单、关系字段、菜单、动作、权限分层可直接复用

### 2. 当前项目仍然缺少的部分

- 缺少独立的司机管理入口
- 缺少司机列表页与司机画像详情页
- 缺少基于物流执行链路的司机指标与趋势区
- 缺少把司机与运单、批次、异常、证据统一串起来的前端对象页

### 3. 设计路径判断

- 后台工作人员管理：`extend Odoo`
- 司机基础档案：`extend Odoo`
- 司机画像详情页与司机经营视角：`create custom capability`
- 司机与车辆、运单、批次、异常联动：`extend Odoo + custom capability`

## Current Understanding

### 1. 当前系统在一期、二期完成后的现状

- 系统主线已经围绕运单、批次、留痕、证据、异常建立起来
- 二期已开始强调首页、统计、导入和对象阅读体验
- 但人员对象仍然没有形成与物流执行强绑定的专题设计

### 2. 当前真正缺的不是“再建一个员工列表”

- 后台工作人员更偏组织管理对象
- 司机更偏执行资源对象
- 两者可以共享部分基础主数据，但前端管理视角不能混为同一套普通员工页

### 3. 当前司机对象最缺的能力

- 没有独立列表入口
- 没有画像式详情页
- 没有司机风险和执行表现的摘要卡
- 没有司机个人趋势图区
- 没有把最近运单和最近异常自然挂到司机页上

### 4. 当前已冻结的关键结论

1. 司机页要支持“画像式详情页”
2. 全局统计页只保留 `司机月均异常率排行图`
3. 司机个人趋势图统一放进司机画像详情页
4. 司机管理暂时不区分“自有司机 / 外协司机”
5. 司机仍需保留“是否自己有车”字段
6. 司机详情页第一页统一命名为 `概览`
7. 司机详情页第一版关联记录区先放 `最近运单 + 最近异常`

## Outcome

如果本轮方案后续按阶段执行，目标状态应是：

1. 员工相关入口被明确拆成“后台工作人员管理”和“司机管理”两条线
2. 司机成为系统中的独立管理对象，而不是只隐含在运单或批次关联字段里
3. 管理者进入司机详情页后，可以快速看懂司机是谁、最近跑得怎么样、风险高不高
4. 司机相关趋势图、指标卡、最近运单和最近异常可以在同一页连续阅读和下钻
5. 全局统计页和司机画像页职责清晰，避免一处做全局排行、一处又重复堆同类图表

## Information Architecture

### 1. 专题结构总览

```text
员工模块
├─ 后台工作人员管理
│  ├─ 工作人员列表
│  └─ 工作人员详情（本轮不展开重度画像）
└─ 司机管理
   ├─ 司机列表
   └─ 司机画像详情页
      ├─ 概览
      ├─ 指标卡
      ├─ 个人趋势图
      ├─ 执行概览
      ├─ 风险与异常
      └─ 最近运单 / 最近异常
```

### 2. 关键页面关系

- 司机列表 -> 司机画像详情页
- 全局统计页中的 `司机月均异常率排行图` -> 司机画像详情页
- 司机画像详情页指标卡 -> 对应运单列表 / 异常列表 / 缺证据列表
- 司机画像详情页趋势图 -> 按时间过滤后的关联列表

### 3. 当前结构判断

- 后台工作人员管理是组织对象入口
- 司机管理是执行资源对象入口
- 两者可以在导航上并列，但页面心智不能混用

## Object Boundary

### 1. 后台工作人员管理

建议定位为：

- 面向内部组织的后台工作人员档案入口
- 以基础身份信息、岗位信息、组织归属为主
- 不承担物流执行绩效画像的主体职责

### 2. 司机管理

建议定位为：

- 面向物流执行侧的司机资源管理入口
- 重点承载司机档案、车辆关系、执行表现、风险表现和关联业务对象
- 它不是普通员工详情页，而是“司机经营画像页”的入口

### 3. 当前不做的对象拆分

- 当前不正式拆 `自有司机 / 外协司机` 两类对象
- 当前先用统一司机对象承载，保留 `是否自己有车` 字段
- 如果后续业务需要，再在三期后半段补“司机类型”维度

## Page Design

### 1. 司机列表页

司机列表页第一版建议至少展示下面这些字段：

- 司机姓名
- 联系方式
- 所属车辆
- 当前状态
- 最近执行时间
- 关联运单数
- 月均异常率

说明：

- `所属车辆` 是当前已确认需要显性展示的字段
- 列表页中的车辆信息先以“当前所属车辆”为主，不展开历史车辆关系
- 月均异常率是列表页最值得保留的风险信号

### 2. 司机画像详情页

司机详情页第一页统一命名为 `概览`。

第一版页面结构固定为 6 个区块：

1. 顶部对象头
2. 核心指标带
3. 个人趋势图区
4. 执行概览区
5. 风险与异常区
6. 关联记录区

### 3. 顶部对象头

建议展示：

- 司机姓名
- 联系方式
- 当前状态
- 所属车辆
- 是否自己有车
- 最近执行时间
- 备注信息

建议动作：

- 查看关联运单
- 查看关联异常
- 返回司机列表

### 4. 核心指标带

第一版建议放下面 6 个指标卡：

1. 本月运单量
2. 月均异常率
3. 当前月签收率
4. 当前月超时率
5. 缺证据率
6. 关联异常数

要求：

- 每张卡都支持下钻
- 指标卡优先承担快速判断，不承担复杂解释

### 5. 个人趋势图区

司机画像详情页第一版固定 3 张图：

1. `司机月度运单量趋势图`
2. `司机异常率趋势图`
3. `司机签收率 + 超时率双指标趋势图`

设计结论：

- 这 3 张图不再放入全局统计图表页
- 它们属于单司机纵向画像，不属于全局横向比较

### 6. 执行概览区

建议展示：

- 关联批次数
- 关联运单总数
- 最近 30 天运单数
- 最近 30 天批次数
- 最近服务门店数
- 最近服务地区数

补充摘要：

- 主要服务地区 Top 3
- 主要服务门店 Top 3
- 最近使用车辆信息

### 7. 风险与异常区

建议拆成 3 小块：

1. 风险摘要  
   异常运单数、严重异常数、超时运单数、缺证据运单数

2. 异常类型摘要  
   优先展示高频异常类型列表或轻量分布

3. 最近异常记录  
   展示异常编号、运单号、异常类型、状态、上报时间、跳转按钮

### 8. 关联记录区

第一版确认：

- `最近运单 + 最近异常` 一起放

最近运单建议字段：

- 运单号
- 门店
- 门店地区
- 状态
- 配送日期
- 是否超时
- 是否缺证据

最近异常建议字段：

- 异常编号
- 运单号
- 类型
- 状态
- 上报时间

当前取舍：

- 批次列表可作为后续增强项
- 第一版优先保证“用户看完画像后，能继续看最近具体对象”

## Vehicle Relation

### 1. 列表页表达

- 仅显示当前所属车辆

### 2. 详情页表达

- 显示当前所属车辆
- 显示最近使用车辆
- 多车辆历史关系暂不作为第一版重点展开

### 3. 设计原则

- 司机页需要看见车辆，但不能被拖成完整车队管理页
- 车辆信息服务于“判断这个司机当前执行资源状态”，不是服务于车辆台账本身

## Metrics And Charts

### 1. 全局统计页中的司机图

全局统计页当前只保留：

- `司机月均异常率排行图`

它承担的职责是：

- 从全局视角发现高风险司机
- 作为跳转到司机画像页的入口

### 2. 司机画像页中的司机图

司机画像页承接单司机纵向趋势：

- 司机月度运单量趋势图
- 司机异常率趋势图
- 司机签收率 + 超时率双指标趋势图

### 3. 指标口径依赖

司机页中的指标和图表，后续统一依赖：

- `按执行归属统计司机`
- `超时按超过承诺时效仍未签收判断`
- `缺证据统一包含 missing + partial`

具体口径以后续指标字典和接口设计为准。

- 后台接口前缀继续建议使用：`/api/admin/logistics/...`

## Risks

### 1. 对象边界风险

如果把后台工作人员和司机重新混回一个普通员工列表，三期专题价值会明显下降。

### 2. 页面过重风险

如果在司机详情页一次性塞入过多图表、批次表、车辆历史和复杂筛选，第一页会很重。

### 3. 口径漂移风险

司机异常率、签收率、超时率、缺证据率如果不与统计指标字典保持一致，后续会出现“司机页和统计页数据说法不一致”。

### 4. 车辆关系误判风险

如果把司机与车辆关系做成过强绑定，容易误导成“一个司机永远只对应一辆车”。第一版应只强调当前所属车辆和最近使用车辆。
