适用范围：

- 当前只覆盖后台 `admin` 场景

## 1. 文档定位

这份文档用于把三期承接的二期收尾项，进一步收口成一份可直接开发的接口补充说明。

它重点回答 5 个问题：

1. 二期导入结果相关接口当前到底落在哪些真实路径和文件上
2. 三期要做“导入结果详情 / 回看页”，应复用哪一口，哪些字段需要补
3. 二期存量导入接口和三期新增接口，在命名与口径上应该怎样统一
4. 哪些改动属于最小扩字段，哪些不应误判成重开一套导入中心体系
5. 前后端各自应按什么粒度拆任务

---

## 2. Objective

在不打乱三期三条主线的前提下，把可承接的二期接口收尾项收口为下面 3 件事：

1. 让导入结果页从“导入中心页内结果区”进一步升级成可直接回看、可继续跳转的结果详情页
2. 让二期已落地的导入接口命名、路径和三期新增接口文档之间不再出现两套平行口径
3. 让后续开发优先走“复用现有路由 + 最小扩字段”，而不是重新搭第二套导入结果体系

---

## 3. Boundary

本说明覆盖：

- 运单标准导入 `V2 XLSX` 结果读取与结果页页面化
- 导入结果接口扩字段建议
- 导入域与三期其他接口域的命名/口径统一
- 当前真实代码文件与推荐落点映射

本说明不覆盖：

- 非运单对象的导入中心化扩建
- 独立客户明细 / 货物明细模板
- 固定需求 + 临时需求体系
- 导入历史列表页、导入审计中心、导入权限重构
- 全量重写导入中心前端

---

## 4. Current Understanding

### 4.1 当前真实实现基线

当前仓库里，运单标准导入主路径已经真实落在下面这些路由上：

- `GET /api/admin/logistics/imports/waybill-standard/template`
- `GET /api/admin/logistics/imports/waybill-standard/template/download`
- `POST /api/admin/logistics/imports/waybill-standard/precheck`
- `POST /api/admin/logistics/imports/waybill-standard/confirm`
- `GET /api/admin/logistics/imports/waybill-standard/result`
- `GET /api/admin/logistics/imports/waybill-standard/error-report`

当前主要实现文件：

- controller：`custom_addons/logistics_web/controllers/logistics_web_import_v3.py`
- service：`custom_addons/logistics_web/services/waybill_standard_import_service_v2.py`
- batch model：`custom_addons/logistics_dispatch/models/logistics_import_batch.py`
- frontend action：`custom_addons/logistics_web/static/src/js/actions/import_center_action.js`

### 4.2 当前结果页的真实状态

当前已完成：

- 结果统计展示
- 结果查询接口
- 错误报告下载
- 从导入中心继续跳运单列表

当前未完成：

- 独立结果详情页
- 更完整的结果回看页
- 结果信息的区块化页面化组织

结论：

- 当前“结果能力”已经存在
- 当前缺的是“页面化收口”和“最小扩字段”，不是第二套导入结果接口

### 4.3 当前接口口径冲突点

当前二期与三期文档并存时，容易出现下面 3 类冲突：

1. 路由和方法都存在，但文档里一个偏“理想命名”，一个偏“真实实现命名”
2. 三期 driver/stats 文档更偏新增专题接口，而导入域仍沿用二期主路径
3. 三期有些 JSON 示例写 `code: "OK"`，而导入中心当前真实 controller 使用 `code: 0/1`

本文件的处理原则是：

- 先保证当前真实导入链路可继续开发
- 当前不强行回写整个三期所有接口的成功码风格
- 只固定“导入域继续沿用现有 controller 返回口径”

## 5. 统一口径结论

## 5.1 路由口径

导入域继续固定使用：

- `/api/admin/logistics/imports/waybill-standard/...`

不建议为了文档整齐把它改写成：

- `/api/admin/logistics/import-results/...`
- `/api/admin/logistics/imports/results/...`

原因：

- 当前前端与服务层已经接线
- 当前下载地址、错误报告地址和模板入口都已经依赖这条主路径
- 三期承接的是收尾项，不是导入中心重构项目

## 5.2 方法命名口径

文档层统一使用下面映射：

| 文档名 | 当前真实职责 | 当前真实路径 |
| --- | --- | --- |
| `downloadWaybillStandardTemplate` | 模板元信息读取 + 文件下载 | `template` / `template/download` |
| `precheckWaybillStandardImport` | 上传与预校验 | `precheck` |
| `confirmWaybillStandardImport` | 正式导入 | `confirm` |
| `getWaybillImportResult` | 导入结果读取 | `result` |
| `downloadWaybillImportErrorReport` | 错误报告下载 | `error-report` |

说明：

- `downloadWaybillStandardTemplate` 在实现上分成“模板元信息”和“模板文件流”两口，这是当前接受的实现方式
- 三期不需要为文档统一再把它们压成一口

## 5.3 返回包络口径

当前导入域真实 controller 继续固定为：

```json
{
  "code": 0,
  "message": "成功",
  "data": {},
  "request_id": "req_xxx"
}
```

失败时：

```json
{
  "code": 1,
  "message": "失败提示",
  "data": {
    "errors": []
  },
  "request_id": "req_xxx"
}
```

结论：

- 当前导入域继续沿用 `0/1`
- 三期 driver/stats 文档中的字符串型 `OK` 不在本文件强制改写
- 若后续要统一全局成功码风格，应走“前端 service 适配层统一”而不是先改导入主路径

## 6. 导入结果页页面化补充

## 6.1 页面定位

三期承接后的结果页建议统一定位为：

- 导入完成后的结果详情 / 回看页
- 不是新的导入入口页
- 不是完整导入历史中心

它需要回答：

1. 这次导入的是哪一批
2. 当前状态是什么
3. 成功写入了多少数据
4. 如果失败或部分失败，问题在哪里
5. 下一步应该跳去哪里核验

## 6.2 页面结构建议

第一版建议固定为 4 个区块：

1. 顶部结果头
2. 结果摘要卡
3. 文件与批次信息区
4. 后续动作区

如当前批次存在失败信息，可追加：

5. 失败说明 / 错误报告区

## 6.3 页面动作建议

第一版固定保留下面动作：

- `刷新结果`
- `下载错误报告`
- `进入运单列表`
- `按导入批次继续核验`

当前不建议第一版强制加入：

- 重新导入
- 克隆上次导入配置
- 导入历史列表跳转
- 逐条结果明细页

## 7. 结果接口补充策略

## 7.1 核心结论

导入结果页页面化优先采用：

**扩现有 `getWaybillImportResult` 返回结构**

不建议新增：

- `getWaybillImportResultDetail`
- `getWaybillImportResultReview`
- `getImportBatchDetail`

原因：

- 当前结果页仍然只围绕单个 `import_batch_no`
- `logistics.import.batch` 已经有足够多的基础字段可直接支撑第一版页面化
- 新开接口只会让导入域再次出现两套路由和平行 DTO

## 7.2 当前已存在的可复用字段

来自 `logistics.import.batch` 或当前 service payload 的可复用字段包括：

- `import_batch_no`
- `status`
- `status_label`
- `template_code`
- `template_version`
- `file_name`
- `total_row_count`
- `passed_row_count`
- `failed_row_count`
- `created_waybill_count`
- `created_customer_line_count`
- `created_goods_line_count`
- `updated_record_count`
- `skipped_record_count`
- `failed_record_count`
- `error_report_url`
- `failure_reason`
- `confirmed_at`
- `finished_at`

当前实现里，`getWaybillImportResult` 已返回的是：

- `import_batch_no`
- `status`
- `status_label`
- `created_waybill_count`
- `created_customer_line_count`
- `created_goods_line_count`
- `updated_record_count`
- `skipped_record_count`
- `failed_record_count`
- `error_report_url`
- `failure_reason`

因此三期第一版只需要在现有结果接口上补回：

- `template_code`
- `template_version`
- `file_name`
- `total_row_count`
- `passed_row_count`
- `failed_row_count`
- `confirmed_at`
- `finished_at`

## 7.3 建议请求参数

`GET /api/admin/logistics/imports/waybill-standard/result`

基础入参：

- `import_batch_no`

可选扩展入参：

- `include`

当前建议支持的 `include` 值：

- `basic`
- `summary`
- `errors`

说明：

- 第一版即使不做 `include` 分片，也可以直接返回完整结构
- 如果后续考虑结果页加载性能，再补 `include`，当前不要提前复杂化

## 7.4 建议返回结构

```json
  "message": "成功",

    "template_version": "v2",
    "file_name": "TSL-IMPORT-WAYBILL-V2.zh_CN.xlsx",
    "confirmed_at": "2026-04-17 11:20:00",
    "finished_at": "2026-04-17 11:20:08",
    "total_row_count": 12,
    "passed_row_count": 12,
    "failed_row_count": 0,
    "created_waybill_count": 2,
    "created_customer_line_count": 4,
    "created_goods_line_count": 6,
    "updated_record_count": 0,

```

## 7.5 错误与失败场景

当批次失败时，建议继续复用同一路由返回：

- `status = failed`
- `failure_reason`
- `failed_record_count`
- 如存在预校验错误或错误报告，则保留 `error_report_url`

当批次不存在时：

- 继续返回当前 `IMPORT_RESULT_NOT_FOUND`
- 不建议为结果页单独新开一组错误码

## 9. 前后端任务拆分建议

## 9.1 后端任务包

1. 补 `getWaybillImportResult` 扩字段
2. 保持 `error-report` 下载兼容
3. 清理导入域中与当前主路径直接相关的旧兼容分支

## 9.2 前端任务包

1. 结果详情 / 回看页页面结构落地
2. 导入中心到结果页的跳转与回跳
3. 结果页动作区接线

## 9.3 联调任务包

1. 成功批次回看联调
2. 失败批次回看联调
3. 错误报告下载回归
4. 进入运单列表后的结果核验回归

---

## 10. 当前不建议做的事

下面这些当前不建议借“结果页页面化”顺手扩进去：

- 导入历史批次列表页
- 逐行导入结果明细页
- 非运单对象导入结果统一中心
- 固定需求 / 临时需求导入联动
- 客户明细 / 货物明细独立模板分叉

原因：

- 这些会把当前收尾项重新拉成一条新主线
- 与“三期只承接小范围二期收尾项”的边界冲突
