## 1. 文档定位

这份文档不是再解释“页面想看什么”，而是把前端真正要消费的数据结构收口成可开发的字段级契约。

它主要解决 4 个问题：

1. 每个接口到底服务哪一页
2. 接口最少需要返回哪些字段
3. 哪些字段必须稳定存在，哪些允许为空
4. 分页、排序、筛选、错误返回要按什么口径统一

---

## 2. 当前契约原则

### 2.1 主对象口径

- 执行主线：`wave -> batch -> waybill -> waybill_order_line`
- 追溯主线：`waybill -> trace_event -> evidence -> exception`
- 订单不是留痕主对象
- 证据默认挂在留痕事件下，通过留痕事件反查运单、批次

### 2.2 接口路线口径

- 标准后台列表、详情、搜索优先走 `Odoo RPC`
- 聚合看板、复杂摘要、证据预览允许走自定义 `JSON controller`
- 前端页面层不要自行拼装“关键状态摘要”，优先消费后端已经聚合好的字段

### 2.3 字段命名口径

- 统一使用 `snake_case`
- 文案类字段和编码类字段分开
- 摘要字段要显式命名为 `*_label`、`*_summary`、`*_count`
- 时间字段统一使用 `*_at`
- 布尔字段统一使用 `is_*` / `has_*`

## 3. 通用请求与返回规范

## 3.1 通用分页参数

所有列表类接口统一支持：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `page` | integer | 否 | 页码，从 `1` 开始，默认 `1` |
| `page_size` | integer | 否 | 每页条数，默认 `20`，最大建议 `100` |
| `order_by` | string | 否 | 排序字段，如 `updated_at desc` |
| `keyword` | string | 否 | 主搜索关键字 |

## 3.2 通用列表返回

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0,
  "has_more": false
}
```

说明：
- `items` 必须始终返回数组
- 即使无结果，也不要返回 `null`
- `total` 必须返回，便于分页器稳定显示

## 3.3 通用错误返回

```json
{
  "code": "WAYBILL_NOT_FOUND",
  "message": "运单不存在或当前用户无权查看",
  "details": null
}
```

说明：
- `code` 给程序判断
- `message` 给页面提示
- `details` 可选

## 8. 前端开发使用建议

前端现在可以按下面的方式用这份文档：

1. 先用本文件锁定页面的核心数据结构
2. 再按 `接口路线决策文档` 判断该页走 RPC 还是 controller
3. 如果某页缺少字段，不先在页面层硬拼，先回补到这里
4. 后续如果要写接口样例响应，可以在本文件基础上追加“示例 payload”章节
