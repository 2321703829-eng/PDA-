## 1. 文档目标

这份文档用于正式回答一个此前没有收口的问题：

**前端页面的数据，到底主要通过哪条接口路线获取。**

需要解决的不是“有没有办法取到数据”，而是：
- 主路线是什么
- 哪些场景允许例外
- 哪些场景不能混用
- 后续前后端应该按什么方式协作

---

## 2. 候选路线

当前项目里实际上存在 3 条可选路线：

### 2.1 路线 A：以 Odoo RPC 为主

典型方式：
- `search_read`
- `read`
- `name_search`
- `call_kw`
- 模型方法返回结构化数据

优点：
- 和 Odoo 权限体系天然一致
- 适合后台列表、表单、搜索视图
- 实现快，和原生视图契合

问题：
- 前端自定义交互复杂时，返回结构不够稳定
- 聚合接口会越来越像“伪 API”
- 控制返回字段和版本演进不够优雅

### 2.2 路线 B：以自定义 REST controller 为主

典型方式：
- `/api/logistics/waybills`
- `/api/logistics/exceptions`
- `/api/logistics/dashboard/summary`

优点：
- 接口契约清晰
- 适合自定义页面和工作台
- 更适合做聚合接口和证据接口

问题：
- 需要单独处理权限、上下文、错误结构
- 如果后台大部分页面仍是原生视图，会形成两套取数方式

### 2.3 路线 C：混合路线

典型方式：
- 标准后台 CRUD 用 RPC
- 聚合、工作台、证据等用 REST

优点：
- 兼顾原生 Odoo 与增强页面

问题：
- 如果边界不清，很容易失控
- 最忌讳“想到哪用哪”

---

## 3. 当前决策

### 3.1 正式结论

当前项目推荐采用：

**路线 C，但必须是“以 Odoo RPC 为主、以少量定制 JSON controller 为补充”的受控混合路线。**

换句话说：
- 主路线：`Odoo RPC`
- 例外路线：`定制 JSON / REST controller`

这不是“双主路线”，而是：

**一条主路 + 一条有边界的例外通道。**

---

## 4. 为什么这样选

### 4.1 不能纯走 RPC

因为你现在的页面并不全是标准表单页。

这些页面或区块，如果全靠 RPC 临时拼模型方法，后面会越来越难维护：
- 工作台卡片
- 证据查看区
- 证据大图预览
- 留痕时间线增强版
- 老板页摘要聚合

### 4.2 也不适合全走 REST

因为你现在大量页面仍然是 Odoo 后台语义：
- 列表页
- 搜索视图
- form 详情页
- smart button 跳转
- act_window 上下文

如果这些全走 REST，相当于主动放弃 Odoo 原生能力，成本反而更高。

### 4.3 所以最合理的是受控混合

即：
- 能用原生视图和模型方法承接的，优先走 RPC
- 只有当页面明显超出原生阅读能力时，才开 controller

---

## 5. 主路线边界

## 5.1 必须优先走 Odoo RPC 的场景

以下场景默认不得优先上 REST：

1. 运单追溯列表页
2. 当前异常列表页
3. 批次追溯列表页
4. 基础 form 详情页
5. 配置页
6. 搜索建议中的标准对象搜索

推荐能力：
- `search_read`
- `read`
- `name_search`
- 模型层封装轻量聚合字段

### 原因

这些页面本质上仍是 Odoo 标准后台页面。

如果这里不用 RPC，会失去：
- 原生权限控制优势
- 上下文传参优势
- act_window / search view 的自然配合

## 5.2 允许走自定义 controller 的场景

以下场景可以作为受控例外：

1. 工作台总览聚合接口
2. 老板页摘要聚合接口
3. 证据预览 / 大图 / 元数据接口
4. 时间线增强读取接口
5. 复杂跨模型统计接口

推荐方式：
- `/api/logistics/dashboard/*`
- `/api/logistics/evidence/*`
- `/api/logistics/traces/*`

### 原因

这些场景的共同点是：
- 结构不是单一模型记录
- 前端需要稳定的聚合返回
- RPC 做起来会越来越像“假装不是 API 的 API”

## 6. 页面级接口路线表

| 页面 / 区块 | 推荐路线 | 说明 |
|---|---|---|
| 运单追溯列表页 | RPC | 标准列表页，优先 `search_read` + 聚合字段 |
| 运单详情页主体 | RPC | form 主体适合 RPC |
| 留痕时间线简版 | RPC | 一期简版可用模型方法或 one2many |
| 留痕时间线增强版 | Controller | 若做卡片化阅读和复杂筛选，建议单独接口 |
| 证据查看区简版 | RPC | 一期可读元数据和关系 |
| 证据预览 / 大图 / 切换 | Controller | 更适合稳定的 JSON 返回 |
| 当前异常列表页 | RPC | 标准列表页 |
| 异常详情页主体 | RPC | form 主体适合 RPC |
| 异常详情关键证据链 | Controller 或 RPC 模型方法 | 取决于是否做增强版 |
| 批次追溯列表页 | RPC | 标准列表页 |
| 批次详情页 | RPC | 中枢页可先走原生 |
| 管理工作台简版 | Controller | 聚合卡片和优先队列更适合单独接口 |
| 老板追溯查看页简版 | Controller | 摘要式页面更适合单独接口 |
| 配置页 | RPC | 纯后台配置页 |

## 7. 当前推荐的技术边界

### 7.1 RPC 负责什么

RPC 负责：
- 标准对象的增删改查
- 列表和详情主数据
- 搜索、筛选、分页、排序
- act_window 进入的标准后台页面

### 7.2 Controller 负责什么

Controller 负责：
- 跨模型聚合
- 卡片总览
- 证据预览
- 时间线增强阅读
- 老板页摘要型输出

### 7.3 明确禁止的做法

禁止：
- 同一个页面主体一半靠 RPC，一半靠随意 REST 拼接，且没有边界说明
- 一个列表页既写 RPC 版本又写 REST 版本
- 工作台卡片直接临时拼多个 `search_read` 结果后在前端再做复杂聚合

## 8. 数据返回规范建议

## 8.1 RPC 返回规范

适用于：
- 标准列表页
- 标准详情页

建议：
- 模型字段尽量稳定
- 聚合字段明确命名
- 不把前端展示逻辑塞进字段名

示例：
- `waybill_no`
- `current_status`
- `latest_trace_at`
- `evidence_status`

## 8.2 Controller 返回规范

适用于：
- 工作台
- 证据区
- 时间线增强

建议：
- 返回结构按页面组织
- 不要求前端自己再拼多模型数据
- 同一类接口统一 `code / message / data`

示例结构：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "summary_cards": [],
    "priority_items": []
  }
}
```

## 9. 权限策略建议

### 9.1 RPC 权限

依赖 Odoo 原生：
- `ir.model.access`
- record rules
- 用户上下文

### 9.2 Controller 权限

即使使用 controller，也必须复用 Odoo 权限体系，不允许独立绕开。

最低要求：
- 在 controller 内校验用户登录态
- 校验用户组
- 校验可访问对象范围

### 9.3 当前原则

不允许因为“写 REST 方便”而绕过 Odoo 权限模型。

---

## 10. 页面跳转上下文建议

### 10.1 如果页面主体走 RPC

优先通过：
- `act_window` context
- domain
- search default

### 10.2 如果页面局部增强走 controller

优先通过：
- 当前对象 id
- 当前对象类型
- 当前筛选上下文

### 10.3 当前推荐

页面跳转上下文以 Odoo 原生 context 为主。  
controller 只消费最小必要上下文，不自己发明另一套跳转系统。

## 12. 当前结论

当前最合理的接口路线不是“二选一彻底排他”，而是：

**用 RPC 承接标准后台页面，用受控 controller 承接聚合与增强页面。**

但必须明确：
- RPC 是主路线
- controller 是例外路线
- 页面边界要先定，不能自由漂移

只要按这条规则推进，当前前端设计就能既保留 Odoo 的优势，又不被原生能力完全绑死。
