## 1. 当前问题判断

当前 `专题设计/前端设计/一期前端相关设计/` 的核心问题不是文件数量本身，而是**不同层级、不同生命周期、不同用途的文档都堆在同一层**。

主要混杂了这 5 类内容：

1. 系统级总纲文档  
   例如总体设计、计划、菜单总表、页面关系总览

2. 模块级正式设计稿  
   例如工作台、留痕与追溯、运输与调度、仓储管理、业务单据

3. 跨模块规范与契约  
   例如接口路线、字段契约、组件规范、权限矩阵、Smart Button

4. 落地执行文档  
   例如 P0 落地清单、联调前检查、开发任务拆分

5. 历史草图与旧版资产  
   例如 `设计图/` 下的草图、改造方案、旧清单，以及原始 docx

如果继续全部放在根目录，后续会越来越难分辨：

- 哪些是“正式有效稿”
- 哪些是“规范性母文档”
- 哪些是“落地清单”
- 哪些只是“历史草图”

---

## 2. 重组原则

目录重组建议统一按下面 6 条原则执行：

1. 先按文档层级分，再按模块分  
   先区分系统级、模块级、规范级、落地级，再处理具体模块。

2. 正式稿和草图分离  
   草图、改造方案、旧资产不再和正式模块稿混放。

3. 跨模块规范单独成组  
   接口、字段、动作、组件、权限这类文档不挂在某个模块下面。

4. 落地文档单独成组  
   开发任务、联调检查、P0 清单不和设计稿混放。

5. 原始资料单独归档  
   docx、旧草图、早期改造稿放到 `archive` 或 `source_assets`。

6. 根目录只保留导航性文件  
   未来根目录尽量只保留 `README` 或少量入口文件，不再承载大批正文文档。

## 4. 为什么这样分

这套结构的核心好处有 4 个：

1. 找总纲时只看 `00_导航与总纲`
2. 找模块正式稿时只看 `01_模块设计`
3. 找接口、字段、组件、权限规则时只看 `02_跨模块规范`
4. 找旧草图或原始资料时只看 `04_来源资料与历史草图`

这样可以明显降低两个常见问题：

- “这份文档到底是不是正式稿？”
- “这份文档到底是给设计看的，还是给开发落地看的？”

## 7. README 建议内容

重组后建议在 `00_导航与总纲/README.md` 或根目录 `README.md` 里只放一个简单导航：

1. 先看 `00_导航与总纲/`
2. 再按模块进入 `01_模块设计/`
3. 需要开发落地时看 `02_跨模块规范/` 和 `03_落地与联调/`
4. 旧草图与原始资料统一去 `04_来源资料与历史草图/`

这样新同事进入目录后，不需要先猜文档权威性。

## 8. 建议的执行顺序

如果后续要真的动目录，建议按下面顺序执行，而不是一次性乱搬：

1. 先创建新目录树
2. 先移动 `00_导航与总纲`
3. 再移动 `02_跨模块规范`
4. 再移动 `03_落地与联调`
5. 最后整体处理 `设计图/` 历史资产
6. 搬完后统一修正文档内的相对引用

原因：

- 系统总纲和规范文档最容易先稳定
- 历史草图引用最散，应该最后处理

## 9. 当前最推荐的落地方式

如果只做一次“风险最低、收益最高”的整理，我建议先做下面这版：

```text
专题设计/前端设计/一期前端相关设计/
├─ 00_导航与总纲/
├─ 01_模块设计/
├─ 02_跨模块规范/
├─ 03_落地与联调/
├─ 04_来源资料与历史草图/
└─ 99_待归档/
```

先把大类分清，再逐步细分子目录。  
这样不会一开始就搬得太细，也更容易批量修链接。

## 10. 当前阶段结论

当前最合理的整理方向不是继续在根目录堆文档，而是把 `专题设计/前端设计/一期前端相关设计/` 重构成：

1. 总纲入口层
2. 模块正式稿层
3. 跨模块规范层
4. 落地执行层
5. 历史资产层

这套结构比单纯按“文件名首字”或“写作时间”分目录更稳定，也更适合后面继续扩文档。
