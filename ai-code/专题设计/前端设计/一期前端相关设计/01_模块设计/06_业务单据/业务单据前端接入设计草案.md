# 业务单据前端接入设计草案

适用范围：
- `ai-code/专题设计/前端设计/一期前端相关设计/` 下 Odoo 物流后台的业务单据接入设计
- Odoo 原生 `sale`、`purchase`、库存相关单据在物流追溯后台中的前端接入、反查入口与链路挂接

## 1. 文档定位

这份文档不负责重做销售、采购或库存单据页面，也不把业务单据模块写成新的执行主链。

它主要回答 4 个问题：

1. 哪些业务单据页面直接复用 Odoo 原生入口
2. 哪些地方需要增加 Smart Button、摘要字段和反查入口
3. 销售订单、采购订单、出入库单据如何跳到批次、运单、追溯主链
4. 业务单据页应该承担哪些入口职责，不承担哪些主阅读职责

当前阶段的重点是：

- 让业务单据成为“业务来源入口”和“单据反查入口”
- 让执行主链继续停留在 `波次 -> 批次 -> 运单`
- 让事实主阅读链继续停留在 `运单 -> 留痕/证据/异常`
- 用最小增强方式把 Odoo 原生单据接入到物流追溯体系

---

## 2. 模块定位

`业务单据` 在整套前端结构中的定位是：

- 它属于 `业务接入层`
- 它以复用 Odoo 原生单据页为主
- 它负责承接“这笔业务从哪来”和“从单据如何反查执行与追溯”
- 它不是物流执行主对象页面

因此，业务单据页主要回答的问题是：

- 这张销售单、采购单或出入库单据对应了哪些物流执行对象
- 当前相关批次、运单、仓储作业推进到了哪一步
- 如果要继续判断事实或异常，应跳到哪个主页面

它不负责单独回答：

- 这单物流执行的最终事实全貌
- 留痕时间线的完整阅读
- 证据核验与责任裁定
- 异常处理闭环

这些仍由 `运输与调度`、`留痕与追溯`、`异常中心` 承担。

## 3. 核心边界

当前必须明确下面这个边界：

- `sale.order` 不是物流执行运单
- `purchase.order` 不是物流执行批次
- 仓储单据也不是最终追溯主对象

它们的统一角色是：

- 来源单据
- 关联单据
- 反查入口

因此，推荐理解为：

```text
业务单据 = 业务来源层
仓储管理 = 仓侧事实入口层
运输与调度 = 执行组织层
留痕与追溯 = 事实主阅读层
异常中心 = 问题处理层
```

这条边界如果不先写清，后续很容易把 `sale.order` 或 `purchase.order` 误写成物流主对象，和一期架构口径冲突。

## 4. 接入原则

当前业务单据前端接入统一按下面 6 条原则执行：

1. 原生单据优先  
   销售、采购、库存单据优先复用 Odoo 原生 `tree/form/search` 页面。

2. 反查增强优先  
   重点补充 Smart Button、关联摘要字段、默认筛选跳转，不重做整页。

3. 来源语义优先  
   单据页优先回答“业务从哪来”，不抢执行链和追溯链的主对象职责。

4. 运单和批次优先  
   单据与物流链的首要连接点优先是 `批次`、`运单`，不是直接堆叠大量异常证据。

5. 单据可回溯，但不做主阅读  
   单据页可以展示轻量摘要，但不能替代 `运单详情`、`批次详情`。

6. Odoo 原生动作传参优先  
   跳转统一优先使用 `act_window + domain + context + search_default_*`。

## 5. 菜单与入口结构

当前建议在 `业务单据` 一级模块下保留 3 类二级入口：

```text
物流后台
└── 业务单据
    ├── 销售单据
    ├── 采购单据
    └── 出入库单据
```

三类入口的定位如下：

| 二级入口 | 页面类型 | 当前定位 |
|---|---|---|
| 销售单据 | 原生页面入口 | 从销售来源反查相关执行链与追溯链 |
| 采购单据 | 原生页面入口 | 从采购来源反查相关入仓、批次与运单 |
| 出入库单据 | 原生页面入口 | 从库存执行单据反查批次、运单与追溯对象 |

说明：

- `业务单据` 一级模块强调的是“来源链入口”
- 当前不建议为业务单据额外设计复杂的自研首页
- 优先靠原生单据页 + Smart Button + 预设筛选把链路串起来

## 6. 原生页面接入清单

当前建议优先接入下面这些 Odoo 原生单据对象页面：

| 页面对象 | Odoo 基础模块 | 页面角色 | 当前接入说明 |
|---|---|---|---|
| `sale.order` | `sale` | 销售来源单据页 | 从销售来源反查相关运单与执行链 |
| `purchase.order` | `purchase` | 采购来源单据页 | 从采购来源反查入仓、批次、运单 |
| `stock.picking` | `stock` | 出入库事实单据页 | 作为业务单据层和仓储层的共享入口 |
| `account.move` | `account` | 财务业务单据页 | 仅在需要业务回溯时做轻量关联入口 |

接入优先级建议如下：

1. `sale.order`
2. `purchase.order`
3. `stock.picking`
4. `account.move`

说明：

- `stock.picking` 在仓储模块里已经作为重点接入页，这里只强调其“业务单据反查”角色
- `account.move` 当前不作为主入口，只保留后续可接入位

## 7. 各类单据页面接入设计

## 7.1 `sale.order` 页面

销售订单是最典型的业务来源页。

它最适合回答：

- 这笔业务需求对应了哪些物流执行对象
- 当前相关运单是否已经形成、是否已经执行
- 是否需要继续下钻查看批次、运单、异常

建议补充的入口：

- `关联运单` Smart Button
- `关联批次` Smart Button
- `查看追溯` Smart Button
- `查看异常` Smart Button

建议暴露的摘要字段：

- 客户
- 门店
- 单据状态
- 关联运单数
- 关联批次数
- 当前异常数
- 最新留痕时间
- 最近仓储作业状态

推荐跳转关系：

- `sale.order -> 运单追溯列表`
- `sale.order -> 批次详情 / 批次列表`
- `sale.order -> 当前异常列表`
- `sale.order -> 相关出入库单据`

当前判断：

- `sale.order` 是业务来源页
- 它可以做强反查入口
- 但它不能取代 `运单详情`

## 7.2 `purchase.order` 页面

采购订单更偏向“入仓来源”与“供应侧执行入口”。

它最适合回答：

- 这笔采购对应了哪些入库或收货执行
- 当前相关批次是否已经形成
- 是否存在到货异常、收货缺口或后续执行问题

建议补充的入口：

- `关联批次` Smart Button
- `关联运单` Smart Button
- `查看入仓追溯` Smart Button
- `查看异常` Smart Button

建议暴露的摘要字段：

- 供应商
- 单据状态
- 入仓进度摘要
- 关联批次数
- 关联运单数
- 当前异常数
- 最新留痕时间

推荐跳转关系：

- `purchase.order -> 批次详情 / 批次列表`
- `purchase.order -> 运单追溯列表`
- `purchase.order -> 当前异常列表`
- `purchase.order -> 相关入库单据`

当前判断：

- `purchase.order` 更适合优先连到 `批次`
- 再由 `批次` 下钻到 `运单` 与异常

## 7.3 `stock.picking` 页面

`stock.picking` 同时属于仓储模块和业务单据模块，但两边视角不同。

在业务单据模块里，它更偏向：

- 承接单据执行事实
- 从单据角度回到批次、运单和追溯链

建议补充的入口：

- `关联批次` Smart Button
- `关联运单` Smart Button
- `查看追溯` Smart Button
- `查看异常` Smart Button

建议暴露的摘要字段：

- 单据类型
- 仓库
- 来源单据
- 关联批次数
- 关联运单数
- 最新留痕时间
- 未闭环异常数

推荐跳转关系：

- `stock.picking -> 批次详情 / 批次列表`
- `stock.picking -> 运单追溯列表`
- `stock.picking -> 当前异常列表`

说明：

- 在业务单据层，它是“单据执行事实页”
- 在仓储层，它是“仓侧事实入口页”
- 同一个原生页面可以承接两类设计语义，但不应拆成两份平行 UI

## 7.4 `account.move` 页面

财务单据当前只建议保留轻量接入位。

它更适合承担：

- 从财务单据反查相关业务单据
- 再从业务单据跳到物流执行链

当前不建议：

- 直接把财务单据做成物流主入口
- 在财务单据页堆叠完整追溯摘要

如果后续确实需要接入，建议只补：

- `相关业务单据`
- `相关运单`
- `相关异常`

## 8. 业务单据页建议暴露的关联字段

为了让业务单据页具备“来源可读”和“反查可用”的价值，当前建议统一补充一组轻量摘要字段。

| 字段类别 | 推荐字段 | 主要用途 |
|---|---|---|
| 来源主体类 | 客户、门店、供应商、来源渠道 | 判断业务归属 |
| 执行关联类 | 关联批次、关联运单、相关仓储单据 | 判断执行链是否已经形成 |
| 留痕摘要类 | 最新留痕时间、最新留痕类型 | 判断是否需要进入主阅读链 |
| 异常摘要类 | 当前异常数、未闭环异常数、高风险标记 | 判断是否需要进入异常中心 |
| 状态辅助类 | 单据状态、履约进度、入仓进度 | 保持单据页自身可读性 |

字段补充原则：

- 先补“入口摘要”，不补“证据明细”
- 先补“是否该往下看”，不补“完整事实页面”
- 只做轻量聚合，不把单据页做成复杂工作台

## 9. 单据到追溯主链的跳转设计

当前统一建议按下面这条顺序理解业务单据链路：

```text
销售/采购/出入库单据
  -> 批次或运单
  -> 运单详情 / 批次详情
  -> 留痕时间线 / 证据查看 / 异常详情
```

推荐跳转规则如下：

| 起点单据 | 首选跳转对象 | 次级跳转对象 | 当前说明 |
|---|---|---|---|
| `sale.order` | 运单 | 批次 | 销售更偏履约结果与客户侧交付 |
| `purchase.order` | 批次 | 运单 | 采购更偏收货与聚合入仓 |
| `stock.picking` | 批次 / 运单 | 异常 | 根据作业场景选择更近的执行对象 |
| `account.move` | 业务单据 | 运单 | 不直接做主跳转源 |

说明：

- `sale.order` 优先跳 `运单`，是为了更快看到客户交付事实
- `purchase.order` 优先跳 `批次`，是为了更符合聚合收货与入仓语义
- `stock.picking` 可以同时连接 `批次` 和 `运单`

## 10. 上下文传递设计

业务单据页跳转到执行链和追溯链时，统一建议保留下面几类上下文：

- 来源单据模型  
  例如：`sale.order`、`purchase.order`、`stock.picking`

- 来源单据 ID  
  用于返回、日志、面包屑和动作留痕

- 客户 / 门店 / 供应商上下文  
  便于目标列表页做默认筛选

- 来源单据状态上下文  
  便于在目标页做视角补充或筛选预设

推荐动作方式：

| 场景 | 推荐方式 |
|---|---|
| 跳运单列表 | `act_window + domain + search_default_*` |
| 跳批次列表 | `act_window + domain` |
| 跳异常列表 | `act_window + context` |
| 跳详情页 | `act_window` 直接开目标 form |

上下文字段建议包含：

- `default_source_model`
- `default_source_id`
- `search_default_customer_id`
- `search_default_store_id`
- `search_default_supplier_id`
- `search_default_has_open_exception`

## 11. 业务单据与仓储管理的边界

当前两者都属于接入层，但职责不同：

| 模块 | 主要回答什么 | 首要连接对象 |
|---|---|---|
| 业务单据 | 业务从哪来、单据如何反查执行链 | 销售单、采购单、出入库单据 |
| 仓储管理 | 货现在在哪、仓侧事实发生了什么 | 仓库、货位、出入库作业 |

因此推荐关系是：

- 从 `业务单据` 先看到来源和履约关联
- 需要看仓侧执行时跳 `stock.picking`
- 需要看执行组织时跳 `批次` 或 `运单`
- 需要看事实和证据时跳 `运单详情`

不推荐：

- 用业务单据页取代仓储事实页
- 用业务单据页直接承载完整时间线
- 用业务单据页直接承担异常处理主界面

## 12. 实现层建议

当前实现策略建议尽量轻：

1. 复用 Odoo 原生 `sale`、`purchase`、`stock` 页面
2. 给单据页增加少量关联字段
3. 用 Smart Button 提供批次、运单、异常入口
4. 用动作上下文承接默认筛选
5. 把复杂聚合和事实阅读留在追溯主链中

如果需要实现优先级排序，建议按下面顺序推进：

1. `sale.order` 入口增强
2. `purchase.order` 入口增强
3. `stock.picking` 单据视角增强
4. `account.move` 轻量预留

---

## 13. 当前阶段结论

当前阶段对 `业务单据` 的前端判断可以收口为：

1. 业务单据继续定位为来源层与反查入口层
2. `sale.order`、`purchase.order`、`stock.picking` 都不是物流主对象
3. 单据页最重要的任务是把来源单据稳定接到 `批次`、`运单`、`追溯` 主链
4. `sale.order` 更适合优先跳 `运单`
5. `purchase.order` 更适合优先跳 `批次`
6. 单据页只做轻量摘要，不替代 `运单详情`、`批次详情`、`异常详情`
