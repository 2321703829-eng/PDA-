## 6. SQL / 聚合 / 索引结论

这部分用于回答评审和开发都会立刻追问的一个问题：

**这套设计包到底依赖怎样的后端聚合能力，是否需要额外 SQL 和索引支持。**

### 6.1 当前正式结论

当前最推荐的总体结论是：

1. P0 主体页面优先用 Odoo 原生 RPC、标准 `tree / form / search / act_window` 承接
2. 列表首屏判断、详情头部摘要、工作台卡片、老板页摘要必须依赖聚合字段
3. 时间线区和证据区允许使用受控的轻量增强接口
4. 一期先不引入复杂 SQL 视图或重型物化层
5. 如果查询性能不足，再补索引和受控聚合方案

### 6.2 哪些页面只靠原生 RPC 基本可落

当前更适合先用原生承接的部分：

- 运单追溯列表页主体壳
- 运单详情页基础表单
- 当前异常列表页主体壳
- 异常详情页基础表单
- 批次追溯列表页主体壳

这些页面即使暂时没有完整增强，也可以先用：

- `search view`
- `tree/list`
- `form`
- `smart button`
- `stat button`

落出可运行版本。

### 6.3 哪些页面必须依赖聚合字段

下面这些页面如果没有聚合字段，虽然“能打开”，但很难达到设计包要求：

- 运单追溯列表页
- 运单详情页头部摘要
- 当前异常列表页
- 批次追溯列表页
- 管理工作台
- 老板总览页
- 争议对象列表页

一期必须优先稳定的聚合方向：

- 运单当前状态摘要
- 最新留痕摘要
- 证据完整度
- 当前异常摘要
- 批次风险摘要
- 工作台概览指标
- 老板页风险摘要

### 6.4 哪些地方涉及查询性能与索引要求

当前最值得优先关注索引和性能的位置：

- 运单号
- 外部单号
- 批次号
- 异常编号
- 提交人
- 风险等级
- 时间范围 + 状态组合筛选
- 异常状态 + 证据完整度组合筛选

当前设计层结论是：

- 先保主链查询与排序稳定
- 再保聚合字段可解释
- 最后再决定是否需要更重的聚合实现

## 9. 命名、状态机、编号规则最终引用口径

这部分用于锁定设计包层面的最终引用顺序，避免后续出现：

- 业务名称和模型名称混用
- 前端页面文案和接口字段命名分家
- 执行状态和异常状态分别引用不同版本的口径
- 编号规则到底看哪份文档不清楚

### 9.1 业务对象命名口径

当前设计包的业务对象命名统一按下面顺序引用：

1. `ai-code/docs/context/Odoo19物流留痕系统运单主对象与留痕主流程设计.md`
2. `docs/architecture/ARCHITECTURE.md`
3. `docs/architecture/logistics_order_mapping_bridge.md`

当前固定结论：

- 执行主线：`wave -> batch -> waybill -> waybill_order_line`
- 追溯主线：`waybill -> trace_event -> evidence -> exception`
- `运单` 是当前追溯主对象
- `订单` 不是留痕主对象
- 如果实现层仍沿用历史 `order` 命名，只能视为兼容命名，不再代表业务口径

### 9.2 前端页面、菜单、动作命名口径

当前前端页面、菜单、动作命名统一按下面顺序引用：

1. `专题设计/前端设计/一期前端相关设计/00_导航与总纲/前端模块结构与菜单总表.md`
2. `专题设计/前端设计/一期前端相关设计/04_来源资料与历史草图/03_页面草图与旧清单/后台信息架构图.md`
3. `专题设计/前端设计/一期前端相关设计/02_跨模块规范/01_接口与数据/最终接口总表.md`

当前固定结论：

- 页面与菜单文案优先使用业务语义中文
- 页面编码与对象语义统一使用 `waybill / batch / wave / exception`
- 动作命名统一使用 `action_logistics_{module}_{object}_{page}` 模式
- 接口字段统一使用 `snake_case`
- 文案字段统一使用 `*_label`
- 摘要字段统一使用 `*_summary`
- 聚合计数字段统一使用 `*_count`
- 时间字段统一使用 `*_at`

### 9.3 状态机与状态流转引用口径

当前状态机与状态流转统一按下面顺序引用：

1. 执行主线状态：`docs/architecture/logistics_dispatch_addon_design.md`
2. 异常状态流转：`docs/architecture/logistics_trace_exception_addon_design.md`
3. 前端显示与动作限制：`专题设计/前端设计/一期前端相关设计/01_模块设计/03_异常中心/异常中心前端设计草案.md`、`专题设计/前端设计/一期前端相关设计/04_来源资料与历史草图/03_页面草图与旧清单/页面动作清单.md`

当前固定结论：

- 执行状态以 `logistics_dispatch` 设计稿为后台主依据
- 异常状态以 `logistics_trace_exception` 设计稿为后台主依据
- 前端只负责展示与受控动作，不单独发明新状态机
- 老板页不承担大量状态流转
- 批次页、老板页等非问题主页面不承接复杂状态机操作

### 9.4 编号规则引用口径

当前编号规则统一按下面顺序引用：

1. `docs/architecture/ARCHITECTURE.md`
2. `专题设计/前端设计/一期前端相关设计/01_模块设计/09_设置与规则/设置与规则模块前端设计草案.md`
3. `docs/dev/project_coordination/Odoo19物流留痕系统五人分工与前端改造安排.md`

当前固定结论：

- 编号规则归属于 `设置与规则` / `logistics_trace_rule` 方向承接
- 前端当前只负责“编号规则页的展示与配置承接”，不在业务页面分散定义编号口径
- 波次、批次、运单、异常编号规则都属于统一治理范围
- 编号规则页当前优先级为 `P2`

当前仓库还没有一份独立的“编号规则正式设计稿”作为单独主文档。  
在该文档建立之前，本设计包以上述 3 份文档组合作为当前最终引用口径。
