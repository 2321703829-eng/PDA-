## 1. 文档定位

这份文档用于把“系统级总纲”继续收口成一张可直接引用的模块与菜单总表。

它主要解决 4 个问题：

1. 整套后台到底有哪些一级模块
2. 每个一级模块下应该挂哪些二级菜单
3. 哪些模块以自研为主，哪些模块以复用 Odoo 为主
4. 后续模块级设计草案、菜单 XML、动作设计应该挂在哪个结构下面

这份文档不替代页面草图，也不替代页面字段清单。

它的作用是：

- 固定模块边界
- 固定菜单口径
- 固定“模块级文档 -> 页面级文档 -> Odoo 菜单动作”的挂接关系

---

## 2. 模块结构总原则

当前后台模块结构统一按下面 4 条原则理解：

1. 先分模块，再分页面，不再以零散页面为设计起点
2. 先区分“执行主线”与“追溯阅读主线”，再决定菜单如何组织
3. 能复用 Odoo 的模块优先复用，不把所有页面都重做成自研界面
4. 菜单只是入口结构，不等于业务边界本身

补充约定：

- `运单` 是当前追溯主对象
- `批次` 是当前聚合与执行组织主对象
- `波次` 是调度组织主对象
- `订单` 在当前前端设计中退到运单详情下的从属明细层

## 4. 一级模块与 Odoo / 自研边界

| 一级模块 | 自研核心 | 复用 Odoo | 当前说明 |
|---|---|---|---|
| 工作台 | 工作台卡片、快捷下钻、摘要阅读区 | Odoo 基础菜单与动作能力 | 首页体验以自研聚合为主 |
| 留痕与追溯 | 运单追溯、批次追溯、时间线、证据、异常阅读 | Odoo tree/form/search 壳子 | 最核心阅读链，优先保证主闭环 |
| 运输与调度 | 波次、批次、运单、车辆、司机的管理视图 | Odoo 标准列表/详情承载 | 负责提供稳定执行上下文 |
| 仓储管理 | 追溯入口、摘要字段、Smart Button | `stock` 等原生仓储能力 | 重点是接入，不是重做 |
| 业务单据 | 单据到运单/批次/追溯的入口 | `sale`、`purchase`、库存单据 | 重点是反查链路 |
| 商品与基础资料 | 少量追溯关联摘要 | 商品、客户、仓库等原生主数据 | 不承担主阅读链职责 |
| 统计与看板 | 聚合卡片、摘要接口、排行页 | Odoo kanban/graph/pivot 承载 | 建立在主链稳定后 |
| 设置与规则 | 少量业务解释性页面 | 原生配置页模式、权限页模式 | 以稳定和可维护为先 |

## 5. 推荐菜单结构总览

当前推荐按下面 8 个一级模块组织后台菜单：

```text
物流后台
├─ 工作台
├─ 留痕与追溯
├─ 运输与调度
├─ 仓储管理
├─ 业务单据
├─ 商品与基础资料
├─ 统计与看板
└─ 设置与规则
```

说明：

- 这是“系统模块口径”
- 实际 Odoo 菜单落地时，可以根据一期范围控制显示层级与顺序
- 但后续模块设计、页面归档、动作命名都应先按这 8 个一级模块归类

## 7. 一期冻结版菜单建议

为了避免一期范围继续扩散，当前建议先冻结成下面这个最小版本：

```text
物流后台
├─ 工作台
│  └─ 管理工作台
├─ 留痕与追溯
│  ├─ 运单追溯
│  ├─ 批次追溯
│  ├─ 当前异常
│  └─ 历史异常
└─ 运输与调度
   ├─ 波次管理
   ├─ 批次管理
   └─ 运单管理
```

补充说明：

- `证据查看` 优先挂在详情页区块，不单独顶层化
- `待处理争议` 可以先做成异常列表预设筛选视图
- `车辆管理`、`司机管理` 可以在执行主线稳定后补入
- `仓储管理`、`业务单据`、`基础资料`、`统计与看板`、`设置与规则` 可先保留设计位，不抢 P0 主闭环优先级

## 8. 菜单命名与文档归类规则

## 8.1 文档归类规则

从现在开始，前端相关文档建议统一按下面口径归类：

- 系统级总纲文档：挂在一级模块之上
- 模块级设计草案：挂在一级模块之下
- 页面草案：挂在具体二级菜单或页面之下
- 字段/动作/交互/接口/聚合策略：作为跨模块规范文档

## 8.2 菜单命名规则

菜单名称统一使用业务语义，不使用技术兼容命名。

例如：

- 用 `运单追溯`，不用 `订单追溯`
- 用 `批次管理`，不用 `shipment batch manage`
- 用 `设置与规则`，不用过于技术化的 `system config`

## 8.3 动作命名规则

推荐统一使用下面模式：

```text
action_logistics_{module}_{object}_{page}
```

例如：

- `action_logistics_trace_waybill_list`
- `action_logistics_trace_batch_list`
- `action_logistics_dispatch_wave_list`
- `action_logistics_dashboard_workbench`

## 10. 当前阶段结论

当前这份总表的核心结论是：

1. 整套后台前端已经可以按 8 个一级模块稳定归类
2. 当前最需要优先落文档和落实现的是 `工作台 + 留痕与追溯 + 运输与调度`
3. 仓储、单据、基础资料、看板、规则应视为接入层和完整度层，不抢主闭环优先级
4. 后续任何新页面、菜单、模块草案，都应先判断它属于哪个一级模块，再继续展开设计
