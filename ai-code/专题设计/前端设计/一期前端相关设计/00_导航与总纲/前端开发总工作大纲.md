## 2. 当前项目的前端目标

当前前端不是在做一个通用 ERP 界面，也不是在做一套完全独立的管理后台。

当前前端的核心目标是：

**在 Odoo Web 后台中，把物流执行主线和追溯阅读主线做成一套可查询、可阅读、可判断、可下钻的前端系统。**

两条主线如下：

### 2.1 执行主线

```text
波次 -> 批次 -> 运单 -> 运单下订单明细
```

### 2.2 追溯主线

```text
运单 -> 留痕 -> 证据 -> 异常
```

当前最重要的判断是：

- 运单是留痕主对象
- 订单不是留痕主对象
- 批次是执行组织对象
- 证据必须跟留痕事实链绑定阅读

## 3. 当前前端开发边界

## 3.1 当前明确在范围内

- 管理工作台
- 运单追溯列表与详情
- 留痕时间线阅读
- 证据查看
- 异常列表与详情
- 老板追溯摘要页
- 运输与调度相关后台页面
- 仓储、单据、基础资料、规则、统计的后台接入层

## 3.2 当前明确不作为主线

- 独立前端工程
- 完全脱离 Odoo Web 的单页前端壳
- Discuss / 聊天 / 频道 / 私聊这类协同能力
- 日历 / 会议类办公协同页
- 与留痕主链无关的泛 CRM / 泛 OA 页面

## 4. 当前前端实现模式

当前模式不是纯前后端分离，而是：

**以 Odoo RPC 为主，以少量 JSON controller 为补充的 Odoo Web 受控混合模式。**

也就是说：

- 标准列表、详情、搜索、菜单、跳转：优先用 Odoo 原生能力
- 工作台、老板页、时间线增强、证据 viewer：允许用 client action、widget、controller 做增强

## 5. 当前代码组织方式

当前前端代码不建议做成完全独立项目，而应继续留在 Odoo addon 体系中。

推荐的代码归属方式是：

- 业务基础视图留在业务模块
- 前端增强能力集中到 `logistics_web`

当前推荐模块职责：

- `logistics_dispatch`：波次 / 批次 / 运单基础页面与对象
- `logistics_trace_core`：留痕事实对象与基础页
- `logistics_trace_exception`：异常对象与基础页
- `logistics_web`：工作台、老板页、时间线 widget、证据 viewer、通用前端组件

对应文档入口：

- `ai-code/docs/architecture/前端代码目录规划.md`
- `ai-code/docs/architecture/logistics_web_addon_design.md`

4. 证据查看区

7. 管理工作台

### 7.2 当前最优先模块

1. `logistics_dispatch`
2. `logistics_web`
3. `logistics_trace_core`
4. `logistics_trace_exception`

---

## 8. 当前推荐的推进顺序

建议按下面顺序推进：

1. 继续完成 `P0` 核心页面真实落地
2. 边做边补 `logistics_trace_core`
3. 再落异常模块基础页
4. 再把时间线和证据增强区挂回详情页
5. 最后继续扩工作台和老板页

这意味着：

- 不再需要继续大规模补总纲型文档
- 文档只在遇到明确缺口时补
- 编码和文档同步小步推进
