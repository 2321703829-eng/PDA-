# 异常详情页草图

适用范围：
- 管理员后台
- `物流留痕 -> 异常中心 -> 当前异常 / 历史异常 / 待处理争议 -> 异常详情`

关联文档：
- `管理员后台界面改造方案.md`
- `后台页面改造清单.md`
- `页面字段清单.md`
- `页面动作清单.md`

---

## 1. 页面目标

这页的目标不是把异常信息“展示完整”，而是让管理员完成下面这条链：

1. 看清楚异常本身
2. 看清楚它关联哪个对象
3. 看清楚关键留痕
4. 看清楚关键证据
5. 做出处理动作

所以这页必须围绕：

`异常摘要 -> 关联对象 -> 关键留痕 -> 关键证据 -> 处理动作`

---

## 2. 页面结构原则

异常详情页不是运单详情页的复制版，但它要复用同一种阅读逻辑：

1. 先看摘要结论
2. 再看事实依据
3. 再看证据
4. 最后处理

区别在于：
- 运单详情从“业务对象”开始
- 异常详情从“问题对象”开始

## 4. 页面分区说明

## 4.1 头部摘要区

这是异常详情页第一优先层。

必须固定展示：
- 异常编号
- 异常类型
- 严重程度
- 当前状态
- 当前责任人
- 最近处理时间

主动作也应固定放在这里：
- 标记处理中
- 标记已核实
- 添加处理备注
- 查看证据

设计原则：
- 先把问题本身说明白
- 让处理动作在摘要区就能看到

## 4.2 异常摘要区

这一块回答：
- 这个异常到底是什么

建议字段：
- 异常说明
- 发现时间
- 来源
- 问题简述

设计原则：
- 这块是问题描述，不是过程区
- 不宜过长，可摘要 + 展开

## 4.3 关联对象区

这一块回答：
- 这个问题挂在哪个业务对象上

建议字段：
- 运单号
- 当前状态
- 批次号
- 车次号（P2）

动作：
- 跳运单详情
- 跳批次详情

设计原则：
- 问题对象必须能一眼看见
- 不能让管理员自己再去找对象

## 4.4 关键留痕区

这一块回答：
- 问题是在什么时候、哪条留痕里体现出来的

建议展示：
- 关键异常留痕
- 前后相邻留痕

每条建议展示：
- 时间
- 留痕类型
- 提交人
- 图片数量
- 备注摘要

设计原则：
- 先放关键异常留痕
- 再补前后文留痕
- 让管理员能快速判断异常是在什么时间段出现

## 4.5 关键证据区

这一块回答：
- 这次异常有没有足够的证据

建议展示：
- 关键图片缩略图
- 留痕归属
- 时间
- 图片备注

设计原则：
- 默认优先显示异常对应的关键图
- 不必一上来就把所有图铺开

## 4.6 处理状态区

这一块回答：
- 这个问题现在处理到哪了

建议字段：
- 当前状态
- 当前责任人
- 最近处理时间
- 最近处理备注摘要

设计原则：
- 做成右侧固定卡片
- 不与问题摘要混在一起

## 4.7 处理记录区

这一块回答：
- 后台对这个问题做过什么动作

建议字段：
- 时间
- 处理人
- 动作
- 备注摘要

设计原则：
- 以时间倒序展示
- 方便复盘，不做主判断区

---

## 5. 右侧摘要栏设计

右侧建议固定为“处理与跳转区”，而不是更多字段区。

建议放：
- 处理状态卡
- 快速跳转卡
- 技术信息折叠区

不建议放：
- 太多业务正文
- 太多可编辑字段

---

## 6. 关键交互草图

## 6.1 标记处理中

```text
[标记处理中]
    -> 确认动作
    -> 当前状态变更为处理中
    -> 处理记录区新增一条记录
```

## 6.2 标记已核实

```text
[标记已核实]
    -> 确认动作
    -> 当前状态变更为已核实
    -> 可选要求填写简短备注
```

## 6.3 添加处理备注

```text
[添加处理备注]
    -> 打开轻量备注输入
    -> 写入处理记录区
```

## 6.4 查看证据

```text
[查看证据]
    -> 聚焦关键证据区或打开证据预览层
```

## 7. 字段优先级落位

## 第一优先层

- 异常编号
- 异常类型
- 严重程度
- 当前状态
- 当前责任人
- 最近处理时间

## 第二优先层

- 关联运单号
- 关联批次号
- 关键异常留痕
- 关键证据

## 第三优先层

- 来源
- 发现时间
- 更长的异常说明
- 处理历史完整展开

## 技术层

- linked_trace_external_id
- linked_image_access_key
- external_exception_id

这些应放到折叠区。

## 8. Odoo 落地建议

这页建议落地为：
- 主表单 `form`
- 右侧摘要 / 操作区
- smart button
- 异常对象上的关联留痕区和证据区

推荐结构：

```text
form
├─ header
├─ summary sheet
├─ main content
│  ├─ exception summary block
│  ├─ linked object block
│  ├─ key trace block
│  ├─ key evidence block
│  └─ process record block
└─ side action block
```

注意：
- 处理动作建议落在异常对象方法上
- 处理记录可以走业务字段或专门 history 模型
- 不建议只靠 chatter 表达处理过程

## 10. 结论

异常详情页的核心不是“把异常信息说全”，而是：

**让管理员从问题对象直接读到证据链，并立即采取处理动作。**

所以这页最重要的顺序是：

- 先看问题
- 再看对象
- 再看关键留痕
- 再看关键证据
- 最后处理

只要这条顺序稳住，异常页就会成为管理员处理争议的主战场。
