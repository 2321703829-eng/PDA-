---

## 1. 页面目标

这页是后台里的“证据阅读页”。

它的目标不是只把图片放大，而是让管理员完成三件事：
1. 看清图片本身
2. 看清图片属于哪条留痕、哪张运单或哪个批次
3. 快速判断这张图是否足够支撑追溯判断

所以这页必须把“图片”和“上下文”牢牢绑在一起。

---

## 2. 页面结构原则

证据查看页必须遵循这个顺序：
1. 先看图
2. 再看图属于谁
3. 再看图来自哪条留痕
4. 最后做跳转判断

不能做成：
- 纯图片灯箱，没有上下文
- 纯附件列表，看不出和留痕的关系
- 图片和运单、异常完全分离

## 4. 页面分区说明

## 4.1 顶部上下文区
必须固定展示：
- 页面标题
- 当前对象上下文
- 返回上页
- 刷新

设计原则：
- 看图时不能丢失追溯上下文
- 证据页必须知道当前图片属于哪条链路

## 4.2 搜索与筛选区
建议支持：
- 图片备注
- 上传人
- 关联运单号
- 时间范围
- 图片分类
- 存储状态
- 是否异常相关

设计原则：
- 便于快速找到关键图片
- 不做成纯技术存储检索页

## 4.3 图片主区
主区应固定承担：
- 当前图片大图预览
- 上一张 / 下一张
- 查看原图

设计原则：
- 大图永远是第一阅读中心
- 操作尽量轻，不打断阅读

## 4.4 图片缩略条
建议展示：
- 当前组内全部图片
- 当前选中状态
- 顺序感

设计原则：
- 管理员应能快速切换对比同组图片
- 不应每次都回列表重新进入

## 4.5 图片备注与留痕摘要区
这一块必须把图片和留痕对应起来。

建议展示：
- 图片备注
- 对应留痕时间
- 留痕类型
- 提交人
- 留痕备注摘要

设计原则：
- 图片本身不是孤立证据
- 必须放回它所属的事实节点里理解

## 4.6 图片列表区
建议展示：
- 序号
- 图片分类
- 上传时间
- 上传人
- 对应留痕
- 存储状态

设计原则：
- 这是辅助浏览区
- 不要让图片列表压过大图阅读区

## 4.7 右侧上下文区
建议放：
- 图片信息卡
- 归属上下文卡
- 快速跳转卡
- 技术信息折叠区

设计原则：
- 右侧只负责辅助解释和跳转
- 不是主看图区

## 6. 字段落位建议

## 第一优先层
- 图片预览
- 序号
- 图片分类
- 上传时间
- 上传人
- 对应留痕
- 存储状态

## 第二优先层
- 图片备注
- 运单号
- 批次号
- 当前异常摘要

## 第三优先层
- 原始文件名
- 文件扩展名
- 存储提供方

## 技术层
- external_image_id
- image_access_key
- storage_relative_path
- external_upload_user_id

这些字段只应放在折叠技术区。

- 查看原图
- 查看留痕

## 辅助动作
- 查看运单

设计原则：
- 主动作服务连续看图
- 辅助动作服务回到事实和对象
- 不建议在证据页承载复杂处理流程

## 9. 关键交互草图

## 9.1 查看留痕
```text
[查看留痕]
    -> 进入留痕时间线页
    -> 自动带上当前 trace_id
    -> 高亮该图片所属留痕
```

## 9.2 查看运单
```text
[查看运单]
    -> 进入运单详情页
    -> 自动定位到证据区或对应留痕区
```

## 9.3 查看异常
```text
[查看异常]
    -> 进入异常详情页
    -> 聚焦当前图片对应的异常对象
```

## 9.4 查看原图
```text
[查看原图]
    -> 打开原图预览
    -> 不脱离当前上下文链路
```

## 11. Odoo 落地建议

建议落地为：
- `act_window`
- `form view`
- 图片预览区 + 下方列表区

增强点：
- 证据主区可做轻量自定义 widget
- 右侧上下文卡仍可用原生 form 区块承载
- 若后续需要，再增强为更好的灯箱或轮播体验

注意：
- 不建议一开始重写整页前端
- 先把图片和留痕归属关系展示清楚

---

## 12. 结论

证据查看页最重要的不是“把图放大”，而是：

**让管理员在看图的同时，不丢掉证据所属的事实和对象。**

只要用户在这页能快速知道：
- 这张图拍了什么
- 这张图属于谁
- 这张图来自哪条留痕
- 下一步该回哪个对象继续判断

这页就达标。
