## 1. 文档目标

本方案用于明确：

1. 管理员后台要解决什么问题
2. 后台页面应该如何组织
3. 运单、批次、留痕、证据、异常应如何串成可阅读闭环
4. 哪些页面先做，哪些页面后做
5. 最终如何落到 Odoo 的菜单、动作、搜索、列表和详情视图

本方案不是视觉稿，也不是前端代码稿，而是后台追溯阅读层的正式设计方案。

---

## 2. 设计前提

当前必须统一接受以下前提：

1. 这套系统的本质是物流留痕取证系统。
2. 后台管理端的核心价值是“查、看、追溯、判断”，不是复杂审批流。
3. 当前阶段成熟度最高的链路是：
   - 波次 / 批次 / 运单快照
   - 留痕事实
   - 图片证据
   - 异常对象
4. 留痕与证据的直接主对象是运单号，不是订单明细。
5. 订单仍然存在，但在后台阅读链中应退到运单详情下的从属明细层。
6. 客户、门店、联系人、泛主数据管理，不是本阶段后台重点。
7. 聊天、频道、日历、会议、泛协同页面，当前不纳入管理员后台改造主范围。

---

## 3. 管理员后台的核心任务

管理员在后台最常见的任务，不是录入，而是判断。

后台必须服务下面 5 类任务：

1. 查询对象
   - 找运单
   - 找批次
   - 找异常
2. 看当前状态
   - 当前到了哪一步
   - 当前有没有异常
   - 最新留痕是什么
3. 看历史过程
   - 某个节点何时发生
   - 谁提交了留痕
   - 过程有没有中断或缺失
4. 看证据链
   - 有几张图
   - 图属于哪次留痕
   - 图是否足以支持判断
5. 做处理动作
   - 标记处理中
   - 添加处理备注
   - 从异常追到运单 / 批次 / 留痕 / 证据

因此，管理员后台不是“运营后台”，而是“追溯与判断后台”。

---

## 4. 设计原则

## 4.1 先读懂，再操作

管理员进入页面后，优先看到：
- 当前状态
- 最新留痕
- 证据摘要
- 异常摘要

而不是先看到大量编辑字段。

## 4.2 页面围绕三层组织

所有关键页面都应按下面三层设计：

1. 当前状态层
2. 留痕事实层
3. 图片证据层

## 4.3 先摘要，再细节

详情页不应一上来就把全部字段摊开。

推荐顺序：

1. 头部摘要
2. 当前状态与执行上下文
3. 时间线
4. 证据区
5. 异常与处理记录

## 4.4 证据不能被普通附件替代

图片证据必须作为正式业务信息被阅读，而不是只放在 chatter 或附件列表里。

## 4.5 优先打通主闭环

第一阶段优先打通：

`运单列表 -> 运单详情 -> 留痕时间线 -> 证据查看 -> 异常判断`

## 5. 页面结构模型

## 5.1 当前状态层

用于回答：
- 现在怎么样

建议承载内容：
- 运单当前状态
- 批次当前状态
- 当前是否异常
- 最新留痕摘要
- 最新证据摘要

适用页面：
- 列表页
- 详情页头部
- 工作台卡片

## 5.2 留痕事实层

用于回答：
- 发生过什么

建议承载内容：
- 留痕时间
- 留痕类型
- 提交人
- 留痕备注
- 留痕所属对象
- 是否异常留痕

适用页面：
- 时间线
- 留痕详情区
- 异常关联区

## 5.3 图片证据层

用于回答：
- 有哪些可查看证据

建议承载内容：
- 图片顺序
- 图片缩略图
- 对应留痕
- 拍摄 / 上传时间
- 上传人
- 图片备注
- 证据完整度

适用页面：
- 证据区
- 图片弹层 / 抽屉
- 异常详情区

## 6. 后台信息架构建议

```text
物流留痕
├─ 追溯中心
│  ├─ 运单追溯
│  ├─ 批次追溯
│  ├─ 波次追溯（P1/P2）
│  ├─ 车次追溯（P2）
│  └─ 证据总览（P1/P2）
├─ 异常中心
│  ├─ 当前异常
│  ├─ 历史异常
│  └─ 待处理争议
├─ 看板中心
│  ├─ 管理工作台
│  ├─ 缺图看板
│  └─ 异常闭环看板
└─ 配置与规则
   ├─ 留痕类型
   ├─ 异常类型
   └─ 留痕规则
```

信息架构原则：

- 追溯中心是一级主入口
- 异常中心独立成组，不埋在运单下
- 看板中心服务管理效率，不抢追溯主入口
- 配置与规则只做后台承接，不在一期过度扩写

## 7. 页面范围与优先级

## 7.1 P0 页面

P0 目标是先把后台证据闭环打通。

必须先做：

1. 运单追溯列表页
2. 运单详情页
3. 留痕时间线区块
4. 证据查看区块

## 7.2 P1 页面

P1 目标是补齐运营追溯能力。

建议补做：

1. 批次追溯列表页
2. 批次详情页
3. 异常列表页
4. 异常详情页
5. 管理工作台
6. 波次追溯页

## 7.3 P2 页面

P2 目标是增强视角与效率。

后续再做：

1. 车次追溯页
2. 证据中心页
3. 高级导出与统计页
4. 更细粒度聚合看板

---

## 8. 核心页面设计

## 8.1 运单追溯列表页

页面目标：
- 快速找到要看的运单
- 快速判断当前状态和证据完整度

建议字段：

| 字段 | 说明 |
|---|---|
| 运单号 | 主显示字段 |
| 门店 / 店铺 | 业务识别字段 |
| 批次号 | 执行上下文 |
| 当前状态 | 当前状态层核心字段 |
| 异常状态 | 是否存在异常 |
| 最新留痕时间 | 判断最近更新 |
| 最新留痕类型 | 快速理解最近动作 |
| 证据完整度 | 快速判断是否值得进入详情 |
| 最新责任对象 | 当前判断辅助 |
| 更新时间 | 排序与筛选辅助 |

页面动作：
- 查看详情
- 查看异常
- 快捷筛选
- 复制运单号

设计重点：
- 第一列固定可点击
- 默认按更新时间倒序
- 高价值状态用标签化显示
- 列表不承载复杂编辑动作
- 订单信息只作为运单下从属明细，不抢主列表阅读权

## 8.2 运单详情页

页面目标：
- 用一个页面完成运单级追溯判断

建议分区：

1. 头部摘要区
2. 当前状态区
3. 执行上下文区
4. 留痕时间线区
5. 证据查看区
6. 异常摘要区
7. 运单下订单明细区
8. 处理记录区

头部摘要建议字段：

| 字段 | 说明 |
|---|---|
| 运单号 | 主标识 |
| 当前状态 | 当前状态层核心字段 |
| 异常状态 | 当前是否异常 |
| 最新留痕时间 | 最近过程摘要 |
| 最新留痕人 | 最近责任线索 |
| 证据完整度 | 快速判断 |

页面主动作：
- 查看完整时间线
- 查看证据
- 查看异常详情
- 标记处理中
- 添加处理备注

设计重点：
- 先摘要后事实
- 时间线和证据区必须是主区，不是附属区
- 异常必须能从详情页直接看到，不应只在列表体现
- 订单列表是解释性区块，不是主追溯对象区块

## 8.3 留痕时间线区块

区块目标：
- 快速理解历史过程

建议展示字段：

| 字段 | 说明 |
|---|---|
| 留痕时间 | 时间轴核心 |
| 留痕类型 | 节点类型 |
| 提交人 | 责任线索 |
| 留痕备注摘要 | 过程解释 |
| 所属对象 | 运单或批次 |
| 图片数量 | 与证据区联动 |
| 是否异常 | 异常留痕高亮 |

设计原则：
- 建议按时间倒序
- 异常留痕视觉高亮
- 每条记录应可跳到证据区
- 时间线只展示摘要，不在这里堆全部元数据

## 8.4 证据查看区块

区块目标：
- 不离开详情页即可完成证据核对

建议展示字段：

| 字段 | 说明 |
|---|---|
| 图片序号 | 同留痕下稳定顺序 |
| 缩略图 | 快速浏览 |
| 对应留痕事件 | 建立证据归属 |
| 对应对象 | 运单或批次 |
| 拍摄 / 上传时间 | 判断真实性和时序 |
| 上传人 | 责任线索 |
| 图片备注 | 辅助判断 |
| 存储状态 | 图片是否有效 |

页面动作：
- 打开大图
- 跳转对应留痕
- 查看原始元数据

设计原则：
- 多图顺序稳定
- 查看大图不打断主流程
- 证据必须能反跳到留痕

## 8.5 异常列表页

页面目标：
- 从问题出发定位对象

建议字段：

| 字段 | 说明 |
|---|---|
| 异常编号 | 主显示字段 |
| 异常类型 | 问题分类 |
| 严重程度 | 判断优先级 |
| 关联运单 / 批次 | 追溯入口 |
| 当前状态 | 是否待处理 |
| 当前责任人 | 当前处理线索 |
| 最近处理时间 | 处理进度判断 |
| 证据是否完整 | 是否能直接判断 |

页面动作：
- 查看异常详情
- 跳运单详情
- 跳批次详情

## 8.6 异常详情页

页面目标：
- 让管理员从异常直接读到证据链

建议分区：

1. 异常摘要
2. 关联对象区
3. 关联留痕区
4. 关联证据区
5. 当前责任与状态区
6. 处理动作区

主动作：
- 标记处理中
- 标记已核实
- 添加处理备注
- 跳运单 / 批次 / 留痕 / 证据

## 9. 搜索与筛选设计

## 9.1 默认搜索项

运单追溯页建议至少支持：

- 运单号
- 批次号
- 门店 / 店铺
- 异常编号
- 车牌号
- 司机
- 留痕提交人

订单号可以保留，但应退为从属检索项，不应继续占主搜索优先级。

## 9.2 常用筛选项

- 时间范围
- 当前状态
- 异常状态
- 证据完整度
- 是否有最新留痕
- 是否存在未闭环异常

## 9.3 设计原则

- 高价值筛选放在前面
- 默认排序稳定
- 不做“很多但没人用”的筛选项堆砌
- 列表页必须有业务快捷筛选，不只做通用搜索

---

## 10. 页面动作规范

主动作建议统一：

- 查看详情
- 查看时间线
- 查看证据
- 查看异常
- 添加处理备注
- 标记处理中
- 标记已核实

辅助动作建议统一：

- 复制编号
- 打开大图
- 查看原始元数据
- 快捷筛选

动作规范原则：

- 主动作位置固定
- 同一类页面动作命名统一
- 次要动作不抢主动作视觉层级
- 列表页少编辑，多跳转

## 11. 后端依赖要求

为了让后台可读，后端至少需要提供下面这些摘要能力。

## 11.1 对运单快照层的要求

依赖来源：
- `logistics.waybill`

建议具备：
- 当前状态字段
- 异常状态字段
- 最新留痕摘要字段
- 最新图片摘要字段
- 证据完整度字段
- 运单下订单数量与摘要字段

## 11.2 对留痕事实层的要求

依赖来源：
- `logistics.trace`

建议具备：
- 按运单 / 批次 / 时间范围查询
- 留痕时间线最小摘要字段
- 异常留痕标记

## 11.3 对证据层的要求

依赖来源：
- `logistics.trace.image`

建议具备：
- 图片顺序稳定
- 图片访问键
- 图片有效性状态
- 证据摘要能力

## 11.4 对异常层的要求

依赖来源：
- `logistics_trace_exception`

建议具备：
- 异常状态机
- 当前责任人口径
- 是否支持从异常直接跳对象和证据

## 12. Odoo 落地方式

本方案默认使用 Odoo 标准后台能力落地。

优先使用：

- `menuitem`
- `ir.actions.act_window`
- `search` 视图
- `tree` 视图
- `form` 视图
- smart button
- stat button
- 必要的 `kanban`

当前不建议：

- 过早重写 WebClient
- 一开始就做重型前端壳子
- 用 chatter 冒充时间线主区

正确落地顺序：

1. 先定菜单结构
2. 再定 action
3. 再定 search / tree
4. 再定 form 分区
5. 最后补增强交互

---

## 13. 当前不做范围

本方案当前明确不覆盖：

- 聊天、频道、Discuss 风格协同页面
- 日历、会议、办公协同视图
- 泛联系人中心
- CRM 式客户运营界面
- 与留痕主闭环无关的复杂审批页

理由：
- 这些内容会稀释留痕证据主线
- 当前不是系统成败关键

## 15. 与老板追溯界面的差异对比

本方案聚焦管理员后台的追溯与处理能力，而《老板追溯界面改造方案》则专门为老板/管理层的决策判断场景设计。两者在核心价值、信息密度、操作重点等方面存在本质差异，具体对比如下：

| 维度 | 管理员后台 | 老板追溯界面 |
|---|---|---|
| **核心价值** | 追溯、处理、协调 | 判断、决策、追责 |
| **核心用户** | 运营管理员、客服、操作员 | 老板、管理层、决策者 |
| **信息密度** | 中高，支持运营判断和过程排查 | 低，支持快速决策和风险识别 |
| **第一眼内容** | 待处理事项、最新留痕、证据完整度 | 风险摘要、争议对象、证据缺失情况 |
| **证据呈现** | 完整时间线 + 原始证据附件，支持逐条核对 | 关键证据摘要 + 争议焦点对比，隐藏原始过程 |
| **操作重点** | 标记处理中、添加处理备注、状态变更 | 记录判断结论、标记已核实、指派跟进 |
| **技术字段** | 可展开，供技术排查和过程追溯使用 | 默认折叠，尽量隐藏，避免干扰决策 |
| **默认筛选** | 今日有更新、未闭环异常、证据不足 | 争议对象、高风险批次、证据缺失 |
| **页面组织** | 围绕“当前状态层、留痕事实层、图片证据层”三层模型 | 围绕“风险摘要层、争议对象层、证据摘要层、决策记录层”四层模型 |
| **交互复杂度** | 支持多步骤操作、批量处理、复杂筛选 | 交互极简，主动作不超过3个，不支持批量操作 |

### 设计衔接建议
1. **权限隔离**：老板页应使用独立权限组，防止管理员误操作决策功能
2. **状态同步**：老板的“已核实”标记应在管理员后台可见，作为处理参考
3. **下钻路径**：老板从争议对象下钻到管理员后台时，应自动定位到对应对象和留痕
4. **数据一致性**：双方界面消费同一套后端数据模型，确保判断依据一致

### 开发落地建议
- 管理员后台使用标准 Odoo tree/form 视图实现，注重功能完整性
- 老板追溯界面可适度使用 kanban 和定制卡片，注重信息摘要和视觉层次
- 两者共享同一套业务模型和 API，仅在前端呈现层做差异化设计

## 16. 结论

管理员后台改造的核心，不是把 Odoo 后台做得更像“定制系统”，而是把下面这条链读顺：

`运单 / 批次当前状态 -> 留痕历史 -> 图片证据 -> 异常判断 -> 处理动作`

只要这条链顺了，后台就能真正支撑物流留痕系统的核心价值。
