# 2026-05-07 六期分支任务：监控与导出体验优化设计

## 1. 文档目的

本设计用于沉淀六期优化中的一个独立分支任务：

- 物流小程序与后台关键链路的监控能力建设
- 证据图片批量导出结果页与导出包体验优化

本任务当前不立即进入开发实施，但需要提前固定设计口径，便于后续单独排期、拆分和联调。

## 2. 背景

当前系统已完成以下主链打通：

- 小程序 `stops` 查询链
- 小程序 `traces / evidences / images` 上传链
- 图片预览链
- 证据页缩略图展示
- 证据图片 ZIP 批量导出主链

但在联调过程中暴露出两个体验层问题：

1. 出现接口异常时，缺少稳定的链路级监控，排查仍依赖人工截图、日志和临时 SQL。
2. 证据图片批量导出的“结果展示”和“下载包结构”虽然已能工作，但仍不够符合业务理解，尤其是在部分图片缺失、历史数据不完整时，结果解释性不足。

因此将“监控”和“导出体验”单独作为六期优化分支任务处理。

## 3. 设计目标

### 3.1 监控目标

- 让研发、测试、运维能快速判断哪条链路在失败
- 区分“接口成功”和“业务成功”
- 能快速定位失败是系统异常、历史数据问题，还是公网入口问题

### 3.2 导出体验目标

- 让业务用户明确知道“导出了什么、没导出什么、为什么”
- 让证据图片导出真正以“图片”为主单位，而不是被证据主记录噪音干扰
- 让下载包拿到手后更容易对图、找图、追溯归属

## 4. 范围定义

### 4.1 本任务纳入范围

- mini 查询链、上传链、预览链的轻量监控设计
- 后台导入/导出任务的结果监控设计
- 证据图片批量导出结果页文案与统计口径设计
- 证据图片 ZIP 包结构与索引文件设计

### 4.2 本任务暂不纳入范围

- 公网 `7084` 入口代理层治理
- 完整 Prometheus / Grafana / APM 平台建设
- 证据链历史脏数据全量修复
- 证据页面主查询/主筛选的结构化改造

## 5. 监控设计

## 5.1 监控分层

监控按三层建设：

### 5.1.1 接口层监控

优先覆盖以下接口：

- `GET /api/mini/logistics/waybills/<no>/stops`
- `POST /api/mini/logistics/traces`
- `POST /api/mini/logistics/evidences`
- `POST /api/mini/logistics/evidences/<id>/images`
- `GET /logistics_trace/evidence-images/<key>`

建议记录字段：

- 请求时间
- 请求路径
- 方法
- 状态码
- 耗时
- `request_id`
- 业务键
  - 批次号
  - 运单号
  - `trace_event_id`
  - `evidence_id`

### 5.1.2 业务结果层监控

重点不只看接口 `200`，还要看业务结果是否真正成功。

建议统计：

- `stops` 查询成功率
- `stops` 查无结果次数
- `traces` 创建成功率
- `evidences` 创建成功率
- `images` 上传成功率
- 图片预览 `404` 比例
- 证据图片导出任务成功率
- 证据图片导出中“未导出-数据缺失”比例
- 证据图片导出中“未导出-系统异常”比例

### 5.1.3 页面/任务层监控

建议覆盖：

- 导入任务成功率
- 导出任务成功率
- 导出文件生成成功率
- 证据图片导出 ZIP 生成成功率
- 导出任务中：
  - 命中运单数
  - 命中证据数
  - 命中图片数
  - 成功导出图片数
  - 未导出图片数

## 5.2 监控展示建议

第一版不做重平台建设，建议先做轻量看板。

按四块展示：

- 小程序查询链
- 小程序上传链
- 图片预览链
- 导入导出任务链

每块先看三个核心指标：

- 今日请求量
- 今日成功率
- 最近 24h 失败 Top 原因

## 5.3 告警建议

第一版先配高价值告警：

- `traces` 成功率低于阈值
- `images` 上传连续失败
- 图片预览 `404` 激增
- 证据图片导出 ZIP 生成失败
- 公网入口 `7084` 502 激增

## 6. 导出体验设计

## 6.1 导出入口口径

证据图片批量导出入口应明确表达：

- 导出范围来自“当前列表筛选结果”
- 导出主单位是“图片”
- 压缩包中会附带索引文件

建议入口提示文案：

- 导出当前筛选结果中的所有可用图片，并附索引清单

## 6.2 结果页状态口径

不再直接对业务暴露：

- `Success`
- `Failed`
- `Skipped`

统一为更符合业务理解的状态。

### 6.2.1 任务级状态

- 导出成功
- 部分导出成功
- 导出失败

### 6.2.2 图片级统计

- 已导出图片
- 未导出-数据缺失
- 未导出-系统异常

## 6.3 导出结果页展示建议

结果页摘要建议固定展示：

- 命中运单
- 命中证据
- 命中图片
- 已导出图片
- 未导出-数据缺失
- 未导出-系统异常
- 导出文件

同时保留说明文案：

- 历史图片文件缺失，未导出
- 该证据没有可导图片
- 导出文件生成失败
- 导出包写入失败
- 系统处理异常，请联系管理员

## 6.4 ZIP 包结构建议

压缩包建议固定结构：

- `/images/...`
- `/index.csv`
- `/manifest.json`

### 6.4.1 index.csv 建议字段

- 批次号
- 运单号
- 留痕事件类型
- 留痕时间
- 门店名称
- 图片 key
- 文件名
- 导出状态

### 6.4.2 manifest.json 建议字段

- `entry_type`
- `export_scope`
- `generated_at`
- `matched_waybill_count`
- `matched_evidence_count`
- `matched_image_count`
- `exported_image_count`
- `skipped_image_count`
- `failed_image_count`

## 7. 推荐实施顺序

建议按以下顺序推进：

1. 先补链路监控埋点
2. 再落结果页业务状态口径
3. 再做轻量监控看板
4. 最后细化 ZIP 包索引和导出说明文案

## 8. 验证重点

### 8.1 监控侧

- 小程序五条主接口是否都能产生日志与统计
- 失败接口是否能准确区分 4xx / 5xx / 业务失败
- 导出任务是否能展示图片级统计

### 8.2 导出体验侧

- 当前筛选结果导出的是否真是“图片”
- ZIP 是否稳定生成
- `index.csv` 是否可直接对图
- 历史缺图数据是否清晰归类为“未导出-数据缺失”
- 任务级状态是否符合业务直觉

## 9. 后续衔接

本任务适合在以下前提下进入开发：

- 当前主业务链保持稳定
- 公网 `7084` 入口问题不阻塞内部联调
- 证据链中期结构已保持统一
