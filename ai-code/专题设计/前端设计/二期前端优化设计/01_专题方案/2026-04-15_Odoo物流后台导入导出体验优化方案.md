## Objective

在不改变当前模块边界和 Odoo 承载方式的前提下，补一轮面向中国物流团队的导入导出体验优化。

这轮方案重点解决 3 个问题：

1. 导入入口藏在齿轮菜单里的 `导入记录` 中，操作路径不直观
2. 导入字段映射中暴露过多 `外部 ID / 数据库 ID` 之类技术字段，不利于业务人员理解
3. 导出表格在部分对象和部分模式下仍偏英文或偏技术字段名，不符合日常使用习惯

---

## Boundary

本方案覆盖：

- `custom_addons/logistics_web` 中的列表页导入入口增强
- `custom_addons/logistics_dispatch` 中波次、批次、运单的导入导出字段优化
- `custom_addons/logistics_base` 中客户、门店、员工基础字段命名优化
- `custom_addons/logistics_trace_core`
- `custom_addons/logistics_trace_evidence`
- `custom_addons/logistics_trace_exception`

本方案不覆盖：

- 官方 `addons/base_import` 与 `addons/web` 的直接源码修改
- 单独新建 Excel 导入向导或批量导入接口
- 上传二进制图片本体的专用批量导入方案

---

## Benchmark

本轮优化统一参考 3 条基准：

1. 当前项目主线基准  
   `wave -> batch -> waybill -> trace -> evidence -> exception`

2. Odoo 原生能力基准  
   继续复用 Odoo 标准导入导出能力，不另起一套后台工具

3. 中国物流团队使用基准  
   用户优先理解 `运单号 / 批次号 / 波次号 / 客户号 / 门店号`，不优先理解 `External ID / Database ID`

## Current Understanding

### 1. 当前导入入口不够显性

- Odoo 19 默认把导入入口放在列表页齿轮菜单里
- 入口文案是 `导入记录`
- 用户必须先点齿轮，再点菜单，才能进入导入页

### 2. 当前导入字段树偏技术视角

- Many2one 字段在 Odoo 原生导入树中，优先暴露的是 `外部 ID` 与 `数据库 ID`
- 这对技术联调有帮助，但不适合业务同学日常录入
- 当前业务对象缺少一批更贴近场景的业务别名字段，例如：
  - `waybill_no`
  - `batch_no`
  - `wave_no`
  - `customer_no`
  - `store_no`

### 3. 当前导出有两套口径

- 标准导出：优先使用字段标题，适合业务阅读
- 导入兼容导出：优先使用字段技术名，适合再次导入

因此这轮优化的目标不是推翻 Odoo 两套口径，而是：

- 标准导出尽量中文化
- 导入兼容导出尽量业务化，减少纯技术字段名

---

## Outcome

如果本轮完成，用户应该能感知到下面这些变化：

1. 列表页上可以直接看到独立的 `导入` 按钮，不必再通过齿轮里的 `导入记录`
2. 运单、批次、波次的导入字段更接近业务词，而不是一串技术 ID
3. 标准导出的表头更稳定地显示为中文
4. 导入兼容导出的列名尽量收口为业务字段代码，例如 `waybill_no`、`batch_no`、`customer_no`
5. 常见旧英文表头和中文业务表头能自动匹配到物流字段，而不是每次都手工重新选择

---

## Behavior

### 1. 导入入口

- 在物流相关列表页顶部新增显性 `导入` 按钮
- 原齿轮菜单中的 `导入记录` 保留，作为原生备用入口
- 新按钮点击后直接进入物流自定义 `导入中心` 页面

### 2. 业务别名字段

在导入导出场景下，优先补齐下面这些业务别名：

- 波次：`wave_no`
- 批次：`batch_no`、`wave_no`
- 运单：`waybill_no`、`batch_no`、`wave_no`、`customer_no`、`customer_name`、`store_no`、`store_name`

这些字段的目标不是替代现有主字段，而是：

- 提高导入字段匹配准确率
- 让导入兼容导出的字段名更接近业务语义

### 3. 导出中文化

- 标准导出优先输出中文字段标题
- 物流相关模型的字段标题、动作标题、搜索标题统一收口为中文
- 导入兼容导出仍保留“可回导”的口径，但优先使用业务字段代码，不优先暴露纯技术 ID

### 4. 中英文表头兼容

- 预置常见英文表头与业务字段的映射关系，例如：
  - `Batch -> batch_no`
  - `Waybill -> waybill_no`
  - `Exception Type -> exception_type`
  - `Severity -> severity_level`
  - `Trace Event -> trace_event_name`
- 同时补充常见中文业务表头映射，例如：
  - `运单号`
  - `批次号`
  - `异常单号`
  - `处理负责人姓名`

### 5. 中文表格适配结论

- 中文表头：Odoo 原生会优先按字段中文标题匹配，这一层基础适配是有的
- 中文值：选择字段和 Many2one 字段原生支持按中文标签或名称匹配
- 当前主要短板不是“中文值不能导”，而是“旧英文表头 / 业务别名表头自动匹配不稳”
- 因此本轮优化重点放在：
  - 预置表头映射
  - 补齐异常模型的业务别名字段
  - 让后续成功导入保存下来的映射规则更稳定可复用

---

## Boundary Notes

### 1. 不直接改 Odoo 原生导入树规则

原生导入树中 `外部 ID / 数据库 ID` 的机制继续保留。  
本轮通过新增业务别名字段和显性入口来降低业务使用难度，而不是直接篡改官方导入引擎。

### 2. 不把导入兼容导出强改成完全中文列名

导入兼容导出本质上承担“再次导回系统”的职责。  
因此它更适合输出稳定的业务字段代码，而不是完全自然语言列头。

## Verify

完成后至少人工确认：

1. 物流相关列表页顶部已出现独立 `导入` 按钮
2. 点击 `导入` 按钮可以直接进入物流自定义 `导入中心` 页面
3. 运单导入字段中可见 `waybill_no / customer_no / store_no / batch_no`
4. 批次和波次导入字段中可见 `batch_no / wave_no`
5. 标准导出生成的表头不再出现 `Batch No / Wave No / Customer Code / Store Code`
6. `Batch / Waybill / Exception Type / Severity / Trace Event` 这类旧英文表头在物流模型中能自动匹配到正确字段

## Risks

### 1. 业务别名字段与原字段并存，可能造成选择成本上升

需要通过字段标题命名区分“主字段”和“导入导出别名”。

### 2. 关联字段按名称导入存在重名风险

对客户、门店等字段优先推荐按编号导入，不推荐只按名称导入。

### 3. 导入兼容导出无法完全摆脱字段代码

这是 Odoo 原生导入导出机制的边界。  
本轮优化重点是“业务化”，不是“彻底自然语言化”。

### 4. 表头能匹配，不代表基础数据一定可导入

即使表头能自动匹配成功，如果批次号、运单号、客户号、门店号存在重名、重复或基础档案未建好，Many2one 导入仍会失败。  
因此唯一编号列仍然是批量导入的优先方案。
