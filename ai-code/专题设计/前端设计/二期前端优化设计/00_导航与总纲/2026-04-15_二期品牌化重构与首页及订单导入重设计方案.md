## Objective

在不直接进入代码改造的前提下，先输出一份可落地执行的二期设计方案，用于指导后续对当前 Odoo 物流后台进行更彻底的品牌化重构、导航重构、首页重构以及订单导入模型重设计。

本轮方案重点回应下面 4 类需求：

1. 页面风格要从“带明显 Odoo 痕迹的后台”升级为“天枢科技自有物流系统后台”
2. 暂时不使用的 `讨论` 与 `联系人` 模块要从当前使用路径中隐藏
3. 需要增加首页，将仪表盘、数据看板、系统指引统一放到首页
4. 订单导入需要支持更完整的业务结构，至少覆盖运单、客户、货物三个层次，并支持数量、重量、体积、配送备注等字段

## Boundary

本方案覆盖：

- 后台整体品牌视觉与命名体系

## Benchmark

本轮方案统一参考 4 条基准：

1. 当前项目业务主线  
`wave -> batch -> waybill -> waybill order lines -> trace -> evidence -> exception`

2. 当前项目架构基准  
执行主线仍以 `dispatch` 为中心，追溯主线仍以 `trace/evidence/exception` 为中心

3. Odoo 原生能力基准  
复用 Odoo 的模型、权限、菜单、动作、导入导出与 Web 承载能力，但不再接受默认视觉和默认术语直接暴露给终端用户

4. 天枢科技品牌基准  
用户使用时应感知为“天枢科技物流系统”，而不是“Odoo 上改过一点颜色的系统”

## Odoo Baseline Comparison

### 1. Odoo 已有能力

- 提供成熟的后台框架、列表页、表单页、搜索、权限、菜单和导入能力
- `mail` 提供讨论、活动、关注者、chatter 等协同能力
- `contacts` 与 `res.partner` 提供客户、门店、联系人基础对象
- 标准导入支持 CSV / Excel、字段映射、导入兼容导出

### 2. 当前项目仍然缺少的部分

- 缺少“天枢科技”品牌化后台壳层
- 缺少首页作为统一入口和使用指引
- 缺少物流业务更强的统计看板
- 缺少适配“一个运单多个客户、一个客户多个货物”的导入结构
- 缺少统一的用户可见字段命名标准

### 3. 设计路径判断

- 后台视觉：`扩展 Odoo`，不建议直接替换 Odoo 内核
- 用户命名体系：`扩展 Odoo`，先统一显示层和导入层命名
- 首页与品牌壳层：`创建项目自定义能力`
- 订单导入分层结构：`创建项目自定义能力`

## Current Understanding

### 1. 当前系统最大问题已经不是单个页面文案，而是整体“系统感知”

即使做完一轮本土化和中文化，用户仍然容易感知到：

- 顶部导航、交互结构、按钮位置仍然像 Odoo
- 页面之间缺少统一的品牌入口和系统性引导
- 使用者在进入系统后，不容易知道“今天先做什么、从哪里开始”

### 2. “完全摆脱 Odoo 痕迹”不能只理解成换皮

如果只是换成蓝色、换 Logo、改标题，用户还是会感知到：

- 术语仍是 Odoo 风格
- 字段仍是模型视角
- 首页仍缺失
- 导入结构仍然不符合业务习惯

所以本轮必须同时处理：

- 视觉壳层
- 导航入口
- 系统命名
- 首页
- 导入模型

### 3. “把所有 Odoo 字段改为天枢科技字段”需要分层处理

这个需求本质正确，但不能粗暴理解成“数据库字段名全部改掉”。

更可落地的分层应该是：

1. 用户可见层  
菜单名、页面标题、字段标题、导入模板列头、导出表头、帮助提示，全部统一成天枢科技业务字段体系

2. 接口 / DTO 层  
对外接口和导入模板字段逐步从 Odoo 模型词过渡到业务字段词

3. ORM / 数据库技术层  
一期不建议大规模重命名底层模型字段，否则会直接放大升级风险、联调风险和历史数据迁移成本

结论是：

**二期应先实现“用户完全看不到 Odoo 术语”，而不是优先做“底层所有技术名全部改写”。**

### 4. 本轮新增纠偏结论

经过本轮人工验收，方案需要补充两个硬性纠偏：

1. **去 Odoo 化不能只停留在主页面换蓝色**  
不仅首页主视觉要改成蓝色，整个系统壳层都不能再残留 Odoo 默认淡紫色，包括但不限于：
  - 顶栏底色
  - 应用切换区
  - 菜单 hover / active 态
  - Tab 激活态
  - 选中描边
  - 徽标、链接、焦点色
  - 下拉菜单和弹层中的默认主题色

2. **系统信息架构不能直接以“调度中心 / 运单中心 / 留痕中心”作为全局一级导航**  
正确的全局结构应是：
  - `天枢科技首页`
  - `发票`
  - `物流`
  - `车队`
  - `员工`
  - 以及后续可能扩展的企业模块

也就是说，`调度 / 运单 / 留痕 / 证据 / 异常` 应该下沉为 `物流` 模块内部的二级工作区，而不是整个系统的一级入口。

### 5. 本轮导航命名与排序补充纠偏

结合本轮人工验收，还需要补充下面 4 条具体规则：

1. 顶部导航中的 `数据看板 / 仪表盘` 类入口，统一改名为 `所有统计图表`  
当前用户心智更容易理解“所有统计图表”是一个完整统计入口，而不是 Odoo 风格的抽象 `仪表盘`

2. `链接追踪器` 视为当前阶段不推荐直接暴露给业务用户的入口  
该命名带有明显机翻感，也不属于物流主工作路径。当前阶段建议默认隐藏；若后续确需开放，建议改名为 `追踪链接`

3. `应用` 模块当前阶段从用户导航中隐藏  
它更接近系统管理入口，不适合作为业务用户当前阶段的常用模块

4. `发票` 模块当前阶段下调优先级  
在一级导航和首页系统模块中，都放在 `设置` 左侧，而不是放在导航前部

### 6. 本轮导航结构补充纠偏

结合最新人工验收，进一步补充 2 条结构性规则：

1. **现有左上角应用下拉菜单应整体取消**  
既然 `链接追踪器` 与 `应用` 当前阶段都要隐藏，而首页本身已经承担企业入口作用，那么继续保留一个只剩少量入口的 Odoo 风格应用下拉菜单，会放大“系统仍然像 Odoo”的感知。因此建议直接取消该下拉层，不再把一级模块入口藏在品牌区下拉菜单里。

2. **统计入口应直接进入顶部一级导航**  
原先通过下拉或次级入口承载的 `仪表盘 / 数据看板`，统一上提为顶部一级导航 `所有统计图表`，与 `物流 / 车队 / 员工 / 库存 / 发票 / 设置` 并列。

## Outcome

如果本轮方案后续按阶段执行，目标状态应是：

1. 用户打开系统首先进入“天枢科技首页”，而不是散落的 Odoo 菜单页
2. 后台整体视觉、导航和命名都表现为天枢科技自有系统
3. `讨论`、`联系人` 不再出现在当前主导航和工作路径里
4. 首页既能看物流看板，也能给新用户提供使用指引
5. 仪表盘不再只显示通用计数，而是能看异常率、证据补齐率、运单执行趋势等物流指标
6. 订单导入支持“运单 -> 客户 -> 货物”的层次结构，导入结果能直接进入运单详情中的订单明细区域
7. 货物明细不只记录“是什么货”，还要明确记录“这张运单下该货物有多少数量 / 件数”
8. 全局一级导航改为企业模块导航，不再直接暴露“调度中心 / 运单中心 / 留痕中心 / 证据中心 / 异常中心”
9. 首页定位为 `天枢科技系统首页`，物流看板是首页中的重点区块之一，但不是首页的唯一内容
10. 全局视觉中不得再出现淡紫色残留或 Odoo 默认主题感

## Brand Direction

### 1. 品牌原则

- 后台品牌统一为 `天枢科技物流系统`
- 页面视觉主色统一为蓝色系，不再延续淡紫色
- 全局壳层必须彻底清除淡紫色残留，不能出现“主页面是蓝色、导航和弹层还是紫色”的过渡态
- 风格关键词统一为：
  - 稳定
  - 清晰
  - 专业
  - 物流运营感

### 2. 视觉关键词

- 主色：深蓝 + 中蓝 + 浅灰蓝
- 辅助色：成功绿、风险橙、异常红
- 中性色：高比例留白、灰白底、低噪声边框
- 组件风格：更偏业务看板，而不是 ERP 配置页

### 3. 禁止项

- 不再保留 Odoo 默认淡紫品牌感
- 不再保留明显 Odoo 顶栏交互痕迹
- 不再保留任何紫色 hover、紫色 active、紫色链接、紫色描边、紫色弹层高亮
- 不再在用户可见层暴露 `Discuss / Contacts / Frontend / Trace & Evidence` 这类原词
- 不再将物流内部工作区直接平铺成整个系统的一级导航

### 4. 品牌落地最小交付物

为了避免“品牌化”停留在口号层，本方案建议在正式实现前先冻结下面 6 个最小交付物：

1. 系统正式中文名：`天枢科技物流系统`
2. 系统英文辅助名：`Tianshu Logistics Console`
3. 主色板：主蓝、深蓝、浅灰蓝、成功绿、风险橙、异常红
4. 组件圆角、阴影、边框、表格密度、按钮等级统一规则
5. 用户可见字段命名字典
6. 首页与主导航信息架构

### 5. 页面壳层视觉规则

#### 5.1 顶栏

- 左上角固定展示天枢科技品牌标识
- 顶栏不再承担 Odoo 式“应用切换器”职责，不再保留左上角应用下拉菜单
- 品牌标识点击后直接返回首页，不再弹出模块列表
- 顶栏右侧只保留与当前用户密切相关的入口：
  - 消息提醒
  - 当前组织
  - 当前用户
  - 快速帮助
- 顶栏及其下拉层的底色、边框、焦点色全部使用蓝色和中性色，不允许残留紫色主题变量

#### 5.2 主导航

- 主导航改为企业级模块导航，而不是物流工作区导航
- 顶部一级导航直接平铺主要企业模块，不再依赖品牌区下拉菜单承载模块切换
- 一级导航建议围绕企业业务域展开，例如：
  - 首页
  - 物流
  - 车队
  - 员工
  - 库存
  - 所有统计图表
  - 发票
  - 设置
- `物流` 作为一级模块进入后，再在模块内部呈现二级工作区：
  - 调度
  - 运单
  - 留痕
  - 证据
  - 异常
- 当前所在一级模块和二级工作区都应有明显高亮和面包屑关系

#### 5.3 页面标题区

- 每个业务页都需要一个统一标题区
- 标题区包含：
  - 页面标题
  - 一句当前页职责说明
  - 当前页快捷操作
  - 最近更新时间或统计口径提示

#### 5.4 表格与筛选器

- 列表页顶部优先放业务动作按钮，不放技术动作
- 筛选器与搜索区优先暴露业务常用条件
- 表格列顺序优先满足运营阅读，而不是模型字段顺序

### 4. 落地建议

- 页面标签和字段标题优先替换
- 导入模板和导出表头同步替换
- 搜索条件标题同步替换
- 数据库技术名一期保留，二期再评估是否做接口级统一重命名

### 5. 用户可见字段替换原则

#### 5.1 替换范围

下面这些位置必须统一替换成天枢科技字段体系：

- 菜单名称
- 页面标题
- 页签名称
- 按钮名称
- 列头名称
- 导入模板列头
- 导出表头
- 筛选项标题
- 空态与错误提示中的对象名

#### 5.2 保留技术名的范围

下面这些位置允许一期继续保留技术名：

- ORM 模型名
- Python 字段名
- XML view id
- JS 组件 id
- 数据库列名
- 外部接口内部映射层

#### 5.3 建议补充的字段映射字典

为了让后续实现不反复争论，建议在本方案确认后补一份“用户可见词 -> 技术词”的固定字典，例如：

- 运单详情 -> `logistics.dispatch.waybill`
- 客户明细 -> `waybill customer line`
- 货物明细 -> `waybill customer goods line`
- 异常单 -> `logistics.trace.exception`
- 留痕事件 -> `logistics.trace.event`

## Navigation Strategy

### 1. 导航纠偏原则

- 一级导航必须代表“企业模块”，不能直接代表物流内部工位
- `天枢科技首页` 是整个系统的总入口，不是物流模块的别名首页
- `物流` 只是一级模块之一，物流内部再拆二级工作区
- 用户看到的第一层结构应是“企业有哪些模块”，而不是“物流内部有哪些表”

### 2. 新一级导航建议

建议统一为：

1. 首页
2. 物流
3. 车队
4. 员工
5. 库存
6. 所有统计图表
7. 发票
8. 系统设置

补充说明：

- 这 8 个一级模块直接平铺在顶部导航
- 不再通过左上角品牌区下拉菜单再次重复展示
- 品牌区只承担“返回首页”的角色，不再承担“应用列表”的角色

### 3. 物流模块二级导航建议

进入 `物流` 模块后，再展示物流内部工作区：

1. 调度
2. 运单
3. 留痕
4. 证据
5. 异常
6. 导入中心

### 4. 当前应隐藏的模块

现阶段建议从用户主导航中隐藏：

- `讨论`
- `联系人`
- `应用`
- `链接追踪器`
- 左上角应用下拉菜单

### 5. 隐藏原则

- 只隐藏入口，不立即删除底层依赖
- `mail.thread`、`mail.activity`、`res.partner` 仍可继续作为底层能力使用
- `应用` 与 `链接追踪器` 若未来确有业务场景需要，可通过菜单、权限或角色开关重新开放
- 若后续需要重新开放，再通过菜单和权限重新启用

### 5.1 命名替换补充

- `数据看板 / 仪表盘` 统一收口为 `所有统计图表`
- `链接追踪器` 当前阶段默认隐藏；若后续开放，统一命名为 `追踪链接`

### 6. 用户体验效果

用户当前看到的导航，应该先理解“这是天枢科技系统”，再理解“物流是其中一个重点模块”。  
物流业务导航应下沉到物流模块内部，而不是把全系统都做成物流内部导航。

### 7. 导航显隐实施原则

#### 5.1 隐藏层级

建议分三层处理：

1. 主导航层隐藏  
用户日常工作路径中不再看到 `讨论`、`联系人`

2. 搜索与快捷入口层隐藏  
全局搜索和常用入口中不主动推荐这两个模块

3. 权限层保留  
管理员和技术人员仍可通过配置入口访问，以避免底层能力失控

#### 5.2 例外规则

- 如果某个业务页必须依赖 `res.partner` 做客户/门店维护，则通过业务页内嵌入口承接
- 如果某个业务页必须依赖 chatter，则在业务页内部保留，而不是重新开放 `讨论` 独立入口

#### 5.3 验收标准

- 普通物流用户首次进入系统时，不应再看到 `讨论`、`联系人`
- 普通物流用户首次进入系统时，不应再看到 `应用`、`链接追踪器`
- 普通物流用户首次进入系统时，不应再看到左上角 Odoo 风格应用下拉菜单
- 用户仍可正常创建客户、门店、跟进活动，不因入口隐藏而失去底层能力
- 普通用户首次进入系统时，顶层先看到 `首页 / 物流 / 车队 / 员工 / 库存 / 所有统计图表 / 发票 / 设置` 这类企业模块
- 普通用户不应再把 `调度 / 运单 / 留痕 / 证据 / 异常` 误认为整个系统的一级结构

## 首页设计

### 1. 首页定位

首页不是单纯欢迎页，而是：

- 天枢科技系统总入口
- 企业模块导航落点页
- 物流等重点模块的工作看板入口
- 新用户使用引导入口
- 常用业务入口聚合页

### 2. 首页结构

建议首页拆成 6 个区块：

#### 2.1 顶部品牌区

- 系统名称：`天枢科技物流系统`
- 当前日期
- 当前登录用户角色
- 一级模块入口：物流、车队、员工、库存、所有统计图表、发票、设置
- 左上品牌区只负责返回首页，不再弹出“仪表盘 / 链接追踪器 / 应用”下拉层
- 常用快捷入口：进入物流工作台、导入订单、查看异常、查看运单

#### 2.2 今日工作区

- 本区为首页中的“物流重点区”，不是整个首页的唯一功能
- 今日待处理异常
- 今日待补证据
- 今日待执行运单
- 今日超时风险运单

每张卡既显示数据，也直接作为处理入口。

#### 2.3 物流核心指标区

- 今日运单总量
- 已签收率
- 证据补齐率
- 异常运单率
- 超时风险率
- 门店签收完成率

#### 2.4 趋势看板区

- 异常运单率日环比
- 运单完成率日环比
- 证据补齐率日环比
- 异常类型分布趋势
- 批次执行趋势

#### 2.5 系统使用指引区

分角色展示：

- 新用户：先理解一级模块，再进入对应模块工作区
- 调度：进入物流 -> 调度，先看批次和待执行运单
- 运营：进入物流 -> 异常 / 证据，先看异常和待补证据
- 管理层：先看首页摘要，再进入 `所有统计图表` 看环比和排行
- 财务或开票角色：从首页直接进入发票模块，不强行经过物流模块

### 2.7 首页系统模块顺序建议

首页中的“系统模块”卡片顺序，应与顶部一级导航保持一致，建议统一为：

1. 物流
2. 车队
3. 员工
4. 库存
5. 所有统计图表
6. 发票
7. 设置

补充原则：

- `物流` 永远放在系统模块区前部，作为当前阶段主工作模块
- `所有统计图表` 放在运营和管理常用模块组中，不再命名为 `仪表盘`
- `发票` 下调到 `设置` 左侧，避免在当前阶段过度前置
- `应用`、`链接追踪器` 不进入首页系统模块区

#### 2.6 最近动态区

- 最新异常
- 最新补证据
- 最新签收完成
- 最新高风险批次

### 3. 首页交互原则

#### 3.1 首页不是报表页

- 首页只展示“足够决策”的摘要，不承载全部分析能力
- 用户在首页的典型动作应是：
  - 快速看风险
  - 快速进处理页
  - 快速知道今天从哪里开始

#### 3.2 首页卡片交互要求

- 每张卡片都必须可点击
- 每张卡片点击后都要有明确跳转目标：
  - 业务列表
  - 数据看板
  - 导入页
  - 重点对象详情页

#### 3.3 首页加载优先级

为避免首页过重，建议按优先级加载：

1. 顶部品牌区与今日工作区
2. 物流核心指标区
3. 趋势看板区
4. 最近动态区
5. 指引与帮助区

### 4. 首页角色化策略

#### 4.1 调度角色

- 默认优先看到：
  - 今日待执行运单
  - 待装车批次
  - 超时风险批次

#### 4.2 运营角色

- 默认优先看到：
  - 待处理异常
  - 待补证据
  - 今日新增异常

#### 4.3 管理层

- 默认优先看到：
  - 异常运单率
  - 异常运单率日环比
  - 严重异常数
  - 高风险批次排行

#### 4.4 新用户

- 默认优先看到：
  - 系统使用引导
  - 常用入口说明
  - 标准导入模板入口

### 5. 首页验收标准

- 首页必须能让首次进入系统的用户知道先从哪里开始
- 首页必须能让用户理解一级模块结构，不把物流内部导航误认为整个系统结构
- 首页必须能让运营和调度在 10 秒内识别当天重点
- 首页必须能在不进入数据看板的前提下完成第一轮分诊
- 首页不能退化成简单的欢迎页或指标堆叠页

### 0. 命名纠偏

### 1. 指标原则

- 优先物流业务指标，不堆泛 ERP 统计
- 指标要能驱动动作，不只做展示
- 指标要支持日维度、周维度、月维度

### 2. 推荐 P0 指标

#### 2.1 执行指标

- 运单总量
- 批次总量

- 在途运单数

- 已完成运单数

#### 2.2 风险指标

- 异常运单率日环比
- 超时运单率
- 待处理异常数
- 严重异常数
- 待补证据异常数

#### 2.3 留痕与证据指标

- 留痕覆盖率
- 到店留痕完成率
- 签收留痕完成率
- 证据补齐率
- 单运单平均证据数

#### 2.4 履约指标

- 门店签收完成率
- 客户维度异常率
- 批次维度异常率
- 司机维度异常率

### 3. 推荐 P1 指标

- 客户异常率排行
- 门店异常率排行
- 司机异常率排行
- 批次异常率排行
- 证据缺失原因分布

### 4. 指标定义冻结建议

为避免上线后统计口径反复变更，建议在实现前先冻结下面 4 项：

1. 统计周期  
默认按自然日，补充近 7 日、近 30 日

2. 运单总量口径  
按创建量、执行量还是配送日期口径，需要明确

3. 异常运单率口径  
分母是全部运单还是已执行运单，需要明确

4. 环比口径  
日环比、周环比、月环比的比较基准要统一

### 5. 指标落地优先级建议

- P0：首页必须可见，且具备可操作性
- P1：放入完整数据看板，支持分析
- P2：后续再做排行、钻取、筛选联动

## 订单导入重设计

### 1. 当前问题

当前运单下订单明细模型较轻，只有摘要字段，尚不足以承接：

- 一个运单多个客户
- 一个客户多个货物
- 货物数量、重量、体积、配送备注等更细颗粒度数据

### 2. 目标结构

建议将现有“运单下订单明细”扩展为 3 层导入模型：

```text
运单
  -> 运单客户
      -> 客户货物明细
```

### 3. 推荐模型方向

#### 3.1 运单主表

保留：

- 运单号
- 批次号
- 波次号
- 配送日期
- 仓库
- 车辆
- 司机
- 运单状态

#### 3.2 运单客户子表

新增建议对象：

- 一个运单对应多个客户
- 每条客户子表记录记录该客户在此运单下的履约信息

建议字段：

- 运单号
- 客户编号
- 客户名称
- 门店编号
- 门店名称
- 客户配送备注
- 客户签收要求
- 客户货物总数量
- 客户货物总件数
- 客户货物总重量
- 客户货物总体积

#### 3.3 客户货物明细子表

新增建议对象：

- 一个客户子表记录对应多个货物明细

建议字段：

- 运单号
- 客户编号
- 货物编码
- 货物名称
- 规格
- 数量
- 件数
- 单位
- 重量
- 体积
- 温层
- 包装类型
- 货物备注

补充说明：

- `数量` 表示该货物在当前运单下的业务数量，例如箱数、瓶数、托数中的基础计量值
- `件数` 表示更贴近物流执行的包装件数量，用于装车、签收、异常核对
- 若一个货物同时存在“业务数量”和“物流件数”，两者都应保留，不建议只保留其中一个

### 4. 与现有模型的关系

可落地执行的推荐方式：

#### 4.1 一期过渡方案

- 保留现有 `waybill order line`
- 先将其重解释为“运单客户明细或运单履约明细”
- 追加必要字段

#### 4.2 二期标准方案

新增两张子表：

- `logistics.dispatch.waybill.customer.line`
- `logistics.dispatch.waybill.customer.goods.line`

这样更符合你的业务口径，也更利于导入模板标准化。

### 5. 三层结构与页面结构的对应关系

为了避免“导入模型”和“页面展示模型”脱节，建议直接对应如下：

- 运单主表 -> 运单概览页签
- 运单客户子表 -> 客户明细页签
- 客户货物明细子表 -> 货物明细页签

这样导入完成后，用户可以直接在详情页中验证导入结果，而不是进入隐藏技术模型查看。

## 导入模板设计

### 1. 结论

如果自动匹配和自由导入会显著增加复杂度，建议建立“标准导入模板”作为主路径。

### 2. 推荐导入模式

采用双轨制：

#### 2.1 标准模板导入

适合业务团队正式导入，优先推荐。

优点：

- 字段固定
- 层次明确
- 校验更容易
- 培训成本更低

#### 2.2 自由表头导入

适合作为兼容模式，保留给技术或历史数据迁移使用。

优点：

- 兼容旧表
- 便于一次性历史迁移

缺点：

- 匹配规则复杂
- 错误率更高

### 3. 推荐标准模板结构

建议先采用“单张明细表模板”，每一行代表“某运单下某客户的一条货物明细”：

#### 3.1 模板列建议

- 运单号
- 批次号
- 波次号
- 配送日期
- 客户编号
- 客户名称
- 门店编号
- 门店名称
- 客户配送备注
- 货物编码
- 货物名称
- 规格
- 数量
- 件数
- 单位
- 重量
- 体积
- 温层
- 包装类型
- 货物备注

#### 3.2 导入聚合逻辑

- 相同 `运单号` 聚合到同一运单
- 相同 `运单号 + 客户编号` 聚合到同一客户子表
- 不同货物明细按行写入客户货物子表

#### 3.3 标准模板字段分层建议

为了方便培训和后续做导入校验，建议在模板说明中将字段分成 4 组：

1. 运单层字段  
`运单号 / 批次号 / 波次号 / 配送日期`

2. 客户层字段  
`客户编号 / 客户名称 / 门店编号 / 门店名称 / 客户配送备注`

3. 货物层字段  
`货物编码 / 货物名称 / 规格 / 数量 / 件数 / 单位 / 重量 / 体积 / 温层 / 包装类型 / 货物备注`

4. 系统辅助字段  
`行序号 / 导入批次标识 / 备注`

#### 3.4 推荐模板版本策略

建议模板采用版本号管理，例如：

- `TSL-IMPORT-WAYBILL-V1`
- `TSL-IMPORT-WAYBILL-V2`

这样可以避免后续字段新增后，旧模板与新模板难以区分。

#### 3.5 模板下载入口建议

标准模板不应藏在帮助文档中，建议后续直接放在：

- 首页快捷入口
- 物流 -> 运单列表页
- 导入页顶部说明区

### 4. 导入校验规则

#### 4.1 必填校验

- 运单号
- 客户编号
- 货物名称
- 数量

建议增强必填：

- 当业务场景对装车、交接、签收核对要求较高时，`件数` 也应纳入必填

#### 4.2 唯一校验

- 运单号在同一次导入中必须唯一归组
- `运单号 + 客户编号 + 货物编码 + 行序号` 应可唯一定位一条货物记录

#### 4.3 合法性校验

- 重量、体积必须为非负数
- 数量必须为正数
- 件数必须为非负整数；若填写则应大于 0
- 批次号、波次号若存在，必须能匹配当前系统主数据

#### 4.4 分层一致性校验

- 同一 `运单号` 下的配送日期、仓库、车辆、司机等主信息必须一致
- 同一 `运单号 + 客户编号` 下的客户名称、门店编号、门店名称必须一致
- 同一货物行若同时提供 `货物编码` 与 `货物名称`，二者必须能对得上业务主数据或允许作为自由货物导入

### 5. 导入结果落位

导入完成后：

- 运单主信息进入运单详情页
- 客户子表进入运单详情中的“客户明细”页签
- 货物子表进入客户明细下的“货物明细”区域

### 6. 导入流程设计

#### 6.1 用户流程

建议后续统一为下面 6 步：

1. 下载标准模板
2. 按模板填写数据
3. 上传文件
4. 系统预校验并返回错误清单
5. 用户修正后再次上传
6. 正式导入并生成导入结果报告

#### 6.2 预校验结果页

建议预校验页至少展示：

- 总行数
- 通过行数
- 失败行数
- 失败原因分类
- 可下载的错误明细

#### 6.3 正式导入结果页

建议正式导入后展示：

- 新建运单数
- 新建客户子表数
- 新建货物明细数
- 更新记录数
- 跳过记录数
- 异常记录数

#### 6.4 错误反馈原则

- 错误信息优先说业务对象，不优先说技术字段
- 错误信息必须带行号
- 错误信息必须能告诉用户下一步改什么

### 3. 客户明细页建议内容

- 客户编号
- 客户名称
- 门店编号
- 门店名称
- 客户配送备注
- 客户签收要求
- 客户货物总数量
- 客户货物总件数
- 客户货物总重量
- 客户货物总体积
- 异常状态摘要

### 4. 货物明细页建议内容

- 客户编号
- 货物编码
- 货物名称
- 规格
- 数量
- 件数
- 单位
- 重量
- 体积
- 温层
- 包装类型
- 货物备注

### 5. 运单详情页验收标准

- 用户在详情页内就能看清“这个运单给了哪些客户、每个客户有什么货、每种货有多少”
- 用户不需要再通过技术字段表去反推导入结果
- 留痕与异常页签继续保留，但阅读顺序应排在客户与货物之后

## 模块隐藏设计

### 1. 讨论模块

建议当前阶段：

- 从顶部导航隐藏
- 从主工作路径隐藏
- 保留底层 `mail.thread` 能力
- 运单、异常、留痕详情中的 chatter 可后续单独评估是否保留

### 2. 联系人模块

建议当前阶段：

- 从主导航隐藏
- 不再让业务用户直接进入联系人中心
- 客户、门店仍通过物流页面中的业务入口维护

### 3. 风险提示

隐藏不等于废弃：

- `res.partner` 仍然是客户 / 门店底座
- `mail` 仍然是消息和活动底座

因此这里只是“隐藏入口”，不是“删除依赖”。

### 4. 非当前阶段模块补充策略

#### 4.1 应用

建议当前阶段：

- 从顶部导航隐藏
- 从首页系统模块区隐藏
- 从普通业务用户入口中隐藏
- 仅在后续确有系统扩展或管理员配置需要时再重新开放

#### 4.2 链接追踪器

建议当前阶段：

- 从顶部导航隐藏
- 从首页系统模块区隐藏
- 不作为物流业务用户的常用功能模块展示

若后续确需重新开放：

- 推荐先更名为 `追踪链接`
- 再评估其是否应放入 `设置` 或单独的营销/运营工具分组，而不是与物流主模块并列

#### 4.3 左上角应用下拉菜单

建议当前阶段：

- 直接取消，不保留“精简版应用列表”
- 不再作为模块切换的备用入口
- 若未来企业模块数量明显增加，再重新评估是否需要新的模块切换器，但不建议回退为 Odoo 默认应用下拉菜单形态

## Risks

### 1. 如果追求“完全摆脱 Odoo”过快，可能会把项目拉到高风险区

需要强调：

- 用户可见层彻底品牌化是应该做的
- 但 ORM、模型技术名、底层依赖不建议一期全面重命名

否则会显著增加：

- 升级风险
- 历史数据兼容风险
- 文档和接口同步成本

### 2. 首页如果同时承担太多职责，容易变成信息堆叠页

因此首页必须坚持：

- 少量高价值指标
- 明确入口
- 明确引导

### 3. 导入结构如果一步到位改太深，联调周期会变长

因此建议：

- 先做标准模板
- 再做三层模型
- 最后做智能兼容导入

### 4. 字段字典如果不先冻结，后续页面和模板会持续返工

因此建议：

- 先确认用户可见字段命名
- 再做页面
- 最后再补接口和导出统一

### 5. 首页默认落地页切换过早，可能影响老用户路径

因此建议：

- 先灰度开放首页
- 允许一段时间保留旧入口
- 收集反馈后再切成默认 landing page
