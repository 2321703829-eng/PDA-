## 1. 文档定位

- 本文用于沉淀企业隔离 `P1` 讨论中的三个关键判断。
- 本文不是新方案稿，而是对当前方案收口逻辑的解释性说明。
- 本文主要回答：
  - 为什么当前企业隔离专题会先补 `trace / evidence / exception`
  - 为什么 `customer_line` 还没有真正成为图片、留痕、异常的主阅读入口
  - 为什么如果不围绕 `customer_line` 建立主阅读入口，就会影响当前定义下的 `P1`

## 2. 为什么当前专题先补 `trace / evidence / exception`

这并不代表企业隔离专题跑偏成了留痕专题，而是因为当前企业隔离 `P1` 的真实目标不是平台控制面，而是：

- 数据库级企业隔离底盘成立
- 每个租户库能运行同一套现有物流模块
- 租户化后不打坏当前物流主线、页面主阅读链和图片阅读链

在这个前提下，当前最稳定的主链其实已经是：

- `wave -> batch -> waybill -> customer_line -> order_line -> goods_line`

真正最容易在租户化过程中发生口径漂移的，是下面三层：

- `trace`
- `evidence`
- `exception`

原因是执行主链对象已经基本稳定，但以下问题如果不先锁住，租户化以后仍然会乱：

- `customer_line` 到底是不是门店节点主阅读入口
- 图片业务阅读到底围绕谁
- 正式证据对象到底挂谁
- 异常到底围绕谁流转
- 租户内查看、提交、处理、导出边界怎么切

所以当前补出的这些文档，本质上是在处理：

**企业隔离 `P1` 下，最容易因为租户化而失控的业务承接层设计。**

## 3. 为什么 `customer_line` 还没有真正成为主阅读入口

当前 `customer_line` 已经在对象和页面上存在，但它还没有把“主阅读入口”真正落成闭环。

更准确地说，`customer_line` 目前只完成了：

- 对象存在
- 页面存在
- 业务意义存在

但还没有完整完成下面四层。

### 3.1 页面入口层还主要长在 `waybill`

当前 `waybill` 页已经有留痕、证据、异常的聚合字段和摘要入口，且 `trace_core` 已给运单表单增加留痕 smart button。

但 `customer_line` 页当前主要还是：

- 客户信息
- 汇总信息
- 货物明细

尚未形成稳定的：

- 留痕摘要区
- 证据摘要区
- 异常摘要区
- 直达 trace / evidence / exception 的入口

所以它现在还是“有节点页”，还不是“主阅读入口页”。

### 3.2 查询与服务层还主要按 `waybill` 拉数据

当前运单页的证据读取逻辑仍然是直接按 `waybill_id` 查询证据列表。

这意味着：

- 实现层的图片阅读链仍以运单聚合视角为主
- `customer_line` 还没有形成自己的 reader 或自己的查询域
- 门店节点页还不能稳定承接“按门店节点读图、读留痕、读异常”

### 3.3 正式挂点没问题，但 `customer_line` 的反读桥还没补完整

当前正式对象挂点本身是正确的：

- `trace_event` 继续围绕 `batch / waybill`
- `evidence` 继续围绕 `trace_event`
- `exception` 继续围绕 `waybill / batch / trace_event`

问题不在正式挂点，而在于：

**从 `customer_line` 到这些正式对象的反读桥还没有真正补完整。**

也就是还缺：

- `customer_line` 如何找到相关 trace
- `customer_line` 如何读取本节点相关证据
- `customer_line` 如何看到本节点相关异常摘要

### 3.4 图片命中与补链逻辑还没正式落稳

当前口径已经收口到：

- 图片业务阅读优先围绕 `customer_line`
- 图片命中优先按 `waybill_no + customer_line_no`
- 兜底按 `waybill_no + store_no`

但实际实现层，`image_package` 虽然已经进入任务对象枚举，图片包导入、命中、补链、证据化流程还没有完整落到模块里。

没有这层，`customer_line` 就只能停留在“应该成为入口”，而不是“系统已经按它来读”。

## 4. 为什么不围绕 `customer_line` 建主阅读入口，会影响当前定义下的 `P1`

这里需要先说清楚一句话：

**不是说没有 `customer_line` 就完全不能做 `P1`，而是说如果不把它立成主阅读入口，做出来的就不是当前定义下合格的 `P1`。**

### 4.1 `P1` 的要求不只是“分库成功”和“模块能装”

当前企业隔离 `P1` 的定义不是只有：

- 分库成功
- 模块能装
- 页面能打开

还包括：

- 现有物流主线不变形
- 当前四期前端阅读链不变形
- 图片、留痕、异常阅读口径不倒退

既然当前有效基线已经收口成：

- `waybill -> customer_line -> order_line`
- `waybill -> customer_line -> 图片预览 / 留痕 / 证据`

那 `P1` 如果不围绕 `customer_line` 建主阅读入口，就已经偏离当前 `P1` 定义。

### 4.2 不主动立 `customer_line`，系统会自然倒回运单独占阅读

如果不补 `customer_line` 入口，最省事的实现路径一定会变成：

- 留痕继续只在 `waybill` 看
- 图片继续只在 `waybill` 按整单聚合看
- 异常继续只从 `waybill` 或异常列表进

这样当然“能用”，但它会把门店节点层重新压扁。

结果就是：

- 店侧事实阅读会越来越糊
- 图片只剩整单汇总视角
- 哪个门店节点缺证据、哪个节点有异常，很难稳定阅读

这会直接和四期前端已经锁下来的对象分层冲突。

### 4.3 `customer_line` 不是装饰层，而是门店现场事实承接层

当前对象链之所以恢复出 `customer_line`，不是为了页面好看，而是因为业务上确实需要这一层：

- 一个 `waybill` 下可能有多个门店节点
- 每个门店节点的到店、签收、图片、异常上下文不完全一样
- 如果不在 `customer_line` 这一层承接，很多现场事实只能被粗暴并回运单级聚合

所以问题不是“要不要多一个入口”，而是：

**没有 `customer_line` 主阅读层，店侧事实就会被运单级汇总再次吞掉。**

### 4.4 这不是可轻松后补的点，而是会牵动后续返工

如果 `P1` 先不立 `customer_line` 主阅读入口，后面一旦要补，通常会连带牵动：

- 页面入口
- 查询 domain
- 证据分组方式
- 异常摘要口径
- 导出范围
- 审计口径

所以这不是“先跳过，后面轻轻补一下”的问题，而更像是：

**如果本轮不锁，后续 `evidence` 和 `exception` 很可能一起返工。**

## 5. 当前最准确的结论

### 5.1 关于当前专题为什么偏向 `trace / evidence / exception`

- 当前补这些文档，不是因为企业隔离专题跑偏
- 而是因为企业隔离 `P1` 下最容易失控的正是这三层业务承接

### 5.2 关于 `customer_line` 为什么还没真正站住主阅读入口

- 方向已经锁了
- 对象和页面已经有了
- 但入口、查询、反读桥、补链、权限与导出闭环还没跟齐

### 5.3 关于“不围绕 `customer_line` 是否还能做 `P1`”

- 从纯技术角度讲，不围绕 `customer_line`，也能做出一个“能跑”的租户化版本
- 但从当前已经锁定的 `P1` 目标讲，那不算合格的 `P1`
- 因为它会违背当前前端基线，也会把门店节点阅读链做回旧口径

## 6. 一句话收口

当前企业隔离 `P1` 的关键，不只是把系统分成多个租户库，而是要在租户化后继续保住当前已经稳定下来的对象分层与阅读链；而这件事能不能成立，`customer_line` 是否真正成为门店侧主阅读入口，是最关键的判定点之一。
