# 企业隔离方案可行性与分期落地调整说明

## 1. 文档定位

本文作为当前企业隔离专题的现行总纲，只保留与当前落地方案直接相关的内容。

本文不再展开旧 `.docx` 的平台化原方案介绍，也不再把“完整 SaaS 多租户平台设计”作为本期设计主体；但 `P0 / P1` 的设计边界、工作流、交付重点和可用性判断仍需完整保留，供后续设计、拆单和联调直接使用。

当前统一目标是：

**在不打散现有物流主线的前提下，先把企业隔离 `P0 / P1` 的设计和落地边界锁清楚，并让 `P1` 具备可直接指导开发与联调的完整度。**

---

## 2. 当前主判断

### 2.1 总边界

- 企业之间隔离：默认采用数据库级隔离
- 同一企业内部多法人或多公司协同：才考虑 `multi-company`
- 当前专题以 `P0 / P1` 为设计主体，不把 `P2 / P3` 当成当前落地主线

### 2.2 当前业务基线

本专题必须兼容当前项目已经稳定下来的物流与前端基线：

- 执行与数据主链：`wave -> batch -> waybill -> customer_line -> order_line -> goods_line`
- 页面主阅读入口：`waybill`
- 页面主阅读链：`waybill -> order_line`
- 图片阅读链：`waybill -> 图片预览 / 留痕 / 证据`
- 追溯主线：`waybill -> trace -> evidence -> exception`

### 2.3 当前模块边界

当前企业隔离设计默认承接以下模块边界，不另起一套 `tms_*` 业务对象体系：

- `logistics_base`
- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`

### 2.4 当前关键判断

- `waybill` 仍是正式留痕主对象
- `waybill` 是当前 `P1` 的主阅读入口
- `customer_line` 在“一运单一门店”强约束下收口为运单下的兼容 / 扩展结构层
- 图片业务主阅读优先围绕 `waybill`
- 正式证据对象仍围绕 `trace_event`
- 异常优先围绕 `waybill / batch / trace_event`

## 3. 当前边界与基准

### 3.1 当前项目边界

本专题当前仍以“单租户物流系统基线之上的企业隔离扩展”为前提，不把项目重心改写成平台级多租户产品设计。

当前现实边界包括：

- 当前主要目标仍是物流执行与追溯系统设计沉淀
- 当前成熟主线仍是运单主对象与留痕主流程
- 当前文档和模块都以物流业务闭环为主，而不是以平台级租户编排为主
- 企业隔离设计必须服从当前物流主线、四期前端阅读链和现有模块边界

### 3.2 当前设计基准

本专题默认以以下文档为准：

- `docs/context/odoo_logistics_context.md`
- `docs/context/odoo_logistics_feasibility.md`
- `docs/architecture/ARCHITECTURE.md`

- `专题设计/前端设计/四期前端优化设计/00_导航与总纲/2026-04-21_四期页面信息架构与阅读链方案.md`
- `专题设计/前端设计/四期前端优化设计/00_导航与总纲/数据库与接口现状盘点说明-2026-04-21.md`

如果其他文档与本文冲突，以本文和上述当前基线为优先。

### 3.3 当前最重要的收口原则

- 企业之间隔离：优先靠数据库
- 企业内部多法人协同：才使用 `multi-company`
- 物流正式留痕主对象：仍以 `waybill` 为核心
- `P1` 数据对象链继续保留：`wave / batch / waybill / customer_line / order_line / goods_line`
- 当前已确认“一运单一门店”强约束后，`P1` 页面主阅读入口统一收口为：`waybill`
- 图片业务阅读统一收口为：`waybill -> 图片预览 / 留痕 / 证据`
- `customer_line` 当前不再作为 `P1` 主阅读入口，而作为结构、快照、导入导出和后续扩展层保留
- 新方案不能脱离当前执行主线与追溯主线，也不能与四期对象分层冲突

## 4. 当前分期口径

### 4.1 `P0`：多数据库底盘验证期

#### 目标

确认数据库级企业隔离在当前 Odoo 环境可稳定运行，且不会在访问路由、数据库选择、基础模块安装和备份恢复链路上出现结构性问题。

#### 本期要解决的问题

- 不同企业是否可以稳定命中各自数据库
- 子域名、反向代理、`Host` 透传和 `dbfilter` 是否能稳定配合
- 数据库列表、数据库管理入口是否能在正式访问场景下正确关闭
- 单个租户库能否人工完成建库、装模块、初始化、备份和恢复
- 租户库与文件存储链路能否按“成对恢复”理解和验证

#### 本期大致工作流

1. 约定租户库命名规则与子域名规则。
2. 配置反向代理、`Host` 透传与 `dbfilter`。
3. 手工创建示例租户数据库。
4. 在租户库安装 `logistics_base`、`logistics_dispatch` 等当前基础模块。
5. 初始化租户管理员与基础参数。
6. 通过独立域名访问租户库并完成登录验证。
7. 验证数据库列表与数据库管理入口在正式链路下不可误入。
8. 验证单租户库备份、恢复与文件存储配对恢复链路。

#### 本期关注重点

- `dbfilter` 规则是否简单、稳定、可运维
- 子域名到数据库映射是否清晰、可追踪
- 关闭数据库列表与数据库管理页是否真正生效
- 备份恢复时是否把数据库与文件存储视作一组对象
- 当前做法是否仍停留在“人工运维可跑通”而不是“自动化平台编排”

#### 本期交付结果

- 可以明确数据库级企业隔离在当前 Odoo 环境是否成立
- 可以明确最小人工运维链路是否成立
- 可以为 `P1` 提供可复用的访问与建库前提

#### 本期不做

- 不做平台后台
- 不做自动开租户
- 不做套餐、授权、到期、降级
- 不做跨租户指标汇总
- 不做灰度发布和平台调度中心

### 4.2 `P1`：现有物流模块租户化落地期

#### 目标

让每个租户数据库都能运行同一套现有物流模块，并保持当前物流业务主线、页面阅读链、图片阅读链和追溯链不变形。

#### 本期要解决的问题

- 当前 `wave / batch / waybill / customer_line / order_line / goods_line` 主链能否稳定落在租户库内
- `trace / evidence / exception` 三层是否能在租户库中独立安装和运行
- 在“一运单一门店”强约束下，`waybill` 是否能稳定承担门店级主阅读入口
- 图片业务命中、证据补链、异常联动是否能和当前四期前端口径保持一致
- 租户内角色边界、记录规则、导入审计链和联调顺序是否能被清晰定义

#### 本期大致工作流

1. 在目标租户库安装 `logistics_base`、`logistics_dispatch`。
2. 验证 `waybill / customer_line / order_line / goods_line` 主链可正常读取。
3. 在租户库安装 `logistics_trace_core`，验证运单与批次留痕链。
4. 在租户库安装 `logistics_trace_evidence`，验证图片阅读、图片命中与 `trace_event` 挂点。
5. 在租户库安装 `logistics_trace_exception`，验证异常对象、状态流转和证据反读。
6. 按租户内角色补齐查看、提交、处理、导出等边界。
7. 按 `trace_core -> evidence -> exception -> 三层联动回归` 固定顺序联调。

#### 本期关注重点

- 不能为企业隔离重新起一套 `tms_*` 业务对象体系
- 不能把 `customer_line` 再误抬成当前 `P1` 的主阅读入口
- 不能把图片直接主挂到 `order_line`
- 不能因为页面阅读链变化而改写正式 `trace_event` 和 `evidence` 主挂点
- 不能把 `dispatch_main` 与 `image_package` 混成一条审计链

#### 本期交付结果

- 每个租户数据库都能跑同一套现有物流模块
- 当前物流主线与页面阅读链在租户库中保持稳定
- `trace / evidence / exception` 三层形成最小业务闭环
- 设计、实施、验收和联调可以围绕统一口径推进

#### 本期不做

- 不做平台库和平台后台
- 不做跨租户汇总看板
- 不做套餐、版本、授权和计费
- 不做自动化能力快照同步
- 不把异常扩成完整工单平台

## 5. `P1` 必须锁住的统一口径

### 5.1 对象口径

- `waybill`：正式留痕主对象
- `waybill`：当前 `P1` 主阅读入口
- `customer_line`：运单下兼容 / 扩展结构层
- `order_line`：`customer_line` 下业务明细层
- `goods_line`：底层货物事实层
- `trace_event`：正式留痕事件对象
- `evidence`：正式证据对象
- `exception`：异常对象

### 5.2 阅读口径

- 页面主阅读入口：`waybill`
- 页面主阅读链：`waybill -> order_line`
- 图片业务阅读链：`waybill -> 图片预览 / 留痕 / 证据`
- 正式追溯链：`waybill -> trace_event -> evidence -> exception`

### 5.3 导入与审计口径

租户内导入审计链建议统一保留为：

- `import_source_file`
- `import_task`
- `import_task_line`
- `import_error_line`

其中任务类型至少区分：

- `dispatch_main`
- `image_package`

### 5.4 权限口径

- 企业隔离边界先由数据库保证
- 租户内角色权限再由 `groups / access / rule / action` 承接
- 页面隐藏不等于安全边界
- 关键业务动作仍要落到模型层与接口层校验

## 7. 当前可用性边界

### 7.1 `P1` 的可用性边界

`P1` 不是“设计讨论期”，而是企业隔离下业务正式可用的第一期。

这句话的含义是：

- 用户不需要等到 `P2` 完成后，才可以在企业隔离前提下使用物流系统
- 只要 `P0` 底盘成立，`P1` 就应能支撑租户库内的物流主链、图片阅读、留痕、证据和异常闭环
- `P1` 解决的是“企业隔离下业务能不能用、能不能稳定联调”，而不是“平台能不能自动化运营”

### 7.2 `P2` 的可用性边界

`P2` 解决的是平台能否更高效地管理租户。

更准确地说：

- `P2` 不是“系统才开始可用”
- `P2` 是“系统从人工运维管理升级为平台化管理”

### 7.3 `P3` 的可用性边界

`P3` 解决的是平台能否规模化运营和持续商业化。

也就是说：

- `P3` 不是基础业务可用性的起点
- `P3` 才开始承担套餐、授权、指标仓、灰度升级等商用能力

---

## 8. 当前推荐推进顺序

当前专题继续推进时，建议固定按下面顺序：

1. 先锁总边界与 OBB
2. 再补 `trace / evidence / exception` 三块细稿
3. 再做差距盘点
4. 再拆开发任务
5. 最后按验收清单反推联调顺序

当前建议联调顺序：

1. `trace_core`
2. `evidence`
3. `exception`
4. 三层联动回归

## 10. 一句话结论

当前企业隔离专题不再把“完整平台化多租户方案”当成本期设计主体，而是先把“数据库级企业隔离 + 现有物流主线 + 四期前端已稳定阅读链”稳稳接起来，优先完成 `P0 / P1` 的设计收口、实施准备和联调闭环。
