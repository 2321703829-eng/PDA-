# 2026-05-08 企业隔离回归原设计实施方案

## 1. 目标

当前企业隔离环境已经偏向：

- 多端口
- 多容器
- 单库绑定

本次目标不是继续叠加这种模式，而是新开一套恢复环境，让企业隔离重新回到原设计主线：

- `19099` 作为新的内部验证端口
- 同一套 Odoo 服务承接多个租户数据库
- 不通过数据库选择器切库
- 只通过 `Host + dbfilter` 命中租户库

## 2. 目标状态

本次恢复后的目标形态：

- Odoo 容器：
  - 新建 1 套恢复环境容器
- 访问端口：
  - `19099`
- 数据库实例：
  - `enterprise-isolation-pg18`
- 目标租户库：
  - `tenant_hq`
  - `tenant_kebi`
  - `tenant_template`

目标访问方式：

- `tenant-hq.<base_domain>:19099`
- `tenant-kebi.<base_domain>:19099`
- `tenant-template.<base_domain>:19099`

目标路由方式：

- 同一个 `19099`
- 不同 `Host`
- `dbfilter` 命中不同数据库

## 3. 与现状的边界

本方案明确不直接改动以下现有环境：

- `19069`
- `19079`
- `19089`

原因：

- `19069` 已承担当前小程序导入与联调主链路
- `19089` 已绑定 `tenant_hq`，但模块升级历史较乱
- 原设计恢复验证不应建立在污染现有可用环境的前提上

所以本次策略是：

- 保留现状
- 新开 `19099`
- 用 `19099` 验证原设计是否成立

## 4. 设计原则

### 4.1 单服务多库

`19099` 对应的新 Odoo 服务不再写死：

- `db_name = tenant_hq`

而应满足：

- `db_host = enterprise-isolation-pg18`
- 不固定单一 `db_name`
- 允许同一服务承接多个 `tenant_*` 数据库

### 4.2 单租户单命中

保留原设计原则：

- 一租户一数据库
- 一租户一主访问域名
- 一个 `Host` 只命中一个数据库

### 4.3 不开放原生切库

即使恢复为单服务多库，也不开放 Odoo 原生数据库选择能力：

- `list_db = False`
- `/web/database/selector` -> 关闭
- `/web/database/manager` -> 关闭
- `/web/database/list` -> 关闭

### 4.4 先恢复底盘，不先做平台

本次不做：

- 平台后台
- 自动开租户
- 跨租户聚合看板
- 租户套餐/授权/计费

本次只做：

- 多库命中底盘恢复
- 原设计 `P0` 路线验证

## 5. 19099 新环境建议形态

### 5.1 容器建议

建议新增容器，示例命名：

- `enterprise-multidb-odoo19`

建议不要复用：

- `enterprise-hq-odoo19`
- `odoo-lite-test-v19-web`

### 5.2 配置建议

建议配置形态：

```ini
db_host = enterprise-isolation-pg18
dbfilter = ^tenant_%d$
list_db = False
```

注意：

- 不要再写死 `db_name = tenant_hq`
- `dbfilter` 的 `%d` 前提是 `Host` 中的租户码与数据库命名规则严格对应

### 5.3 端口建议

建议映射：

```text
19099 -> 8069
```

### 5.4 域名与 hosts 建议

如果当前还不准备正式申请完整域名，先走内部验证口径：

- `tenant-hq.odoo.test`
- `tenant-kebi.odoo.test`
- `tenant-template.odoo.test`

本地或内网 `hosts` 暂时映射到：

- `192.168.0.17`

访问时统一走：

- `http://tenant-hq.odoo.test:19099`
- `http://tenant-kebi.odoo.test:19099`

## 6. 实施步骤

### 第一步：准备代码基线

`19099` 使用当前较干净、已验证过的代码基线：

- 小程序导入相关代码可保留
- `database_guard` 修复必须带上
- 不继续沿用 `19089` 的脏升级状态

### 第二步：创建新容器

基于当前可运行 Odoo 19 镜像复制一套新服务：

- 新容器
- 新配置
- 连接 `enterprise-isolation-pg18`
- 监听 `19099`

### 第三步：配置多库命中

完成以下配置：

- `dbfilter`
- 反向代理或直接 `Host` 透传
- `list_db = False`
- 数据库入口关闭

### 第四步：验证三个租户库

至少验证：

- `tenant_hq`
- `tenant_kebi`
- `tenant_template`

验证项：

- 正确 `Host` 命中正确数据库
- 错误 `Host` 不误命中其他库
- 不出现数据库选择器

### 第五步：验证业务模块完整性

对每个租户至少验证：

- 登录
- 首页加载
- 基础物流菜单
- `waybill`
- `trace/evidence/exception`

### 第六步：验证备份恢复链

必须按“数据库 + 文件存储”成对验证：

- 单库备份
- 单库恢复
- 恢复后同域名仍可命中正确租户库

## 7. 风险点

### 7.1 dbfilter 命中失败

如果 `Host`、租户码和数据库命名不严格一致，会出现：

- 无法命中
- 误命中

### 7.2 代理层未透传 Host

如果代理层未透传 `Host`，即使 `dbfilter` 正确也无法稳定多租户命中。

### 7.3 tenant_hq 旧环境历史污染

`tenant_hq` 当前在 `19089` 上已有历史残留，所以 `19099` 不应直接复用旧容器，只能复用数据库。

### 7.4 模块状态不一致

同样是 `tenant_*` 库，不同库中模块安装和升级状态可能不一致，需要逐库确认。

## 8. 验收标准

满足以下条件，才算“已回到原设计主线”：

1. 同一个 `19099` 可以承接多个 `tenant_*` 数据库
2. 通过不同 `Host` 稳定命中不同数据库
3. 不需要数据库选择器，不允许手工选库
4. `/web/database/*` 全部关闭
5. 任一错误域名不会串到其他库
6. 至少两个真实租户库完成登录与业务页回归
7. 至少一个租户完成“数据库 + 文件存储”成对恢复验证

## 9. 当前建议

当前最优策略不是直接修改现有 `19069/19089`，而是：

1. 新开 `19099`
2. 恢复原设计的多库命中底盘
3. 完成 `P0` 验收
4. 再决定后续是否替换现有多端口单库模式

## 10. 一句话收口

`19099` 应被定义成“企业隔离原设计恢复验证环境”，它的目标不是增加一个新单库环境，而是证明：同一套 Odoo 服务承接多个租户库、并通过 `Host + dbfilter` 稳定命中的原设计底盘，仍然可以在当前项目里重新成立。
