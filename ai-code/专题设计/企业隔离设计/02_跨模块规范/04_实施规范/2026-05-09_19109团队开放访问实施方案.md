# 2026-05-09 `19109` 团队开放访问实施方案

## 1. 目标

将当前依赖：

- 本机 `hosts`
- 本机 SSH 隧道
- 本机代理绕过

的 `19109` 企业隔离验证环境，收敛成团队可直接访问的统一入口。

目标访问方式：

- `http://hq.odoo.test/web`
- `http://kebi.odoo.test/web`
- `http://template.odoo.test/web`

## 2. Outcome

- 团队成员不再需要手工配置 `hosts`
- 团队成员不再需要自行建立 SSH 隧道
- 团队成员不再需要单独设置浏览器代理绕过
- 同一套 `19109` Odoo 服务继续通过 `Host + dbfilter` 命中：
  - `tenant_hq`
  - `tenant_kebi`
  - `tenant_template`

## 3. Behavior

### 3.1 核心事实

本方案不是纯内网单机入口，而是建立在**两层分离部署**之上：

- 云服务器：
  - 对团队暴露统一访问域名
  - 运行 Nginx
  - 承接隧穿落点
- 本地服务器：
  - 运行 `enterprise-multidb-odoo19`
  - 挂载 Odoo 数据与 filestore
  - 连接 `enterprise-isolation-pg18`

### 3.2 实际访问链路

访问链路为：

`浏览器 -> DNS -> 云服务器 Nginx(80/443) -> 云服务器本地隧穿端口(127.0.0.1:19109) -> 隧穿通道 -> 本地 Odoo(19109) -> dbfilter 命中租户库`

### 3.3 Host 保留

Nginx 与隧穿链路都必须保留原始 `Host`：

- `hq.odoo.test`
- `kebi.odoo.test`
- `template.odoo.test`

因为 `19109` 的数据库命中依赖：

- `proxy_mode = True`
- `dbfilter = ^tenant_%d$`

### 3.4 用户访问方式

用户最终只访问：

- `http://hq.odoo.test/web`
- `http://kebi.odoo.test/web`
- `http://template.odoo.test/web`

团队成员不再直接触达：

- 本地服务器 IP
- `:19109`
- 个人本机隧道

## 4. Boundary

本方案负责：

- 团队内部访问入口标准化
- 云服务器域名入口
- 云服务器 Nginx 转发
- 云服务器到本地服务器的隧穿链路
- `Host` 透传

本方案不负责：

- 新租户数据库创建
- 平台后台
- 公网正式证书
- 公网开放

## 5. 实际部署架构

### 5.1 部署拓扑

```text
团队成员浏览器
  -> http://hq.odoo.test / kebi.odoo.test / template.odoo.test
  -> 公网 / 团队 DNS
  -> 云服务器 Nginx(:80/:443)
  -> 云服务器本地隧穿端口(:19109)
  -> 隧穿通道
  -> 本地服务器 Odoo(:19109)
  -> dbfilter 命中 tenant_hq / tenant_kebi / tenant_template
```

### 5.2 各层职责

云服务器负责：

- 域名承接
- 统一入口
- Nginx 转发
- 隧穿接入点

本地服务器负责：

- Odoo 计算
- PostgreSQL 连接
- filestore
- 租户业务数据

### 5.3 后端服务基线

- Odoo 容器：`enterprise-multidb-odoo19`
- PostgreSQL：`enterprise-isolation-pg18`
- 租户库：
  - `tenant_hq`
  - `tenant_kebi`
  - `tenant_template`
- 运行配置：
  - `proxy_mode = True`
  - `list_db = False`
  - `dbfilter = ^tenant_%d$`

## 6. 为什么必须保留隧穿

### 6.1 原因

本地服务器部署在 NAT / 防火墙之后时，云服务器无法主动向本地 Odoo 发起 TCP 连接。

所以：

- Nginx 不能直接替代隧穿
- 反向代理只能连接**可达的** IP:Port
- 不能负责穿透本地网络边界

### 6.2 隧穿职责

隧穿负责：

- 本地服务器主动向云服务器建立一条持久加密通道
- 让云服务器上的 `127.0.0.1:19109` 请求回流到本地 Odoo

### 6.3 Nginx 与隧穿关系

Nginx 负责：

- 域名
- 统一入口
- 请求转发

隧穿负责：

- 云服务器到本地服务器之间的连接打通

两者是配合关系，不是替代关系。

## 7. DNS 与域名方案

### 7.1 团队 DNS

需要在团队可访问的 DNS 中增加 A 记录，统一指向**云服务器 IP**：

```text
hq.odoo.test        -> <云服务器IP>
kebi.odoo.test      -> <云服务器IP>
template.odoo.test  -> <云服务器IP>
```

注意：

- 指向的是云服务器
- 不是本地 Odoo 机器

### 7.2 过渡方案

如果 DNS 暂时不能立刻修改，可先在少量访问机器上维护 `hosts`，但仍应指向**云服务器 IP**。

这只能作为短期过渡方案，不建议长期保留。

## 8. Nginx 反向代理方案

### 8.1 部署位置

Nginx 应部署在**云服务器侧**，而不是本地 Odoo 侧。

### 8.2 核心要求

- 监听 `80`
- 按域名承接三个租户入口
- 转发到云服务器本地隧穿落点 `127.0.0.1:19109`
- 保留原始 `Host`

### 8.3 推荐配置

```nginx
server {
    listen 80;
    server_name hq.odoo.test kebi.odoo.test template.odoo.test;

    location / {
        proxy_pass http://127.0.0.1:19109;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_redirect off;
    }
}
```

### 8.4 说明

- `proxy_set_header Host $host;` 是必须项
- 不允许统一改写成固定主机名
- 不建议按租户拆成不同 upstream
- 因为租户路由逻辑已经在 `19109` 的 `Host + dbfilter` 内完成

## 9. 隧穿方案

### 9.1 选型

隧穿工具可选：

- frp
- ngrok
- Cloudflare Tunnel
- SSH 反向隧道 / autossh

### 9.2 配置要求

- 本地服务器侧：
  - 将本地 `19109` 映射到云服务器本地监听端口
- 云服务器侧：
  - 隧穿端口仅监听 `127.0.0.1`
  - 不对外暴露
- 通道本身必须加密
- 建议配置断线自动重连

## 10. 安全与网络边界

### 10.1 云服务器侧

建议对团队开放：

- `80/tcp`
- 后续可扩 `443/tcp`

不建议对团队开放：

- 云服务器侧隧穿端口
- `19109/tcp`

### 10.2 本地服务器侧

本地服务器上的 Odoo `19109` 不应对团队直接开放。

### 10.3 代理风险

部分访问机器如果本地代理接管 `*.odoo.test`，仍可能出现：

- `502`
- 样式异常
- 资源加载错乱

上线前应确认浏览器或系统代理不会错误劫持目标域名。

## 11. 与当前临时访问方式的切换

### 11.1 当前依赖

当前个人可访问方式依赖：

- 本机 `hosts`
- 本机 `ssh -L 19109:127.0.0.1:19109 ...`
- 本地代理绕过 `*.odoo.test`

### 11.2 切换后目标

切换完成后应移除这些个人调试依赖，让团队统一通过：

`DNS -> 云服务器 Nginx -> 云服务器隧穿落点 -> 隧穿通道 -> 本地 Odoo`

访问系统。

### 11.3 推荐切换顺序

1. 先完成团队 DNS
2. 确认隧穿稳定运行
3. 再落云服务器 Nginx 配置
4. 再做团队直接访问验收
5. 验收通过后，逐步停止传播本机隧道与 `hosts` 的临时方案

## 13. 风险点

### 13.1 Host 被改写

如果代理层或隧穿层没有正确保留原始 `Host`：

- `%d` 无法按预期展开
- `dbfilter` 会失效
- 可能出现误命中或无法命中

### 13.2 隧穿中断

如果隧穿中断，所有团队访问都会整体失效。

建议：

- 自动重连
- 健康检查
- 日志监控

### 13.3 DNS 缓存

DNS 切换后短时间内，部分机器可能仍命中旧缓存。

## 14. 一句话结论

`19109` 团队开放访问的正确落地方式，不是让每个人复制本机隧道和 `hosts`，也不是简单在本地 Odoo 前面再套一层 Nginx，而是通过**云服务器统一入口 + 隧穿回流 + 本地 Odoo 多租户命中**，把现有个人调试链路收口成团队可直接使用的标准访问方案。
