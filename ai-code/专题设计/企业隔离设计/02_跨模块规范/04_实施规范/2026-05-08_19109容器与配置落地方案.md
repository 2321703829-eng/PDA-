# 2026-05-08 `19109` 容器与配置落地方案

## 1. 文档目标

本文把 `19109` 企业隔离恢复环境继续收成命令级实施稿。

目标：

- 新增一套 Odoo 19 容器
- 新端口 `19109`
- 连接 `enterprise-isolation-pg18`
- 使用 `Host + dbfilter` 命中多个 `tenant_*` 数据库
- 不开放数据库选择器

本文默认：

- 不直接改动现有 `19069 / 19079 / 19089`
- 不复用 `19089` 旧运行态
- 先落一套新的恢复环境，再做 `P0` 验收

## 2. 目标环境

### 2.1 建议命名

- 容器名：`enterprise-multidb-odoo19`
- 可选代理容器名：沿用现有代理，或新增 `enterprise-multidb-proxy`

### 2.2 端口

- 宿主机：`19109`
- 容器内：`8069`

### 2.3 数据库实例

- PostgreSQL 容器：`enterprise-isolation-pg18`

### 2.4 首批租户库

- `tenant_hq`
- `tenant_kebi`
- `tenant_template`

## 3. 代码基线建议

### 3.1 来源

建议代码基线来源：

- 当前最新 `feat-text`
- 携带本地已验证的 `database_guard` 修复

### 3.2 必带修复

必须确保以下代码已经进入 `19109` 环境：

- `custom_addons/logistics_web/controllers/__init__.py`
- `custom_addons/logistics_web/controllers/database_guard.py`

原因：

- `list_db = False` 只是配置关闭
- 企业隔离环境还需要 guard 真正把 `/web/database/*` 收成强关闭状态

## 4. 配置文件目标口径

建议新环境配置文件核心项为：

```ini
db_host = enterprise-isolation-pg18
db_port = 5432
db_user = odoo
db_password = <按现网口径填写>
list_db = False
dbfilter = ^tenant_%d$
proxy_mode = True
```

说明：

- 不写 `db_name = tenant_hq`
- 保留 `list_db = False`
- `dbfilter = ^tenant_%d$` 依赖 `Host`
- `proxy_mode = True` 适用于经反向代理透传的访问方式

## 5. 目录与文件建议

### 5.1 建议宿主机目录

如沿用现有结构，建议新增：

- `/opt/enterprise-multidb-odoo19/`
- `/opt/enterprise-multidb-odoo19/config/`
- `/opt/enterprise-multidb-odoo19/extra-addons/`

### 5.2 建议配置文件

- `/opt/enterprise-multidb-odoo19/config/odoo.conf`

### 5.3 建议日志

- `/opt/enterprise-multidb-odoo19/logs/`

## 6. 容器创建方案

### 6.1 原则

最稳方式不是从零拼镜像，而是复制一套当前可运行的 Odoo 19 容器启动参数，再改：

- 容器名
- 端口
- 配置挂载
- 数据库目标

### 6.2 推荐起容器思路

如果当前环境已经有稳定的 Odoo 19 容器模板，建议参考：

- `odoo-lite-test-v19-web`

但注意只参考其：

- 镜像
- volume 挂载方式
- 基础运行参数

不要继承其：

- `dbfilter`
- 单库绑定配置

### 6.3 宿主机端口映射

目标映射：

```text
19109:8069
```

## 7. 代理与 Host 透传方案

### 7.1 目标访问方式

首期内部验证建议：

- `tenant-hq.odoo.test:19109`
- `tenant-kebi.odoo.test:19109`
- `tenant-template.odoo.test:19109`

### 7.2 hosts 方案

在访问机器上增加：

```text
192.168.0.17 tenant-hq.odoo.test
192.168.0.17 tenant-kebi.odoo.test
192.168.0.17 tenant-template.odoo.test
```

### 7.3 透传要求

如果直连 `19109`：

- 浏览器请求中的 `Host` 必须保持为测试域名

如果经过代理：

- 代理必须保留原始 `Host`
- 不允许统一改写成固定主机名

### 7.4 关键风险

如果 `Host` 没有被正确保留：

- `%d` 无法正确展开
- `dbfilter` 无法稳定命中目标库

## 8. 建议实施顺序

### 第一步：准备代码

- 在目标目录放置 Odoo 代码与 `extra-addons`
- 确认 `database_guard` 修复已在代码里

### 第二步：准备配置

- 创建新的 `odoo.conf`
- 写入多库版 `dbfilter`
- 关闭 `list_db`

### 第三步：起容器

- 启动 `enterprise-multidb-odoo19`
- 映射 `19109 -> 8069`

### 第四步：升级模块

至少升级：

- `logistics_base`
- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- `logistics_web`

### 第五步：验证数据库入口关闭

验证：

- `/web/database/selector`
- `/web/database/manager`
- `/web/database/list`

### 第六步：验证多租户命中

分别访问：

- `tenant-hq.odoo.test:19109`
- `tenant-kebi.odoo.test:19109`
- `tenant-template.odoo.test:19109`

## 9. 建议命令模板

以下为“实施时建议照着补齐”的命令模板，不代表当前已执行。

### 9.1 查看现有容器启动口径

```bash
docker inspect odoo-lite-test-v19-web
```

### 9.2 新建配置目录

```bash
mkdir -p /opt/enterprise-multidb-odoo19/config
mkdir -p /opt/enterprise-multidb-odoo19/extra-addons
mkdir -p /opt/enterprise-multidb-odoo19/logs
```

### 9.3 起新容器

```bash
docker run -d \
  --name enterprise-multidb-odoo19 \
  -p 19109:8069 \
  --network <与 enterprise-isolation-pg18 同网络> \
  -v /opt/enterprise-multidb-odoo19/config/odoo.conf:/etc/odoo/odoo.conf \
  -v /opt/enterprise-multidb-odoo19/extra-addons:/mnt/extra-addons \
  <odoo19-image>
```

### 9.4 模块升级

```bash
docker exec -i enterprise-multidb-odoo19 \
  odoo -d tenant_hq -u logistics_base,logistics_dispatch,logistics_trace_core,logistics_trace_evidence,logistics_trace_exception,logistics_web --stop-after-init
```

说明：

- 首批至少先针对 `tenant_hq` 验证
- 后续再对 `tenant_kebi / tenant_template` 做一致性升级

### 9.5 检查数据库入口

```bash
curl -I http://tenant-hq.odoo.test:19109/web/database/selector
curl -I http://tenant-hq.odoo.test:19109/web/database/manager
```

### 9.6 检查多库命中

```bash
curl -I -H "Host: tenant-hq.odoo.test" http://127.0.0.1:19109/web/login
curl -I -H "Host: tenant-kebi.odoo.test" http://127.0.0.1:19109/web/login
```

## 10. 首轮部署完成标准

以下全部满足，才算 `19109` 落地完成：

1. 新容器已运行
2. `19109` 可访问
3. 未写死 `db_name`
4. `dbfilter` 通过 `Host` 可命中至少两个租户库
5. `/web/database/*` 全关闭
6. `tenant_hq` 与 `tenant_kebi` 均可独立登录

## 11. 当前不建议做的事

- 不在现有 `19069` 上直接改成多库
- 不在 `19089` 旧容器上继续打补丁式演进
- 不把“恢复多库底盘”和“平台后台建设”混成一轮

## 12. 一句话收口

`19109` 的容器与配置落地，不是简单复制一个现有端口，而是重新建立一套“单服务多库、通过 Host 命中租户库”的企业隔离底盘。
