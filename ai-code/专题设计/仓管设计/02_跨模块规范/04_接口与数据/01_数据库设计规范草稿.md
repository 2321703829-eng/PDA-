## 1. 文档定位

本文件用于把当前散落在以下专题中的数据库设计依据集中收口：

- 主数据与基础档案专题
- 入库 / 出库 / 盘点 / 移位状态机专题
- 接口与回传专题
- 权限与角色专题
- 证据 / 附件 / 留痕专题

它不是替代这些业务专题，而是用于：

- 给数据库评审提供统一入口
- 给模型和字段实现提供跨专题的总口径
- 降低后续继续补字段、建索引、做审计字段时的查找成本

## 3. 当前推荐的数据库总体原则

当前更推荐统一理解为：

`先稳定一套与 Odoo 原生对象兼容的仓管业务模型，再补更细的物理设计与性能设计。`

也就是：

- 优先复用 Odoo 原生事实层，不另造并行库存内核
- 业务主单、执行记录、任务、证据元数据用自定义模型承载
- 一期优先定好模型边界、字段边界、状态字段边界、记录规则边界
- 更细的物理库优化、性能优化、对象存储细化后补

## 9. 字段命名与通用落表规则

当前更推荐统一采用：

### 9.1 通用主键与外键

- 主键统一使用 Odoo 默认 `id`
- 外键统一使用 `*_id`
- 反向集合统一使用 `*_ids`

### 9.2 通用业务字段

- 编号：`name`
- 主状态：`state`
- 异常补充状态：`exception_state`
- 备注：`remark`
- 公司：`company_id`
- 货主：`owner_id`
- 仓库：`warehouse_id`

### 9.3 动作与责任字段

- 创建人：Odoo 默认 `create_uid`
- 创建时间：Odoo 默认 `create_date`
- 更新人：Odoo 默认 `write_uid`
- 更新时间：Odoo 默认 `write_date`
- 当前处理人：按业务对象使用 `operator_id` / `responsible_id`

### 9.4 当前统一建议

- 一期优先保持字段短、稳定、可读
- 不提前引入很多项目外部缩写
- 不在数据库字段层混用中英拼音组合命名

## 11. 状态字段与异常补充字段落表规则

当前更推荐统一采用两层表达：

### 11.1 主状态字段

- 字段名统一：`state`
- 作用：表达主流程位置
- 例子：
  - 入库单：`draft / waiting_receipt / receipting / received / putawaying / done / cancel`
  - 出库单：`draft / waiting_pick / picking / picked / checking / waiting_ship / done / cancel`

### 11.2 异常补充状态字段

- 字段名统一：`exception_state`
- 作用：不污染主状态机的前提下表达异常补充状态
- 一期当前统一预留：
  - `terminated`
  - `exception`
  - `pending_action`
- 一期真实优先启用：
  - `terminated`

### 11.3 终止类配套字段

- `terminated_reason`
- `terminated_remark`
- `terminated_by`
- `terminated_at`

## 13. 索引、唯一约束与审计字段基线

当前更推荐一期至少关注：

### 13.1 索引方向

- `state`
- `owner_id`
- `warehouse_id`
- `exception_state`
- 主单编号 `name`
- 外部幂等键 / 外部业务单号

### 13.2 唯一约束方向

- 主单编号在业务模型内唯一
- 关键外部幂等键在任务模型内唯一或近唯一
- 条码映射在约定范围内唯一

### 13.3 审计字段方向

- 使用 Odoo 默认 `create_uid / create_date / write_uid / write_date`
- 需要单独记录动作人和动作时间的对象，再补：
  - `operator_id`
  - `operate_time`
  - 或专项字段如 `terminated_by / terminated_at`

## 14. 任务、证据、日志与二进制数据落位规则

当前更推荐统一理解为：

### 14.1 任务对象

- 独立任务模型承接
- 不把完整任务历史塞进主单单个状态字段

### 14.2 证据对象

- Odoo 侧存元数据
- 二进制大文件走对象存储
- Odoo 中保留关联对象、上传人、时间、说明、访问 key 等元数据

### 14.3 日志对象

- 业务日志与处理日志优先独立承接
- 不把所有历史都压进备注字段

### 14.4 当前统一边界

- `数据库存元数据`
- `对象存储存二进制`
- `主单与任务 / 证据 / 日志通过外键和轻量关联对齐`

## 15. 与权限、记录规则和数据范围的联动口径

当前更推荐统一理解为：

- 货主范围和仓库范围是数据库对象范围控制的两条主维度
- 菜单显隐不等于数据可见
- 前端按钮显隐不等于后端动作放行

### 15.1 记录规则主维度

- `owner_id`
- `warehouse_id`

### 15.2 典型联动方向

- 主数据页按货主 / 仓库范围控制可见对象
- 主单与执行记录按货主 / 仓库范围控制可操作记录
- 任务与证据对象按关联主单派生可见范围

| 执行页稳定监控阶段收尾 | 执行页新周期稳定结项清单 | 执行页下一轮准备清单 | 能明确执行页、PDA、移动端稳定监控收尾后何时完成新周期稳定结项，以及何时进入下一轮准备 |

### 23.84 稳定监控阶段收尾、新周期稳定结项与下一轮准备衔接时的当前统一建议

当前更推荐按下面原则衔接稳定监控阶段收尾、新周期稳定结项和下一轮准备：

1. 稳定监控阶段收尾清单优先回答“稳定监控阶段何时结束”，新周期稳定结项清单优先回答“何时确认本轮稳定运行已经正式结项”，下一轮准备清单优先回答“何时可以把工作切到下一轮准备态”
2. 不建议稳定监控阶段收尾后直接进入下一轮准备而没有新周期稳定结项清单，否则本轮稳定运行的收口会缺少正式结项层
3. 不建议先做新周期稳定结项而没有稳定监控阶段收尾清单，否则稳定结项依据会不清晰
4. 记录编号建议继续沿 `MON2SCLOSE-xx -> STABLEEND-xx -> PREP3-xx` 方式沉淀，便于把稳定监控收尾、稳定结项和下轮准备串成一条线

## 24. 当前不建议的一期做法

当前不建议：

- 另起并行库存主表
- 在数据库层提前做很重的“万能规则引擎”
- 一期就做复杂分库分表
- 未稳定主模型与字段前先写大量物理优化脚本
- 把二进制大附件长期留在 Odoo 默认附件架构中
