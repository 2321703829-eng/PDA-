## 1. 文档定位

这份文档不替代入库、出库、盘点、移位各自的状态机专题。  
它承担的是跨单据统一口径层，用来收住：

- 主状态
- 异常补充状态
- 执行记录状态
- 状态推进规则
- 状态显示规则

## 2. 范围与边界

当前纳入：

- 入库单
- 出库单
- 盘点单
- 移位单
- 收货 / 上架 / 拣货 / 复核执行记录

当前不纳入：

- 计费、结算、对账状态
- 售后、逆向物流全量状态体系
- 更细审批流和活动流

## 3. 统一目标

- 用最少的状态层解释最多的一期业务流程
- 保持主状态机稳定，不让异常把主线冲散
- 保持页面展示和按钮行为一致
- 保持数据库落表、权限控制、执行页交互可对齐

## 4. 状态分层模型

当前统一采用三层模型：

1. 主状态  
回答“单据当前处于哪一段主流程”

2. 异常补充状态  
回答“当前主流程是否存在额外异常语义”

3. 执行记录状态  
回答“某次执行动作自身进行到哪一步”

## 5. 主状态统一命名规则

当前统一建议：

- 主状态优先用短英文词或短英文组合
- 主状态优先表达流程位置，不表达责任归因
- 主状态先覆盖高频正常流程，再考虑异常外围补充

当前四类主单的统一口径：

| 对象 | 当前主状态集合 |
| --- | --- |
| 入库单 | `draft / waiting_receipt / receipting / received / putawaying / done / cancel` |
| 出库单 | `draft / waiting_pick / picking / picked / checking / waiting_ship / done / cancel` |
| 盘点单 | `draft / counting / reviewing / done / cancel` |
| 移位单 | `draft / waiting_execute / executing / done / cancel` |

## 6. 异常补充状态统一命名规则

当前统一建议：

- 异常补充状态不替代主状态
- 异常补充状态应挂在主状态之外
- 一期统一预留：
  - `terminated`
  - `exception`
  - `pending_action`

当前一期实际启用建议：

- 入库单：先启用 `terminated`
- 出库单：先启用 `terminated`
- 盘点单：一期不重点依赖异常补充状态
- 移位单：一期保留轻量异常信息，不强依赖异常补充状态体系

## 7. 执行记录状态统一命名规则

四类执行记录当前统一建议：

- `draft`
- `in_progress`
- `done`
- `cancel`

适用对象：

- receive record
- putaway record
- pick record
- check record

## 8. done / cancel / terminated 边界

### 8.1 done

- `done` 只表示主流程已完成
- `done` 不承载“已异常结束”
- `done` 后发现问题，优先走新单、调整单、异常处理或外围逆向流程

### 8.2 cancel

- `cancel` 优先保留给未发生真实执行事实前的普通取消
- 一旦进入真实执行阶段，不建议再把主单直接打成 `cancel`

### 8.3 terminated

- `terminated` 用于表达“已进入真实执行，但当前无法继续按正常主线推进”
- `terminated` 不替代主状态
- 典型口径：
  - 主状态停在当前执行阶段
  - 异常补充状态挂 `terminated`

## 9. 四类主单统一流程推进规则

当前统一建议：

1. 主状态推进优先由真实业务动作触发
2. 不建议只靠人工改状态推进主线
3. 部分完成优先落在行级或执行记录级，不轻易新增主单级“部分完成”状态
4. 失败优先停留在当前主流程状态，再通过异常补充状态或异常信息区表达

## 10. 主单状态与执行记录联动总规则

统一口径：

- 主单进入执行中状态，通常由第一条有效执行记录触发
- 主单进入完成前状态，通常要求当前主流程对应的执行记录闭环完成
- 执行记录结束不一定立刻把主单推进到终态，要看主流程是否整体满足完成条件

简化理解：

- 收货记录推动入库单从 `waiting_receipt -> receipting -> received`
- 上架记录推动入库单从 `received -> putawaying -> done`
- 拣货记录推动出库单从 `waiting_pick -> picking -> picked`
- 复核记录推动出库单从 `picked / checking -> waiting_ship`

## 11. 状态展示统一口径

### 11.1 列表页

- 主状态占主位
- 异常补充状态做次标签
- 已完成行继续显示，可弱化，不建议自动消失

### 11.2 详情页

- 头部主状态占主位
- 异常补充状态在头部或异常信息区做高辨识展示
- 状态解释文字应简洁，避免同时展示多个层级重复文案

### 11.3 执行页

- 以执行记录状态为当前页主反馈
- 同时在顶部上下文中保留主单状态
- 状态提示条优先显示：
  - 错误
  - 动作结果
  - 记录状态
  - 下一步引导

## 12. 状态与按钮 / 权限 / 记录规则之间的统一边界

当前统一建议：

- 按钮显隐由“权限 + 状态 + 记录规则范围”共同决定
- 前端负责显隐与轻提示
- 后端负责最终校验
- 状态允许不等于用户一定可操作
- 有权限不等于当前状态下按钮一定显示

## 14. 当前不建议的一期做法

- 为每张主单都单独发明一套完全不同的状态命名
- 把异常全部塞进主状态机
- 用“部分完成”过度膨胀主单状态
- 让前端状态显示和后端字段语义不一致
- 让 `done / cancel / terminated` 语义互相重叠

## 19. 与执行页按钮矩阵之间的逐按钮交叉映射

这部分用于回答：

`状态总规范里的状态边界，最终如何落实到执行页里的每一个关键按钮。`

当前优先对齐的按钮包括：

- `确认本次`
- `确认并下一条`
- `完成本次记录`
- `取消`
- `返回主单`
- `刷新`

### 19.1 共用按钮的当前对齐

| 按钮 | 当前主要受哪一层状态影响 | 当前统一口径 |
| --- | --- | --- |
| `确认本次` | 执行记录状态 | 仅在执行记录 `draft / in_progress` 且当前行可处理时可用 |
| `确认并下一条` | 执行记录状态 + 当前待处理队列状态 | 先满足 `确认本次`，再要求存在下一条可处理项 |
| `完成本次记录` | 执行记录状态 + 主单阶段状态 | 当前记录已满足完成条件时才可用，不用它直接推进无关主流程 |
| `取消` | 执行记录状态或主单主状态 | 用于取消当前记录或在允许阶段取消主单，不与 `terminated` 混用 |
| `返回主单` | 页面状态，不直接改变业务状态 | 只承担导航功能，但会受到未保存录入状态约束 |
| `刷新` | 页面状态，不直接改变业务状态 | 只承担页面刷新，不推动主流程前进 |

### 19.2 四类执行页按钮与状态边界的当前对齐

| 执行页 | 当前状态层重点 | 当前应重点对齐的按钮 | 当前说明 |
| --- | --- | --- | --- |
| 收货执行页 | 入库主状态 + 收货记录状态 | `确认本次` / `完成本次记录` | 收货记录先推进记录闭环，再由收货事实推动入库主状态 |
| 上架执行页 | 入库主状态 + 上架记录状态 | `确认本次` / `完成本次记录` | 上架记录完成后再推动入库主状态进入 `done` |
| 拣货执行页 | 出库主状态 + 拣货记录状态 | `确认本次` / `确认并下一条` / `完成本次记录` | 拣货页最强调行级推进与自动切下一条 |
| 复核执行页 | 出库主状态 + 复核记录状态 | `确认本次` / `完成本次记录` | 复核页更强调结果确认与问题备注边界 |

### 19.3 当前统一对齐建议

1. 执行页按钮优先由执行记录状态主导，而不是直接由主单主状态主导

## 17. 与数据库字段总表之间的逐项映射

这部分用于回答一个很实际的问题：

`状态与流程统一规范里说的每一层状态语义，最终应落到数据库稿里的哪些字段。`

当前统一建议按 4 组来对齐：

| 状态流程主题 | 当前建议对齐的数据库字段方向 | 当前说明 |
| --- | --- | --- |
| 主状态 | `state` | 主状态始终优先落在主单对象的 `state` 字段中 |
| 异常补充状态 | `exception_state` | 异常补充状态不替代 `state`，而是额外挂在补充字段中 |
| 终止原因与终止说明 | `terminated_reason / terminated_remark / terminated_by / terminated_at` | 只在明确进入 `terminated` 语义时启用 |
| 执行记录状态 | 执行记录对象自身的 `state` | 收货 / 上架 / 拣货 / 复核记录各自保留统一状态字段 |

### 17.1 四类主单与数据库字段总表的对齐

| 对象 | 当前主状态字段 | 当前异常补充字段 | 当前执行记录字段 | 当前说明 |
| --- | --- | --- | --- | --- |
| 入库单 | `logistics.wms.inbound.state` | `exception_state` | `receive / putaway record.state` | 入库主线由主状态承载，终止挂 `exception_state=terminated` |
| 出库单 | `logistics.wms.outbound.state` | `exception_state` | `pick / check record.state` | 出库主线由主状态承载，拣货 / 复核终止挂异常补充状态 |
| 盘点单 | `logistics.wms.inventory.count.state` | 一期弱依赖 | 盘点执行结果优先落行级 / 结果字段 | 盘点一期更依赖 `reviewing` 与差异结果字段 |
| 移位单 | `logistics.wms.relocation.state` | 一期弱依赖 | 执行记录或异常说明字段 | 移位一期优先用主状态加轻量异常信息承载 |

### 17.2 当前统一对齐建议

1. 状态总规范里的“主状态”默认都要能在数据库稿字段总表里找到明确落表字段  
2. 异常补充状态默认使用 `exception_state` 口径，不建议每个对象重新发明新的异常状态字段名  
3. `done / cancel / terminated` 的边界，在数据库层必须能通过 `state + exception_state + 辅助审计字段` 一起解释  
4. 执行记录状态不建议混入主单字段中，而应由执行记录对象自己的 `state` 承载  

## 18. 与权限矩阵之间的逐项映射

这部分用于回答另一个同样关键的问题：

`状态与流程统一规范里的状态边界，最终如何影响权限矩阵里的按钮、页面和记录规则。`

当前统一建议按 3 层来对齐：

| 状态流程主题 | 当前建议对齐的权限层 | 当前说明 |
| --- | --- | --- |
| 主状态 | 按钮显隐层 / 动作校验层 | 当前状态直接决定哪些按钮应显示、哪些动作应被允许 |
| 异常补充状态 | 异常处理入口层 | `terminated / exception / pending_action` 应直接影响异常入口和处理入口显隐 |
| 执行记录状态 | 执行页按钮层 | 执行记录状态直接决定执行页里的 `确认本次 / 完成本次记录 / 取消` 是否可用 |

### 18.1 主状态到权限矩阵的当前对齐

| 状态层 | 当前建议对应权限专题章节 | 当前说明 |
| --- | --- | --- |
| 主状态 | `13. 更细的单据级动作矩阵` | 主状态决定单据级按钮是否允许 |
| 主状态 + 页面区块 | `14. 更细的页面区块级按钮显隐矩阵` | 主状态继续决定详情页不同区块里的按钮显隐 |
| 主状态 + 权限 + 记录规则 | `17. 四层联动总表` | 最终结果由角色、状态、按钮、记录规则共同决定 |

### 18.2 异常补充状态到权限矩阵的当前对齐

| 异常补充状态 | 当前建议权限口径 | 当前说明 |
| --- | --- | --- |
| `terminated` | 危险动作与异常处理动作分离 | 终止后不应再显示普通主线推进按钮 |
| `exception` | 预留异常处理入口 | 后续若启用，应走异常处理入口，不直接回主线 |
| `pending_action` | 预留人工处理 / 补动作入口 | 当前若启用，应在页面与按钮层给出待处理语义 |

### 18.3 当前统一对齐建议

1. 状态总规范只定义语义边界，具体“谁能点”必须继续回到权限矩阵判断  
2. 任何按钮都不能只依赖角色或只依赖状态，必须同时看：角色、状态、记录规则范围  
3. `terminated` 一类异常补充状态出现后，普通推进按钮应默认收缩，异常处理入口应相对抬高  
4. 执行页按钮和详情页按钮的边界，应优先服从“状态在当前页由谁主导”的原则  

## 21. 与对象与编码统一规范之间的交叉映射

状态与流程统一规范后续需要和“对象与编码统一规范”保持清晰分工。

当前建议统一理解为：
- 对象与编码规范回答“这是什么对象、编号怎么命名、编码怎么生成”
- 状态与流程规范回答“这个对象现在走到哪一步、处在什么流程位置、是否存在异常补充状态”

### 21.1 当前交叉映射总表

| 对象与编码主题 | 当前状态流程对齐点 | 当前说明 |
| --- | --- | --- |
| 主单编号 | 主状态只承载流程语义，不承载对象编号语义 | 编号回答“是哪张单”，状态回答“走到哪一步” |
| 执行记录编号 | 执行记录状态与记录编号并列存在 | 记录编号不能替代执行记录状态 |
| 异常编号 / 终止编号 | 异常补充状态只回答异常类型，不承担独立编号职能 | 终止原因、终止时间、终止人仍通过字段表达 |

| 仓库编码 / 货位编码 | 仅承担空间定位与过滤维度 | 位置编码不用于表达流程阶段 |
| 任务编号 | 任务状态与任务编号并列存在 | 任务编号不替代任务状态机 |

### 21.2 当前统一交叉映射建议

1. 编码字段永远不替代状态字段。
2. 状态字段永远不承担对象身份编码。
3. 页面展示时，对象编码和状态可以并列展示，但职责必须分开。
4. 扫码、条码、主数据编码只参与识别、过滤、定位，不直接决定主状态推进。
5. 后续“对象与编码统一规范”正式成稿时，应直接吸收本章作为状态边界部分，而不要重写一套状态口径。

   - `terminated_remark`

   - `terminated_at`
