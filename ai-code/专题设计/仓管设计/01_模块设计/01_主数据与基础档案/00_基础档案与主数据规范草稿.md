## 1. 文档定位

本文件用于把仓管模块中与主数据、基础档案相关的内容从总讨论稿中进一步抽出，形成一个可独立继续演进的基础数据专题稿。

当前重点不是一步定完所有字段，而是先固定：

- 一期主数据对象范围
- 模块归属与分层
- 原生复用与自定义扩展边界
- 最小关联口径

## 2. 范围与边界

### 2.1 当前纳入范围

- 货主
- 商品扩展
- 条码映射
- 仓库扩展
- 货位扩展
- 基础业务字典
- 货主与仓库 / 商品的基础关联口径

### 2.2 当前不纳入范围

- 复杂货主授权体系
- 虚拟货主 / 虚拟仓完整体系
- 货位容量精细算法
- 复杂商品属性模板
- 复杂标签 / 编码规则引擎

## 3. 当前推荐的主数据总体原则

当前更推荐把仓管主数据统一理解成：

`基础主数据优先扩原生，仓管主线对象优先新建业务模型。`

也就是：

- 商品、伙伴、仓库、货位尽量建立在 Odoo 原生对象上扩展
- 不另造并行的主数据内核
- 但仓管语义字段、客户口径字段、映射规则字段应明确进入 `logistics_wms_base`

## 4. 一期纳入范围

当前一期更推荐先打牢这 5 条主线：

1. `货主`
2. `商品扩展`
3. `仓库扩展`
4. `货位扩展`
5. `条码 / 商品条码映射`

一句话收口：

`logistics_wms_base` 的一期目标不是把主数据体系做得非常重，而是先提供足够支撑入库、库存、出库统一引用的公共底座。`

## 5. 对象分层与模块归属

当前更推荐：

- 货主 -> `logistics_wms_base`
- 商品扩展 -> `logistics_wms_base`
- 仓库 -> `logistics_wms_base`
- 货位 -> `logistics_wms_base`
- 条码 -> `logistics_wms_base`

原因是这些对象都会被：

- 入库
- 库存
- 出库

反复复用，适合作为仓管公共底座，而不是散落在单条业务主线里。

## 6. 原生复用与扩展边界

### 6.1 当前推荐直接建立在原生对象上的底座

- 货主：基于 `res.partner` 扩展
- 商品：基于 `product.template / product.product` 扩展
- 仓库：基于 `stock.warehouse` 扩展
- 货位：基于 `stock.location` 扩展

### 6.2 当前推荐“原生底座 + 仓管映射层”的对象

- 条码
- 商家编码
- 多条码规则
- 客户侧商品识别映射

### 6.3 当前推荐的一句话边界

`原生对象负责底座真相，仓管模块负责业务语义扩展。`

## 7. 当前推荐的主数据对象清单

### 7.1 货主

最小关注点：

- 基础档案身份
- 业务状态
- 与仓库、商品的基础关联

### 7.2 商品扩展

最小关注点：

- 商家编码
- 箱规
- 重量 / 体积
- 仓管侧自定义属性

### 7.3 条码映射

最小关注点：

- 商品 - 条码映射
- 多条码承载
- 条码与仓管执行页 / PDA 的衔接

### 7.4 仓库扩展

最小关注点：

- 仓库业务状态
- 仓库基础配置
- 仓库与货主的基础可用范围

### 7.5 货位扩展

最小关注点：

- 货位编码
- 货区 / 分组
- 基础冻结 / 可用口径
- 货位与库存执行对象的对接

## 8. 主数据之间的最小关联口径

当前更推荐至少固定这些最小关联：

- 货主 -> 商品
- 货主 -> 仓库
- 仓库 -> 货位
- 商品 -> 条码映射

这些关联的意义不是把规则做重，而是先确保：

- 入库单能正确带出货主与商品
- 出库单能正确带出货主与仓库
- 库存与执行页能正确落到货位与条码

- 行点击进入详情

### 10.2 详情页统一基线

当前更推荐主数据详情页统一采用：

- 顶部头部信息区
- 主信息区
- 关联关系区
- 日志 / 备注区

### 10.3 当前推荐的主按钮方向

当前一期更推荐主按钮围绕：

### 10.4 当前推荐的一句话口径

`主数据页面先做成稳定的列表页 + 详情页骨架，不先做复杂工作台。`

## 12. 对象与权限 / 记录规则之间的联动矩阵

### 12.1 当前推荐的总体理解

当前更推荐把主数据对象和权限 / 记录规则的关系理解成三层：

- 角色层：谁能进入主数据页
- 动作层：谁能新建、编辑、启停
- 记录规则层：谁能看到哪些货主 / 仓库 / 货位 / 商品数据

### 12.2 当前推荐的一页联动矩阵

| 对象 | 页面进入基线 | 关键动作基线 | 记录规则主维度 | 当前推荐口径 |
|---|---|---|---|---|
| 货主 | 主管、运营、管理员可见 | 新建、编辑、启停更偏主管 / 管理员 | 货主自身、可用仓库范围 | 货主对象是权限范围收口源头之一 |
| 商品扩展 | 操作、主管、运营可按范围可见 | 编辑更偏主管 / 管理员 | 货主、商品归属范围 | 商品可见范围不建议脱离货主口径单独漂移 |
| 条码映射 | 操作、主管、实施可按范围可见 | 新建、编辑更偏主管 / 实施 | 商品、货主 | 条码映射优先跟商品范围走 |
| 仓库扩展 | 主管、管理员、运营可见 | 编辑更偏主管 / 管理员 | 仓库 | 仓库对象是记录规则另一条主维度 |
| 货位扩展 | 操作、主管可按仓库可见 | 编辑更偏主管 / 管理员 | 仓库、货区 / 分组 | 货位范围优先跟仓库范围走 |

### 12.3 当前推荐的联动原则

- 货主对象优先决定“客户侧可见范围”
- 仓库对象优先决定“仓侧可见范围”
- 商品、条码映射优先跟随货主范围
- 货位优先跟随仓库范围

### 12.4 当前不建议的一期做法

- 为每个主数据对象单独设计完全不同的数据范围体系
- 让条码映射、货位映射脱离商品 / 仓库主维度单独授权
- 只做页面显隐，不做记录规则范围控制

### 12.5 当前推荐的一句话口径

`主数据权限先围绕“货主范围 + 仓库范围”两条主维度收口，其余对象优先跟随这两条主维度派生。`

## 13. 页面与权限侧最小口径

一期更推荐至少保证：

- 有基础档案维护入口
- 基础档案页按角色和仓库 / 货主范围控制可见性
- 不把复杂授权和复杂规则混进一期主数据页

当前更推荐页面层统一采用：

- 列表页
- 详情页
- 轻量配置入口

而不是一开始做复杂工作台。

## 14. 当前不建议的一期做法

当前不建议：

- 主数据体系另起并行数据库内核
- 把复杂客户授权、复杂计费、复杂容量算法一起塞入一期
- 把条码规则做成过重的规则引擎
- 在没有稳定基础字段之前，先做很复杂的可配置界面
