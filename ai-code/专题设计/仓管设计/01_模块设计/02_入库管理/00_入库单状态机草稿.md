## 1. 文档定位

本文件用于从总讨论稿中抽出“入库单状态机”相关内容，形成独立专题草稿。

当前重点不是覆盖全部入库业务细节，而是先固定：

- 一期主状态机
- 各状态进入 / 退出条件
- 普通取消边界
- 异常补充状态边界
- `terminated` 的一期最小规则

## 2. 范围与边界

### 2.1 当前纳入范围

- 入库单一期主状态机
- 收货与上架主流程状态
- 普通取消边界
- `receipting` 阶段终止的处理口径
- 主状态与异常补充状态的关系
- `terminated` 一期最小字段、原因、权限与展示方式

### 2.2 当前不纳入范围

- 全量入库单字段字典
- 收货 / 上架执行页细节
- 质检、预约到仓、月台等复杂扩展流程
- 入库 done 后逆向处理的详细方案
- 完整异常中心设计

## 3. 一期主状态机

当前一期更推荐入库单主状态机保持以下 7 个状态：

- `draft`
- `waiting_receipt`
- `receipting`
- `received`
- `putawaying`
- `done`
- `cancel`

对应业务理解为：

- `draft`：草稿
- `waiting_receipt`：待收货
- `receipting`：收货中
- `received`：已收货待上架
- `putawaying`：上架中
- `done`：已完成
- `cancel`：已取消

## 4. 主状态定义

### 4.1 `draft`

含义：

- 入库单已创建，但尚未进入正式收货流程

进入条件：

- 新建入库单
- 或导入后先落草稿

退出条件：

- 用户确认生效或提交，进入 `waiting_receipt`
- 用户主动取消，进入 `cancel`

### 4.2 `waiting_receipt`

含义：

- 入库单已生效，但尚未开始真实收货动作

进入条件：

- `draft` 提交成功

退出条件：

- 用户开始收货，进入 `receipting`
- 未开始收货前允许取消，进入 `cancel`

### 4.3 `receipting`

含义：

- 已开始收货，但尚未完成全部应收内容

进入条件：

- 第一次正式开始收货
- 或第一笔有效收货动作产生

退出条件：

- 全部应收数量完成收货，进入 `received`
- 收货过程中继续保持 `receipting`

### 4.4 `received`

含义：

- 收货闭环完成，但尚未开始或尚未完成上架

进入条件：

- 全部应收内容完成收货

退出条件：

- 开始上架，进入 `putawaying`
- 若后续存在特殊快捷路径，也不建议直接越过主线概念

### 4.5 `putawaying`

含义：

- 已进入上架过程，但尚未完成全部上架

进入条件：

- 第一次正式开始上架
- 或第一笔有效上架动作产生

退出条件：

- 全部待上架内容完成，进入 `done`
- 上架未完成则继续保持 `putawaying`

### 4.6 `done`

含义：

- 收货与上架都已完成
- 入库单不再存在待处理数量

进入条件：

- 收货完成
- 上架完成

退出条件：

- 无正常退出，视为终态

### 4.7 `cancel`

含义：

- 在允许取消的阶段被取消

进入条件：

- `draft / waiting_receipt` 阶段的普通取消

退出条件：

- 无正常退出，视为终态

## 5. 当前推荐的主状态推进原则

当前更推荐按以下原则推进入库单主状态：

1. 状态推进尽量由真实业务动作触发
2. 不建议仅靠人工手改状态推动主流程
3. 收货完成前不进入 `received`
4. 上架完成前不进入 `done`

一句话收口：

`开始收货，才进入 receipting；全部收完，才进入 received；开始上架，才进入 putawaying；全部上完，才进入 done。`

## 6. 普通取消边界

当前一期更推荐的普通取消边界为：

### 6.1 允许普通取消

- `draft`
- `waiting_receipt`

### 6.2 谨慎允许 / 原则上不建议直接取消

- `receipting`

### 6.3 不建议直接取消

- `received`
- `putawaying`
- `done`
- `cancel`

一句话收口：

`一期普通取消只开放到 draft / waiting_receipt；一旦开始真实收货，就不再走普通取消，而应转异常或特殊处理。`

## 7. `receipting` 阶段终止的处理口径

当前更推荐的处理方式为：

- 不继续沿用普通 `cancel`
- 视为已开始收货后的异常终止
- 保留已发生的收货事实
- 不抹掉已产生的执行痕迹

在命名候选上，当前更推荐：

- `receipt_terminated`

不再建议：

- 把这种情况继续叫普通 `cancel`

## 8. 异常补充状态设计口径

### 8.1 是否纳入主状态机

一期当前更推荐：

`先不要把 receipt_terminated 这类状态纳入入库单主状态机，而是先挂在异常流程外围。`

也就是说：

- 主状态机仍保持 7 个正常主线状态
- 终止等异常通过“异常补充状态”承接

### 8.2 主状态停留位置

若 `receipt_terminated` 挂在外围，当前更推荐：

- 主状态停在 `receipting`

不建议：

- 主状态退回 `waiting_receipt`
- 主状态改成 `cancel`
- 主状态冒充 `received`

### 8.3 页面展示建议

当前更推荐页面这样表达：

- 主状态：`收货中`
- 次标签：`已终止`

也就是说：

- 主状态占主位
- 异常补充状态做高辨识次标签

## 9. 异常补充状态统一枚举

一期当前更推荐先预留一组轻量枚举：

- `terminated`
- `exception`
- `pending_action`

但业务启用层面，一期先只实际启用：

- `terminated`

也就是说：

- 模型层允许未来扩展
- 一期真实业务流只先使用 `terminated`

## 10. `terminated` 的一期最小规则

### 10.1 最小字段

当前更推荐只保留：

- `exception_state`
- `terminated_reason`
- `terminated_remark`
- `terminated_by`
- `terminated_at`

### 10.2 原因枚举

当前更推荐 `terminated_reason` 一期先做轻量统一枚举：

- `customer_cancel`
- `goods_issue`
- `warehouse_issue`
- `other`

并配合：

- `terminated_remark`

作为补充说明。

### 10.3 发起权限

当前更推荐一期只允许以下角色发起 `terminated`：

- 仓管主管 / 组长
- 有专门异常处理权限的人

### 10.4 触发后的处理建议

触发 `terminated` 后，当前更推荐：

- 主单主状态仍停在 `receipting`
- 异常补充状态置为 `terminated`
- 已产生的收货事实继续保留
- 未完成部分不再继续按正常主线推进
- 后续转异常处理或补充流程

### 10.5 一期不支持的能力

当前更推荐一期先不支持：

- “终止后恢复”按钮
- 在原单上直接恢复主线

## 11. 页面与筛选口径

当前更推荐：

- 列表页主状态仍按 `receipting` 归类
- 同时支持按异常补充状态做额外筛选
- 详情页单独有异常处理信息区
- 一期应有轻量“待异常处理”视图

详情页中的异常处理信息区，一期最小展示建议为：

- 异常补充状态
- 原因
- 备注
- 处理人
- 时间

## 12. 入库单按钮与状态联动矩阵

本节用于把前述入库单状态机进一步映射到详情页常见按钮与动作入口，形成一期更可执行的按钮基线。

### 12.1 当前纳入矩阵的按钮范围

当前先聚焦一批高频、关键按钮：

- `提交 / 生效`
- `取消`
- `开始收货`
- `开始上架`
- `查看收货记录`
- `查看上架记录`
- `终止（terminated）`
- `查看异常处理信息`

这里的原则是：

- 普通详情页先只收页面级 / 记录级按钮
- 执行页内的“确认本次”“完成本次记录”不在本节展开

### 12.2 按钮与状态联动的当前总原则

当前更推荐按以下原则统一理解：

1. `draft` 承接建单后确认与取消
2. `waiting_receipt` 承接收货启动入口
3. `receipting` 承接收货中查看与异常终止
4. `received` 承接上架启动入口
5. `putawaying` 承接上架中查看与跟踪
6. `done` 以查看与追溯为主，不再提供主流程推进按钮
7. `cancel` 以查看为主，不再提供普通主流程动作

### 12.3 当前推荐的按钮矩阵

| 按钮 / 动作 | draft | waiting_receipt | receipting | received | putawaying | done | cancel |
|---|---|---|---|---|---|---|---|
| 提交 / 生效 | 是 | 否 | 否 | 否 | 否 | 否 | 否 |
| 取消 | 是 | 是 | 否 | 否 | 否 | 否 | 否 |
| 开始收货 | 否 | 是 | 是 | 否 | 否 | 否 | 否 |
| 开始上架 | 否 | 否 | 否 | 是 | 是 | 否 | 否 |
| 查看收货记录 | 否 | 否 | 是 | 是 | 是 | 是 | 否 |
| 查看上架记录 | 否 | 否 | 否 | 否 | 是 | 是 | 否 |
| 终止（terminated） | 否 | 否 | 是 | 否 | 否 | 否 | 否 |
| 查看异常处理信息 | 否 | 否 | 条件显示 | 否 | 条件显示 | 条件显示 | 否 |

上表中的“是 / 否 / 条件显示”当前建议这样理解：

- `是`：一期默认可显示，仍需满足角色权限
- `否`：一期默认不显示
- `条件显示`：仅当存在异常补充状态或异常信息时显示

### 12.4 关键按钮的当前解释口径

#### A. `提交 / 生效`

当前更推荐：

- 只在 `draft` 显示
- 触发后主状态进入 `waiting_receipt`

#### B. `取消`

当前更推荐：

- 只在 `draft / waiting_receipt` 显示
- 一旦开始真实收货，就不再作为普通按钮出现

#### C. `开始收货`

当前更推荐：

- 在 `waiting_receipt` 显示为主
- 在 `receipting` 可继续显示为“继续收货”语义
- 触发后进入或继续停留在 `receipting`

#### D. `开始上架`

当前更推荐：

- 在 `received` 显示为主
- 在 `putawaying` 可继续显示为“继续上架”语义
- 不在 `receipting` 提前开放

#### E. `终止（terminated）`

当前更推荐：

- 只在 `receipting` 阶段开放
- 且仅对主管 / 异常处理权限角色可见
- 触发后主状态仍停在 `receipting`
- 异常补充状态置为 `terminated`

### 12.5 按钮分层建议

当前更推荐在详情页上按以下层次放置：

#### 顶部主按钮区

优先承接：

- `提交 / 生效`
- `取消`
- `开始收货`
- `开始上架`

#### 次级入口 / smart button 区

优先承接：

- `查看收货记录`
- `查看上架记录`
- `查看异常处理信息`

#### 危险动作或更多菜单

优先承接：

- `终止（terminated）`

也就是说，`terminated` 当前不建议与普通主流程按钮并列抢主位。

### 12.6 当前不建议的一期做法

当前不建议一期采用以下做法：

- 在 `receipting` 继续保留普通 `取消`
- 在 `received` 前提前开放 `开始上架`
- 在 `done` 上继续保留主流程推进按钮
- 把 `terminated` 直接放成和 `开始收货` 同层级的普通主按钮
- 让“查看异常处理信息”长期占位但没有异常内容

### 12.7 当前阶段关于按钮与状态联动的统一收口

截至当前阶段，更推荐统一收敛为：

1. `draft` 负责提交与取消
2. `waiting_receipt / receipting` 负责收货入口
3. `received / putawaying` 负责上架入口
4. `done / cancel` 以查看与追溯为主
5. `terminated` 只在 `receipting` 阶段开放，且作为危险动作下沉

## 13. 入库单状态与执行记录的联动矩阵

本节用于把入库单主状态与两类关键执行记录进一步挂钩：

- `receive record`
- `putaway record`

当前目标不是穷尽所有细节，而是先固定“一期主状态大致对应什么执行记录状态和行为”。

### 13.1 当前联动的统一原则

当前更推荐按以下原则理解：

1. 主状态表达主单所处业务阶段
2. 执行记录表达该阶段内已发生或正在发生的动作
3. 主状态不直接替代执行记录
4. 执行记录也不反向替代主状态
5. 页面展示时，主单状态与执行记录进度应互相印证

### 13.2 当前推荐的联动矩阵

| 主状态 | 收货记录（receive record） | 上架记录（putaway record） | 当前理解 |
|---|---|---|---|
| `draft` | 无 | 无 | 尚未进入执行 |
| `waiting_receipt` | 无 | 无 | 已生效，待开始收货 |
| `receipting` | 可存在 `draft / in_progress / done` | 无 | 已开始收货，允许分批、多次收货 |
| `received` | 已存在且应全部达到 `done` | 无或仅预备 | 收货闭环完成，尚未进入正式上架 |
| `putawaying` | 已存在且应为 `done` | 可存在 `draft / in_progress / done` | 已开始上架，允许分批、多次上架 |
| `done` | 已完成 | 已完成 | 收货与上架均完成 |
| `cancel` | 无 | 无 | 未进入真实执行即取消 |

### 13.3 当前推荐的状态判断口径

#### A. 从 `waiting_receipt` 到 `receipting`

当前更推荐以“第一笔有效收货动作或正式开始收货”为判断点。

也就是说：

- 不是看页面有没有打开
- 而是看是否真实进入收货执行

#### B. 从 `receipting` 到 `received`

当前更推荐以“应收内容全部完成收货”为判断点。

也就是说：

- `receive record` 可以有多条
- 但主单进入 `received` 时，收货闭环应已完成

#### C. 从 `received` 到 `putawaying`

当前更推荐以“第一笔有效上架动作或正式开始上架”为判断点。

#### D. 从 `putawaying` 到 `done`

当前更推荐以“全部待上架内容完成”为判断点。

### 13.4 终止场景下的联动口径

若发生 `terminated`，当前更推荐：

- 主单主状态仍停在 `receipting`
- `receive record` 保留已发生事实
- `putaway record` 不继续正常推进

也就是说：

- 主状态继续反映“已开始收货但未完成”
- 异常补充状态负责告诉用户“当前已终止”

### 13.5 当前不建议的一期做法

当前不建议一期采用以下方式：

- 用 `receive record` 的最后一条状态直接代替主单主状态
- 主单一进入 `received` 就自动生成完整上架记录并视为开始上架
- 让收货未闭环时提前出现 `putaway record` 主体执行语义
- 通过删除执行记录来回退主状态

### 13.6 当前阶段关于状态与执行记录联动的统一收口

截至当前阶段，更推荐统一收敛为：

1. `waiting_receipt` 之前无正式执行记录
2. `receipting` 主要由收货记录承接
3. `received` 表示收货闭环完成、上架尚未正式开始
4. `putawaying` 主要由上架记录承接
5. `done` 表示收货记录与上架记录都已完成

## 14. 入库单详情页 / 列表页状态展示口径

本节用于把入库单主状态与异常补充状态进一步收成页面语言，避免后续同一状态在列表页和详情页各说各话。

### 14.1 当前推荐的展示总原则

当前更推荐按以下原则统一展示：

1. 列表页优先追求短、稳、易扫读
2. 详情页允许比列表页多一层解释
3. 主状态始终占主位
4. 异常补充状态始终做次标签
5. 不把主状态和异常补充状态混写成一个新的数据库状态名

### 14.2 列表页展示口径

当前更推荐列表页按以下方式展示：

| 主状态 | 列表页主展示 | 次标签（如有） |
|---|---|---|
| `draft` | 草稿 | 无 |
| `waiting_receipt` | 待收货 | 无 |
| `receipting` | 收货中 | `已终止`（如 terminated） |
| `received` | 已收货待上架 | 无 |
| `putawaying` | 上架中 | `异常` / `待处理`（后续如启用） |
| `done` | 已完成 | 可不加 |
| `cancel` | 已取消 | 可不加 |

这里的关键统一点是：

- 列表页主列只显示主状态短语义
- 补充情况通过次标签补充
- 不把 `receipting + terminated` 合并成一个新的主状态文案

### 14.3 详情页头部展示口径

当前更推荐详情页头部按以下方式展示：

- 主状态：显示主状态中文语义
- 异常补充状态：显示为次标签
- 辅助说明：必要时补一句更完整的解释文案

例如在 `receipting + terminated` 场景下：

- 主状态：`收货中`
- 次标签：`已终止`
- 说明文案：`当前单据已开始收货，但后续处理已终止。`

### 14.4 列表筛选与状态归类口径

当前更推荐：

1. 主状态筛选继续按主状态归类
2. 异常补充状态单独作为补充筛选条件
3. `receipting + terminated` 在主状态筛选中仍归入 `receipting`
4. 同时支持“仅看已终止”等异常补充状态筛选

也就是说：

- 主状态筛选不被异常补充状态打乱
- 异常筛选另开一条口径

### 14.5 执行记录区与状态展示的当前建议

当前更推荐：

- 在主状态为 `receipting` 时，执行记录区重点展示收货记录
- 在主状态为 `received` 时，执行记录区强调收货已完成、上架待开始
- 在主状态为 `putawaying` 时，执行记录区重点展示上架记录
- 在 `done` 时，收货记录与上架记录都应可完整回看

这意味着页面应让用户同时看清：

- 当前主状态是什么
- 执行动作目前推进到了哪一层

### 14.6 异常信息区的当前展示口径

当存在异常补充状态时，当前更推荐异常信息区最小展示：

- 异常补充状态
- 终止原因 / 异常原因
- 备注
- 处理人
- 时间

若不存在异常补充状态，则：

- 可整体弱化
- 或不在详情页正文中占主视觉位置

### 14.7 当前不建议的一期做法

当前不建议一期采用以下方式：

- 列表页把主状态和异常补充状态拼成过长文案
- 详情页只显示异常标签，不显示主状态
- 因存在 `terminated` 就把主状态从 `receipting` 挪走
- 列表页和详情页对同一状态使用不同中文语义

### 14.8 当前阶段关于页面状态展示的统一收口

截至当前阶段，更推荐统一收敛为：

1. 列表页主状态短展示，异常做次标签
2. 详情页头部保留主状态主位，异常做次标签并允许补说明
3. 主状态筛选与异常补充状态筛选分开
4. `receipting + terminated` 仍按 `receipting` 归主状态，只在页面上补 `已终止`

## 15. 入库单与收货页、上架页的跳转规则

本节用于把入库单主状态进一步映射到：

- 详情页如何进入收货页
- 详情页如何进入上架页
- 执行页如何回到主单
- 哪些状态不应开放错误跳转

当前目标是先固定一期主路径，避免后续收货页、上架页入口分散。

### 15.1 当前推荐的跳转总原则

当前更推荐按以下原则统一理解：

1. 主路径始终是：`列表 -> 详情 -> 执行页`
2. 收货页与上架页都应从入库单详情页发起为主
3. 待处理列表可作为辅助入口，但不替代详情页主入口
4. 执行页完成后应优先回到对应入库单详情上下文
5. 不开放与当前主状态明显不匹配的执行入口

### 15.2 入库单详情页到收货页的当前规则

当前更推荐：

- `waiting_receipt`
  - 可显示并进入“开始收货”
- `receipting`
  - 可显示并进入“继续收货”
- 其他状态
  - 不作为正常收货入口开放

也就是说：

| 主状态 | 收货页入口建议 |
|---|---|
| `draft` | 不开放 |
| `waiting_receipt` | 开放“开始收货” |
| `receipting` | 开放“继续收货” |
| `received` | 不开放 |
| `putawaying` | 不开放 |
| `done` | 不开放 |
| `cancel` | 不开放 |

### 15.3 入库单详情页到上架页的当前规则

当前更推荐：

- `received`
  - 可显示并进入“开始上架”
- `putawaying`
  - 可显示并进入“继续上架”
- 其他状态
  - 不作为正常上架入口开放

也就是说：

| 主状态 | 上架页入口建议 |
|---|---|
| `draft` | 不开放 |
| `waiting_receipt` | 不开放 |
| `receipting` | 不开放 |
| `received` | 开放“开始上架” |
| `putawaying` | 开放“继续上架” |
| `done` | 不开放 |
| `cancel` | 不开放 |

### 15.4 待处理列表到执行页的当前规则

当前更推荐待处理列表作为辅助入口：

- `待收货`
  - 进入收货执行页
- `待上架`
  - 进入上架执行页

但这里仍建议保持两条统一口径：

1. 待处理列表本质是辅助入口，不替代主单详情
2. 从待处理列表进入执行页时，执行页头部应仍清楚保留主单上下文

### 15.5 执行页返回主单的当前规则

当前更推荐：

- 收货页
  - 返回到原入库单详情页
- 上架页
  - 返回到原入库单详情页

返回后应尽量保持：

- 同一主单上下文
- 可继续查看执行记录
- 可继续发起下一步动作

也就是说，当前不建议执行页返回一个泛列表作为默认主出口。

### 15.6 执行页完成后的当前建议路径

当前更推荐：

#### A. 收货页完成后

- 若仍有待收内容：
  - 停留在收货页继续处理
  - 或返回详情页继续观察
- 若全部收货完成：
  - 返回详情页时主状态应体现为 `received`
  - 详情页可进一步出现“开始上架”入口

#### B. 上架页完成后

- 若仍有待上架内容：
  - 停留在上架页继续处理
  - 或返回详情页继续观察
- 若全部上架完成：
  - 返回详情页时主状态应体现为 `done`

### 15.7 终止场景下的跳转口径

若入库单在 `receipting` 阶段发生 `terminated`，当前更推荐：

- 收货页不再作为正常继续推进入口
- 详情页仍可查看收货记录
- 详情页显示异常处理信息区
- 后续转异常处理，不继续开放正常收货主路径

也就是说：

- 主状态仍停在 `receipting`
- 但页面入口行为应按“已终止”收紧

### 15.8 当前不建议的一期做法

当前不建议一期采用以下方式：

- 在 `receipting` 状态同时开放“开始上架”
- 在 `received` 后仍继续保留“开始收货”
- 从普通列表页直接作为主入口跳到收货页 / 上架页
- 执行页默认返回总列表而丢失主单上下文
- `terminated` 之后仍保留正常“继续收货”入口

### 15.9 当前阶段关于入库跳转规则的统一收口

截至当前阶段，更推荐统一收敛为：

1. 收货入口只属于 `waiting_receipt / receipting`
2. 上架入口只属于 `received / putawaying`
3. 详情页是主执行入口，待处理列表是辅助入口
4. 执行页默认返回主单详情，而不是总列表
5. `terminated` 后收紧正常执行入口，转异常处理口径

## 16. 入库单字段字典与状态字段落表方式

本节用于把前述状态机与异常补充状态进一步映射到一期更可执行的数据字段口径。

当前目标不是一次性做完整字段字典，而是先固定：

- 入库单主状态字段
- 异常补充状态字段
- `terminated` 相关最小字段
- 页面展示和筛选最依赖的核心字段

### 16.1 当前推荐的字段分层

当前更推荐把入库单相关字段先分成以下 4 层：

1. 主单身份字段
2. 主流程状态字段
3. 异常补充状态字段
4. 统计 / 展示辅助字段

也就是说，一期先把真正驱动流程的字段和展示辅助字段分开，不建议全部混成一个平铺大表。

### 16.2 一期最小核心字段字典

当前更推荐入库单模型至少先保留以下核心字段：

| 字段名 | 建议类型 | 当前用途 |
|---|---|---|
| `name` | `Char` | 入库单号 |
| `owner_id` | `Many2one` | 货主 |
| `warehouse_id` | `Many2one` | 仓库 |
| `state` | `Selection` | 主状态 |
| `exception_state` | `Selection` | 异常补充状态 |
| `terminated_reason` | `Selection` | 终止原因 |
| `terminated_remark` | `Text` | 终止备注 |
| `terminated_by` | `Many2one` | 终止操作人 |
| `terminated_at` | `Datetime` | 终止时间 |
| `responsible_id` | `Many2one` | 负责人/责任人 |
| `create_date` | `Datetime` | 创建时间 |
| `write_date` | `Datetime` | 最后修改时间 |

如果后续要补业务维度字段，可在此基础上继续扩：

- `inbound_type`
- `source_ref`
- `customer_ref`
- `remark`

但这些不影响当前状态机主线，不作为本节重点。

### 16.3 `state` 字段的当前落表建议

当前更推荐：

- 字段名：`state`
- 类型：`Selection`
- 作为入库单主状态字段

一期枚举值当前更推荐固定为：

- `draft`
- `waiting_receipt`
- `receipting`
- `received`
- `putawaying`
- `done`
- `cancel`

当前更推荐：

- `state` 只承接主流程状态
- 不把 `receipt_terminated` 这类异常终止值塞进 `state`

### 16.4 `exception_state` 字段的当前落表建议

当前更推荐：

- 字段名：`exception_state`
- 类型：`Selection`
- 用途：承接主状态之外的异常补充状态

一期先预留枚举：

- `terminated`
- `exception`
- `pending_action`

但一期真实业务启用层面，当前更推荐只实际使用：

- `terminated`

也就是说：

- 模型上可先做可扩展设计
- 页面和业务流上一期只先落 `terminated`

### 16.5 `terminated_*` 字段的当前落表建议

当前更推荐以下字段直接落在入库单主模型上：

- `terminated_reason`
- `terminated_remark`
- `terminated_by`
- `terminated_at`

原因是：

1. 一期暂不做完整异常中心
2. 当前只需要最小异常闭环
3. 这些字段与入库单详情页异常信息区直接对应

当前不建议一期为了这组字段额外起一张重型异常子表。

### 16.6 `terminated_reason` 的当前落表建议

当前更推荐：

- 字段名：`terminated_reason`
- 类型：`Selection`

一期建议枚举为：

- `customer_cancel`
- `goods_issue`
- `warehouse_issue`
- `other`

同时保留：

- `terminated_remark`

作为自由补充说明。

### 16.7 当前推荐的页面字段映射关系

当前更推荐页面层按以下关系取值：

| 页面位置 | 推荐字段来源 |
|---|---|
| 列表页主状态列 | `state` |
| 列表页异常次标签 | `exception_state` |
| 详情页头部主状态 | `state` |
| 详情页头部异常标签 | `exception_state` |
| 异常信息区原因 | `terminated_reason` |
| 异常信息区备注 | `terminated_remark` |
| 异常信息区处理人 | `terminated_by` |
| 异常信息区时间 | `terminated_at` |

也就是说：

- 页面主状态统一来自 `state`
- 页面异常补充展示统一来自 `exception_state` 与 `terminated_*`

### 16.8 当前推荐的筛选字段口径

一期更推荐列表与搜索至少支持以下状态相关筛选：

- `state`
- `exception_state`
- `terminated_reason`

其中：

- `state` 负责主流程归类
- `exception_state` 负责异常补充状态归类
- `terminated_reason` 负责异常原因进一步下钻

### 16.9 当前不建议的一期落表方式

当前不建议一期采用以下方式：

- 把 `terminated` 直接塞进 `state`
- 同时再做一套并行的“页面状态字段”
- 为一期最小异常闭环单独拆重型异常主表
- 用计算文案字段替代真正的 `state / exception_state`
- 把收货执行记录状态直接存回主单，替代主状态字段

### 16.10 当前阶段关于字段字典与落表方式的统一收口

截至当前阶段，更推荐统一收敛为：

1. `state` 只承接主流程状态
2. `exception_state` 只承接异常补充状态
3. `terminated_*` 先作为入库单主模型上的最小异常字段组直接落表
4. 页面主状态、异常标签、异常信息区都直接从这组字段取值
5. 一期不额外构建并行页面状态字段或重型异常子表

## 17. 入库单状态与 stock 原生对象的字段级关联

本节用于把前述入库单主状态机进一步挂到 Odoo 原生 stock 对象上，形成一期更清楚的字段级关联基线。

当前目标不是一次性给出所有技术字段，而是先固定：

- 主单与 `stock.picking` 的关联
- 入库单明细与 `stock.move` 的关联
- 收货 / 上架记录与 `stock.move.line` 的关联
- 主状态推进时更依赖哪些 stock 层事实

### 17.1 当前推荐的总体关联原则

当前更推荐继续沿以下原则推进：

1. 入库单负责业务主线与业务语义
2. `stock.picking / stock.move / stock.move.line` 负责执行事实
3. 主状态判断尽量依赖真实执行事实，而不是手工改状态
4. 不额外构建并行库存事实表

一句话收口：

`入库单负责“为什么做、做到哪”，stock 负责“货实际上怎么动了”。`

### 17.2 入库单主单与 `stock.picking` 的当前关联建议

当前更推荐：

- 收货执行：
  - `stock.picking.wms_inbound_receipt_id -> logistics.wms.inbound`
- 上架执行：
  - `stock.picking.wms_inbound_putaway_id -> logistics.wms.inbound`

对应在入库单主模型上反查：

- `receipt_picking_ids`
- `putaway_picking_ids`

当前建议的理解是：

- 收货对应一组 receipt picking
- 上架对应一组 internal picking
- 一张入库单允许对应多张 picking，不做死的一对一

### 17.3 入库单明细与 `stock.move` 的当前关联建议

当前更推荐：

- `stock.move.wms_inbound_line_id -> logistics.wms.inbound.line`

对应在入库单明细上反查：

- `stock_move_ids`

这条关联主要用于承接：

- 哪条入库明细产生了哪些商品级移动计划
- 收货与后续上架的 move 如何回到入库单明细

### 17.4 收货记录与 `stock.move.line` 的当前关联建议

当前更推荐：

- `stock.move.line.wms_receive_record_id -> logistics.wms.receive.record`

对应在收货记录上反查：

- `stock_move_line_ids`

当前建议的理解是：

- `receive record` 表达一次收货业务动作
- `move.line` 表达该动作下实际收了哪些货、批次、数量、位置

### 17.5 上架记录与 `stock.move / stock.move.line` 的当前关联建议

当前更推荐：

- `stock.move.wms_putaway_line_id -> logistics.wms.putaway.line`
- `stock.move.line.wms_putaway_line_id -> logistics.wms.putaway.line`

如果一期上架记录先不拆明细表，则当前至少保留：

- `putaway record -> stock.picking`
- `putaway record -> stock.move.line` 的反查口径

当前建议的理解是：

- 上架业务记录负责表达“这一轮上架动作”
- stock 侧对象负责表达“从哪里移到哪里、移了多少”

### 17.6 主状态与 stock 事实的当前对应口径

当前更推荐按以下方式理解主状态与 stock 层事实的关系：

| 主状态 | 更依赖的 stock 事实 |
|---|---|
| `draft` | 尚无正式 stock 执行事实 |
| `waiting_receipt` | 尚无正式 receipt picking 执行事实 |
| `receipting` | 已存在 receipt picking / receipt move line |
| `received` | 收货相关 move line 已形成完整闭环 |
| `putawaying` | 已存在 putaway internal picking / putaway move line |
| `done` | 收货与上架相关 stock 执行事实均完成 |
| `cancel` | 未形成正式执行事实或已在允许阶段取消 |

也就是说：

- `receipting` 的成立应与 receipt picking / move line 对上
- `putawaying` 的成立应与 putaway picking / move line 对上

### 17.7 `terminated` 场景与 stock 事实的当前口径

若发生 `terminated`，当前更推荐：

- 主状态仍停在 `receipting`
- `receipt picking / move line` 已发生的事实继续保留
- 不通过删除 stock 执行事实来“伪造回退”
- `putaway picking` 不继续正常推进

也就是说：

- `terminated` 是对主线推进的收紧
- 不是对既有 stock 事实的抹除

### 17.8 当前推荐的字段级最小清单

当前更推荐一期至少先把以下字段级关联稳定下来：

#### 入库单主单侧

- `state`
- `exception_state`
- `receipt_picking_ids`
- `putaway_picking_ids`

#### 入库单明细侧

- `stock_move_ids`

#### stock.picking 侧

- `wms_inbound_receipt_id`
- `wms_inbound_putaway_id`

#### stock.move 侧

- `wms_inbound_line_id`
- `wms_putaway_line_id`

#### stock.move.line 侧

- `wms_receive_record_id`
- `wms_putaway_line_id`

### 17.9 当前不建议的一期做法

当前不建议一期采用以下方式：

- 入库单自己再造一套并行库存主表
- 用主单状态直接替代 picking / move / move line 的完成事实
- 用删除 stock 记录的方式回退主状态
- 让 `received` 在没有形成完整收货事实时提前成立
- 让 `putawaying` 在没有正式上架 stock 事实时提前成立

### 17.10 当前阶段关于入库单与 stock 字段级关联的统一收口

截至当前阶段，更推荐统一收敛为：

1. 主单与 `stock.picking` 通过收货 / 上架两组外键反查关联
2. 入库单明细与 `stock.move` 建立稳定行级关联
3. 收货记录、上架记录与 `stock.move.line` 建立执行层关联
4. 主状态推进尽量以 stock 执行事实为基础判断
5. `terminated` 不抹除已发生的 stock 事实，只改变主线推进口径

## 18. 入库单 search / filter / group by 的最终口径

本节用于把前述状态机、异常补充状态、页面展示与字段落表方式，进一步收成一期入库单搜索与列表分析的统一口径。

当前目标不是一次性定义所有高级搜索，而是先固定：

- search view 的最小搜索字段
- filter 的最小状态 / 异常 / 时间口径
- group by 的最小分析维度
- 主状态与异常补充状态在搜索上的分层方式

### 18.1 当前推荐的总体原则

当前更推荐按以下原则统一理解：

1. `search` 负责快速定位单据
2. `filter` 负责固定业务场景筛选
3. `group by` 负责常用管理分析维度
4. 主状态与异常补充状态在搜索口径上继续分层
5. 一期先做高频、低歧义的搜索项，不把 search view 做得过重

### 18.2 当前推荐的 search 字段口径

一期当前更推荐 search view 至少支持以下关键字搜索对象：

- 入库单号 `name`
- 货主名称 / 编码
- 来源单号 / 外部参考号（如后续启用）
- 仓库名称

如果一期业务字段已落地，也可补：

- `source_ref`
- `customer_ref`

但当前更推荐最小搜索仍以：

- `name`
- `owner_id`
- `warehouse_id`

为主。

### 18.3 当前推荐的 filter 口径

一期当前更推荐至少保留以下固定筛选：

#### A. 主状态类 filter

- 草稿
- 待收货
- 收货中
- 已收货待上架
- 上架中
- 已完成
- 已取消

这些 filter 统一对应：

- `state`

#### B. 异常补充状态类 filter

- 仅看异常
- 仅看已终止

这些 filter 统一对应：

- `exception_state`

当前更推荐：

- 主状态 filter 与异常补充状态 filter 分开定义
- 不把“收货中已终止”做成新的主状态 filter

#### C. 时间类 filter

一期当前更推荐至少保留：

- 今日创建
- 近 7 天
- 近 30 天

时间口径当前优先建议基于：

- `create_date`

如后续业务更强调处理时间，再按需补：

- `terminated_at`

### 18.4 当前推荐的异常原因 filter 口径

若一期已启用 `terminated_reason`，当前更推荐再补一组轻量异常原因筛选：

- 客户取消
- 货物异常
- 仓内原因
- 其他

这些 filter 统一对应：

- `terminated_reason`

当前更推荐仅在：

- 已启用 `terminated`
- 且异常处理视图或详情分析场景

中强化使用，不必在所有普通视图默认铺满。

### 18.5 当前推荐的 group by 口径

一期当前更推荐至少保留以下 group by：

- 按主状态
- 按异常补充状态
- 按货主
- 按仓库
- 按创建日期（月 / 日）

如果后续业务字段启用，也可逐步补：

- 按入库类型
- 按负责人

但当前不建议一期就堆太多 group by 维度。

### 18.6 当前推荐的主状态与异常口径分层

当前更推荐继续按以下方式统一：

| 口径层 | 对应字段 | 当前用途 |
|---|---|---|
| 主流程筛选 | `state` | 主流程阶段归类 |
| 异常补充筛选 | `exception_state` | 异常补充状态归类 |
| 异常原因筛选 | `terminated_reason` | 终止原因下钻 |

也就是说：

- 搜索时先找主流程阶段
- 再看异常补充状态
- 最后才按异常原因细分

### 18.7 当前推荐的视图使用方式

当前更推荐：

#### 普通入库单列表页

优先保留：

- 主状态 filter
- 货主 / 仓库
- 时间
- 关键字搜索

#### 待异常处理视图

优先强化：

- `exception_state`
- `terminated_reason`
- 货主
- 仓库
- 时间

也就是说，异常视图应比普通列表更强调异常补充状态口径。

### 18.8 当前不建议的一期做法

当前不建议一期采用以下方式：

- 把 `state` 和 `exception_state` 混成一套搜索字段
- 在普通列表里默认铺满所有异常原因 filter
- 一上来就提供太多 group by 维度
- 为每个状态都再做一套重复的“快捷搜索别名”
- 让 `receipting + terminated` 变成新的主流程 group by 项

### 18.9 当前阶段关于 search / filter / group by 的统一收口

截至当前阶段，更推荐统一收敛为：

1. `search` 以单号、货主、仓库为主
2. `filter` 以主状态、异常补充状态、时间为主
3. `group by` 以主状态、异常补充状态、货主、仓库、日期为主
4. `state / exception_state / terminated_reason` 三层口径继续分开
5. 异常视图比普通列表页更强调异常补充筛选与异常原因筛选
