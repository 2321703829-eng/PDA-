## 1. 文档定位

本文件用于承接仓管模块中 4 类主单的统一页面结构规范草稿，当前覆盖：

- 入库单
- 出库单
- 盘点单
- 移位单

这份文档的目标不是替代各单据的详细业务设计，而是先固定一套可复用的页面骨架、跳转路径、按钮职责、状态表达与差异化边界，供后续：

- 设计稿整理
- 前端实现
- 页面评审
- 正式规范沉淀

共同参照。

## 2. 统一目标

4 类主单页面当前统一目标为：

1. 在同一个 Odoo 后台内保持一致的信息架构与操作节奏
2. 尽量参照现有物流模块的页面结构、按钮位置、状态展示和交互习惯
3. 让差异主要体现在业务对象与字段上，而不是整体布局语言上
4. 让列表页、详情页、执行页形成稳定且可预期的跳转路径

## 3. 统一骨架

### 3.1 列表页骨架

列表页统一采用：

- 顶部筛选区
- 中部主表格
- 右上新建 / 导入 / 批量动作区
- 行点击进入详情
- 底部分页

列表页的主要职责当前定义为：

- 查找
- 筛选
- 进入详情

列表页不承担主执行入口。

### 3.2 详情页骨架

详情页统一采用：

- 头部
- 主信息
- 执行记录
- 异常信息
- 日志

其中：

- 头部用于主单身份、状态和页面级动作
- 主信息用于核心业务信息
- 执行记录用于承接收货、上架、拣货、复核、盘点、移位等动作记录
- 异常信息用于承接异常补充状态和处理信息
- 日志用于追溯

### 3.3 执行页骨架

执行页统一采用：

- 顶部上下文区
- 中部主从双栏
- 底部 tab 区

当前统一理解为：

- 顶部：主单上下文 + 页面级按钮
- 中部左侧：待处理表格
- 中部右侧：当前执行面板
- 底部：进度摘要 / 执行日志 / 关联执行对象 / 证据附件

### 3.4 主跳转路径

主跳转路径统一为：

`列表 -> 详情 -> 执行 / 处理子动作`

当前只在特殊情况下允许从待处理视图直接进入执行页，不作为主路径。

## 4. 统一规则

### 规则 1

`主跳转路径统一为：列表 -> 详情 -> 执行 / 处理子动作`

### 规则 2

`详情页统一采用：头部 + 主信息 + 执行记录 + 异常信息 + 日志`

### 规则 3

`执行页统一采用：顶部上下文 + 中部主从双栏 + 底部 tab`

### 规则 4

`头部字段统一采用：公共字段 + 少量单据特有字段`

### 规则 5

`顶部按钮统一只放页面级 / 记录级动作，不放当前动作级按钮`

### 规则 6

`左侧列表统一采用表格，不用卡片作为主形态`

### 规则 7

`状态表达统一采用：主状态占主位，异常补充状态做次标签`

### 规则 8

`列表筛选统一采用：公共筛选骨架 + 单据补一个关键维度`

### 规则 9

`提示反馈统一采用：提示条 / toast / 弹窗三层分工`

### 规则 10

`done 统一视为终态，后续问题走新单、异常或调整流程，不直接回退原单`

## 5. 头部字段统一规则

### 5.1 公共字段

4 类主单头部当前统一建议保留：

- 单号
- 货主
- 仓库
- 当前主状态
- 异常补充状态（如有）
- 负责人 / 操作人
- 创建时间

### 5.2 各单据特有字段

- 入库单：供应来源 / 入库类型
- 出库单：出库类型 / 客户单号
- 盘点单：盘点范围
- 移位单：来源区域 / 目标区域摘要

## 6. 列表筛选统一规则

### 6.1 公共筛选骨架

4 类主单列表当前统一建议保留：

- 关键字搜索
- 主状态
- 仓库
- 货主
- 时间范围

### 6.2 单据补充筛选

- 入库单：异常补充状态或入库类型
- 出库单：异常补充状态或出库类型
- 盘点单：盘点范围
- 移位单：来源 / 目标区域

## 7. 按钮区统一规则

### 7.1 顶部按钮区

顶部按钮区统一只放：

- 页面级动作
- 记录级动作

不放：

- 当前动作级按钮

### 7.2 当前动作级按钮

当前动作级按钮统一放在执行页右侧执行面板中，例如：

- 确认本次
- 确认并下一条
- 完成本次记录
- 取消

## 8. 状态与异常表达统一规则

### 8.1 主状态

主状态始终占主位，负责表达当前主流程所处阶段。

### 8.2 异常补充状态

异常补充状态当前统一作为次标签显示，不直接取代主状态。

例如：

- 主状态：`收货中`
- 次标签：`已终止`

### 8.3 done 终态

4 类主单中，`done` 当前统一视为终态。

后续如发现问题，当前统一建议：

- 走新单
- 走异常流程
- 走调整流程

而不是直接回退原单。

## 9. 提示反馈统一规则

### 9.1 三层分工

提示反馈统一采用：

- 提示条：页内持续反馈
- toast：短暂结果反馈
- 弹窗：确认或阻断决策

### 9.2 提示条

提示条当前用于承接：

- 阻断性校验
- 当前动作结果
- 记录级状态
- 下一步引导

### 9.3 toast

success toast 当前统一建议采用：

`动作结果 + 当前对象`

例如：

- `本次收货已确认`
- `本次拣货已确认`

### 9.4 弹窗

确认弹窗当前统一建议采用：

- 普通确认
- 危险确认

并遵守：

- 安全按钮在左
- 危险或继续动作在右
- 默认焦点给安全按钮

## 10. 差异化说明

### 10.1 仅保留必要差异

本规范中的差异化说明当前只建议保留到以下 4 层：

- 头部特有字段
- 列表补充筛选
- 执行记录差异
- 异常信息差异

当前不建议在统一页面结构规范中继续下钻到过细的按钮文案、颜色或低层实现细节。

### 10.2 四类主单差异边界

四类主单当前只在以下 4 个维度保留差异化说明：

1. 头部特有字段
2. 列表补充筛选
3. 执行记录区内容
4. 异常信息区内容

#### 入库单

头部特有字段：

- 供应来源
- 入库类型

列表补充筛选：

- 入库类型
- 异常补充状态

执行记录区内容：

- 收货记录
- 上架记录
- 收货与上架的数量进度

异常信息区内容：

- 收货终止信息
- 待上架异常说明
- 终止原因、备注、处理人、时间

当前说明：

- 入库单的执行记录重点是“货进仓”和“货落位”
- 异常信息重点围绕收货中断、收货完成未上架、上架卡住等场景

#### 出库单

头部特有字段：

- 出库类型
- 客户单号

列表补充筛选：

- 出库类型
- 异常补充状态

执行记录区内容：

- 拣货记录
- 复核记录
- 发货确认记录

异常信息区内容：

- 拣货终止信息
- 复核终止信息
- 待发货前异常说明
- 终止原因、备注、处理人、时间

当前说明：

- 出库单执行记录重点是“从拣货到发货”
- 异常信息重点围绕发货前仓内异常，不承接发货后物流/履约异常主语义

#### 盘点单

头部特有字段：

- 盘点范围
- 盘点方式（后续如启用）

列表补充筛选：

- 盘点范围
- 差异处理结果

执行记录区内容：

- 盘点过程记录
- 差异确认记录
- 差异结果摘要

异常信息区内容：

- 一期不做重异常补充状态区
- 优先通过差异处理结果、差异说明和处理备注表达

当前说明：

- 盘点单天然自带“差异处理”语义
- 一期不建议额外叠加重异常状态体系
- 差异处理结果比异常补充状态更重要

#### 移位单

头部特有字段：

- 来源区域摘要
- 目标区域摘要

列表补充筛选：

- 来源区域
- 目标区域

执行记录区内容：

- 移位执行记录
- 已移 / 未移进度

异常信息区内容：

- 执行失败说明
- 轻量异常信息
- 备注、处理人、时间

当前说明：

- 移位单执行主线相对直接
- 差异化重点不在状态扩展，而在执行说明和失败处理信息

## 11. 标准骨架示意

### 11.1 列表页标准骨架

```text
顶部：搜索 / 状态 / 仓库 / 货主 / 时间范围 / 单据补充筛选
中部：主表格
右上：新建 / 导入 / 批量动作
表格行：进入详情
底部：分页
```

#### 11.1.1 列表页各区职责

当前建议列表页各区职责固定为：

- 顶部筛选区：用于快速收敛结果集，不承载复杂录入
- 右上动作区：用于页面级新建、导入、批量动作
- 中部主表格：用于承接主信息浏览和进入详情
- 底部分页区：用于翻页和结果总量感知

当前不建议把：

- 执行类主动作
- 复杂异常处理
- 过多详情信息

直接堆在列表页主表格层。

#### 11.1.2 列表页主表格的统一节奏

当前建议 4 类主单列表页主表格统一遵守以下节奏：

1. 左侧先放主身份字段
2. 中部承接状态、业务摘要
3. 右侧保留少量辅助信息与进入详情入口

统一理解为：

- 左侧回答“这是什么单”
- 中部回答“当前到哪一步”
- 右侧回答“还能看什么 / 去哪里继续”

#### 11.1.3 列表页行级动作的当前建议

当前建议列表页行级动作尽量收敛：

- 主入口：进入详情
- 辅助动作：查看、轻量跳转

当前不建议一期在列表页行内堆叠：

- 大量执行按钮
- 多个危险动作
- 复杂状态切换入口

#### 11.1.4 列表页空状态的当前建议

当前建议列表页空状态只保留最小信息：

- 无数据提示
- 当前筛选结果为空的说明
- 清空筛选或新建入口

不建议在列表页空状态堆叠复杂帮助信息。

#### 11.1.5 列表页标准列结构模板

当前建议 4 类主单列表页标准列结构统一按以下层次组织：

##### 第一组：身份列

用于回答“这是什么单”，当前建议优先放在最左侧：

- 单号
- 单据特有识别字段（如客户单号 / 入库类型摘要 / 盘点范围摘要）

##### 第二组：归属列

用于回答“这张单归谁、在哪个仓”，当前建议放在身份列之后：

- 货主
- 仓库

##### 第三组：流程列

用于回答“当前走到哪一步”，当前建议放在表格中部：

- 主状态
- 异常补充状态（如有）

##### 第四组：进度列

用于回答“完成得怎么样”，当前建议按单据类型差异化补充：

- 入库单：收货进度 / 上架进度
- 出库单：拣货进度 / 复核进度 / 发货进度摘要
- 盘点单：已盘进度 / 差异处理结果
- 移位单：已移 / 未移进度

##### 第五组：责任与时间列

用于回答“谁负责、什么时候创建或处理”，当前建议放在表格右侧：

- 负责人 / 操作人
- 创建时间

##### 第六组：入口列

用于承接轻量动作和进入详情入口，当前建议放在最右侧：

- 查看详情
- 少量辅助动作

当前不建议将大量状态切换按钮和危险动作直接堆在入口列。

#### 11.1.6 列表页列展示优先级的当前建议

当前建议列表页列展示优先级按以下顺序理解：

1. 身份列
2. 主状态列
3. 进度列
4. 归属列
5. 时间列
6. 入口列

也就是说，当屏宽有限时，应优先保留：

- 单号
- 主状态
- 关键进度
- 详情入口

而不是优先保留过多补充字段。

### 11.2 详情页标准骨架

```text
头部：
  左侧：单号、货主、仓库、主状态、异常补充状态、负责人、创建时间、单据特有字段
  右侧：页面级 / 记录级按钮
  下方：状态 / 提示条（按需要显示）

正文：
  第一块：主信息
  第二块：执行记录
  第三块：异常信息
  第四块：日志
```

#### 11.2.1 详情页头部的统一布局模板

当前建议 4 类主单详情页头部统一采用三层：

1. 左侧主单关键信息区
2. 右侧顶部主按钮区
3. 下方状态 / 提示条

其中：

- 左侧关键信息区回答“这张单是什么、归谁、当前到哪”
- 右侧按钮区承接页面级和记录级动作
- 下方状态 / 提示条承接页内持续反馈

#### 11.2.2 详情页头部左侧信息区模板

当前建议详情页头部左侧统一按以下顺序组织：

1. 单号
2. 主状态
3. 异常补充状态（如有）
4. 货主
5. 仓库
6. 负责人 / 操作人
7. 创建时间
8. 单据特有字段

当前不建议把：

- 大量统计数字
- 过多说明文字
- 很长的备注

直接堆在头部左侧。

#### 11.2.3 详情页头部右侧按钮区模板

当前建议详情页头部右侧按钮区统一承接：

- 返回列表 / 返回上一层
- 页面刷新
- 记录级主动作
- 更多菜单中的次级或危险动作

当前不建议在头部右侧直接放：

- 当前动作级按钮
- 需要频繁点按的执行按钮

这些动作更适合留在执行页或执行记录区。

#### 11.2.4 详情页头部状态 / 提示条模板

当前建议详情页头部下方预留统一的状态 / 提示条位置，用来承接：

- 记录级状态提示
- 轻量异常提醒
- 下一步引导

这条提示条当前应作为头部和正文之间的过渡层，而不是额外的消息中心。

#### 11.2.5 详情页正文四区的统一节奏

当前建议详情页正文统一按以下阅读顺序展开：

1. 先看主信息
2. 再看执行记录
3. 再看异常信息
4. 最后看日志

这样可以让用户按“对象 -> 进度 -> 问题 -> 追溯”的顺序理解单据。

#### 11.2.6 详情页按钮区标准分层

当前建议 4 类主单详情页按钮区统一分为以下三层：

##### 第一层：主按钮

用于承接最重要的页面级 / 记录级动作，当前建议放在头部右侧主位。

当前建议主按钮只保留少量高频动作，例如：

- 返回列表 / 返回上一层
- 刷新
- 当前记录最核心的下一步动作

##### 第二层：次按钮

用于承接重要但不应抢主位的动作，当前建议与主按钮并列但视觉降级。

例如：

- 导出
- 打印
- 进入相关执行记录
- 轻量辅助处理

##### 第三层：更多菜单 / 危险动作

用于承接低频、危险、管理性动作，当前建议统一放入更多菜单或危险按钮位。

例如：

- 取消记录
- 特殊终止
- 覆盖性处理
- 低频管理动作

当前不建议把危险动作直接和主按钮并排争抢主位。

#### 11.2.7 详情页按钮区的当前排序建议

当前建议详情页按钮区统一按以下顺序理解：

1. 导航动作
2. 工具动作
3. 记录级主动作
4. 更多菜单 / 危险动作

也就是说：

- 返回类动作应更稳定、更靠前
- 刷新和工具类动作处于中间
- 当前单据最重要的记录级动作占主位
- 危险动作收口到更多菜单或危险按钮位

#### 11.2.8 详情页按钮区与执行页按钮区的边界

当前建议明确以下边界：

- 详情页按钮区承接页面级 / 记录级动作
- 执行页右侧按钮区承接当前动作级按钮

例如：

- “进入执行”可以放在详情页
- “确认本次 / 确认并下一条”不应放在详情页头部

当前不建议两个层级混用，否则页面职责会变得模糊。

#### 11.2.9 四类主单详情页按钮清单统一模板

当前建议 4 类主单详情页的按钮清单优先按以下三层模板组织：

##### A. 主按钮模板

当前建议主按钮只保留最关键、最高频、最能代表“下一步”的动作。

统一模板建议为：

- `返回列表` 或 `返回上一层`
- `刷新`
- `进入执行 / 继续处理`

其中：

- `返回列表 / 返回上一层`：导航主入口
- `刷新`：页面级工具动作
- `进入执行 / 继续处理`：当前单据最核心的记录级动作

若当前单据已不适合继续执行，则第三个主按钮可替换为：

- `查看执行`
- `查看结果`

##### B. 次按钮模板

当前建议次按钮承接重要但不应抢主位的动作。

统一模板建议从以下动作中按单据需要选用：

- `导出`
- `打印`
- `查看执行记录`
- `查看异常处理`
- `进入相关子页`

次按钮当前应满足两个特点：

- 重要
- 但不是单据的主下一步动作

##### C. 更多菜单 / 危险动作模板

当前建议更多菜单统一承接低频、危险、覆盖性或管理性动作。

统一模板建议从以下动作中按单据需要选用：

- `取消记录`
- `终止处理`
- `补录说明`
- `特殊调整`
- `管理性低频动作`

危险动作当前更建议：

- 收口到更多菜单
或
- 以独立危险按钮位承接

但当前不建议与主按钮并排争抢主位。

#### 11.2.11 使用这份按钮清单模板的当前原则

当前建议使用这份模板时遵守以下原则：

1. 每张单据的主按钮数量尽量收敛在 2 到 3 个
2. “下一步动作”优先进入主按钮，不要同时出现多个并列主动作
3. 低频动作优先下沉到次按钮或更多菜单
4. 危险动作不应默认进入主按钮链
5. 同类主单在不同状态下允许切换动作名称，但层级关系尽量不变

#### 11.2.12 执行记录区标准结构模板

当前建议 4 类主单详情页中的“执行记录”统一作为一个独立主区块，用来回答：

- 这张单做到了哪一步
- 实际发生了哪些执行动作
- 每个动作由谁、在什么时间完成

当前不建议把执行记录零散拆到主信息、日志、异常信息等区块中。

#### 11.2.13 执行记录区的统一结构建议

当前建议执行记录区统一按以下三层理解：

##### 第一层：执行阶段摘要

用于快速概览当前主流程已经走到哪一步。

当前建议统一展示：

- 当前执行阶段
- 已完成的关键动作摘要
- 剩余待处理动作摘要

##### 第二层：执行记录列表

用于按时间或阶段展示已产生的执行动作记录。

当前建议每条记录最小展示：

- 动作类型
- 动作状态
- 操作人
- 动作时间
- 关键结果摘要

##### 第三层：执行入口 / 反查入口

用于承接：

- 进入执行页
- 查看该类动作记录详情
- 反查关联执行对象

当前建议这层入口应收敛，不应替代顶部按钮成为主入口，但应作为辅助入口保留。

#### 11.2.14 执行记录区统一字段模板

当前建议 4 类主单的执行记录区统一优先保留以下字段：

- 动作类型
- 动作状态
- 操作人
- 动作时间
- 结果摘要
- 详情入口（按需要）

当前不建议一期在执行记录区直接铺开过多底层技术字段。

#### 11.2.15 四类主单执行记录区差异化模板

##### 入库单

执行阶段摘要重点：

- 收货进度
- 上架进度

执行记录列表重点：

- 收货记录
- 上架记录

结果摘要重点：

- 已收数量
- 已上架数量
- 剩余待上架数量

##### 出库单

执行阶段摘要重点：

- 拣货进度
- 复核进度
- 发货确认情况

执行记录列表重点：

- 拣货记录
- 复核记录
- 发货确认记录

结果摘要重点：

- 已拣数量
- 已复核数量
- 是否已发货

##### 盘点单

执行阶段摘要重点：

- 已盘进度
- 差异确认进度

执行记录列表重点：

- 盘点过程记录
- 差异确认记录

结果摘要重点：

- 已盘数量 / 行数
- 差异处理结果

##### 移位单

执行记录列表重点：

- 移位执行记录

结果摘要重点：

- 已移数量
- 未移数量
- 当前失败说明（如有）

#### 11.2.16 执行记录区与其他区块的边界

当前建议执行记录区与其他区块明确分工：

- 主信息区：回答“这张单是什么”
- 执行记录区：回答“这张单做到了哪一步”
- 异常信息区：回答“这张单卡在什么问题上”
- 日志区：回答“这张单发生过哪些追溯事件”

当前不建议：

- 用日志区替代执行记录区
- 用执行记录区承接全部异常说明
- 在主信息区重复铺开大段执行过程

#### 11.2.17 执行记录区的当前实现建议

当前更建议执行记录区采用：

- 顶部阶段摘要
- 下方执行记录表格 / 清单
- 末尾辅助入口

而不建议一期就做成复杂流程图或重工作台。

#### 11.2.18 异常信息区标准结构模板

当前建议 4 类主单详情页中的“异常信息区”统一作为一个独立主区块，用来回答：

- 当前是否存在异常补充状态
- 异常具体是什么
- 由谁处理
- 处理到什么程度

当前不建议把异常信息零散塞进主信息、执行记录或日志区中。

#### 11.2.19 异常信息区的统一结构建议

当前建议异常信息区统一按以下三层理解：

##### 第一层：异常状态摘要

用于快速回答当前单据是否处于异常补充状态中。

当前建议统一展示：

- 异常补充状态
- 是否仍待处理
- 是否已终止 / 已说明 / 已结束

##### 第二层：异常处理信息

用于承接当前异常最小处理信息。

当前建议最小展示：

- 原因
- 备注
- 处理人
- 处理时间

##### 第三层：异常相关入口

用于承接：

- 查看异常记录
- 进入待异常处理视图
- 查看相关证据 / 附件

当前建议这层入口保持辅助性质，不替代详情页主动作。

#### 11.2.20 异常信息区统一字段模板

当前建议 4 类主单异常信息区统一优先保留以下字段：

- 异常补充状态
- 原因
- 备注
- 处理人
- 处理时间

若当前单据一期尚未启用重异常补充状态，也可对该区块做弱化，但当前仍建议保留统一区块位置。

#### 11.2.21 四类主单异常信息区差异化模板

##### 入库单

- 终止备注
- 处理人

辅助入口重点：

##### 出库单

异常状态摘要重点：

- 是否已终止拣货
- 是否已终止复核
- 是否存在待发货前异常

异常处理信息重点：

- 终止原因
- 终止备注
- 处理人
- 终止时间

辅助入口重点：

- 查看异常处理说明
- 查看相关证据 / 附件

##### 盘点单

异常状态摘要重点：

- 一期不强调重异常补充状态
- 更强调差异是否仍待处理

异常处理信息重点：

- 差异说明
- 差异处理备注
- 处理人

辅助入口重点：

- 查看差异确认记录

##### 移位单

异常状态摘要重点：

异常处理信息重点：

- 失败原因
- 备注
- 处理人
- 处理时间

辅助入口重点：

- 查看异常说明
- 查看相关附件

#### 11.2.22 异常信息区与其他区块的边界

当前建议异常信息区与其他区块明确分工：

- 主信息区：回答“这张单是什么”
- 执行记录区：回答“这张单做到了哪一步”
- 异常信息区：回答“这张单为什么卡住或终止”
- 日志区：回答“这张单发生过哪些追溯事件”

当前不建议：

- 用日志区替代异常信息区
- 在执行记录区承接全部异常处理说明
- 在主信息区堆叠异常详情

#### 11.2.23 异常信息区的当前实现建议

当前更建议异常信息区采用：

- 顶部状态摘要
- 中部处理信息
- 末尾辅助入口

当前不建议一期就做成复杂异常工作台或重审批区。

#### 11.2.24 日志区标准结构模板

当前建议 4 类主单详情页中的“日志区”统一作为一个独立主区块，用来回答：

- 这张单发生过哪些关键事件
- 这些事件按什么时间顺序发生
- 由谁触发
- 当时的结果是什么

当前不建议让日志区替代执行记录区或异常信息区，但建议将它作为统一追溯入口保留。

#### 11.2.25 日志区的统一结构建议

当前建议日志区统一按以下两层理解：

##### 第一层：日志摘要

用于快速回答这张单近期是否有关键变化。

当前建议统一展示：

- 最近操作时间
- 最近操作人
- 最近关键事件

##### 第二层：日志时间线 / 日志列表

用于承接完整的追溯信息。

当前建议每条日志最小展示：

- 时间
- 操作人
- 事件类型
- 事件结果
- 简短说明

当前更建议用清晰列表或轻时间线表达，而不建议一期做复杂富文本审计中心。

#### 11.2.26 日志区统一字段模板

当前建议 4 类主单日志区统一优先保留以下字段：

- 时间
- 操作人
- 事件类型
- 事件结果
- 简短说明

如后续确有需要，再补：

- 关联对象
- 来源系统
- 操作入口

但一期当前不建议把这些扩成默认必显字段。

#### 11.2.27 四类主单日志区差异化模板

- 开始拣货
- 拣货完成
- 开始复核
- 复核完成
- 发货确认
- 发货前异常处理

##### 盘点单

日志重点事件建议包括：

- 创建盘点单
- 开始盘点
- 盘点完成
- 差异确认

- 执行失败说明
- 作废 / 取消

#### 11.2.28 日志区与执行记录区、异常信息区的边界

当前建议：

- 执行记录区回答“做了什么业务动作”
- 异常信息区回答“为什么卡住或终止”
- 日志区回答“时间线上发生过什么”

也就是说：

- 执行记录区偏业务阶段和动作
- 异常信息区偏问题与处理
- 日志区偏追溯与审计

当前不建议：

- 用日志区承接全部执行细节
- 用日志区承接全部异常说明
- 在执行记录区重复堆叠完整时间线

#### 11.2.29 日志区的当前实现建议

当前更建议日志区采用：

- 顶部最近事件摘要
- 下方简洁日志列表 / 轻时间线

当前不建议一期就做：

- 很重的富文本日志中心
- 复杂筛选日志面板
- 超深层级事件树

#### 11.5.7 视图与前端承载分工建议

为了避免后续把同一类页面一部分做在原生视图里、一部分做在自定义前端里而失去边界，当前建议再补一层统一分工：

##### A. 业务模块优先承载的内容

更适合放在各业务模块自身视图中的内容包括：

- 列表页
- 详情页
- search view
- tree/list view
- form view
- header buttons
- button_box / smart buttons
- one2many 执行记录区
- 异常信息区字段块
- 日志区的轻量只读列表

也就是说：

- `logistics_wms_inbound`
- `logistics_wms_outbound`
- `logistics_wms_inventory`

应优先各自承接其主单的原生视图、搜索视图和标准详情页结构。

##### B. `logistics_wms_web` 优先承载的内容

更适合放在 `logistics_wms_web` 中统一承接的内容包括：

- 4 类执行页容器
- 主从双栏执行页布局
- 页内提示条
- 自定义 tab 容器
- 更强的执行态交互
- toast 与确认弹窗的统一调用封装
- 需要跨 4 类主单统一复用的前端交互壳层

也就是说，`logistics_wms_web` 更像：

- 执行页壳层
- 统一交互层
- 统一反馈层

而不是去承接所有主单的普通列表页和普通详情页。

##### C. 当前推荐的统一边界

截至当前阶段，更推荐统一采用以下边界：

1. 主单列表页和详情页优先走 Odoo 原生视图体系
2. 执行页优先走 `logistics_wms_web` 自定义页面容器
3. 统一反馈能力由 `logistics_wms_web` 承接
4. 业务字段、业务按钮、业务 one2many 区块仍尽量留在各自业务模块中
5. 非必要不把普通详情页整体做成重前端自定义页

- 业务字段、主单表单、列表页、搜索页优先在业务模块
- 执行页容器和统一交互壳层优先在 `logistics_wms_web`

##### D. 主单普通页面的推荐文件命名草稿

当前建议普通页面优先采用“模型语义 + 视图类型”的文件命名：

- 入库单：
  - `logistics_wms_inbound_views.xml`
  - `logistics_wms_inbound_search_views.xml`
- 出库单：
  - `logistics_wms_outbound_views.xml`
  - `logistics_wms_outbound_search_views.xml`
- 盘点单：
  - `logistics_wms_inventory_count_views.xml`
  - `logistics_wms_inventory_count_search_views.xml`
- 移位单：
  - `logistics_wms_relocation_views.xml`
  - `logistics_wms_relocation_search_views.xml`

如果后续某一类页面明显变重，再拆成：

- `*_list_views.xml`
- `*_form_views.xml`
- `*_action_views.xml`

但一期不建议过早把 XML 文件切得太碎。

##### E. 执行页相关文件的推荐命名草稿

当前建议执行页相关文件采用“动作语义 + 页面壳层类型”的命名方式。

例如在 `logistics_wms_web` 中可优先采用类似结构：

- `wms_receive_execution_page`
- `wms_putaway_execution_page`
- `wms_pick_execution_page`
- `wms_check_execution_page`

但同一轮开发中应避免两套命名混用。

##### F. 页面区块到文件职责的当前推荐映射

当前建议先统一采用以下映射：

1. 列表页骨架：
   - 主承载：业务模块 `views/*.xml`
2. 详情页头部与主信息区：
   - 主承载：业务模块 `views/*.xml`
3. 执行记录区：
   - 主承载：业务模块 `views/*.xml`
   - 若需要更强交互，再由 `logistics_wms_web` 补辅助入口
4. 异常信息区：
   - 主承载：业务模块 `views/*.xml`
5. 日志区：
   - 轻量查看优先在业务模块 `views/*.xml`
   - 更重时间线样式可后续由 `logistics_wms_web` 增强
6. 执行页主从双栏壳层：
   - 主承载：`logistics_wms_web`
7. 提示条 / toast / confirm dialog：
   - 主承载：`logistics_wms_web`

##### G. 当前阶段关于命名与落位的统一收口

截至当前阶段，更推荐统一收敛为：

1. 业务模块负责主单的普通列表页、搜索页、详情页
2. `logistics_wms_web` 负责执行页与统一交互壳层
3. 文件命名优先按“业务对象 + 页面类型”或“动作语义 + 执行页类型”组织
4. 一期先避免把视图文件切得过碎
5. 一期先避免在普通详情页和执行页之间重复定义同一套按钮和字段区块

#### 11.5.10 菜单 / action / client action 命名映射草稿

以下草稿用于把前述页面骨架、模块边界与文件命名继续下沉到 Odoo 入口对象层，减少后续菜单、`ir.actions.act_window`、client action 命名发散的问题。

##### A. 当前统一命名原则

当前建议入口对象统一采用以下原则：

1. 菜单优先用中文业务名，便于后台使用者理解
2. `xml id` 优先用英文、短语义、对象导向命名
3. 普通列表/详情入口统一优先使用 `act_window`
4. 执行页统一优先使用 client action 或指向自定义执行容器的 action
5. 同一类对象的菜单、action、view、client action 命名应保持同前缀

##### B. 菜单命名草稿

当前建议菜单在用户可见层统一按以下方向命名：

- 入库单：`入库单`
- 出库单：`出库单`
- 盘点单：`盘点单`
- 移位单：`移位单`
- 待收货：`待收货`
- 待上架：`待上架`
- 待拣货：`待拣货`
- 待复核：`待复核`
- 待异常处理：`待异常处理`

如果后续需要加二级菜单，建议先按：

- 主单中心
- 待处理中心
- 异常处理中心

这三个层次去组织，不建议一开始把菜单切得过深。

##### C. `ir.actions.act_window` 命名草稿

当前建议普通页面入口统一采用“对象 + 页面用途”的命名方式。

推荐方向例如：

- `action_logistics_wms_inbound`
- `action_logistics_wms_outbound`
- `action_logistics_wms_inventory_count`
- `action_logistics_wms_relocation`

待处理视图类入口可采用：

- `action_logistics_wms_inbound_waiting_receipt`
- `action_logistics_wms_inbound_waiting_putaway`
- `action_logistics_wms_outbound_waiting_pick`
- `action_logistics_wms_outbound_waiting_check`
- `action_logistics_wms_exception_pending`

这里的关键统一点是：

- 普通主单入口统一保持对象中心命名
- 待处理入口统一显式写出 `waiting_*`
- 异常入口统一显式写出 `exception_*` 或 `*_pending`

##### D. client action 命名草稿

当前建议执行页相关入口统一按“动作语义 + execution”的命名方式组织。

推荐方向例如：

- `action_logistics_wms_receive_execution`
- `action_logistics_wms_putaway_execution`
- `action_logistics_wms_pick_execution`
- `action_logistics_wms_check_execution`

对应的 client action tag 或前端注册键也建议统一保持同方向，例如：

- `logistics_wms.receive_execution`
- `logistics_wms.putaway_execution`
- `logistics_wms.pick_execution`
- `logistics_wms.check_execution`

如果后续团队更希望与模块名完全对齐，也可采用：

- `logistics_wms_web.receive_execution`
- `logistics_wms_web.putaway_execution`
- `logistics_wms_web.pick_execution`
- `logistics_wms_web.check_execution`

但应在正式实现前统一一套，不建议混用。

##### E. 菜单、action、client action 的当前推荐对应关系

当前建议先统一采用以下对应方式：

1. 主单菜单
   - 指向主单 `act_window`
2. 待处理菜单
   - 指向待处理 `act_window`
3. 详情页顶部执行按钮
   - 跳转到对应执行页 client action
4. 待处理列表中的“开始处理”
   - 也跳转到同一执行页 client action
5. 普通列表页本身不直接承载执行页全部逻辑

也就是说：

- 菜单主要进列表
- 列表主要进详情
- 执行动作主要进 client action

##### F. 推荐 XML ID 组织草稿

当前建议相关 XML ID 先统一按以下方向组织：

```text
menu_logistics_wms_*
action_logistics_wms_*
view_logistics_wms_*
client_action_logistics_wms_*
```

例如：

- `menu_logistics_wms_inbound`
- `menu_logistics_wms_outbound_waiting_pick`
- `action_logistics_wms_inbound`
- `action_logistics_wms_pick_execution`
- `view_logistics_wms_inbound_tree`
- `view_logistics_wms_inbound_form`
- `client_action_logistics_wms_pick_execution`

这样做的好处是：

- 模块间更容易检索
- 评审时更容易看出对象归属
- 与现有物流模块命名节奏更容易保持一致

##### G. 当前阶段关于入口命名映射的统一收口

截至当前阶段，更推荐统一收敛为：

1. 菜单名以中文业务名为主，xml id 以英文对象名为主
2. 主单页面入口优先用 `act_window`
3. 执行页入口优先用 client action
4. 命名优先围绕：
   - 业务对象
   - 页面用途
   - 动作语义
5. 菜单、action、view、client action 应尽量共享统一前缀，避免多套命名体系并行

#### 11.5.12 菜单树层级与 action 绑定关系草稿

以下草稿用于把前述命名规则进一步落到后台菜单组织方式。当前目标不是一步做出最终菜单树，而是先把一期可落地的层级、入口和绑定关系收紧成统一方向。

##### A. 当前推荐的一级菜单口径

当前建议仓管模块在系统中先以一个统一一级入口承接，例如：

- `仓管模块`

如果后续需要与物流模块并列展示，也建议保持同级兄弟关系，而不要把仓管散落进多个无关一级菜单。

##### B. 当前推荐的二级菜单层级

一期更推荐先统一成以下三个二级层级：

- `主单中心`
- `待处理中心`
- `异常处理中心`

这三个层级足够承接当前已确认的 4 类主单与执行入口，不建议一期继续拆得更深。

##### C. 当前推荐的三级菜单草稿

在上述二级层级下，当前更推荐先组织为：

```text
仓管模块
├─ 主单中心
│  ├─ 入库单
│  ├─ 出库单
│  ├─ 盘点单
│  └─ 移位单
├─ 待处理中心
│  ├─ 待收货
│  ├─ 待上架
│  ├─ 待拣货
│  └─ 待复核
└─ 异常处理中心
   └─ 待异常处理
```

这个树形结构与我们前面已确认的：

- 主单中心
- 执行入口从待处理视图或详情页发起
- 异常补充状态单独成口径

是对齐的。

##### D. 当前推荐的菜单到 action 绑定关系

当前建议先统一采用以下绑定：

| 菜单 | 绑定 action | 说明 |
|---|---|---|
| 入库单 | `action_logistics_wms_inbound` | 入库单普通列表/详情入口 |
| 出库单 | `action_logistics_wms_outbound` | 出库单普通列表/详情入口 |
| 盘点单 | `action_logistics_wms_inventory_count` | 盘点单普通列表/详情入口 |
| 移位单 | `action_logistics_wms_relocation` | 移位单普通列表/详情入口 |
| 待收货 | `action_logistics_wms_inbound_waiting_receipt` | 待收货列表入口 |
| 待上架 | `action_logistics_wms_inbound_waiting_putaway` | 待上架列表入口 |
| 待拣货 | `action_logistics_wms_outbound_waiting_pick` | 待拣货列表入口 |
| 待复核 | `action_logistics_wms_outbound_waiting_check` | 待复核列表入口 |
| 待异常处理 | `action_logistics_wms_exception_pending` | 异常处理列表入口 |

##### E. action 到详情页与执行页的后续衔接关系

当前建议再明确一层统一衔接：

1. 主单类 `act_window`
   - 进入普通列表
   - 行点击进入详情页
2. 待处理类 `act_window`
   - 进入待处理列表
   - 行点击优先进入对应主单详情
   - 行级或顶部动作再进入执行页 client action
3. 执行页 client action
   - 不直接挂在一级或二级主菜单下
   - 主要通过详情页按钮与待处理列表动作进入

这条边界很重要，因为它能避免：

- client action 直接变成一堆孤立菜单
- 主单流程和执行流程在入口上混成一团

##### F. 当前不建议的一期菜单绑定方式

当前不建议一期采用以下方式：

- 直接把 4 类执行页都挂成独立主菜单
- 普通主单菜单直接跳 client action
- 入库、出库、盘点、移位分别拆成不同一级菜单
- 把异常处理入口散落到每个对象的一级菜单下

这些做法都会让后台结构过散，也不利于与物流模块保持同系统的统一节奏。

##### G. 当前阶段关于菜单树与 action 绑定的统一收口

截至当前阶段，更推荐统一收敛为：

1. 一级入口统一为仓管模块
2. 二级统一为主单中心、待处理中心、异常处理中心
3. 三级菜单承接 4 类主单与 4 类待处理入口
4. 菜单优先绑定 `act_window`
5. 执行页优先通过详情页与待处理列表动作进入，不直接成为主菜单主体

#### 11.5.13 菜单权限分层与角色可见性草稿

以下草稿用于把前述菜单树继续下沉到权限与可见性层。当前阶段先明确“角色看到什么、能进入什么”，不急着把每个按钮权限一次性做完。

##### A. 当前推荐的权限分层口径

当前建议先把权限分成 3 层来理解：

1. 菜单可见权限
2. 页面进入权限
3. 动作执行权限

也就是说：

- 能看到菜单
- 不等于能查看全部页面
- 能进入页面
- 也不等于能执行所有按钮动作

这三层应尽量分开设计，避免一期把“看得见”和“做得了”混在一起。

##### B. 当前推荐的基础角色草稿

当前阶段更推荐先以以下几类角色作为菜单可见性的基础口径：

- 仓管操作员
- 仓管主管 / 组长
- 异常处理角色
- 仓管管理员
- 只读查询角色

这里先强调菜单与页面口径，不在本节展开更细的人岗矩阵。

##### C. 一级与二级菜单的当前可见性建议

当前建议：

- `仓管模块`
  - 对仓管相关角色统一可见
- `主单中心`
  - 对操作员、主管、管理员、只读角色可见
- `待处理中心`
  - 对操作员、主管、管理员可见
- `异常处理中心`
  - 对主管、异常处理角色、管理员可见

这意味着一期不建议让普通仓管操作员默认看到完整异常处理中心。

##### D. 三级菜单的当前可见性建议

当前建议先按下列方向组织：

| 菜单 | 推荐可见角色 |
|---|---|
| 入库单 | 操作员 / 主管 / 管理员 / 只读 |
| 出库单 | 操作员 / 主管 / 管理员 / 只读 |
| 盘点单 | 主管 / 管理员 / 只读 |
| 移位单 | 操作员 / 主管 / 管理员 / 只读 |
| 待收货 | 操作员 / 主管 / 管理员 |
| 待上架 | 操作员 / 主管 / 管理员 |
| 待拣货 | 操作员 / 主管 / 管理员 |
| 待复核 | 操作员 / 主管 / 管理员 |
| 待异常处理 | 主管 / 异常处理角色 / 管理员 |

这里的盘点单我更建议默认偏向主管与管理口径，而不是一开始就给所有操作员开放完整入口。

##### E. 菜单可见性与 action 进入权限的当前边界

当前建议统一按以下边界处理：

1. 菜单可见只决定“用户是否能看到入口”
2. `act_window` 仍应受模型与记录规则保护
3. client action 仍应再校验是否有对应执行权限
4. 详情页顶部执行按钮应按动作权限继续控制显隐

也就是说：

- 菜单隐藏是第一层
- action 权限和按钮权限仍是第二层、第三层

##### F. 当前不建议的一期做法

当前不建议一期采用以下方式：

- 只靠菜单显隐来承接全部权限控制
- 所有仓管角色看到完全相同的菜单树
- 把异常处理入口完全开放给普通操作员
- 把执行页入口直接作为“看得到就一定能执行”

这些做法都会让权限边界过于粗糙，后面补动作权限时会很乱。

##### G. 当前阶段关于菜单权限与可见性的统一收口

截至当前阶段，更推荐统一收敛为：

1. 菜单权限、页面权限、动作权限分三层设计
2. 仓管模块一级入口对仓管相关角色可见
3. 主单中心偏通用可见，待处理中心偏执行角色可见
4. 异常处理中心优先开放给主管、异常处理角色、管理员
5. 菜单可见性不是最终权限边界，仍需配合 action、记录规则和按钮权限

##### E. 当前推荐的权限理解方式

为了避免后续矩阵被误读，当前建议统一这样理解：

1. “是”表示一期建议默认开放
2. “否”表示一期建议默认不开放
3. 主管与管理员通常具备更高覆盖面
4. 异常处理角色不等于日常执行角色
5. 只读角色可以进入查看型页面，但不应看到执行按钮

##### F. 当前不建议的一期做法

当前不建议一期采用以下方式：

- 用一套“仓管通用角色”覆盖所有菜单、页面、动作
- 只按菜单可见与否定义角色，不再细分执行页和按钮
- 给只读角色保留会触发执行的 client action 入口
- 让异常处理角色默认承担全部日常执行动作

这些做法会让角色边界很快失真，也不利于后面补记录规则与按钮显隐。

##### G. 当前阶段关于角色矩阵的统一收口

截至当前阶段，更推荐统一收敛为：

1. 先用 5 类角色建立一期基线矩阵
2. 菜单、页面、动作三层矩阵分别维护，不混成一张粗表
3. 操作员负责高频执行，主管负责管理与关键动作，异常处理角色负责异常闭环
4. 管理员保留全局覆盖能力，只读角色保留查看能力
5. 后续若新增角色，应优先在这套矩阵上增量扩展，而不是重起一套权限口径
