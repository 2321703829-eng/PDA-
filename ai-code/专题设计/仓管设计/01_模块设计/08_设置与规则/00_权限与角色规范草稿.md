## 1. 文档定位

本文件用于从：

- `四类主单统一页面结构规范草稿 v0.1`

中与权限、菜单、角色矩阵相关的内容进一步抽出，形成仓管模块自己的独立权限专题稿。

当前重点不是一步做出全部记录规则，而是先固定：

- 一期的基础角色
- 菜单、页面、动作三层权限口径
- 各角色在执行页与异常处理入口上的边界

## 2. 范围与边界

### 2.1 当前纳入范围

- 仓管一期基础角色基线
- 菜单可见性矩阵
- 页面进入权限矩阵
- 动作执行权限矩阵
- 执行页入口与详情页按钮显隐的基础理解

### 2.2 当前不纳入范围

- 全量 Odoo `res.groups` 最终技术拆分
- 全量 record rule 细节
- 字段级只读 / 可编辑细粒度规则
- 审批流专用权限体系
- 多租户场景下的数据库级隔离策略细节

## 3. 权限分层总口径

当前更推荐把仓管权限统一拆成三层：

1. 菜单可见权限
2. 页面进入权限
3. 动作执行权限

也就是说：

- 能看到菜单
- 不等于能进入页面
- 能进入页面
- 也不等于能执行按钮动作

一句话收口：

`仓管权限不应只靠菜单显隐，应按菜单、页面、动作三层分别设计。`

## 4. 基础角色定义

当前一期更推荐先基于以下 5 类角色建立权限基线：

- 仓管操作员
- 仓管主管 / 组长
- 异常处理角色
- 仓管管理员
- 只读查询角色

### 4.1 仓管操作员

定位：

- 高频执行角色
- 重点参与收货、上架、拣货、复核等日常执行动作

### 4.2 仓管主管 / 组长

定位：

- 管理与关键动作角色
- 重点参与盘点、关键取消、关键终止、异常判断与工作安排

### 4.3 异常处理角色

定位：

- 异常闭环角色
- 重点参与待异常处理中心、异常说明、异常跟踪与补充处理

### 4.4 仓管管理员

定位：

- 全局维护角色
- 重点参与配置、全局维护与权限兜底

### 4.5 只读查询角色

定位：

- 查看与追溯角色
- 可看列表、详情、日志、进度、证据，但不应触发执行动作

## 5. 菜单可见性矩阵

当前推荐的一期菜单可见性矩阵如下：

| 菜单 | 操作员 | 主管/组长 | 异常处理 | 管理员 | 只读 |
|---|---|---|---|---|---|
| 仓管模块 | 是 | 是 | 是 | 是 | 是 |
| 主单中心 | 是 | 是 | 是 | 是 | 是 |
| 待处理中心 | 是 | 是 | 否 | 是 | 否 |
| 异常处理中心 | 否 | 是 | 是 | 是 | 否 |
| 设置与规则 | 否 | 否 | 否 | 是 | 否 |

当前更推荐理解为：

- 主单中心偏通用入口
- 待处理中心偏执行角色入口
- 异常处理中心偏主管 / 异常 / 管理口径
- 设置与规则偏管理口径

## 6. 页面进入权限矩阵

当前页面进入权限建议再细分为：

- 主单列表页
- 主单详情页
- 执行页
- 异常处理页

当前推荐矩阵如下：

| 页面类型 | 操作员 | 主管/组长 | 异常处理 | 管理员 | 只读 |
|---|---|---|---|---|---|
| 主单列表页 | 是 | 是 | 是 | 是 | 是 |
| 主单详情页 | 是 | 是 | 是 | 是 | 是 |
| 执行页 | 是 | 是 | 否 | 是 | 否 |
| 异常处理页 | 否 | 是 | 是 | 是 | 否 |

这里建议特别记住两条：

1. 只读角色可以进查看型页面，但不应进入执行页
2. 异常处理角色不等于默认承担全部日常执行角色

## 7. 动作执行权限矩阵

当前动作权限建议先聚焦一批高频关键动作：

| 动作 | 操作员 | 主管/组长 | 异常处理 | 管理员 | 只读 |
|---|---|---|---|---|---|
| 新建入库单 | 否 | 是 | 否 | 是 | 否 |
| 新建出库单 | 否 | 是 | 否 | 是 | 否 |
| 开始收货 | 是 | 是 | 否 | 是 | 否 |
| 开始上架 | 是 | 是 | 否 | 是 | 否 |
| 开始拣货 | 是 | 是 | 否 | 是 | 否 |
| 开始复核 | 是 | 是 | 否 | 是 | 否 |
| 普通取消单据 | 否 | 是 | 否 | 是 | 否 |
| 执行终止 / terminated | 否 | 是 | 是 | 是 | 否 |
| 进入异常处理 | 否 | 是 | 是 | 是 | 否 |
| 查看日志 / 证据 | 是 | 是 | 是 | 是 | 是 |

当前更推荐理解为：

- 操作员负责日常高频执行
- 主管负责关键动作与单据管理
- 异常处理角色负责异常闭环，不默认覆盖日常执行
- 管理员保留全局兜底能力

## 8. 当前推荐的权限理解方式

为了避免后续矩阵被误读，当前建议统一这样理解：

1. “是”表示一期建议默认开放
2. “否”表示一期建议默认关闭
3. 菜单可见不是最终权限边界
4. 页面进入权限和按钮执行权限必须继续独立控制
5. 只读角色可以看，但不应触发执行类 client action

一句话收口：

`权限矩阵应先定义“默认开放什么”，再由记录规则和按钮显隐继续细化，而不是把所有控制都压成一张粗表。`

## 9. 当前不建议的一期做法

当前不建议一期采用以下方式：

- 只靠菜单显隐来承接全部权限控制
- 所有仓管角色看到完全相同的菜单树
- 把异常处理入口完全开放给普通操作员
- 给只读角色保留会触发执行的 client action 入口
- 用一套“仓管通用角色”覆盖所有菜单、页面、动作

这些做法都会让角色边界过于粗糙，后面补记录规则与按钮显隐时会很乱。

## 10. 与 res.groups 的实际落地映射草稿

当前更推荐先把前面已经确认的 5 类业务角色，映射成一版轻量但可落地的 `res.groups` 草稿。  
目标不是现在就锁死全部技术细节，而是先让“业务角色”和“Odoo 组对象”之间有一层清楚的对应关系。

### 10.1 当前推荐的映射原则

当前建议先遵守以下原则：

1. 业务角色不直接等于最终所有技术组，但应有一组清晰主映射
2. 一期优先按“角色职责”建组，不按单个页面零碎建组
3. 菜单可见、页面进入、动作执行仍需在组基础上继续细化
4. 管理员组应是兜底组，但不要替代其他业务组的定义

一句话收口：

`先有稳定业务组，再在其上叠菜单、页面、按钮和记录规则，不反过来从零碎技术点拼角色。`

### 10.2 当前推荐的组命名草稿

当前更推荐统一使用 `logistics_wms.group_*` 这一组 XML ID 方向。

推荐草稿如下：

- `logistics_wms.group_wms_operator`
- `logistics_wms.group_wms_supervisor`
- `logistics_wms.group_wms_exception_handler`
- `logistics_wms.group_wms_admin`
- `logistics_wms.group_wms_readonly`

对应业务理解：

- `group_wms_operator`：仓管操作员
- `group_wms_supervisor`：仓管主管 / 组长
- `group_wms_exception_handler`：异常处理角色
- `group_wms_admin`：仓管管理员
- `group_wms_readonly`：只读查询角色

### 10.3 当前推荐的角色到 group 对应关系

| 业务角色 | 推荐 group XML ID | 当前理解 |
|---|---|---|
| 仓管操作员 | `logistics_wms.group_wms_operator` | 高频执行组 |
| 仓管主管 / 组长 | `logistics_wms.group_wms_supervisor` | 管理与关键动作组 |
| 异常处理角色 | `logistics_wms.group_wms_exception_handler` | 异常闭环组 |
| 仓管管理员 | `logistics_wms.group_wms_admin` | 全局维护与兜底组 |
| 只读查询角色 | `logistics_wms.group_wms_readonly` | 查看与追溯组 |

这里建议后续继续保持：

- 业务讨论里先用“角色名”说清职责
- 技术实现里再稳定映射到这些 group XML ID

### 10.4 当前推荐的组职责边界

当前更推荐这样理解这 5 个组：

**1. `group_wms_operator`**

- 重点开放执行页入口
- 重点开放收货、上架、拣货、复核等高频动作
- 不默认开放异常处理中心与关键终止动作

**2. `group_wms_supervisor`**

- 在操作员基础上增加关键管理与关键动作能力
- 可开放普通取消、关键终止、盘点与重要页面入口

**3. `group_wms_exception_handler`**

- 重点开放异常处理中心
- 重点开放异常查看、异常处理、terminated 补充处理
- 不默认承担全部日常执行动作

**4. `group_wms_admin`**

- 作为全局兜底与维护组
- 可看到设置与规则
- 可保留更广的菜单、页面和动作权限

**5. `group_wms_readonly`**

- 重点开放查看型列表页、详情页、日志、证据
- 不开放执行页与执行类按钮

### 10.5 当前不建议的一期组映射做法

当前不建议：

- 直接拿一个“仓管通用管理员组”覆盖所有角色
- 为每个页面单独造一个组，导致组爆炸
- 用 group 直接混合业务职责和技术临时需求
- 只定义菜单组，不定义执行页和按钮对应组

这些做法会让组结构很快失控，也不利于后面补记录规则和按钮显隐。

### 10.6 当前推荐的一句话 group 映射口径

`一期先把 5 类业务角色映射成 5 个稳定的 logistics_wms group，再在其上继续叠菜单、页面、按钮和记录规则。`

## 11. 记录规则与货主 / 仓库范围控制口径

当前更推荐把菜单、页面、动作权限之外的数据可见边界，统一再收一层到：

- 货主范围
- 仓库范围

也就是说：

- 菜单、页面、动作解决“你能进哪里、点什么”
- 记录规则解决“你在页面里最终能看到哪些数据”

### 11.1 当前推荐的记录规则总口径

当前建议至少按以下两个维度控制仓管数据范围：

1. `owner_id`
2. `warehouse_id`

这两个维度建议作为一期记录规则的主口径，因为它们最能对应：

- 多货主场景下的数据隔离
- 仓内组织与人员职责范围

一句话收口：

`一期记录规则优先按货主和仓库两层做数据收口，不急着一开始就做更细碎的货位级规则。`

### 11.2 不同角色的数据范围建议

当前更推荐这样理解各角色的数据范围：

**1. 仓管操作员**

- 默认只看自己有权限的仓库范围
- 默认只看自己有权限的货主范围
- 不应默认看到全仓、全货主数据

**2. 仓管主管 / 组长**

- 可看自己负责仓库范围内的更多数据
- 可在同仓范围内跨操作员查看
- 是否跨货主要看岗位口径，但一期不建议天然全开

**3. 异常处理角色**

- 重点看异常相关对象
- 但仍建议限制在授权货主 / 仓库范围内
- 不建议只因为“负责异常”就默认全仓全货主可见

**4. 仓管管理员**

- 可作为全局兜底角色
- 可保留更广范围的数据可见性

**5. 只读查询角色**

- 仍应受货主 / 仓库范围约束
- 只是“只能看不能做”，不等于“可以看全部”

### 11.3 当前推荐的规则落点理解

当前更推荐后续记录规则优先依附在主业务对象和主查询对象上，例如：

- 入库单
- 出库单
- 盘点单
- 移位单
- 执行记录
- 相关日志 / 异常信息

当前不建议一期先从：

- 很细的字段级限制
- 很细的货位级限制
- 很复杂的动态拼装规则

开始，否则规则会很快失控。

### 11.4 当前推荐的货主 / 仓库范围控制方式

当前更推荐后续按以下方向继续细化：

- 用户 -> 角色组
- 用户 -> 可访问货主范围
- 用户 -> 可访问仓库范围

也就是说：

- group 决定大类权限
- 货主 / 仓库范围决定数据边界

这里建议保持：

- group 不直接承担全部数据范围定义
- record rule 不直接替代动作权限

### 11.5 当前不建议的一期做法

当前不建议：

- 菜单可见了就默认能看到全部单据
- 只按角色分，不再叠货主 / 仓库范围
- 给只读角色放开全部数据
- 异常处理角色直接天然拥有全局数据访问权

这些做法都会让后面货主隔离与仓库职责边界变得很难收回。

### 11.6 当前推荐的一句话记录规则口径

`一期权限建议分成四层理解：菜单、页面、动作、记录规则；记录规则优先按货主与仓库做数据收口。`

## 12. 与设置页、规则页、基础档案页的权限细分

当前更推荐把“设置与规则”这一类后台页面，再从主单与执行页权限之外单独拉出一层。  
原因很直接：

- 这类页面更接近配置与治理，不属于高频执行
- 一旦权限开得太宽，后续规则口径很容易失控
- 只靠“管理员能看，其他都不能看”又会过粗

所以当前更推荐继续按“查看 / 维护 / 配置生效”三个强度来理解。

### 12.1 基础档案页的当前推荐口径

这里主要指：

- 货主档案
- 仓库档案
- 货位档案
- 商品扩展档案
- 条码映射档案

当前更推荐：

- 操作员：可查看与自己执行相关的基础档案，但不默认开放维护
- 主管 / 组长：可查看，大多数情况下可维护部分业务相关档案
- 异常处理角色：以查看为主，不默认开放全量维护
- 管理员：可查看、可维护、可兜底修正
- 只读角色：只查看

一句话收口：

`基础档案页默认偏查看型，维护权不应自然下放给全部执行角色。`

### 12.2 设置页的当前推荐口径

这里主要指：

- 仓管系统参数
- 扫码 / 打印 / 页面行为类设置
- 执行页交互类开关

当前更推荐：

- 操作员：不开放
- 主管 / 组长：默认不开放，必要时可开放极少量与现场执行直接相关的参数查看
- 异常处理角色：默认不开放
- 管理员：开放
- 只读角色：不开放

这里建议保持：

- 设置页偏管理口径
- 不要把日常执行岗位变成配置岗位

### 12.3 规则页的当前推荐口径

这里主要指：

- 状态推进规则
- 异常处理规则
- 分配 / 执行策略规则
- 条码或扫描匹配规则

当前更推荐：

- 操作员：不开放
- 主管 / 组长：默认查看，谨慎开放少量业务规则维护
- 异常处理角色：仅开放与异常闭环直接相关的规则查看或局部维护
- 管理员：开放
- 只读角色：不开放

这里建议特别注意：

- 规则页比基础档案更敏感
- 因为它会直接改变系统行为

所以一期不建议把规则维护广泛下放。

### 12.4 当前推荐的页面类型权限理解

当前更推荐把三类页面这样理解：

**1. 基础档案页**

- 偏“查看 + 局部维护”

**2. 设置页**

- 偏“管理配置”

**3. 规则页**

- 偏“系统行为治理”

这三类页面虽然都不属于主单执行流，但敏感度不同：

- 基础档案页最低
- 设置页更高
- 规则页最高

### 12.5 当前不建议的一期做法

当前不建议：

- 把基础档案、设置页、规则页统一视为同一权限层
- 让操作员默认拥有规则维护能力
- 让主管默认拥有所有设置页维护能力
- 只靠“管理员 / 非管理员”二分法处理所有后台配置页

这些做法都会让后台治理边界很快失真。

### 12.6 当前推荐的一句话细分口径

`基础档案页偏查看与局部维护，设置页偏管理配置，规则页偏系统治理；三者不应视为同一权限层。`

## 14. 更细的页面区块级按钮显隐矩阵

当前第 `13` 章已经把权限从“跨单据动作”推进到了“四类主单动作”。
如果后面要真正落到详情页和执行页实现，还需要继续往下一层拆：

- 顶部按钮区
- 执行记录区
- 异常信息区
- 日志区

也就是同样一个动作，不只要知道“谁能做”，还要知道“它应该出现在哪个区块，以及哪些角色看得到、点得动”。

一句话收口：

`页面区块级按钮显隐矩阵负责定义按钮在页面哪个区块出现，以及各角色在该区块中的默认显隐边界。`

### 14.1 当前推荐的区块分层

当前更推荐把详情页和执行页里常见按钮先按这 4 类区块理解：

1. `顶部主按钮区`
2. `执行记录区按钮`
3. `异常信息区按钮`
4. `日志 / 证据区按钮`

- 顶部主按钮区偏“页面级 / 单据级关键动作”
- 执行记录区按钮偏“过程查看与继续执行”
- 异常信息区按钮偏“异常闭环与补充处理”
- 日志 / 证据区按钮偏“查看与补充留痕”

这里主要承接：

- 高风险和关键状态推进动作优先收在顶部区
- 操作员可在顶部区看到并触发高频执行入口

`顶部区偏关键动作，执行记录区偏查看与继续执行，异常信息区偏异常闭环，日志 / 证据区偏追溯与留痕。`

## 15. 与状态机专题之间的逐按钮联动校对表

当前前面已经拆出了：

- 入库单状态机草稿
- 出库单状态机草稿
- 盘点单状态机草稿
- 移位单状态机草稿

所以权限专题再往下一步时，不能只回答“谁能点按钮”，还要继续回答：

- 这个按钮在哪些状态下本来就不该出现
- 这个按钮在当前状态下是“看得到但禁用”，还是“直接不显示”
- 这个按钮是权限专题控制，还是状态机专题控制

一句话收口：

`权限专题决定谁有资格点，状态机专题决定当前状态下按钮是否应出现或应可用。`

### 15.1 联动校对总原则

当前更推荐按下面三层顺序校对按钮：

1. 先看角色是否允许
2. 再看当前主状态 / 异常补充状态是否允许
3. 最后看当前记录是否在用户可操作范围内

也就是说，一个按钮最终可执行，至少要同时满足：

- 角色矩阵开放
- 状态机允许
- 记录规则允许

### 15.2 入库单关键按钮联动校对

| 按钮 | 角色基线 | 主要状态约束 | 当前推荐校对口径 |
|---|---|---|---|
| 提交 / 生效 | 主管、管理员 | `draft` | 非 `draft` 不显示或禁用 |
| 普通取消 | 主管、管理员 | `draft`、`waiting_receipt` | 超出可取消状态不应继续显示为普通取消 |
| 开始收货 | 操作员、主管、管理员 | `waiting_receipt`、`receipting` | 已 `received` 后不再作为主入口 |
| 开始上架 | 操作员、主管、管理员 | `received`、`putawaying` | 未收货完成前不应出现 |
| 终止 / terminated | 主管、异常处理、管理员 | 重点在 `receipting` | 已 `done` / `cancel` 不应出现 |

### 15.3 出库单关键按钮联动校对

| 按钮 | 角色基线 | 主要状态约束 | 当前推荐校对口径 |
|---|---|---|---|
| 提交 / 生效 | 主管、管理员 | `draft` | 非 `draft` 不显示或禁用 |
| 普通取消 | 主管、管理员 | `draft`、`waiting_pick` | 开始拣货后不再作为普通取消 |
| 开始拣货 | 操作员、主管、管理员 | `waiting_pick`、`picking` | 已 `picked` 后不应继续作为主入口 |
| 开始复核 | 操作员、主管、管理员 | `picked`、`checking` | 未拣货完成前不应出现 |
| 开始发货 | 主管、管理员 | `waiting_ship` | 只在待发货阶段出现 |
| 终止 / terminated | 主管、异常处理、管理员 | 重点在 `picking`、`checking` | 已 `done` / `cancel` 不应出现 |

### 15.4 盘点单关键按钮联动校对

| 按钮 | 角色基线 | 主要状态约束 | 当前推荐校对口径 |
|---|---|---|---|
| 新建盘点单 | 主管、管理员 | 列表页入口 | 详情页不作为状态联动按钮 |
| 开始盘点 | 操作员、主管、管理员 | `draft`、`counting` | 已进入 `reviewing` 后不应继续出现 |
| 提交确认 / 进入 reviewing | 主管、管理员 | `counting` | 未完成盘点过程前不应启用 |
| 发起调整 / 确认差异 | 主管、管理员 | `reviewing` | 仅在差异处理阶段开放 |
| 取消 | 主管、管理员 | `draft`、必要时 `counting` | 超出边界不应保留普通取消口径 |

### 15.5 移位单关键按钮联动校对

| 按钮 | 角色基线 | 主要状态约束 | 当前推荐校对口径 |
|---|---|---|---|
| 提交 / 生效 | 主管、管理员 | `draft` | 非 `draft` 不显示或禁用 |
| 开始执行 | 操作员、主管、管理员 | `waiting_execute`、`executing` | 已 `done` 后不应继续出现 |
| 继续执行 | 操作员、主管、管理员 | `executing` | 只在执行中保留 |
| 取消 | 主管、管理员 | `draft`、`waiting_execute` | 执行中及完成后不应保留普通取消口径 |
| 查看异常信息 | 主管、异常处理、管理员、只读 | 有异常信息时 | 以查看型入口为主，不承担状态推进 |

### 15.6 当前推荐的一句话逐按钮联动口径

`权限矩阵先决定“谁有资格”，状态机再决定“当前该不该出现”，二者缺一不可。`

## 16. 执行页按钮与详情页按钮之间的边界校对表

当前仓管体系里，同一个动作往往会同时涉及：

- 详情页顶部按钮
- 执行页内按钮

如果这层边界不收紧，后面很容易出现：

- 重复按钮
- 两边都能推进状态
- 用户搞不清该在哪点

一句话收口：

`详情页按钮负责“进入动作”，执行页按钮负责“完成动作过程”。`

### 16.1 边界总原则

当前更推荐遵守下面三条：

1. 详情页按钮负责入口与页面级动作
2. 执行页按钮负责当前动作过程的提交与完成
3. 不要让两个页面上的按钮同时承担同一层级职责

### 16.2 详情页按钮负责什么

详情页按钮当前更适合承接：

- 开始收货 / 上架 / 拣货 / 复核 / 执行
- 提交 / 生效
- 普通取消
- 终止 / terminated
- 返回主流程的关键入口动作

也就是说，详情页主要回答：

`我现在要不要进入某个动作。`

### 16.3 执行页按钮负责什么

执行页按钮当前更适合承接：

- 确认本次
- 确认并下一条
- 完成本次记录
- 取消当前未保存录入

也就是说，执行页主要回答：

`我已经进入动作后，这次过程如何提交和收尾。`

### 16.4 当前不建议的重叠做法

当前不建议：

- 在详情页直接放“确认本次”这类过程按钮
- 在执行页再放“普通取消单据”这类单据级按钮
- 让详情页和执行页同时承担终态推进

这会让状态推进和按钮职责混在一起。

### 16.5 四类动作的当前推荐边界

| 动作主线 | 详情页主按钮 | 执行页主按钮 | 当前推荐边界 |
|---|---|---|---|
| 收货 | 开始收货 | 确认本次 / 完成本次记录 | 详情页负责进入，执行页负责收货过程 |
| 上架 | 开始上架 | 确认本次 / 完成本次记录 | 详情页负责进入，执行页负责上架过程 |
| 拣货 | 开始拣货 | 确认本次 / 确认并下一条 | 详情页负责进入，执行页负责拣货过程 |
| 复核 | 开始复核 | 确认本次 / 完成本次记录 | 详情页负责进入，执行页负责复核过程 |

### 16.6 当前推荐的一句话页面边界口径

`详情页是动作入口层，执行页是动作过程层；入口和过程不要由同一个按钮体系混合承接。`

## 17. 角色、状态、按钮、记录规则四层联动总表

当前这份权限专题一路往下已经拆到了：

- 角色层
- 页面区块层
- 单据动作层
- 状态机联动层
- 页面边界层

为了后面评审、前端实现、后端按钮校验时不来回翻多份章节，当前更推荐再补一张“一页总表”，把四层关系压成统一理解口径。

一句话收口：

`四层联动总表不是替代前面各章节，而是把“谁、在什么状态、在哪个按钮、对哪条记录”压成统一校对入口。`

### 17.1 四层联动总原则

当前更推荐按下面顺序判断一个按钮最终能不能点：

1. `角色层`
   - 这个角色理论上是否有资格触发该按钮
2. `状态层`
   - 当前主状态 / 异常补充状态下该按钮是否应该出现或应可用
3. `按钮层`
   - 该按钮属于详情页顶部、执行记录区、异常区还是执行页过程按钮
4. `记录规则层`
   - 当前记录是否属于该用户授权的货主 / 仓库 / 数据范围

只要其中任意一层不满足，最终都不应可执行。

### 17.2 四层联动一页总表

| 联动层 | 核心问题 | 主要承载位置 | 典型判断口径 | 当前不该承担什么 |
|---|---|---|---|---|
| 角色层 | 谁理论上有资格做 | `res.groups`、角色矩阵 | 操作员 / 主管 / 异常处理 / 管理员 / 只读 | 不直接决定具体状态下是否可用 |
| 状态层 | 当前状态下该不该出现、该不该可点 | 各主单状态机专题 | `draft` / `waiting_*` / `executing` / `done` / `terminated` 等 | 不直接决定用户是否有资格 |
| 按钮层 | 按钮放在哪个页面、哪个区块 | 详情页 / 执行页 / 区块级矩阵 | 顶部主按钮、执行记录区按钮、异常区按钮、执行页过程按钮 | 不替代角色和记录规则 |
| 记录规则层 | 这条记录当前用户能不能操作 | record rule、货主 / 仓库范围 | `owner_id`、`warehouse_id` 授权范围 | 不替代角色分工和状态推进 |

### 17.3 一条典型判断链示例

以“开始上架”为例，当前更推荐这样校对：

1. 角色层：
   - 操作员 / 主管 / 管理员可具备资格
   - 异常处理 / 只读默认无资格
2. 状态层：
   - 仅在入库单 `received` / `putawaying` 阶段允许出现
3. 按钮层：
   - 详情页顶部按钮负责“进入上架”
   - 执行页内部按钮负责“确认本次上架”
4. 记录规则层：
   - 用户必须对当前 `owner_id`、`warehouse_id` 范围内的入库单有操作权

只有四层都满足，按钮才最终可点。

### 17.4 当前推荐的实现理解

当前更推荐把这四层理解成：

- 角色层决定“默认谁能做”
- 状态层决定“现在能不能做”
- 按钮层决定“在哪里做”
- 记录规则层决定“能不能对这条数据做”

这也是后面做实现时最稳的分工方式：

- 角色矩阵不去硬编码状态
- 状态机不去替代角色矩阵
- 页面按钮不去偷偷承担权限判断
- 记录规则不去伪装成按钮启用条件

### 17.5 当前推荐的一句话四层联动口径

`角色定资格，状态定时机，按钮定位置，记录规则定对象。`

## 18. 与前端显隐实现、后端校验实现之间的落地对照表

当前这份权限专题如果只停留在规则层，后面实现时最容易出现两种偏差：

- 把所有控制都压给前端显隐
- 或者完全不做前端分层，全部等后端报错

这两种都不理想。当前更推荐把前端和后端的职责明确拆开。

一句话收口：

`前端负责减少误操作和保持页面清晰，后端负责真正的权限兜底与规则校验。`

### 18.1 当前推荐的前后端分工总原则

当前更推荐这样理解：

**前端显隐实现**

- 负责把当前不该出现的入口尽量隐藏或弱化
- 负责在页面层做“默认正确引导”
- 负责把只读、无资格、无状态条件的按钮尽量不暴露给用户

**后端校验实现**

- 负责最终拦截无权限操作
- 负责最终拦截状态不合法操作
- 负责最终拦截记录范围不合法操作
- 即使前端漏显、绕过、接口直调，也不能放过

### 18.2 当前推荐的一页落地对照表

| 控制层 | 前端显隐职责 | 后端校验职责 | 当前推荐实现口径 |
|---|---|---|---|
| 角色层 | 无资格按钮默认不显示或置灰 | 再次校验当前用户 group / 角色边界 | 前端减噪，后端兜底 |
| 状态层 | 不符合当前状态的按钮不显示或禁用 | 再次校验主状态 / 异常补充状态是否合法 | 状态推进不能只靠前端 |
| 页面边界层 | 详情页和执行页各自只放本层按钮 | 后端按动作语义校验是否允许从当前入口执行 | 避免页面职责串层 |
| 记录规则层 | 可通过空状态、无按钮、只读态弱提示 | 最终以 record rule / owner / warehouse 范围拦截 | 数据边界必须以后端为准 |

### 18.3 哪些更适合前端优先处理

当前更推荐前端优先处理这些内容：

- 角色无资格时不展示入口
- 当前状态下不应出现的按钮直接隐藏
- 只读角色统一进入查看态页面
- 执行页过程按钮与详情页入口按钮做清晰分层
- 通过提示条 / toast 给用户即时解释

这些内容的目标是：

- 降低误操作
- 降低页面噪音
- 让用户更容易理解当前该做什么

### 18.4 哪些必须以后端校验为准

当前更推荐后端必须兜底这些内容：

- 用户是否真的属于允许的角色组
- 当前单据状态是否真的允许该动作
- 当前记录是否在授权货主 / 仓库范围内
- 当前动作是否违反已定义的状态机规则
- 终止、取消、调整、发货确认等关键动作是否满足业务约束

也就是说：

前端即使判断正确，后端也必须再做一次完整校验。  
前端即使判断出错，后端也不能放过。

### 18.5 当前不建议的实现方式

当前不建议：

- 只做前端隐藏，不做后端校验
- 只做后端报错，不做前端显隐和页面分层
- 前端和后端各自维护两套完全不同的按钮口径
- 在前端把“禁用”和“无权限”混成同一种表现

这些做法后面都会导致：

- 用户体验差
- 联调成本高
- 规则漂移
- 权限漏洞风险

### 18.6 当前推荐的一句话落地口径

`前端负责把入口收干净，后端负责把规则守住。`

## 19. 权限矩阵到 XML / Python / JS 三层实现对象的映射草稿

当前这份权限专题如果继续往实现落地推进，下一步最关键的问题不是“规则还有没有”，而是：

- 这些规则具体由哪些工程对象承接
- 哪一层该写在 XML
- 哪一层必须写在 Python
- 哪一层适合写在 JS / OWL 前端

一句话收口：

`权限矩阵不能只停留在文档层，必须明确映射到 XML、Python、JS 三层对象，各层只承担自己该承担的职责。`

### 19.1 当前推荐的三层分工总原则

当前更推荐这样拆：

**XML 层**

- 承担菜单、act_window、基础 view 级别的显隐入口
- 承担 `groups` 属性能直接表达的基础可见性

**Python 层**

- 承担最终权限校验
- 承担状态合法性校验
- 承担记录范围与业务约束校验

**JS 层**

- 承担执行页、client action、OWL 组件里的前端显隐和交互弱引导
- 承担只读态、按钮禁用态、空状态、提示反馈

### 19.2 当前推荐的一页映射总表

| 规则层 / 对象 | XML 承接 | Python 承接 | JS 承接 | 当前推荐口径 |
|---|---|---|---|---|
| 菜单可见性 | `ir.ui.menu` + `groups` | 不作为主承接 | 不作为主承接 | 菜单显隐优先落 XML |
| 列表 / 详情页入口 | `ir.actions.act_window`、view `groups` | 可补服务端拦截 | 可补前端空状态解释 | 入口以 XML 为主，后端兜底 |
| 详情页按钮显隐 | view button `groups`、`attrs` / 条件 | 按钮方法内校验 | 页面层弱显隐较少 | 传统详情按钮先 XML，最终再 Python |
| 执行页按钮显隐 | 不作为主承接 | RPC / action 方法校验 | OWL 组件内主承接 | 执行页交互主要落 JS，后端兜底 |
| 状态合法性 | 只做基础界面限制 | 模型方法 / service 方法 / action 方法校验 | 页面禁用态、提示条 | 状态最终以后端为准 |
| 记录规则范围 | 不作为主承接 | `ir.rule`、domain、模型访问校验 | 只做前端提示 | 数据范围必须以后端为准 |
| 只读角色页面态 | view 只读属性可辅助 | 后端拒绝写操作 | 前端统一只读态表现 | 三层可协作，但最终以后端拒写为准 |

### 19.3 XML 层当前更适合承接什么

当前更推荐 XML 层优先承接这些对象：

- `ir.ui.menu`
- `ir.actions.act_window`
- 表单 / 列表 / 搜索 view
- 传统按钮的 `groups`
- 传统表单按钮的基础显示条件

当前更推荐理解为：

- XML 层负责把“明显不该看到的传统入口”先收掉
- 但不要指望 XML 一层承接所有动态状态判断

### 19.4 Python 层当前必须兜住什么

当前更推荐 Python 层必须兜住这些对象：

- 模型按钮方法
- 状态推进方法
- 终止 / 取消 / 调整等关键动作方法
- 执行页 RPC 后端入口
- record rule 与 domain 范围

当前更推荐理解为：

- 所有关键动作必须在 Python 再做一次最终校验
- 即使 XML 和 JS 都已经做了限制，Python 也不能省

### 19.5 JS 层当前更适合承接什么

当前更推荐 JS / OWL 层优先承接这些对象：

- 执行页 client action
- 左侧待处理区按钮和行选择
- 右侧执行区按钮禁用 / 启用
- 只读态、空状态、提示条、toast
- PDA / 扫码场景下的交互弱引导

当前更推荐理解为：

- JS 层重点不是“定义最终权限”，而是把正确入口和正确交互呈现出来
- 执行页里大量细粒度按钮体验，应主要落在 JS 层

### 19.6 当前不建议的实现映射方式

当前不建议：

- 把所有按钮控制都压给 XML
- 把所有显隐都推给 JS，不做 XML 入口收口
- 把 Python 只当数据层，不做动作校验
- 三层分别维护互相矛盾的按钮口径

这些做法后面都会导致：

- 入口显隐不一致
- 前后端联调反复
- 按钮体验和真实权限脱节

### 19.7 当前推荐的一句话对象映射口径

`XML 收入口，JS 收交互，Python 守规则。`

## 20. 角色、状态、按钮到具体文件 / 方法 / 组件的落地命名清单

当前这份权限专题如果继续往开发落地推进，下一步最关键的问题已经不只是：

- 规则在哪一层实现

而是：

- 这些实现应该大致落到哪些文件
- 哪些动作更像模型方法
- 哪些更像前端组件能力
- 哪些对象命名需要尽早统一

一句话收口：

`规则分层确定后，还需要把角色、状态、按钮继续映射到可实现的文件、方法、组件命名清单里。`

### 20.1 当前推荐的命名落位总原则

当前更推荐：

1. `角色` 优先落在 `security` 与 group XML ID 命名里
2. `状态` 优先落在模型字段、状态推进方法、显示枚举里
3. `详情页按钮` 优先落在 XML 按钮定义和 Python 模型方法里
4. `执行页按钮` 优先落在 JS / OWL 组件动作和 Python RPC 方法里

也就是说：

- 名称要先在文档里稳定
- 再在 XML / Python / JS 中分别复用同一套业务词汇

## 22. 更细的前端权限辅助 service / hook 设计口径

当前前面已经把：

- 前端显隐与后端校验分工
- XML / Python / JS 对象映射
- 执行页相关组件与模块落位

都收了一轮。  
如果继续往前端实现推进，下一步最值得单独抽出来的就是：

- 哪些权限辅助逻辑适合做成 `service`
- 哪些更适合做成 `hook`
- 哪些不要过早抽成前端公共层

一句话收口：

`前端权限辅助层的目标，不是替代后端权限，而是把执行页里的显隐、只读态、提示与弱校验逻辑稳定复用。`

### 22.1 当前推荐的设计原则

当前更推荐遵守这 4 条：

1. `service` 负责稳定的跨页面权限上下文与接口封装
2. `hook` 负责组件内的轻量判断与状态组合
3. 不把最终权限判断只放在前端
4. 不过早把高度业务化逻辑抽成“通用权限框架”

### 22.2 当前更适合抽成 service 的内容

当前更推荐先抽这几类：

- 当前用户仓管权限上下文读取
- 当前角色组与只读态判断
- 执行页按钮权限辅助判断的统一封装
- 当前记录 owner / warehouse 范围相关的前端辅助判断
- 执行页 RPC 权限相关错误的统一解释

当前推荐命名方向例如：

- `wmsPermissionService`
- `wmsRoleService`
- `wmsExecutionAccessService`

这些 service 更适合放在：

- `logistics_wms_web/static/src/js/shared/services/**`

### 22.3 当前更适合抽成 hook 的内容

当前更推荐先抽这几类：

- 当前页面是否只读
- 当前按钮是否应显示 / 禁用
- 当前状态下是否允许继续执行
- 当前选中行切换时是否存在未保存输入
- 当前提示条应显示哪一类反馈

当前推荐命名方向例如：

- `useWmsReadonlyState`
- `useWmsActionAvailability`
- `useWmsUnsavedInputGuard`
- `useWmsHintPriority`

这些 hook 更适合放在：

- `logistics_wms_web/static/src/js/shared/hooks/**`

### 22.4 当前不建议过早抽成公共层的内容

当前不建议太早抽这些：

- 把收货 / 上架 / 拣货 / 复核全部业务规则塞进一个超大权限 hook
- 把所有状态机判断都做成一个“万能 service”
- 把后端 record rule 逻辑镜像成完整前端权限引擎

这些做法很容易让前端权限层过重，而且和后端规则漂移。

### 22.5 当前推荐的一页分工表

| 前端辅助对象 | 更适合形态 | 当前推荐承载内容 | 不应承担什么 |
|---|---|---|---|
| 角色与只读态 | `service` + 轻 hook | 角色组、只读、查看态基线 | 最终权限裁决 |
| 按钮显隐 | `hook` | 当前状态、当前页面、当前区块下的显隐组合 | 后端动作合法性替代 |
| 未保存输入保护 | `hook` | 切换行、离开页、确认弹窗前置判断 | 业务状态推进 |
| 提示条优先级 | `hook` | 成功 / 警告 / 错误展示排序 | 后端错误定义 |
| RPC 权限错误解释 | `service` | 把后端拒绝映射成统一前端提示 | 决定是否真的允许执行 |

### 22.6 当前推荐的一句话 service / hook 口径

`service 收上下文和共性封装，hook 收页面内组合判断；真正的权限兜底始终留在后端。`

## 23. 更细的执行页按钮到 client action / client view 的控制口径

当前前面已经把执行页按钮的：

- 角色边界
- 状态边界
- 前后端分工
- JS / OWL 落位

都收了一轮。  
如果继续往真正的 Odoo 前端入口对象推进，下一步就需要补清：

- 哪些按钮更像 `client action` 入口控制
- 哪些按钮更像 `client view` / 页面内部控制
- 哪些控制不应该继续往入口对象层下沉

一句话收口：

`执行页按钮不是都落在同一层；入口类按钮更靠 client action，过程类按钮更靠 client view / 页面内部组件。`

### 23.1 当前推荐的分层总原则

当前更推荐这样理解：

1. `client action` 负责承接“进入哪一个执行页”
2. 页面容器 / `client view` 层负责承接“进入后当前页能做什么”
3. 右侧执行区组件负责承接“当前过程按钮是否可点”

也就是说：

- 入口按钮不要和过程按钮落在同一层
- 页面容器不要替代右侧执行组件去处理全部细粒度动作

### 23.2 当前更适合落到 client action 的按钮控制

当前更推荐这类按钮更接近 `client action` 控制层：

- 开始收货
- 开始上架
- 开始拣货
- 开始复核
- 从详情页进入执行页
- 从待处理中心进入执行页

当前推荐理解为：

- 这类按钮本质是在决定“打开哪一个执行页”
- 所以应优先和 `ir.actions.client.tag`、registry key、页面容器入口对应

### 23.3 当前更适合落到 client view / 页面容器层的按钮控制

当前更推荐这类按钮更接近页面容器层：

- 完成本次记录
- 切换下一条
- 是否显示空状态操作按钮
- 是否显示顶部只读 / 提示条辅助按钮

当前推荐理解为：

- 这类按钮已经进入执行页语境
- 但还不是最细一层的业务提交流程

### 23.4 当前更适合落到右侧执行组件层的按钮控制

当前更推荐这类按钮落在右侧执行区组件内部：

- 确认本次
- 确认并下一条
- 清空输入
- 当前明细禁用 / 可点击判断

当前推荐理解为：

- 这些按钮和当前选中行、当前输入值、当前动作上下文强绑定
- 不应继续上提到 `client action` 层

### 23.5 当前推荐的一页控制对照表

| 按钮类型 | 更适合控制层 | 当前推荐承载对象 | 不应承担什么 |
|---|---|---|---|
| 开始收货 / 上架 / 拣货 / 复核 | `client action` 入口层 | action tag、registry key、页面容器入口 | 过程内细粒度提交 |
| 完成本次记录 | 页面容器 / `client view` 层 | 执行页容器组件 | 当前行输入细节判断 |
| 确认本次 / 确认并下一条 | 右侧执行组件层 | 右侧执行组件、action hook | 页面入口级控制 |
| 空状态恢复动作 | 页面容器层 | 空状态组件、容器级 action | 后端最终权限裁决 |

### 23.6 当前推荐的一句话 client action / client view 口径

`入口按钮归 client action，过程按钮归页面容器与右侧执行组件；不要把所有执行页按钮都压到同一层。`

## 24. 与执行页组件命名专题之间的一对一映射校对表

当前权限专题已经把执行页相关的这些内容逐步补齐了：

- 执行页按钮和详情页按钮边界
- 执行页按钮到 client action / client view 的控制口径
- 前端 service / hook 抽层口径

而另外一份：

- `执行页组件命名与文件映射草稿`

已经把执行页入口对象、组件容器、模板、service / hook、目录映射收得比较细。

所以现在最值得再补的一步，不是继续发明新规则，而是把两份专题之间做一张一对一校对表。

一句话收口：

`权限专题回答“为什么这样分层”，组件命名专题回答“这些层最终叫什么、写在哪”；一对一映射表负责把两者对齐。`

### 24.1 当前推荐的校对总原则

当前更推荐按下面方式对齐：

1. 权限专题里的“入口层”对应组件专题里的 `client action`、registry key、页面容器
2. 权限专题里的“页面容器层”对应组件专题里的 `ExecutionPageShell`、`ExecutionActionPanel` 这类壳层
3. 权限专题里的“右侧执行组件层”对应组件专题里的 `ExecutionPrimaryActions`、`ExecutionPrimaryFields` 等录入层组件
4. 权限专题里的“service / hook 辅助层”对应组件专题里的 shared `services/**` 和 `hooks/**`

### 24.2 当前推荐的一页映射校对表

| 权限专题概念 | 组件命名专题对应层 | 当前推荐承载对象 | 当前校对重点 |
|---|---|---|---|
| 开始收货 / 上架 / 拣货 / 复核入口 | `client action` 入口层 | action tag、registry key、页面容器组件 | 入口命名是否与动作语义一致 |
| 执行页页面容器层 | 页面壳层组件 | `ExecutionPageShell`、动作页页面容器 | 顶部 / 左右 / 底部三区结构是否一致 |
| 右侧过程按钮层 | 右侧执行组件层 | `ExecutionPrimaryActions`、动作页右侧组件 | 确认本次 / 下一条 / 完成记录的分层是否一致 |
| 前端权限辅助层 | shared `services/**` / `hooks/**` | `wmsPermissionService`、`useWmsActionAvailability` 等 | 名称是否与权限语义一致 |
| 空状态 / 提示层 | 反馈与容器层 | `ExecutionHintBar`、空状态组件、toast bridge | 是否仍遵守“前端减噪、后端兜底” |

### 24.3 当前推荐的重点校对关系

当前更推荐特别盯住这几组：

**1. 入口按钮 <-> client action**

- 权限专题里“开始收货 / 上架 / 拣货 / 复核”应能在组件专题里找到对应的 client action 命名和入口文件
- 如果组件专题里已有入口对象，但权限专题没有明确其角色边界，就说明权限稿不完整
- 反过来，如果权限稿定义了入口，但组件专题没有对应入口命名，也说明前端专题还没对齐

**2. 过程按钮 <-> 右侧执行组件**

- 权限专题里“确认本次 / 确认并下一条 / 完成本次记录”的层级
- 应能对应到组件专题里的右侧按钮组件与容器边界

**3. 权限辅助判断 <-> service / hook**

- 权限专题里“只读态、按钮可见 / 禁用、未保存输入保护、提示优先级”
- 应能在组件专题里对应到 shared `service / hook` 层

### 24.4 当前不建议的错位做法

当前不建议：

- 权限专题说按钮在入口层，但组件专题把它做成右侧过程按钮
- 权限专题说是 shared hook，组件专题却把逻辑散落到四个动作页各自 hardcode
- 权限专题说前端只做弱引导，但组件专题又把最终权限裁决放进 JS

这些错位会让两份专题看起来都对，但实现时彼此打架。

### 24.5 当前推荐的一句话专题对齐口径

`权限专题定边界，组件专题定载体；一对一映射表负责防止“边界对、载体错”或“载体对、边界错”。`
