## 1. 文档定位

当前重点不是覆盖全部盘点业务细节，而是先固定：

- 一期主状态机
- `reviewing` 阶段的业务含义
- 差异处理结果字段口径
- 部分完成边界
- done 后处理边界
- 盘点单与异常补充状态的边界

## 2. 范围与边界

### 2.1 当前纳入范围

- 盘点单一期主状态机

- 差异处理结果字段口径
- 部分完成边界

- 完整异常中心设计

## 3. 一期主状态机

当前一期更推荐盘点单主状态机保持以下 5 个状态：

- `draft`
- `counting`
- `reviewing`
- `done`
- `cancel`

对应业务理解为：

- `draft`：草稿
- `counting`：盘点中
- `reviewing`：待确认 / 待审核差异
- `done`：已完成
- `cancel`：已取消

## 4. 主状态定义

### 4.1 `draft`

含义：

- 盘点单已创建，但尚未进入正式盘点执行

进入条件：

- 新建盘点单

退出条件：

- 用户开始盘点，进入 `counting`
- 用户主动取消，进入 `cancel`

### 4.2 `counting`

含义：

- 已进入盘点执行，但盘点结果尚未整体确认

进入条件：

- 第一次正式开始盘点
- 或第一笔有效盘点动作产生

退出条件：

- 盘点执行完成后，进入 `reviewing`
- 盘点过程中继续保持 `counting`

### 4.3 `reviewing`

含义：

- 盘点已完成，但差异结果仍待确认、吸收或处理

进入条件：

- 盘点执行完成
- 已形成盘点结果
- 存在需要确认的差异或待确认结果

退出条件：

- 差异已确认并处理完，进入 `done`
- 用户放弃或作废，进入 `cancel`

### 4.4 `done`

含义：

- 盘点闭环已完成
- 差异结果已确认并吸收

进入条件：

- `reviewing` 阶段完成确认

退出条件：

- 无正常退出，视为终态

### 4.5 `cancel`

含义：

- 盘点单在允许阶段被取消或作废

进入条件：

- `draft` 阶段主动取消
- 或特殊情况下在 `reviewing` 放弃

退出条件：

- 无正常退出，视为终态

## 5. 当前推荐的主状态推进原则

当前更推荐按以下原则统一理解：

1. 盘点单的重点不只是“盘完没有”，而是“差异有没有被确认”
2. `reviewing` 是真实业务阶段，不是技术过渡态
3. 盘点单不追求像入库/出库那样细分很多执行中状态
4. done 后不建议继续在原单上反复调整

一句话收口：

`盘点开始后进入 counting，盘点完成后进入 reviewing，差异确认吸收后进入 done。`

## 6. reviewing 阶段的进入与退出口径

当前更推荐：

### 6.1 进入 `reviewing`

- 盘点执行完成
- 已形成盘点结果
- 存在需要确认的差异或待确认结果

### 6.2 退出 `reviewing`

- 差异已确认并处理完，进入 `done`
- 用户放弃或作废，进入 `cancel`

当前更推荐把 `reviewing` 理解成：

- 盘点动作已经结束
- 但结果还没有真正完成业务闭环

## 7. 盘点差异处理结果字段口径

当前更推荐一期单独保留一个轻量“差异处理结果”字段。

建议值先收为：

- `matched`
- `adjusted`
- `pending`

对应理解为：

- `matched`：无差异或已对齐
- `adjusted`：已按盘点结果调整
- `pending`：差异待处理

当前更推荐：

- 这个字段服务于页面展示、筛选与后续统计
- 不必一开始扩张成复杂差异处理体系

## 8. 部分完成与 done 后处理边界

### 8.1 盘点单是否需要“部分完成”状态

当前更推荐：

- 一期不单独新增“部分完成”主状态

更稳的做法是：

- 行级支持已盘 / 未盘
- 主单级仍停留在 `counting`

### 8.2 done 后是否允许再次调整

当前更推荐：

- 不直接在原盘点单上继续反复调整

更稳的做法是：

- 走新的盘点单
- 或专门调整流程

这样更利于审计和历史追溯。

## 9. 异常补充状态的当前边界

当前更推荐：

- 盘点单一期先不重点做“主状态 + 异常补充状态”这一套

主要因为：

1. 盘点单天然就包含差异处理语义
2. 很多所谓“异常”本身就是盘点主流程的一部分
3. 一期更适合靠：
   - 主状态
   - 差异字段
   - 差异处理结果
   来表达，而不是再叠一层异常补充状态

一句话收口：

`入库单、出库单更适合“主状态 + 异常补充状态”；盘点单一期先不必强行套这套。`

## 10. 盘点单按钮与状态联动矩阵

本节用于把前述盘点单状态机进一步映射到详情页常见按钮与动作入口，形成一期更可执行的按钮基线。

### 10.1 当前纳入矩阵的按钮范围

当前先聚焦一批高频、关键按钮：

- `开始盘点`
- `继续盘点`
- `提交确认`
- `取消`
- `查看盘点结果`
- `查看差异处理信息`
- `发起调整 / 生成调整`

这里的原则是：

- 普通详情页先只收页面级 / 记录级按钮
- 盘点执行页内的逐行录入动作不在本节展开

### 10.2 按钮与状态联动的当前总原则

当前更推荐按以下原则统一理解：

1. `draft` 承接开始盘点与取消
2. `counting` 承接继续盘点与查看阶段性结果
3. `reviewing` 承接差异确认与结果吸收
4. `done` 以查看与追溯为主，不再提供主流程推进按钮
5. `cancel` 以查看为主，不再提供普通主流程动作

### 10.3 当前推荐的按钮矩阵

| 按钮 / 动作 | draft | counting | reviewing | done | cancel |
|---|---|---|---|---|---|
| 开始盘点 | 是 | 否 | 否 | 否 | 否 |
| 继续盘点 | 否 | 是 | 否 | 否 | 否 |
| 提交确认 | 否 | 否 | 是 | 否 | 否 |
| 取消 | 是 | 否 | 条件允许 | 否 | 否 |
| 查看盘点结果 | 否 | 是 | 是 | 是 | 否 |
| 查看差异处理信息 | 否 | 否 | 是 | 是 | 否 |
| 发起调整 / 生成调整 | 否 | 否 | 是 | 否 | 否 |

上表中的“是 / 否 / 条件允许”当前建议这样理解：

- `是`：一期默认可显示，仍需满足角色权限
- `否`：一期默认不显示
- `条件允许`：仅在当前业务允许放弃或作废盘点结果时显示

### 10.4 关键按钮的当前解释口径

#### A. `开始盘点`

当前更推荐：

- 只在 `draft` 显示
- 触发后主状态进入 `counting`

#### B. `继续盘点`

当前更推荐：

- 只在 `counting` 显示
- 语义上表示继续当前盘点任务，而不是进入新的状态

#### C. `提交确认`

当前更推荐：

- 只在 `reviewing` 显示
- 触发后表示差异已确认并吸收
- 完成后主状态进入 `done`

#### D. `查看盘点结果`

当前更推荐：

- 在 `counting / reviewing / done` 显示
- 用于查看阶段性结果或最终结果

#### E. `发起调整 / 生成调整`

当前更推荐：

- 只在 `reviewing` 显示
- 用于把差异处理结果落到库存调整动作
- 不建议在 `counting` 阶段提前开放

### 10.5 按钮分层建议

当前更推荐在详情页上按以下层次放置：

#### 顶部主按钮区

优先承接：

- `开始盘点`
- `继续盘点`
- `提交确认`

#### 次级入口 / smart button 区

优先承接：

- `查看盘点结果`
- `查看差异处理信息`

#### 更多菜单或次级动作区

优先承接：

- `取消`
- `发起调整 / 生成调整`

这里的重点是：

- 盘点单不需要太多危险动作语义
- 但也不建议把“生成调整”与主流程按钮完全混成一个层级

### 10.6 当前不建议的一期做法

当前不建议一期采用以下做法：

- 在 `counting` 期间开放“提交确认”
- 在 `done` 后继续保留主流程推进按钮
- 因存在差异就把盘点单按钮体系做成完整异常中心
- 把“部分完成”单独做成一个按钮驱动的主状态分支

### 10.7 当前阶段关于按钮与状态联动的统一收口

截至当前阶段，更推荐统一收敛为：

1. `draft` 负责开始与取消
2. `counting` 负责继续盘点与查看结果
3. `reviewing` 负责差异确认、查看结果与生成调整
4. `done / cancel` 以查看与追溯为主
5. 一期不围绕盘点单单独扩张一套异常按钮体系

## 11. 盘点单状态与执行记录的联动矩阵

本节用于把盘点单主状态与关键执行记录进一步挂钩：

- 盘点执行记录
- 差异确认结果
- 调整动作结果

当前目标不是穷尽所有细节，而是先固定“一期主状态大致对应什么执行记录和差异处理行为”。

### 11.1 当前联动的统一原则

当前更推荐按以下原则理解：

1. 主状态表达盘点单所处业务阶段
2. 执行记录表达该阶段内已发生或正在发生的盘点动作
3. 差异处理结果不替代主状态
4. 主状态也不替代差异处理结果
5. 页面展示时，主状态、执行记录、差异结果应互相印证

### 11.2 当前推荐的联动矩阵

| 主状态 | 盘点执行记录 | 差异处理结果 | 调整动作结果 | 当前理解 |
|---|---|---|---|---|
| `draft` | 无 | 无 | 无 | 尚未进入正式盘点 |
| `counting` | 可存在进行中的盘点执行事实 | 可阶段性形成，但未最终确认 | 无或不作为闭环依据 | 已开始盘点，允许分批、分区域盘点 |
| `reviewing` | 已完成盘点动作 | 应明确为 `matched / adjusted / pending` 之一 | 可开始进入调整吸收 | 盘点动作结束，结果待确认与吸收 |
| `done` | 已完成 | 已完成确认 | 已完成或已明确无需调整 | 盘点闭环完成 |
| `cancel` | 无或不再继续 | 无或作废 | 无 | 未正常形成有效闭环 |

### 11.3 当前推荐的状态判断口径

#### A. 从 `draft` 到 `counting`

当前更推荐以“正式开始盘点”或“第一笔有效盘点动作产生”为判断点。

也就是说：

- 不是看页面有没有打开
- 而是看是否真实进入盘点执行

#### B. 从 `counting` 到 `reviewing`

当前更推荐以“盘点动作结束，已形成可确认结果”为判断点。

也就是说：

- 行级可以仍有已盘 / 未盘过程痕迹
- 但主单进入 `reviewing` 时，应已结束本轮盘点动作

#### C. 从 `reviewing` 到 `done`

当前更推荐以“差异已确认并吸收”为判断点。

这里的“吸收”可包括：

- 无差异直接确认
- 已生成并完成调整
- 其他符合当前一期口径的差异关闭方式

### 11.4 `pending` 场景下的联动口径

若差异处理结果为 `pending`，当前更推荐：

- 主状态继续停在 `reviewing`
- 不提前进入 `done`
- 页面应强调“差异待处理”

也就是说：

- `pending` 是 reviewing 阶段的重要判断信号
- 不是一个独立主状态

### 11.5 当前不建议的一期做法

当前不建议一期采用以下方式：

- 用差异处理结果直接替代主状态
- 主单一进入 `counting` 就自动视为已形成最终差异结果
- 在 `pending` 场景下仍直接把主单推进到 `done`
- 通过删除盘点执行记录来回退主状态

### 11.6 当前阶段关于状态与执行记录联动的统一收口

截至当前阶段，更推荐统一收敛为：

1. `draft` 之前无正式执行记录
2. `counting` 主要由盘点执行记录承接
3. `reviewing` 表示盘点动作已结束、差异结果待确认
4. `done` 表示盘点记录、差异确认与调整吸收都已完成
5. 差异处理结果字段与主状态继续分层表达

## 12. 盘点单详情页 / 列表页状态展示口径

本节用于把盘点单主状态与差异处理结果进一步收成页面语言，避免后续同一状态在列表页和详情页各说各话。

### 12.1 当前推荐的展示总原则

当前更推荐按以下原则统一展示：

1. 列表页优先追求短、稳、易扫读
2. 详情页允许比列表页多一层解释
3. 主状态始终占主位
4. 差异处理结果作为补充标签或补充信息
5. 不把主状态和差异处理结果混写成一个新的数据库状态名

### 12.2 列表页展示口径

当前更推荐列表页按以下方式展示：

| 主状态 | 列表页主展示 | 次标签（如有） |
|---|---|---|
| `draft` | 草稿 | 无 |
| `counting` | 盘点中 | 可按需要显示阶段提示 |
| `reviewing` | 待确认差异 | `待处理`（如 pending） / `已调整` / `已对齐` |
| `done` | 已完成 | 可不加 |
| `cancel` | 已取消 | 可不加 |

这里的关键统一点是：

- 列表页主列只显示主状态短语义
- 差异处理情况通过次标签补充
- 不把 `reviewing + pending` 合并成新的主状态文案

### 12.3 详情页头部展示口径

当前更推荐详情页头部按以下方式展示：

- 主状态：显示主状态中文语义
- 差异处理结果：显示为次标签或补充标签
- 辅助说明：必要时补一句更完整的解释文案

例如在 `reviewing + pending` 场景下：

- 主状态：`待确认差异`
- 次标签：`待处理`
- 说明文案：`当前盘点动作已完成，但差异结果仍待处理。`

### 12.4 列表筛选与状态归类口径

当前更推荐：

1. 主状态筛选继续按主状态归类
2. 差异处理结果单独作为补充筛选条件
3. `reviewing + pending` 在主状态筛选中仍归入 `reviewing`
4. 同时支持“仅看待处理差异”等补充筛选

也就是说：

- 主状态筛选不被差异结果打乱
- 差异结果筛选另开一条口径

### 12.5 执行记录区与状态展示的当前建议

当前更推荐：

- 在主状态为 `counting` 时，执行记录区重点展示盘点执行进度
- 在主状态为 `reviewing` 时，执行记录区强调盘点已完成、差异待确认
- 在 `done` 时，盘点记录、差异结果与调整结果都应可完整回看

### 12.6 差异信息区的当前展示口径

当存在差异结果时，当前更推荐详情页单独展示：

- 差异处理结果
- 差异摘要
- 处理说明
- 处理人
- 时间

若无差异或无需强调，则：

- 可整体弱化
- 但仍建议保留结果口径

### 12.7 当前不建议的一期做法

当前不建议一期采用以下方式：

- 列表页把主状态和差异处理结果拼成过长文案
- 详情页只显示差异结果，不显示主状态
- 因存在 `pending` 就把主状态从 `reviewing` 挪走
- 列表页和详情页对同一状态使用不同中文语义

### 12.8 当前阶段关于页面状态展示的统一收口

截至当前阶段，更推荐统一收敛为：

1. 列表页主状态短展示，差异结果做次标签
2. 详情页头部保留主状态主位，差异结果做补充标签并允许补说明
3. 主状态筛选与差异结果筛选分开
4. `reviewing + pending` 仍按 `reviewing` 归主状态，只在页面上补 `待处理`

## 13. 盘点单字段字典与状态字段落表方式

本节用于把前述盘点单状态机与差异结果口径进一步映射到一期更可执行的数据字段口径。

当前目标不是一次性做完整字段字典，而是先固定：

- 盘点单主状态字段
- 差异处理结果字段
- 页面展示和筛选最依赖的核心字段
- 盘点范围与责任口径的最小字段组

### 13.1 当前推荐的字段分层

当前更推荐把盘点单相关字段先分成以下 4 层：

1. 主单身份字段
2. 主流程状态字段
3. 差异处理结果字段
4. 统计 / 展示辅助字段

也就是说，一期先把真正驱动流程的字段和展示辅助字段分开，不建议全部混成一个平铺大表。

### 13.2 一期最小核心字段字典

当前更推荐盘点单模型至少先保留以下核心字段：

| 字段名 | 建议类型 | 当前用途 |
|---|---|---|
| `name` | `Char` | 盘点单号 |
| `warehouse_id` | `Many2one` | 仓库 |
| `owner_id` | `Many2one` | 货主 |
| `state` | `Selection` | 主状态 |
| `difference_result` | `Selection` | 差异处理结果 |
| `responsible_id` | `Many2one` | 负责人/责任人 |
| `count_scope_type` | `Selection` | 盘点范围类型 |
| `count_scope_ref` | `Char` 或 `Many2one` | 盘点范围摘要/引用 |
| `remark` | `Text` | 备注 |
| `create_date` | `Datetime` | 创建时间 |
| `write_date` | `Datetime` | 最后修改时间 |

如果后续业务字段已明确，也可继续扩：

- `count_type`
- `location_id`
- `inventory_adjustment_ref`

但这些不影响当前状态机主线，不作为本节重点。

### 13.3 `state` 字段的当前落表建议

当前更推荐：

- 字段名：`state`
- 类型：`Selection`
- 作为盘点单主状态字段

一期枚举值当前更推荐固定为：

- `draft`
- `counting`
- `reviewing`
- `done`
- `cancel`

当前更推荐：

- `state` 只承接主流程状态
- 不把差异处理结果塞进 `state`

### 13.4 `difference_result` 字段的当前落表建议

当前更推荐：

- 字段名：`difference_result`
- 类型：`Selection`
- 用途：承接盘点差异的处理结果口径

一期建议值为：

- `matched`
- `adjusted`
- `pending`

当前更推荐：

- `difference_result` 与 `state` 分层表达
- `state` 负责盘点流程阶段
- `difference_result` 负责差异结果

### 13.5 当前推荐的页面字段映射关系

当前更推荐页面层按以下关系取值：

| 页面位置 | 推荐字段来源 |
|---|---|
| 列表页主状态列 | `state` |
| 列表页差异次标签 | `difference_result` |
| 详情页头部主状态 | `state` |
| 详情页头部补充标签 | `difference_result` |
| 差异信息区结果字段 | `difference_result` |
| 差异信息区说明 | `remark` 或后续差异说明字段 |

也就是说：

- 页面主状态统一来自 `state`
- 页面差异补充展示统一来自 `difference_result`

### 13.6 当前推荐的筛选字段口径

一期更推荐列表与搜索至少支持以下状态相关筛选：

- `state`
- `difference_result`
- `warehouse_id`
- `owner_id`

其中：

- `state` 负责主流程归类
- `difference_result` 负责差异结果归类

### 13.7 当前不建议的一期落表方式

当前不建议一期采用以下方式：

- 把 `matched / adjusted / pending` 直接塞进 `state`
- 同时再做一套并行的“页面状态字段”
- 用计算文案字段替代真正的 `state / difference_result`
- 为一期最小差异闭环单独拆重型差异主表

### 13.8 当前阶段关于字段字典与落表方式的统一收口

截至当前阶段，更推荐统一收敛为：

1. `state` 只承接盘点主流程状态
2. `difference_result` 只承接差异处理结果
3. 页面主状态、补充标签、差异信息区都直接从这组字段取值
4. 一期不额外构建并行页面状态字段或重型差异主表

## 14. 盘点单与库存调整 / stock 对象的字段级关联

本节用于把前述盘点单状态机进一步挂到库存调整与 Odoo 原生 stock 对象上，形成一期更清楚的字段级关联基线。

当前目标不是一次性给出所有技术字段，而是先固定：

- 盘点单与盘点明细的关系
- 盘点单明细与 `stock.quant` 的关系
- 差异确认与库存调整动作的关系
- 主状态推进时更依赖哪些库存事实

### 14.1 当前推荐的总体关联原则

当前更推荐继续沿以下原则推进：

1. 盘点单负责业务主线与业务语义
2. 盘点明细负责承接盘点范围内的理论数、实盘数、差异数
3. `stock.quant` 负责实时库存事实
4. 库存调整结果仍应回到 Odoo 原生库存调整机制

一句话收口：

`盘点单负责“为什么盘、盘到哪一步”，quant 与库存调整负责“账上库存和调整实际上怎么变”。`

### 14.2 盘点单与盘点明细的当前关联建议

当前更推荐：

- `logistics.wms.inventory.count.line.count_id -> logistics.wms.inventory.count`

对应在盘点单主模型上反查：

- `line_ids`

当前建议的理解是：

- 一张盘点单对应多条盘点明细
- 盘点主单不直接替代明细层的数量事实

### 14.3 盘点明细与 `stock.quant` 的当前关联建议

当前更推荐：

- `logistics.wms.inventory.count.line.quant_id -> stock.quant`

当前建议的理解是：

- `quant_id` 用于引用盘点时对应的理论库存口径
- 盘点明细可记录盘点当下的理论快照
- 但实时库存仍应继续看 `stock.quant`

### 14.4 差异确认与库存调整的当前关联建议

当前更推荐：

- `difference_result = adjusted` 时，应有明确的库存调整吸收动作
- 该吸收动作优先回到 Odoo 原生库存调整机制

如果后续需要显式反查，可补：

- `adjustment_ref`
- 或 `adjustment_move_ids`

但一期当前更推荐先把“有无完成差异吸收”作为主口径，而不是先扩很重的调整对象体系。

### 14.5 主状态与 stock 事实的当前对应口径

当前更推荐按以下方式理解主状态与 stock 层事实的关系：

| 主状态 | 更依赖的库存 / stock 事实 |
|---|---|
| `draft` | 尚无正式盘点执行事实 |
| `counting` | 已有盘点明细与盘点记录，理论库存以 `stock.quant` 为基准 |
| `reviewing` | 盘点动作结束，差异结果已形成，但尚未完全确认或吸收 |
| `done` | 差异已确认并完成吸收或明确无需调整 |
| `cancel` | 未形成有效闭环，或已在允许阶段作废 |

### 14.6 当前推荐的字段级最小清单

当前更推荐一期至少先把以下字段级关联稳定下来：

#### 盘点单主单侧

- `state`
- `difference_result`
- `line_ids`

#### 盘点明细侧

- `count_id`
- `quant_id`
- `theoretical_qty`
- `counted_qty`
- `difference_qty`

#### 库存事实侧

- `stock.quant`

### 14.7 当前不建议的一期做法

当前不建议一期采用以下方式：

- 盘点单自己再造一套并行库存主表
- 用主状态直接替代 quant 或调整事实
- 在没有完成差异确认时提前进入 `done`
- 用删除盘点明细的方式回退主状态

### 14.8 当前阶段关于盘点单与库存调整 / stock 关联的统一收口

截至当前阶段，更推荐统一收敛为：

1. 盘点单与盘点明细建立稳定主从关系
2. 盘点明细与 `stock.quant` 建立理论库存关联
3. 差异吸收继续回到 Odoo 原生库存调整机制
4. 主状态推进尽量以盘点事实与差异吸收事实为基础判断
5. 一期不额外构建并行库存事实层

## 15. 盘点单 search / filter / group by 的最终口径

本节用于把前述状态机、差异结果口径、页面展示与字段落表方式，进一步收成一期盘点单搜索与列表分析的统一口径。

当前目标不是一次性定义所有高级搜索，而是先固定：

- search view 的最小搜索字段
- filter 的最小状态 / 差异 / 时间口径
- group by 的最小分析维度
- 主状态与差异结果在搜索上的分层方式

### 15.1 当前推荐的总体原则

当前更推荐按以下原则统一理解：

1. `search` 负责快速定位单据
2. `filter` 负责固定业务场景筛选
3. `group by` 负责常用管理分析维度
4. 主状态与差异处理结果在搜索口径上继续分层
5. 一期先做高频、低歧义的搜索项，不把 search view 做得过重

### 15.2 当前推荐的 search 字段口径

一期当前更推荐 search view 至少支持以下关键字搜索对象：

- 盘点单号 `name`
- 仓库名称
- 货主名称 / 编码
- 盘点范围摘要

如果一期业务字段已落地，也可补：

- `count_scope_ref`
- `responsible_id`

但当前更推荐最小搜索仍以：

- `name`
- `warehouse_id`
- `owner_id`

为主。

### 15.3 当前推荐的 filter 口径

一期当前更推荐至少保留以下固定筛选：

#### A. 主状态类 filter

- 草稿
- 盘点中
- 待确认差异
- 已完成
- 已取消

这些 filter 统一对应：

- `state`

#### B. 差异处理结果类 filter

- 已对齐
- 已调整
- 待处理

这些 filter 统一对应：

- `difference_result`

当前更推荐：

- 主状态 filter 与差异处理结果 filter 分开定义
- 不把“待确认差异 + 待处理”做成新的主状态 filter

#### C. 时间类 filter

一期当前更推荐至少保留：

- 今日创建
- 近 7 天
- 近 30 天

时间口径当前优先建议基于：

- `create_date`

### 15.4 当前推荐的 group by 口径

一期当前更推荐至少保留以下 group by：

- 按主状态
- 按差异处理结果
- 按仓库
- 按货主
- 按创建日期（月 / 日）

如果后续业务字段启用，也可逐步补：

- 按盘点范围类型
- 按负责人

但当前不建议一期就堆太多 group by 维度。

### 15.5 当前推荐的主状态与差异口径分层

当前更推荐继续按以下方式统一：

| 口径层 | 对应字段 | 当前用途 |
|---|---|---|
| 主流程筛选 | `state` | 盘点流程阶段归类 |
| 差异结果筛选 | `difference_result` | 差异处理结果归类 |

也就是说：

- 搜索时先找盘点流程阶段
- 再看差异处理结果

### 15.6 当前推荐的视图使用方式

当前更推荐：

#### 普通盘点单列表页

优先保留：

- 主状态 filter
- 仓库 / 货主
- 时间
- 关键字搜索

#### 差异待处理视图

优先强化：

- `difference_result = pending`
- 仓库
- 货主
- 时间

也就是说，差异待处理视图应比普通列表更强调差异结果口径。

### 15.7 当前不建议的一期做法

当前不建议一期采用以下方式：

- 把 `state` 和 `difference_result` 混成一套搜索字段
- 在普通列表里默认铺满所有差异结果筛选
- 一上来就提供太多 group by 维度
- 为每个状态都再做一套重复的“快捷搜索别名”
- 让 `reviewing + pending` 变成新的主流程 group by 项

### 15.8 当前阶段关于 search / filter / group by 的统一收口

截至当前阶段，更推荐统一收敛为：

1. `search` 以单号、仓库、货主为主
2. `filter` 以主状态、差异处理结果、时间为主
3. `group by` 以主状态、差异处理结果、仓库、货主、日期为主
4. `state / difference_result` 两层口径继续分开
5. 差异待处理视图比普通列表页更强调差异结果筛选
