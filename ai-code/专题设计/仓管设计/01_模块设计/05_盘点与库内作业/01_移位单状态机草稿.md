- 一期主状态机
- 普通取消边界
- 执行失败时主状态停留口径
- 部分完成边界
- done 后修正边界
- 轻量异常信息区口径

## 2. 范围与边界

### 2.1 当前纳入范围

## 3. 一期主状态机

当前一期更推荐移位单主状态机保持以下 5 个状态：

- `draft`
- `waiting_execute`
- `executing`
- `done`
- `cancel`

对应业务理解为：

- `draft`：草稿
- `waiting_execute`：待执行
- `executing`：执行中
- `done`：已完成
- `cancel`：已取消

## 4. 主状态定义

### 4.1 `draft`

含义：

- 移位单已创建，但尚未进入正式执行

进入条件：

- 新建移位单

退出条件：

- 用户开始执行，进入 `waiting_execute` 或直接进入可执行态准备
- 用户主动取消，进入 `cancel`

当前一期更推荐：

- 先经 `waiting_execute`

### 4.2 `waiting_execute`

含义：

- 移位单已具备执行条件，但尚未开始真实移位动作

进入条件：

- `draft` 生效成功

退出条件：

- 开始执行，进入 `executing`
- 未开始执行前允许取消，进入 `cancel`

### 4.3 `executing`

含义：

- 已开始移位，但尚未完成全部移位动作

进入条件：

- 第一次正式开始移位
- 或第一笔有效移位动作产生

退出条件：

- 全部移位动作完成，进入 `done`
- 执行过程中继续保持 `executing`

### 4.4 `done`

含义：

- 移位闭环已完成

进入条件：

- 全部移位动作完成

退出条件：

- 无正常退出，视为终态

### 4.5 `cancel`

含义：

- 移位单在允许阶段被取消

进入条件：

- `draft / waiting_execute` 阶段的普通取消

退出条件：

- 无正常退出，视为终态

## 5. 当前推荐的主状态推进原则

当前更推荐按以下原则统一理解：

1. 移位单状态机保持轻量，不追求复杂中间态
2. 真实执行开始后，主状态应反映“已在执行中”
3. 行级可出现部分完成，但主单级不额外新增“部分完成”主状态
4. done 后不建议回退原单

一句话收口：

`开始执行后进入 executing，全部完成后进入 done。`

## 6. 普通取消边界

当前一期更推荐的普通取消边界为：

### 6.1 允许普通取消

- `draft`
- `waiting_execute`

### 6.2 谨慎允许 / 原则上不建议普通取消

- `executing`

### 6.3 不建议直接取消

- `done`
- `cancel`

一句话收口：

`移位单普通取消只开放到 draft / waiting_execute。`

## 7. 执行失败的处理口径

当前更推荐：

- 执行失败时主状态停在 `executing`

主要因为：

1. 已经开始真实库内动作
2. 不应退回 `waiting_execute`
3. 失败不等于没开始过

当前更推荐页面上表达为：

- 主状态仍是 `执行中`
- 配合轻量异常信息区说明“执行失败 / 待处理”

## 8. 部分完成与 done 后处理边界

### 8.1 是否需要“部分完成”主状态

当前更推荐：

- 一期不单独新增“部分完成”主状态

更稳的做法是：

- 行级支持部分完成
- 主单级仍停留在 `executing`

### 8.2 done 后发现问题如何处理

当前更推荐：

- 不回退原移位单
- 通过新移位单或调整流程修正

这样更利于：

- 审计
- 历史追溯
- 与入库 / 出库的 done 终态口径保持一致

## 9. 异常信息区的当前边界

当前更推荐：

- 移位单详情页应有轻量异常信息区

一期最小展示建议为：

- 当前问题说明 / 失败原因
- 备注
- 处理人
- 时间

当前不急着为移位单扩一套很重的异常补充状态体系，主要因为：

1. 移位单状态机当前保持轻量更合适
2. 页面上能看清失败原因和处理信息就够支撑一期

一句话收口：

`移位单一期需要轻量异常信息区，但不必急着扩成一套很重的异常状态体系。`

## 10. 移位单按钮与状态联动矩阵

当前建议把移位单详情页中的关键动作，先收成与一期主状态机一致的轻量矩阵。

### 10.1 一期纳入矩阵的关键按钮范围

一期建议先纳入以下按钮或入口：

- `提交 / 生效`
- `取消`
- `开始执行`
- `继续执行`
- `查看移位记录`
- `查看异常信息`

这里的口径是：

- `提交 / 生效`：把草稿单推进到可执行状态
- `开始执行`：从待执行进入执行中，并跳转到移位执行页
- `继续执行`：从执行中再次进入移位执行页
- `查看移位记录`：进入与该移位单关联的执行记录或执行明细查看页
- `查看异常信息`：查看当前移位单已有的异常说明、失败原因、处理人、处理时间

当前不建议把下面这些动作纳入一期主按钮矩阵：

- `部分完成`
- `回退`
- `撤销完成`
- `反向移位`

这些都会明显放大状态机复杂度，不适合一期。

### 10.2 五个主状态的按钮可见矩阵

| 按钮 / 动作 | `draft` | `waiting_execute` | `executing` | `done` | `cancel` |
| --- | --- | --- | --- | --- | --- |
| `提交 / 生效` | 是 | 否 | 否 | 否 | 否 |
| `取消` | 是 | 是 | 否 | 否 | 否 |
| `开始执行` | 否 | 是 | 否 | 否 | 否 |
| `继续执行` | 否 | 否 | 是 | 否 | 否 |
| `查看移位记录` | 否 | 否 | 是 | 是 | 否 |
| `查看异常信息` | 否 | 否 | 条件显示 | 条件显示 | 否 |

这里建议按下面几条理解：

- `draft` 阶段主要做资料确认，不直接进入执行页
- `waiting_execute` 阶段是一期最自然的执行起点
- `executing` 阶段允许继续进入执行页，但不再开放普通取消
- `done` 阶段只保留查看型入口，不再保留主流程推进按钮
- `cancel` 视为普通终态，不再保留执行入口

### 10.3 按钮与状态推进的解释口径

**1. `提交 / 生效`**

- 只在 `draft` 可见
- 点击后把主单推进到 `waiting_execute`
- 不直接创建“已完成”类执行事实

**2. `取消`**

- 只在 `draft / waiting_execute` 可见
- 一旦进入 `executing`，即不再开放普通取消
- `executing` 阶段如出现问题，应走异常说明或补充处理，而不是回到普通取消

**3. `开始执行`**

- 只在 `waiting_execute` 可见
- 点击后推进主状态到 `executing`
- 同时进入移位执行页，开始生成或承接执行记录

**4. `继续执行`**

- 只在 `executing` 可见
- 点击后再次进入移位执行页
- 不改变主状态，只恢复执行上下文

**5. `查看移位记录`**

- 在 `executing / done` 可见
- 用于查看与当前移位单对应的执行记录、执行明细、相关 `stock.picking / move / move.line`

**6. `查看异常信息`**

- 仅在已产生失败说明、异常备注或处理记录时显示
- 当前建议主要在 `executing / done` 阶段条件显示
- 一期先作为查看型入口，不延展成完整异常处理工作台

### 10.4 顶部主按钮、次级入口、更多菜单的分层建议

当前建议移位单详情页按钮区先分成三层：

**顶部主按钮**

- `提交 / 生效`
- `开始执行`
- `继续执行`

**次级入口 / smart button**

- `查看移位记录`
- `查看异常信息`

**更多菜单或次级动作**

- `取消`

这里建议保持和前面几类主单一致：

- 推进主流程的动作放主按钮位
- 查看型入口放次级入口
- 风险动作或终止动作放更多菜单或次级危险位

### 10.5 一期当前不建议采用的做法

当前不建议：

- 在 `executing` 阶段继续开放普通取消
- 在主状态机里增加 `partial_done`
- 给 `done` 增加常规回退或撤销完成按钮
- 让移位失败后把主状态退回 `waiting_execute`

更稳的口径仍然是：

- 执行失败时主状态停在 `executing`
- 页面通过异常信息区表达问题
- done 后发现问题，走新移位单或调整流程，而不是回退原单

## 11. 移位单状态与执行记录的联动矩阵

当前更推荐把移位单主状态与执行记录的关系，先收成“主单表达业务阶段，执行记录表达执行事实”的轻量口径。

### 11.1 一期建议纳入联动的执行对象

当前建议一期主要联动以下执行对象：

- 移位执行记录
- `stock.picking`（内部调拨）
- `stock.move`
- `stock.move.line`

这里的理解是：

- 移位单主单负责表达“当前走到哪一步”
- 移位执行记录负责表达“谁在何时做了哪次执行”
- `stock` 原生对象负责表达“库内货物事实上怎么移动”

### 11.2 主状态与执行记录的推荐联动口径

| 主状态 | 执行记录口径 | `stock` 执行事实口径 | 当前推荐理解 |
| --- | --- | --- | --- |
| `draft` | 尚未形成正式执行记录 | 尚未形成正式内部调拨执行事实 | 仅完成单据录入 |
| `waiting_execute` | 可预生成轻量记录上下文，但不要求已形成正式执行结果 | 尚未产生有效 `move.line` 执行结果 | 已具备执行条件但尚未开始 |
| `executing` | 已产生移位执行记录，且允许继续累积执行明细 | 已存在内部调拨 `picking / move / move.line` 执行事实 | 已进入真实执行阶段 |
| `done` | 执行记录闭环完成 | 内部调拨执行事实完成 | 移位主线闭环完成 |
| `cancel` | 不再生成新的执行记录 | 不应再形成新的执行事实 | 普通取消终态 |

### 11.3 几个关键联动点

**1. 从 `draft` 到 `waiting_execute`**

- 可以生成业务层准备数据
- 但不要求已经有正式移位执行记录
- 也不要求已经产生 `stock.move.line`

当前重点是让单据进入“可执行”状态，而不是提前制造执行事实。

**2. 从 `waiting_execute` 到 `executing`**

- 第一次正式开始移位时，主状态推进到 `executing`
- 同时应开始形成或承接对应的移位执行记录
- 同时开始产生真实的 `stock.picking / move / move.line` 执行事实

这一步建议视为移位单从“业务准备”转入“真实执行”的关键分界点。

**3. `executing` 阶段**

- 允许多次继续执行
- 行级可出现部分完成
- 但主单继续保持 `executing`
- 执行记录可以继续累积，`stock.move.line` 也可以继续累积

这里和前面已经定下来的“不新增 `partial_done` 主状态”保持一致。

**4. 从 `executing` 到 `done`**

- 当全部移位动作完成时，主状态进入 `done`
- 执行记录闭环完成
- 对应内部调拨执行事实也应完成

当前更推荐：
- 主状态是否进入 `done`
- 不由人工主观判断
- 而应依赖真实执行完成事实

**5. 执行失败场景**

- 主状态停在 `executing`
- 已有执行记录继续保留
- 已有 `stock` 执行事实继续保留
- 页面通过异常信息区说明“执行失败 / 待处理”

这里建议和入库单、出库单保持一致：
- 失败不回退主状态
- 不抹掉已发生事实

### 11.4 当前推荐的一句话联动口径

`移位单主状态负责表达业务阶段，移位执行记录与 stock 原生对象共同表达真实执行事实；状态推进应依赖执行事实，而不是脱离事实手工改状态。`

## 12. 移位单详情页 / 列表页状态展示口径

当前更推荐把移位单的页面状态展示，先统一成“列表页强调识别与筛选，详情页强调理解与处理”的口径。

### 12.1 列表页状态展示口径

列表页当前建议重点展示：

- 主状态
- 执行进度摘要
- 异常提示摘要（如有）

当前更推荐：

**1. 主状态占主位**

列表页主状态列先只展示：

- `草稿`
- `待执行`
- `执行中`
- `已完成`
- `已取消`

不要在列表页主状态列里叠过多细碎语义。

**2. 进度信息单独一列或单独摘要**

当前建议列表页补一个轻量进度展示，例如：

- `已执行 / 总行数`
- 或 `已完成行数 / 总行数`

这样可以在不增加主状态数量的前提下，反映执行进展。

**3. 异常提示做次级展示**

如果存在失败说明或异常备注，列表页更推荐：

- 在异常列显示简短标签
- 或在状态旁显示弱化异常标识

不要让异常信息抢掉主状态位置。

### 12.2 详情页状态展示口径

详情页当前建议重点展示：

- 主状态
- 执行记录
- 异常信息
- 当前可动作入口

当前更推荐：

**1. 头部主状态清晰单独展示**

详情页头部应明确显示主状态，例如：

- `待执行`
- `执行中`
- `已完成`

并与顶部按钮区联动。

**2. 主状态解释放在执行记录区和异常信息区**

当前不建议在头部堆太多状态解释文本。
更稳的做法是：

- 执行记录区解释“做到了哪一步”
- 异常信息区解释“为什么卡住 / 为什么失败”

**3. `executing` 阶段最需要强调两块**

- 执行记录区
- 异常信息区

因为移位单在这一阶段最容易出现：

- 部分执行
- 执行失败
- 待继续处理

### 12.3 列表页与详情页的统一收口

当前建议统一成：

- 列表页：主状态清晰、进度摘要轻量、异常提示弱化
- 详情页：主状态清晰、执行记录可追、异常信息可读、按钮入口明确

一句话收口：

`移位单列表页重点解决“看得懂和找得到”，详情页重点解决“看得深和继续处理”。`

## 13. 移位单字段字典与状态字段落表方式

当前更推荐先把移位单的字段落表方式，收成“主单字段轻量、状态字段单一、异常信息独立但不膨胀”的口径。

### 13.1 一期主单字段字典建议

当前建议一期移位单主单最小字段先收成以下几类：

**1. 身份字段**

- `name`
- `company_id`

**2. 归属字段**

- `warehouse_id`
- `owner_id`

**3. 主状态字段**

- `state`

**4. 业务基础字段**

- `source_location_id`
- `dest_location_id`
- `remark`

**5. 轻量异常信息字段**

- `issue_reason`
- `issue_remark`
- `issue_by`
- `issue_at`

**6. 审计字段**

- `create_uid`
- `create_date`
- `write_uid`
- `write_date`

### 13.2 当前推荐的主状态字段落表方式

当前建议移位单主状态继续采用单字段存储：

- `state`

推荐枚举值为：

- `draft`
- `waiting_execute`
- `executing`
- `done`
- `cancel`

这里建议和前面三份专题稿保持一致：

- 主状态字段只承载主流程状态
- 不把行级部分完成、失败细节、异常标签直接塞进主状态字段

### 13.3 当前推荐的异常信息字段落表方式

当前更推荐移位单一期异常信息先不做完整异常补充状态体系，而是用轻量问题字段承接。

推荐口径：

- `issue_reason`
  - 用于存储当前问题说明或失败原因
- `issue_remark`
  - 用于存储补充说明
- `issue_by`
  - 用于记录处理人
- `issue_at`
  - 用于记录处理时间

这里建议保持和前面已经确认的页面口径一致：

- 详情页有轻量异常信息区
- 但当前不把移位单扩成重型异常状态模型

### 13.4 当前推荐的字段设计原则

当前更推荐保持以下原则：

1. 主状态只保留一个 `state`
2. 行级进度不要反向堆到主状态字段里
3. 失败说明先用轻量问题字段承接
4. done 后修正不通过修改原主单状态解决，而通过新单或调整流程解决

一句话收口：

`移位单一期字段落表应保持轻量：主状态单一、异常说明轻量、审计字段完整。`

## 14. 移位单与 stock 原生对象的字段级关联

当前更推荐把移位单和 Odoo 原生 `stock` 对象的关系，收成“主单对执行主单、明细对执行明细、执行事实不复制”的口径。

### 14.1 移位单主单与 `stock.picking`

当前建议：

- 移位单主单与内部调拨 `stock.picking` 建立主关联

推荐字段口径：

- 在 `stock.picking` 上扩：
  - `wms_relocation_id = fields.Many2one('logistics.wms.relocation')`
- 在移位单上反向：
  - `internal_picking_ids = fields.One2many('stock.picking', 'wms_relocation_id')`

这里的理解是：

- 移位单负责业务语义
- `stock.picking` 负责表达库内内部移动执行主单

### 14.2 移位单明细与 `stock.move`

当前建议：

- 移位单明细与 `stock.move` 建立主关联

推荐字段口径：

- 在 `stock.move` 上扩：
  - `wms_relocation_line_id = fields.Many2one('logistics.wms.relocation.line')`
- 在移位单明细上反向：
  - `stock_move_ids = fields.One2many('stock.move', 'wms_relocation_line_id')`

这里建议继续保持和入库单、出库单一致：

- 业务明细承接业务语义
- `stock.move` 承接商品级移动计划 / 执行骨架

### 14.3 执行记录与 `stock.move.line`

当前建议：

- 移位执行记录与 `stock.move.line` 建立执行粒度关联

如果后续为移位执行记录单独建模，更推荐：

- 在 `stock.move.line` 上扩对应执行记录的 `Many2one`
- 在执行记录上反向 `One2many`

当前一期如果还没有把移位执行记录做得很重，也建议至少保持：

- 真实执行数量
- 来源位 / 目标位
- 实际移动事实

都以 `stock.move.line` 为准。

### 14.4 当前推荐的一句话字段级关联口径

当前更推荐统一成：

- 主单 -> `stock.picking`
- 明细 -> `stock.move`
- 执行事实 -> `stock.move.line`

也就是说：

`移位单负责表达业务主线，stock 原生对象负责表达库内真实移动事实；二者必须双向可追溯，但不重复维护两套执行真相。`

## 15. 移位单 search / filter / group by 的最终口径

当前更推荐把移位单的搜索口径，收成“关键字搜索轻量、筛选围绕状态与归属、分组围绕管理视角”的统一方式。

### 15.1 search 的当前推荐口径

当前建议移位单列表页和搜索视图中的关键字搜索，优先支持以下字段：

- `name`
- `warehouse_id`
- `owner_id`
- `source_location_id`
- `dest_location_id`

如果后续移位单关联更多业务对象，再逐步补充，不建议一期一开始就把搜索口子开得很散。

当前更推荐：

- 把关键字搜索重点放在“单号 + 仓库 + 货主 + 来源位 + 目标位”
- 不把大量低频备注字段混进默认关键字搜索

### 15.2 filter 的当前推荐口径

当前建议一期列表页最小筛选先保留以下几类：

- 主状态
- 仓库
- 货主
- 时间范围

在此基础上，移位单可补一个最关键的单据差异化筛选：

- 来源位 / 目标位

如果页面空间有限，当前更推荐先做：

- 来源位
- 目标位

作为两个独立可选筛选，而不是一开始做很复杂的区域组合筛选。

### 15.3 group by 的当前推荐口径

当前建议一期分组先围绕管理视角来做，不围绕复杂执行策略来做。

当前更推荐的分组为：

- 按主状态分组
- 按仓库分组
- 按货主分组
- 按来源位分组
- 按目标位分组

这里建议保持和前面几类主单一致：

- 分组先服务“看单、管单、找问题”
- 不急着服务复杂调度优化

### 15.4 当前推荐的一句话搜索口径

`移位单一期 search / filter / group by 先围绕单号、归属、来源位、目标位和主状态收口，不做复杂执行策略型搜索体系。`

## 16. v0.1 收口与后续补充方向

本文件当前已作为移位单状态机专题的 `v0.1` 基线稿。

本版已经固定的重点包括：

- 一期 5 个主状态
- 普通取消边界
- 执行失败时主状态停在 `executing`
- 一期不加“部分完成”主状态
- done 后通过新单或调整流程修正，不回退原单
- 详情页保留轻量异常信息区
- 详情页按钮先按“主按钮 / 次级入口 / 更多菜单”三层收口，并与主状态推进保持一致
- 主状态、执行记录与 `stock` 执行事实的联动口径已固定
- 列表页 / 详情页的状态展示口径已固定
- 主单字段、状态字段与轻量异常字段的落表方式已固定
- 主单 / 明细 / 执行事实与 `stock` 原生对象的字段级关联已固定
- search / filter / group by 的当前推荐口径已固定

后续建议继续补充：

- 目录索引与章节总览的正式收口
