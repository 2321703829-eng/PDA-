# 仓管设计启动讨论稿

## 1. 文档定位

这份文档用于承接仓管模块的第一轮设计讨论。

它的目标不是直接定稿字段和流程，而是先回答 3 个问题：

1. 仓管模块有哪些核心组成部分
2. 哪些能力适合复用 Odoo 原生
3. 哪些能力需要在 Odoo 底座之上扩展，或单独自定义

当前口径：

- 这是`讨论稿`
- 可用于后续“先讨论，再确定，后写入”的确定阶段
- 还不是最终规格说明或开发定稿

## 2. 当前资料能支撑到哪里

基于目前已读的会议纪要、截图和 Excel 模板，我们已经可以开始做：

- 模块边界讨论
- 对象分层讨论
- Odoo 原生复用判断
- 一期范围初步收口

但暂时还不适合直接定稿：

- 完整底表
- 全量状态机
- 全量接口契约
- 全量字段必填规则

## 3. 仓管模块的主要组成部分

### 3.1 主数据与基础档案

这部分负责仓管模块的“基础底座”，决定系统里有哪些主体和对象可以被业务单据引用。

当前主要包括：

- 货主
- 仓库
- 货位
- 商品
- 条码
- 员工
- 物流公司

### 3.2 入库管理

这部分负责货物从外部进入仓库时的业务承接。

它通常包含：

- 入库通知或来源单据
- 实际收货
- 上架
- 回传客户或外部系统

### 3.3 库存管理

这部分负责记录“现在仓里有什么货、在哪、多少、是什么状态”。

它通常包含：

- 库存现状
- 库存明细
- 货位库存
- 批次库存
- 冻结与可用量

### 3.4 出库管理

这部分负责从接单到配货、发货、物流回传的完整出库过程。

它通常包含：

- 出库单
- 配货/拣货
- 包装/装箱
- 发货确认
- 物流单号与回传

### 3.5 盘点与库内作业

这部分负责仓内调整类动作，不一定高频，但决定库存是否长期准确。

它通常包含：

- 盘点
- 移位
- 调拨
- 正残转换
- SN 管理

### 3.6 接口与回传

这部分负责系统与外部 ERP、平台、快递或客户系统的协作。

它通常包含：

- 单据导入
- WMS 单号回传
- 状态回传
- 物流信息回传
- 包裹信息回传

### 3.7 统计与报表

这部分负责管理层和业务层的查看口径，不直接产生库存事实，但会影响运营效率和客户体验。

它通常包含：

- 库存查询
- 发货汇总
- 接单统计
- 客户维度查询
- 异常或超时统计

### 3.8 设置与规则

这部分负责规则配置和全局参数，是系统长期稳定运行的约束层。

它通常包含：

- 编码规则
- 权限角色
- 业务开关
- 搜索和表头配置
- 自定义属性

## 4. Odoo 原生复用的总体原则

建议把 Odoo 的角色理解为：

`仓储底座 + 标准库存事实层 + 通用协同能力`

而你们的仓管模块要负责的是：

`面向多客户、多货主、WMS 回传和业务场景的扩展层`

因此不建议直接拿 Odoo 原生对象去硬等同你们的完整 WMS 业务模型。

## 5. 直接复用 Odoo 原生的能力

这部分是 Odoo 已经有成熟底座、并且和仓储语义天然接近的能力，优先直接复用。

| 部分 | Odoo 原生对象/能力 | 简要介绍 |
|---|---|---|
| 商品/SKU 底座 | `product.template`、`product.product` | 用于承接商品基础信息、规格和具体 SKU，是仓储商品资料的自然底座。 |
| 计量单位 | `uom.uom` | 用于统一件、箱、包等计量关系，避免各模块自行维护单位规则。 |
| 仓库/货位 | `stock.warehouse`、`stock.location` | 用于承接仓库结构、货位层级和库内位置关系。 |
| 库存现状 | `stock.quant` | 用于记录某商品在某位置上的当前库存数量，是库存查询的核心事实表。 |
| 库存执行明细 | `stock.move`、`stock.move.line` | 用于记录货物移动、收发和明细执行过程。 |
| 标准仓储动作 | `stock.picking` | 可承接入库、出库、调拨等标准作业的执行骨架。 |
| 批次/序列/效期 | `stock.lot` | 适合承接批次号、序列号、生产日期、有效期等追踪字段。 |
| 盘点调整 | Odoo 原生盘点/调整能力 | 适合做库存差异修正和盘点落账。 |
| 基础伙伴档案 | `res.partner` | 可作为客户、供应商、承运商等外部主体的底座。 |
| 员工/用户/权限组 | `hr.employee`、`res.users`、`res.groups` | 可用于人员档案、登录账号和权限分配。 |
| 协同与轻量附件 | `mail.thread`、`mail.activity`、`ir.attachment` | 可承接消息、活动、轻量日志和少量附件。 |

## 6. 适合“原生复用 + 业务扩展”的能力

这部分说明 Odoo 能做底座，但还不足以直接表达你们当前的业务口径，需要在原生对象上扩字段、扩关系或加业务规则。

| 部分 | 建议方式 | 简要介绍 |
|---|---|---|
| 货主 | 基于`res.partner`扩展 | 货主不是普通客户概念，除了基础档案，还涉及仓库授权、回传、结算口径和业务开关。 |
| 商品资料 | 基于`product`扩展 | 你们现有 Excel 里的`商家编码`、`箱规`、多组`自定义属性`更像 WMS 业务字段，建议挂在商品扩展层。 |
| 仓库结构 | 基于`stock.warehouse/location`扩展 | 原生可承接仓和位，但货区、货位分组、冻结、容量、客户可见口径需要增强。 |
| 入库/出库业务单 | 基于`stock.picking`重扩展或包业务层 | 原生适合做执行骨架，但`WMS 单号`、`原始单号`、`平台单号`、`客户回传号`通常需要更强业务层。 |
| 条码/PDA | 原生能力 + 自定义流程 | Odoo 可承接条码基础，但 PDA 扫描、打印和现场交互往往需要更贴业务的改造。 |
| 承运商/物流公司 | 基于`res.partner`扩展 | 原生伙伴可做主体档案，但物流路由、面单、运单回传仍需业务层补充。 |
| 查询与表头配置 | 自定义前后端扩展 | 会议纪要里强调“表头跨场景使用”和“搜索界面可按人调整”，这明显是业务体验层能力。 |

## 7. 建议自定义承接的能力

这部分不建议直接硬套 Odoo 原生对象，应该视为你们自己的 WMS 业务能力。

| 部分 | 建议 | 简要介绍 |
|---|---|---|
| 货主体系 | 自定义业务语义层 | 货主不只是伙伴档案，还涉及仓储规则、授权关系和业务隔离。 |
| 虚拟货主 / 虚拟仓 | 自定义 | 截图和纪要里都提到了虚拟概念，这通常不是标准 Odoo 仓储语义。 |
| 商家编码 / WMS 编码 / 多条码规则 | 自定义 | 这是客户侧商品识别和仓内识别之间的映射层，需要明确独立规则。 |
| 外部 ERP / 平台回传 | 自定义接口层 | 包括创建单据、状态同步、物流回传、包裹回传等业务协作。 |
| 多客户隔离与授权 | 自定义业务规则层 | 涉及不同货主、不同仓、不同可见范围，不建议只靠原生权限粗放处理。 |
| 业务日志与纠纷材料 | 自定义，必要时接外部对象存储 | 纪要提到视频/图片方向，这类证据材料不宜只靠轻量附件。 |
| 接单统计、发货汇总、客户视角报表 | 自定义聚合层 | 这些更像管理视角和客户视角的数据产品，不是原生库存事实层。 |
| 业务状态机 | 自定义 | 入库、出库、回传、取消、异常等状态需要按你们业务口径设计。 |

## 8. 与当前资料的映射理解

基于本次已读资料，可以先得到下面的初步映射：

### 8.1 已经比较明确的部分

- 商品主数据
- 条码映射
- 货主概念
- 仓库/货位概念
- 库存详情
- 入库与出库都是主线能力
- 搜索和表头体验很重要

### 8.2 仍然偏弱的部分

- 入库单和出库单的完整底表
- 单据状态流转
- 客户接口和回传字段
- 盘点、移位、SN 的详细规则
- 权限边界
- 异常与纠纷处理口径

## 9. 当前结论

现阶段最合理的设计判断是：

1. Odoo 原生足够做仓管模块底座
2. 但不能直接把原生对象当成完整 WMS 业务模型
3. 仓管模块应建立在`product / stock / partner / user`之上
4. 在其上补足`货主化、多客户化、WMS 化、回传化`的业务扩展层

## 11. 当前技术架构讨论结论

基于当前仓库现实和本轮讨论，仓管模块的技术架构建议先明确为：

`Odoo 单体主系统 + 模块化业务分层 + 少量外围增强服务`

它的核心含义是：

- 不单独再起一套独立 WMS 系统
- 不一开始就拆成多微服务
- 继续以 Odoo 和 PostgreSQL 作为主系统底座
- 仓管能力通过自定义 addon 集成进当前主系统

当前推荐理解的技术层次包括：

### 11.1 基础平台层

这一层由 Odoo 和 PostgreSQL 提供基础运行能力。

它负责：

- ORM
- 权限
- 菜单与视图
- 附件与活动
- 模块安装与升级

### 11.2 原生仓储底座层

这一层主要复用 Odoo 原生对象和库存事实能力。

它负责：

- 商品
- 单位
- 仓库
- 货位
- 库存
- 库存移动
- 批次/序列/效期

### 11.3 仓管业务模块层

这一层承接你们自己的 WMS 业务语义。

它负责：

- 货主
- 商家编码
- 入库/出库业务单据
- 客户回传
- 多场景搜索
- 仓库现场作业口径

### 11.4 外围增强层

这一层不是一开始就要很重，但应该从架构上预留。

它主要包括：

- 异步任务
- 批量导入
- 回传重试
- 对象存储
- 日志审计

## 12. 单租户先落地、后续扩展多租户

本轮讨论已达成的技术口径是：

`先把单租户做好，但从第一天就按未来可扩展为多租户来约束设计。`

这个结论的重点不在“先单租户”，而在：

- 现在按单租户交付
- 但设计时不能写死成永远只能单租户

### 12.1 为什么先单租户更合适

当前项目最现实的目标仍然是先把仓管能力落地，而不是先做完整的平台控制面。

如果一开始就直接进入平台级多租户，会明显增加：

- 平台库设计
- 租户开通流程
- 域名与数据库路由
- 备份恢复编排
- 租户级升级和监控

这些内容的工程复杂度高于当前仓管一期本身。

### 12.2 后续多租户的目标架构

虽然一期先单租户，但未来目标架构应继续保持为：

- 企业之间隔离优先靠数据库
- 企业内部多法人协同才使用 `multi-company`

也就是说，未来如果进入真正多租户阶段，更推荐的是：

`1 个平台层 + N 个租户数据库 + 1 套 Odoo 服务`

### 12.3 当前设计必须提前遵守的约束

为了避免后续返工，当前单租户设计应尽量避免：

- 写死数据库名
- 写死域名
- 写死对象存储路径
- 写死只能有一个企业主体的业务假设
- 写死必须人工干预数据库生命周期

## 13. 仓管与物流模块的关系

本轮讨论已明确：

`仓管模块和物流模块是并列模块，不是从属关系。`

这意味着：

- 物流继续承接现有执行与留痕主线
- 仓管承接仓储、库存、出入库与库内作业主线
- 二者共享基础层和部分通用能力

### 13.1 为什么应做并列模块

这样做的好处是：

- 边界更清晰
- 后续可独立迭代
- 更适合并行开发
- 不会把仓管逻辑过度塞进物流模块

### 13.2 哪些能力适合共享

目前已明确适合共享或统一口径的部分包括：

- 基础扩展层
- 商品与伙伴底座
- 仓库与货位底座
- 留痕证据技术路线
- 异步任务能力
- 通用配置和字典

## 14. 仓管与物流的库存事实关系

本轮讨论已明确不建议仓管再另造一套独立库存事实内核。

更稳妥的路线是：

`复用 Odoo stock 作为库存事实和执行内核，在其上扩展仓管业务层。`

### 14.1 这样做的主要原因

如果仓管自己再做一套库存事实层，会带来：

- 库存真相出现两份
- 物流和仓管联查路径变长
- 异常排查更困难
- 后续同步和对账成本升高

### 14.2 复用 stock 并不等于照搬原生页面

复用 Odoo stock 的重点在于：

- 复用库存真相
- 复用货物移动真相
- 复用批次、货位、库存调整等底层能力

但不代表：

- 必须完全照搬原生仓储页面
- 必须放弃本土化 WMS 业务语义
- 必须直接修改官方模块逻辑

更推荐的方式是：

- 原生 stock 承接事实层
- 自定义 addon 承接业务层

## 15. 图片和视频存储口径

本轮讨论已明确：

`图片和视频的存储策略应参照物流留痕功能的技术方向来设计。`

当前建议口径是：

- Odoo 存业务关系、元数据和状态
- 图片/视频二进制走外部对象存储
- Odoo 中只保留访问 key、类型、大小、上传人、上传时间和关联对象

### 15.1 为什么要沿用这条路线

这样做的好处是：

- 与物流留痕技术口径统一
- 避免大附件长期压在 Odoo 默认附件体系上
- 更适合后续扩多租户和对象存储命名空间隔离

### 15.2 仓管场景下的主要挂点

仓管模块中的证据材料，后续主要可能挂在：

- 入库收货
- 上架
- 盘点
- 移位
- 拣货
- 复核
- 装箱
- 发货

也就是说，存储策略可以共享，但业务挂点需要按仓管场景扩展。

## 16. 同步与异步的实现口径

本轮讨论已明确不建议把所有动作都做成同步，也不建议把所有流程都做成异步。

更合理的实现口径是：

`本地提交和轻量校验优先同步，外部联动和重处理优先异步。`

### 16.1 适合同步的动作

这类动作通常需要即时结果，且链路短、依赖少。

例如：

- 基础查询
- 表单保存
- 轻量校验
- 小范围对象创建

### 16.2 适合异步的动作

这类动作通常链路长、依赖外部系统、容易失败或需要重试。

例如：

- 批量导入
- 客户系统回传
- 物流状态同步
- 图片/视频处理
- 大批量通知

### 16.3 发货回传场景的建议动作链

后续更推荐的发货回传方式是：

1. 仓库本地先确认发货
2. 系统将本地状态更新为“已发货待回传”
3. 系统生成回传任务
4. 页面立即返回本地发货成功
5. 后台任务异步调用客户或平台接口
6. 成功后更新为“已回传”
7. 失败后更新为“回传失败”并支持重试

这种方式比“前台点一次按钮就同步把所有外部系统都调完”更适合仓库现场。

## 17. PDA 的技术判断

本轮讨论已明确：

`PDA 对真正的仓管模块很重要，但不一定要求在 P0 就全量落地。`

### 17.1 为什么 PDA 很重要

仓库现场很多动作天然更适合扫码终端而不是 PC：

- 收货
- 上架
- 拣货
- 复核
- 移位
- 盘点
- 扫码核对条码/SN/批次

如果完全没有 PDA 或移动扫码端，往往会出现：

- 现场动作和系统录入分离
- 条码和货位价值发挥不出来
- 账实一致性更难保证

### 17.2 为什么又不一定必须 P0 全量上线

PDA 一旦进入范围，会连带影响：

- 前端交互
- 条码规则
- 扫码流程
- 网络要求
- 终端选型

所以当前更合理的口径是：

- 架构上从第一天就按未来支持 PDA 设计
- 但交付节奏可以分阶段推进

## 18. 物流与仓管并行开发的影响与规避

本轮讨论已明确：

`物流模块优化与仓管模块一期开发可以并行进行，但共享层改动会相互影响。`

### 18.1 容易互相影响的部分

并行开发时，风险主要集中在以下共享区域：

- 基础扩展层
- 商品、伙伴、仓库、货位等共享主数据
- 公共前端资产
- 留痕证据能力
- 异步任务与回传能力
- 对 Odoo 原生模型的扩展

### 18.2 可能出现的具体问题

主要包括：

- 字段口径冲突
- 视图继承冲突
- 状态定义冲突
- 回传和任务口径冲突
- 升级联调相互影响

### 18.3 建议的规避方式

后续并行开发时，建议明确遵守：

1. 共享层少改，并单独管控
2. 业务模块尽量各自独立新增，不相互侵入
3. 共享对象先定契约，再开发
4. 前端资产尽量分模块放置
5. 联动尽量走明确接口，不走隐式耦合
6. 涉及共享层的改动先写文档，再实施

## 19. 当前阶段的综合结论

截至本轮讨论，仓管模块的技术口径可先收敛为：

1. 架构先走模块化单体，不另起独立 WMS 系统
2. 一期先交付单租户，但从设计上预留未来多租户扩展
3. 企业级隔离的长期目标仍是数据库级隔离
4. 仓管和物流是并列模块，而不是互相从属
5. 库存事实层优先复用 Odoo stock
6. 图片与视频存储参照物流留痕路线
7. 同步与异步采用混合策略
8. PDA 要作为架构前提考虑，但交付可分期
9. 物流优化和仓管开发可以并行，但共享层要收口治理

## 23. 当前拆分方案的理解口径

为了避免后续实现时边界漂移，当前拆分方案应按如下方式理解：

- `logistics_wms_base` 负责仓管公共业务基础，不直接承接完整入库或出库流程
- `logistics_wms_inbound / inventory / outbound` 是仓管业务主线模块
- `logistics_wms_integration` 负责外部系统协作，不直接承接库存事实真相
- `logistics_wms_web` 负责仓管前端体验增强，不应把核心业务逻辑堆进前端层
- 共享层与仓管层之间应尽量通过清晰模型和能力边界协作，而不是相互侵入

## 25. 按对象划分的模块归属结论

本轮讨论已进一步按对象确认仓管模块内部的业务归属。

这里的“归属”指的是：

- 哪个模块负责该对象的业务语义和设计口径
- 不等于底层必须完全新建独立模型
- 底层仍可优先复用 Odoo 原生对象

## 26. 当前已确认的对象归属

| 对象 | 归属层 | 归属模块 | 当前说明 |
|---|---|---|---|
| 货主 | 仓管基础层 | `logistics_wms_base` | 货主是仓管域核心主数据，会被入库、库存、出库多处复用，底座建议基于 `res.partner` 扩展。 |
| 商品扩展 | 仓管基础层 | `logistics_wms_base` | 原生底座仍是 `product`，但商家编码、箱规、自定义属性等仓管语义字段应统一放在仓管基础层。 |
| 仓库 | 仓管基础层 | `logistics_wms_base` | 原生底座建议继续复用 `stock.warehouse`，仓管侧授权和业务配置由 `wms_base` 负责。 |
| 货位 | 仓管基础层 | `logistics_wms_base` | 原生底座建议继续复用 `stock.location`，货位编码、货区、分组、容量和冻结口径由 `wms_base` 负责。 |
| 条码 | 仓管基础层 | `logistics_wms_base` | 条码规则同时服务入库、库存、出库和 PDA，适合统一放在仓管基础层。 |
| 批次 | 库存主线层 | `logistics_wms_inventory` | 底层可复用 `stock.lot`，但业务上与库存、效期、盘点和库内作业关系最紧。 |
| 库存详情 | 库存主线层 | `logistics_wms_inventory` | 这是库存模块的核心对象和核心查询口径。 |
| 盘点 | 库存主线层 | `logistics_wms_inventory` | 属于典型库内库存作业，应由库存模块承接。 |
| 移位 | 库存主线层 | `logistics_wms_inventory` | 本质是库内位置调整动作，建议归库存模块。 |
| 出库单 | 出库主线层 | `logistics_wms_outbound` | 出库单、拣货、复核、装箱、发货应作为一条完整业务主线归 `outbound`。 |
| 发货回传 | 集成层 | `logistics_wms_integration` | 本地发货动作归 `outbound`，对外 ERP/客户/物流回传归 `integration`。 |

## 27. 当前归属结论的理解口径

为了避免实现时出现边界混淆，当前这组对象归属需要按以下方式理解：

### 27.1 业务归属不等于底层模型必须新建

例如：

- 仓库和货位的业务归属在 `logistics_wms_base`
- 但底层仍建议复用 `stock.warehouse`、`stock.location`

同理：

- 批次的业务归属在 `logistics_wms_inventory`
- 但底层仍建议优先复用 `stock.lot`

### 27.2 发货与发货回传必须拆开看

这两者虽然连续发生，但不是同一个模块职责：

- 本地发货是仓库现场业务动作，归 `logistics_wms_outbound`
- 发货后的客户/ERP/物流系统回传是外部系统协作，归 `logistics_wms_integration`

### 27.3 基础主数据优先收口在 `logistics_wms_base`

后续如果不先把基础主数据收口好，入库、库存、出库三个主线模块很容易出现：

- 各自定义字段
- 各自定义规则
- 口径不一致

因此，当前已确认：

- 货主
- 商品扩展
- 仓库
- 货位
- 条码

应优先由 `logistics_wms_base` 统一承接。

## 38. 一期数据库搭建结论

本轮讨论已明确，仓管模块的一期数据库搭建应优先遵守“单租户、单业务库、同库联动”的原则。

当前更推荐的一期数据库形态是：

- `1` 个 PostgreSQL 实例
- `1` 个 Odoo 业务数据库
- 在同一个业务库中同时安装：
  - 现有物流模块
  - 后续仓管模块

也就是说，当前阶段的数据库口径是：

`一个租户 = 一个 Odoo 业务库 = 物流 + 仓管一起跑`

### 38.1 为什么一期先这样搭建

这样做的主要原因是：

- 物流和仓管天然可联查
- 不需要跨库同步库存和单据
- 开发和联调复杂度最低
- 后续扩展多租户时，可以把这一整套业务库作为标准租户单元复制

### 38.2 当前不建议的数据库形态

当前不建议做成：

- 物流一个业务库
- 仓管另一个业务库

因为这样会带来：

- 库存跨库
- 单据跨库
- 回传跨库
- 联查和对账都明显变复杂

## 39. 后续多租户的数据库方向

虽然一期先单租户单业务库，但长期目标仍然保持为：

- 平台层单独库
- 每个客户一个业务库
- 每个业务库中同时安装物流模块和仓管模块

也就是说，后续更推荐的多租户方向仍然是：

`1 个平台层 + N 个租户业务库 + 1 套 Odoo 服务`

这里需要继续保持两个边界：

- 企业之间隔离优先靠数据库
- 企业内部多法人协同才使用 `multi-company`

## 40. 当前数据库设计原则

基于本轮讨论，仓管模块在数据库设计上应优先遵守以下原则：

### 40.1 所有业务数据进入 Odoo 主业务库

包括：

- 主数据
- 入库
- 库存
- 出库
- 回传任务
- 日志元数据

当前不建议再单独维护一套并行的外部业务数据库。

### 40.2 图片和视频不直接进入业务库

数据库中只保留：

- 关联对象
- 文件 key
- 文件类型
- 文件大小
- 上传时间
- 上传人
- 状态

真正的二进制文件走对象存储或外部文件存储。

### 40.3 库存事实只保留一套真相

当前更推荐建立在以下 Odoo 原生能力之上：

- `stock.quant`
- `stock.move`
- `stock.move.line`
- `stock.lot`

当前不建议仓管再独立维护一套并行库存主表。

### 40.4 自定义数据优先走 Odoo ORM 模型

也就是：

- 先定义模型
- 再由 Odoo 生成表
- 业务对象优先通过 ORM 管理

不建议优先手工造 SQL 表作为业务主路径。

### 40.5 现在按单租户交付，但按未来多租户约束设计

虽然一期是单库单租户，但当前仍应避免：

- 写死数据库名
- 写死路径
- 写死单企业假设
- 写死附件命名规则

### 40.6 备份恢复必须按“数据库 + 文件存储”成对设计

尤其考虑到后续存在图片和视频材料，后续恢复不能只恢复数据库而忽略对象存储或文件存储。

## 41. 物流模块的对象实现模式参考

为了指导仓管模块的数据库设计，本轮还复盘了现有物流模块的对象实现方式。

当前物流模块采用的不是“全部建立在 Odoo 原生业务对象上”，而是：

`少量扩展 Odoo 原生主数据对象 + 大量新建物流业务对象`

### 41.1 已确认的原生扩展对象

当前已明确扩展了以下 Odoo 原生对象：

- `res.partner`
  - 承接物流客户、门店、编码、等级、状态等扩展信息
- `hr.employee`
  - 承接物流角色、默认仓库、员工编号等扩展信息
- `stock.warehouse`
  - 承接仓库联系人、联系电话、状态备注和作业备注等扩展信息

### 41.2 已确认的新建物流业务对象

物流主线的大部分核心对象都是新建模型承接，例如：

- `logistics.dispatch.wave`
- `logistics.dispatch.batch`
- `logistics.dispatch.waybill`
- `logistics.dispatch.waybill.order.line`
- `logistics.dispatch.waybill.customer.line`
- `logistics.dispatch.waybill.customer.goods.line`
- `logistics.trace.event`
- `logistics.trace.evidence`
- `logistics.trace.exception`
- `logistics.trace.exception.process.log`

### 41.3 这对仓管模块的参考意义

这说明当前项目已经形成了一条比较清晰的实现口径：

- 基础主数据层可以扩展 Odoo 原生对象
- 业务主线层不一定要硬套原生业务对象
- 如果业务语义已经明显超出原生对象表达能力，则更适合新建业务模型承接

## 42. 基于当前数据库结论的下一步建议

在补充数据库搭建结论和物流实现模式参考后，下一步更适合继续讨论的是：

`仓管里哪些对象应像物流一样扩原生，哪些对象应像物流主线一样新建业务模型。`

## 43. 仓管对象的模型实现策略讨论结论

本轮讨论已进一步确认，仓管对象在数据库层应继续沿用当前项目已经形成的实现口径：

`基础主数据优先扩原生，仓管主线对象优先新建业务模型。`

## 44. 适合优先扩原生的仓管对象

以下对象更适合建立在 Odoo 原生主数据或库存底座之上扩展：

### 44.1 货主

建议基于 `res.partner` 扩展。

原因是：

- 本质仍然是外部业务主体
- 只是需要补充仓管语义、授权和业务字段

### 44.2 商品扩展

建议基于 `product.template / product.product` 扩展。

原因是：

- SKU 底座需要和其他模块共享
- 仓管主要是在其上补商家编码、箱规、自定义属性等业务字段

### 44.3 仓库

建议基于 `stock.warehouse` 扩展。

原因是：

- 仓库底座原生已具备
- 仓管主要补业务配置和授权口径

### 44.4 货位

建议基于 `stock.location` 扩展。

原因是：

- 货位本身就是典型原生库存位置对象
- 仓管只是在其上补货区、分组、编码、容量和业务口径

### 44.5 条码

条码建议优先挂在商品扩展层，必要时补一层“商品条码映射”模型。

原因是：

- 单一主条码可走商品扩展
- 多条码、客户条码、业务条码映射更适合单独建映射对象

### 44.6 批次

建议基于 `stock.lot` 扩展。

原因是：

- 批次、效期、追踪本来就是 Odoo 原生能力

### 44.7 库存详情

当前不建议新建并行库存主表。

建议基于以下原生对象形成查询口径：

- `stock.quant`
- `stock.move`
- `stock.move.line`
- `stock.lot`

库存详情更适合做成：

- SQL view
- 报表模型
- 查询服务层

而不是新的库存真相表。

## 45. 适合新建业务模型的仓管对象

以下对象更适合像物流主线一样，由仓管模块自己新建业务模型承接：

### 45.1 入库主线对象

- 入库单
- 入库单明细
- 收货记录
- 上架记录

### 45.2 库内作业对象

- 盘点单
- 盘点单明细
- 移位单
- 移位单明细

### 45.3 出库主线对象

- 出库单
- 出库单明细
- 拣货记录
- 复核记录
- 发货确认记录

### 45.4 集成与任务对象

- 导入任务
- 回传任务
- 回传日志
- 重试记录

## 46. 当前模型实现策略的核心口径

为了避免后续数据库设计走偏，当前应明确收口为：

- 不新建并行库存事实内核
- 但应新建仓管业务主线对象

更准确地说：

- `库存真相` 优先复用 Odoo 原生
- `仓管业务单据` 优先由 `logistics_wms_*` 新建模型承接

## 47. 仓管业务模型与 Odoo stock 的关联原则

本轮讨论已进一步确认，仓管新建业务模型和 Odoo 原生 `stock` 的关系，应统一按以下原则理解：

### 47.1 仓管单据负责业务语义，stock 负责执行事实

- 仓管单据回答“为什么做这件事、业务现在到哪一步了”
- `stock.picking / stock.move / stock.move.line / stock.quant` 回答“货实际上怎么动了”

### 47.2 仓管单据不替代 stock，但必须能反查到 stock

任何入库单、出库单、移位单、盘点单，都应能反查到对应的执行对象。

### 47.3 stock 侧也要能反查回业务单据

现场如果从原生仓储对象进入，也应能知道它属于哪个仓管业务单据。

### 47.4 库存结果尽量从 stock 派生，不重复维护两套真相

尤其是：

- 数量
- 批次
- 货位
- 可用库存

尽量不在仓管业务表里重复维护一套主值。

## 48. 各业务模型与 stock 的当前建议关联

### 48.1 入库单与 stock 的关联

`logistics_wms_inbound` 建议关联到：

- `stock.picking`
- 必要时 `stock.picking.type`

当前更推荐的理解是：

- 入库单作为业务主单
- 实际收货执行由一个或多个 `stock.picking` 承接

### 48.2 入库单明细与 stock 的关联

`logistics_wms_inbound_line` 建议关联到：

- `stock.move`
- 必要时 `stock.move.line`

当前更推荐：

- 行级主关联优先落在 `stock.move`
- 更细的执行明细由 `stock.move.line` 承接

### 48.3 收货记录与 stock 的关联

收货记录更贴近：

- `stock.move.line`

因为它天然涉及：

- 某商品
- 某批次
- 某数量
- 某收货位或暂存位

### 48.4 上架记录与 stock 的关联

上架记录建议关联到：

- 内部调拨类型的 `stock.picking`
- `stock.move`
- `stock.move.line`

当前更推荐把上架理解为：

- 从收货位或暂存位移动到正式货位
- 本质属于仓内内部移动

### 48.5 库存详情与 stock 的关联

库存详情不建议做实体主表，而应建立在：

- `stock.quant`
- `stock.move`
- `stock.move.line`
- `stock.lot`

之上形成查询口径。

### 48.6 盘点单与 stock 的关联

盘点单建议关联到：

- `stock.quant`
- 盘点完成后形成的库存调整结果

当前更推荐的理解是：

- 盘点单记录一次盘点业务行为
- 真正库存修正仍回到 Odoo 原生库存调整机制

### 48.7 移位单与 stock 的关联

移位单建议关联到：

- 内部 `stock.picking`
- `stock.move`
- `stock.move.line`

当前更推荐把移位理解为：

- 库内内部调拨
- 主业务语义在移位单
- 实际货位移动由原生执行对象承接

### 48.8 出库单与 stock 的关联

`logistics_wms_outbound` 建议关联到：

- `stock.picking`
- 必要时 `stock.picking.type`

当前更推荐：

- 出库单承接业务主语义
- 一个或多个 `stock.picking` 承接实际发货执行

### 48.9 出库单明细与 stock 的关联

`logistics_wms_outbound_line` 建议关联到：

- `stock.move`
- 必要时 `stock.move.line`

当前更推荐：

- 商品级移动计划落在 `stock.move`
- 批次、货位、实拣数量等明细落在 `stock.move.line`

### 48.10 拣货记录与 stock 的关联

拣货记录更贴近：

- `stock.move.line`

因为拣货动作天然发生在：

- 货位
- 批次
- 数量
- 操作人

这个粒度上。

### 48.11 复核记录与 stock 的关联

复核记录建议关联到：

- `stock.picking`
- `stock.move.line`

当前更推荐：

- 主记录挂整单或整次出库执行
- 明细核对仍回到 `move line` 粒度

### 48.12 发货确认记录与 stock 的关联

发货确认记录建议关联到：

- `stock.picking`

因为它最贴近“这一票出库执行完成”的语义。

### 48.13 回传任务与 stock 的关联

回传任务建议主关联到：

- 仓管业务单据

并辅助保留：

- 对应 `stock.picking`

这样既能保留业务语义，也能引用实际执行结果。

## 49. 当前建议保留的最小双向反查口径

为了保证后续从仓管单据和 stock 执行对象都能顺利互查，当前建议至少保留下列双向关系口径：

### 49.1 业务模型侧

- `inbound.receipt_picking_ids`
- `inbound.putaway_picking_ids`
- `inbound_line.stock_move_ids`
- `outbound.delivery_picking_ids`
- `outbound_line.stock_move_ids`
- `pick.stock_move_line_ids`
- `relocation.internal_picking_id`

### 49.2 stock 扩展侧

- `stock.picking.wms_inbound_id`
- `stock.picking.wms_outbound_id`
- `stock.picking.wms_relocation_id`
- `stock.move.wms_inbound_line_id`
- `stock.move.wms_outbound_line_id`

## 50. 当前阶段的关联设计结论

截至本轮讨论，仓管与 stock 的关系可先收敛为一句话：

`仓管单据负责业务主线，stock 对象负责仓内执行和库存事实；二者必须双向可追溯。`

## 51. 基于当前结论的下一步建议

在确认仓管业务模型与 stock 的关联方向后，下一步更适合继续讨论的是：

`这些关联里，哪些是一对一，哪些必须从一开始就按一对多设计。`

## 52. 关联基数的总体设计原则

本轮讨论已进一步确认，仓管业务模型与 Odoo `stock` 之间的关联基数，应优先遵守以下原则：

### 52.1 核心业务关联优先使用 Many2one + One2many

当前更推荐：

- 子对象或执行对象上放 `Many2one`
- 主业务对象上通过 `One2many` 反查

这样做的好处是：

- 更符合“一个执行对象有唯一业务归属”的设计
- 更利于审计、追溯和状态控制
- 也更适合后续继续扩展

### 52.2 不轻易把核心业务链路做成 Many2many

当前不建议在仓管核心链路中优先使用 `Many2many`。

原因是：

- 容易把归属关系做模糊
- 后续审计、约束和状态机控制会更复杂

`Many2many` 更适合以下类型的关系：

- 标签
- 附件集合
- 关注人
- 没有唯一业务归属的松散关联

### 52.3 不轻易做真正的一对一

除非业务上几乎不可能拆分，否则当前不建议轻易做严格一对一。

原因是：

- 仓管现场很容易出现拆单、分批、补货、多次执行
- 一旦后续发生拆分，严格一对一最容易返工

## 53. 当前建议必须从一开始按一对多设计的关系

以下关系即便一期场景看起来比较简单，当前也建议直接按“一对多”设计：

### 53.1 入库主线

- 入库单 -> 收货 `stock.picking`
- 入库单 -> 上架 `stock.picking`
- 入库单明细 -> `stock.move`

原因主要包括：

- 可能分批到货
- 可能分批收货
- 可能分多次上架
- 一条业务明细也可能拆成多个执行对象

### 53.2 出库主线

- 出库单 -> delivery `stock.picking`
- 出库单明细 -> `stock.move`

原因主要包括：

- 可能部分发货
- 可能分仓发货
- 可能分批次、分货位执行

### 53.3 执行记录主线

- 拣货记录 -> `stock.move.line`
- 复核记录 -> `stock.move.line`

原因主要包括：

- 一次拣货或复核动作往往覆盖多条明细执行记录

### 53.4 回传任务主线

- 回传任务 -> 业务主单
- 回传任务 -> `stock.picking`

原因主要包括：

- 一个业务单据可能存在首次回传、重试回传、补偿回传

## 54. 当前建议按“单一主关联 + 可扩展反查”处理的关系

以下关系当前不建议做成严格一对一，但可以在业务上允许“一次操作通常对应一个主执行对象”：

### 54.1 移位单 -> internal picking

当前建议：

- 模型上保留一对多扩展余地
- 业务上允许大多数场景只生成一个主 `internal picking`

### 54.2 移位单明细 -> `stock.move`

当前建议：

- 先按一个明细通常对应一个主 `move` 去理解
- 但模型上仍保留拆分能力

### 54.3 发货确认记录 -> `stock.picking`

当前建议：

- 主方向按单条确认记录指向一个 `picking`
- 反查时可由 `picking` 看到多条确认或历史记录

## 55. 当前建议以 Many2one 为主的关系

以下关系当前更适合直接使用 `Many2one` 作为主方向：

### 55.1 盘点明细 -> `stock.quant`

建议：

- 每条盘点明细引用一个盘点时刻的目标库存口径

同时需要注意：

- 盘点明细更像对 `quant` 的引用或快照
- 不应把盘点明细本身当成实时库存真相

### 55.2 发货确认记录 -> `stock.picking`

建议：

- 发货确认记录用 `Many2one` 指向对应执行 `picking`

### 55.3 复核记录 -> `stock.picking`

建议：

- 在复核记录上补一个指向整票执行对象的 `Many2one`
- 明细核对仍回到 `move.line`

## 56. 各主要关系的字段类型建议

### 56.1 入库单 -> 收货 picking

建议：

- `stock.picking.wms_inbound_receipt_id = fields.Many2one('logistics.wms.inbound')`
- `logistics.wms.inbound.receipt_picking_ids = fields.One2many('stock.picking', 'wms_inbound_receipt_id')`

当前不建议：

- `Many2many`

### 56.6 盘点单 -> 盘点单明细

### 56.7 盘点明细 -> stock.quant

建议：

### 56.8 移位单 -> internal picking

建议：

### 56.10 出库单 -> delivery picking

建议：

- `stock.picking.wms_outbound_id = fields.Many2one('logistics.wms.outbound')`
- `logistics.wms.outbound.delivery_picking_ids = fields.One2many('stock.picking', 'wms_outbound_id')`

当前不建议：

- `Many2many`

### 56.11 出库单明细 -> stock.move

建议：

- `stock.move.wms_outbound_line_id = fields.Many2one('logistics.wms.outbound.line')`
- `logistics.wms.outbound.line.stock_move_ids = fields.One2many('stock.move', 'wms_outbound_line_id')`

## 57. 当前明确不建议优先使用 Many2many 的核心关系

本轮讨论已进一步确认，以下核心链路当前都不建议优先使用 `Many2many`：

- 入库单和 `picking`
- 出库单和 `picking`
- 入库/出库明细和 `move`
- 执行记录和 `move.line`

## 58. 当前阶段的字段设计结论

截至本轮讨论，字段类型层面可先收敛为：

- 核心归属链路优先 `Many2one + One2many`
- 单点引用关系优先 `Many2one`
- 仓管核心业务链路当前不建议优先使用 `Many2many`

## 59. 基于当前结论的下一步建议

在确认字段关系类型后，下一步更适合继续讨论的是：

`这些建议字段里，哪些必须放在 stock 扩展上，哪些只放在仓管模型上就够了。`

## 60. stock 原生对象的最小扩展集结论

本轮讨论已进一步确认，`stock.picking / stock.move / stock.move.line` 的扩展应尽量保持克制。

当前建议遵守的总原则是：

- `stock.picking` 负责反查业务主单
- `stock.move` 负责反查业务明细

## 68. 执行记录模型的一期落地结论

本轮讨论已进一步确认，一期不再把以下对象只视为“move.line + 日志”的轻量过渡能力，而是正式承认为完整模型：

- `putaway record`
- `pick record`
- `check record`

但当前同时明确：

`模型完整落地，不等于一期就把字段和流程做成很重的子系统。`

更推荐的一期口径是：

- 四个执行记录对象都正式建模

## 69. 四个执行记录模型的定位结论

### 69.1 receive record

定位为：

- 一次收货业务动作记录
- 记录谁在什么时间对哪张入库单完成了收货动作

它应重点关联：

- `inbound`
- `inbound line`
- `stock.move.line`

### 69.2 putaway record

定位为：

- 一次上架业务动作记录
- 记录从收货位或暂存位到正式货位的业务执行

它应重点关联：

- `inbound`
- `stock.picking`
- `stock.move`
- `stock.move.line`

### 69.3 pick record

定位为：

- 一次拣货业务动作记录
- 记录出库过程中的实际拣货行为

它应重点关联：

- `outbound`
- `outbound line`
- `stock.move.line`

### 69.4 check record

定位为：

- 一次复核业务动作记录
- 记录对出库执行结果的核对确认

它应重点关联：

- `outbound`
- `stock.picking`
- `stock.move.line`

## 70. 执行记录模型与 move.line 的边界

本轮讨论已进一步确认：

`执行记录模型是业务执行记录对象，stock.move.line 仍然是执行事实对象。`

也就是说：

- `record` 负责表达“谁在什么业务上下文里做了这次动作”
- `move.line` 负责表达“货实际上怎么动了”

当前不建议让执行记录模型自己维护一套并行库存真相。

## 71. 执行记录模型的一期结构结论

本轮讨论已进一步确认：

`一期这 4 个执行记录模型先不全部拆成“主表 + 明细表”两层结构，而是先以主表为主。`

更推荐的一期设计是：

- `receive record`：先做主表
- `putaway record`：先做主表
- `pick record`：先做主表
- `check record`：先做主表

执行明细则优先通过以下对象承接：

- `stock.move.line`
- 必要时 `stock.move`
- 必要时 `stock.picking`

### 71.1 为什么一期先不全部拆明细表

这样做的主要原因是：

- 模型数量不会过快膨胀
- 页面数量不会翻倍
- 状态机复杂度更可控
- 能避免“记录明细”和“执行明细”两套明细过早重复

### 71.2 后续什么时候再考虑升级为主表 + 明细表

只有当后续出现以下场景时，再考虑单独升级：

- 一次记录天然包含多组独立业务明细
- 业务明细和执行明细不再等价
- 需要复杂 PDA 流程
- 需要计划与实际差异比对
- 需要独立打印、审批或审核明细

2. 一期先只做主表，不急于拆独立明细表
3. 明细优先由 `stock.move.line` 承接
4. 四个主表先按最小必须字段收口
5. 业务输入字段优先存储，摘要统计优先计算

在确认执行记录模型的一期落法后，下一步更适合继续讨论的是：

`这 4 个记录主表的状态值到底怎么定，是否统一成 draft / in_progress / done / cancel，还是每个模型各自采用更贴业务的状态。`

## 76. 执行记录模型的状态设计结论

本轮讨论已进一步确认，一期当前不建议让四个执行记录模型各自发展出完全不同的状态机。

当前更推荐统一采用一套基础状态：

- `draft`
- `in_progress`
- `done`
- `cancel`

## 77. 为什么一期先统一状态

当前更推荐统一状态，主要因为：

1. 一期模型已经较多，如果四个执行记录模型都各自有独立状态体系，复杂度会明显上升。
2. 四个对象本质上都是“执行动作记录”，统一状态更有利于：
   - 权限控制
   - 页面筛选
   - 列表展示
   - 日志理解
3. 更细的业务差异，当前更适合先放在：
   - 主业务单据状态
   - `stock` 执行对象状态
   - 结果字段
   - 备注字段

## 78. 四个执行记录模型对统一状态的当前理解

### 78.1 receive record

- `draft`：收货记录已创建，但未正式开始收货
- `in_progress`：收货已开始，但尚未完成
- `done`：本次收货动作已完成
- `cancel`：本次收货记录已取消

### 78.2 putaway record

- `draft`：上架记录已创建
- `in_progress`：上架已开始
- `done`：本次上架动作已完成
- `cancel`：本次上架记录已取消

### 78.3 pick record

- `draft`：拣货记录已创建
- `in_progress`：拣货进行中
- `done`：本次拣货动作已完成
- `cancel`：本次拣货记录已取消

### 78.4 check record

- `draft`：复核记录已创建
- `in_progress`：复核进行中
- `done`：本次复核动作已完成
- `cancel`：本次复核记录已取消

## 79. 业务差异不优先靠状态枚举承载

本轮讨论已进一步确认，当前不建议通过不断增加状态枚举去表达所有业务差异。

更推荐的方式是：

- `state` 负责表达流程位置
- 业务结果差异由额外字段表达

例如：

- `check record` 当前建议额外保留 `check_result`
  - `pass`
  - `problem`

## 80. 当前阶段的状态设计结论

截至本轮讨论，执行记录模型的状态设计可先收敛为：

1. 四个执行记录模型统一采用：
   - `draft`
   - `in_progress`
   - `done`
   - `cancel`
2. 一期不再为每个执行记录模型单独设计复杂状态机
3. 更细的业务差异优先通过结果字段和关联执行事实表达

## 81. 基于当前结论的下一步建议

在确认执行记录模型的统一状态后，后续更适合继续讨论的是：

`这 4 个执行记录模型里，哪些允许手工创建，哪些必须由主业务单据自动生成。`

## 82. 执行记录模型的创建方式结论

本轮讨论已进一步确认，四个执行记录模型的一期创建方式应统一采用：

`自动生成为主，手工创建为辅。`

更准确地说：

- 默认应由主业务单据在关键动作节点自动生成执行记录
- 手工创建只能作为受控补录或特殊场景入口

## 83. 为什么整体上以自动生成为主

当前更推荐自动生成为主，主要因为：

1. 四个执行记录模型都不是孤立业务对象，而是挂在入库/出库主单之下的执行记录。
2. 它们都需要和 `stock.picking / stock.move / stock.move.line` 严格对应。
3. 如果允许大量裸手工创建，很容易出现：
   - 记录有了，但没有主单上下文
   - 记录有了，但没有对应执行对象
   - 记录和库存事实脱节
   - 后续审计和追溯说不清来源

## 84. 各执行记录模型的创建方式口径

### 84.1 receive record

当前建议：

- 自动生成为主
- 允许受控手工补录

这里的“允许补录”并不等于允许裸建，而应收紧为：

- 必须绑定 `inbound_id`
- 必须绑定仓库和货主
- 最终必须能落到对应 `move.line`
- 不允许完全脱离入库主单存在

### 84.2 putaway record

当前建议：

- 自动生成为主
- 允许受控手工补录

更推荐的补录方式是：

- 从入库单上下文发起
- 从待上架记录发起
- 从指定收货记录发起

当前不建议允许脱离业务上下文自由裸建。

### 84.3 pick record

当前建议：

- 自动生成为主
- 当前不建议开放裸手工创建

更推荐只允许以下方式进入：

- 从出库单发起
- 从待拣货任务发起
- 由系统根据出库执行自动生成

### 84.4 check record

当前建议：

- 自动生成为主
- 当前不建议开放裸手工创建

更推荐只允许以下方式进入：

- 从出库单发起
- 从执行单进入复核
- 从待复核列表发起

## 85. 当前“受控补录”的理解口径

本轮讨论已进一步确认，所谓允许手工创建，当前应收口为“允许在业务上下文中补录”，而不是开放成完全自由的新建菜单。

“受控补录”至少应满足：

- 必须从主业务单据或待执行上下文进入
- 自动带出仓库、货主、主单信息
- 必须绑定对应执行对象
- 必须受权限控制
- 必须记录其是补录还是正常生成

## 86. 当前阶段的创建方式结论

截至本轮讨论，四个执行记录模型的一期创建方式可先收敛为：

- `receive record`
  - 自动生成为主

## 88. 执行记录模型的自动生成节点结论

## 120. 当前不优先采用卡片列表与重型展开表格的原因

当前不优先采用任务卡片列表，主要因为：

- 卡片占用空间更大
- 不利于仓管高密度明细浏览
- 与物流模块现有后台主风格一致性较弱

当前不优先采用重型可展开表格，主要因为：

- 一期实现复杂度偏高
- 容易让左侧待处理区过重
- 会削弱右侧执行区作为主操作区的地位

因此，一期当前更推荐先把左侧待处理区收敛为：
`标准表格列表`

## 121. 基于当前结论的下一步建议

在确认左侧待处理区优先采用标准表格列表后，后续更适合继续讨论的是：
`左侧表格在四个执行页里是否统一列结构，还是每个页面各自定一组最小核心列。`

## 122. 左侧表格列结构的当前结论

本轮讨论已进一步确认，四个执行页左侧待处理表格不建议：

- 完全统一成一套毫无差异的列结构
- 也不建议四个页面完全各自独立设计一套列结构

当前更推荐的方案是：
`统一基础列骨架 + 各页面补充少量业务专属列`

这样既能保持与物流模块一致的清单节奏，也能兼顾收货、上架、拣货、复核四类动作的业务差异。

## 123. 左侧表格统一基础列与页面专属列建议

截至本轮讨论，左侧表格建议统一保留以下基础列：

- 商品
- 应处理数量
- 已处理数量
- 剩余数量
- 状态

在统一基础列之外，各执行页再补充少量更贴近本动作的业务列：

- `收货执行页`
  - 条码摘要
  - 批次摘要
- `上架执行页`
  - 来源位
  - 目标位摘要
- `拣货执行页`
  - 推荐货位
  - 批次摘要
- `复核执行页`
  - 已拣数量参考
  - 复核结果摘要

## 124. 基于当前结论的下一步建议

在确认左侧表格采用“统一基础列骨架 + 页面专属列”后，后续更适合继续讨论的是：
`这组基础列和专属列里，哪些必须常驻展示，哪些可以放到列折叠、次级信息或鼠标悬浮提示中。`

## 125. 右侧执行区的统一骨架结论

本轮讨论已进一步确认，四个执行页右侧“当前执行操作区”一期优先采用：
`上方当前项摘要区 + 中部主录入区 + 下方动作区`

当前不建议把右侧执行区做成普通详情页样式。

更合适的理解是：

- 右侧是执行面板
- 重点是快速完成当前动作
- 它与左侧待处理表格形成清晰主从关系

## 126. 右侧执行区的统一录入节奏建议

截至本轮讨论，右侧执行区建议统一按下面的动作节奏理解：

1. 左侧选中一条待处理明细
2. 右侧自动带出当前项摘要
3. 用户录入本次动作的关键字段
4. 系统即时校验
5. 用户点击 `确认本次`
6. 系统更新左侧当前行状态和数量
7. 用户继续处理当前行，或自动切换下一条

这一节奏建议作为：

- `收货`
- `上架`
- `拣货`
- `复核`

四类执行页的统一交互基础。

## 127. 右侧执行区的统一区块建议

当前建议右侧执行区至少包含以下三块：

### 当前项摘要区
- 当前商品
- 当前待处理数量
- 当前已处理数量
- 当前剩余数量
- 批次或货位关键提示

### 主录入区
- 本次处理数量
- 本次动作关键字段
- 扫码或手输入口
- 当前校验提示

### 动作区
- `确认本次`
- `完成本次记录`
- `跳过或切换下一条`
- `取消`

## 128. 四个执行页右侧执行区的差异化字段建议

在统一右侧执行区骨架下，四个执行页主要通过动作字段来体现差异：

- `收货`
  - 数量
  - 批次
  - 生产日期或效期
  - 暂存位
- `上架`
  - 来源位
  - 目标货位
  - 本次上架数量
- `拣货`
  - 当前货位
  - 当前批次
  - 本次拣货数量
- `复核`
  - 本次复核数量
  - 复核结果
  - 问题备注

也就是说：

- 骨架统一
- 录入字段按业务动作不同而不同

## 129. 右侧执行区的按钮口径建议

当前建议四个执行页右侧主按钮顺序尽量统一为：

- `确认本次`
- `完成本次记录`
- `取消`

如需提升现场操作节奏，可补一个次级动作按钮：

- `确认并下一条`

当前不建议一期就在右侧执行区堆叠过多附加内容，例如：

- 大段历史日志
- 复杂统计卡片
- 异常处理中心
- 多层折叠块

这些内容当前更适合继续放在底部补充区或后续深化设计中承载。

## 130. 基于当前结论的下一步建议

在确认右侧执行区采用统一骨架和统一录入节奏后，后续更适合继续讨论的是：
`右侧执行区里，哪些字段必须一屏常驻，哪些可以放到折叠区、条件展示区或次级信息区。`

## 131. 右侧执行区常驻字段与次级字段的当前结论

本轮讨论已进一步确认，右侧执行区字段的组织应优先遵守以下原则：

`凡是当前动作必须立即判断、立即输入、立即确认的字段，必须常驻；凡是只在部分场景出现、或者更多承担补充说明作用的字段，应放入条件展示区、折叠区或次级信息区。`

也就是说，一期当前不建议把所有关联信息和补充信息都堆在右侧执行面板中。

## 132. 右侧执行区的一屏常驻内容建议

截至本轮讨论，右侧执行区一屏常驻内容建议优先收敛为以下四类：

1. 当前项核心摘要
2. 本次数量输入
3. 本动作关键字段
4. 主按钮区

其中：

### 当前项核心摘要
- 当前商品
- 当前剩余数量
- 当前关键提示

### 本次数量输入
- 本次处理数量

### 本动作关键字段
按动作不同而不同，但只保留本动作最关键的少量字段。

### 主按钮区
- `确认本次`
- `确认并下一条`
- `完成本次记录`
- `取消`

## 133. 四个执行页右侧执行区的常驻字段建议

### `收货页` 常驻
- 当前商品
- 剩余待收数量
- 本次收货数量
- 批次
- 生产日期或效期
- 暂存位
- 主按钮

### `上架页` 常驻
- 当前商品
- 剩余待上架数量
- 来源位
- 目标货位
- 本次上架数量
- 主按钮

### `拣货页` 常驻
- 当前商品
- 剩余待拣数量
- 当前货位
- 当前批次
- 本次拣货数量
- 主按钮

### `复核页` 常驻
- 当前商品
- 当前待复核数量
- 本次复核数量
- 复核结果
- 问题备注
- 主按钮

## 134. 四个执行页右侧执行区的次级信息建议

### `收货页` 次级信息
- 条码详细信息
- 更多商品属性
- 历史收货说明
- 附件或证据入口

### `上架页` 次级信息
- 货位更多属性

### `拣货页` 次级信息

### `复核页` 次级信息

- 附件或证据入口

## 135. 当前不建议在右侧执行区常驻展示的内容

当前不建议一期把以下内容都做成右侧常驻项：

- 大段说明文字
- 复杂日志
- 多层统计
- 过多扩展属性
- 完整附件区

这些内容当前更适合放入：

- 底部补充区
- 条件展示区
- 次级信息区

## 136. 基于当前结论的下一步建议

在确认右侧执行区常驻字段与次级字段的边界后，后续更适合继续讨论的是：
`右侧执行区里，哪些字段在不同状态下需要动态显示、动态禁用，或随着动作阶段自动切换。`

## 137. 右侧执行区动态显示与动态禁用的当前原则

本轮讨论已进一步确认，右侧执行区在状态控制上应优先影响：

- 字段是否可编辑
- 主按钮是否可用
- 少量必要字段是否显示

当前不建议一期把右侧执行区做成非常复杂的字段显隐迷宫。

更合适的理解是：

- 一期先做少量必要的动态显示
- 一期先做明确的编辑与禁用规则
- 一期先做清晰的主按钮启用条件

## 138. 右侧执行区按统一状态的动态规则建议

截至本轮讨论，右侧执行区建议优先按以下统一状态来控制字段和按钮：

### `draft`
- 核心录入字段可编辑
- `确认本次` 可用
- `完成本次记录` 通常先禁用，除非已无待处理量
- 结果类字段按动作需要显示

### `in_progress`
- 核心录入字段继续可编辑
- `确认本次` 可用
- `确认并下一条` 可用
- `完成本次记录` 在满足完成条件时可用
- 已完成摘要同步更新

### `done`
- 核心录入字段只读
- `确认本次` 禁用
- `确认并下一条` 禁用
- `完成本次记录` 禁用
- 保留查看与日志能力

### `cancel`
- 核心录入字段只读
- 主动作按钮禁用
- 保留取消原因或备注查看

## 139. 四个执行页的业务差异化动态规则建议

### `收货页`
- 只有在启用批次管理时，批次字段显示或必填
- 只有在启用效期管理时，生产日期或效期字段显示
- 当剩余待收为 `0` 时，`完成本次记录` 可用

### `上架页`
- 目标货位始终作为关键字段显示
- 来源位在已有默认来源时可只读展示
- 当待上架量清零时，允许完成

### `拣货页`
- 当前货位与批次随左侧选中行自动切换
- 若存在推荐货位，则优先显示推荐货位
- 若无推荐货位，则显示人工选择入口
- 当剩余待拣为 `0` 时，允许完成

### `复核页`
- `复核结果` 始终显示
- 当结果为 `problem` 时，问题备注变为重点显示或必填
- 当待复核量清零且结果已确认时，允许完成

## 140. 一期优先收紧的动态规则范围

当前更推荐一期优先只收紧以下三类动态规则：

1. 状态驱动编辑或只读
2. 业务开关驱动字段显示
3. 结果驱动补充字段显示

具体可理解为：

- `状态驱动编辑或只读`
  - 例如 `draft / in_progress / done / cancel` 对输入框和按钮启禁的影响
- `业务开关驱动字段显示`
  - 例如批次、效期是否启用
- `结果驱动补充字段显示`
  - 例如复核异常时的问题备注

## 141. 当前不建议一期优先引入的复杂动态规则

当前不建议一期优先做：

- 多层条件联动
- 过多自动隐藏字段
- 很复杂的按钮矩阵
- 一个页面里频繁切换多种模式

这些规则会明显提高前端复杂度，也会削弱执行页的清晰性。

## 142. 基于当前结论的下一步建议

在确认右侧执行区动态显示和动态禁用规则后，后续更适合继续讨论的是：
`这 4 个执行页里，各自主按钮的启用条件到底怎么定。`

## 143. 执行页主按钮的统一口径

本轮讨论已进一步确认，四个执行页的主按钮优先统一为：

- `确认本次`
- `确认并下一条`
- `完成本次记录`
- `取消`

当前更推荐先统一主按钮口径，再针对收货、上架、拣货、复核四类动作补少量差异，而不是从一开始为每个执行页设计完全不同的一套按钮规则。

## 144. `确认本次` 的启用条件建议

截至本轮讨论，`确认本次` 当前建议在以下条件同时满足时启用：

- 当前记录状态为 `draft` 或 `in_progress`
- 左侧已有当前选中行
- 本次数量大于 `0`
- 当前动作必填字段已满足
- 当前没有阻断性校验错误

当前建议在以下场景禁用：

- 当前记录状态为 `done` 或 `cancel`
- 当前未选中任何待处理行
- 本次数量为空或小于等于 `0`
- 关键字段缺失
- 当前存在校验失败

## 145. `确认并下一条` 的启用条件建议

截至本轮讨论，`确认并下一条` 当前建议在以下条件同时满足时启用：

- 已满足 `确认本次` 的全部启用条件
- 系统仍然可以切换到下一条待处理项

当前建议在以下场景禁用：

- 当前已是最后一条可处理项
- 当前动作尚未满足确认条件

## 146. `完成本次记录` 的启用条件建议

截至本轮讨论，`完成本次记录` 当前建议在以下条件同时满足时启用：

- 当前记录状态为 `draft` 或 `in_progress`
- 本次记录对应的待处理量已经清零，或已满足当前动作的完成口径
- 当前不存在未处理的阻断性异常

当前建议在以下场景禁用：

- 仍有剩余待处理量
- 关键字段尚未补齐
- 当前记录状态已为 `done` 或 `cancel`

## 147. `取消` 的启用条件建议

截至本轮讨论，`取消` 当前建议在以下条件满足时启用：

- 当前记录状态不是 `done`
- 当前用户具备取消权限

当前建议在以下场景禁用：

- 当前记录状态已为 `done`
- 当前用户无权限

## 148. 四个执行页主按钮的差异化启用条件建议

### `收货`

`确认本次` 还应补充要求：

- 批次商品必须填写批次
- 启用效期管理的商品必须填写生产日期或效期

`完成本次记录` 当前更建议在以下条件满足时启用：

- 当前收货记录剩余待收为 `0`

### `上架`

`确认本次` 还应补充要求：

- 目标货位已选择
- 本次上架数量合法

`完成本次记录` 当前更建议在以下条件满足时启用：

- 当前上架记录剩余待上架为 `0`

### `拣货`

`确认本次` 还应补充要求：

- 当前货位明确
- 启用批次管理时当前批次明确
- 本次拣货数量不超过可拣量

`完成本次记录` 当前更建议在以下条件满足时启用：

- 当前拣货记录剩余待拣为 `0`

### `复核`

`确认本次` 还应补充要求：

- 复核结果已选择
- 当结果为 `problem` 时，问题备注已填写

`完成本次记录` 当前更建议在以下条件满足时启用：

- 当前复核记录剩余待复核为 `0`
- 当前复核结果已确认

## 149. 当前阶段的主按钮规则建议

当前更推荐一期将主按钮规则先收得较硬：

- 满足条件即启用
- 不满足条件即禁用
- 配合清晰的校验提示

当前不建议一期优先引入：

- 过多模糊中间态
- 复杂按钮矩阵
- 难以预测的按钮跳变逻辑

## 150. 基于当前结论的下一步建议

在确认四个执行页主按钮的启用条件后，后续更适合继续讨论的是：
`点击“确认本次”之后，左侧当前行和右侧当前面板应如何联动更新。`

## 151. `确认本次` 之后的统一联动更新原则

本轮讨论已进一步确认，点击 `确认本次` 成功后，执行页的左右区域联动更新应优先遵守以下统一节奏：

1. 先更新右侧当前动作结果
2. 再同步更新左侧当前行
3. 再根据按钮类型决定是否切下一条

当前更推荐把反馈顺序做清楚，而不是左右区域同时无序跳变。

## 152. `确认本次` 成功后的右侧更新建议

截至本轮讨论，点击 `确认本次` 成功后，右侧应优先立即刷新：

- 本次处理数量清零，或回到默认值
- 当前项已处理数量更新
- 当前项剩余数量更新
- 当前校验提示清空
- 保留当前动作上下文

也就是说，右侧应先明确告诉用户：
`本次动作已成功记账或成功提交`

## 153. `确认本次` 成功后的左侧更新建议

截至本轮讨论，点击 `确认本次` 成功后，左侧当前行应同步更新：

- 已处理数量
- 剩余数量
- 状态
- 必要时状态标签颜色

若当前行已处理完成：

- 行状态应变为完成态
- 但当前不建议一成功就立刻把该行直接从列表中移除

这样更利于用户确认自己刚刚完成的动作结果。

## 154. `确认本次` 与 `确认并下一条` 的联动差异

当前建议按按钮类型区分联动节奏：

### 点击 `确认本次`
- 默认停留在当前行
- 适合继续处理当前项
- 不强制自动跳下一条

### 点击 `确认并下一条`
- 成功后自动切换到下一条未完成项
- 左侧高亮同步切换
- 右侧当前项摘要和录入区同步切换到新项

这样可以同时支持：

- 分批处理当前项
- 快速连续处理多条明细

## 155. 当前行已完成时的联动建议

若点击 `确认本次` 后，当前行剩余数量变为 `0`，当前建议：

- 左侧行标记为完成
- 右侧给出轻提示，例如：
  - `当前项已完成`

若仍有下一条待处理项：

- 页面可保留明显入口让用户切到下一条
- 或在点击 `确认并下一条` 时自动切换

当前不建议普通 `确认本次` 成功后就默认强制跳转到下一条，因为现场场景下用户常常还需要确认刚完成项的结果。

## 156. 整个记录已满足完成条件时的联动建议

若本次确认后，整个执行记录已无剩余待处理项，当前建议：

- 左侧所有项更新为完成
- 右侧主录入区进入“已完成可收尾”状态
- `完成本次记录` 按钮变为可用
- 页面给出明确提示，例如：
  - `当前记录已满足完成条件`

## 157. `确认本次` 失败时的联动建议

若点击 `确认本次` 失败，当前建议：

- 左侧不更新
- 右侧保留用户刚输入的数据
- 右侧给出清晰错误提示
- 不自动跳行

这一点当前非常重要，因为它直接影响现场执行体验与纠错效率。

## 158. 当前阶段的统一联动规则建议

截至本轮讨论，当前更推荐先统一收敛为以下规则：

- `确认本次` 成功
  - 右侧先更新
  - 左侧再同步
  - 默认不跳行
- `确认并下一条` 成功
  - 右侧更新
  - 左侧同步
  - 自动切下一条
- `确认失败`
  - 左侧不变
  - 右侧保留输入并报错

## 159. 基于当前结论的下一步建议

在确认 `确认本次` 之后的左右联动更新规则后，后续更适合继续讨论的是：
`左侧已完成行应继续显示、置灰、置底，还是从默认视图中过滤掉。`

## 160. 左侧已完成行的默认展示策略结论

本轮讨论已进一步确认，一期执行页左侧待处理表格中的已完成行默认建议采用：
`继续显示 + 置灰弱化 + 保持原排序位置`

当前不建议一期默认采用：

- 完成后立即从默认视图中过滤掉
- 完成后自动置底

## 161. 当前推荐这一策略的主要原因

当前更推荐“继续显示 + 置灰弱化 + 保持原位”，主要因为：

1. 现场执行场景需要明确确认感
2. 更适合与“确认本次成功后默认不跳行”的联动规则保持一致
3. 比自动置底更稳定，不会导致列表频繁跳动

## 162. 已完成行在默认视图中的当前建议

截至本轮讨论，默认视图下的已完成行当前建议：

- 继续显示
- 行样式置灰
- 状态明确显示为完成态
- 保持原列表位置不变

## 163. 已完成行的视觉弱化与交互建议

当前建议通过以下方式弱化已完成行，但不让其完全消失：

- 行文字降权
- 状态标签保留
- 仍可点击查看
- 默认不再作为自动跳转的下一条目标

## 164. 当前不优先采用“默认过滤”与“默认置底”的原因

### 不优先默认过滤

主要因为：

- 刚完成项会缺乏确认感
- 不利于用户复核刚刚提交的结果
- 对分批处理场景不够友好

### 不优先默认置底

主要因为：

- 列表会频繁跳动
- 用户视线容易中断
- 批量处理时体验不稳

## 165. 后续可补充的轻量筛选方向

当前虽然不建议默认过滤已完成行，但后续可以补充轻量筛选，例如：

- `显示全部`
- `仅看未完成`

也就是说：

- 默认视图先保留已完成行
- 过滤应作为用户主动选择的辅助能力

## 166. 基于当前结论的下一步建议

在确认左侧已完成行的默认展示策略后，后续更适合继续讨论的是：
`自动切下一条时，系统应按什么规则选择“下一条”。`

## 167. 自动切下一条的当前统一规则结论

本轮讨论已进一步确认，一期执行页在点击 `确认并下一条` 后，系统默认建议采用：
`按当前列表顺序，选择当前行之后的第一条未完成且可处理的行`

这一规则当前不建议做成全表范围内的复杂智能跳转，也不建议来回扫描。

## 168. 自动切下一条的当前执行顺序建议

截至本轮讨论，自动切下一条的执行顺序当前建议如下：

1. 从当前行的下一行开始向下查找
2. 找到第一条未完成且可处理的行
3. 若找到，则自动切换到该行
4. 若未找到，则保持当前上下文，不再自动跳转

## 169. 当前不建议自动回头跳转的原因

当前不建议一期自动向上回扫或来回跳转，主要因为：

- 用户会感觉页面在无规律跳动
- 现场操作节奏容易被打断
- 不利于保持与物流模块一致的清单顺序感

## 170. “可处理的下一条”当前建议口径

截至本轮讨论，“可处理的下一条”当前建议优先收敛为以下简单口径：

- 状态不是完成
- 状态不是取消
- 当前用户具备处理权限
- 当前未被筛选条件隐藏

当前不建议一期把这一判断做得过于复杂。

## 171. 当前列表下方无可处理项时的建议

若从当前行往下已找不到可处理项，当前建议：

- 不自动跳到上方
- 不自动跳到列表中其他位置
- 保持当前上下文
- 给出轻提示，例如：
  - `后续无可处理项`

若此时整个记录已满足完成条件，则应同步引导用户执行：

- `完成本次记录`

## 172. 基于当前结论的下一步建议

在确认自动切下一条的统一规则后，后续更适合继续讨论的是：
`左侧待处理表格的默认排序应按什么口径来排。`

## 173. 左侧待处理表格默认排序的当前结论

本轮讨论已进一步确认，一期执行页左侧待处理表格默认排序当前建议采用：
`主业务顺序优先，其次按明细行号稳定排序`

更具体地说，当前建议：

- 默认先按主单里的业务顺序排
- 若存在明确行号，则按行号升序
- 若无明确行号，再按创建顺序或明细主键顺序兜底

## 174. 当前推荐默认稳定排序的主要原因

当前更推荐默认稳定排序，主要因为：

1. 更匹配“自动切下一条按当前列表向下找”的规则
2. 更容易被用户理解为按单据原始顺序逐条处理
3. 更适合作为一期的清晰基线

## 175. 当前不建议作为默认排序的口径

截至本轮讨论，当前不建议一期默认按以下口径排序：

- 剩余数量优先
- 货位优先
- 批次优先
- 最近操作优先
- 智能推荐优先

这些排序口径后续如确有价值，更适合做成用户主动切换的辅助排序视图，而不是默认排序。

## 176. 默认排序与完成态、筛选的关系建议

截至本轮讨论，当前建议同时明确以下几点：

### 完成行不改变排序

- 行完成后继续保留原位置
- 不因状态变化而自动重排

### 筛选与排序分开

- `仅看未完成` 应视为筛选
- 默认排序仍保持业务原始顺序
- 不建议因为筛选动作改变核心排序逻辑

## 177. 基于当前结论的下一步建议

在确认左侧待处理表格默认采用稳定排序后，后续更适合继续讨论的是：
`左侧表格顶部到底需要哪些最小筛选和搜索。`

## 178. 左侧表格顶部最小筛选与搜索的当前结论

本轮讨论已进一步确认，一期执行页左侧表格顶部的工具条当前建议优先收敛为：
`高频、低歧义、现场马上用得上`

当前不建议一期一开始就把顶部工具条做得过重。

## 179. 左侧表格顶部最小入口建议

截至本轮讨论，左侧表格顶部最小建议保留以下四类入口：

- 关键字搜索
- 完成状态筛选
- 异常或问题筛选
- 刷新

## 180. 关键字搜索的当前建议

当前建议左侧顶部的关键字搜索最小支持以下对象：

- 商品名称
- 商品编码
- 条码

这是当前更高频、也更容易被现场人员理解的搜索范围。

## 181. 完成状态筛选的当前建议

当前建议完成状态筛选一期最小先只做：

- `全部`
- `仅看未完成`

如后续确有需要，可再补：

- `仅看已完成`

但当前不建议作为一期必需项优先加入。

## 182. 异常或问题筛选的当前建议

当前建议异常或问题筛选按“需要的执行页启用”来理解，尤其在复核页更有价值。

一期最小建议口径可先收为：

- `全部`
- `仅看有问题`

若某些执行页当前一期尚未形成明确的“问题项”语义，则可暂不强制提供该筛选。

## 183. 刷新入口的当前建议

当前建议左侧顶部保留一个清晰的刷新入口即可。

当前不建议一期优先在左侧顶部叠加过多工具栏动作。

## 184. 当前不建议一期优先放入顶部工具条的内容

截至本轮讨论，当前不建议一期优先放入左侧顶部工具条的内容包括：

- 多字段组合筛选
- 货位筛选
- 批次筛选
- 高级排序切换
- 表头自定义
- 过多快捷标签

这些内容容易让左侧顶部工具条过重，并压缩主操作空间。

## 185. 基于当前结论的下一步建议

在确认左侧表格顶部最小筛选和搜索后，后续更适合继续讨论的是：
`右侧执行区与左侧顶部搜索或筛选联动时，当前选中行应如何处理。`

## 186. 搜索或筛选变化时的选中行处理原则

本轮讨论已进一步确认，左侧顶部搜索或筛选变化后，当前选中行的处理优先建议采用以下统一规则：

`如果当前选中行在新结果集里仍存在，就保留选中；如果已不在结果集里，就自动切到新结果集的第一条可处理行；如果没有可处理行，就清空右侧执行区并进入空状态。`

当前不建议在筛选变化后继续隐式保留一个用户看不见的旧选中项。

## 187. 当前选中行仍在结果集里时的建议

截至本轮讨论，若左侧搜索或筛选变化后，当前选中行在新结果集里仍存在，当前建议：

- 保持当前选中不变
- 右侧执行区不重置
- 继续保留当前动作上下文

这样更有利于保持用户操作稳定性，不会因为筛选变化而突然丢失上下文。

## 188. 当前选中行已不在结果集里、但仍有可处理项时的建议

若当前选中行已不在新结果集里，但结果集中仍存在可处理项，当前建议：

- 自动切换到新结果集中的第一条可处理行
- 左侧高亮同步切换
- 右侧执行区同步切换到新当前项
- 只给轻量过渡提示，不做强打扰式弹窗

## 189. 结果集为空或无可处理项时的建议

若搜索或筛选变化后结果集为空，或虽有结果但无可处理项，当前建议：

- 左侧显示空结果
- 右侧不再保留旧执行面板
- 右侧切换到空状态
- 页面给出明确提示，例如：
  - `当前筛选结果下无可处理项`

## 190. 当前不建议采用的处理方式

当前不建议：

- 在左侧已无该行时，右侧仍继续保留旧选中项执行面板
- 让左右区域出现“列表不可见、面板仍保留”的隐式状态

这样容易导致用户对当前操作对象产生混淆。

## 191. 基于当前结论的下一步建议

在确认搜索或筛选变化时的选中行处理规则后，后续更适合继续讨论的是：
`右侧空状态应显示哪些最小信息和引导动作。`

## 192. 右侧空状态的当前定位

本轮讨论已进一步确认，右侧空状态一期当前不建议做成复杂信息页，而应优先理解为：
`轻量占位态`

它的目标不是承载大量说明，而是：

- 明确告诉用户当前无可处理项
- 简短说明原因
- 提供最小恢复动作

## 193. 右侧空状态的最小信息建议

截至本轮讨论，右侧空状态当前建议最小只包含以下三块：

1. 主提示
2. 原因提示
3. 引导动作

### 主提示
例如：

- `当前无可处理项`
- `当前筛选结果下无可处理项`

### 原因提示
当前建议只做简短原因说明，例如：

- 已被筛选隐藏
- 当前列表为空
- 当前已全部完成

### 引导动作
当前建议最小只保留：

- `清空筛选`
- `刷新`

若当前整单已满足完成条件，可补一个：

- `完成本次记录`

## 194. 当前不建议在空状态中堆叠的内容

当前不建议一期在右侧空状态中放入：

- 大段说明文字
- 复杂帮助文档入口
- 复杂日志
- 过多按钮

这些内容会让空状态失去“快速恢复到可操作状态”的本意。

## 195. 基于当前结论的下一步建议

在确认右侧空状态的最小信息和引导动作后，后续更适合继续讨论的是：
`执行页底部 tab 区一期最小应该保留哪些页签。`

## 196. 执行页底部 tab 区一期最小页签结论

本轮讨论已进一步确认，执行页底部 tab 区一期当前建议保留以下 4 个页签：

- `进度摘要`
- `执行日志`
- `关联执行对象`
- `证据/附件`

当前不建议一期在底部 tab 区继续扩展过多次要页签。

## 197. 当前推荐保留这 4 个页签的原因

截至本轮讨论，当前更推荐保留这 4 个页签，主要因为：

### `进度摘要`

最有现场执行价值，可快速查看：

- 已处理数量
- 剩余数量
- 当前记录状态
- 是否满足完成条件

### `执行日志`

最有利于现场确认与排查，可快速查看：

- 谁执行了什么动作
- 什么时间执行
- 成功还是失败

### `关联执行对象`

最有利于与 Odoo `stock` 执行层对齐，可快速查看：

- `picking`
- `move`
- `move line`
- 必要时 `lot`

### `证据/附件`

最有利于延续物流模块的留痕思路，也更符合仓管后续对异常、复核、争议场景的支撑需求。

## 198. 当前不建议一期优先放入底部 tab 区的内容

截至本轮讨论，当前不建议一期优先放入底部 tab 区的内容包括：

- 复杂统计
- 大报表
- 长篇说明
- 过多次要页签

## 199. 基于当前结论的下一步建议

在确认执行页底部 tab 区一期最小页签后，后续更适合继续讨论的是：
`这 4 个底部页签里，各自最小应该展示哪些字段。`

## 200. 底部 4 个页签的当前定位

本轮讨论已进一步确认，执行页底部的 4 个页签一期应优先理解为：
`轻量查看型页签`

当前不建议一期就把这些页签做成很重的编辑中心。

更准确地说，底部 tab 区当前主要承担：

- 补充上下文
- 支撑追溯
- 提供反查入口
- 提供轻量证据查看

## 201. `进度摘要` 页签的最小展示字段建议

截至本轮讨论，`进度摘要` 页签当前建议最小展示：

- 当前记录状态
- 已处理数量
- 剩余数量
- 总行数
- 已完成行数
- 是否满足完成条件

## 202. `执行日志` 页签的最小展示字段建议

截至本轮讨论，`执行日志` 页签当前建议最小展示：

- 时间
- 操作人
- 动作
- 结果
- 简短说明

当前建议一期优先保证日志可追溯，不必一开始就做成长篇复杂日志中心。

## 203. `关联执行对象` 页签的最小展示字段建议

截至本轮讨论，`关联执行对象` 页签当前建议最小展示：

- `picking` 编号
- `move` 数量或条数摘要
- `move line` 数量或条数摘要
- `lot` 或批次摘要（有则显示）

当前更建议把它理解为：
`反查入口`

而不是一期就做成很重的执行对象管理中心。

## 204. `证据/附件` 页签的最小展示字段建议

截至本轮讨论，`证据/附件` 页签当前建议最小展示：

- 证据类型
- 上传时间
- 上传人
- 关联说明或备注
- 预览入口

若一期某些执行页尚未挂接完整证据能力，当前也可允许该页签在无内容时为空，但结构应先保留。

## 205. 当前不建议一期优先放入页签的内容

截至本轮讨论，当前不建议一期优先在这 4 个页签里放入：

- 复杂统计图
- 大段正文
- 很深的多层明细
- 很重的编辑能力

## 206. 当前阶段的底部页签实现建议

当前更推荐一期先把这 4 个页签统一做成：
`轻量查看型，不做重编辑型`

## 207. 基于当前结论的下一步建议

`这 4 个页签默认打开哪个，以及不同执行页是否需要不同默认页签。`

## 208. 底部页签默认打开策略的当前结论

本轮讨论已进一步确认，一期执行页底部 tab 区当前建议统一默认打开：
`进度摘要`

当前不建议一期一开始就让四个执行页分别默认打开不同页签。

## 209. 当前推荐统一默认打开 `进度摘要` 的主要原因

当前更推荐统一默认打开 `进度摘要`，主要因为：

1. 最稳定，用户每次进入执行页都能在同一位置建立认知
2. 最贴近一期执行场景，优先看到已处理、剩余与是否满足完成条件
3. 更符合底部页签当前“轻量查看型”的定位

## 210. 其他底部页签的当前角色建议

截至本轮讨论，除 `进度摘要` 外，其余页签当前更建议理解为：

### `执行日志`
- 排查页签
- 追溯页签

### `关联执行对象`
- `stock` 反查页签

### `证据/附件`
- 留痕查看页签

也就是说，这些页签当前更适合作为辅助查看，而不是执行页一打开就优先占据默认位置。

## 211. 当前不建议一期优先做页面级差异化默认的原因

当前不建议一期优先做“不同执行页默认打开不同底部页签”，主要因为：

- 会增加用户切换认知成本
- 会削弱执行页整体结构的一致性
- 与当前阶段“统一骨架、统一节奏”的方向不一致

后续若某些场景确有明显差异，再考虑是否补充页面级差异化默认。

## 212. 基于当前结论的下一步建议

在确认底部页签统一默认打开 `进度摘要` 后，后续更适合继续讨论的是：
`执行页顶部上下文区最小应该展示哪些字段。`

## 213. 执行页顶部上下文区最小字段的当前结论

本轮讨论已进一步确认，一期执行页顶部上下文区当前建议优先收敛为：
`少而稳`

也就是说，顶部上下文区只保留用户进入页面第一眼必须确认的信息，不建议把顶部做成第二个详情页。

## 218. 基于当前结论的下一步建议

在确认执行页顶部上下文区的最小字段后，后续更适合继续讨论的是：
`顶部上下文区右上角主按钮最小应保留哪些。`

## 219. 顶部右上角主按钮的最小集合结论

本轮讨论已进一步确认，一期执行页顶部右上角当前建议优先只保留：

- `刷新`
- `返回主单`
- `完成本次记录`

若后续确有需要，再考虑补充：

- `取消记录`

当前不建议一期一开始就在顶部堆叠过多动作按钮。

## 220. 顶部右上角主按钮的当前设计原则

截至本轮讨论，顶部右上角主按钮当前更建议遵守以下原则：

`只放页面级动作和记录级动作，不放当前动作级按钮。`

也就是说：

- 顶部承担页面级、记录级动作
- 右侧执行区承担当前动作级按钮

这样可以避免两个区域在职责上互相打架。

## 221. 当前推荐保留这几个顶部按钮的主要原因

### `刷新`

这是典型页面级动作，放在顶部最自然。

### `返回主单`

执行页不是孤立页面，回到主业务单据是高频动作，适合作为顶部常驻入口。

### `完成本次记录`

这是记录级收尾动作，与右侧的 `确认本次` 不同层级，放顶部是成立的。

### `取消记录`

该动作有价值，但由于风险更高，当前更建议作为可补充动作，而不是一期顶部最小必备动作。

## 222. 当前不建议一期优先放入顶部的动作

截至本轮讨论，当前不建议一期优先放入顶部右上角的动作包括：

- `确认本次`
- `确认并下一条`
- 过多跳转按钮
- 过多工具型动作

这些动作当前更适合继续放在右侧执行区，不建议在顶部重复出现。

## 223. 基于当前结论的下一步建议

在确认顶部右上角主按钮的最小集合后，后续更适合继续讨论的是：
`顶部右上角这几个按钮的主次关系和顺序应如何排列。`

## 224. 顶部右上角主按钮的主次关系与顺序结论

本轮讨论已进一步确认，一期执行页顶部右上角按钮当前建议按以下顺序排列：

- `返回主单`
- `刷新`
- `完成本次记录`

若后续确有需要补充 `取消记录`，当前也不建议让它直接进入主按钮链。

## 225. 当前推荐这一顺序的主要原因

截至本轮讨论，当前更推荐这一顺序，主要因为：

### `返回主单`

作为最稳定的导航动作，当前更适合放在最左侧，便于用户一眼找到返回路径。

### `刷新`

作为工具型动作，重要但并非页面最核心结果动作，当前更适合放在中间。

### `完成本次记录`

作为顶部最重要的结果动作，当前更适合放在最右侧主位。

## 226. 顶部右上角按钮的当前层级理解

截至本轮讨论，顶部右上角按钮当前更建议按以下层级理解：

1. 导航动作
2. 工具动作
3. 结果动作

也就是说：

- `返回主单` 属于导航动作
- `刷新` 属于工具动作
- `完成本次记录` 属于结果动作

## 227. `取消记录` 的当前建议摆放方式

截至本轮讨论，若后续确需补充 `取消记录`，当前更建议：

- 放入更多菜单
或
- 作为次级危险动作独立摆放

当前不建议：

- 让 `取消记录` 与 `完成本次记录` 并排争夺主位
- 将危险动作直接纳入顶部默认主按钮链

## 228. 基于当前结论的下一步建议

在确认顶部右上角主按钮的主次关系和顺序后，后续更适合继续讨论的是：
`执行页顶部上下文区和右侧执行区之间，是否还需要一条状态或提示条。`

## 229. 顶部与中部之间状态/提示条的当前结论

本轮讨论已进一步确认，执行页顶部上下文区与中部主从双栏之间当前建议保留：
`一条轻量状态/提示条`

当前不建议一期把它做成复杂通知中心。

## 230. 当前推荐保留状态/提示条的主要原因

截至本轮讨论，当前更推荐保留这条轻量状态/提示条，主要因为：

- 它可以承接当前执行页最关键的单条反馈
- 有利于在顶部上下文区与中部执行区之间形成清晰过渡
- 比弹窗和多段提示更轻，更适合现场执行节奏

## 231. 状态/提示条的当前摆放位置建议

当前建议这条轻量状态/提示条放在：

- 顶部上下文区下方
- 中部主从双栏上方

也就是说，它应作为一个较薄的过渡层，承接“当前执行提醒”。

## 232. 状态/提示条一期优先承接的信息类型

截至本轮讨论，这条状态/提示条一期当前优先承接以下 4 类信息：

1. 当前记录级状态提示
2. 当前动作结果提示
3. 轻量校验提醒
4. 下一步引导

### 当前记录级状态提示
例如：

- `当前记录进行中`
- `当前记录已满足完成条件`
- `当前记录已完成`

### 当前动作结果提示
例如：

- `本次确认成功`
- `当前项已完成`
- `当前无可处理项`

### 轻量校验提醒
例如：

- `请先填写批次`
- `请先选择目标货位`

### 下一步引导
例如：

- `可继续处理当前项`
- `可点击“完成本次记录”收尾`

## 233. 当前不建议让状态/提示条承接的内容

截至本轮讨论，当前不建议让这条状态/提示条承接：

- 长日志
- 多条堆叠消息
- 复杂通知列表
- 过多颜色状态

当前更推荐把它理解为：
`当前页执行助手`

而不是：
`消息中心`

## 234. 状态/提示条的当前展示节奏建议

截至本轮讨论，当前更推荐这条状态/提示条默认一次只显示：
`一条主提示`

这样可以避免页面在执行过程中出现过多干扰。

## 235. 基于当前结论的下一步建议

在确认执行页顶部与中部之间保留轻量状态/提示条后，后续更适合继续讨论的是：
`这条状态/提示条在不同场景下应优先显示什么。`

## 236. 状态/提示条优先级的当前结论

本轮讨论已进一步确认，执行页这条轻量状态/提示条一期当前建议按以下优先级从高到低显示：

1. 阻断性错误或校验
2. 当前动作结果
3. 记录级状态
4. 下一步引导

当前建议同一时刻只显示优先级最高的一条主提示。

## 237. 各类提示的当前优先级理解

### 1. 阻断性错误或校验

当前建议作为最高优先级，例如：

- `请先填写批次`
- `请先选择目标货位`
- `本次数量不可超过剩余数量`

只要存在这类提示，当前建议优先显示它。

### 2. 当前动作结果

当前建议作为第二优先级，例如：

- `本次确认成功`
- `当前项已完成`
- `确认失败，请重试`

这类提示适合在用户刚完成一次动作后，短时间优先顶掉普通状态提示。

### 3. 记录级状态

当前建议作为第三优先级，例如：

- `当前记录进行中`
- `当前记录已满足完成条件`
- `当前记录已完成`

这类提示更适合作为页面的常驻背景提示。

### 4. 下一步引导

当前建议作为第四优先级，例如：

- `可继续处理当前项`
- `可点击“完成本次记录”收尾`

只有前面几类提示都不占位时，当前更推荐显示这类引导。

## 238. 当前不建议一期优先采用的提示方式

截至本轮讨论，当前不建议一期优先采用：

- 同时并列显示多条提示
- 让成功提示、错误提示、引导提示同时抢占一条提示条
- 复杂轮播式提示

这些方式会明显削弱页面反馈的清晰性。

## 239. 基于当前结论的下一步建议

在确认状态/提示条的优先级顺序后，后续更适合继续讨论的是：
`这条状态/提示条与 toast、弹窗之间的边界应如何划分。`

## 240. 提示条、toast、弹窗的当前边界结论

本轮讨论已进一步确认，一期执行页的反馈方式当前建议优先收敛为以下三层：

- `提示条`：页内持续反馈
- `toast`：短暂结果反馈
- `弹窗`：需要确认或阻断决策

当前更推荐三者各司其职，不混用。

## 241. `提示条` 的当前定位建议

截至本轮讨论，`提示条` 当前更适合承接：

- 当前页的持续状态
- 阻断性校验
- 下一步引导
- 当前记录层提示

它的主要特征当前建议理解为：

- 位于页内固定位置
- 相对持续
- 更适合承接“你现在该知道什么”

## 242. `toast` 的当前定位建议

截至本轮讨论，`toast` 当前更适合承接：

- 一次动作刚完成后的短反馈
- 轻量成功提示
- 不需要用户额外决策的瞬时结果

例如：

- `本次确认成功`
- `已切换到下一条`
- `刷新完成`

它的主要特征当前建议理解为：

- 短暂出现
- 自动消失
- 不承担复杂说明

## 243. `弹窗` 的当前定位建议

截至本轮讨论，`弹窗` 当前更适合承接：

- 需要用户确认的动作
- 高风险动作
- 无法靠提示条解决的阻断场景

例如：

- `确认取消本次记录？`
- `存在未保存变更，是否离开？`
- `当前操作将覆盖已录入内容，是否继续？`

它的主要特征当前建议理解为：

- 明确打断当前流程
- 需要用户做决定
- 不应滥用

## 244. 当前不建议的反馈方式混用

截至本轮讨论，当前不建议：

- 用弹窗提示普通成功
- 用 toast 承担复杂错误解释
- 用提示条承担确认决策

## 245. 基于当前结论的下一步建议

在确认提示条、toast、弹窗的边界后，后续更适合继续讨论的是：
`哪些场景必须弹窗，哪些场景只用 toast 或提示条就够了。`

## 246. 必须弹窗与非弹窗场景的当前结论

本轮讨论已进一步确认，一期执行页中“必须弹窗”的场景当前建议优先收得较窄，只保留真正需要用户做明确决策、或者存在明显风险的场景。

当前更推荐的整体边界是：

- 涉及确认、覆盖、离开、撤销等风险动作时，优先弹窗
- 普通成功结果，优先使用 `toast`
- 页内状态、校验与引导，优先使用提示条

## 247. 当前建议必须弹窗的场景

截至本轮讨论，当前建议必须弹窗的场景优先只保留以下 4 类：

1. `取消记录`
2. `离开页面但存在未保存录入`
3. `覆盖已有录入`
4. `会导致明显业务后果的逆向或高风险动作`

当前典型示例如下：

- `确认取消本次记录？`
- `当前有未保存内容，是否离开？`
- `当前操作将覆盖已录入结果，是否继续？`
- `当前操作将撤销/重置已完成结果，是否继续？`

## 248. 当前建议只用 toast 即可的场景

截至本轮讨论，以下场景当前更建议优先只用 `toast`：

- `本次确认成功`
- `已切换到下一条`
- `刷新完成`
- `复制成功`
- `保存成功`

这些场景的共同特点是：

- 结果轻量
- 反馈瞬时
- 不需要用户额外决策

## 249. 当前建议只用提示条即可的场景

截至本轮讨论，以下场景当前更建议优先只用提示条：

- `请先填写批次`
- `请先选择目标货位`
- `本次数量不可超过剩余数量`
- `当前记录已满足完成条件`
- `当前无可处理项`

这些场景的共同特点是：

- 属于页内持续性提醒
- 不需要打断用户
- 需要与当前页的上下文一起存在

## 250. 基于当前结论的下一步建议

在确认必须弹窗与非弹窗场景的边界后，后续更适合继续讨论的是：
`执行页里哪些动作算“未保存录入”，从而触发离开确认弹窗。`

## 251. “未保存录入”的当前结论

本轮讨论已进一步确认，一期执行页中“未保存录入”的当前建议口径为：

`凡是用户已经在右侧执行区改动了可提交字段，但还未成功执行“确认本次”或被明确清空，这就算未保存录入。`

也就是说，当前判断重点不是“用户有没有点过页面”，而是：

`是否已经形成尚未提交的有效录入改动。`

## 252. 当前建议算作“未保存录入”的动作

截至本轮讨论，以下情况当前建议算作“未保存录入”：

- 已填写 `本次处理数量`
- 已填写批次、效期、目标货位、问题备注等关键输入字段
- 已修改当前动作字段，但尚未点击 `确认本次`
- 已通过扫码带入部分可提交值，但尚未提交

## 253. 当前建议不算作“未保存录入”的动作

截至本轮讨论，以下情况当前建议不算作“未保存录入”：

- 仅切换左侧当前行
- 仅查看底部 tab
- 仅展开或收起次级信息
- 仅使用搜索、筛选、刷新，但未改动右侧录入字段
- 已成功执行 `确认本次`，且右侧执行区已重置

## 254. 当前更稳的实现口径建议

截至本轮讨论，当前更推荐把“未保存录入”直接理解为：
`右侧执行区存在脏表单状态`

这样更便于实现，也更容易与前端交互保持一致。

## 255. 当前建议触发离开确认弹窗的典型场景

若右侧执行区存在未保存录入，当前建议以下场景触发离开确认弹窗：

- 点击 `返回主单`
- 切换页面
- 刷新页面
- 关闭页面
- 切到别的主单

## 256. 当前不建议纳入“未保存录入”的内容

截至本轮讨论，当前不建议把以下内容纳入“未保存录入”：

- 纯只读查看行为
- 页面自动联动更新
- 成功后的 toast 提示存在中
- 已完成项之间的查看切换

## 257. 基于当前结论的下一步建议

在确认“未保存录入”的判断口径后，后续更适合继续讨论的是：
`哪些动作可以自动清空这份未保存录入，哪些动作必须先弹确认。`

## 258. 未保存录入的自动清空与确认边界结论

本轮讨论已进一步确认，一期执行页中“未保存录入”的处理当前建议优先分成两类：

- 可以自动清空
- 必须先弹确认

当前更推荐把“是否会导致用户无感知地丢失录入”作为划分标准。

## 259. 当前建议可以自动清空未保存录入的动作

截至本轮讨论，以下动作当前建议可以自动清空未保存录入：

- `确认本次` 成功后
- `确认并下一条` 成功后
- 用户主动点击明确的 `清空输入`
- 用户切回同一行，且系统明确执行“重置当前录入”

这些场景的共同特点是：

- 用户预期系统会收尾或重置
- 不会造成无感知的数据丢失

## 260. 当前建议必须先弹确认的动作

截至本轮讨论，以下动作当前建议必须先弹确认：

- `返回主单`
- 切到别的主单
- 离开当前页面
- 刷新整个页面
- 关闭页面或标签页
- 当前存在脏数据时切换左侧到另一条明细
- 任何会覆盖当前未提交录入的动作

## 261. 对“切换左侧当前行”的当前特别建议

截至本轮讨论，当前特别建议明确一点：

若右侧执行区已有未保存录入，则：

- `切换左侧当前行` 必须先弹确认
- 当前不建议让系统直接默默清空右侧输入

这样更能避免现场操作中无感知丢失数量、批次、货位等关键录入。

## 262. 当前阶段的收口建议

截至本轮讨论，当前更推荐先统一收敛为：

- 成功提交后可自动清空
- 用户主动明确清空时可自动清空
- 导航、跳转、覆盖、换行等可能导致录入丢失的动作，必须先弹确认

## 263. 基于当前结论的下一步建议

在确认未保存录入的自动清空与确认边界后，后续更适合继续讨论的是：
`这类确认弹窗里的按钮文案和按钮顺序应如何确定。`

## 264. 确认弹窗按钮结构的当前结论

本轮讨论已进一步确认，一期执行页中的确认弹窗按钮当前建议优先采用：
`安全优先`

当前更推荐的总原则是：

`默认主按钮优先放“留在当前/返回”，危险或不可逆动作不抢主位。`

## 265. 确认弹窗按钮顺序的当前建议

截至本轮讨论，确认弹窗按钮的当前推荐顺序为：

- 左侧：安全按钮
- 右侧：继续或危险动作

也就是说：

- 安全返回型动作放前
- 危险继续型动作放后
- 默认焦点给安全按钮

## 266. 离开页面类弹窗的当前按钮建议

针对离开页面、返回主单、切换主单等场景，当前建议按钮优先收敛为：

- `留在当前页`
- `继续离开`

若场景确需明确表达丢弃输入，也可使用：

- `留在当前页`
- `清空后离开`

当前不建议默认把“离开”设置成最强主按钮。

## 267. 切换左侧当前行的当前按钮建议

针对存在未保存录入时切换左侧当前行的场景，当前建议按钮收敛为：

- `留在当前项`
- `清空并切换`

当前更推荐 2 个按钮即可，不建议一开始做成 3 键弹窗。

## 268. 覆盖已有录入的当前按钮建议

针对覆盖已有录入的场景，当前建议按钮收敛为：

- `保留当前录入`
- `覆盖并继续`

## 269. 取消记录或撤销结果的当前按钮建议

针对取消记录、撤销结果等高风险动作，当前建议按钮收敛为：

- `返回`
- `确认取消`

或

- `返回`
- `确认撤销`

当前即便危险动作需使用危险按钮样式，也不建议将其放成默认焦点按钮。

## 270. 当前阶段的统一按钮口径建议

截至本轮讨论，当前更推荐统一收敛为：

- 安全按钮在左
- 危险或继续动作在右
- 默认焦点给安全按钮
- 危险动作不抢默认主位

## 271. 基于当前结论的下一步建议

在确认确认弹窗按钮结构、按钮文案和顺序原则后，后续更适合继续讨论的是：
`确认弹窗的标题和正文文案应如何统一。`

## 272. 确认弹窗标题与正文文案的当前结论

本轮讨论已进一步确认，一期执行页中的确认弹窗文案当前建议优先采用：
`标题只说动作，正文说明后果和选择`

当前不建议把确认弹窗写成长篇背景说明，也不建议使用过多模糊措辞。

## 273. 确认弹窗标题的当前建议

截至本轮讨论，确认弹窗标题当前更建议遵守以下原则：

- 直接说风险动作
- 不写长句
- 不写模糊话

例如：

- `离开当前页面？`
- `切换当前项？`
- `覆盖当前录入？`
- `取消本次记录？`
- `撤销当前结果？`

## 274. 确认弹窗正文的当前建议

截至本轮讨论，确认弹窗正文当前更建议统一按以下结构表达：

1. 先说明当前会丢失、覆盖或取消什么
2. 再说明继续后会发生什么
3. 最后提示用户确认是否继续

也就是说，正文当前更建议围绕：

- 当前风险是什么
- 继续后的后果是什么
- 用户现在要做什么决定

## 275. 当前建议的典型文案模板

### 1. 离开页面 / 返回主单

标题：

- `离开当前页面？`

正文：

- `当前存在未保存录入。离开后，当前输入的数量、批次或货位等内容将不会保留。请确认是否继续离开。`

### 2. 切换左侧当前行

标题：

- `切换当前项？`

正文：

- `当前存在未保存录入。切换后，当前项尚未提交的输入将被清空。请确认是否继续切换。`

### 3. 覆盖已有录入

标题：

- `覆盖当前录入？`

正文：

- `当前操作将覆盖已录入结果。继续后，原有输入将被替换。请确认是否继续。`

### 4. 取消记录

标题：

- `取消本次记录？`

正文：

- `取消后，本次执行记录将不再继续处理。请确认是否继续取消。`

### 5. 撤销 / 重置结果

标题：

- `撤销当前结果？`

正文：

- `当前操作将撤销已完成结果。继续后，需要重新处理相关内容。请确认是否继续。`

## 276. 当前不建议的文案方式

截至本轮讨论，当前不建议：

- 文案过长
- 同时解释过多背景
- 使用过多术语
- 写成开发或系统内部语言

## 277. 基于当前结论的下一步建议

在确认确认弹窗的标题和正文文案后，后续更适合继续讨论的是：
`这些确认弹窗是否需要区分普通确认和危险确认两种视觉级别。`

## 278. 确认弹窗视觉级别的当前结论

本轮讨论已进一步确认，一期执行页中的确认弹窗当前建议区分：

- `普通确认`
- `危险确认`

当前不建议一期继续细分为更多级别。

## 279. 当前建议只分两级的主要原因

截至本轮讨论，当前更推荐只分普通确认和危险确认两级，主要因为：

- 足以覆盖一期主要风险场景
- 更容易让用户形成稳定认知
- 不会因为级别过多而让交互体系变重

## 280. `普通确认` 的当前适用场景建议

截至本轮讨论，以下场景当前更建议归入 `普通确认`：

- 离开页面
- 切换当前项
- 覆盖未提交录入
- 返回主单

这些动作的共同特点是：

- 可能丢失当前输入
- 但通常不会直接改变已形成的业务结果

## 281. `危险确认` 的当前适用场景建议

截至本轮讨论，以下场景当前更建议归入 `危险确认`：

- 取消记录
- 撤销已完成结果
- 重置已提交执行结果
- 任何明确影响业务结果的逆向动作

这些动作的共同特点是：

- 不只是丢失当前输入
- 还可能改变已形成的业务事实

## 282. 当前不建议归入“危险确认”的场景

截至本轮讨论，当前不建议把以下场景归入 `危险确认`：

- 普通离开页面
- 普通切换当前项
- 轻量覆盖未提交输入

当前主要是为了避免用户对危险样式产生疲劳与麻木。

## 283. 当前阶段的统一收口建议

截至本轮讨论，当前更推荐统一收敛为：

- 丢未提交输入：`普通确认`
- 改变已形成业务结果：`危险确认`

## 284. 基于当前结论的下一步建议

在确认确认弹窗采用普通确认和危险确认两级后，后续更适合继续讨论的是：
`普通确认和危险确认在视觉上最小应区别到哪些元素。`

## 285. 普通确认与危险确认的最小视觉差异结论

本轮讨论已进一步确认，一期执行页中普通确认与危险确认当前建议最小只区分以下 3 个元素：

- 主确认按钮颜色
- 标题强调方式
- 风险提示语气

当前不建议一期继续扩展更多视觉分级元素。

## 286. `普通确认` 的当前视觉建议

截至本轮讨论，`普通确认` 当前更建议采用：

- 主按钮：普通主按钮样式
- 标题：正常强调
- 正文：中性提示语气

## 287. `危险确认` 的当前视觉建议

截至本轮讨论，`危险确认` 当前更建议采用：

- 主按钮：危险色按钮
- 标题：增加风险强调
- 正文：更直接地说明后果

## 288. 当前不建议一期优先引入的视觉差异元素

截至本轮讨论，当前不建议一期优先引入：

- 不同图标体系
- 不同弹窗布局
- 大面积背景色变化
- 很重的警告插画
- 过多颜色层级

当前主要是为了：

- 保持与物流模块整体风格一致
- 只做“够区分，但不过度跳戏”的风险分级

## 289. 基于当前结论的下一步建议

在确认普通确认与危险确认的最小视觉差异后，后续更适合继续讨论的是：
`执行页里是否需要给“确认本次”成功后的 toast 设定统一文案模板。`

## 290. 成功 toast 文案模板的当前结论

本轮讨论已进一步确认，一期执行页中“确认本次”成功后的 `toast` 当前建议统一设定文案模板。

当前更推荐的统一模板是：
`动作结果 + 当前对象`

当前主要是为了让成功反馈保持：

- 短
- 稳
- 一致

## 291. 成功 toast 的当前模板建议

截至本轮讨论，成功 `toast` 当前更建议采用以下表达方式：

- `本次收货已确认`
- `本次上架已确认`
- `本次拣货已确认`
- `本次复核已确认`

若成功后同时发生自动切换下一条，当前可再补一个较短后缀，例如：

- `已切换到下一条`

组合后例如：

- `本次拣货已确认，已切换到下一条`

若未发生自动切换，则当前不建议强行补充后半句。

## 292. 当前不建议的成功 toast 文案方式

截至本轮讨论，当前不建议成功 `toast` 写成：

- 很长的完整句子
- 携带过多数字
- 携带过多业务解释
- 与提示条重复过多状态信息

## 293. 基于当前结论的下一步建议

在确认成功 `toast` 的统一文案模板后，后续更适合继续讨论的是：
`失败 toast 或错误反馈是否也需要统一模板，还是优先交给提示条承接。`

## 294. 失败反馈与错误反馈的当前结论

本轮讨论已进一步确认，一期执行页中的失败反馈当前更建议：
`优先交给提示条承接，toast 只保留极少量补充。`

当前主要是因为失败通常不是一个“看一眼就可以消失”的信息，而是需要用户：

- 看清原因
- 回到当前输入继续修正
- 知道下一步怎么做

## 295. 当前建议优先用提示条承接的失败场景

截至本轮讨论，以下场景当前更建议优先由提示条承接：

- 校验失败
- 数量不合法
- 批次、货位或效期缺失
- 当前操作不满足提交条件
- 当前页内仍可继续修正的错误

这类信息当前更适合在页内持续可见，而不是快速消失。

## 296. 当前建议仅用极短 toast 补充的失败场景

截至本轮讨论，以下场景当前可考虑用极短 `toast` 作为补充：

- 非阻断性的后台失败提示
- 某个轻量动作失败，但页内已有主提示
- 作为“失败已发生”的瞬时提醒

但当前不建议让 `toast` 承担失败反馈的主承载角色。

## 297. 失败提示条的当前文案模板建议

截至本轮讨论，失败提示条当前更建议统一采用：
`动作未完成 + 原因`

例如：

- `本次收货未完成，请先填写批次`
- `本次上架未完成，请先选择目标货位`
- `本次拣货未完成，本次数量不可超过剩余数量`
- `本次复核未完成，请先选择复核结果`

## 298. 当前阶段的成功与失败反馈收口建议

截至本轮讨论，当前更推荐统一收敛为：

- 成功优先 `toast`
- 失败优先提示条
- 成功文案采用：`动作结果 + 当前对象`
- 失败文案采用：`动作未完成 + 原因`

## 299. 基于当前结论的下一步建议

在确认成功与失败反馈的分工后，后续更适合继续讨论的是：
`成功 toast 和提示条的显示时长、消失方式是否需要统一。`

## 300. 成功 toast 与提示条的时长和消失方式结论

本轮讨论已进一步确认，一期执行页中：

- `成功 toast`
  - 短时显示
  - 自动消失
  - 不要求用户手动关闭
- `提示条`
  - 默认持续显示
  - 直到被新提示替换，或当前状态解除
  - 不依赖自动消失

## 301. 当前推荐这一处理方式的主要原因

截至本轮讨论，当前更推荐上述处理方式，主要因为：

- `toast` 的职责是快速反馈“刚刚成功了”
- `提示条` 的职责是持续表达“当前状态仍然成立”

也就是说：

- `toast` 应短、轻、尽快让位给页面本身
- `提示条` 应稳、清晰、由状态驱动

## 302. 当前不建议一期优先采用的方式

截至本轮讨论，当前不建议一期优先采用：

- 让成功 `toast` 长时间悬挂
- 让错误或状态类提示条自动消失
- 让两者都依赖手动关闭

这些做法要么会让页面过吵，要么会削弱反馈的可用性。

## 303. 基于当前结论的下一步建议

在确认成功 `toast` 与提示条的时长和消失方式后，后续更适合继续讨论的是：
`执行页里是否需要给提示条增加手动关闭能力。`

## 304. 当前仍待继续讨论的主题清单

为便于后续继续衔接讨论，当前仍未完全收紧、或尚未展开到定稿层的主题主要包括以下几类。

### 304.1 执行页细化

- 提示条是否需要手动关闭
- 成功 `toast` 的具体显示时长
- 不同提示之间的替换节奏
- 顶部、中部、底部在移动端或窄屏下的退化方式
- 右侧执行区的扫码节奏设计
- 空状态、成功提示、失败提示的视觉细节

### 304.2 执行流程与状态机

- `receive / putaway / pick / check` 四个执行记录的更细状态流转
- 每个动作的异常分支
- `完成本次记录` 之后的后续流转

## 306. 提示条手动关闭能力的当前结论

本轮讨论已进一步确认，执行页中的提示条当前建议：
`不是统一都可关闭，而是只给“非阻断、非状态型提示”手动关闭能力。`

当前更推荐按提示类型分层处理，而不是一刀切。

## 307. 当前不建议允许手动关闭的提示类型

截至本轮讨论，以下提示当前不建议允许手动关闭：

- 阻断性校验
- 当前仍成立的记录状态提示
- 当前仍成立的关键引导

例如：

- `请先填写批次`
- `请先选择目标货位`
- `本次数量不可超过剩余数量`
- `当前记录已满足完成条件`

## 308. 当前可以允许手动关闭的提示类型

截至本轮讨论，以下提示当前可允许手动关闭：

- 一次性的轻提醒
- 已经过时的动作结果提示
- 不影响当前继续操作的辅助引导

例如：

- `当前项已完成`
- `可继续处理下一条`
- `已切换到下一条`

## 309. 提示条关闭后再次出现的当前结论

本轮讨论已进一步确认，提示条关闭后是否再次出现，当前建议按以下原则处理：

`只有当提示对应的状态重新成立，或者用户进入了新的相关上下文时，才再次出现。`

当前不建议用户刚关闭后，页面一刷新或轻微联动就原样反复出现。

## 310. 各类提示关闭后再次出现的当前建议

### 错误或校验类提示

这类提示当前一般不允许手动关闭，因此当前建议按以下方式处理：

- 问题未解决时持续显示
- 问题解决后自动消失
- 新问题出现时由新提示替换

### 状态类提示

若后续某些状态类提示支持关闭，当前建议：

- 在同一状态周期内关闭一次后不重复出现
- 状态发生变化后，如新状态需要提示，可再次出现

### 辅助引导类提示

当前建议：

- 用户关闭后，在当前行或当前记录上下文内不再出现
- 切换到新的明细、记录或执行页后，可重新判断是否出现

## 311. 当前阶段关于提示条关闭与重现的统一收口

截至本轮讨论，当前更推荐统一收敛为：

- `错误提示`
  - 不支持关闭
  - 问题解除才消失
- `状态提示`
  - 若支持关闭，则同一状态周期内不重复出现
- `引导提示`
  - 关闭后在当前上下文内静默
  - 状态变化或上下文切换后可重新判断

## 312. 基于当前结论的下一步建议

在确认提示条关闭与再次出现的规则后，后续更适合继续讨论的是：
`提示条是否需要区分成功、警告、错误三种颜色语义。`

## 313. 提示条颜色语义的当前结论

本轮讨论已进一步确认，一期执行页中的提示条当前建议区分以下三种颜色语义：

- `成功`
- `警告`
- `错误`

当前不建议一期继续细分为更多颜色级别。

## 314. 当前建议只分三种颜色语义的主要原因

截至本轮讨论，当前更推荐只分成功、警告、错误三种颜色语义，主要因为：

- 足以覆盖一期执行页中的主要提示类型
- 更容易和物流模块现有风格保持一致
- 不会因为颜色层级过多而让提示体系变重

## 315. `成功` 语义的当前建议

截至本轮讨论，`成功` 语义当前更适合承接：

- 当前动作成功完成后的页内短状态
- 当前记录已满足完成条件
- 当前项已完成

这类提示的共同特点是：

- 语气正向
- 不带风险
- 更偏“已完成 / 已满足”

## 316. `警告` 语义的当前建议

截至本轮讨论，`警告` 语义当前更适合承接：

- 当前仍可继续操作，但需要注意
- 不属于报错，也不属于成功
- 带有提醒、待处理、可收尾等含义

例如：

- `当前记录已满足完成条件，可点击“完成本次记录”收尾`
- `当前无可处理项，可调整筛选后继续`
- `已切换到下一条，请继续处理`

## 317. `错误` 语义的当前建议

截至本轮讨论，`错误` 语义当前更适合承接：

- 阻断性校验
- 当前动作未完成
- 必须先修正才能继续

例如：

- `请先填写批次`
- `请先选择目标货位`
- `本次数量不可超过剩余数量`

## 318. 当前不建议的颜色语义使用方式

截至本轮讨论，当前不建议：

- 把所有非成功提示都统一打成错误
- 把“可继续操作的提醒”也用错误色
- 再单独拆出更多低频颜色层级

## 319. 当前阶段的统一收口建议

截至本轮讨论，当前更推荐统一收敛为：

- 成功：表达完成
- 警告：表达提醒
- 错误：表达阻断

## 320. 基于当前结论的下一步建议

在确认提示条采用成功、警告、错误三种颜色语义后，后续更适合继续讨论的是：
`这三种颜色语义分别对应哪些典型提示文案。`

## 321. 三种颜色语义对应的典型提示文案结论

本轮讨论已进一步确认，一期执行页中的提示条文案当前建议按颜色语义固化少量标准句式，后续尽量复用，不建议每个页面自由发挥。

## 322. `成功` 语义的当前典型文案建议

截至本轮讨论，`成功` 语义当前更建议优先使用以下类型的表达：

- `当前项已完成`
- `当前记录已满足完成条件`
- `本次处理已完成`

这类文案当前主要用于表达：

- 已完成
- 已满足
- 已就绪

## 323. `警告` 语义的当前典型文案建议

截至本轮讨论，`警告` 语义当前更建议优先使用以下类型的表达：

- `当前无可处理项，可调整筛选后继续`
- `已切换到下一条，请继续处理`
- `当前记录已满足完成条件，可点击“完成本次记录”收尾`

这类文案当前主要用于表达：

- 当前仍可继续
- 但需要注意
- 或需要采取下一步动作

## 324. `错误` 语义的当前典型文案建议

截至本轮讨论，`错误` 语义当前更建议优先使用以下类型的表达：

- `本次收货未完成，请先填写批次`
- `本次上架未完成，请先选择目标货位`
- `本次拣货未完成，本次数量不可超过剩余数量`
- `本次复核未完成，请先选择复核结果`

这类文案当前更推荐统一为：
`动作未完成 + 原因`

## 325. 当前阶段的文案收口建议

截至本轮讨论，当前更推荐团队后续优先按以下三条统一理解提示条文案：

- 成功：`完成 / 满足 / 就绪`
- 警告：`提醒 / 继续 / 收尾`
- 错误：`未完成 + 原因`

## 326. 基于当前结论的下一步建议

在确认提示条三类颜色语义对应的典型文案后，后续更适合继续讨论的是：
`执行页这条线是否先暂停，转去讨论核心业务单据状态机。`

## 327. 当前建议从执行页切换到核心业务单据状态机

截至本轮讨论，执行页这条线已经对以下内容形成了较完整的讨论基础：

- 页面骨架
- 左右分区
- 顶部上下文区
- 底部 tab 区
- 提示条、toast、弹窗
- 风险动作与未保存录入

因此，当前更推荐先将执行页这一条线阶段性收住，转去继续讨论：
`核心业务单据状态机`

## 328. 入库单一期状态机的当前建议

本轮讨论已进一步确认，入库单一期当前建议先采用以下 7 个状态：

- `draft`
- `waiting_receipt`
- `receipting`
- `received`
- `putawaying`
- `done`
- `cancel`

对应当前建议理解为：

- `draft`：草稿
- `waiting_receipt`：待收货
- `receipting`：收货中
- `received`：已收货待上架
- `putawaying`：上架中
- `done`：已完成
- `cancel`：已取消

## 329. 当前建议保留 `received` 的原因

截至本轮讨论，当前更建议保留 `received`，主要因为：

- 能明确区分“货还没收到”与“货已到仓但还未上架”
- 是真实存在且有管理价值的中间业务状态
- 有利于待上架列表、上架入口和库存口径的收敛

当前不建议把 `received` 直接并入 `putawaying`。

## 330. 当前建议保留 `putawaying` 的原因

截至本轮讨论，当前更建议保留 `putawaying`，主要因为：

- 上架通常不是瞬时动作
- 可能存在部分上架、分货位上架、多人分批上架
- 保留“上架中”有利于表达真实现场进度

当前不建议把 `putawaying` 直接并入 `done`。

## 331. `done` 与 `cancel` 的当前口径建议

截至本轮讨论，当前建议：

- `done` 只表示收货与上架都已完成
- `cancel` 作为独立终态保留

当前不建议把“已收货但未上架”也计入 `done`。

## 332. 当前阶段关于入库单状态机的统一收口

截至本轮讨论，当前更推荐统一收敛为：

- 入库单一期先保留以上 7 个状态
- 当前不建议合并 `received`
- 当前不建议合并 `putawaying`

## 333. 基于当前结论的下一步建议

在确认入库单一期状态机的状态集合后，后续更适合继续讨论的是：
`这 7 个状态各自的进入条件和退出条件。`

## 334. `draft` 的进入条件与退出条件建议

截至本轮讨论，入库单 `draft` 当前建议按以下方式理解：

### 进入条件

- 新建入库单
- 或导入后先落草稿

### 退出条件

- 用户确认生效或提交，进入 `waiting_receipt`
- 用户主动取消，进入 `cancel`

当前建议 `draft` 阶段仍属于准备态，不产生真正执行动作。

## 335. `waiting_receipt` 的进入条件与退出条件建议

截至本轮讨论，入库单 `waiting_receipt` 当前建议按以下方式理解：

### 进入条件

- 草稿提交成功
- 入库单已生效，但尚未开始收货

### 退出条件

- 用户开始收货，进入 `receipting`
- 未开始收货前允许取消，进入 `cancel`

当前关键点是：

- 该状态仅表示“可收货”
- 尚未发生真正收货执行

## 336. `receipting` 的进入条件与退出条件建议

截至本轮讨论，入库单 `receipting` 当前建议按以下方式理解：

### 进入条件

- 第一次正式进入收货执行
- 或第一笔有效收货动作产生

### 退出条件

- 全部应收数量已完成收货，进入 `received`
- 收货过程中继续保持 `receipting`

当前这一状态的核心含义是：

- 已经开始收货
- 但还未全部收完

## 337. `received` 的进入条件与退出条件建议

截至本轮讨论，入库单 `received` 当前建议按以下方式理解：

### 进入条件

- 入库单全部应收内容已完成收货
- 但尚未开始或尚未完成上架

### 退出条件

- 开始上架，进入 `putawaying`
- 若收完即全部一键完成上架，理论上也可直接进 `done`，但当前更建议显式经过 `putawaying`

当前这一状态的核心含义是：

- 收货闭环已完成
- 上架闭环尚未开始或未完成

## 338. `putawaying` 的进入条件与退出条件建议

截至本轮讨论，入库单 `putawaying` 当前建议按以下方式理解：

### 进入条件

- 第一次正式开始上架
- 或第一笔有效上架动作产生

### 退出条件

- 全部待上架内容已完成，进入 `done`
- 上架未完成则继续保持 `putawaying`

当前这一状态的核心含义是：

- 已进入库内落位过程
- 但还未全部落位完成

## 339. `done` 的进入条件与退出条件建议

截至本轮讨论，入库单 `done` 当前建议按以下方式理解：

### 进入条件

- 收货完成
- 上架完成
- 入库单不再存在待处理数量

### 退出条件

- 无正常退出，作为终态
- 后续若涉及逆向操作，应走特殊流程，不建议直接常规回退

## 340. `cancel` 的进入条件与退出条件建议

截至本轮讨论，入库单 `cancel` 当前建议按以下方式理解：

### 进入条件

- 在允许取消的阶段被用户或系统取消

### 退出条件

- 无正常退出，作为终态

## 341. 当前阶段关于入库单状态推进的统一原则

截至本轮讨论，当前更推荐统一收敛为：

`状态推进尽量由真实业务动作触发，而不是仅靠人工改状态。`

也就是说：

- 开始收货，才进入 `receipting`
- 全部收完，才进入 `received`
- 开始上架，才进入 `putawaying`
- 全部上架完成，才进入 `done`

## 342. 基于当前结论的下一步建议

在确认入库单 7 个状态的进入条件与退出条件后，后续更适合继续讨论的是：
`入库单在哪些状态允许取消，哪些状态不允许取消。`

## 343. 入库单取消边界的当前结论

本轮讨论已进一步确认，一期入库单的取消规则当前建议收得较保守：

### 允许普通取消

- `draft`
- `waiting_receipt`

### 谨慎允许 / 原则上不建议直接取消

- `receipting`

### 不建议直接取消

- `received`
- `putawaying`
- `done`
- `cancel`

## 344. 当前建议允许 `draft / waiting_receipt` 普通取消的原因

截至本轮讨论，当前更建议允许 `draft` 和 `waiting_receipt` 直接取消，主要因为：

- 尚未发生真实仓储动作
- 尚未形成收货或上架事实
- 取消代价最低

因此，这两个状态一期当前可直接开放普通取消。

## 345. 当前对 `receipting` 的谨慎建议

截至本轮讨论，当前不建议把 `receipting` 做成“无脑可取消”状态，主要因为：

- 此时已经开始收货
- 可能存在部分已收
- 可能已经产生执行数据
- 直接取消会带来回滚、异常记录、执行数据清理等问题

因此，当前更建议：

- `receipting` 默认不开放普通取消按钮
- 若业务上确需终止，后续应作为特殊处理流程继续讨论

## 346. 当前不建议直接取消 `received / putawaying / done / cancel` 的原因

截至本轮讨论，当前不建议直接取消以下状态：

### `received`

因为此时收货已完成，只是尚未上架，不宜再用普通取消去表达业务终止。

### `putawaying`

因为此时已经开始上架，更适合进入异常、逆向或调整流程，而不是普通取消。

### `done`

因为其为完成终态，不应再直接取消。

### `cancel`

因为其本身已为取消终态。

## 347. 当前阶段关于入库单取消规则的统一收口

截至本轮讨论，当前更推荐统一收敛为：

`一期普通取消只开放到 draft / waiting_receipt；一旦开始真实收货，就不再走普通取消，而应转异常或特殊处理。`

## 348. 基于当前结论的下一步建议

在确认入库单普通取消边界后，后续更适合继续讨论的是：
`receipting 阶段如果业务上确实要终止，应该怎么命名和怎么处理。`

## 349. `receipting` 阶段终止的当前命名建议

本轮讨论已进一步确认，若入库单在 `receipting` 阶段因业务原因无法继续，当前不建议继续沿用普通的 `cancel` 命名。

当前更推荐的候选命名为：

- `receipt_terminated`
- `receipt_aborted`

其中，当前更偏向：

- `receipt_terminated`

主要因为其语义更中性，更适合表达“已开始收货，但已终止继续处理”的业务含义。

## 350. 当前不建议继续使用 `cancel` 的原因

截至本轮讨论，当前不建议在 `receipting` 阶段仍使用 `cancel`，主要因为：

- `cancel` 已被定义为未开始真实仓储动作前的普通取消
- `receipting` 阶段终止本质上属于已开始收货后的异常终止
- 两者在业务语义上不应混为一类

## 351. `receipting` 阶段终止的当前处理口径

截至本轮讨论，若 `receipting` 阶段业务上确需终止，当前更建议按以下原则处理：

### 1. 视为异常终态，而非普通终态

它不是“未开始前的普通取消”，而是“已开始收货但无法继续正常完成”的异常终止。

### 2. 保留已发生事实

当前建议：

- 已经完成的收货事实继续保留
- 不为了让主单状态回到普通取消而抹掉执行痕迹

### 3. 主单不进入 `cancel`

当前建议：

- 主单不回到 `cancel`
- 而是进入一个单独的终止或异常状态

### 4. 后续靠异常或补充流程处理

例如：

- 人工补录说明
- 转异常单
- 后续补单、补上架或调整流程

## 352. 当前阶段关于 `receipting` 终止的统一收口

截至本轮讨论，当前更推荐统一收敛为：

`receipting` 阶段若确需终止，应进入独立的“收货终止”类异常状态，而不是回到普通 `cancel`。

## 353. 基于当前结论的下一步建议

在确认 `receipting` 阶段终止的命名与处理口径后，后续更适合继续讨论的是：
`入库单一期是否真的要把这个“收货终止”状态纳入主状态机，还是先只作为异常流程挂在外围。`

## 354. `receipt_terminated` 是否纳入入库单主状态机的当前结论

本轮讨论已进一步确认，一期当前更建议：

`先不要把 receipt_terminated 这类状态纳入入库单主状态机，而是先挂在异常流程外围。`

也就是说，入库单一期主状态机当前仍建议保持以下 7 个主状态：

- `draft`
- `waiting_receipt`
- `receipting`
- `received`
- `putawaying`
- `done`
- `cancel`

## 355. 当前建议先挂外围异常流程的主要原因

截至本轮讨论，当前更推荐先将 `receipt_terminated` 挂在异常流程外围，主要因为：

1. 有利于先稳住主线状态机
2. 异常状态通常不是主线高频状态
3. 更利于一期先落地，不必过早把主状态机做重
4. 可以避免后续更多异常状态不断膨胀主状态字段

## 356. 若 `receipt_terminated` 挂外围，主单主状态的当前结论

本轮讨论已进一步确认，若 `receipt_terminated` 挂在外围异常流程，主单主状态当前更建议停在：

- `receipting`

当前更推荐的理解是：

- 主状态仍表示“已开始收货但未完成”
- 异常补充状态再表达“已终止继续处理”

## 357. 当前建议主状态停在 `receipting` 的主要原因

截至本轮讨论，当前更推荐主状态停在 `receipting`，主要因为：

- 最符合“已开始收货但未完成”的真实业务事实
- 不会误导成“已收货完成”
- 不会误导成“尚未开始收货”
- 不需要为了异常状态污染主状态机

当前不建议：

- 主状态退回 `waiting_receipt`
- 主状态硬改成 `cancel`
- 主状态冒充 `received`

## 358. 当前建议的系统层与页面层口径

截至本轮讨论，当前更建议先按以下两层理解：

### 系统层

- 主状态：`receipting`
- 异常补充状态：`receipt_terminated` 或类似字段

### 页面层

可对用户展示为：

- `收货中` + `已终止`

或组合表达为：

- `收货异常终止`

## 359. 基于当前结论的下一步建议

在确认“主状态 + 异常补充状态”的分工后，后续更适合继续讨论的是：
`这种“主状态 + 异常补充状态”在页面上应如何显示得最清楚。`

## 360. 主状态与异常补充状态的页面展示结论

本轮讨论已进一步确认，页面上对于“主状态 + 异常补充状态”的展示，当前更建议采用：
`主状态占主位，异常补充状态做高辨识次标签`

当前不建议把两者完全混成一个单独状态名，也不建议只显示其中一个让用户自行猜测。

## 361. 当前推荐两层显示的主要原因

截至本轮讨论，当前更推荐两层显示，主要因为：

- 可以保留主流程状态机的清晰性
- 可以单独表达异常信息
- 更利于后续列表、详情、筛选的统一口径

## 362. 当前建议的页面展示方式

截至本轮讨论，当前更建议页面统一按以下两层显示：

### 1. 主状态

仍显示主流程状态，例如：

- `收货中`
- `待收货`
- `已收货`
- `上架中`

主状态当前应继续占据主位，颜色和位置都按主状态体系走。

### 2. 异常补充状态

若存在异常补充状态，则在主状态旁边增加明显次标签，例如：

- `已终止`
- `异常`
- `待处理`

当前针对 `receipt_terminated` 场景，更建议显示为：

- 主状态：`收货中`
- 次标签：`已终止`

## 363. 当前不建议直接合并成单一状态文案的原因

截至本轮讨论，当前不建议直接只显示：

- `收货异常终止`

主要因为这样会削弱主状态与异常补充状态的边界，不利于用户理解“主状态仍然停在 receipting，异常信息来自外围补充”。

## 364. 列表页、详情页与筛选的当前建议口径

截至本轮讨论，当前更建议：

### 列表页

- 主状态徽标：`收货中`
- 异常次标签：`已终止`

### 详情页头部

- 主状态：`收货中`
- 异常标记：`已终止`
- 可补一句状态说明文案

### 筛选 / 搜索

- 主状态仍按 `receipting` 归类
- 同时支持按异常补充状态做额外筛选

## 365. 当前阶段的统一收口建议

截至本轮讨论，当前更推荐统一收敛为：

`页面上主状态和异常补充状态分两层显示：主状态占主位，异常补充状态做高辨识次标签。`

## 366. 基于当前结论的下一步建议

在确认主状态与异常补充状态的页面展示方式后，后续更适合继续讨论的是：
`异常补充状态除了 receipt_terminated，一期是否还要预留一组统一枚举。`

## 367. 异常补充状态统一枚举的当前结论

本轮讨论已进一步确认，一期当前更建议为“异常补充状态”预留一组统一枚举，而不是只为了 `receipt_terminated` 临时增加一个孤立字段值。

但当前不建议一开始就预留过大的一组异常枚举。

## 368. 异常补充状态一期当前建议预留的轻量枚举

截至本轮讨论，异常补充状态一期当前更建议先预留以下 3 个轻量枚举：

- `terminated`
- `exception`
- `pending_action`

## 369. `terminated` 的当前建议口径

截至本轮讨论，`terminated` 当前更建议表达：

- 当前主流程已被终止
- 不能继续按原路径自然推进

它当前可以覆盖：

- `receipt_terminated`

也就是说，页面可显示为：

- 主状态：`收货中`
- 异常补充：`已终止`

## 370. `exception` 的当前建议口径

截至本轮讨论，`exception` 当前更建议表达：

- 当前流程存在明确异常
- 但不一定已经终止

例如后续可能扩展到：

- 异常待确认
- 异常待补录
- 异常待处理

一期当前不建议继续细拆，但建议先把这个口子预留出来。

## 371. `pending_action` 的当前建议口径

截至本轮讨论，`pending_action` 当前更建议表达：

- 当前主流程本身未结束
- 但已经进入等待人工动作或补充动作的状态

后续可扩展到例如：

- 待人工确认
- 待异常处理
- 待补资料

## 372. 当前不建议一期优先预留过多异常枚举

截至本轮讨论，当前不建议一期优先预留过多异常补充状态，例如：

- `partial_done`
- `rollbacking`
- `reopened`
- `awaiting_review`
- `force_closed`

当前主要是为了避免异常补充状态本身也过早膨胀。

## 373. 当前阶段关于异常补充状态的统一收口

截至本轮讨论，当前更推荐统一收敛为：

`一期异常补充状态可以统一预留，但先只收成 terminated / exception / pending_action 三个轻量枚举。`

## 374. 基于当前结论的下一步建议

在确认异常补充状态统一预留的轻量枚举后，后续更适合继续讨论的是：
`入库单一期是否真的需要把这 3 个都用上，还是先只启用 terminated。`

## 375. 入库单一期异常补充状态启用范围的当前结论

本轮讨论已进一步确认，入库单一期当前更建议：

- 枚举层面先预留：
  - `terminated`
  - `exception`
  - `pending_action`
- 业务启用层面先只实际落地：
  - `terminated`

## 376. 当前建议一期只启用 `terminated` 的主要原因

截至本轮讨论，当前更推荐一期只启用 `terminated`，主要因为：

1. 当前已经具备明确业务场景的，只有 `terminated`
2. `exception / pending_action` 目前仍更偏向未来扩展预留
3. 若一期同时启用三者，会明显增加前端展示、筛选、联动和文案复杂度
4. `terminated` 的业务语义当前最清楚，最适合作为第一步落地

## 377. 当前阶段关于异常补充状态启用范围的统一收口

截至本轮讨论，当前更推荐统一收敛为：

`一期先预留 3 个异常补充枚举，但只实际启用 terminated。`

也就是说：

- 模型允许未来扩展
- 一期真实业务流只使用 `terminated`
- `exception / pending_action` 暂不进入真实业务流和页面筛选主口径

## 378. 基于当前结论的下一步建议

在确认入库单一期只启用 `terminated` 后，后续更适合继续讨论的是：
`terminated 一期需要哪些最小配套字段。`

## 379. `terminated` 一期最小配套字段的当前结论

本轮讨论已进一步确认，`terminated` 一期当前建议只保留以下最小配套字段：

- `exception_state`
- `terminated_reason`
- `terminated_remark`
- `terminated_by`
- `terminated_at`

当前不建议一期一开始就把它做成完整异常中心。

## 380. `terminated_reason` 一期是否统一枚举的当前结论

本轮讨论已进一步确认，`terminated_reason` 一期当前建议：

- 做成统一轻量枚举
- 同时配一个 `terminated_remark` 作为补充说明

当前建议一期先收为以下 4 类：

- `customer_cancel`
- `goods_issue`
- `warehouse_issue`
- `other`

## 381. `terminated` 的发起权限当前建议

截至本轮讨论，`terminated` 当前不建议开放过宽，一期先只建议允许以下角色发起：

- 仓管主管 / 组长
- 有专门异常处理权限的人

当前不建议普通收货操作员直接终止整张入库单。

## 382. 触发 `terminated` 后主单与执行记录的当前处理建议

截至本轮讨论，触发 `terminated` 后，当前更建议：

- 主单主状态仍停在 `receipting`
- 异常补充状态置为 `terminated`
- 已产生的收货事实继续保留
- 未完成部分不再继续按正常主线推进
- 后续只通过异常处理或人工补充流程继续处理

## 383. `terminated` 的当前页面展示建议

截至本轮讨论，页面上当前更建议这样表达：

### 列表页

- 主状态：`收货中`
- 次标签：`已终止`

### 详情页头部

- 同样显示主状态 + 次标签

### 详情页异常信息区

补充展示：

- 终止原因
- 终止备注
- 终止人
- 终止时间

## 384. 一期是否支持“终止后恢复”的当前结论

本轮讨论已进一步确认，一期当前建议：

- 先不支持“终止后恢复”按钮

一期先只做到：

- 能终止
- 能看终止信息
- 能通过后续新单或补充流程处理

当前不建议一开始就把“恢复主线”纳入范围，以免状态机过早膨胀。

## 385. 当前阶段关于 `terminated` 的统一收口

截至本轮讨论，当前更推荐统一收敛为：

1. 一期最小字段只做：状态、原因、备注、操作人、时间
2. `terminated_reason` 做轻量统一枚举
3. `terminated` 仅开放给主管或异常处理权限角色
4. 触发后主状态停在 `receipting`，异常补充状态置为 `terminated`
5. 一期先不支持“终止后恢复”

## 386. 基于当前结论的下一步建议

为保持讨论节奏更整组化，后续更适合继续以 3 到 5 个问题为一组，继续讨论：
`入库单 done 之后是否需要预留逆向处理、上架异常如何表达、received/putawaying 阶段的异常边界、入库单头部是否显示异常补充状态筛选、以及入库单是否需要“待异常处理”视图。`

## 387. `done` 之后是否预留逆向处理入口的当前结论

本轮讨论已进一步确认，入库单在 `done` 之后：

- 需要预留逆向处理概念
- 但一期先不做成主流程入口

当前更建议：

- `done` 仍保持为终态
- 若后续确需处理，走单独异常或调整流程
- 不直接在主单上做“反完成 / 回退”按钮

## 388. `received / putawaying` 阶段异常表达的当前结论

本轮讨论已进一步确认，若 `received / putawaying` 阶段出现异常，当前也建议继续沿用：
`主状态 + 异常补充状态`

也就是说：

- `received` 阶段出异常，主状态仍为 `received`
- `putawaying` 阶段出异常，主状态仍为 `putawaying`
- 异常统一挂外围补充状态

当前更建议整条入库主线都保持这一表达方式，而不是不同阶段采用不同异常机制。

## 389. 是否需要“待异常处理”视图的当前结论

本轮讨论已进一步确认，一期当前建议提供：
`轻量的待异常处理视图`

当前建议其最小能力为：

- 只看存在异常补充状态的单据
- 支持按仓库、货主、主状态、异常补充状态筛选

当前不建议一期就把它做成复杂异常工作台。

## 390. 入库单列表/搜索按异常补充状态筛选的当前结论

本轮讨论已进一步确认，入库单列表与搜索当前建议支持按异常补充状态筛选。

一期当前建议最小支持：

- `全部`
- `仅看异常`
- `仅看已终止`

若后续异常补充状态真正扩起来，再继续细分。

## 391. 入库单详情页“异常处理信息区”的当前结论

本轮讨论已进一步确认，入库单详情页当前建议单独设置：
`异常处理信息区`

当前不建议把异常信息零散塞进备注中。

一期当前建议最小展示：

- 异常补充状态
- 原因
- 备注
- 处理人
- 时间

## 392. 当前阶段关于入库单异常处理的一组统一收口

截至本轮讨论，当前更推荐统一收敛为：

1. `done` 后逆向处理先预留概念，不做主流程入口
2. `received / putawaying` 出异常也统一走外围异常补充状态
3. 一期应有轻量“待异常处理”视图
4. 入库单列表要支持按异常补充状态筛选
5. 详情页要单独有异常处理信息区

## 393. 基于当前结论的下一步建议

后续更适合继续以一组问题推进：
`出库单一期状态机怎么定、哪些状态允许取消、是否复用“主状态 + 异常补充状态”、以及拣货/复核失败时主单应停在哪个状态。`

## 394. 出库单一期主状态机的当前结论

本轮讨论已进一步确认，出库单一期当前建议先采用以下 8 个主状态：

- `draft`
- `waiting_pick`
- `picking`
- `picked`
- `checking`
- `waiting_ship`
- `done`
- `cancel`

对应当前建议理解为：

- `draft`：草稿
- `waiting_pick`：待拣货
- `picking`：拣货中
- `picked`：已拣货待复核
- `checking`：复核中
- `waiting_ship`：待发货
- `done`：已发货完成
- `cancel`：已取消

当前不建议一期在 `picked` 与 `waiting_ship` 之间继续提前扩张过多主状态。

## 395. 出库单取消边界的当前结论

本轮讨论已进一步确认，出库单一期当前建议：

### 允许普通取消

- `draft`
- `waiting_pick`

### 谨慎允许 / 原则上不建议普通取消

- `picking`
- `picked`
- `checking`

### 不建议直接取消

- `waiting_ship`
- `done`
- `cancel`

当前阶段更推荐统一收敛为：

`一期普通取消只开放到 draft / waiting_pick。`

## 396. 出库单异常表达方式的当前结论

本轮讨论已进一步确认，出库单一期当前也建议复用：
`主状态 + 异常补充状态`

也就是说：

- 主状态继续表达主流程位置
- 异常补充状态表达当前单据出现的额外问题

当前建议出库单与入库单保持同一套设计思想，以便统一：

- 列表展示
- 筛选
- 异常处理视图
- 详情页表达

## 397. 拣货 / 复核失败时主状态停留位置的当前结论

本轮讨论已进一步确认，若拣货或复核失败，当前更建议：

### 拣货失败

- 主状态停在 `picking`
- 异常补充状态挂外围

### 复核失败

- 主状态停在 `checking`
- 异常补充状态挂外围

当前不建议：

- 拣货失败退回 `waiting_pick`
- 复核失败退回 `picked`

主要因为这样会抹掉“已进入执行阶段”的真实事实。

## 398. 当前阶段关于出库单主线与异常的一组统一收口

截至本轮讨论，当前更推荐统一收敛为：

1. 出库单一期主状态机建议：
   `draft -> waiting_pick -> picking -> picked -> checking -> waiting_ship -> done / cancel`
2. 普通取消只开放到：
   `draft / waiting_pick`
3. 出库单也复用：
   `主状态 + 异常补充状态`
4. 拣货 / 复核失败时：
   主状态停在 `picking / checking`，异常挂外围

## 400. `checked` 是否纳入出库单一期主状态机的当前结论

本轮讨论已进一步确认，出库单一期当前不建议在 `picked` 与 `waiting_ship` 之间单独新增：

- `checked`

当前更建议：

- 复核完成后直接从 `checking` 进入 `waiting_ship`

主要因为：

- `checking` 已足够表达“进入复核”
- `waiting_ship` 已足够表达“复核完成后待发货”
- 额外新增 `checked` 会让主状态机变长，但一期收益有限

## 401. `waiting_ship` 是否允许回退到 `checking` 的当前结论

本轮讨论已进一步确认，`waiting_ship` 当前建议：

- 原则上不走普通回退到 `checking`
- 如发货前发现问题，应通过异常处理或人工处理重新进入复核

当前不建议一期提供普通“回退到 checking”按钮。

## 402. 出库单一期是否需要“待异常处理”视图的当前结论

`轻量的待异常处理视图`

当前建议其最小能力为：

- 只看存在异常补充状态的出库单
- 支持按仓库、货主、主状态、异常补充状态筛选

当前不建议一期就做成复杂异常工作台。

## 403. 出库单详情页“异常处理信息区”的当前结论

`异常处理信息区`

2. 拣货终止与复核终止在业务说明和页面文案上区分，但异常补充状态枚举不拆分
3. 出库单 `done` 后也只预留逆向处理概念，不做主流程回退
4. 发货前终止与发货后异常应明确区分两类处理口径

其中当前更建议：

- 发货前异常归仓管主线

## 407. 盘点单一期主状态机的当前结论

本轮讨论已进一步确认，盘点单一期当前建议先采用以下 5 个状态：

- `draft`
- `counting`
- `reviewing`
- `done`
- `cancel`

对应当前建议理解为：

- `draft`：草稿
- `counting`：盘点中
- `reviewing`：待确认 / 待审核差异
- `done`：已完成
- `cancel`：已取消

当前更建议保留 `reviewing`，因为盘点天然容易产生差异，需要有一个差异确认阶段。

## 408. 盘点单是否需要异常补充状态的当前结论

本轮讨论已进一步确认，盘点单一期当前不建议重点引入：
`主状态 + 异常补充状态`

当前更建议盘点单先通过以下内容表达盘点中的问题与分歧：

- 主状态
- 差异字段
- 差异确认结果

主要因为盘点单本身就天然带有差异处理属性，很多所谓异常实际上属于盘点主流程的一部分。

## 409. 移位单一期主状态机的当前结论

本轮讨论已进一步确认，移位单一期当前建议先采用以下 5 个状态：

- `draft`
- `waiting_execute`
- `executing`
- `done`
- `cancel`

对应当前建议理解为：

- `draft`：草稿
- `waiting_execute`：待执行
- `executing`：执行中
- `done`：已完成
- `cancel`：已取消

当前不建议一期把移位单状态机做得过重，因为它本质上是相对直接的库内执行动作。

## 410. 移位单取消与回退边界的当前结论

本轮讨论已进一步确认，移位单一期当前建议：

### 允许普通取消

- `draft`
- `waiting_execute`

### 谨慎允许 / 原则上不建议普通取消

- `executing`

### 不建议直接取消

- `done`
- `cancel`

关于“回退”，当前更建议：

- 一期不做普通回退按钮
- 若执行中出问题，先走异常说明或补充流程
- `done` 后若发现问题，走新移位单或调整流程，不回退原单

## 411. 当前阶段关于盘点单与移位单的一组统一收口

截至本轮讨论，当前更推荐统一收敛为：

1. 盘点单一期状态机建议：
   `draft -> counting -> reviewing -> done / cancel`
2. 盘点单一期先不重点做异常补充状态
3. 移位单一期状态机建议：
   `draft -> waiting_execute -> executing -> done / cancel`
4. 移位单普通取消只开放到 `draft / waiting_execute`，不做普通回退

## 412. 基于当前结论的下一步建议

后续更适合继续以一组问题推进：
`盘点单 reviewing 的进入/退出条件、盘点差异是否需要单独差异处理结果字段、移位单执行失败时主单停在哪个状态、以及移位单是否也需要轻量异常处理信息区。`

## 413. 盘点单 `reviewing` 的进入与退出条件结论

本轮讨论已进一步确认，盘点单 `reviewing` 当前更建议理解为：
`盘点执行完成，但盘点结果仍待确认 / 吸收的真实业务状态`

### 进入 `reviewing`

截至本轮讨论，当前建议在以下条件满足时进入：

- 盘点执行完成
- 已形成盘点结果
- 存在需要确认的差异或待确认结果

### 退出 `reviewing`

截至本轮讨论，当前建议在以下条件满足时退出：

- 差异已确认并处理完成，进入 `done`
- 用户放弃或作废，进入 `cancel`

## 414. 盘点差异处理结果字段的当前结论

本轮讨论已进一步确认，盘点差异当前建议单独设置：
`差异处理结果`

但一期当前更建议先做轻量结果体系，不宜过早做重。

当前建议一期先收为以下 3 类：

- `matched`
- `adjusted`
- `pending`

其中当前建议理解为：

- `matched`：无差异或已对齐
- `adjusted`：已按盘点结果完成调整
- `pending`：差异待处理

## 415. 移位单执行失败时主状态停留位置的当前结论

本轮讨论已进一步确认，若移位单执行失败，当前更建议：

- 主状态停在 `executing`

主要因为：

- 已经开始真实执行
- 失败不等于未开始
- 不建议退回 `waiting_execute`

当前若需对用户表达异常，页面上可通过异常说明或信息区补充。

## 416. 移位单轻量异常信息区的当前结论

`轻量异常信息区`

- 当前问题说明或失败原因
- 备注
- 处理人
- 时间

它不一定必须命名为“异常处理信息区”，也可以使用更贴近执行语义的名称，但当前更建议在详情页中单独成块。

## 417. 当前阶段关于盘点与移位的一组统一收口

截至本轮讨论，当前更推荐统一收敛为：

1. `reviewing` 是盘点完成后、结果确认前的真实业务状态
2. 盘点差异应单独有轻量“差异处理结果”字段

## 446. 第一版建议优先写死的 10 条统一规则

### 规则 1

`主跳转路径统一为：列表 -> 详情 -> 执行 / 处理子动作`

### 规则 2

`详情页统一采用：头部 + 主信息 + 执行记录 + 异常信息 + 日志`

### 规则 3

`执行页统一采用：顶部上下文 + 中部主从双栏 + 底部 tab`

### 规则 4

`头部字段统一采用：公共字段 + 少量单据特有字段`

### 规则 5

`顶部按钮统一只放页面级 / 记录级动作，不放当前动作级按钮`

### 规则 6

`左侧列表统一采用表格，不用卡片作为主形态`

### 规则 7

`状态表达统一采用：主状态占主位，异常补充状态做次标签`

### 规则 8

`列表筛选统一采用：公共筛选骨架 + 单据补一个关键维度`

### 规则 9

`提示反馈统一采用：提示条 / toast / 弹窗三层分工`

### 规则 10

`done 统一视为终态，后续问题走新单、异常或调整流程，不直接回退原单`

## 447. 当前建议优先写死这 10 条规则的主要原因

截至本轮讨论，当前更推荐优先写死这 10 条规则，主要因为它们已经覆盖了第一版页面结构规范中最核心的统一约束，包括：

- 页面骨架
- 跳转路径
- 按钮区职责
- 列表主形态
- 状态展示方式
- 筛选组织方式
- 反馈机制
- `done` 终态边界

## 448. 当前阶段关于统一页面结构规范第一版的统一收口

截至本轮讨论，当前更推荐统一收敛为：

- 先用这 10 条规则作为第一版统一页面结构规范的核心骨架
- 后续差异化说明、标准骨架示意和细节扩展都围绕这 10 条展开
