# 2026-05-07 小程序原始单表导入模式设计

## 1. 文档定位

本文档用于定义一套新的导入模式：

- 入口在小程序端
- 源文件是小程序侧上传的原始单表 Excel
- 服务端负责解析、清洗、匹配、预校验、确认导入
- 不再依赖人工先改 `数据输入表 / template` 后再回到系统导入

本文档面向：

- 小程序端入口设计
- `logistics_web` 导入接口设计
- `logistics_dispatch` 业务落库设计
- 后续实现拆分与联调验收

当前样例文件基准：

- 原始文件：[小程序导入原数据.xlsx](D:\Desktop\小程序导入原数据.xlsx)
- 现有加工模板：[小程序导入模板V1.xlsx](D:\Desktop\小程序导入模板V1.xlsx)

---

## 2. 背景与现状

当前小程序导入链路的真实业务过程是：

1. 从原始单表中提取 `收货单位 / 收货地址 / 发车单号`
2. 手工或脚本处理 merged cells
3. 先写入模板的 `数据输入表`
4. 做去重、汇总、客户信息匹配
5. 再通过 `template` 表生成最终导入数据
6. 最后导入系统

这条链路已经验证业务可行，但仍有 4 个明显问题：

1. 核心业务逻辑停留在 Excel 模板和脚本中，不在系统内
2. merged cells、去重、匹配失败等问题缺少系统级可追溯结果
3. 小程序侧无法直接给出预校验反馈与导入结果回显
4. `VLOOKUP` 和人工模板调整不适合作为长期正式路径

因此本次设计目标不是“把旧脚本照搬进项目”，而是把它升级成系统内的正式导入模式。

---

## 3. 结论概览

## 3.1 是否可以在小程序端做入口

可以。

但这里的“小程序端做入口”应理解为：

- 小程序端负责选择文件、上传文件、发起预校验、查看结果、确认导入
- 服务端负责解析 Excel、处理合并单元格、做客户匹配、生成标准导入结构、执行正式落库

不建议把以下逻辑放到小程序端：

- merged cells 解析
- 大批量行清洗
- 客户主数据匹配
- 最终导入确认判定
- 业务对象正式写库

原因是这些逻辑：

- 规则复杂且会持续演进
- 需要复用主数据与业务模型
- 需要可追溯和可审计
- 更适合放在 `logistics_web` + `logistics_dispatch` 的服务端边界中

## 3.2 本次关键业务决策

- 小程序原始文件中的 `发车单号` 直接作为 `batch_no`
- 客户信息底表的正式来源首期直接复用系统内客户/门店主数据：
  - `res.partner`
  - 已落库的 logistics customer/store profile 扩展数据
- 首期不再引入独立的“受控底表镜像”作为正式匹配源
- 匹配失败时：
  - 允许预校验通过到“可查看错误结果”
  - 不允许直接 confirm 成正式业务数据
  - 未匹配门店进入“待人工确认 / 待补主数据”状态
- 首期先沿用旧 Excel 模板的单命中口径：
  - 以 `客户名称/门店名称` 单字段命中为成功
  - 后续如业务确认需要更严规则，再升级为“名称 + 地址双命中”

## 3.3 推荐主链路

```text
小程序上传原始单表
-> 服务端解析原始表
-> 补齐 merged cells
-> 提取发车单号(batch_no)
-> 提取收货单位/收货地址
-> 标准化清洗
-> 去重汇总
-> 匹配客户信息底表
-> 形成标准 route planning 导入数据
-> 预校验结果回显
-> 用户确认导入
-> 写入 route planning draft / 后续业务对象
```

## 4. OBB

## 4.1 Outcome

本次能力落地后，应满足以下结果：

1. 小程序端可以直接上传原始单表 Excel，不再要求先人工加工为模板文件
2. 系统能够自动处理 merged cells，并正确提取 `收货单位 / 收货地址 / 发车单号`
3. 系统能够基于 `收货单位 + 收货地址` 与客户底表完成匹配
4. 系统能够在预校验阶段明确输出：
   - 重复行
   - 匹配失败行
   - 多命中行
   - 格式错误行
   - 可确认导入与不可确认导入结论
5. `发车单号` 直接作为 `batch_no`
6. 确认导入后，系统把数据写入正式导入链路承接对象，而不是依赖线下脚本中转

## 4.2 Behavior

用户在小程序端执行的标准行为为：

1. 打开“小程序原始导入”入口
2. 上传原始单表 `.xlsx`
3. 发起预校验
4. 查看解析摘要、去重结果、匹配结果和错误明细
5. 若全部关键错误已消除，则点击确认导入
6. 系统写入导入任务与排线草稿结果
7. 用户查看导入成功结果或错误报告

服务端必须保证以下行为：

1. 只接受约定的原始单表 `.xlsx`
2. 自动兼容 merged cells
3. 自动提取 `发车单号` 并映射为 `batch_no`
4. 同一 `batch_no + 标准化门店名 + 标准化地址` 只保留一条有效停靠点记录
5. 未匹配客户不得进入正式 confirm 成功态
6. 所有错误与警告都落在系统导入任务中，可回查

## 4.3 Boundary

本次设计明确边界如下。

本次包含：

- 小程序端上传入口
- 原始单表解析
- 合并单元格补齐
- 去重与标准化
- 客户底表匹配
- 预校验
- 确认导入
- 导入任务结果回显

本次不包含：

- 小程序端离线解析 Excel
- 小程序端本地做 `VLOOKUP`
- 司机侧权限体系重构
- 客户主数据中心大范围重构
- 完整的人工匹配工作台实现
- 自动经纬度补齐服务

本次默认复用：

- 现有 mini token 安全口径
- 现有导入任务模型
- 现有 route planning 导入结果承接方向

## 5. 基准与复用判断

## 5.1 当前最接近的现有能力

现有系统里最接近本次需求的能力有两套：

1. `route-planning` 单表导入
2. `phase5-workbook` 多表导入

其中：

- `route-planning` 更接近最终业务落点
- `phase5-workbook` 更接近“先解析外部 Excel，再映射系统对象”的处理方式

## 5.2 复用结论

推荐路径：

1. 复用现有导入任务主框架
2. 新增一种 object type：`mini_program_raw_sheet`
3. 在 `logistics_web` 中新增独立 import service
4. confirm 阶段复用 `route planning` 的业务落点思路

不建议直接扩写现有 `route-planning` service 的原因：

- 原始表结构与 route template 完全不同
- 需要单独处理 merged cells 和客户底表匹配
- 错误语义与 route planning 原模板并不相同

## 6.1 原始文件结构

[小程序导入原数据.xlsx](D:\Desktop\小程序导入原数据.xlsx) 当前特征：

- 单 sheet
- 第 2 行含 `发车单号`
- 第 4 行是业务表头
- 实际业务列至少包括：
  - `客户订单号`
  - `收货单位`
  - `收货地址`
- 存在大量 merged cells

## 6.2 模板 V1 结构

[小程序导入模板V1.xlsx](D:\Desktop\小程序导入模板V1.xlsx) 当前结构：

- `template`
- `数据输入表`
- `客户信息底表`

其本质作用是：

1. `数据输入表`
   - 提取原始列
   - 做去重汇总
2. `客户信息底表`
   - 提供门店主数据映射来源
3. `template`
   - 形成最终导入格式

本次系统化后，这三层逻辑仍保留，但迁移到服务端：

- `数据输入表` -> 系统内部 normalize staging
- `客户信息底表` -> 系统客户匹配源
- `template` -> 系统标准 route planning payload / 审计导出物

## 7.1 小程序端主流程

```text
选择原始单表
-> 上传文件
-> 调用预校验
-> 展示解析结果/错误/警告
-> 用户确认
-> 调用 confirm
-> 查看导入结果
```

## 7.2 服务端内部流程

```text
接收文件
-> 创建 source file
-> 解析 sheet
-> 识别标题区和数据区
-> 处理合并单元格补值
-> 提取 batch_no(发车单号)
-> 提取收货单位/收货地址
-> 标准化清洗
-> 生成业务主键
-> 去重汇总
-> 匹配客户底表
-> 形成 route stop 候选数据
-> 预校验
-> 若 confirm，则写入 route planning draft
```

## 8. 数据处理设计

## 8.1 原始解析规则

服务端需要识别以下关键位置：

1. 标题区：
   - `发车单号`
2. 表头区：
   - `收货单位`
   - `收货地址`
3. 数据区：
   - 表头下一行到最后一行有效记录

若表头文本存在轻微变体，允许按别名匹配。

建议别名支持：

- `收货单位`
- `收货地址`
- `发车单号`

## 8.2 合并单元格处理规则

对于 merged cells：

1. 先读取 merged range
2. 以左上角单元格为主值
3. 对 range 内所有业务读取位置执行“展开后视图”
4. 业务解析阶段拿到的是补齐后的值，而非原始空白值

建议实现方式：

- 不直接改原 workbook
- 在解析层生成一份 normalized cell map

## 8.3 标准化规则

### 门店名称标准化

- 去首尾空白
- 合并换行
- 压缩连续空格
- 中文括号/英文括号统一
- 全角符号统一到标准形式
- 去除仅用于展示的无意义换行

### 地址标准化

- 去首尾空白
- 合并换行
- 压缩连续空格
- 去除因 merged cell 或复制导致的多余换行

### 批次号标准化

- 从原始文件提取 `发车单号`
- 去空格
- 保持原始大小写与主编号文本
- 直接映射为 `batch_no`

## 8.4 去重规则

建议以以下业务键作为主去重键：

`batch_no + normalized_store_name + normalized_address`

行为：

1. 第一次出现的记录为主记录
2. 后续同键记录记为重复来源行
3. 主记录保留
4. 导入结果中记录：
   - `duplicate_source_row_nos`
   - `duplicate_count`

默认重复行为：

- 记为 warning，不直接失败
- 汇总后只导入一条停靠点

## 8.5 客户匹配规则

匹配数据源优先顺序：

1. 系统内正式客户/门店主数据
   - `res.partner`
   - 已落库的 customer/store profile 扩展信息
2. 首期不再单独引入“受控底表镜像”作为正式匹配源

本次冻结结论：

- 客户信息底表的正式来源直接复用系统主数据
- 后续如需离线底表，只能作为辅助核对材料，不能覆盖正式匹配结论

匹配优先级：

1. `客户名称/门店名称` 单字段精确命中
2. 如单字段无命中，则进入失败或人工确认

本次冻结结论：

- 首期先沿用旧 Excel 模板口径，以 `客户名称/门店名称` 单命中为成功
- 地址在首期主要作为：
  - 原始数据保留字段
  - 回显字段
  - 后续规则升级的预留条件
- 下列情况均不得视为成功：
  - 名称多命中
  - 名称无命中

匹配输出状态建议：

- `matched_exact`
- `matched_name_only`
- `matched_ambiguous`
- `unmatched`

confirm 约束：

- `matched_exact` 可导入
- `matched_name_only` 首期可视为兼容成功态，允许 confirm
- `matched_ambiguous` 不可 confirm
- `unmatched` 不可 confirm

## 9. 落库对象设计

## 9.1 导入对象类型

建议在 `selection_options.py` 中新增：

- `mini_program_raw_sheet`

用途：

- 表示“小程序原始单表导入”这种新模式

## 9.2 导入任务复用

复用现有：

- `logistics.import.source.file`
- `logistics.import.task`
- `logistics.import.task.line`
- `logistics.import.error.line`
- `logistics.import.batch`

## 9.3 建议新增 staging 模型

建议新增两类轻量 staging 模型。

### A. 原始解析行

建议模型名：

- `logistics.mini.import.raw.row`

建议字段：

- `task_id`
- `source_row_no`
- `batch_no`
- `raw_store_name`
- `raw_address`
- `normalized_store_name`
- `normalized_address`
- `is_duplicate`
- `duplicate_group_key`
- `duplicate_source_row_nos_json`
- `match_status`
- `matched_partner_id`
- `matched_customer_profile_id`
- `warning_json`
- `error_json`

### B. 汇总候选停靠点

建议模型名：

- `logistics.mini.import.stop.candidate`

建议字段：

- `task_id`
- `batch_no`
- `stop_seq`
- `store_name`
- `address_detail`
- `contact_phone`
- `partner_id`
- `customer_profile_id`
- `match_status`
- `can_confirm_import`
- `source_row_count`
- `source_row_nos_json`

如果本轮不想新增实际模型，也可以先落在 task line JSON 中。

但从长期维护看，建议有 staging 模型，便于：

- 人工核对
- 错误复盘
- 二次确认

## 9.4 正式业务落点

confirm 成功后，建议落到：

- `logistics.route.planning.batch`
- `logistics.route.planning.stop.line`

原因：

- 本次原始表导入的最直接产物是“排线停靠点”
- 当前原始文件只稳定提供门店停靠维度，不是完整运单四 sheet 数据

即：

本次默认先承接到 route planning draft，而不是直接生成完整 waybill/order/goods。

本次冻结结论：

- 首期 confirm 后只写：
  - `logistics.route.planning.batch`
  - `logistics.route.planning.stop.line`
- 首期明确不直接扩写：
  - `waybill`
  - `order`
  - `goods`

## 10. 接口草案

## 10.1 入口归属

入口在小程序端，但后端仍走 mini 风格接口前缀：

- `/api/mini/logistics/imports/...`

同时保留后台复用或人工补录能力时，可再提供 admin 镜像接口：

- `/api/admin/logistics/imports/mini-program-raw-sheet/...`

本设计先以 mini 入口为主。

- 获取该模式元信息
- 获取字段说明
- 获取样例模板或说明下载地址

## 10.3 mini 与 admin 的关系

建议共用同一 service，只区分 controller：

- mini controller：给小程序调用

- 两套逻辑漂移
- 两套错误口径不一致

## 11. 预校验规则

## 11.1 文件级校验

1. 只能上传 `.xlsx`
2. 文件不能为空
3. 必须识别到表头区
4. 必须识别到 `发车单号`
5. 必须识别到：
   - `收货单位`
   - `收货地址`

错误示例：

- `TEMPLATE_FILE_TYPE_INVALID`
- `TEMPLATE_HEADER_NOT_FOUND`
- `BATCH_NO_NOT_FOUND`
- `REQUIRED_COLUMN_MISSING`

## 11.2 行级基础校验

每条候选记录至少校验：

1. `收货单位` 不为空
2. `收货地址` 不为空
3. `batch_no` 不为空

错误示例：

- `STORE_NAME_REQUIRED`
- `ADDRESS_REQUIRED`
- `BATCH_NO_REQUIRED`

## 11.3 合并单元格补齐校验

如果某行原始值为空，但可以从 merged cells 展开后补齐：

- 不记错误
- 在行结果中标记 `filled_from_merged_cells = true`

如果补齐后仍为空：

- 记正式错误

## 11.4 去重校验

同一 `batch_no + normalized_store_name + normalized_address` 重复时：

- 主行保留
- 后续重复行记 warning
- 不阻断 confirm

warning 示例：

- `DUPLICATE_STOP_COLLAPSED`

## 11.5 客户匹配校验

### 可确认

- `matched_exact`

### 不可确认

- `matched_name_only`
- `matched_ambiguous`
- `unmatched`

错误示例：

- `CUSTOMER_MATCH_NOT_FOUND`
- `CUSTOMER_MATCH_AMBIGUOUS`
- `CUSTOMER_MATCH_WEAK_ONLY`

## 11.6 confirm 阶段约束

以下情况不允许 confirm：

1. 存在未匹配门店
2. 存在多命中门店
3. 存在关键字段缺失
4. 导入任务状态不是 `prechecked`

## 13. 权限与安全

建议新增独立开关：

## 15. 风险

1. 原始表头未来可能发生轻微漂移，需要别名容错
2. 首期沿用单命中口径，存在同名门店误匹配风险，后续可能需要升级到“名称 + 地址”双命中
3. 客户信息底表如果不系统化，会形成新的外部依赖
4. merged cells 规则若变化，需要补解析测试样例
5. 小程序端上传大文件时需确认网关和超时策略

---

## 16. 验证建议

开发完成后，至少验证以下样例：

1. 正常样例：
   - merged cells 可正确补齐
   - 成功提取 `batch_no`
   - 门店精确匹配成功
2. 重复样例：
   - 同门店地址重复时只保留一条停靠点
3. 未匹配样例：
   - 预校验给出错误
   - confirm 被阻断
4. 多命中样例：
   - 给出不可确认结论
5. 缺列样例：
   - 直接文件级失败

## 17. 一句话结论

本次推荐把“小程序导入原数据”正式收口为：

**小程序端上传原始单表作为入口，服务端负责 merged cells 解析、标准化清洗、客户底表匹配、预校验与确认导入，并以 `发车单号 = batch_no` 的规则写入排线导入正式链路。**
