## 1. 角色重新定义

你的职责不再理解成“负责 Odoo 后台页面优化”，而应理解成：

**负责把留痕证据链，转译成后台可读、可追、可判断、可处理的管理界面。**

你不是页面美化负责人，你是：
- 追溯阅读体验负责人
- 后台信息架构负责人
- 管理员与老板视角的入口收口负责人

你最重要的交付，不是让页面更像定制系统，而是让下面这条链真正顺：

`当前状态 -> 历史留痕 -> 图片证据 -> 异常判断 -> 处理动作`

---

## 2. 当前设计前提

基于当前正式前端方案与已收口的重构结论，后续工作必须默认以下事实：

1. 这套系统本质上是“物流过程留痕取证系统”，不是通用 ERP 页面改造项目。
2. 后台的第一价值是“查、看、追溯、判断”，不是重审批、重运营、重协同。
3. 第一阶段真正成熟的设计主线是：
   - 运单 / 批次 / 车次上下文
   - 留痕事件
   - 图片证据
   - 异常对象
4. 客户、门店、联系人、泛主数据后台，不应成为你当前工作的主轴。
5. Discuss、聊天、会议、日历、泛联系人中心，当前明确不纳入你的页面主范围。

这意味着：
- 你做的不是“后台全量改版”
- 你做的是“围绕留痕证据链的后台追溯层”

---

## 3. 你的核心设计目标

## 3.1 管理员目标

管理员进入后台后，应能快速完成：

1. 找到运单、批次、车次或异常对象
2. 看到当前状态和最近留痕摘要
3. 打开详情页
4. 沿时间线回看关键历史
5. 查看关联证据图
6. 判断问题何时出现、谁提交、证据是否完整
7. 对异常对象做跟进和处理

## 3.2 老板目标

老板进入界面后，应能快速完成：

1. 看到问题分布和高风险对象
2. 进入争议对象
3. 先看摘要结论
4. 再看证据链
5. 最后在需要时看原始时间线

## 3.3 最终判断标准

如果最后只是：
- 视图更整齐
- 布局更好看
- 默认 Odoo 页面更像“项目系统”

那不算完成。

只有当下面这些问题被解决，才算完成：
- 用户更快找到对象
- 用户更快看到当前状态
- 用户更快看到证据链
- 用户更快完成责任判断

## 4. 你的页面设计必须围绕三层模型

重构文档里最值得吸收的，是后台页面应该围绕三层组织，而不是围绕模型堆字段。

## 4.1 当前状态层

用于回答：
- 现在怎么样

页面上要承接的典型信息：
- 运单当前状态
- 批次当前进度
- 车次当前状态
- 当前是否异常
- 最新一次留痕摘要
- 最新一张证据图入口

这层主要服务：
- 列表页
- 首页卡片
- 详情页头部摘要区

## 4.2 留痕事实层

用于回答：
- 过程中发生过什么

页面上要承接的典型信息：
- 何时发生留痕
- 谁提交的
- 属于哪个节点
- 是否异常
- 留痕备注
- 留痕关联对象

这层主要服务：
- 时间线
- 历史追溯区
- 异常关联区

## 4.3 图片证据层

用于回答：
- 有哪些可直接查看的证据

页面上要承接的典型信息：
- 图片列表
- 顺序
- 对应留痕事件
- 上传人 / 拍摄时间
- 图片备注
- 证据完整度

这层主要服务：
- 证据预览区
- 证据抽屉 / 弹层
- 老板快速判断区

你的所有页面结构，建议都按这三层去拆，不要反过来先按 Odoo 默认分组去拼。

## 5. 你真正负责的对象链

你不直接拥有模型定义，但你的页面必须围绕下面这三条主线设计。

## 5.1 运单主线

`stock.picking`
-> `logistics.trace.event`
-> `logistics.trace.evidence`

这是后台最核心的一条追溯主线。

## 5.2 批次主线

`stock.picking.batch`
-> `stock.picking`
-> `logistics.trace.event`

它主要服务仓内和批量问题视角，不应替代运单主线。

## 5.3 运输主线

`logistics_dispatch`
-> `stock.picking`
-> `logistics.trace.event`
-> `logistics.trace.evidence`

它主要服务司机、车次、运输上下文，不应替代证据主线。

## 5.4 重要页面约束

- 批次不是证据主对象
- 车次不是证据主对象
- 证据图必须挂在留痕事实下面被阅读
- chatter 只能是协作补充，不能替代正式留痕时间线
- 普通附件不能替代证据对象页

## 6. 你需要协作的模块边界

你需要重点对接的模块：

- `logistics_dispatch`
- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_exception`
- `logistics_trace_dashboard`

你依赖的 Odoo 原生后台能力：
- `menu`
- `action`
- `search view`
- `tree/list`
- `form`
- `kanban`
- smart button
- stat button
- notebook
- chatter 作为辅助协作区

你不拥有这些模块的业务定义权，但你拥有以下界面要求权：
- 页面必须消费哪些聚合字段
- 哪些页面必须能直接查看摘要
- 哪些页面必须能从对象跳到证据
- 哪些页面不能只靠默认表单拼装完成

## 7. 当前明确不做的页面范围

根据最新范围收缩口径，你当前不要把精力投入在这些方向：

- Discuss 风格消息中心
- 聊天、频道、私聊页面
- 日历、会议、办公协同页面
- 泛联系人中心
- CRM 式客户经营视图
- 和留痕主闭环无关的复杂审批壳子

替代口径：
- 留痕用正式业务对象表达
- 异常用正式异常对象表达
- 必要协作先落备注和处理记录，不先做消息系统

## 9. 优先级必须按 P0 / P1 / P2 推进

重构文档已经把节奏说得很清楚，你的页面设计也必须同步这个优先级。

## 9.1 P0：最小可用追溯后台

这一阶段只聚焦“证据闭环”：

- 运单追溯列表页
- 运单详情页
- 留痕时间线区
- 证据查看区
- 后台从运单直达留痕和证据

这一阶段不要过度铺开：
- 大而全菜单
- 复杂批次页
- 复杂老板看板
- 泛协同页面

## 9.2 P1：运营追溯后台

在 P0 打通后再补：

- 异常列表页
- 异常详情页
- 批次追溯列表页
- 批次详情页
- 老板追溯总览页
- 基础留痕质量看板

## 9.3 P2：增强层

后续再考虑：

- 更完整的车次视角
- 多端接入下的统一追溯入口
- 更细颗粒度统计
- 高级导出
- 更强的图片元数据查看

## 10. 建议的后台信息架构

你可以直接按下面这个结构开始画图。

```text
物流留痕
├─ 追溯中心
│  ├─ 运单追溯
│  ├─ 批次追溯
│  ├─ 车次追溯（P2）
│  └─ 证据总览（P1/P2）
├─ 异常中心
│  ├─ 当前异常
│  ├─ 历史异常
│  └─ 待处理争议
├─ 看板中心
│  ├─ 老板总览
│  ├─ 缺图看板
│  └─ 异常闭环看板
└─ 配置与规则
   ├─ 留痕类型
   ├─ 异常类型
   └─ 留痕规则（后端为主，前端只承接入口）
```

设计原则：
- 一层入口少而清晰
- 追溯中心优先于看板中心
- 证据不做成散附件入口，而要和追溯链挂钩
- 老板入口应该从看板和争议清单切入，不从全量列表切入

## 12. 关键页面设计要求

## 12.1 运单追溯列表页

页面目标：
- 快速找运单
- 快速看到当前状态和证据摘要

最低字段建议：
- 运单号
- 外部单号
- 当前状态
- 异常状态
- 最新留痕时间
- 最新留痕类型
- 证据完整度
- 最新责任对象
- 更新时间

页面重点：
- 搜索必须强
- 列表字段不能杂
- 默认排序要明确
- 能一键进入详情

## 12.2 运单详情页

页面目标：
- 用一个页面承接完整追溯阅读

建议分区：
- 头部摘要区
- 当前状态区
- 执行上下文区
- 留痕时间线区
- 证据查看区
- 异常摘要区
- 处理记录区

重要原则：
- 先看摘要，再看事实，再看原始证据
- 时间线和证据区不能被挤到页面很后面

## 12.3 异常列表页

页面目标：
- 从问题出发找对象

最低字段建议：
- 异常编号
- 异常类型
- 严重程度
- 关联运单 / 批次
- 当前状态
- 当前责任人
- 最近处理时间
- 证据是否完整

## 12.4 异常详情页

页面目标：
- 让管理员从异常直达证据链

建议分区：
- 异常摘要
- 关联运单 / 批次 / 车次
- 关联留痕
- 关联证据
- 当前责任与处理状态
- 处理动作区

## 12.5 老板追溯总览页

页面目标：
- 先看到问题分布，再进入争议对象

建议卡片：
- 今日异常数
- 待处理争议数
- 证据不完整对象数
- 高风险批次数
- 异常闭环率

重要原则：
- 先结论，后明细
- 每张卡都尽量支持下钻

## 12.6 证据查看区

页面目标：
- 高效看图，不打断追溯判断

最低字段建议：
- 图片序号
- 缩略图
- 大图入口
- 对应留痕事件
- 拍摄 / 上传时间
- 上传人
- 图片备注

重要原则：
- 不把证据当普通附件堆在 chatter 里
- 必须支持从证据反跳留痕

## 13. 搜索与筛选设计重点

这是后台是否好用的关键点之一。

## 13.1 运单追溯常用搜索项

- 运单号
- 外部单号
- 批次号
- 车次号
- 异常编号
- 留痕提交人

## 13.2 常用筛选项

- 时间范围
- 当前状态
- 异常状态
- 证据完整度
- 是否有最新留痕
- 是否存在未闭环异常

## 13.3 老板视角快捷筛选

- 今日新增异常
- 待处理争议
- 证据不足
- 高风险批次
- 多次异常对象

## 13.4 必须避免的问题

- 搜索入口过多但无主次
- 高价值筛选被埋太深
- 只做通用搜索，不做业务快捷筛选
- 默认排序不稳定

---

## 14. 后台交互规范重点

## 14.1 列表页规范

- 默认排序明确
- 第一列优先放可点击主对象
- 状态标签统一
- 主动作位置统一
- 是否开放批量操作要谨慎

## 14.2 详情页规范

- 摘要区固定在最上方
- 当前状态优先于扩展信息
- 时间线区和证据区必须是主体，不是附属
- 异常区不要只做一个状态字段

## 14.3 时间线规范

- 建议按时间倒序
- 每条留痕必须能看到：时间、类型、提交人、备注摘要、图片数、异常标记
- 异常留痕要有更明显的视觉标识

## 14.4 证据查看规范

- 缩略图与大图切换明确
- 多图顺序稳定
- 缺图有占位提示
- 加载失败有明确反馈
- 支持留痕 <-> 证据双向跳转

## 14.5 状态反馈规范

- 加载中
- 空数据
- 无搜索结果
- 数据不完整
- 证据缺失
- 操作成功
- 操作失败

## 15. 你要向后端负责人明确追问的问题

## 15.1 给 `logistics_dispatch`

- 批次、车次、运单三者的最终页面跳转关系是什么
- `stock.picking.batch` 与 `logistics_dispatch` 的职责边界是否已经锁定
- 哪些上下文字段会在详情页直接展示

## 15.2 给 `logistics_trace_core`

- 留痕是否统一支持挂运单 / 批次 / 车次
- 是否会提供“最新留痕摘要”聚合字段
- 时间线最小展示字段有哪些
- 是否支持按对象和时间范围高效查询

## 15.3 给 `logistics_trace_evidence`

- 一条留痕最多挂多少图
- 图片顺序是否稳定
- 是否有首图 / 封面摘要
- 是否有证据完整度口径
- 哪些字段会给老板视角直接消费

## 15.4 给 `logistics_trace_exception`

- 异常是否必须关联留痕
- 异常状态机是什么
- 异常责任人口径是什么
- 异常是否支持直接下钻到证据

## 15.5 给 `logistics_trace_dashboard`

- 老板首页最终要看的卡片有哪些
- 哪些指标支持点击下钻
- 指标是实时算还是预聚合

## 16. Odoo 落地方式建议

你做的方案，最终应该能直接指导 Odoo 视图实现。

建议优先落在这些载体上：
- 菜单 `menuitem`
- 动作 `act_window`
- 搜索视图 `search`
- 列表视图 `tree`
- 表单视图 `form`
- 统计按钮 `stat button`
- smart button
- 必要的看板 `kanban`

不建议一上来就重前端壳子或过度自定义 WebClient。

正确方向是：
- 先把信息架构和视图结构做对
- 再判断哪些区域需要更强的前端交互
