# Odoo19物流留痕图片存储架构建议

本文档用于回答一个很现实的问题：

当物流留痕图片量很大时，Odoo 原生附件机制还能不能直接扛住，以及你的系统应该怎么设计图片存储架构。

当前已知业务量级是：

- 一个批次大约产生 `100` 张图片
- 连续运营 `6` 个月大约产生 `3T` 图片

这意味着系统面对的已经不是“普通附件管理”，而是一个中高规模的业务证据存储场景。

---

## 1. 先给结论

对你这套系统来说：

- 不建议把 Odoo 默认 `ir_attachment + 本地 filestore` 作为长期正式方案
- 也不建议把大体量留痕图片直接塞数据库大字段
- 更合适的正式方案是：

```text
业务表存证据元数据
  + 对象存储保存图片实体
  + 独立缩略图 / 预览图
  + 生命周期与归档策略
```

一句话判断：

**3T / 6个月 这个量级下，Odoo 原生附件机制可以参考，但不适合直接作为你们物流留痕图片的最终主架构。**

---

## 2. 为什么默认方案不适合

Odoo 默认图片 / 附件机制是：

- `ir_attachment` 存元数据
- 本地 filestore 存文件实体

它适合：

- 普通办公附件
- 一般 ERP 图片上传
- 中小规模后台文档管理

但对你们这种物流留痕图片场景，有几个明显问题：

- 图片量增长快，文件数量巨大
- 热点查询集中在最近几天或最近几周
- 需要按批次、运单号、门店、时间快速回看
- 需要长期保留证据，不能只考虑“能上传”
- 后面大概率会遇到迁移、扩容、容灾、归档问题

如果继续把图片实体只放本地 filestore，风险会逐渐变成：

- 单机磁盘压力越来越大
- 备份窗口越来越长
- 恢复时间不可控
- 多节点部署时文件同步复杂
- 跨环境迁移成本高
- 图片访问链路难以优化

---

## 3. 这个量级意味着什么

按你给的数据粗算：

- `3T / 6个月`
- 约等于每月 `500GB`
- 约等于每天 `16GB ~ 17GB`

这还只是图片原始量，不含：

- 缩略图
- 预览图
- 重试上传临时文件
- 备份副本
- 容灾副本
- 日志和索引增长

如果再考虑：

- 上传高峰集中在发货波次时段
- 现场网络不稳定导致重传
- 后台频繁预览最近证据图

那这已经非常像一个“业务对象存储系统”，而不是普通表单附件。

---

## 4. 推荐的正式架构

推荐把图片分成两层管理：

## 4.1 业务层

业务层维护：

- 留痕事件
- 证据对象
- 图片清单
- 图片和运单 / 批次 / 门店 / 留痕事件的关联关系

例如：

- `logistics_trace_event`
- `logistics_trace_evidence`
- `logistics_trace_evidence_image`

业务表里只保留：

- 主键
- 关联业务对象
- 图片对象键
- 上传状态
- 文件大小
- 宽高
- mime type
- 摘要值
- 拍摄时间
- 上传人
- 顺序号

不要把原始图片二进制直接放业务主表。

## 4.2 存储层

存储层建议使用对象存储：

- MinIO
- S3
- 阿里云 OSS
- 腾讯云 COS

其中如果你们当前是自建环境，MinIO 会比较合适，原因是：

- 和 S3 接口兼容
- 成本可控
- 迁移路线清晰
- 后面如果切云厂商，对接成本相对低

---

## 5. 推荐的图片对象结构

建议把一张留痕图片抽象成一个对象：

```text
evidence_image
  -> object_key
  -> thumb_object_key
  -> preview_object_key
  -> checksum
  -> mime_type
  -> file_size
  -> width
  -> height
  -> taken_at
  -> sort_no
  -> upload_state
```

推荐对象路径风格：

```text
trace-images/{yyyy}/{mm}/{dd}/{batch_no}/{waybill_no}/{image_id}.jpg
```

或者：

```text
trace-images/{biz_date}/{trace_event_no}/{image_no}.jpg
```

这样做的好处是：

- 对象路径可读
- 迁移和归档方便
- 批量排查时容易定位
- 后台生成预签名地址更方便

---

## 6. 图片访问建议

不要让前端直接感知物理存储路径。

更稳的做法是：

- 后台只返回图片访问键或图片 ID
- 服务端根据权限生成临时访问地址
- 小程序和后台都通过统一图片访问接口取图

建议保留这几类地址：

- 原图
- 预览图
- 缩略图

因为对于后台列表、时间线、看板来说，很多场景只需要缩略图或预览图，不应该每次都拉原图。

---

## 7. 对留痕系统最重要的附加设计

物流留痕图片不是普通附件，它更像证据材料，所以除了“存下来”，还应补这些能力：

- 图片摘要值校验
- 重复上传识别
- 上传失败重试
- 图片与业务对象强关联
- 删除受控，不允许业务层随意硬删
- 访问日志
- 归档策略
- 保留策略

如果后面真遇到争议或审计，这些能力会比“图片有没有上传成功”更重要。

---

## 8. 分阶段建议

## 8.1 P0 阶段

如果你们现在重点还是先打通业务链，可以这样做：

- 业务模型先定好
- 图片元数据单独建表
- 存储接口按对象存储口径设计
- 本地开发环境可以临时用本地文件或 MinIO

也就是说，即使 P0 没有上完整生产级存储，也要把接口和模型设计成以后能平滑切对象存储。

## 8.2 正式生产阶段

如果进入正式运营，我更建议直接上：

- 对象存储
- 图片元数据表
- 缩略图 / 预览图
- 预签名访问
- 生命周期策略
- 冷热分层

不要先大规模上线本地 filestore，再过几个月被动迁移。

---

## 9. 和 Odoo 的关系怎么处理

这里最稳的思路不是“完全不用 Odoo”，而是：

- Odoo 仍负责主业务对象、后台流程、菜单视图、业务编排
- 物流留痕图片走你自己的证据对象模型
- 如有需要，可和 `ir_attachment` 做轻量兼容

更直白一点说：

- Odoo 负责业务
- 你的证据中心负责图片

这比把 3T 级别的留痕图片完全压进 Odoo 默认附件体系里稳得多。

---

## 10. 最终建议

针对你现在这个量级，我建议直接按下面这条路线推进：

1. 不把 Odoo 默认附件机制当作正式生产图片主方案
2. 证据中心单独设计图片元数据对象
3. 图片实体直接按对象存储路线设计
4. 从一开始就考虑缩略图、预览图、归档和权限访问
5. 后台和小程序都只消费统一图片访问接口，不感知真实存储路径

一句话总结：

**你们现在面对的不是“ERP 附件上传”，而是“物流证据图片平台”问题；3T / 6个月 这个规模，应该从一开始就按对象存储架构来设计。**
