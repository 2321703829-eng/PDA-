# Odoo 19 承载物流留痕系统的扩展规划

本文档面向后续接手本仓库的人，目标不是解释 Odoo 本身，而是回答：

1. 为什么要基于 Odoo 来扩展物流留痕系统
2. Odoo 原生负责什么
3. 哪些能力必须自定义模块实现
4. 应该按什么阶段落地

相关文档：

- `Odoo19系统总览.md`：Odoo 19 系统总览

---

## 1. 规划结论先行

本项目建议把 Odoo 定位为：

**物流留痕系统的业务底座和运营后台，而不是留痕产品本体。**

也就是说：

- Odoo 负责订单、库存、批次、车辆、司机、权限、消息、附件、流程、报表等通用企业能力
- 自定义模块负责“留痕事件、证据图片、司机端上传、异常追溯、老板视角看板”这些真正决定产品价值的能力

如果用一句话概括：

**用 Odoo 把业务跑起来，用自定义模块把证据链沉淀下来。**

---

## 2. 为什么基于 Odoo 而不是另起一套后台

从当前仓库和 Odoo 19 的能力看，Odoo 很适合作为这套系统的母体，原因主要有四个：

### 2.1 它已经具备物流运营底座

本仓库内已经有：

- `stock`：库存与物流活动主模块
- `stock_picking_batch`：批次/波次能力
- `fleet`：车辆管理
- `stock_fleet`：运输调度相关扩展
- `stock_delivery_trip`：车次与交付证明相关扩展

这说明订单执行、批次、车辆、配送这些对象，并不需要你完全重造。

### 2.2 它已经具备后台系统基础设施

Odoo 原生已经有：

- 用户、角色、组、ACL、记录规则
- 多公司隔离
- 审批、消息、活动、跟踪
- 报表、菜单、视图、搜索、列表、看板
- 定时任务、邮件、基础 API 能力

这些都是“企业系统共性”，复用价值很高。

### 2.3 它天然适合做后台，不天然适合做司机端

这不是 Odoo 的缺点，而是边界。

Odoo 非常适合：

- 后台主控
- 运营管理
- 仓储执行
- 调度与订单履约

但它并不天然擅长：

- 微信小程序式司机端体验
- 极简拍照上传流程
- 弱网环境下的连续录入

所以正确做法不是强行拿 Odoo Web 客户端去顶司机端，而是让 Odoo 承接后台和业务核心，再单独做轻量移动入口。

### 2.4 它已经开始碰到“证明”这个方向

当前仓库里已经出现两个对你很有价值的线索：

- `stock.picking` 上已经有签名能力
- `stock_delivery_trip` 已经开始做车次和交付照片证明

这说明扩展方向与 Odoo 并不冲突，只是现有能力还不够系统化。

## 3. 本项目的核心业务目标

基于你前面的要求，这套系统真正要完成的不是“大而全仓库管理”，而是三件事：

### 3.1 给老板留下证据

核心要解决的是争议场景：

- 这票货有没有在关键节点被处理
- 是谁处理的
- 当时有没有图片或签名
- 证据是否能回溯到订单、批次、车次、司机

### 3.2 让司机和现场人员省事

司机端价值不在于功能多，而在于：

- 少点几步
- 少填几个字段
- 扫码后快速拍照提交
- 成功后立即下一单

### 3.3 让后台能快速追溯

后台最重要的不是复杂审批，而是快速回答：

- 当前状态是什么
- 最近一次留痕是什么
- 有没有异常
- 对应证据图在哪
- 历史链路是怎样的

---

## 4. Odoo 原生负责什么

下面这些能力，建议优先复用 Odoo 原生对象和机制，不单独重做。

### 4.1 业务主对象

建议直接基于以下对象扩展：

- `stock.picking`
  用作订单明细与出库执行基础对象
- `stock.picking.batch`
  用作仓内波次/批次对象
- `fleet.vehicle`
  用作车辆对象
- `res.partner`
  用作司机、客户、收发货联系人等基础主体

### 4.2 后台通用能力

- 用户、权限、菜单、视图、搜索、列表、详情
- chatter、activity、mail tracking
- `ir.attachment`
- `ir.cron`
- 多公司隔离
- 基础统计和报表

### 4.3 运输调度相关能力

本仓库已有两个方向接近的运输中心对象：

- `stock.picking.batch`
- `stock.delivery.trip`

这里必须尽早定原则：

**不要让批次和车次同时成为“运输主对象”。**

建议口径如下：

- `stock.picking.batch`：负责仓内拣配、波次、装车前组织
- `stock.delivery.trip`：负责车辆出车、司机执行、交付证明

这样职责清晰，后续留痕和证据链也更容易落位。

## 5. 必须自定义实现的核心模块

这些模块是项目真正的产品核心，不建议只靠 Odoo 现有 chatter、附件、备注字段拼出来。

### 5.1 `logistics_trace_core`

定位：

- 留痕中心

职责：

- 定义“留痕事件”对象
- 管理留痕类型、来源、提交时间、提交人、所属对象
- 统一承接运单级、批次级留痕，并兼容车次执行上下文
- 提供留痕时间线能力

不要直接把留痕混在 chatter 里。

原因：

- chatter 适合协作和消息记录
- 留痕是正式业务事实，必须可查询、可聚合、可统计、可约束

### 5.2 `logistics_trace_evidence`

定位：

- 证据中心

职责：

- 管理留痕关联图片、签名、备注、附件元数据
- 区分“普通附件”和“证据材料”
- 支持一条留痕关联多份证据
- 支持证据预览、下载、有效性状态
- 为后续 MinIO/S3 等对象存储扩展留接口

关键原则：

- 证据不能只作为杂散附件存在
- 证据必须有明确的业务归属和查询入口

### 5.3 `logistics_trace_mobile`

定位：

- 司机端/现场端接入层

职责：

- 提供微信小程序/H5/移动端可调用的轻量接口
- 支持扫码或输入运单号
- 支持快速拍照上传
- 自动创建留痕并挂接证据
- 适配弱网和连续录入

关键原则：

- 不让司机直接使用 Odoo 标准后台页面
- 移动端单独优化体验

### 5.4 `logistics_trace_exception`

定位：

- 异常与争议中心

职责：

- 把异常从普通状态字段中提升为正式业务对象
- 支持当前异常、历史异常、异常追溯
- 关联订单、批次、车次、留痕、证据
- 支持老板和管理者从异常直接看证据

### 5.5 `logistics_trace_dashboard`

定位：

- 管理看板

职责：

- 缺图看板
- 节点合规率
- 异常数量与闭环率
- 司机留痕质量
- 批次/车次证据完整度

重点不是通用 ERP 指标，而是“留痕质量和证据完整性”。

### 5.6 `logistics_trace_cn`

定位：

- 中国本地物流场景适配层

职责：

- 运单号规则
- 微信生态接入
- 本地打印和标签适配
- 中国物流业务状态与异常字典
- 后续对接第三方物流接口

这个模块可以后置，但要预留。

## 6. 推荐的对象关系

为了防止后续开发越做越乱，建议统一采用下面这条主线：

### 6.1 业务主线

`stock.picking`
-> `logistics.trace.event`
-> `logistics.trace.evidence`

这条链路用于运单级证据闭环，订单作为从属明细展开查看。

### 6.2 运输主线

`stock.delivery.trip`
-> `stock.picking`
-> `logistics.trace.event`
-> `logistics.trace.evidence`

这条链路用于司机和车次视角。

### 6.3 批次主线

`stock.picking.batch`
-> `stock.picking`
-> `logistics.trace.event`

这条链路用于仓内组织视角。

### 6.4 重要约束

- 批次不是证据主对象，运单号和留痕才是；订单是运单下的履约明细
- 车次不是证据替代品，车次只是执行上下文
- 图片不是普通附件，而是证据对象
- chatter 不是留痕主表，只是协作补充

## 7. 分阶段落地规划

### 7.1 P0：最小可用版

目标：

- 先把“证据闭环”做通

范围：

- `logistics_trace_core`
- `logistics_trace_evidence`
- `logistics_trace_mobile`
- 后台订单详情里的留痕时间线和证据区

交付结果：

- 能从运单进入留痕，并展开查看运单下订单
- 能从司机端提交图片
- 能自动生成留痕事件
- 能在后台看到证据图

这是第一优先级。

### 7.2 P1：运营版

目标：

- 把后台追溯和调度管理做顺

范围：

- `logistics_trace_exception`
- `logistics_trace_dashboard`
- 批次、车次视角下的留痕摘要
- 缺图、异常、未闭环看板

交付结果：

- 老板和管理者可直接查证据
- 调度和仓库可看留痕质量

### 7.3 P2：增强版

目标：

- 做强现场适配和规模化能力

范围：

- 对象存储与图片归档优化
- 地理位置、水印、拍摄规则
- 弱网补传
- 第三方物流接口
- 自动巡检与补偿

交付结果：

- 系统从可用变成稳定可运营

## 8. 关键设计原则

### 8.1 证据优先，不是附件优先

图片、签名、备注不应只挂在普通附件里，而应先成为业务证据对象，再落到附件或对象存储层。

### 8.2 留痕是正式业务对象，不是聊天记录

`mail.thread` 可以继续用，但不能替代 `logistics.trace.event`。

### 8.3 优先继承扩展，不改核心源码

原则上：

- 扩展 `stock.picking`
- 扩展 `stock.picking.batch`
- 扩展 `stock.delivery.trip`
- 新增自定义模块

尽量不直接修改 Odoo 核心文件。

### 8.4 后台和司机端分开设计

- 后台优先考虑查询、追溯、管理
- 司机端优先考虑拍照、提交、连续录入

不要拿同一套 UI 同时满足两边。

### 8.5 当前状态和历史事实分开

建议系统里始终区分两层：

- 当前状态层：运单当前状态、批次当前状态、车次当前状态、订单履约状态
- 历史事实层：留痕事件、异常事件、证据材料

这样才能既好查当前，又能做争议追溯。

## 9. 当前已知风险

### 9.1 社区版与其他版本能力边界

官方产品家族里有 Documents、Sign、Quality 等能力，但当前仓库是否全部包含对应模块，需要按本地代码和后续部署版本确认。

因此规划上不应假设所有官方产品能力都已在当前仓库现成可用。

### 9.2 图片存储规模

如果现场图片很多，只依赖默认附件存储可能会遇到：

- 空间压力
- 备份压力
- 读取性能压力

所以从 P0 起就应预留对象存储抽象。

### 9.3 司机端体验与 Odoo Web 客户端不匹配

移动端入口如果完全照搬后台页面，落地体验会差，后期返工概率很高。

### 9.4 运输对象边界容易混乱

如果批次、车次、订单三层关系没定清楚，后面留痕归属和异常归属会越来越乱。

## 11. 本轮规划最终结论

基于 Odoo 19 扩展物流留痕系统是可行的，而且方向正确。

但必须坚持下面这个边界：

- Odoo 是底座
- 留痕系统是产品层

如果后续一直沿着这个边界推进：

- 原生模块负责经营与履约
- 自定义模块负责证据链与司机端

那么系统既能继承 Odoo 的成熟能力，也不会失去你最看重的“物流留痕取证”这个核心价值。
