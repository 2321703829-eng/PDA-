# Odoo19物流留痕系统跨模块接口与数据约束总规范

本文档用于统一当前 Odoo 物流留痕系统的跨模块接口和数据约束口径。

它不是单个模块的实现说明，而是：

- 模块之间怎样交互
- 数据归谁负责
- 哪些字段能跨模块传
- 哪些字段不能越界写

## 1. 总原则

所有跨模块交互，统一遵守 6 条原则：

1. 优先模块内方法调用，外部终端才走 HTTP 接口
2. 数据只在拥有者模块中维护，其他模块只引用、不越权写入
3. 前端不直接碰 Odoo 原生对象细节，只消费稳定 DTO
4. 证据访问统一通过证据接口，不暴露物理存储路径
5. 规则判断统一收口到规则模块，不散落到各个页面和控制器
6. 所有查询和写入默认遵守公司隔离、多租户和权限约束

---

## 2. 模块交互方式

## 2.1 模块内交互

同一 Odoo 运行时内，优先使用：

- 模型方法
- service/helper 抽象
- `env['model.name']` 调用
- 统一 DTO 组装方法

不推荐：

- 为了“看起来解耦”而让模块内部也强行走 HTTP
- 在 XML 视图、JS 页面、控制器里散落业务规则

## 2.2 对外终端交互

只有下面这些场景应走稳定 HTTP 接口：

- 司机端 H5 / 小程序
- 后台前端异步查询
- 第三方系统接入
- 回调、Webhook、对象存储访问

HTTP 接口统一由专用接入层或控制器对外暴露，不把底层模型直接暴露出去。

---

## 3. 数据拥有权

## 3.1 Odoo 原生对象拥有的数据

以下数据由 Odoo 原生对象负责：

- 订单履约主体：`stock.picking`
- 批次主体：`stock.picking.batch`
- 车辆主体：`fleet.vehicle`
- 车次主体：`stock.delivery.trip`
- 公司、用户、权限、附件、定时任务等平台设施

自定义模块对这些对象以“扩展字段、扩展视图、引用关系”为主，不重造平行主表。

## 3.2 自定义模块拥有的数据

以下数据由自定义模块负责：

- 留痕事件：`logistics.trace.event`
- 证据对象：`logistics.trace.evidence`
- 规则对象：`logistics.trace.rule`
- 异常对象：`logistics.trace.exception`
- 仪表盘聚合结果
- 外部集成配置和回调记录

## 3.3 不允许的数据越界

不允许出现这些情况：

- `mobile` 模块直接维护证据主数据
- `dashboard` 模块直接写留痕事实
- `exception` 模块私自定义自己的证据归属关系
- 页面层自己拼接状态、自己解释规则、自己判断是否合规

## 4. 核心接口依赖关系

## 4.1 调度模块提供给留痕中心

`logistics_dispatch` 必须提供稳定执行上下文，至少包括：

- 当前对象属于运单、批次还是车次
- 对应的 Odoo 主对象 ID
- 执行状态
- 司机、车辆、批次、车次上下文
- 是否允许当前节点留痕

留痕中心只消费这些上下文，不自己猜批次和车次关系。

## 4.2 留痕中心提供给证据中心

`logistics_trace_core` 必须提供：

- 留痕主键
- 留痕业务编号
- 留痕来源
- 留痕类型
- 所属对象类型与对象 ID
- 提交人和提交时间

证据中心不自己创建“孤立证据”，证据必须挂在明确留痕之下。

## 4.3 规则模块提供给留痕与司机端

`logistics_trace_rule` 必须提供：

- 当前节点是否必须留痕
- 最少证据数量
- 是否必须备注
- 是否必须签名
- 不满足时的阻断或提示信息

司机端、后台前端、留痕中心统一消费同一份规则结果。

## 4.4 留痕与证据中心提供给异常模块

`logistics_trace_exception` 只从留痕与证据中提取异常事实，不重复维护另一套图片和时间线。

异常模块依赖：

- 留痕事件
- 证据材料
- 规则判断结果

## 4.5 留痕、证据、异常提供给看板模块

`logistics_trace_dashboard` 只消费汇总事实，不回写源事实。

它的数据来源应明确标记为：

- 留痕统计
- 证据统计
- 异常统计
- 批次/车次执行统计

---

## 5. 外部接口分层

## 5.1 司机端接口

司机端接口只面向最小闭环，建议统一放在移动接入层。

必须覆盖：

- 任务/订单识别
- 是否允许上传
- 创建留痕
- 上传证据
- 提交结果
- 弱网重试结果

司机端不直接调用后台列表、后台详情、后台管理类接口。

## 5.2 后台前端接口

后台接口面向查询、追溯、管理。

必须覆盖：

- 运单/批次/车次列表
- 详情
- 留痕时间线
- 证据列表与预览
- 异常列表与详情
- 看板指标

后台前端不直接读取底层附件表，不直接拼装对象关系。

## 5.3 第三方集成接口

第三方接口统一由 `logistics_trace_integration` 收口。

包括：

- 小程序回调
- 第三方物流状态推送
- 对象存储回调
- OCR / AI / 水印等后续扩展

不允许各业务模块分别对外暴露风格不一的集成接口。

---

## 6. 统一响应与 DTO 约束

## 6.1 HTTP 响应结构

建议所有对外接口统一返回：

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "20260410-abc123",
  "data": {}
}
```

分页接口统一返回：

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "20260410-abc123",
  "data": {
    "list": [],
    "total": 0,
    "page": 1,
    "page_size": 20
  }
}
```

## 6.2 DTO 约束

对外 DTO 必须满足：

- 不直接暴露物理路径
- 不直接暴露 Odoo 原生内部杂项字段
- 不把多个模块的原始字段原封不动扔给前端
- 页面需要的聚合结果由服务层统一组装

## 6.3 前端消费口径

前端只消费：

- 稳定字段名
- 稳定状态值
- 稳定嵌套结构

不消费：

- 物理存储路径
- Odoo ORM 内部技术字段
- 临时调试字段

---

## 7. 数据约束

## 7.1 留痕对象约束

一条留痕必须满足：

- 必须有明确所属对象
- 必须有留痕类型
- 必须有来源
- 必须有提交时间
- 必须有提交人或系统提交来源

不允许出现无法回溯归属的留痕。

## 7.2 证据对象约束

一条证据必须满足：

- 必须归属一条留痕
- 必须有证据类型
- 必须有可访问标识
- 必须有有效性状态
- 必须能判断是否已落存储

不允许出现只在附件层存在、但业务层无法查询的证据。

## 7.3 异常对象约束

一条异常必须满足：

- 必须能追到运单、批次或车次，并能从运单展开订单明细
- 必须能追到触发它的留痕或规则判断
- 必须能关联相关证据

不允许出现只有状态标签、但找不到证据链的异常。

## 7.4 公司与权限约束

所有业务数据默认遵守：

- 多公司隔离
- 当前用户权限校验
- 角色可见范围限制

不允许某个模块通过“方便开发”为由绕过统一权限边界。

---

## 8. 存储与附件约束

## 8.1 证据的逻辑归属

逻辑上，证据属于 `logistics_trace_evidence`。

物理上，证据可以落在：

- `ir.attachment`
- MinIO / S3 / OSS

但无论物理落哪里，业务查询入口都必须统一。

## 8.2 路径约束

不允许：

- 前端拿绝对路径
- 控制器直接把存储真实路径返回给调用方
- 页面直接拼接附件路径

必须：

- 通过稳定访问键或业务接口访问证据
- 由后端完成解析、鉴权和输出

---

## 9. 跨模块评审清单

任何模块设计文档在评审时，都应至少回答下面问题：

1. 这个模块拥有的数据是什么
2. 它引用别人的什么数据
3. 它通过什么接口获得这些数据
4. 它是否越权写了不属于自己的数据
5. 它给其他模块输出什么稳定接口
6. 前端是否只能消费稳定 DTO
7. 是否暴露了物理路径、内部字段或技术细节

---

## 10. 结论

跨模块设计的核心不是“接口越多越完整”，而是：

- 边界清楚
- 数据归属清楚
- 外部入口清楚
- 对前端输出稳定

从现在开始，团队统一按下面这句话执行：

**调度负责执行上下文，留痕负责事实，证据负责材料，规则负责约束，异常负责问题对象化，看板负责汇总展示，集成负责对外接入，前端只消费稳定结果。**
