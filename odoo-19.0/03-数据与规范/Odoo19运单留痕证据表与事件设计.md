# Odoo19运单留痕证据表与事件设计

本文档用于把你现在最核心的三类自定义数据对象定下来：

- `waybill`
- `trace_event`
- `evidence_image`

同时补上一张必要的关系表：

- `waybill_order`

以及一张事件驱动落库时非常有价值的辅助表：

- `event_outbox`

这份设计有 4 个目标：

1. 名字尽量简单，方便中国团队理解和沟通
2. 能直接承接你现在的真实留痕流程
3. 能支撑你已经明确的高频查询场景
4. 能兼容 Odoo 原生订单、批次、车辆、仓库结构

相关文档：

- `Odoo19物流留痕系统运单主对象与留痕主流程设计.md`
- `Odoo19原生SQL结构梳理-订单车辆批次仓库调度.md`
- `Odoo19订单批次店铺查询性能与索引能力评估.md`

---

## 1. 先给结论

推荐你们把核心业务表收敛成下面这一组：

```text
waybill
waybill_order
trace_event
evidence_image
event_outbox
```

其中：

- `waybill` 是门店运单主对象
- `waybill_order` 负责运单和订单多对多归并
- `trace_event` 负责记录一次留痕事实
- `evidence_image` 负责记录一张留痕图片及其对象存储信息
- `event_outbox` 负责把业务事件可靠送出去

一句话总结：

**运单是主对象，留痕事件是过程对象，图片是证据对象。**

---

## 2. 命名建议

为了让名字更好懂，我建议：

- 物理表名直接用短英文
- Odoo 模型名可以继续保留命名空间

例如：

```text
模型名: logistics.waybill
表名: waybill

模型名: logistics.trace.event
表名: trace_event

模型名: logistics.evidence.image
表名: evidence_image
```

这样有几个好处：

- 数据库层好看、好查、好写 SQL
- Odoo 层仍然不会和原生模型冲突
- 团队沟通时不用总说很长的前缀名

---

## 3. 设计原则

这几张表设计时，建议始终守住下面几个原则：

- 运单号是主对象，不是订单
- 留痕按事件组织，不把图片直接挂在运单主表上
- 图片只存元数据和对象键，不存大二进制
- 高频查询优先按“店铺、日期、批次、运单号、司机、车辆”建索引
- 状态值尽量短，小词汇，少层级

这里统一约定：

- `state`：生命周期状态
- `trace_type`：留痕类型
- `source_app`：数据来自后台还是小程序

---

## 4. 表关系总览

推荐按这条关系组织：

```text
stock_picking_batch
  -> waybill
     -> waybill_order
        -> sale_order
     -> trace_event
        -> evidence_image
```

如果从业务层理解：

```text
批次
  -> 多个运单
     -> 每个运单对应多个订单
     -> 每个运单产生多次留痕事件
        -> 每次留痕事件包含多张图片
```

同时还要支持：

- 批次级留痕事件
- 运单级留痕事件

所以 `trace_event` 既能挂 `batch_id`，也能挂 `waybill_id`。

## 5. 推荐状态与类型枚举

## 5.1 `waybill.state`

建议只保留：

- `new`
- `ready`
- `going`
- `done`
- `cancel`

解释：

- `new`：刚生成
- `ready`：已分配批次和路线，待装车/待出发
- `going`：配送中
- `done`：本运单交付完成
- `cancel`：取消

## 5.2 `trace_event.state`

建议只保留：

- `new`
- `done`
- `void`

解释：

- `new`：已创建，还没最终提交
- `done`：已提交完成
- `void`：作废

## 5.3 `evidence_image.state`

建议只保留：

- `new`
- `ok`
- `bad`
- `del`

解释：

- `new`：刚上传或待校验
- `ok`：校验通过，可正常使用
- `bad`：损坏、丢失、校验失败
- `del`：业务删除标记

## 5.4 `trace_event.trace_type`

建议第一阶段先只保留这些：

- `sort`
- `load`
- `arrive`
- `sign`
- `except`

解释：

- `sort`：分拣留痕
- `load`：装车留痕
- `arrive`：到店/交接留痕
- `sign`：签收留痕
- `except`：异常留痕

这个集合已经能覆盖你现在最真实的流程，而且足够好懂。

## 6. `waybill` 表设计

`waybill` 是最重要的主表。

它负责表达：

- 某天
- 某店铺
- 某次配送
- 该店铺这次配送下的一组订单

## 6.1 建表 SQL

```sql
create table if not exists waybill (
    id integer generated by default as identity primary key,
    waybill_no varchar(40) not null,
    biz_date date not null,
    company_id integer not null,

    store_id integer not null,
    store_code varchar(64),
    store_name varchar(128) not null,

    batch_id integer,
    warehouse_id integer,
    dock_id integer,
    vehicle_id integer,
    driver_id integer,

    route_no integer,
    stop_no integer,

    order_count integer not null default 0,
    item_count numeric(14, 3) not null default 0,
    total_weight numeric(14, 3) not null default 0,
    total_volume numeric(14, 3) not null default 0,

    state varchar(16) not null default 'new',
    has_exception boolean not null default false,

    load_trace_state varchar(16) not null default 'new',
    store_trace_state varchar(16) not null default 'new',
    sign_trace_state varchar(16) not null default 'new',

    plan_depart_at timestamp,
    plan_arrive_at timestamp,
    real_depart_at timestamp,
    real_arrive_at timestamp,
    real_done_at timestamp,

    note text,
    create_uid integer,
    write_uid integer,
    create_date timestamp not null default now(),
    write_date timestamp not null default now(),

    constraint uk_waybill_no unique (waybill_no),
    constraint ck_waybill_state check (state in ('new', 'ready', 'going', 'done', 'cancel')),
    constraint ck_waybill_load_trace_state check (load_trace_state in ('new', 'done', 'void')),
    constraint ck_waybill_store_trace_state check (store_trace_state in ('new', 'done', 'void')),
    constraint ck_waybill_sign_trace_state check (sign_trace_state in ('new', 'done', 'void')),

    constraint fk_waybill_store
        foreign key (store_id) references res_partner(id),
    constraint fk_waybill_batch
        foreign key (batch_id) references stock_picking_batch(id),
    constraint fk_waybill_warehouse
        foreign key (warehouse_id) references stock_warehouse(id),
    constraint fk_waybill_dock
        foreign key (dock_id) references stock_location(id),
    constraint fk_waybill_vehicle
        foreign key (vehicle_id) references fleet_vehicle(id),
    constraint fk_waybill_driver
        foreign key (driver_id) references res_partner(id)
);
```

## 6.2 字段解释

这里最关键的字段是：

- `waybill_no`：运单号，业务唯一编号
- `biz_date`：业务日期，绝大多数查询都会带它
- `store_id`：店铺
- `batch_id`：所属批次
- `dock_id`：装车地库 / 装车位
- `vehicle_id` / `driver_id`：配送执行人和车
- `route_no` / `stop_no`：线路顺序
- `order_count` / `total_weight` / `total_volume`：调度结果聚合值

`store_code`、`store_name` 建议保留冗余，不要每次列表都去 join `res_partner` 才能显示。

## 7. `waybill_order` 表设计

虽然你主要问三张表，但这张关系表实际上是必须的。

因为一个运单下会有多个订单，而一个订单在当前设计里通常只归属一个运单。

## 7.1 建表 SQL

```sql
create table if not exists waybill_order (
    id integer generated by default as identity primary key,
    waybill_id integer not null,
    order_id integer not null,
    company_id integer not null,
    biz_date date not null,
    store_id integer not null,
    batch_id integer,
    create_date timestamp not null default now(),

    constraint uk_waybill_order unique (waybill_id, order_id),
    constraint fk_waybill_order_waybill
        foreign key (waybill_id) references waybill(id) on delete cascade,
    constraint fk_waybill_order_order
        foreign key (order_id) references sale_order(id),
    constraint fk_waybill_order_store
        foreign key (store_id) references res_partner(id),
    constraint fk_waybill_order_batch
        foreign key (batch_id) references stock_picking_batch(id)
);
```

## 7.2 这张表为什么必要

它主要解决：

- 从运单展开订单列表
- 从订单反查运单
- 查询某店铺某天全部订单归在哪些运单下
- 后面如果调度重排或改单，也能做清晰调整

## 8. `trace_event` 表设计

`trace_event` 是过程主表。

它不直接表达“结果”，而是表达“一次留痕事实”。

例如：

- 分拣拍照一次
- 装车拍照一次
- 到店交接拍照一次
- 异常上报一次

## 8.1 建表 SQL

```sql
create table if not exists trace_event (
    id integer generated by default as identity primary key,
    event_no varchar(40) not null,
    company_id integer not null,
    biz_date date not null,

    biz_level varchar(16) not null,
    trace_type varchar(16) not null,
    state varchar(16) not null default 'new',

    batch_id integer,
    waybill_id integer,
    store_id integer,
    warehouse_id integer,
    dock_id integer,
    vehicle_id integer,
    driver_id integer,

    source_app varchar(16) not null default 'admin',
    operator_id integer,
    operator_name varchar(64),

    image_count integer not null default 0,
    note text,

    event_time timestamp not null,
    done_time timestamp,
    create_date timestamp not null default now(),
    write_date timestamp not null default now(),

    constraint uk_trace_event_no unique (event_no),
    constraint ck_trace_event_biz_level check (biz_level in ('batch', 'waybill')),
    constraint ck_trace_event_type check (trace_type in ('sort', 'load', 'arrive', 'sign', 'except')),
    constraint ck_trace_event_state check (state in ('new', 'done', 'void')),
    constraint ck_trace_event_source_app check (source_app in ('admin', 'mini', 'open')),
    constraint ck_trace_event_biz_ref check (
        (biz_level = 'batch' and batch_id is not null)
        or
        (biz_level = 'waybill' and waybill_id is not null)
    ),

    constraint fk_trace_event_batch
        foreign key (batch_id) references stock_picking_batch(id),
    constraint fk_trace_event_waybill
        foreign key (waybill_id) references waybill(id) on delete cascade,
    constraint fk_trace_event_store
        foreign key (store_id) references res_partner(id),
    constraint fk_trace_event_warehouse
        foreign key (warehouse_id) references stock_warehouse(id),
    constraint fk_trace_event_dock
        foreign key (dock_id) references stock_location(id),
    constraint fk_trace_event_vehicle
        foreign key (vehicle_id) references fleet_vehicle(id),
    constraint fk_trace_event_driver
        foreign key (driver_id) references res_partner(id),
    constraint fk_trace_event_operator
        foreign key (operator_id) references res_users(id)
);
```

## 8.2 字段解释

这里最关键的是：

- `biz_level`：到底是批次级还是运单级
- `trace_type`：分拣、装车、到店、签收、异常
- `event_no`：事件编号
- `event_time`：事件发生时间
- `source_app`：后台还是小程序

为什么要有 `biz_level`：

- 因为你现在既有批次级装车前留痕
- 也有运单级门店到货留痕

这两个场景不能混成一个字段猜。

## 9. `evidence_image` 表设计

`evidence_image` 是图片主表。

它负责描述一张图片的业务归属和对象存储信息。

注意：

- 不存图片二进制
- 只存元数据和对象键

## 9.1 建表 SQL

```sql
create table if not exists evidence_image (
    id integer generated by default as identity primary key,
    image_no varchar(40) not null,
    company_id integer not null,
    biz_date date not null,

    trace_event_id integer not null,
    batch_id integer,
    waybill_id integer,
    store_id integer,

    source_app varchar(16) not null default 'admin',
    image_type varchar(16) not null default 'raw',
    state varchar(16) not null default 'new',

    bucket_name varchar(64) not null,
    object_key varchar(255) not null,
    preview_key varchar(255),
    thumb_key varchar(255),

    file_name varchar(255),
    mime_type varchar(64),
    file_ext varchar(16),
    file_size bigint not null default 0,
    width integer,
    height integer,
    checksum varchar(64),

    sort_no integer not null default 1,
    taken_at timestamp,
    uploaded_at timestamp,
    note text,

    create_date timestamp not null default now(),
    write_date timestamp not null default now(),

    constraint uk_evidence_image_no unique (image_no),
    constraint ck_evidence_image_source_app check (source_app in ('admin', 'mini', 'open')),
    constraint ck_evidence_image_type check (image_type in ('raw', 'preview', 'thumb')),
    constraint ck_evidence_image_state check (state in ('new', 'ok', 'bad', 'del')),

    constraint fk_evidence_image_event
        foreign key (trace_event_id) references trace_event(id) on delete cascade,
    constraint fk_evidence_image_batch
        foreign key (batch_id) references stock_picking_batch(id),
    constraint fk_evidence_image_waybill
        foreign key (waybill_id) references waybill(id) on delete cascade,
    constraint fk_evidence_image_store
        foreign key (store_id) references res_partner(id)
);
```

## 9.2 字段解释

最关键的字段是：

- `trace_event_id`：这张图属于哪次留痕事件
- `bucket_name` / `object_key`：对象存储位置
- `preview_key` / `thumb_key`：后台查看用
- `checksum`：做校验和去重
- `sort_no`：一组图的顺序
- `taken_at`：拍摄时间

如果门店留痕是多张图，这张表正好支撑：

- 一次事件
- 多张图片
- 按顺序展示

## 10. `event_outbox` 表设计

如果你们决定走事件驱动，这张表非常建议有。

它不是业务主表，但能大幅减少：

- 业务写库成功但消息没发出去
- 消息发了但业务表没落成

这类问题。

## 10.1 建表 SQL

```sql
create table if not exists event_outbox (
    id integer generated by default as identity primary key,
    event_name varchar(80) not null,
    biz_key varchar(80) not null,
    biz_type varchar(32) not null,
    payload jsonb not null,
    state varchar(16) not null default 'new',
    retry_count integer not null default 0,
    next_retry_at timestamp,
    sent_at timestamp,
    create_date timestamp not null default now(),

    constraint ck_event_outbox_state check (state in ('new', 'done', 'fail'))
);
```

## 12. 事件设计

如果你们走事件驱动，我建议事件名也用简单短英文。

不要用太长、太抽象的名字。

推荐事件分 4 类：

- 调度事件
- 运单事件
- 留痕事件
- 图片事件

## 12.1 调度事件

建议事件名：

- `dispatch.done`
- `batch.ready`
- `route.set`

解释：

- `dispatch.done`：调度求解已完成，产出批次、门店顺序、车辆分配
- `batch.ready`：某个批次已确认可执行
- `route.set`：批次或运单路线顺序已写定

其中最关键的是 `dispatch.done`。

它可以驱动：

- 创建 / 更新 `waybill`
- 写入 `waybill_order`
- 更新批次、车辆、地库、顺序字段

## 12.2 运单事件

建议事件名：

- `waybill.upsert`
- `waybill.orders_bind`
- `waybill.go`
- `waybill.done`
- `waybill.cancel`

解释：

- `waybill.upsert`：创建或更新运单主数据
- `waybill.orders_bind`：订单归并到运单
- `waybill.go`：运单进入配送中
- `waybill.done`：运单完成
- `waybill.cancel`：运单取消

## 12.3 留痕事件

建议事件名：

- `trace.add`
- `trace.done`
- `trace.void`

配合 `trace_type` 使用。

例如：

- `trace.add` + `trace_type=load`
- `trace.add` + `trace_type=arrive`

这样事件名不会爆炸，业务含义也清楚。

## 12.4 图片事件

建议事件名：

- `image.add`
- `image.ok`
- `image.bad`
- `image.del`

解释：

- `image.add`：新增图片元数据
- `image.ok`：图片校验通过
- `image.bad`：图片损坏或校验失败
- `image.del`：删除标记

## 13. 推荐的事件驱动落库顺序

这里给你一个最贴近当前业务的版本。

## 13.1 调度完成后

```text
dispatch.done
  -> upsert waybill
  -> bind waybill_order
  -> set batch / vehicle / driver / dock / stop_no
  -> emit batch.ready
```

## 13.2 仓内分拣或装车留痕

```text
trace.add (trace_type=sort or load, biz_level=batch)
  -> insert trace_event

image.add
  -> insert evidence_image

trace.done
  -> update trace_event.state=done
  -> update related waybill.load_trace_state=done
```

## 13.3 门店轻量留痕

```text
trace.add (trace_type=arrive, biz_level=waybill)
  -> insert trace_event

image.add
  -> insert evidence_image (multiple rows)

trace.done
  -> update trace_event.state=done
  -> update waybill.store_trace_state=done
  -> if delivery finished then emit waybill.done
```

## 14. 事件 payload 建议

为了让消费端简单，我建议 payload 里尽量总是带这些基础键：


## 15. 这些表为什么能扛住你当前最常用的查询

这套设计主要就是为了扛下面这些查询：

- 按店铺查最近 30 天所有运单
- 按批次查全部运单
- 按运单号查详情
- 从运单展开订单列表
- 查看运单时间线
- 查看某次留痕下的全部图片
- 按司机 / 车辆查当天执行记录
- 按地库查看当前装车组织

它和 Odoo 原生结构的分工是：

- Odoo 原生负责订单、批次、车辆、仓库
- 你自定义表负责运单、留痕、证据

这样能避免后面每次都从很多原生表临时拼一大串查询。

## 16. 最终建议

如果你现在准备正式进入开发，我建议直接采用下面这套组合：

1. 主业务表用 `waybill`
2. 订单归并表用 `waybill_order`
3. 留痕过程表用 `trace_event`
4. 图片证据表用 `evidence_image`
5. 事件可靠投递用 `event_outbox`
6. 事件名统一用短英文，如 `dispatch.done`、`trace.add`、`image.add`

一句话总结：

**表名尽量短，状态尽量少，事件尽量直白；运单是主对象，事件是过程，图片是证据。**
