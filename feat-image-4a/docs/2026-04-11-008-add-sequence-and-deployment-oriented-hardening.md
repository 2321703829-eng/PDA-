# 2026-04-11-008 Add Sequence and Deployment-Oriented Hardening

## 背景
在完成第一轮命名与状态机纠偏后，`feat-image-4a` 还缺几项更适合真正落地部署的基础能力：

- 标准 Odoo 编号
- 上传完成后的业务状态推进
- 更明确的上传类型约束
- 更贴近当前口径的接入与验收说明

## 本次改动

### 1. 为留痕和证据对象补标准编号
新增了 Odoo `ir.sequence`：

- `logistics.trace.event`
- `logistics.trace.evidence`

对应前缀：

- `TR`
- `EV`

现在创建留痕事件和证据对象时，如果没有手工填写名称，会自动生成符合当前规范方向的编号。

### 2. 上传向导补业务约束
上传向导现在会校验：

- 只有 `image` / `sign` 类型证据支持图片上传

同时在成功上传后：

- 自动创建图片引用记录
- 自动回写 `captured_at`
- 如果证据还处于 `new`，自动推进到 `ok`

### 3. 图片引用唯一性增强
对 `image_access_key` 增加唯一约束，避免同一访问键被重复写入多条记录。

### 4. 去除无效外部依赖声明
由于当前实现已经不再依赖 `requests` 去访问外部图片服务，移除了 manifest 中不再准确的 Python 依赖声明。

### 5. 更新当前接入文档
重写了这两份文档，使其更符合当前真实实现：

- `接入与验收说明.md`
- `协作边界说明.md`

重点强调：

- 最终数据库由你们自己创建
- 最终部署由你们自己完成
- 图片落服务器侧目录，不走 Odoo 默认附件图片存储
- 最终与其他同事的 `feat` 模块一起总装验收

## 当前结果
本轮之后，`feat-image-4a` 更接近一个可并入总装环境的 Odoo 功能包，而不是只完成一半的原型：

- 有编号
- 有真实上传
- 有真实存储
- 有真实预览 / 下载
- 有更明确的部署前提和验收步骤
