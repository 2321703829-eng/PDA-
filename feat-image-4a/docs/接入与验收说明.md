# feat-image-4a 接入与验收说明

## 文档目的
本文档用于说明 `feat-image-4a` 这条功能线如何接入最终 Odoo 环境，以及后续在你们自建数据库、自行部署到服务器后的验收方式。

## 当前包含的模块
- `feat-image-4a/addons/logistics_trace_core`
- `feat-image-4a/addons/logistics_trace_evidence`

这两个目录都是标准 Odoo addon，不是独立服务。

## 接入原则
- 最终运行环境是 Odoo，不是独立图片系统。
- 最终数据库由你们自己创建。
- 最终部署由你们自己在服务器上完成。
- `feat-image-4a` 通过 `addons_path` 接入 Odoo。
- 图片二进制不走 Odoo 默认附件图片存储。
- 图片文件落在服务器侧存储目录，Odoo 只保存业务关系和元数据。

## 业务挂接规则
当前图片能力只处理批次号和运单号两类业务主体：

- 装车前类图片：挂批次号
- 到店、签收、异常取证类图片：挂运单号
- 订单号：不是图片上传主挂接键

## 服务器部署前提
后续部署时，至少需要准备：

1. 一套可运行的 Odoo 环境
2. 你们自己的数据库
3. 一个服务器侧图片存储目录
4. Odoo 可访问的公网或内网基础地址

## 模块接入方式
建议最终总装目录保持：

```text
odoo/
  feat-a/addons/
  feat-b/addons/
  feat-image-4a/addons/
```

然后把多个 `feat-*/addons/` 一起加入 Odoo 的 `addons_path`。

## 安装顺序建议
1. 更新应用列表
2. 安装 `Logistics Trace Core`
3. 安装 `Logistics Trace Evidence`

## 安装后必须配置的参数
安装完成后，在 Odoo 设置页配置：

- `Image Public Base URL`
- `Image Storage Root`

对应参数：

- `logistics_trace_evidence.image_public_base_url`
- `logistics_trace_evidence.image_storage_root`

说明：
- `Image Public Base URL` 用于生成预览和下载链接
- `Image Storage Root` 是服务器上的真实图片存储根目录

## 当前已实现的真实能力
这条线当前已经具备：

- 创建批次级 / 运单级留痕事件
- 在留痕事件下创建证据对象
- 上传真实图片到服务器侧目录
- 为图片生成 `image_access_key`
- 创建图片引用记录
- 回写文件类型、大小、存储路径、存储状态
- 从 Odoo 打开图片预览和下载
- 提供小程序可调用的留痕创建、站点查询、图片上传 HTTP 路由

## 当前可用于联调的图片接口
当前图片相关接口包括：

1. 创建留痕事件接口
- `POST /api/mini/logistics/traces`
- 请求体：`application/json`
- 鉴权方式：
  - 走 Odoo 后台登录态
  - 需要先完成 `/web/session/authenticate`
  - 后续请求必须带同一个 `session_id` cookie
- 最小必填：
  - `biz_type`
  - `waybill_no` 或 `batch_no`
- 默认：
  - `trace_type = arrive`
  - `trace_source = mini`
- 说明：
  - 仓库装车场景可直接传 `trace_type = load`
  - 车辆离场场景可直接传 `trace_type = leave`
  - 目前也支持 `location_text`、`route_sequence`

成功返回示例：

```json
{
  "ok": true,
  "message": "Trace event created successfully.",
  "data": {
    "trace_event_id": 11,
    "trace_no": "TR20260413-0001",
    "biz_type": "waybill",
    "trace_type": "arrive",
    "batch_no": null,
    "waybill_no": "WB20260413001",
    "state": "new"
  }
}
```

2. 运单站点查询接口
- `GET /api/mini/logistics/waybills/<waybill_no>/stops`
- 鉴权方式：
  - 走 Odoo 后台登录态
  - 需要先完成 `/web/session/authenticate`
  - 后续请求必须带同一个 `session_id` cookie
- 作用：
  - 返回运单对应的站点列表、联系人、指引链接、货物信息和当前状态
  - 当前口径改为：先读取稳定的 `waybill stop` 站点定义，再叠加 `trace` 留痕状态
  - `trace` 只用于更新站点状态，不再反向生成站点，避免 `location_text` 被误识别成新门店
- 前置写入接口：
  - `POST /api/mini/logistics/waybills/<waybill_no>/stops`
  - 请求体：`application/json`
  - 作用：由调度侧或后续主链模块写入运单站点定义
- `status` 当前细化口径：
  - `PENDING`：还没有相关留痕
  - `CURRENT`：已有 `load`，但还没有 `leave`
  - `LEAVED`：已有 `leave`，但还没有 `arrive`
  - `ARRIVED`：已有 `arrive`，但还没有 `sign`
  - `COMPLETED`：已有 `sign`
  - `EXCEPTION`：已有异常留痕

成功返回示例：

```json
{
  "ok": true,
  "data": {
    "waybill_no": "WB20260413001",
    "batch_no": "BT20260413001",
    "driver_name": "张三",
    "vehicle_no": "粤A12345",
    "stops": [
      {
        "node_id": 1,
        "stop_seq": 1,
        "store_name": "XX便利店",
        "address": "广州市XX路XX号",
        "lat": 23.137588,
        "lng": 113.328755,
        "contact_name": "李店长",
        "contact_phone": "13800001111",
        "contact_list": [
          { "name": "李店长", "phone": "13800001111" },
          { "name": "王副店长", "phone": "13800002222" }
        ],
        "guide_url": "https://docs.qq.com/xxx",
        "goods_info": "冰鲜海产 x 2箱",
        "status": "PENDING"
      }
    ]
  }
}
```

3. 创建证据对象接口
- `POST /api/mini/logistics/evidences`
- 请求体：`application/json`
- 鉴权方式：
  - 走 Odoo 后台登录态
  - 需要先完成 `/web/session/authenticate`
  - 后续请求必须带同一个 `session_id` cookie
- 最小必填：
  - `trace_id`
- 默认：
  - `evidence_type = image`

成功返回示例：

```json
{
  "ok": true,
  "message": "Evidence created successfully.",
  "data": {
    "evidence_id": 12,
    "evidence_no": "EV20260413-0001",
    "trace_event_id": 11,
    "trace_no": "TR20260413-0001",
    "evidence_type": "image",
    "state": "new"
  }
}
```

4. 图片读取接口
- `GET /logistics_trace/evidence-images/<image_access_key>`
- 用于预览图片
- `?download=true` 时按下载返回文件

5. 小程序图片上传接口
- `POST /api/mini/logistics/evidences/<evidence_id>/images`
- 请求方式：`multipart/form-data`
- 鉴权方式：
  - 走 Odoo 后台登录态
  - 需要先完成 `/web/session/authenticate`
  - 后续请求必须带同一个 `session_id` cookie
- 文件字段名：`file`
- 作用：把图片上传到服务器存储目录，并自动创建图片引用记录

成功返回示例：

```json
{
  "ok": true,
  "message": "Image uploaded successfully.",
  "data": {
    "evidence_id": 12,
    "image_id": 34,
    "image_access_key": "img_xxx",
    "preview_url": "http://host/logistics_trace/evidence-images/img_xxx",
    "download_url": "http://host/logistics_trace/evidence-images/img_xxx?download=true",
    "storage_status": "active"
  }
}
```

## 验收步骤建议
1. 在 Odoo 环境中把 `feat-image-4a/addons/` 加入 `addons_path`
2. 更新应用列表
3. 安装：
   - `Logistics Trace Core`
   - `Logistics Trace Evidence`
4. 在设置页配置：
   - `Image Public Base URL`
   - `Image Storage Root`
5. 点击 `Test Image Storage`
6. 创建一条批次级或运单级留痕事件
7. 创建一条证据对象
8. 通过上传向导上传真实图片
9. 打开 `Evidence Images` 列表确认图片引用记录已生成
10. 点击预览或下载，确认 Odoo 返回的是真实图片内容
11. 到服务器目录中确认真实图片文件确实已落盘
12. 确认 Odoo 中保存的是关系和元数据，而不是默认附件图片二进制

如果做小程序联调，建议顺序改为：

1. `POST /web/session/authenticate`
2. 登录时固定 `db = logistics_trace_real`
3. 保留登录返回的 `session_id` cookie
4. `POST /api/mini/logistics/traces`
5. `GET /api/mini/logistics/waybills/<waybill_no>/stops`
6. `POST /api/mini/logistics/evidences`
7. `POST /api/mini/logistics/evidences/<evidence_id>/images`

说明：
- 这 3 个 POST 接口当前仍然是 `auth="user"`
- 小程序不需要额外的独立 token
- 服务器是多库环境，登录时必须显式指定 `logistics_trace_real`
- 如果没有先登录，或者 session 没绑定到正确数据库，就可能出现 `404`

登录请求示例：

```json
POST /web/session/authenticate
{
  "jsonrpc": "2.0",
  "method": "call",
  "params": {
    "db": "logistics_trace_real",
    "login": "your_login",
    "password": "your_password"
  }
}
```

## 当前验收重点
验收时重点看这几件事：

1. 模块是否能正常安装
2. 字段命名和页面是否符合统一规范
3. 图片是否按批次号 / 运单号挂接
4. 上传是否走真实存储，不是 mock
5. 预览和下载是否真实可用
6. 是否没有把图片二进制塞进 Odoo 默认图片附件存储

## 当前已知边界
- 当前不实现波次主对象
- 当前批次号、运单号仍是编号字段挂接，不是最终正式外键
- 当前不实现调度主流程
- 当前不实现司机端完整页面
- 当前不实现后台总追溯首页

## 当前结论
`feat-image-4a` 的正确验收方式不是单独跑，而是：

**作为一组标准 Odoo addon 接入最终 Odoo 环境，并和其他同事的 `feat` 模块一起完成总装验收。**
