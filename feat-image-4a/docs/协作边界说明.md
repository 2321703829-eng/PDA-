# feat-image-4a 协作边界说明

## 功能线定位
`feat-image-4a` 是 4.3 分工下“留痕与证据中心”中的图片能力子线。

这条线负责的是 Odoo 里的图片证据能力，不是独立图片系统，也不是总装仓库本身。

## 当前负责范围
- 批次级、运单级留痕事件的基础对象
- 留痕事件下的证据对象
- 证据对象下的图片引用记录
- Odoo 后台图片上传
- 图片元数据同步
- 图片预览 / 下载入口
- 服务器侧图片真实存储

## 当前不负责
- 波次主对象
- 批次、运单正式主对象
- 调度与排线
- 司机端完整交互页面
- 后台全局追溯首页
- Discuss / Calendar / CRM / OA 等非当前范围模块

## 当前主链理解
基于已读规范，当前按下面这条主链理解并落模块：

```text
波次记录 -> 批次 -> 运单号 -> 运单下订单列表 -> 留痕事件 -> 证据图片/备注
```

对 `feat-image-4a` 的直接影响：

- 波次：当前不实现
- 批次：作为装车前类图片挂接主体
- 运单：作为到店、签收、异常取证类图片挂接主体
- 订单：不是图片主挂接键

## 当前技术边界
- 所有代码都必须写成标准 Odoo addon
- 最终必须通过 `addons_path` 接入 Odoo
- 最终必须适配你们自己创建的数据库
- 最终必须能部署到你们自己的服务器
- 图片二进制必须落在服务器侧目录
- Odoo 只维护业务关系、访问键和元数据

## 与 image-manager-main 的关系
`image-manager-main` 只作为能力参照标准。

当前真正要求是：

- 在 `feat-image-4a` 里把 Odoo 侧需要的图片能力实现出来
- 后续即使没有 `image-manager-main` 目录，这条线也要能在 Odoo 中运行
- 你们上服务器时只需要准备数据库、Odoo 环境和服务器存储目录

## 当前已具备的真实能力
- 真实写入服务器存储目录
- 真实生成 `image_access_key`
- 真实生成图片引用记录
- 真实读取服务器文件
- 真实生成预览 / 下载 URL
- 真实通过 Odoo HTTP 路由返回图片内容

当前图片访问路由：

- `/logistics_trace/evidence-images/<image_access_key>`

## 对其他功能线的依赖
- 调度线后续需要提供正式的批次 / 运单主对象
- 司机端线后续需要提供按运单上传留痕的交互入口
- 后台线后续需要把证据能力接进全局追溯页面

## 对其他功能线提供的能力
- `logistics_trace_core`
  - 批次级 / 运单级留痕事件对象
- `logistics_trace_evidence`
  - 证据对象
  - 图片引用对象
  - 上传向导
  - 元数据同步
  - 图片预览 / 下载入口

## 最终协作方式
这条线最终不是单独验收，而是和大家各自的 `feat` 文件夹一起并入 Odoo。

推荐总装方式：

```text
odoo/
  feat-xxx/addons/
  feat-yyy/addons/
  feat-image-4a/addons/
```

再由总装环境统一把多个 `feat-*/addons/` 加入 `addons_path`。

## 当前验收关注点
1. `logistics_trace_core` 和 `logistics_trace_evidence` 能否正常安装
2. 能否创建批次级 / 运单级留痕事件
3. 能否创建证据对象
4. 能否上传真实图片到服务器侧目录
5. 能否生成图片引用和元数据
6. 能否从 Odoo 打开预览和下载
7. 图片二进制是否确实没有走 Odoo 默认附件图片存储方式

## 当前协作结论
`feat-image-4a` 的目标不是替代 Odoo，而是以 Odoo 兼容方式，为最终物流留痕系统补齐图片证据能力。
后续所有实现都应继续围绕这个边界推进。
