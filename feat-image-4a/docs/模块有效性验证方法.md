# feat-image-4a 模块有效性验证方法

## 目的
这份文档用于帮助你验证当前负责的模块是否：

- 有效
- 可安装
- 符合当前规范
- 适合后续和同事模块一起并入 Odoo 总装环境

这份验证方法只覆盖你当前负责的模块功能，不包含前端整体页面验收。

## 验证结论标准
你这条线最终要满足 4 个层面的要求：

1. 结构上符合 Odoo addon 规范
2. 语义上符合 `odoo-reconstruct-main` 的命名和边界要求
3. 功能上能真实完成图片证据能力
4. 部署上适合后续自建数据库和上服务器

只要这 4 层同时通过，这条线就可以认为是“有效并且基本符合当前要求”。

## 第一层：结构验证
先验证目录结构是否正确。

当前应确认：

- [logistics_trace_core](D:/桌面/odoo/feat-image-4a/addons/logistics_trace_core)
- [logistics_trace_evidence](D:/桌面/odoo/feat-image-4a/addons/logistics_trace_evidence)

每个模块都应包含：

- `__manifest__.py`
- `models/`
- `views/`
- `security/`

`logistics_trace_evidence` 额外应有：

- `wizards/`
- `controllers/`
- `services/`
- `tests/`

通过标准：

- 模块目录完整
- 没有把代码散落到 `odoo/addons` 公共目录
- 代码全部仍在 `feat-image-4a/addons/` 下

## 第二层：规范验证
这一层重点看是否符合项目文档要求。

### 1. 命名是否正确
你要重点核对下面这些：

- 模块名使用 `logistics_` 前缀
- 留痕模型：`logistics.trace.event`
- 证据模型：`logistics.trace.evidence`
- 业务类型字段：`biz_type`
- 留痕类型字段：`trace_type`
- 留痕来源字段：`trace_source`
- 状态字段：`state`

### 2. 状态机是否正确
当前应核对：

- 留痕事件：`new / done / void`
- 证据对象：`new / ok / bad / del`

### 3. 业务主体是否正确
当前应确认：

- 图片主挂接键不是订单号
- 批次类图片挂批次号
- 到店 / 签收 / 异常类图片挂运单号

### 4. 图片存储方式是否正确
当前应确认：

- 图片二进制不走 Odoo 默认附件图片存储
- 图片真实落在服务器存储目录
- Odoo 只保存：
  - `image_access_key`
  - 文件名
  - 类型
  - 存储路径
  - 存储状态
  - 批次号 / 运单号业务关系

## 第三层：模块安装验证
这一步是最关键的可行性验证。

你们后续自己建数据库后，在 Odoo 环境中按下面步骤验证：

1. 把 `feat-image-4a/addons/` 加入 `addons_path`
2. 更新应用列表
3. 安装：
   - `Logistics Trace Core`
   - `Logistics Trace Evidence`

通过标准：

- 模块能正常出现在应用列表中
- 模块能安装成功
- 没有字段不存在、XML 视图报错、模型加载失败

如果这一步失败，优先检查：

- `__manifest__.py`
- `models/__init__.py`
- `controllers/__init__.py`
- 视图里引用的字段名是否真实存在

## 第四层：后台功能验证
这一步只测你负责的功能，不测整体前端。

### 场景 A：创建运单级留痕
1. 进入 `Logistics Trace`
2. 新建一条留痕事件
3. `biz_type` 选 `waybill`
4. 填运单号
5. `trace_type` 选 `arrive` 或 `sign`
6. 保存

通过标准：

- 能保存成功
- 自动生成编号或手工名称有效
- 不要求订单号

### 场景 B：创建批次级留痕
1. 新建一条留痕事件
2. `biz_type` 选 `batch`
3. 填批次号
4. `trace_type` 选 `load`
5. 保存

通过标准：

- 能保存成功
- 不要求运单号

### 场景 C：错误主体校验
分别做两次错误输入：

1. `biz_type = batch`，却填写运单号
2. `biz_type = waybill`，却填写批次号

通过标准：

- 系统阻止保存
- 有明确校验错误

### 场景 D：创建证据对象
1. 进入某条留痕事件
2. 新建证据对象
3. `evidence_type` 选 `image`
4. 保存

通过标准：

- 能正常创建
- 证据对象自动继承批次号或运单号
- `trace_id` 关系正确

### 场景 E：真实上传图片
1. 打开证据对象
2. 进入上传向导
3. 选择一张真实图片
4. 点击上传

通过标准：

- 上传成功
- 生成 `image_access_key`
- 生成图片引用记录
- 证据状态从 `new` 进入 `ok`

### 场景 F：校验真实落盘
上传后到服务器目录检查：

- `Image Storage Root` 对应目录下是否出现真实文件

通过标准：

- 文件真实存在
- 文件大小与上传图片基本一致
- 不是只写了数据库记录

### 场景 G：预览和下载
1. 在 `Evidence Images` 列表打开图片详情
2. 点击 `Open Preview`
3. 点击 `Open Download`

通过标准：

- 能打开真实图片
- 下载返回真实文件
- 访问路径命中 Odoo 路由：
  - `/logistics_trace/evidence-images/<image_access_key>`

## 第五层：是否没有误用 Odoo 图片附件存储
这一点很重要。

你要重点确认：

- 上传图片后，不是靠 Odoo 默认产品图片 / 附件图片字段保存二进制
- `file_data` 只出现在 wizard 临时表单中，而且设置了 `attachment=False`
- 真正落盘位置是服务器存储目录

通过标准：

- 图片上传后能在服务器目录找到真实文件
- 业务主表里只看到元数据，不看到 Odoo 默认图片附件方案的依赖设计

## 第六层：协作验证
这一步是为了确认后面能和同事模块一起合库。

你要确认：

- 代码全部在 `feat-image-4a/addons/`
- 文档全部在 `feat-image-4a/docs/`
- 没有把功能偷偷写进 Odoo 公共 `addons/`
- 没有依赖 `image-manager-main` 目录存在
- 没有依赖我本地临时数据库

通过标准：

- 把这条 `feat` 目录单独交给同事时，结构清楚
- 总装时只需要把 `addons_path` 配进去

## 当前我认为已经通过的部分
按当前代码状态，已经可以认为这几项基本通过：

- 结构符合 Odoo addon 方式
- 命名和状态机已基本收口
- 图片真实落服务器侧目录
- 预览 / 下载入口已补齐
- 上传流程不依赖 mock

## 当前仍建议重点关注的点
你后面验证时，最值得盯紧的是：

1. 模块真实安装时的 XML 和字段加载
2. 服务器图片目录权限是否正确
3. `Image Public Base URL` 是否配置准确
4. 你们最终数据库环境下是否还有其他同事模块字段名冲突

## 最后判断方式
如果下面这些都成立，就可以说你负责的模块是“有效并且基本严格符合当前要求”：

1. 模块能安装
2. 留痕和证据对象能创建
3. 图片能真实上传并落服务器目录
4. 图片按批次号 / 运单号挂接，而不是订单号
5. 预览和下载能打开真实文件
6. 不依赖 `image-manager-main` 目录运行
7. 最终能作为标准 Odoo addon 并入总装环境
